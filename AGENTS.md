# AGENT RULES

Правила обязательны для любого AI-агента (Claude Code, Codex, Cursor) и для человека.
Нарушение правила — основание отклонить работу целиком, даже если код рабочий.

---

## 1. Plan before implementation

Если задача изменяет больше одной функции, таблицу БД, API-контракт,
интеграцию или пользовательский сценарий — **сначала предоставить план**.

До подтверждения плана не создавать и не изменять код.

Причина: план исправляется сообщением; ошибочная реализация — часами или днями.

---

## 2. Data model is controlled by DATA_MODEL.md

Любое изменение:

- сущности;
- поля;
- связи;
- cardinality;
- reservation allocation;
- pricing;
- folio

сначала предлагается в `DATA_MODEL.md`.
Только после утверждения меняются schema / migration / code.

---

## 3. Architecture decisions must be recorded

Каждое архитектурное решение записывать своим файлом `docs/decisions/ГГГГ-ММ-ДД-<ветка>.md` (§21; до 19.10.2026
решения писались в `DECISIONS.md`, теперь это архив): дата, проблема, варианты, решение, причина, последствия.

**Незаписанное решение считается непринятым.**

---

## 4. Never guess business decisions

Если существует развилка, влияющая на: данные, деньги, бронирование, availability,
тариф, guest status, фискализацию, eQonaq, channel manager —
записать вопрос в `QUESTIONS.md`. Не придумывать ответ.
После этого перейти к задаче, не зависящей от вопроса.

---

## 5. External APIs only from project documentation

Для Channex, eQonaq, Smart Bridge, fiscal provider, архивный источник — использовать документацию в `/docs`.
Не писать integration code по памяти модели.

Если документация отсутствует или противоречит API — **STOP**, создать вопрос.

---

## 6. Red before green

Новый bugfix или business rule:

1. создать тест;
2. показать, что тест падает на существующем поведении;
3. исправить код;
4. показать, что тест проходит.

Тест, который никогда не был красным, не считается доказательством исправления.

---

## 7. Secrets

Запрещено выводить API keys, passwords, access tokens, passport data, payment credentials
в код, Git, logs, screenshots, chat.
Secrets — только через environment variables / secret storage. См. `SECURITY.md`.

---

## 8. No real guest data in tests

Все тестовые гости вымышленные. Запрещено копировать реальные ФИО, телефоны,
паспорта, email, карты, документы в fixtures, tests и prompts.

---

## 9. Production is read-only until cutover approval

До отдельного разрешения:

- архивный источник production не изменять;
- OTA production не изменять;
- Channex production ARI не отправлять;
- eQonaq production submissions не отправлять;
- fiscal production receipts не создавать.

---

## 10. Every slice needs evidence

Задача не закрывается словом "done". Нужно одно из:
passing test, screenshot, reconciliation report, API request/response из sandbox,
сравнение с архивный источник.

---

## 11. Never silently lose external events

Каждое внешнее событие (booking, modification, cancellation, payment, notification)
должно иметь: external ID, received_at, processing state, error state, retry state, audit trail.

---

## 12. Money is never float

Деньги хранить в integer minor units / decimal-safe representation.
Никаких JavaScript floating-point вычислений финансов.

---

## 13. Dates and timestamps are different

Stay dates — `DATE` в timezone объекта. События — UTC timestamp.
Не превращать check-in date в UTC datetime без явного правила.

---

## 14. No schema migration without rollback

Каждая production migration должна иметь: backup, migration, validation, rollback procedure.

Миграция «отдельного релиза» (применять только после выкладки определённого кода, метка «ОТДЕЛЬНЫЙ РЕЛИЗ»)
до своего релиза лежит в `packages/database/prisma/migrations-hold/`, а не в общей цепочке `migrations/`
(ADR-137). Порядок переноса в README той папки, сторож `tests/unit/migrations-hold.test.ts`.

---

## 15. Что агенту можно делать без надзора

**Можно:** импорт CSV, UI по утверждённой модели, тесты, refactoring, input validation,
error messages, accessibility, logging, documentation, reconciliation scripts, fixtures,
performance improvements.

**Нельзя:** менять data model, придумывать booking rules, выбирать fiscal provider,
выбирать eQonaq auth, впервые проектировать Channex integration, менять financial logic,
делать production migration, отправлять production ARI.

---

## 16. Scope discipline

MVP-границы зафиксированы в `SPEC.md`. Самостоятельно расширять scope запрещено —
даже если функция «очевидно полезная». Предложение — в `QUESTIONS.md`.

---

## 17. Одно рабочее дерево — одна сессия

В репозитории одновременно работает **один агент**. Причина не в удобстве, а в том, что
общих ресурсов три и все они не переживают двоих:

- **dev-база Supabase.** Пулер отдаёт 15 соединений. Два прогона на общей базе валят
  друг друга ошибкой `EMAXCONNSESSION: max clients reached in session mode`.
- **Отпечаток кода.** `tests/tools/cli-record.ts` считает хэш набора до и после прогона.
  Если сосед правил `apps/` или `packages/` в это время, прогон помечается
  «код набора менялся во время прогона» и как доказательство по §6 не засчитывается.
- **Индекс git.** Два `git add` в одном дереве затирают друг друга. 15.09.2026 миграция
  `20260915000013_accounts` так уехала в чужой коммит про шахматку, а
  `packages/domain/src/accounts/` дважды выпадал из индекса.

Отдельный `git worktree` проблему **не решает**: замок в `tests/runs/.locks/` привязан к
дереву, а база одна на всех. Две копии дерева просто снимут предупреждение и приведут к
ошибке пулера.

Правила:

1. Прежде чем начать работу, проверить `tests/runs/.locks/` и `git status`. Чужой замок или
   чужие незакоммиченные файлы в `apps/`, `packages/`, `scripts/` — ждать, не начинать.
2. Замок `dev-database.lock` руками **не удалять**. Он снимается сам по завершении прогона.
   Удаление замка не останавливает чужой прогон, а только убирает предупреждение.
3. Чужой прогон не прерывать. Если работа встала из-за него — сказать владельцу и ждать.
4. Правка документации (`*.md` в корне, `docs/`, `plans/`, `reports/`) отпечаток набора не
   меняет и разрешена всегда: `watchPathspec` исключает `NOT_CODE`.
5. **Две-три задачи параллельно** только тогда, когда у каждой своя база или проверки с базой идут в GitHub
   (`release-checks` поднимает там свой PostgreSQL 16). Локально тогда только `lint`, `typecheck` и `unit`;
   integration, e2e и UI идут полным гейтом на `main` или кнопкой Actions на ветке.

## 18. Выкладка: сайт и документы сами, стойка автоматически после зелёного гейта; проверка до слияния

Поручение владельца от 20.09.2026 («выкладывать каждую правку без отдельного разрешения») изменено 02.10.2026
по замечанию ментора (ADR-137); 09.10.2026 владелец дал постоянное «да» на автоматическую выкладку стойки
через гейт (ADR-152, поручение «сделай чтобы выкладка на сайт была автоматической»):

- **Сайт wetop.ai и документы** агент выкладывает сам после зелёного `npm run site:check` (тот же набор идёт в
  `release-checks`): сайт командой `npm run site:deploy`
  (`docs/deploy.md`, раздел о сайте), документы (`*.md`, `docs/`, `plans/`, `reports/`) без отдельного «да» владельца, но, как и код,
  только запросом на слияние: прямо в `main` не пушат.
- **Стойка, API и бот** выкладываются автоматически (ADR-152): слияние в `main` делает ответственный за `main`; пуш кода в
  `main` гонит гейт `release-checks`; зелёный гейт перематывает `release` строго вперёд
  (`.github/workflows/auto-release.yml`, без --force); сервер забирает `release` и выкладывает сам, с проверкой
  здоровья и откатом (ADR-080). Агент руками `release` не перематывает; перемотка назад и откат остаются
  ручными (docs/deploy.md §4).
- `release` перематывается только на коммит с зелёной проверкой GitHub `release-checks` (ADR-139): lint, typecheck,
  unit, главная, бот, база (миграции, integration, сквозные) и весь UI на раннерах GitHub, плюс наборы из
  `TESTING.md`. Полный гейт запускается пушем кода в `main` или `release-candidate` и кнопкой Actions; документы и отчёты его
  не гонят (paths-ignore). Перематывает `release` только прогон от пуша в `main`.
- **Проверка до слияния.** Репозиторий приватный (решение владельца 19.10.2026), минуты Actions платные. На каждом
  запросе в `main` идёт быстрая часть того же `release-checks`: lint, typecheck, unit (задача «lint · typecheck ·
  unit · главная», браузерные шаги на запросе пропускаются); полный прогон остаётся на `main`. Вливаем только
  запрос с зелёной быстрой частью; держит это ответственный за `main`. Если тариф GitHub позволяет защиту ветки
  (Pro или Team), для `main` включается: «Require a pull request before merging», «Require status checks to pass
  before merging» с этой задачей, «Require branches to be up to date before merging», «Do not allow bypassing the
  above settings». Красный полный прогон на `main` чинится первым, раньше новых слияний.
- **Ответственный за `main` один, и это человек.** Вливает только он; агенты запросы не вливают. Кто это, решает
  владелец (сейчас вливают двое: владелец и Юрий). Красная проверка: не вливаем и не выкладываем, сначала чиним.
- **Миграции** автоматика не применяет: при новых миграциях сервер откажет и напишет дежурным, применяет их
  владелец, затем на сервере `wetop-auto-deploy --migrations-applied <вершина>`. Ограничения на миграции и
  внешние production API остаются (§15).

Push/merge не считать деплоем: проверять SHA, запущенные образы, health и результат
на рабочем адресе по `docs/deploy.md`. При недоступном SSH/панели сервера закончить
доступные проверки и push, явно сообщить блокер выкладки и запросить недостающий
доступ. Не выдавать локальный preview за обновление публичного приложения.

---

## 19. Длинное тире не используем

Распоряжение владельца от 01.10.2026. Длинное тире (символ U+2014) не использовать
нигде в новых текстах: в ответах и сообщениях агента, документах, комментариях,
коммитах, текстах интерфейса, письмах и ответах бота. Вместо него запятая, двоеточие,
скобки, точка или перестроенная фраза. Дефис в словах и короткое тире в диапазонах
допустимы.

Старые вхождения массово не переписываются: тесты сверяют тексты с этим тире.
Если правишь строку, в которой оно есть, убери его в этой строке.

## 21. Записи о работе, решения, журналы прогонов: файл на задачу

Общий файл, который правит каждая задача, сталкивает любые два запроса и перестаёт читаться (с 3 октября
`CLAUDE.md` менялся 296 раз, `DECISIONS.md` 365, `DESIGN.md` 233, журналы прогонов по 585, разбор ментора 19.10.2026).

- **Запись о сделанной работе:** свой файл `docs/status/ГГГГ-ММ-ДД-<ветка>.md` (дата UTC, ветка без `claude/` и
  `codex/`). Перед работой прочитать файлы за сегодня и вчера (`ls docs/status | tail -n 30`), чужие не править.
  Хроника до 11.10.2026 в `docs/history.md`. Сторож `tests/unit/claude-md-status.test.ts`.
- **Решения:** новое решение пишется своим файлом `docs/decisions/ГГГГ-ММ-ДД-<ветка>.md` (дата, проблема, варианты,
  решение, причина, последствия, как в §3). Номер ADR в имени файла не нужен: девять номеров уже заняты дважды
  разными сессиями. `DECISIONS.md` остаётся архивом решений до 19.10.2026: в него не дописывать, правка старого
  решения (отмена, уточнение) тоже идёт новым файлом со ссылкой на старый номер.
- **Журналы прогонов:** см. §22, строку про `test:record`. Результаты прогонов GitHub лежат артефактами прогона.
- Открытые вопросы пока остаются в `QUESTIONS.md`.

## 22. Жёсткие технические правила

| Правило | Почему |
|---|---|
| Деньги: **integer minor units** (тиын). Никаких float | ADR-008. Расхождение в копейках ломает сверку |
| Stay dates: `DATE` в timezone объекта (Asia/Almaty). События: UTC `timestamptz` | AGENTS.md §13 |
| Каждое внешнее событие: external ID, received_at, статус, retry, audit trail | ADR-007. Дубль или потеря OTA-брони недопустимы |
| Channex SDK и vendor ID: только внутри `packages/integrations` | ADR-004. Домен не знает про Channex |
| Ничего не выводить из номера единицы | Нумерация в архивный источник не сплошная: 1–4 номера, 5–40 койки, 41–48 номера, 49–84 койки, 85–88 номера |
| Integration code: только по документации из `/docs` | AGENTS.md §5. Нет документации → STOP → вопрос |
| Red before green | AGENTS.md §6. Тест, который не был красным, не доказательство |

## 26. Агенты и компьютеры

В репозитории пишут Claude Code, Codex, Hermes, владелец и Юрий, на разных компьютерах.

1. **Задача закрыта, когда она в `main` и `release-checks` на этой вершине зелёный.** «Готово в моей копии» не
   считается.
2. **Смена инструмента или компьютера:** агент отправляет ветку на GitHub, открывает черновой запрос на слияние и
   пишет в его описании три строки: что сделано, что осталось, какие проверки прошли. Следующий берёт ветку с GitHub.
   С локальной копии другого компьютера работу не продолжают.
3. **Боевой сервер только выкладывает.** Агентов там нет: Hermes на сервере не работает, копий проекта под задачи
   там не держат (17-18.10.2026 такие копии дважды доводили диск до 97 %).
4. Пока dev-база одна, работает один агент (§17).

## 27. Модули и дизайн

1. Новый компонент только после строки в `DESIGN.md` §8 и на странице `/design-system`. Сторож
   `tests/unit/design-components-registry.test.ts`: файл в `apps/web/src/components/` (кроме `ui.tsx`) без строки
   в §7-§8 роняет unit.
2. `DESIGN.md`, `design/tokens.json` и общий пакет (`packages/`, `apps/web/src/components/`) меняет **один человек,
   отдельной задачей**. В задаче по экрану эти файлы не правят: нужна правка, значит отдельный запрос.
3. Раздел, который уже есть у другого направления, делается сразу общим, а не копией. Склад уже написан дважды
   (`food/stock-board.tsx` и `bar/stock-board.tsx`), у ресторана свои сотрудники, касса и финансы рядом с общими
   `app/employees` и `app/finance`, время ресторан берёт из папки салона.
4. Главная уже общая: доводить её, а не строить новую. Сотрудников, клиентов и финансы объединять **после первого
   салона**, по разделу за задачу.

## 28. Готово для салона и выпуск

**Готово для салона значит:** `main` зелёный, `release` на нём, миграции применены владельцем на сервере, салон прошёл
свой сценарий. В выпуск входят только экраны и сценарии из списка `docs/release/salon-1.md`; остальное за
выключателем, по умолчанию выключено. Список утверждает владелец; пока он не утверждён, выключатель не строится.
