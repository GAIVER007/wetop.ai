## Принципы

1. `Property` существует в модели, но UI MVP работает с одним property (ADR-001).
2. **Room ≠ sellable inventory** (ADR-005). Но на объекте по **ADR-013** каждая единица
   продажи — самостоятельная ячейка: `PhysicalRoom` заполняется 1:1, иерархия
   «комната → койки» в MVP не строится. Availability, шахматка, уборка, блокировки —
   по `InventoryUnit`.
3. **Reservation ≠ allocation** (ADR-006). Бронь категории может существовать
   без назначенного физического номера.
4. Деньги — integer minor units (ADR-008). Никаких float.
5. Stay dates — `DATE` в timezone объекта (UTC+05:00). События — UTC `timestamptz`.
6. Все внешние события идемпотентны (ADR-007).
7. **Ничего не выводить из номера единицы.** Нумерация в Exely не сплошная и не логичная
   (1–4 номера, 5–40 койки, 41–48 номера, 49–84 койки, 85–88 номера). Только явные связи.

### PhysicalRoom

```
id
floor_id              → Floor
room_number
name
capacity
is_dorm
```

> **Решено — ADR-013, 07.09.2026.** Единица продажи — койка/ячейка, бизнес-логика MVP
> на `PhysicalRoom` не опирается — только на `InventoryUnit`. Статус уборки перенесён
> на `InventoryUnit` (v0.3), см. §4.
>
> Чем заполняется `PhysicalRoom` (со слов владельца 07.09.2026, в Exely этого нет):
> **20 комнат** = 12 одноместных + 4 двухместных + 4 dorm-комнаты по 18 коек
> (2 мужские, 2 женские). Отдельные номера — 1:1 с единицей продажи (16 записей).
> Dorm-комнаты — 4 записи с `capacity` = 18, `is_dorm` = true; какие именно единицы
> Exely (5–40, 49–84) входят в какую комнату — только по явному списку, **Q-095**.
> Из номера единицы принадлежность не выводится (принцип 7).
> **Q-095 отложен владельцем.** До списка импорт заполняет `PhysicalRoom` 1:1 для всех 88
> единиц (исходный вариант А); при получении списка 72 койки перегруппировываются
> в 4 комнаты данными, схема не меняется.

### InventoryUnit

Минимальная единица, куда физически можно назначить гостя.

```
id
physical_room_id      → PhysicalRoom
accommodation_type_id → AccommodationType
kind                  ROOM | BED
code
housekeeping_status   DIRTY | CLEAN | INSPECTED     ← v0.3, см. §4
active
```

Фактически на объекте: **88 единиц = 16 ROOM + 72 BED.**

```
88 = 4 (одноместная с окном)
   + 8 (одноместная без окон)
   + 4 (двухместная)
   + 36 (мужские койки)
   + 36 (женские койки)

Максимальная вместимость гостей = 92
```

Связь единица → категория строго **1:1**. Виртуальных категорий нет,
составные типы размещения в менеджере каналов не используются.

### ReservationItem

Одна продаваемая позиция внутри брони. В терминах Exely — «проживание» (room stay).

```
id
reservation_id        → Reservation
accommodation_type_id → AccommodationType
arrival_date
departure_date
~~quantity~~          ← убран 08.09.2026 (v0.3 утверждена; одно проживание = одна ячейка, ADR-013)
price                 integer minor units
status                ← v0.3: TENTATIVE | CONFIRMED | CHECKED_IN | CHECKED_OUT | CANCELLED | NO_SHOW
rate_plan_id          → RatePlan, NULL   ← 10.09.2026 (Q-102): тариф проживания
adults / children                        ← 10.09.2026 (Q-102): гости проживания
```

> **10.09.2026 (Q-102 закрыт, миграция `20260910000007`):** на проживании хранятся тариф и число гостей.
> Тариф нужен трижды: перерасчёт при изменении дат (раньше `ratePlanCode` приходилось передавать заново),
> штраф при отмене (§6, Q-103) и понимание, какой тариф продан в канале. `NULL` — только у броней,
> перенесённых из Exely: Универсальный API тариф на проживании не отдаёт. `adults` — occupancy для цены.

Подтверждено фактом: бронь Trip.com на 2 единицы = одна бронь, два проживания,
**два счёта** (`…-01`, `…-02`).

> **v0.3 — предложено.** (1) Статус ведётся на проживании: в Exely no-show, переселение и
> счёт — на уровне проживания, и ситуация «из двух проживаний одно заселено, второе no-show»
> иначе не выражается. `Reservation.status` становится производным. (2) `quantity`
> избыточно: в Exely проживание = одна единица, у нас одно проживание = одна ячейка
> (ADR-013), а `Allocation` и folio по проживанию (если Q-091 = б) требуют именно этого.
> Предлагается убрать. Оба пункта утверждаются вместе с Q-091.
>
> **08.09.2026:** оба пункта реализованы в схеме (миграция `20260908000002_reservations_guests`):
> `status` на проживании, `quantity` нет. Основание — утверждение модели v1.0 «включая правки v0.3»
> и режим «работать по умолчаниям, совпадающим с объектом» (владелец 08.09.2026). Внешние ссылки
> для идемпотентного импорта: `Reservation.confirmation_number` = номер брони Exely,
> `ReservationItem.exely_room_stay_id`, `Guest.exely_person_id` (ADR-003).

### Allocation

Фактическое назначение единицы.

```
id
reservation_item_id   → ReservationItem
inventory_unit_id     → InventoryUnit
start_date
end_date
```

Позволяет: продавать категорию до назначения единицы; назначить единицу; переселить
(закрыть одну allocation, открыть другую); назначить несколько коек.

> **Овербукинг запрещает база, не код** (PLAN.md риск №3/№6; реализовано 09.09.2026, миграция
> `20260909000003`): exclusion constraint `allocations_no_overlap_per_unit` на
> `(inventory_unit_id, daterange(start_date, end_date, '[)'))`. Две брони на одну ячейку с пересекающимися
> ночами невозможны физически, даже из двух каналов в одну секунду. В коде — `isOverlapViolation(e)`.

> Факт объекта: единица назначается **сразу** при создании брони, включая брони
> из каналов — 1043 из 1044 заездов августа. Модель это разрешает, но не требует.
> Правило автоназначения ячейки для входящих OTA-броней — **Q-094**, решение владельца.

> **Гражданство у OTA-броней не приходит** — в Exely это поле у канальных броней пустое.
> Для eQonaq данные берутся из паспорта вручную при заселении. Значит: `citizenship`
> заполняется на check-in и является обязательным полем check-in, а не полем импорта.

**Тип и формат (v1.3, 13.09.2026 — Q-117).** `citizenship` и `GuestDocument.issue_country` —
`VARCHAR(3)` с ограничением `IS NULL OR ~ '^[A-Z]{3}$'`: код страны ISO 3166-1 alpha-3 либо NULL.
Не `CHAR(3)`: тип фиксированной длины дополняет пустую строку пробелами, и `'   '` читалось
программой как заполненное гражданство — проверка при заселении пропускала гостя без кода страны,
401 запись пришла такой из импорта Exely (`reports/citizenship-blank-2026-09-12.md`). «Не указано»
хранится только как NULL. Нормализация на входе — `normalizeCitizenship` в `@pms/domain`,
проверка на заселении — `hasCitizenship`. Миграция `20260913000011_citizenship_alpha3`, откат в `down.sql`.

Паспортные данные не дублируются строкой в других таблицах. См. `SECURITY.md`.

> **Предложение v1.7 (24.09.2026, ждёт утверждения) — даты документа шифрованием.** `SECURITY.md` §1 относит дату
> выдачи к особо чувствительным данным: шифрование at rest. Номер шифруется с первого дня (AES-256-GCM,
> `packages/shared/src/pii-crypto.ts`), а `issued_at` и `expires_at` лежат открытым `DATE`. Предложение:
>
> ```
> issued_at_encrypted   TEXT NULL   ← вместо issued_at: ISO-дата, зашифрованная тем же ключом, что номер
> expires_at_encrypted  TEXT NULL   ← вместо expires_at
> issue_country                     ← остаётся открытым: класс «персональные», как citizenship, нужен eQonaq
> ```
>
> Почему можно: даты нигде не участвуют в запросах — только запись и показ (`guests.repository.ts`), расшифровка —
> в приложении, как у номера. Проверка срока документа, если понадобится, — тоже в приложении. На 24.09.2026 в
> рабочей базе документов 0 (ADR-072: пока база не в РК, документы не принимаются) — миграция без переноса данных:
> добавить колонки, снять старые; откат — обратно (данных нет). Нужно до `PII_STORAGE=real`.

## 4. Housekeeping и блокировки

### HousekeepingStatus (enum) — v0.3

```
DIRTY | CLEAN | INSPECTED
```

В Exely три статуса: «Грязно», «Убрано», «Проверено» — ровно эти. Ремонт и вывод
из продажи здесь **не** выражаются: для этого есть `InventoryBlock` ниже. До v0.3
`OUT_OF_ORDER` был и в статусе уборки, и в типе блокировки — два источника правды
для «единица недоступна». Оставлен один: `InventoryBlock`.

Статус уборки ведётся по `InventoryUnit`, а не по `PhysicalRoom`: так делает Exely
(отчёт обслуживания — 88 строк) и так требует ADR-013.

```

> Начисление за проживание создаётся автоматически вместе с проживанием (цена = сумма ночей по календарю)
> и **переписывается при изменении дат**. Услуги начисляются вручную (Q-090 — заставлять ли).
>
> **Как меняется цена проживания при действиях стойки (записано 18.09.2026 по Д5 плана дизайн-системы;
> правило действовало с 09.09 и жило только в JSDoc сервиса, логика не менялась).**
> - *Смена дат* — цена пересчитывается на всё проживание по календарю тарифа проживания (или выбранного).
> - *Продление («+N ночей»)* — прежняя цена **плюс** добавленные ночи по календарю; уже проданные ночи
>   не переоцениваются: их цена согласована с гостем и каналом.
> - *Переселение в другую ячейку той же категории* — цена не меняется.
> - *Переселение в другую категорию* — только на всё проживание; цена пересчитывается по календарю
>   новой категории на все ночи.
> - *Отмена и незаезд* — начисление сторнируется, вместо него штраф по политике тарифа (ниже).
>
> Сумму этих действий стойка видит **до подтверждения**: `GET /reservations/:number/items/:itemId/preview`
> считает её теми же функциями, что и само действие, и ничего не пишет.

Фактически 9 услуг. Завтрака, трансфера, раннего заезда и позднего выезда как услуг нет.

**Баланс счёта** = Σ активных начислений − Σ распределённых платежей + Σ возвратов по счёту.

> **Отмена и незаезд (Q-103 закрыт 10.09.2026 ответом управляющего).** Начисление за проживание
> сторнируется автоматически. Штраф начисляется **только если отмена произошла в день заезда или позже,
> а также при незаезде** — отмена заранее бесплатна на всех каналах (`penaltyDue` в домене).
> Сумма зависит от тарифа (`RatePlan.cancellation_penalty`):
>
> | Тариф                            | Политика      | Почему                                                                                            |
> | -------------------------------- | ------------- | ------------------------------------------------------------------------------------------------- |
> | Базовый (сайт, стойка)           | `NONE`        | «От стойки мы штраф не берём, только доплату по договорённости»                                   |
> | Тариф для ОТА +35% и он же в USD | `FIRST_NIGHT` | Trip.com, Agoda, Expedia: полная онлайн-оплата, при отмене в день заезда удерживается первая ночь |
> | Стандартный и В2В Островок       | `NONE`        | Возвратные                                                                                        |
> | Невозвратный Островок −10%       | `FULL_STAY`   | Невозвратный тариф                                                                                |
>
> **Booking.com — особый случай.** Онлайн-предоплаты там нет, деньги идут в отель, поэтому удержание
> зависит от того, удастся ли списать с карты: управляющий видит запрос и решает сам. Система начисление
> ставит, а стойка **сторнирует его одной кнопкой**, если списать не удалось или отмену признали уважительной.
>
> Начисление `ACCOMMODATION` руками не сторнируется: его ведёт система по проживанию (даты, цена, статус).
> **Перенос из Exely:** оплаченная часть проживания (`totalPrice.amount − toPayAmount`) переносится
> одним платежом `EXTERNAL` с `external_reference = exely:<roomStayId>` — так балансы 209 будущих
> проживаний (96,5 % не оплачено) сходятся с Exely строка к строке. Фискальный чек — §9, провайдер не выбран (Q-050).

> **Правило:** `Reservation.total_amount` и баланс folio — разные вещи, не смешивать.
> На объекте это видно прямо: приход в кассу за август 17,6 млн ₸ против оборота
> проживания по заездам 15,7 млн ₸ — разница из перечислений каналов за прошлые периоды,
> услуг и переходящих оплат. Новая система должна показывать обе цифры и объяснять разницу.

### Пересчёт при действиях стойки (документация, 16.09.2026, срез 7.3)

Правила действующие, срез их не менял — только показывает сумму до подтверждения тем же кодом, что потом пишет начисление
(эндпоинты `move-preview`, `extend-preview`, `cancel-preview` — чтение без записи):

- **переселение в другую категорию** — на всё проживание целиком, цена пересчитывается по календарю новой категории на все
  ночи (тариф проживания или выбранный при смене категории); внутри категории цена не меняется;
- **продление** — прежняя цена плюс новые ночи по календарю той же категории и тарифа; без тарифа (перенесено из Exely) —
  тариф выбирает администратор;
- **отмена и незаезд** — штраф по политике тарифа (`NONE` / `FIRST_NIGHT` / `FULL_STAY`) и только с дня заезда (Q-103);
  предоплата канала после отмены — ADR-022.

## 12. Неисправности системы (v1.4 — принят 13.09.2026, срез 11, ADR-028)

Одно место, куда сторож системы записывает всё, что сломалось: очередь ARI, входящие события, webhook,
база, ответы API 500, овербукинг, упавшие сверки и тесты. Техническая таблица, как `ChannelOutbox`:
бизнес-данных не хранит и не меняет. Сторож и дежурный агент читают только её.

### SystemIncident

```
id
kind              вид неисправности: webhook.suspect | webhook.unreachable | feed.stale |
                  outbox.failed | outbox.stuck | event.failed | event.rejected | sync.missing | db.down |

subject_type      reservation | external_event | outbox | category_night | route | report | suite | null
subject_id        номер брони, id события, маршрут — без ФИО, телефонов, почты и секретов

occurrences       сколько раз замечена
first_seen_at     timestamptz

> **Одна строка на неисправность.** Пока неисправность не закрыта, повтор с тем же `fingerprint` не создаёт
> строку, а увеличивает `occurrences` и `last_seen_at`: частичный уникальный индекс
> `UNIQUE(fingerprint) WHERE status <> 'RESOLVED'`. Закрытая и снова возникшая — новая строка: у ночи
> с двумя падениями туннеля две истории.
>
> **Закрывает сторож, а не человек.** Проверка больше не видит неисправность — строка `RESOLVED`, `GUARD`.
> «Принято» (`ACKNOWLEDGED`) означает только «человек в курсе, будить больше не надо». Закрыть руками
> (`STAFF`) можно то, что проверка не умеет перепроверить (упавшая сверка, падение тестов).
>
> **Персональных данных нет по построению:** в строку попадают номер брони, код категории, id события,
> маршрут API — не имя гостя, не телефон и не тело запроса. Хранение — 90 дней после закрытия.
>
> В `AuditLog` сторож не пишет: он не меняет того, что журнал обязан фиксировать (даты, цены, переселения,
> платежи), а `AuditLog.user_id` — сотрудник.

## 13. Учётные записи и регистрация (v1.5 — принят 15.09.2026, срез 13, ADR-046)

Появляется из ADR-046. Существующие таблицы разделов 1–12 не меняются: разделение данных по
организациям это отдельный срез, до него пробный период пускает в демо-объект, а не в живой.

> **Поправка v1.6 (20–21.09.2026, записано 22.09):** демо-объекта нет — регистрация заводит свой пустой объект,
> дальше онбординг (`/onboarding`); `properties` получила `organization_id` (§1, ADR-061). Остальные таблицы
> разделов 1–12 по-прежнему без `organization_id`: объект определяется через `properties`.

Общие правила раздела:

- почта хранится в нижнем регистре, сравнение по нормализованной форме, уникальность по ней же;

- время в UTC `timestamptz`, как в AGENTS.md §13;
- удаления строк нет, вместо удаления `status`;
- лимиты запроса кода: 5 в час на почту, 20 в час с адреса; адрес посетителя из `CF-Connecting-IP` и
  только от loopback, как в срезе 9 (`SECURITY.md` §11).

## 14. Ошибки, которые видит человек (v1.8 — утверждён 24.09.2026, ADR-076; ТЗ ред. 1, задача П3; ADR-075)

Журнал отказов API, которые получил вошедший человек: 4xx («adults — целое ≥ 1») и 5xx. Нужен ИИ-помощнику, чтобы
ответить «что у меня сломалось» (`docs/assistant/README.md`). Техническая таблица, как `system_incidents`: бизнес-данных
не хранит, существующие таблицы не меняет. Разница с §12: неисправность — поломка системы без человека, строка здесь —
то, что увидел конкретный человек.

> **Кто читает.** Только помощник по узкому ключу (`GET /assistant/errors`, `userId` и `organizationId` обязательны).

## 15. Профиль ИИ-продавца (v1.8 — утверждён 24.09.2026, ADR-076; ТЗ ред. 1, задача П5; ADR-075)

Одна строка на организацию: как продавец говорит с гостями и что он рассказывает о правилах объекта. Правила ядра
(границы, «не считать деньги», «не обещать действий, которых не делаешь») в профиле не хранятся и правке не подлежат —
их держит бот, а платформа передаёт ему профиль полями, не текстом промпта (ТЗ §2 п. 2). Адрес, время заезда, категории
и цены сюда тоже не входят: продавец получает их фактами из карточки объекта и тарифов (П8).

### SellerProfile — таблица `seller_profiles`

| Поле | Тип | Примечание |
|---|---|---|
| `organization_id` | `uuid` PK, FK → `organizations` | одна строка на организацию |
| `bot_name` | `varchar(40)` | NULL — бот без имени |
| `address_form` | enum `FORMAL` \| `INFORMAL` | «вы» или «ты»; продавцу — `vy` / `ty` |
| `emoji` | enum `NEVER` \| `MODERATE` \| `GREETING_ONLY` | эмодзи: нет, изредка, только в приветствии |
| `reply_length` | enum `SHORT` \| `DETAILED` | коротко или развёрнуто |
| `languages` | `text[]` | коды ISO 639-1 из списка домена; CHECK 1…6 штук; первый — основной; продавцу — названиями («русский») |
| `greeting` | `varchar(300)` | приветствие |
| `included_in_price` | `varchar(1000)` | что входит в цену |
| `extra_charges` | `varchar(1000)` | что за доплату |
| `house_rules` | `varchar(2000)` | правила проживания |
| `prohibitions` | `text[]` | запреты, по одному в строке: до 30, каждый ≤ 300 |
| `call_human_when` | `text[]` | когда звать человека, по одному в строке: до 30, каждый ≤ 300 |
| `faq` | `jsonb` | `[{ "question": ≤ 300, "answer": ≤ 1000 }]`, до 50 |
| `updated_at` | `timestamptz` | время последней правки |
| `updated_by` | `uuid` FK → `users` | автор последней правки; NULL — служебный ходок; ON DELETE SET NULL |
| `profile_applied_at` | `timestamptz` | когда продавец принял текущую версию профиля (П8); NULL — не принимал |
| `facts_hash` | `char(64)` | SHA-256 последних доставленных фактов объекта |
| `facts_applied_at` | `timestamptz` | когда факты доставлены |
| `last_error` | `varchar(500)` | последний отказ продавца, маскированный; NULL — отказов нет |
| `last_error_at` | `timestamptz` | |
| `created_at` | `timestamptz` | DEFAULT `now()` |

> **Персональных данных гостей нет:** это настройки владельца. Правка пишется в `audit_logs`
> (`seller.profile.updated`, до и после, автор). Поля доставки человек не правит — их ведёт платформа.
>
> **«Применено»** — `profile_applied_at ≥ updated_at` и отпечаток текущих фактов совпадает с `facts_hash`. Иначе
> служба сверки отправляет продавцу недостающее раз в минуту, пока он не примет (выключатель `SELLER_SYNC=off`).
>
> **Одна копия продавца — одна организация** (`SELLER_ORGANIZATION_ID`, ADR-075): вошедший из другой организации
> раздела не видит. Строка заводится первой правкой профиля.
>
> **Почему поля именно такие.** Продавец принимает профиль моделью с `extra='forbid'` (`src/ai/seller_prompt.py` на
> ветке `ai-seller`, Б6): лишнее поле или значение вне списка — отказ 422. Поэтому перечисления и пределы длины здесь
> ровно его, а название объекта (`object_name`, обязательно у продавца) в профиле не хранится — платформа берёт его из
> карточки объекта при каждой отправке.
>
> **Первая редакция (до сверки с ботом)** — `bot_name` ≤ 60, `use_emoji boolean`, `reply_length`
> `SHORT`/`MEDIUM`/`LONG`, `greeting` ≤ 500, `paid_extras`, `prohibitions` и `handoff_rules` одним текстом ≤ 1000, `faq`
> до 30 с вопросом ≤ 200 — продавец отклонил бы целиком. На рабочей базе её не было; после утверждения (ADR-076)
> миграция `20260924000019` переписана под эту таблицу. Запретов и «когда звать человека» — до 30 строк: CHECK базы.
>
> **Факты объекта** (не таблица — собираются при каждой отправке, в строке хранится только отпечаток): название, адрес,
> часовой пояс, заезд и выезд, валюта тарифа сайта, активные категории с вместимостью и **одной ценой за ночь** —
> если за 60 дней она не меняется, иначе цены нет («уточнит администратор»); цена — при наибольшем числе гостей, на
> которое она есть (ADR-076, Q-179).
