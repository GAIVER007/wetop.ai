## Принципы

1. `Property` существует в модели, но UI MVP работает с одним property (ADR-001).
2. **Room ≠ sellable inventory** (ADR-005). Но на объекте по **ADR-013** каждая единица
   продажи — самостоятельная ячейка: `PhysicalRoom` заполняется 1:1, иерархия
   «комната → койки» в MVP не строится. Availability, шахматка, уборка, блокировки —
   по `InventoryUnit`.
3. **Reservation ≠ allocation** (ADR-006). Бронь категории может существовать
   без назначенного физического номера.
4. Деньги — integer minor units (ADR-008). Никаких float.
5. Stay dates — `DATE` в timezone объекта (UTC+05:00). События — UTC `timestamptz`.
6. Все внешние события идемпотентны (ADR-007).
7. **Ничего не выводить из номера единицы.** Нумерация в архивный источник не сплошная и не логичная
   (1–4 номера, 5–40 койки, 41–48 номера, 49–84 койки, 85–88 номера). Только явные связи.

Минимальная единица, куда физически можно назначить гостя.

```

**v1.12 (26.09.2026, ADR-096).** Код места уникален внутри объекта, а не во всей базе: у каждой гостиницы свои
«101» и «R01». `property_id` дублирует то, что и так выводится через категорию (`accommodation_type.property_id`),

никогда по одному коду — иначе вошедший из чужой организации нашёл бы место Luxx по её коду.
`retired-source_room_number` остаётся глобально уникальным: он есть только у объекта, перенесённого из архивный источник, у остальных NULL.

```

   + 8 (одноместная без окон)

   + 36 (женские койки)

Максимальная вместимость гостей = 92
```

Связь единица → категория строго **1:1**. Виртуальных категорий нет,

### ReservationItem

> Предлагается убрать. Оба пункта утверждаются вместе с Q-091.
>
> **08.09.2026:** оба пункта реализованы в схеме (миграция `20260908000002_reservations_guests`):
> `status` на проживании, `quantity` нет. Основание — утверждение модели v1.0 «включая правки v0.3»
> и режим «работать по умолчаниям, совпадающим с объектом» (владелец 08.09.2026). Внешние ссылки

**Тип и формат (v1.3, 13.09.2026 — Q-117).** `citizenship` и `GuestDocument.issue_country` —
`VARCHAR(3)` с ограничением `IS NULL OR ~ '^[A-Z]{3}$'`: код страны ISO 3166-1 alpha-3 либо NULL.
Не `CHAR(3)`: тип фиксированной длины дополняет пустую строку пробелами, и `'   '` читалось
программой как заполненное гражданство — проверка при заселении пропускала гостя без кода страны,

хранится только как NULL. Нормализация на входе — `normalizeCitizenship` в `@pms/domain`,
проверка на заселении — `hasCitizenship`. Миграция `20260913000011_citizenship_alpha3`, откат в `down.sql`.

Паспортные данные не дублируются строкой в других таблицах. См. `SECURITY.md`.

> **v1.7 (24.09.2026, утверждено 25.09.2026, ADR-082; реализовано 25.09.2026, миграция `20260925000021`) — даты документа
> шифрованием.** `SECURITY.md` §1 относит дату выдачи к особо чувствительным данным: шифрование at rest. Номер
> шифруется с первого дня (AES-256-GCM, `packages/shared/src/pii-crypto.ts`); теперь так же лежат и даты:
>
> ```
> issued_at_encrypted   TEXT NULL   ← вместо issued_at: ISO-дата, зашифрованная тем же ключом, что номер
> expires_at_encrypted  TEXT NULL   ← вместо expires_at
> issue_country                     ← остаётся открытым: класс «персональные», как citizenship, нужен eQonaq
> ```
>
> Даты нигде не участвуют в запросах — только запись и показ: шифрует и расшифровывает `guests.service.ts`, как
> номер (нет ключа — даты не показываются, как «недоступно» у номера). На дату миграции документов в базе 0
> (ADR-072: пока база не в РК, документы не принимаются) — перенос данных не понадобился; откат — `down.sql`
> рядом с миграцией (пересоздаёт таблицу, чтобы вернуть исходный порядок колонок). Сама база проверяется тестом
> `tests/integration/document-dates-encrypted.test.ts`: открытых колонок нет, в строке шифртекст. Успело до
> `PII_STORAGE=real`.

## 4. Housekeeping и блокировки

### HousekeepingStatus (enum) — v0.3

```
DIRTY | CLEAN | INSPECTED
```

В архивный источник три статуса: «Грязно», «Убрано», «Проверено» — ровно эти. Ремонт и вывод
из продажи здесь **не** выражаются: для этого есть `InventoryBlock` ниже. До v0.3
`OUT_OF_ORDER` был и в статусе уборки, и в типе блокировки — два источника правды
для «единица недоступна». Оставлен один: `InventoryBlock`.

Статус уборки ведётся по `InventoryUnit`, а не по `PhysicalRoom`: так делает архивный источник
(отчёт обслуживания — 88 строк) и так требует ADR-013.

### HousekeepingEvent

> Начисление за проживание создаётся автоматически вместе с проживанием (цена = сумма ночей по календарю)
> и **переписывается при изменении дат**. Услуги начисляются вручную (Q-090 — заставлять ли).
>
> **Как меняется цена проживания при действиях стойки (записано 18.09.2026 по Д5 плана дизайн-системы;
> правило действовало с 09.09 и жило только в JSDoc сервиса, логика не менялась).**
> - *Смена дат* — цена пересчитывается на всё проживание по календарю тарифа проживания (или выбранного).
> - *Продление («+N ночей»)* — прежняя цена **плюс** добавленные ночи по календарю; уже проданные ночи
>   не переоцениваются: их цена согласована с гостем и каналом.
> - *Переселение в другую ячейку той же категории* — цена не меняется.
> - *Переселение в другую категорию* — только на всё проживание; цена пересчитывается по календарю
>   новой категории на все ночи.
> - *Отмена и незаезд* — начисление сторнируется, вместо него штраф по политике тарифа (ниже).
>
> Сумму этих действий стойка видит **до подтверждения**: `GET /reservations/:number/items/:itemId/preview`
> считает её теми же функциями, что и само действие, и ничего не пишет.

Фактически 9 услуг. Завтрака, трансфера, раннего заезда и позднего выезда как услуг нет.

**Баланс счёта** = Σ активных начислений − Σ распределённых платежей + Σ возвратов по счёту.

> **Отмена и незаезд (Q-103 закрыт 10.09.2026 ответом управляющего).** Начисление за проживание
> сторнируется автоматически. Штраф начисляется **только если отмена произошла в день заезда или позже,
> а также при незаезде** — отмена заранее бесплатна на всех каналах (`penaltyDue` в домене).
> Сумма зависит от тарифа (`RatePlan.cancellation_penalty`):
>
> | Тариф                            | Политика      | Почему                                                                                            |
> | -------------------------------- | ------------- | ------------------------------------------------------------------------------------------------- |
> | Базовый (сайт, стойка)           | `NONE`        | «От стойки мы штраф не берём, только доплату по договорённости»                                   |
> | Тариф для ОТА +35% и он же в USD | `FIRST_NIGHT` | Trip.com, Agoda, Expedia: полная онлайн-оплата, при отмене в день заезда удерживается первая ночь |
> | Стандартный и В2В Островок       | `NONE`        | Возвратные                                                                                        |
> | Невозвратный Островок −10%       | `FULL_STAY`   | Невозвратный тариф                                                                                |
>
> **Booking.com — особый случай.** Онлайн-предоплаты там нет, деньги идут в отель, поэтому удержание
> зависит от того, удастся ли списать с карты: управляющий видит запрос и решает сам. Система начисление
> ставит, а стойка **сторнирует его одной кнопкой**, если списать не удалось или отмену признали уважительной.
>
> Начисление `ACCOMMODATION` руками не сторнируется: его ведёт система по проживанию (даты, цена, статус).
> **Перенос из архивный источник:** оплаченная часть проживания (`totalPrice.amount − toPayAmount`) переносится
> одним платежом `EXTERNAL` с `external_reference = retired-source:<roomStayId>` — так балансы 209 будущих
> проживаний (96,5 % не оплачено) сходятся с архивный источник строка к строке. Фискальный чек — §9, провайдер не выбран (Q-050).

> **Правило:** `Reservation.total_amount` и баланс folio — разные вещи, не смешивать.
> На объекте это видно прямо: приход в кассу за август 17,6 млн ₸ против оборота
> проживания по заездам 15,7 млн ₸ — разница из перечислений каналов за прошлые периоды,
> услуг и переходящих оплат. Новая система должна показывать обе цифры и объяснять разницу.

### Пересчёт при действиях стойки (документация, 16.09.2026, срез 7.3)

Правила действующие, срез их не менял — только показывает сумму до подтверждения тем же кодом, что потом пишет начисление
(эндпоинты `move-preview`, `extend-preview`, `cancel-preview` — чтение без записи):

- **переселение в другую категорию** — на всё проживание целиком, цена пересчитывается по календарю новой категории на все
  ночи (тариф проживания или выбранный при смене категории); внутри категории цена не меняется;
- **продление** — прежняя цена плюс новые ночи по календарю той же категории и тарифа; без тарифа (перенесено из архивный источник) —
  тариф выбирает администратор;
- **отмена и незаезд** — штраф по политике тарифа (`NONE` / `FIRST_NIGHT` / `FULL_STAY`) и только с дня заезда (Q-103);
  предоплата канала после отмены — ADR-022.

> **v1.10 (25.09.2026, ТЗ аудита, С-14; миграция `20260925000022_integrity_guards`).** Суммы платежа,
> разнесения и возврата держит база: `CHECK (amount > 0)` на `payments`, `payment_allocations`, `refunds` —
> ноль и минус не запишутся даже ошибкой кода. Начисления (`charges`) без CHECK намеренно: сторно — минус.

> **v2.12 (07.10.2026, поручение владельца, ADR-151; план `plans/finance-payments-direct-2026-10-07.md`).
> Схема и миграции не менялись: правила поверх полей, которые уже были.**
> - **Аннулирование платежа.** `Payment.status = VOIDED` ставит команда `POST /finance/payments/:id/void`
>   (право `refunds`): только проведённый платёж без возвратов и без фискального чека (§26), все его счета
>   открыты. Аннулированный платёж из баланса счёта, остатков кассы (§21) и сумм отчётов выпадает, строка
>   остаётся в ленте со статусом «аннулирован». Запрос оплаты (§24), закрытый этим платежом, снова ждёт оплаты.
> - **Замена платежа.** `POST /finance/payments/:id/replace`: старый `VOIDED`, новый `COMPLETED` с тем же
>   `paid_at` одной транзакцией под блокировкой строки платежа и счетов; без `allocations` сумма ложится на
>   единственный счёт старого платежа, групповой платёж без распределения отклоняется словами. Запрос оплаты
>   переводится на новый платёж. Журнал: `finance.payment.void`, `finance.payment.replaced`.
> - **Цена проживания вручную.** `PATCH /reservations/:number/items/:itemId` с `price` пишет
>   `ReservationItem.price`; начисление `ACCOMMODATION` переписывает система тем же `ensureFolioWithAccommodation`,
>   что при смене дат, `Reservation.total_amount` пересчитывается по неотменённым проживаниям. Вниз только с
>   правом `refunds` (как корректировка на уменьшение, ADR-107); отменённое, незаезд и выехавшее не меняются.
>   При смене дат или категории цена снова считается по тарифу: ручная цена не закрепляется. Журнал
>   `reservation.item.price`.
> - **Скидка** это `ADJUSTMENT` со знаком минус и подписью «Скидка N% на проживание» или «Скидка: причина»;
>   процент считается от действующего начисления за проживание целыми тиынами с отбрасыванием остатка
>   (`discountMinor` в домене). Отдельной сущности у скидки нет.
> - Возврат (`Refund`) по-прежнему не аннулируется (Q-278); дата платежа при замене не меняется (Q-277).

received_via           WEBHOOK | PULL | MANUAL

processed_at
```

**UNIQUE (provider, external_event_id)** — обязательно, для идемпотентности (ADR-007).

`received_via` — каким путём событие дошло. Один и тот же вызов `processRevision` работает и по
webhook, и по опросу ленты каждые 5 минут, поэтому без этого поля нельзя доказать, что бронь
пришла сама: в журнале обе записи выглядят одинаково, а «приходит сама» и «подобрал опрос через
пять минут» — разные утверждения. `MANUAL` — разбор по кнопке «Обработать заново».

> **09.09.2026, реализовано (миграция `20260909000004`):** `external_events` с полями выше плюс `payload` (Json) и enum
> статуса `RECEIVED | PROCESSING | PROCESSED | FAILED`. Обработка событий (webhook Channex) — шаг 4.4.
>
> **24.09.2026, что лежит в `payload` (ADR-074, SECURITY.md §2; поправка задним числом, ждёт утверждения):**
> - ревизия Channex — по разрешённому списку полей (`sanitizeRevision`);
> - пока база не в РК — без заказчика (кроме страны), имён гостей, заметки и `meta` номеров;
> - события не о брони — только идентификаторы и поля без гостя, остальные ключи перечислены в `omitted`;
> - карта (`guarantee`) и исходное сообщение площадки (`raw_message`) не хранятся никогда.
>
> Колонку `payload` утверждённая модель не называла: она появилась при реализации. Её ставшее правилом содержимое
> записано здесь.
>
> **10.09.2026, реализовано (миграция `20260910000008`):** добавлено `received_via`
> (`WEBHOOK | PULL | MANUAL`, по умолчанию `PULL`) — путь доставки события.

## 13. Учётные записи и регистрация (v1.5 — принят 15.09.2026, срез 13, ADR-046)

- лимиты запроса кода: 5 в час на почту, 20 в час с адреса; адрес посетителя из `CF-Connecting-IP` и
  только от loopback, как в срезе 9 (`SECURITY.md` §11).

ключом не может быть `id` — он лежит открытым; поле `token_hash` добавлено миграцией
`20260916000014_session_token_hash`, в исходной редакции §13 оно было упущено.

Ключ ходит кукой `HttpOnly`, `Secure`, `SameSite=Lax`, домен `.wetop.ai` — стойка на
`app.wetop.ai` и API на `api.wetop.ai` для браузера один сайт. `HttpOnly` значит, что чужой
скрипт на странице ключ не прочитает; будь он в `localStorage`, любая XSS-дыра уносила бы
сессию. Заголовок `Authorization: Bearer` API тоже принимает — для проверок и для вызовов
не из браузера.

### 13.11. `email_verifications.wizard_session_id`: связь подтверждения почты с гостевым черновиком (v2.14, O5a, ADR-153; **ПРЕДЛОЖЕНИЕ, НЕ УТВЕРЖДЕНО**)

План: `plans/guest-onboarding-ai-seller-2026-10-09.md`, раздача: `plans/guest-onboarding-orchestration-2026-10-09.md` (ТЗ-O5a, поправка П3). Кода нет, миграции нет. Утверждает владелец до среза O5b.

**Зачем.** Мастер `/create` живёт на `app.wetop.ai` и хранит гостевой токен в `localStorage`, а письмо подтверждения человек может открыть на другом устройстве и в другом браузере. Токен в адрес письма класть нельзя (он «носитель»: у кого токен, тот хозяин черновика). Нужна **серверная** связь «эта регистрация, этот черновик», которая переживает письмо и не раскрывает токен.

| Поле | Тип | Примечание |
|---|---|---|
| `wizard_session_id` | `uuid` NULL, FK → `wizard_sessions(id)` | `ON DELETE SET NULL`: очистка просроченных сессий (`WizardRetentionService`, раз в час) не должна ломать подтверждение |

Индекс: `UNIQUE (wizard_session_id) WHERE wizard_session_id IS NOT NULL AND used_at IS NULL`. Одна живая связь на сессию: две регистрации не могут одновременно претендовать на один черновик. Существующие строки получают `NULL`, поведение прежнее.

**Правила**

1. **Кто заполняет.** `POST /auth/register` принимает необязательное `wizardToken` (форма `^wz_[a-f0-9]{64}$`) **в теле запроса**, не в адресе. Сервер находит сессию по SHA-256, и только если она не истекла и у черновика нет `agent_id`, кладёт её `id` в первую ссылку подтверждения. В таблицу пишется id сессии, **токен не пишется нигде**. Любая неудача (токен не той формы, сессия истекла или уже присвоена) молча игнорируется: регистрация не должна падать из-за мастера.
2. **Повторная отправка письма не теряет бота.** `issue()` уже гасит прежние неиспользованные ссылки (одна живая ссылка на человека). Новая строка **наследует** `wizard_session_id` от погашаемой, в одной транзакции: сначала погашение, потом создание, поэтому частичный уникальный индекс не срабатывает.
3. **Присвоение.** После успешного `confirm` (включая окно повторного перехода `VERIFY_REUSE_WINDOW_MS`) сервер присваивает черновик **по id сессии**: тот же код, что `POST /seller-agents/claim` (блокировка `FOR UPDATE` строки сессии, создание `SellerAgent` в `draft`, `WizardDraft.agentId`, `claimedBy`, `organizationId`, событие `complete`, запись в `audit_logs`), отличие одно: ключ не токен, а `wizard_session_id` из проверенной строки подтверждения. Идемпотентно: повтор тем же человеком возвращает того же агента; другой человек не получает ничего. Условия те же: роль владельца (регистрант всегда владелец своей новой организации), почта подтверждена. Название организации берётся из `hotelName`, который форма `/create` подставляет из `businessName`.
4. **Сбой присвоения не ломает вход.** Человек подтвердил почту и вошёл; запись `wizard.handoff.failed` в журнале (без текстов черновика); бот можно присвоить существующей кнопкой на `/create` (путь с токеном из `localStorage` того же origin), пока сессия жива.
5. **Сессия истекла или очищена.** Внешний ключ обнуляется, подтверждение проходит как раньше, бота нет; человеку об этом сказано словами («черновик устарел, создайте бота заново»).
6. **Вход существующим аккаунтом** этой связью не покрывается (аккаунт уже есть, письма нет): остаётся кнопка с токеном (`POST /seller-agents/claim`, без изменений).
7. **Права и RLS.** Как у `email_verifications` (§17.2–17.3): без RLS, у `wetop_app` прав нет, читает и пишет `wetop_service`. Новая колонка и внешний ключ новых прав не требуют; отдельной миграции прав нет.
8. **Миграция.** Одна: `ADD COLUMN`, частичный уникальный индекс, `down.sql` (индекс, затем колонка). Номер берётся **на момент слияния** с `main`, не сейчас (ADR-052). **Применяет владелец до выкладки кода O5b**: код читает колонку, без неё регистрация падает.

**Принятый риск.** Чужую почту можно ввести при регистрации вместе со своим токеном. Нового вреда это не добавляет: аккаунт и организацию создаёт регистрация (так уже было), черновик становится агентом в состоянии `draft` без запуска и без пробного периода, а владелец почты подтверждает ссылку сам.

**Не входит:** перенос знаний в базу бота (очередь индексации `WizardJob(kind=index)` из модели 26.09, срез O5b), пробный период (вопрос Q-O1: в мастере его не обещаем), присвоение при входе.

## 14. Ошибки, которые видит человек (v1.8 — утверждён 24.09.2026, ADR-081; ТЗ ред. 1, задача П3; ADR-079)

Журнал отказов API, которые получил вошедший человек: 4xx («adults — целое ≥ 1») и 5xx. Нужен ИИ-помощнику, чтобы
ответить «что у меня сломалось» (`docs/assistant/README.md`). Техническая таблица, как `system_incidents`: бизнес-данных
не хранит, существующие таблицы не меняет. Разница с §12: неисправность — поломка системы без человека, строка здесь —
то, что увидел конкретный человек.

### UserError — таблица `user_errors`

| Поле | Тип | Примечание |
|---|---|---|
| `id` | `uuid` PK | |
| `at` | `timestamptz` NOT NULL | время ответа; ставит приложение, у колонки нет DEFAULT (ТЗ П3) |
| `user_id` | `uuid` FK → `users` | кто получил ошибку; ON DELETE CASCADE |
| `organization_id` | `uuid` FK → `organizations` | под какой организацией открыта сессия; ON DELETE CASCADE |
| `method` | `varchar(10)` | `GET`, `POST`, `PUT`, `PATCH`, `DELETE` |

| `status` | `smallint` | CHECK 400…599 |
| `message` | `varchar(500)` | текст ошибки, который отдал API, после маскирования (`redactText`: почта, телефоны, секреты) |

## 15. Профиль ИИ-продавца (v1.8 — утверждён 24.09.2026, ADR-081; ТЗ ред. 1, задача П5; ADR-079)

Одна строка на организацию: как продавец говорит с гостями и что он рассказывает о правилах объекта. Правила ядра
(границы, «не считать деньги», «не обещать действий, которых не делаешь») в профиле не хранятся и правке не подлежат —
их держит бот. Платформа передаёт ему профиль полями или, с v1.11, инструкцией владельца одним текстом (ADR-097): бот
ставит роль, границы и правила ядра выше текста и проверяет его на скрытые инструкции. Адрес, время заезда, категории
и цены сюда тоже не входят: продавец получает их фактами из карточки объекта и тарифов (П8).

> если за 60 дней она не меняется, иначе цены нет («уточнит администратор»); цена — при наибольшем числе гостей, на

## 16. Доступ к платформе и расширения (v1.9 — утверждён 25.09.2026, ADR-083; Q-182…Q-184)

> **Утверждён владельцем 25.09.2026** («давай подвеждаю и продолжай дальше», ADR-083). Миграция
> `20260925000020_access_extensions`; на рабочей базе её применяет владелец (AGENTS.md §15). План и логика доступа —
> `plans/platform-roles-extensions-2026-09-25.md`. Существующие таблицы §1–§15 не меняются, кроме `memberships` (§13.3).

Три вещи: роль человека в организации, главный администратор платформы и платные расширения организации. Денег здесь
нет: цена и оплата появятся после Q-141 и Q-143. Персональных данных гостей тоже нет.

### 16.1. `memberships.role` — роль в организации (Q-182)

| Поле | Тип | Примечание |
|---|---|---|
| `role` | enum `MembershipRole` NOT NULL DEFAULT `STAFF` | `OWNER` — владелец организации, `MANAGER` — управляющий (v1.14), `STAFF` — администратор (до v1.14 на экране — «сотрудник») |

- **Заполнение при миграции:** в каждой организации `OWNER` получает самый ранний участник (`min(created_at)`),
  остальные — `STAFF`. Регистрация заводит организацию и первое членство одной транзакцией, поэтому самый ранний — тот,
  кто её зарегистрировал. Список «организация → владелец» до и после миграции — владельцу на сверку.
- Регистрация создаёт членство с ролью `OWNER`, принятое приглашение — с ролью из приглашения (`invites.role`, v1.14;
  до v1.14 — всегда `STAFF`).
- В каждой организации есть хотя бы один `OWNER`. Это проверяет команда смены роли: последнего владельца она не
  снимает. Ограничения в базе на это нет — его пришлось бы писать триггером.
- **С v1.14 роль — готовый набор прав (ADR-107, §16.5).** До v1.14 на стойке роль прав не меняла (ADR-023), а
  владельцу были оставлены сотрудники, приглашения и настройки ИИ-продавца (ADR-083).
- Роль между `MANAGER` и `STAFF` меняет владелец на стойке (v1.14); назначает и снимает владельца только команда на
  сервере. Смена роли пишется в `audit_logs` (`membership.role.updated`: было, стало, автор).
- **Отключить сотрудника** (v1.14) — удалить его строку членства: сессии этой организации гаснут на следующем же
  запросе (сессия живёт, пока есть членство — аудит 26.09, С-10). Владелец отключает управляющих и администраторов,
  управляющий — администраторов; себя и владельца так не отключить. Пишется в `audit_logs` (`membership.removed`:
  роль, автор). Строка `users` остаётся: журнал и членство в других организациях не теряются, позвать снова можно
  приглашением.

### 16.2. `platform_admins` — главный администратор платформы (Q-184)

| Поле | Тип | Примечание |
|---|---|---|
| `user_id` | `uuid` PK, FK → `users` | строки `users` не удаляются (§13) |
| `granted_at` | `timestamptz` NOT NULL DEFAULT `now()` | |
| `revoked_at` | `timestamptz` | NULL — отметка действует |
| `note` | `varchar(200)` | зачем выдана; без персональных данных |

- Отметка действует, если `revoked_at IS NULL` и человек в статусе `ACTIVE`.
- Ставит и снимает её только команда на сервере (`npm run accounts -- platform-admin …`). Маршрута API, который
  пишет в эту таблицу, нет. Выдача и снятие пишутся в `audit_logs` (`platform.admin.granted`, `platform.admin.revoked`).
- Строки не удаляются: при повторной выдаче `revoked_at` обнуляется, `granted_at` ставится заново.
- Отдельная таблица, а не поле в `users`: так правка профиля человека не может задеть отметку ни при какой ошибке.

### 16.3. `organization_extensions` — платные расширения организации (Q-183)

| Поле | Тип | Примечание |
|---|---|---|
| `organization_id` | `uuid` FK → `organizations` | |
| `extension` | enum `ExtensionKind` | пока одно значение — `AI_SELLER` |
| `status` | enum `ExtensionStatus` NOT NULL | `TRIAL` — пробный, `ACTIVE` — оплачен, `OFF` — выключен |
| `active_until` | `timestamptz` | до какого момента действует; NULL — бессрочно. CHECK: у `TRIAL` не NULL |
| `note` | `varchar(300)` | номер счёта и т. п.; без персональных данных |
| `updated_at` | `timestamptz` NOT NULL | |
| `updated_by` | `uuid` FK → `users` | кто изменил; ON DELETE SET NULL |
| `created_at` | `timestamptz` NOT NULL DEFAULT `now()` | |

PK составной (`organization_id`, `extension`).

- **Расширение действует**, если `status` — `TRIAL` или `ACTIVE`, и при этом `active_until IS NULL` или
  `now() < active_until`. Срок проверяется при каждом запросе. Отдельной службы, которая переводит строку в `OFF`, нет:
  расширение с вышедшим сроком и так не действует.
- Меняет строку только главный администратор (`PUT /platform/organizations/:id/extensions/ai-seller`). Каждое изменение
  пишется в `audit_logs` (`extension.updated`: было, стало, автор).
- Строки не удаляются: выключение — это статус `OFF`.
- Что видно и что закрыто, пока расширение не действует, — план §4.1; что происходит после срока — Q-183.

### 16.4. Миграция

Если раздел утверждён целиком, это одна миграция на все три части, иначе — по частям. `down.sql` лежит рядом. Порядок:
бэкап → миграция → проверка → путь отката (AGENTS.md §15). Проверка:
`select o.name, u.email, m.role from memberships m join organizations o on o.id = m.organization_id join users u on
u.id = m.user_id order by o.name, m.created_at;` — у каждой организации ровно один `OWNER`; `platform_admins` и
`organization_extensions` пустые. Миграцию применяет владелец.

### 16.5. Права ролей (v1.14 — утверждено владельцем 27.09.2026, ADR-107)

Роль — готовый набор прав; прав у отдельного человека нет. Таблица живёт в домене
(`packages/domain/src/accounts/permissions.ts`) — одна на API и стойку.

|---|---|---|---|---|

| `dialogs` | ИИ-продавец: диалоги с гостями — читать, перехватить, ответить | да | да | да |
| `reports` | Статистика и «Оплаты» — просмотр | да | да | да |
| `refunds` | Возврат оплаты, сторно начисления (снятие штрафа за отмену — это сторно), корректировка счёта на уменьшение | да | да | — |
| `property` | Номерной фонд: номера и койки, категории, доступность | да | да | — |
| `rates` | Тарифы и цены; сменить тариф у существующей брони (Q-200); назначить брони без тарифа тариф с мягким штрафом (Q-201) | да | да | — |
| `channels` | Менеджер каналов и синхронизация Channex | да | да | — |
| `settings` | Настройки гостиницы, правила отмены, услуги, интеграции, сайт и его аналитика, первичная настройка объекта | да | да | — |
| `journal` | Журнал операций (решение владельца 05.10.2026) | да | нет | нет |
| `seller` | ИИ-продавец: инструкция, знания, подключения, проверка, агенты | да | да | — |
| `staff` | Сотрудники и приглашения; управляющий приглашает и отключает только администраторов | да | да | — |

- Своё — профиль, пароль, сеансы, подпись помощника — открыто всем ролям. Раздел «Платформа» — главному

  разрешить»): тариф записывается в бронь, дальше его меняют владелец и управляющий. У брони без тарифа штрафа нет
  (`NONE`, Q-103), так что назначенный тариф штраф не снимает, а добавляет.

## 17. Целевая архитектура двух вертикалей (v2.0 — заморожена владельцем 27.09.2026, ADR-100; кода нет)

> **Каноническая иерархия — ADR-104 / `ARCHITECTURE.md` v3 и §18 этого файла** (Q-199 закрыт владельцем 27.09.2026,
> вариант Б): `Organization → Business → Location → Property`, `vertical` — только на `Business`, у `locations` нет
> `organization_id` и `vertical`. Этот раздел — история линии ADR-100 (ADR-100 здесь — «целевая архитектура», не «вход
> окном на wetop.ai»); из него в силе только то, что §18 и ADR-104 повторяют. Реализация — миграция
> `20260927000030_platform_p1_business_location`; временная `…029` этой линии удалена до применения куда-либо.

Этот раздел фиксирует **утверждённую и замороженную** целевую иерархию и четыре финальных решения владельца.
Он — рамка, а не спецификация таблиц: детальные описания каждой новой сущности (поля, типы, ключи, CHECK)
добавляются в этот файл **пофазно, перед соответствующей миграцией** (AGENTS.md §2), и утверждаются владельцем
обычным порядком. Существующие разделы §1–§16 этим разделом не меняются. Полные документы:
`ARCHITECTURE.md` (замороженная сводка), `reports/hospitality-beauty-target-architecture-v2-2026-09-27.md`
(действующая редакция архитектуры, там же план миграции по фазам), v1 и аудит — рядом в `reports/`.

### 17.1 Замороженная иерархия

```
WETOP → Partner/Organization → Business → Location → Vertical Domain
```

- `Organization` (§13) — без изменений; получит `reporting_currency` (17.4).
- `Business` — новая сущность: направление/бренд, `vertical` (`HOSPITALITY` | `BEAUTY`) живёт здесь.
- `Location` — новая сущность: филиал/объект (адрес, таймзона, валюта); `vertical` — денормализованная
  неизменяемая копия с Business (тот же приём, что `sessions.organization_id` от membership).
- `Property` (§1) — **не переименовывается и не переписывается**: получает nullable `location_id` и становится
  HOSPITALITY-специализацией Location; все существующие FK (§1–§10) не трогаются. Hotel-enum'ы
  (`InventoryUnitKind`, `AccommodationKind`) не расширяются значениями других вертикалей.
- BEAUTY-домен (`Customer`, `Employee`+`EmployeeLocation`, `BeautyService`+`LocationService`, `WorkingHours`,
  `TimeOff`, `Appointment` c timestamptz `start_at`/`end_at` и GiST-запретом пересечений по мастеру) — параллельные
  новые таблицы; `Reservation` и `Appointment` физически не объединяются.

### 17.2 Решение 1 — RLS / регистрация (gate)

До публичного self-service подключения внешних организаций Row Level Security обязателен. До этого — только
вручную подключённые Partner/пилоты, и только после закрытия P0-долга изоляции (tenant-scope у `Guest`,
`AuditLog`, `ExternalEvent`, `ChannelOutbox`; ключи интеграций per organization — `IntegrationConnection`;
снятие фоллбэка `LUXX_APARTS_PROPERTY`; хардкоды таймзоны). Публичная регистрация не открывается
(`REGISTRATION_OPEN=0`); согласуется с ADR-056, ADR-061, ADR-099.

### 17.3 Решение 2 — Customer / CustomerBusiness

Канонический `Customer` — на уровне Organization (`organization_id` NOT NULL). Видимость/связь клиента в
конкретном Business — join-сущность `CustomerBusiness` (`customer_id` + `business_id`, PK по паре; создаётся при
первом обращении клиента в этот Business). Business-scoped доступ видит только клиентов со строкой своего
Business; Organization Owner — канонического клиента целиком. Существующий `Guest` (§3) не меняется; переход
Hospitality на Customer — отдельное будущее решение, additive.

### 17.4 Решение 3 — Exchange Rates

`organizations.reporting_currency` (ISO 4217) и политика курсов принадлежат Organization. `ExchangeRate`
(`organization_id`, `from_currency`, `to_currency`, `rate`, `as_of`, `source`; UNIQUE по четвёрке без source) на
MVP вводится вручную и используется всеми Business организации. Исторический `reporting_amount` на управленческих
записях — снимок по курсу на дату операции, при просмотре не пересчитывается. Оригинальные `amount`+`currency`
операций неприкосновенны (ADR-008 — деньги integer minor units, включая `reporting_amount`).

### 17.5 Решение 4 — Management Revenue idempotency

Управленческий Finance (`FinancialCategory`, `ManagementFinanceEntry` со scope `organization_id` +
`business_id?` + `location_id?`) — слой поверх операционного Folio/Payment (§6), не замена. Автоматическая
выручка (из закрытых Folio и оплаченных Appointment) обязана нести `source_type`
(`FOLIO`/`APPOINTMENT`/`MANUAL`) + `source_id` c `UNIQUE(source_type, source_id)` — повторный запуск sync-job не
создаёт дубль (у `MANUAL` `source_id` NULL, в UNIQUE не конфликтует). Ручной ввод — только расходы.

### 17.6 ~~Phase 2 — Location~~ (v2.2 — ОТМЕНЕНА 27.09.2026 решением Q-199, вариант Б)

> **Q-199 закрыт владельцем**: `locations` живёт по §18 (ADR-104), не по этому подразделу. Спецификация ниже
> сохранена как история линии ADR-100; её миграция `20260927000029_phase2_location` удалена до применения
> куда-либо. Действующая реализация — Platform P1 (§18, миграция `20260927000030_platform_p1_business_location`).

Поручение владельца 27.09.2026: «Начинай Phase 2 — Location foundation. Строго по замороженной ADR-100».
Содержание — v1 §D.3/§L Фаза 2 и v2 §12 (строка «2 — Location: без изменений от v1»); `Business` в этой фазе
НЕ добавляется — он придёт в Phase 2.5 вместе с `locations.business_id`.

- **enum `LocationVertical`**: `HOSPITALITY` | `BEAUTY`.
- **`locations`** — филиал/точка бизнеса:
  - `id` UUID PK;
  - `organization_id` UUID NOT NULL, FK `organizations` — чья точка;
  - `vertical` `LocationVertical` NOT NULL — денормализованная НЕИЗМЕНЯЕМАЯ копия (пишется при создании,
    каноническое хранилище появится на Business в Phase 2.5);
  - `name` NOT NULL; `address`, `phone`, `email` — nullable;
  - `timezone` NOT NULL; `currency` CHAR(3) NOT NULL;
  - `created_at` timestamptz NOT NULL DEFAULT now();
  - индекс `(organization_id)`.
- **`properties.location_id`** — UUID nullable, FK `locations` (ON DELETE RESTRICT), UNIQUE (1:1:
  Property — HOSPITALITY-специализация Location). `Property` не переименовывается, все её существующие FK
  (§1–§10) не меняются; `properties.organization_id` остаётся рабочим (окно совместимости до Фазы 8).
- **Backfill (детерминированный, в той же транзакции)**: для КАЖДОЙ строки `properties` без `location_id`
  создаётся ровно одна `Location` копией полей (`organization_id`, `'HOSPITALITY'`, `name`, `address`,
  `phone`, `email`, `timezone`, `currency`) и проставляется `properties.location_id`. Для Luxx — одна строка.
  NOT NULL на `location_id` не вводится.
- **RLS (§17 v1.13, ADR-103)**: `locations` — арендаторская таблица с организацией в строке: политика
  `rls_tenant` по `organization_id`, имя вносится в `RLS_TENANT_TABLES`.
- **Код**: `location-ref.ts` (кэш-резолвер Location организации, по образцу `property-ref.ts`); внутренняя
  реализация `organizationPropertyRef()` идёт через Location с фолбэком на прежний путь по
  `properties.organization_id`, пока миграция не применена; внешний контракт `PropertyRef` не меняется.
- Миграция `20260927000029_phase2_location` + `down.sql` (снять политику, колонку, таблицу, тип).
  **На рабочей базе применяет владелец.**

План и обоснование — `plans/rls-2026-09-27.md`. Ответы владельца: RLS-1 — гость принадлежит своей организации; RLS-2 —

### 17.1. Новые колонки

| Таблица | Колонка | Правило | Заполнение существующих строк |

по сущности (фоновые циклы пишут без переменной).

### 17.2. Роли и переменная арендатора

- `wetop_app` — `NOBYPASSRLS`, не владелец таблиц; права `SELECT/INSERT/UPDATE/DELETE` на таблицы схемы, `USAGE` на
  последовательности. Ею ходит API, когда за запросом стоит организация: вошедший человек или публичный путь её сайта.
  **v2.7, v2.9 (SEC-1b, ADR-124):** кроме таблиц из последней строки §17.3 — на них права ограничены (см. там).
- `wetop_service` — `BYPASSRLS`, те же права: фоновые циклы, вебхуки, служебные ключи, вход и регистрация (до
  организации), раздел «Платформа», скрипты.
- Роли создаёт миграция без входа (`NOLOGIN`); вход и пароль включает владелец (`ALTER ROLE … LOGIN PASSWORD`), пароль —
  только в `.env` (`DATABASE_URL` → `wetop_app`, `DATABASE_SERVICE_URL` → `wetop_service`).
- Переменная `app.org_id` ставится на соединение при каждой выдаче его из пула (`set_config(..., false)`; пулер Supabase
  в режиме сессий держит соединение за клиентом). Пустая переменная — ни одной строки у `wetop_app`.
- Уточнение плана (п. 2.3): вместо транзакции на каждый запрос — пул выбирает роль по контексту запроса и ставит
  переменную при выдаче соединения. Итог тот же: запрос организации не видит чужого, служебный путь видит всё.

### 17.3. Политики

Функция `app_current_org()` — `NULLIF(current_setting('app.org_id', true), '')::uuid`. На всех таблицах ниже —
`ENABLE ROW LEVEL SECURITY` и одна политика `TO wetop_app` (`FOR ALL`, `USING` = `WITH CHECK`). `FORCE` не ставится
(уточнение плана п. 2.5): владелец таблиц — роль миграций (`postgres`), и с `FORCE` API на ней остался бы без строк, если
миграция политик придёт раньше смены ролей. Без `FORCE` порядок выкладки ничего не ломает: политики действуют ровно на
`wetop_app`.

| Правило | Таблицы |
|---|---|
| `organization_id = app_current_org()` | `organizations` (по `id`), `memberships`, `sessions`, `invites`, `user_errors`, `seller_profiles`, `organization_extensions`, `seller_agents`, `wizard_drafts`, `properties`, `guests`, `audit_logs` |
| объект своей организации — `app_property_visible(property_id)` | `buildings`, `accommodation_types`, `inventory_units`, `reservations`, `rate_plans`, `channel_mappings`, `services`, `payments`, `tracked_sites` |
| через родителя (`EXISTS` к родителю, у которого своя политика) | `floors`, `physical_rooms`, `reservation_items`, `stay_guests`, `allocations`, `guest_documents`, `housekeeping_events`, `inventory_blocks`, `rate_plan_accommodation_types`, `daily_rates`, `restrictions`, `folios`, `charges`, `payment_allocations`, `refunds`, `web_sessions`, `web_pageviews`, `web_events`, `wizard_jobs`, `wizard_messages` |
| без RLS, только `wetop_service` читает по делу | `users`, `password_resets`, `email_verifications`, `platform_admins`, `wizard_sessions`, `wizard_surveys`, `wizard_events`, `external_events`, `channel_outbox`, `system_incidents` |

`users` без RLS намеренно: вошедшему нужны имена авторов журнала и коллег; почты чужих организаций API наружу не отдаёт.

**Права `wetop_app` на эти таблицы (v2.7 и v2.9, SEC-1b стадии A и B, ADR-124).** До v2.7 миграция `…026` выдала ей полный доступ ко

| Таблица | Права `wetop_app` |

Задача просила обосновать, нужен ли он на миграционный период. Не нужен: организация выводится через

колонка-правда потребовала бы составного FK `(business_id, organization_id) →
businesses(id, organization_id)`, чтобы не разъехаться (урок денормализации v1.12: её заводили только
ради UNIQUE в базе — здесь такого UNIQUE нет). Если Row Level Security (путь Б из ADR-061) потребует
`organization_id` на каждой строке — колонка добавится тогда, сразу с этим составным FK.

### 19.1. Уточнение перед фазой 3 (v2.9, УТВЕРЖДЕНО владельцем 03.10.2026, ADR-138)

**Статус.** Раздел §19 выше утверждён ADR-104 как состав и связи и сам требует уточнения планом среза
(«Перед фазой 3 раздел уточняется планом среза»). Здесь поля, типы, ограничения, RLS и порядок миграции.
План, `plans/beauty-phase3-2026-10-03.md`. **Утверждено владельцем 03.10.2026** («да давай делай», ADR-138);
по разделу сделан срез B1: миграция `20261003000044_beauty_domain`, модели в `schema.prisma`, домен
`packages/domain/src/beauty/`, отчёт `reports/beauty-b1-2026-10-03/README.md`. **Миграцию на рабочей базе
применяет владелец** (`AGENTS.md` §15).

**Поправка к §19, не новое решение.** В §19 у `Customer` указан `business_id` FK NOT NULL со ссылкой на
развилку Q-198. **Q-198 закрыт владельцем 27.09.2026** (freeze-решение №2, оно же в §17.3 и в
`ARCHITECTURE.md` §9): канонический клиент живёт на Organization, видимость в бизнесе ведёт
`CustomerBusiness`. Текст §19 приводится к принятому решению, как там и записано.

Деньги целыми тиынами (ADR-008), моменты `timestamptz` в UTC, показ в часовом поясе филиала
(`AGENTS.md` §13), удаления строк нет (архив статусом, как во всём §13).

#### `customers` (Organization)

`id` uuid PK; `organization_id` uuid NOT NULL FK → `organizations`; `first_name` varchar(100) NOT NULL;
`last_name` varchar(100) NULL; `phone` varchar(32) NULL; `email` varchar(320) NULL; `notes` text NULL;
`status` `CustomerStatus` (`ACTIVE` | `ARCHIVED`) default `ACTIVE`; `created_at`, `updated_at`.
UNIQUE (`organization_id`, `phone`) при непустом телефоне, индекс по `organization_id`. Гость §3 не
меняется: переход Hospitality на Customer отдельное будущее решение (§17.3).

#### `customer_businesses` (Customer × Business)

`customer_id` + `business_id`, PK по паре, `created_at`. Строку создаёт код при первом обращении клиента в
этот бизнес. Триггер: организация клиента равна организации бизнеса.

#### `employees` (Business)

`id` uuid PK; `business_id` uuid NOT NULL FK → `businesses`; `name` varchar(200) NOT NULL; `phone`
varchar(32) NULL; `email` varchar(320) NULL; `user_id` uuid NULL FK → `users` ON DELETE SET NULL (мастер со
входом в систему, уровень «Employee / Self» из `ARCHITECTURE.md` §13; самого входа фаза 3 не делает);
`status` `EmployeeStatus` (`ACTIVE` | `ARCHIVED`) default `ACTIVE`; `created_at`, `updated_at`.
UNIQUE (`business_id`, `user_id`) при непустом `user_id`, индекс по `business_id`.

#### `employee_locations` (Employee × Location)

`employee_id` + `location_id`, PK по паре, `created_at`. Триггер: филиал принадлежит бизнесу мастера.

#### `beauty_services` (Business)

`id` uuid PK; `business_id` uuid NOT NULL FK → `businesses`; `name` varchar(200) NOT NULL; `category`
varchar(100) NULL; `duration_minutes` integer NOT NULL CHECK > 0; `price` bigint NOT NULL CHECK >= 0
(тиыны); `currency` varchar(3) NOT NULL; `active` boolean NOT NULL default true; `created_at`,
`updated_at`. Индекс по `business_id`.

**Валюта каталога (Q-257).** В §19 у услуги есть цена и нет валюты, а операционная валюта живёт на филиале
(`locations.currency`, §18.2). Предложение: у услуги своя `currency`; действующая цена в филиале равна
`location_services.price_override` в валюте филиала, если переопределение задано, иначе цене каталога,
если валюта каталога совпадает с валютой филиала. Не совпадает и переопределения нет, услуга в этом
филиале не продаётся и экран говорит это словами. Так цена всегда имеет известную валюту и сеть с
филиалами в разных валютах не получает 1 000 в неизвестных деньгах.

#### `location_services` (Location × BeautyService)

`location_id` + `service_id`, PK по паре; `enabled` boolean NOT NULL default true; `price_override` bigint
NULL CHECK >= 0; `duration_override` integer NULL CHECK > 0; `created_at`, `updated_at`. Триггер: филиал и
услуга одного бизнеса. Пусто, действует каталог бизнеса с оговоркой о валюте выше.

#### `employee_services` (Employee × BeautyService)

`employee_id` + `service_id`, PK по паре, `created_at`. Триггер: мастер и услуга одного бизнеса.

#### `working_hours` (Employee × Location)

`id` uuid PK; `employee_id` uuid NOT NULL; `location_id` uuid NOT NULL; `weekday` smallint NOT NULL
CHECK 0..6; `time_from` time NOT NULL; `time_to` time NOT NULL CHECK `time_to` > `time_from`;
`created_at`, `updated_at`. UNIQUE (`employee_id`, `location_id`, `weekday`, `time_from`). Триггер: пара
мастер и филиал есть в `employee_locations`. **Форма графика (Q-251):** предложен недельный шаблон,
исключения через `time_offs`; календарные интервалы на дату добавляются позже additive.

#### `time_offs` (Employee)

`id` uuid PK; `employee_id` uuid NOT NULL FK → `employees`; `date_from` date NOT NULL; `date_to` date NOT
NULL CHECK >= `date_from`; `reason` varchar(200) NULL; `created_at`, `updated_at`. Индекс по
(`employee_id`, `date_from`).

#### `appointments` (Location)

`id` uuid PK; `location_id` uuid NOT NULL FK → `locations`; `customer_id` uuid NOT NULL FK → `customers`;
`employee_id` uuid NOT NULL FK → `employees`; `service_id` uuid NOT NULL FK → `beauty_services`;
`starts_at`, `ends_at` timestamptz NOT NULL CHECK `ends_at` > `starts_at`; `status` `AppointmentStatus`
(`BOOKED` | `CONFIRMED` | `DONE` | `NO_SHOW` | `CANCELLED`) default `BOOKED`; `price` bigint NOT NULL
CHECK >= 0 и `currency` varchar(3) NOT NULL (снимок цены и валюты на момент записи, не ссылка на каталог);
`notes` text NULL; `created_by` uuid NULL FK → `users` ON DELETE SET NULL; `created_at`, `updated_at`.

Пересечение записей одного мастера запрещает база, не код:

```
EXCLUDE USING gist (
  employee_id WITH =,
  tstzrange(starts_at, ends_at, '[)') WITH &&
) WHERE (status NOT IN ('CANCELLED', 'NO_SHOW'))
```

Расширение `btree_gist` уже стоит (миграция `…003`). Триггеры: мастер работает в этом филиале
(`employee_locations`), услуга включена в этом филиале (`location_services.enabled`), организация клиента
равна организации бизнеса филиала. Что ещё считать конфликтом, Q-255: предложено только занятого мастера.

#### RLS (дополнение к §17.3)

У `locations` нет `organization_id` по §18.3, поэтому Beauty не ложится ни на правило «своя
`organization_id`», ни на `app_property_visible`. **Сделано без новых функций** (поправка к предложению,
срез B1): у `locations` в миграции `…030` уже есть образец «через родителя»,
`EXISTS (SELECT 1 FROM businesses parent WHERE parent."id" = …)`, и политика родителя сама режет чужие
строки. Применён он; функции `app_business_visible` и `app_location_visible` не понадобились.

| Правило | Таблицы |
|---|---|
| `organization_id = app_current_org()` | `customers` |
| через родителя-`businesses` | `employees`, `beauty_services`, `customer_businesses` |
| через родителя-`locations` | `appointments`, `working_hours`, `location_services`, `employee_locations` |
| через родителя-`employees` | `employee_services`, `time_offs` |

Все десять таблиц вписаны в `RLS_TENANT_TABLES` (`packages/database/src/rls.ts`): реестр и база сверяются
тестом `rls-isolation`.

**Триггерные функции принадлежности пишут имена таблиц без схемы**, как `cash_operations_category_guard`
в §21: те же таблицы живут и в схеме `pms_test` (ADR-042), и одна функция должна работать в обеих.

**Поправка 03.10.2026 (миграция `20261003000045_beauty_function_search_path`).** В B1 путь у этих шести
функций не закреплялся вовсе: первая версия с `SET search_path = ''` и именами через `public.` роняла все
одиннадцать интеграционных тестов. Способ из миграции `…043` (той же датой, соседняя сессия, советник
Supabase «function_search_path_mutable») решает это лучше: путь закрепляется **по своей схеме**,
`current_schema()`, то есть `public, pg_temp` в `public` и `pms_test, public, pg_temp` в `pms_test`.
Неквалифицированные имена по-прежнему находят таблицы своей схемы, а подменить их таблицей из чужой схемы,
стоящей в пути раньше, уже нельзя. Функции Beauty приведены к этому правилу отдельной миграцией: тела не
менялись, только путь. Новые функции обязаны закреплять путь сами, это держит
`tests/integration/function-search-path.test.ts`.

#### Миграция

Одна миграция `20261003000044_beauty_domain` с `down.sql` (`AGENTS.md` §14): enum'ы, десять таблиц,
ограничения, триггеры принадлежности, exclusion constraint и RLS. Права `wetop_app` отдельной строкой не
выдаются: `ALTER DEFAULT PRIVILEGES` из миграции `…026` накрывает таблицы, созданные позже.
**Сделано в срезе B1 и проверено:** цепочка из 46 миграций на чистой базе, откат этой миграции возвращает
схему в прежнее состояние, своего дрейфа схемы она не даёт (разбор общего FAIL скрипта, в отчёте
`reports/beauty-b1-2026-10-03/README.md`). **На рабочей базе применяет владелец** (`AGENTS.md` §15), до
выкладки кода.

Онлайн-запись на сайте салона, вход мастера, зарплаты и комиссии, склад материалов, лояльность и
абонементы, напоминания клиенту, Beauty в аналитике и управленческих финансах (фаза 4). Финансовый контур

## 20. Производный тариф и промокод (v2.8 — УТВЕРЖДЕНО владельцем 29.09.2026; ADR-128, срез D4, Q-233, Q-230, Q-231)

**Статус.** Владелец 29.09.2026 выбрал минимальный набор: тариф-производный процентом от базового с окном продаж и
минимумом ночей, плюс промокод с процентом; один промокод на бронь, скидки не суммируются. **Утверждено владельцем
29.09.2026** вместе с решениями Q-230 (производный тариф в каналы не выгружается) и Q-231 (при двух скидках — одна
большая). Деньги — целые тиыны, процент — целый. Миграцию на рабочей базе применяет владелец.

### RatePlan — новые необязательные поля

```
parent_rate_plan_id       → RatePlan, NULL   ← тариф-родитель; NULL — обычный тариф
discount_percent          integer, NULL      ← 1…90; задан только вместе с parent_rate_plan_id
min_days_before_arrival   integer, NULL      ← «раннее бронирование»: заезд не раньше чем через N дней
max_days_before_arrival   integer, NULL      ← «last minute»: заезд не позже чем через N дней
min_nights                integer, NULL      ← «long stay»: срок проживания не короче N ночей
```

- У производного тарифа своих `DailyRate` нет: цена ночи = цена родителя на ту же дату и вместимость, умноженная на
  `(100 − discount_percent) / 100`, округление к ближайшему тиыну (половина — вверх). Функция одна, в домене рядом с
  `priceStay`; float не участвует.
- Ограничения (`Restriction`) производный тариф берёт у родителя; свои `min_nights` и окна добавляются сверху.
- Инвентарь общий с родителем: отдельного остатка производный тариф не имеет.
- Цепочка «производный от производного» запрещена: родитель — обычный тариф той же валюты и того же объекта.
- **Каналы.** По умолчанию производный тариф в Channex не выгружается: он продаётся на сайте и со стойки (Q-230).

### PromoCode — новая таблица

```
id
property_id               → Property
code                      строка, верхний регистр, уникальна в объекте
discount_percent          integer, 1…90
stay_from, stay_to        date, NULL          ← первая и последняя ночь проживания, включительно; NULL — без границы
max_uses                  integer, NULL       ← NULL — без предела
active                    boolean
created_at
```

- Использования не хранятся счётчиком: `Reservation.promo_code_id → PromoCode, NULL` (новое поле) даёт число
  использований запросом и след в брони. Скидка в счёт уходит обычным начислением со знаком минус, а не правкой цены.
- Один промокод на бронь. Промокод действует на тарифы сайта и стойки; условия «страна гостя» и «мобильный» не
  входят.
- **Конфликт скидок** (Q-231): если у выбранного тарифа уже есть `discount_percent`, гостю применяется одна
  большая скидка, суммирования нет; в предложении цены обе скидки показываются словами.

### Что не входит

Бесплатная ночь, суммирование скидок, лояльность и скрытые цены для участников, детские цены, промо по стране и
устройству, привязка промокода к каналу. Их нет ни в модели, ни в срезе D4.

### Миграция

Одна миграция: три колонки-фильтра и `parent_rate_plan_id`/`discount_percent` у `rate_plans`, таблица `promo_codes`
с политикой Row Level Security по образцу §17 и колонка `reservations.promo_code_id`. У неё есть `down.sql`, проверка
данных до применения (нет циклов и родителей другой валюты) и запись в журнал аудита (§10) на создание и правку
тарифа-производного и промокода. Применяет владелец на рабочей базе по `docs/deploy.md`.

Владелец утвердил модель 26.09.2026 ответом «Утверждаю модель для реализации и тестовой базы». Production migration этим не разрешена; текущий SellerProfile не заменяется молча.

- `Agent`: UUID, organization_id FK, name, scenario (sales/support), profile JSON с валидацией,
  lifecycle (draft/preparing/ready/error/archived), created_by FK, created_at, updated_at.
  Организация 1:N Agent. Существующий продавец переносится в один Agent своей организации;
  знания, диалоги и подключения должны получить agent_id с проверкой принадлежности организации.
- `WizardSession`: UUID, token_hash unique, ref до 200, last_step, created_at, expires_at.
  Исходный секрет не хранится в таблице/журнале. Истёкшая сессия не получает доступ к черновику.
- `WizardDraft`: UUID, guest_session_id unique FK, claimed_by nullable FK, organization_id nullable FK,
  business_name, niche, description, config JSON, sources JSON, revision integer,
  generated_revision nullable, generated_prompt, generated_knowledge JSON,
  test_messages_used integer >= 0, agent_id nullable unique FK, created_at, updated_at.
  1:1 с гостевой сессией; один черновик может стать только одним агентом.
- `WizardJob`: UUID, draft_id FK, kind (scan/generate/index), revision,
  state (queued/running/succeeded/failed), attempt, retry_at, masked_error, created_at, updated_at.
  Уникальный ключ (draft_id, kind, revision); новые настройки не используют старую генерацию.
- `WizardMessage`: UUID, draft_id FK, request_id, role, text, state, created_at;
  уникальный request_id в пределах draft, серверная история. Квота резервируется атомарно;
  технический отказ освобождает резерв, повтор с тем же ID не оплачивает второй ответ.
- `WizardSurvey`: guest_session_id unique FK, goal, team_size, leads_per_day, source, industry.
- `WizardEvent`: UUID, guest_session_id FK, event_type из allowlist, payload с лимитом,
  deduplication_key unique, created_at; без токенов, текстов переписки и паролей.
- Присвоение Agent, связь draft, запись outbox для индексации и право на trial — одна транзакция
  платформы. Бот применяет outbox идемпотентно; общая транзакция двух баз не предполагается.
- Email handoff: одноразовая серверная связь подтверждённой регистрации с draft, не guestToken
  в публичных метаданных. Повтор после входа возвращает прежний agent_id только владельцу.

До миграции: согласовать TTL/retention, trial с текущими расширениями и лимит расходов;
описать backup, backfill существующего продавца, validation и rollback без удаления его истории.


## 20. Business Agent: личность, филиал и рабочий продавец (v2.8, УТВЕРЖДЕНО ВЛАДЕЛЬЦЕМ 30.09.2026 с поправками; ADR-127, SA1.5)

> **Статус: утверждён владельцем 30.09.2026 с поправками (ниже и в 20.9).** Схемы, миграций и кода по нему ещё нет: их делает
> срез SA1.6 (только фундамент, без мастера), SA2 начинается после SA1.6 и отдельного «да». Продолжает утверждённый 26.09 раздел «Гостевой мастер и несколько агентов» (там же: организация
> 1:N `Agent`, существующий продавец переносится в одного агента, знания, диалоги и подключения получают `agent_id`) и
> ничего из него не отменяет. Здесь, то, чего в нём не хватало для рабочего продавца: привязка к филиалу, состояния, личность
> переносимого продавца, устройство базы бота и порядок выкладки. Контекст, аудит в `plans/business-ai-seller-v2-2026-09-29.md`.

### 20.1. Что сегодня и что меняется

Сегодня продавец в PMS и в боте один на организацию: `seller_profiles.organization_id`, первичный ключ, у бота профиль,
ключ модели, WhatsApp, знания и диалоги привязаны к `organization_id`. Таблица `seller_agents` (§ гостевого мастера), черновики,
которые с ботом не связаны и к филиалу не привязаны. Расширение «ИИ-продавец» (§16.3) действует на организацию и не меняется.

Предлагается: **агент, это продавец одного филиала.** Организация → Business → Location → агент; расширение по-прежнему
организации. Рабочий продавец, который есть сегодня, становится одним из агентов организации, без потери данных и без смены
ключей, которые уже стоят на сайтах партнёров и в консоли Meta.

### 20.3. Состояния агента

Хранится одно поле `lifecycle`, **ровно четыре значения (Q-SA-11, решено 30.09):** `draft` → `active` ⇄ `paused`; из любого,
`archived` (агент не удаляется, переписка и знания остаются читаемыми). Переход `draft` → `active`, только через чек-лист
запуска (SA9): филиал выбран, инструкция применена, доступ к данным объекта есть, канал без ошибки, проверочные сценарии пройдены.

`TESTING` и `ERROR` **не хранятся** и не являются состоянием жизненного цикла. Это вычисляемое здоровье и режим:
`lifecycle = active` при `channelHealth = error`, обычный случай (агент включён, WhatsApp временно с ошибкой). «Тестирование»,
шаг песочницы (SA7), «ошибка» вычисляется по `last_error` и состоянию каналов. Прежние шаги мастера `preparing`, `ready`,
`error` (раздел 26.09), тоже не хранимые состояния агента: это ход подготовки черновика, он показывается по заданиям мастера
(`WizardJob`), а не по `lifecycle`. Слова карточки SA1 (`agentStatus`) до SA9 остаются вычисляемыми и потом строятся из
`lifecycle` и здоровья.

### 20.4. Личность переносимого продавца: тот же идентификатор

Существующий продавец каждой организации становится агентом с **`id = organization_id`** (Q-SA-9, решено 30.09, да, **только для переносимых записей**: это совместимость миграции, а не правило модели). Причина
практическая: публичный ключ виджета, `sk_` + первые 24 hex `HMAC-SHA256(служебный ключ, "seller-widget|<id>")`
(`widgetOrgKey`), а адрес вебхука WhatsApp, `/channels/whatsapp/webhook/<id>`. Если `id` агента равен `organization_id`, ни один
тег на сайте партнёра и ни один адрес в консоли Meta не меняется, переписка и подключение не прерываются. Все новые агенты получают
обычный отдельный UUID и свои ключи. Пространства идентификаторов организаций и агентов не пересекаются в таблицах, коллизия
возможна только при случайном совпадении UUID и отсекается уникальностью `seller_agents.id`.

Правила переноса (одна транзакция, идемпотентно):
- агент создаётся для каждой организации, у которой есть строка `seller_profiles` **или** строка расширения «ИИ-продавец»;
- `name` = `bot_name` или «AI-продавец»; `scenario` = `sales`; `created_by` = самый ранний владелец организации;
- `location_id` = филиал самого раннего объекта организации, то же правило, что у фактов и котировки сегодня (нет объекта, NULL);
- `lifecycle` = `active`, если `profile_applied_at` не пуст и филиал определён, иначе `draft`;
- `seller_profiles.agent_id` = `organization_id`;
- вся существующая история переходит к этому агенту (Q-SA-12, решено 30.09, обязательно): переписка и сообщения, клиенты и контакты,
  знания (документы и чанки), подключение канала, журнал действий и учёт использования получают `agent_id` = этот агент.

### 20.5. База бота (`apps/ai-seller`, отдельная база, миграции применяет владелец)

**Как SA1.6 устроил переход (30.09.2026).** `agent_id` в таблицах бота, NULL-able, с внешним ключом на `agents`; при создании строки
с организацией ORM ставит `agent_id = organization_id`, миграция `0008` заполнила существующие. Строка `organizations`
остаётся источником, `agents`, её зеркало: слушатель модели обновляет агента вместе с организацией любым писателем.
Уникальность клиента по `(agent_id, channel, external_id)` добавлена рядом со старой, старая снимается в «сужении»; пока агент
один на организацию, они совпадают. Проверка `X-Agent` уже работает (20.6): чужой или неизвестный агент, 403, без заголовка,
агент с `id = organization_id`.

Изоляция в боте сегодня, фильтры приложения (политики RLS есть, но бот ходит владельцем таблиц). Это предложение на RLS в боте

### 20.6. Протокол платформа ↔ бот

- Панельные вызовы едут с `X-Organization` **и** `X-Agent`; бот проверяет, что агент принадлежит организации (сегодня
  `X-Organization` проверяется только как UUID), иначе 403. Старый бот `X-Agent` игнорирует, а новый бот без `X-Agent` берёт
  агента с `id`, равным `organization_id`,, выкладка в любом порядке не ломается, пока `id` переносимого агента равен `organization_id`.
- Сверка раз в минуту идёт по агентам: `PUT /seller/agents/<id>` с `organization_id`, названием, публичным ключом, доменами
  сайта филиала и `active` (расширение действует **и** `lifecycle = active`).
- Профиль, инструкция и факты: `PUT /seller/agents/<id>/{profile|prompt|facts}`; факты собираются по объекту филиала агента, а не
  по «самому раннему объекту организации».
- Котировка: `GET /bot/availability?agent=<uuid>&arrival&departure&adults`. Платформа сама переводит агента в филиал, объект и
  сайт бронирования; параметр `organization` остаётся для совместимости и означает агента с тем же `id`. Идентификатор агента бот
  берёт из своей личности агента, а не из аргументов модели.
- Публичный ключ виджета: на агента (`widgetOrgKey(служебный ключ, id агента)`), адрес вебхука, `/channels/whatsapp/webhook/<id агента>`.

### 20.7. Порядок выкладки, проверка и откат (AGENTS.md §14)

Расширение → перенос → сужение: на каждом шаге старый код продолжает работать.
1. Резервные копии базы PMS и базы бота (владелец).
2. Миграция PMS (добавление колонок, индекса, триггера, перенос 20.4) с `down.sql`; применяет владелец **до** выкладки кода.
3. Выкладка API и стойки: читают агента, при его отсутствии, организацию; пишут в оба.
4. Миграция бота (таблица `agents`, `agent_id` во всех таблицах; заполнение `agent_id = organization_id`); затем образ бота, читающий агента первым.
5. Проверка на Luxx до и после (ниже); только потом, перевод сверки на агентов.
6. Отдельной миграцией позже (после релиза без происшествий): `agent_id NOT NULL`, снятие устаревших колонок организации в боте.

Проверки до/после (запросы только на чтение, значения ключей не выводятся):
- агентов ровно столько, сколько организаций со строкой `seller_profiles` или расширения; активных без филиала, 0;
- в боте нет строк с пустым `agent_id`; число диалогов, документов и клиентов на агента равно прежнему на организацию;
- `phone_number_id` и адрес вебхука не изменились; `widgetOrgKey` для Luxx до и после совпадает;
- бот отвечает в виджете и в WhatsApp, `active` не сменился.

Откат: код, прежние образы (`pms-lux:rollback-<sha>`, образ бота); `down.sql` PMS удаляет добавленные колонки, индекс,
триггер и созданных переносом агентов (у которых `id = organization_id` и нет `wizard_drafts`), возвращая `seller_profiles`
первичный ключ `organization_id`; база бота на шаге 4 старые колонки не трогает, откат, образом и удалением `agents`.
Историю переписки при откате не удаляют.

### 20.8. Что этот раздел не вводит

Агента без филиала в рабочем состоянии и агента на «весь Business»; несколько неархивных AI-продавцов на филиал (другие типы агентов на филиале допустимы, Q-SA-2); ключ модели на агенте или на партнёре (Q-SA-10: ключ платформы, перевод, отдельным срезом); оплату и цену расширения по агентам, самообслуживание подключения; привязку разговора к брони и атрибуцию (Q-188);
инструменты записи и бронь из чата (ADR-086, Q-114, Q-115); роли Business Manager и Location Manager (Q-140); RLS в базе бота.

### 20.9. Решения владельца (30.09.2026)

- **Q-SA-2: ДА с поправкой.** Один неархивный AI-продавец (`scenario = 'sales'`) на Location. Другие типы агентов на филиале допустимы.
- **Q-SA-9: ДА.** Переносимый продавец сохраняет `id = organization_id`; новые агенты, отдельный UUID.
- **Q-SA-10: ИЗМЕНЕНО.** Ключ провайдера модели, секрет платформы WETOP; партнёр его не вводит. Организация, право, лимиты и учёт; агент, настройки модели без секрета; BYOK, если появится,, секрет организации. WhatsApp-секреты, на подключении канала агента.
- **Q-SA-11: ДА.** Хранимые состояния: `draft`, `active`, `paused`, `archived`. `TESTING` и `ERROR`, вычисляемые.
- **Q-SA-12: ДА, обязательно.** Вся история существующего продавца переходит перенесённому агенту.
- **Q-SA-7: ЧИНИТЬ СЕЙЧАС** отдельным баг-PR (BUG-WA-1), до дальнейшего расширения AI-продавца.

### 20.10. Инвариант принадлежности (SA1.6)

Цепочка должна сходиться в одну организацию: `agents.organization_id` = `businesses.organization_id` для филиала агента
(`location → business`). Проверка, в API и триггером БД (20.2); бот сверяет «агент принадлежит организации» при каждом панельном
вызове (20.6). Слои, которые SA1.6 вводит: **личность агента** (`seller_agents`, `agents` в боте), **подключение канала**
(WhatsApp и его секреты) и **учётные данные модели** (платформа), разные вещи и в одной таблице не хранятся.


### 20.11. Рантайм по агенту (SA2.5, план утверждён владельцем 30.09.2026 с поправками)

Схема §20.2–20.5 не менялась по составу; SA2.5 переводит **чтение и запись** на `agent_id` и готовит два шага выкладки.

**Правило.** Ни одна дверь, писатель и читатель данных продавца не выводит «агент = организация». Организация, граница арендатора
(права, расширение, дневной предел токенов, ключ модели); данные продавца, клиент, диалог, документ, промпт, подключение
WhatsApp, дедуп, живут в пределах `agent_id`. У перенесённого продавца `agent.id = organization_id` (§20.4): ключ виджета,
адрес вебхука и все прежние данные не меняются, но равенство ничего не решает, агент называется явно: из ключа в теге
(`agents.public_key`), из адреса вебхука (`agent_id`), из `X-Agent` панели.

**Домены виджета** не хранятся в агенте: allowlist вычисляется платформой во время запроса, `Agent → Location → действующие
сайты объекта филиала` (`GET /bot/agent-origins?agent=`, узкий ключ бота), бот кэширует ответ на минуту и держит последний
ответ сутки на случай сбоя платформы. Нет домена, черновик создаётся, публичный виджет на внешнем сайте не открывается.
`agents.hosts` остаётся зеркалом для прежнего образа и читается только как запасной путь при недоступной платформе.

**Котировка и факты.** `GET /bot/availability?agent=`, `agent` недоверенный селектор: платформа находит строку агента (не
архивного), а организацию, филиал, объект и сайт бронирования берёт только из неё; чужой, несуществующий и архивный отвечают
одинаково. Факты продавцу собираются по объекту филиала агента; «самый ранний объект организации» не читается. Прежний запрос
только по `organization` при нескольких неархивных AI-продавцах, 400.

**Протокол.** Панельные вызовы едут с `X-Organization` и `X-Agent`; без `X-Agent`, единственный агент организации, при двух и
более, 400 (не «самый ранний»); чужой или неизвестный, 403. Вместо `PUT /seller/agents/<id>/…` из §20.6 в SA2.5 использованы те
же маршруты с заголовком: отдельные пути агента появятся вместе с запуском (SA9).

**Порядок выкладки, «расширить → переключить → сузить»:**
1. **Расширить.** PMS-миграция `035` (предпроверка однозначности цепочки `seller_profile → Organization → legacy Agent → Business →
   Location`: любая неоднозначность, отказ без изменений; строгий выбор филиала, только единственный возможный; функции
   `seller_scope_precheck/assert`, `seller_agent_bind_location`), бот `0009` (агенты и `agent_id` добраны, уникальность по агенту
   рядом со старой, индексы). Старый код продолжает работать.
2. **Переключить.** Образ API и стойки, образ бота: рантайм читает по агенту и совместим со схемой шага 1.
3. **Проверить.** Смоуки Luxx (`docs/ops/sa25-agent-scope.md`).
4. **Сузить (отдельный релиз, отдельный PR).** PMS `036` (`seller_profiles`: первичный ключ `agent_id`, NOT NULL), бот `0010` (снять
   уникальность клиента и документа по организации, первичный ключ подключения WhatsApp, `agent_id`, CHECK «строка организации
   имеет агента»). До шага 4 у организации один агент, прежних ключей достаточно; второй агент, отвечающий гостям, возможен
   только после него.

Ключ провайдера модели и дневной предел токенов остаются на организации (Q-SA-10, уточнено 30.09).

## 21. Касса: операции мимо счетов гостей, переводы, статьи (УТВЕРЖДЕНО владельцем 02.10.2026 — «давай делай»; ADR-135 (в сессии — ADR-135; номер при интеграции 02.10.2026: ADR-135 занял top-nav))

Поручение владельца 02.10.2026 (снимки кассы старой системы); закрывает «F2 касса» из Q-207 п. 2
в части операций и остатков — кассовые смены и сверка наличных сюда **не входят** (отдельный ADR).
План — `plans/finance-cashbox-2026-10-02.md`. Миграция `20261002000040_cashbox` (+`down.sql`);
Q-236…Q-239 закрыты умолчаниями тем же ответом. **На рабочей базе миграцию применяет владелец.**

Принцип: гостевые оплаты в кассу не дублируются. Остаток по способу оплаты вычисляется:
Σ `payments` COMPLETED по способу − Σ `refunds` (по способу платежа) + поступления кассы
− расходы − переводы-откуда + переводы-куда. Валюта — валюта объекта.

```prisma
enum CashOperationKind { INCOME EXPENSE TRANSFER }

/// Статья кассы: справочник объекта. Удаления нет — архив через active (как Service).
model CashCategory {
  id         String            @id @default(uuid()) @db.Uuid
  propertyId String            @map("property_id") @db.Uuid
  kind       CashOperationKind // INCOME или EXPENSE; у TRANSFER статей нет
  name       String
  active     Boolean           @default(true)

  property Property @relation(fields: [propertyId], references: [id])

  @@unique([propertyId, kind, name])
  @@map("cash_categories")
}

/// Движение денег мимо счетов гостей: поступление, расход, перевод между способами.
model CashOperation {
  id          String            @id @default(uuid()) @db.Uuid
  propertyId  String            @map("property_id") @db.Uuid
  kind        CashOperationKind
  method      PaymentMethod     // для TRANSFER — «откуда»
  methodTo    PaymentMethod?    @map("method_to") // только TRANSFER — «куда»
  /// integer minor units (тиын), ADR-008; > 0
  amount      BigInt
  categoryId  String?           @map("category_id") @db.Uuid // статья INCOME/EXPENSE
  note        String?
  relatedId   String?           @map("related_id") @db.Uuid // комиссия → своя операция/перевод
  status      PaymentStatus     @default(COMPLETED) // VOIDED — аннулирование; прошлое не правится
  occurredAt  DateTime          @map("occurred_at") @db.Timestamptz(6)
  createdById String?           @map("created_by_id") @db.Uuid
  createdAt   DateTime          @default(now()) @map("created_at") @db.Timestamptz(6)

  property Property      @relation(fields: [propertyId], references: [id])
  category CashCategory? @relation(fields: [categoryId], references: [id])

  @@index([propertyId, occurredAt])
  @@map("cash_operations")
}
```

Правила (детали — план §3): начальный остаток — поступление со служебной статьёй
«Начальный остаток»; комиссия — связанный расход (`relatedId`) одной транзакцией, в базе
только сумма целыми тиынами; аннулирование — `status = VOIDED` с записью в журнал, комиссия
аннулируется вместе с основной; `EXTERNAL`, `DEPOSIT`, `CARD_GUARANTEE` в остатках кассы
не участвуют (Q-237); RLS — как у остальных таблиц организации (§17). `payments`, `refunds`,
`folios` не меняются. Открытые вопросы — Q-236…Q-239.

### 21.4. Сверка наличных (K4 — утверждено владельцем 02.10.2026, «давай продолжай»; дополнение к ADR-135)

/// Пересчёт денег в кассе: снимок «по системе» и факт. Аннулирования нет — ошиблись, сверили заново
model CashReconciliation {
  id          String        @id @default(uuid()) @db.Uuid
  propertyId  String        @map("property_id") @db.Uuid
  method      PaymentMethod
  /// остаток по системе в момент сверки, тиыны: потом не восстановить — операции сдвигают историю

### 21.5. Касса филиала (решение по Q-252 от 03.10.2026, ADR-143; кода нет, срез B7)

**Статус.** Владелец 03.10.2026 поручил закрыть вопросы по Beauty самому («ответь на все вопросы сам»).
По Q-252 решено: **Beauty не использует Folio §6**, а касса салона это этот раздел, расширенный с объекта
на филиал. Предложение ниже утверждено тем же поручением; **кода по нему нет**, он делается срезом B7
(`plans/beauty-phase3-2026-10-03.md`).

**Почему не Folio.** Счёт §6 висит на `ReservationItem`: без второй сущности «проживание» к записи салона
он не прикладывается, а заводить её ради денег значит придумать Beauty второе бронирование, чего ADR-104
прямо запрещает. Деньги записи это её собственный снимок `price` и `currency` (§19.1, сделано в B1).

**Что меняется.** `cash_categories` и `cash_operations` (и `cash_reconciliations`) получают
`location_id uuid NULL` FK на `locations`, а `property_id` становится необязательным; CHECK: ровно одно из
двух полей заполнено. Объект и филиал равноправны: гостиница ведёт кассу по объекту, как сейчас, салон по
филиалу. Остальное не меняется: статьи, переводы, комиссия, аннулирование, сверка наличных и правило
«гостевые оплаты в кассу не дублируются» остаются как в §21.1 и §21.4.

**Остаток и выручка.** У гостиницы остаток по способу считается как сейчас (§21.1). У салона гостевых
`payments` нет вовсе, поэтому остаток это только операции кассы филиала, а выручка за период это сумма
записей в статусе `DONE` по их снимку цены. Пересчёта валют нет (Q-239 открыт): филиалы с разными валютами
считаются раздельно.

**RLS.** Политика `rls_tenant` на трёх таблицах переписывается на «объект своей организации **или** филиал
своей организации»: `app_property_visible(property_id)` при заполненном объекте, иначе через родителя
`locations`, как у таблиц Beauty в §19.1.

**Миграция.** Своя, с `down.sql`: добавление колонки, снятие `NOT NULL`, CHECK, перезапись политик.
Существующие строки не трогаются, у них остаётся `property_id`. **На рабочей базе применяет владелец**
(`AGENTS.md` §15).

**Чего раздел не вводит:** кассовых смен (их нет и у гостиницы), пересчёта валют, зарплат и комиссий

## 24. Запросы оплаты: счёт Kaspi и ссылка банка в брони (УТВЕРЖДЕНО 03.10.2026 поручением владельца, ADR-144)

**Зачем.** Гостю нужно отправить счёт на предоплату или остаток: в Kaspi по номеру телефона (официального API для
внешнего софта у Kaspi нет), ссылку банка (Halyk ePay, Freedom, Tiptop) или реквизиты перевода. До этой таблицы такой
счёт жил в телефоне администратора, и оплата переносилась в WETOP руками без связи со счётом. Запрос оплаты связывает
выставленный счёт со счётом проживания и превращается в обычный платёж одним действием.

**`payment_requests`**

| Колонка | Тип | Правило |
|---|---|---|
| `id` | uuid | |
| `property_id` | uuid → properties | RLS `app_property_visible` |
| `folio_id` | uuid → folios | счёт проживания, на который ляжет оплата |
| `amount` | bigint | > 0, тиыны (ADR-008) |
| `currency` | char(3) | валюта счёта проживания |
| `method` | `PaymentMethod` | только `KASPI`, `HALYK`, `BANK_TRANSFER_PERSON`, `CARD_TERMINAL`: живые деньги, у которых бывает счёт или ссылка |
| `link` | text, null | ссылка банка, только `https://`, до 500 знаков; у Kaspi по телефону ссылки нет |
| `status` | `PaymentRequestStatus` | `PENDING`, `PAID`, `CANCELLED` |
| `payment_id` | uuid → payments, null, unique | платёж, которым запрос закрыт; `PAID` ⇔ не null |
| `note` | text, null | маска контактов, как у платежа |
| `created_by_id` | uuid → users, null | |
| `created_at`, `closed_at` | timestamptz | `closed_at` у `PAID` и `CANCELLED` |

**Правила.**
1. «Оплачено» создаёт обычный `Payment` (способ и сумма запроса, распределение на счёт запроса) и закрывает запрос
   **одной транзакцией** под блокировкой строки запроса: повтор нажатия не создаёт второй платёж (409).
2. Закрытый счёт проживания (`CLOSED`) запрос не принимает, как и платёж (аудит 26.09, С-25).
3. Отменить можно только `PENDING`; оплаченный запрос не отменяется: деньги возвращаются возвратом платежа.
4. Сумма запроса не обязана равняться остатку (предоплата первой ночи, часть суммы); экран предлагает остаток.
5. Ссылка банка в этой версии вставляется администратором из кабинета банка; адаптеры банков (создание ссылки и
   отметка оплаты по уведомлению банка) появятся после документации в `/docs` (Q-262), без изменения таблицы:
   у запроса добавится только внешний идентификатор.
6. Журнал: `finance.payment_request.created`, `.paid`, `.cancelled`.
7. **Запрос это второстепенный путь (07.10.2026, ADR-151).** Оплату на месте, на терминале и переводом стойка
   принимает без запроса, одним шагом; запрос нужен, когда гостю отправляют счёт заранее (5–6 раз в период).
   Аннулирование платежа по запросу (§6 v2.12) возвращает запрос в `PENDING` (`payment_id = null`,
   `closed_at = null`), замена платежа переводит `payment_id` на новый платёж, статус `PAID` остаётся.

**Миграция** `20261003000046_payment_requests` с `down.sql`; на рабочей базе применяет владелец.

## 25. Намерение брони ИИ-продавца (контракт утверждён 30.09.2026 и 01.10.2026, реализация 03.10.2026, ADR-144)

Оформление того, что записано в «30.09.2026: бронь из WhatsApp» выше. **`seller_booking_intents`**: `id`, `agent_id` →
seller_agents, `organization_id`, `property_id` (выводятся из агента на сервере, не из запроса бота), `conversation_id`,

## 26. Фискальный чек по запросу гостя (УТВЕРЖДЕНО 03.10.2026 поручением владельца, ADR-144; K2)

**Зачем.** Владелец 03.10.2026: «фискальный чек выдаём по запросу». Чек пробивает касса объекта (онлайн-ККМ); подключение
облачной кассы ждёт документацию оператора (Q-263). До этого WETOP хранит факт: по какому платежу, когда и кем выдан
чек и его номер из кассы, чтобы не пробить второй чек на тот же платёж и найти чек при споре.

**`fiscal_receipts`**

| Колонка | Тип | Правило |
|---|---|---|
| `id` | uuid | |
| `property_id` | uuid → properties | RLS `app_property_visible` |
| `payment_id` | uuid → payments, unique | один чек на платёж |
| `number` | text | номер чека или фискальный признак из кассы, 1–64 знака после обрезки пробелов |
| `issued_at` | timestamptz | когда отмечено |
| `issued_by_id` | uuid → users, null | кто отметил |

**Правила.**
1. Отметить можно только проведённый платёж (`COMPLETED`); второй чек на тот же платёж — отказ 409 (проверка под
   блокировкой строки платежа, уникальный индекс страхует).
2. Счёт проживания может быть уже закрыт: гость просит чек и после выезда.
3. Отметка не меняет деньги, платёж и кассу. Возврат по платежу с чеком в этой версии чек возврата не пробивает:
   экран напоминает, что чек возврата пробивается в кассе.
4. Журнал: `finance.receipt.issued` (платёж, номер).
5. Адаптер облачной кассы добавит внешний идентификатор и состояние отправки, не меняя смысла строки.

**Миграция** `20261003000048_fiscal_receipts` с `down.sql`; на рабочей базе применяет владелец.

Важные инварианты:

1. Проведенный приход не редактируется, только сторнируется.
2. Каждое движение имеет источник, автора, время и аудит.
3. Остаток не хранится как единственное изменяемое число. Он сходится с лентой движений и партиями.
4. Приход товара не равен оплате поставщику. Денежный расход создается при оплате.
5. Суммы хранятся только в integer minor units. Количество и проценты хранятся в decimal-safe виде, не float.
6. Продажа и списание не могут уменьшить остаток ниже нуля без отдельного утвержденного режима.
7. Себестоимость продажи и цена продажи фиксируются снимком на момент операции.

### BAR Property boundary repair (2026-10-05, утверждено владельцем)

BAR-REPAIR-2, migration 56 после неизменённой migration 55. Новых сущностей, полей,
связей, цен или stock/FIFO правил нет. База проверяет ownership при INSERT и UPDATE
relation fields независимо от RLS и роли, включая wetop_service с BYPASSRLS.

1. Property принадлежность после INSERT неизменяема для bar_categories, bar_products,
   bar_suppliers, bar_receipts, bar_stock_lots, bar_stock_movements, bar_sales.
   Для другого объекта создаётся новая сущность. Присваивание прежнего property_id допустимо.
2. Категория продукта (если задана) и обязательный поставщик прихода принадлежат той же Property.
3. bar_receipt_lines: receipt.property = product.property.
4. bar_stock_lots: property = product.property = receipt_line.receipt.property;
   product = receipt_line.product.
5. bar_stock_movements: property = product.property; если lot задан, lot.property = property
   и lot.product = product. Изменение родителя не может разрушать равенство с уже связанным потомком.
6. bar_sale_lines: sale.property = product.property, включая смену sale_id или product_id.
7. bar_supplier_payments: receipt.property = cash_operation.property.
8. bar_sales: заданные Folio, CashOperation и Charge через Folio принадлежат Property продажи.
   Если одновременно заданы folio_id и charge_id, Charge.folio_id = BarSale.folio_id.

Guards остаются SECURITY INVOKER; SECURITY DEFINER запрещён. Путь каждой новой функции
закреплён: current_schema(), public, pg_temp (public без повторения).
source_type/source_id движений остаются существующей ссылкой источника; отдельная
polymorphic ownership система не вводится. Это отдельный audit item, не новая модель.

### BAR external parent ownership (2026-10-05, approved Q-BAR-REVERSE-PARENTS)

Only updates breaking an existing BAR reference are denied. CashOperation.property_id
must preserve payment Receipt.property and Sale.property. Charge.folio_id must preserve
Sale.property and an explicit Sale.folio_id. Folio.reservation_item_id,
ReservationItem.reservation_id and Reservation.property_id must preserve the derived
Property of every direct folio sale and indirect charge sale. Same-property relinks and
unreferenced external rows remain mutable. No Hospitality/cashbox global immutability.
Concurrent parent mutation and BAR create/relink must preserve these invariants.

BAR link writes also fence referenced parent tuple versions, preserving all field values,
so a stale REPEATABLE READ parent transaction must retry instead of missing a new link.

Valid external reparenting with BAR dependencies fences the new ancestor tuple versions
too, so an older ancestor snapshot cannot miss the relocated BAR dependency.

## 28. Food Service v1 (MV6, approved by owner 2026-10-05)

Location -> DiningArea -> DiningTable; Location -> ServicePeriod; Location + existing Customer -> RestaurantReservation -> optional TableAssignment -> DiningTable. Business.vertical is the only vertical source, FOOD_SERVICE required. No new guest/customer identity, POS, payments or UI.

- DiningArea: UUID id, locationId FK, name varchar(200), sortOrder int default 0, active default true, createdAt/updatedAt timestamptz.

Unique(locationId,creationKey); indexes locationId+startsAt, customerId, status, servicePeriodId. Server derives endsAt from ServicePeriod; whole interval inside local service window.
- TableAssignment: reservationId UUID PK/FK, tableId FK, assignedAt timestamptz, assignedById nullable user FK, updatedAt. One table maximum; history only in audit.

New functions pin current_schema(), public, pg_temp. Catalog parent links are immutable in the API. Additive migration, no existing backfill; guarded down refuses any Food rows. Application rollback leaves data intact.

|---|---|---|

| `site_id` | UUID NOT NULL FK → `marketing_sites` ON DELETE RESTRICT | |

| `spec` | JSONB NOT NULL | документ `SiteSpec`, объект. Допустимый размер один: 256 КБ канонической записи, держит проверка документа и API. | `source` | enum `SiteVersionSource` | `MANUAL` (ручная правка), `AI` (результат `GenerationRun`), `IMPORT` (перенос готового документа, например при смене версии схемы). | `created_at` | timestamptz | |

**Что значит «неизменяемая».** После вставки строку не меняют и не удаляют командами приложения: `UPDATE` и
`DELETE` запрещает триггер, как у `audit_logs` (`20260925000022_integrity_guards`). В таблицу попадает только
документ, прошедший проверку схемы `SiteSpec` той версии, что указана в `schema_version`.

**Как правится черновик.** Правки не меняют версию, а создают новую: сохранение принимает `baseRevision`; если оно
не равно `revision` версии `latest_version_id`, ответ 409 (кто-то сохранил раньше); иначе в одной транзакции
вставляется версия `revision + 1` с `parent_version_id = latest_version_id`, и `latest_version_id` переставляется на неё.
Невалидный документ не сохраняется вовсе (ошибки показываются в редакторе). Ссылки на ассеты проверяются при
сохранении и повторно при публикации.

**Как публикация ссылается на версию.** `published_version_id` указывает на одну из версий сайта. Публикация и откат
только переставляют указатель и пишут строку `marketing_site_publications`; сама версия не меняется. Откат допускается
только на версию того же сайта, которая раньше была опубликована (есть в журнале), и только после повторной проверки
схемы и ссылок; рантайм видит её лишь после перестановки указателя.

Хранение (Q-272, решение владельца 06.10.2026): версии, которые хоть раз были опубликованы, хранятся всегда;
неопубликованные черновые можно удалять старше 90 дней, сохраняя не меньше 50 последних версий сайта. Очистки в
MKT3 нет, и сторож неизменяемости исключения для неё не делает: способ удаления решается срезом очистки.

**Как это держит база (MKT3).** Триггер `marketing_site_version_immutable` отклоняет `UPDATE` и `DELETE` версии
(пропускает только обнуление `created_by_id` по `ON DELETE SET NULL`), у ролей `wetop_app` и `wetop_service` на версиях
отозваны `UPDATE` и `DELETE`, на сайтах `DELETE` (отдельной миграцией прав 061, как Food 059: восстановление копии
повторяет только миграции без DDL). Триггер `marketing_site_version_guard`: версия без родителя только
с `revision = 1`, родитель того же сайта, `revision` ровно на 1 больше родителя. Триггер `marketing_site_guard`:
`latest_version_id` и `published_version_id` указывают только на версии этого сайта, `location_id` не меняется.
CHECK: формат `slug`, `published_version_id` задан при `PUBLISHED` и `PAUSED`, `archived_at` задан ровно при
`ARCHIVED`. Частичные UNIQUE: один неархивный сайт на `location_id`, неархивный `slug` глобально. После ревью владельца
(06.10.2026) добавлено: `tracked_site_id`, если задан, ведёт на `TrackedSite` объекта того же филиала (триггер
`marketing_site_guard`); зарезервированные адреса запрещены CHECK; `schema_version` совпадает с `schemaVersion`
документа; источник версии пока только `MANUAL`.

`PROCESSING → READY | REJECTED`, `READY → DELETED`, `REJECTED → DELETED`.

Удаление: только переходом в `DELETED` (у ролей приложения нет `DELETE`). Ассет хоть раз опубликованной версии остаётся
в хранилище: библиотека его прячет, текущий сайт и откат видят; ассет только из черновиков удаляется и из хранилища. Тип
файла проверяется по содержимому, EXIF и GPS снимаются, сырой файл не хранится нигде (`docs/marketing/site-assets-v0.md`).

человека (обрезан, без управляющих символов кроме перевода строки, до 1800 знаков); у `SECTION` версионированный конверт:
первая строка канонический JSON `{"pageId":"…","sectionId":"…","v":1}`, после перевода строки текст человека как есть
(до 1500 знаков, пусто значит команда по умолчанию). Текст не экранируется, поэтому конверт гарантированно не длиннее
`VARCHAR(2000)`; разбирают его только `encodeSectionInstruction` и `decodeSectionInstruction` домена. Текст команды
наружу не отдаётся и в журнал не пишется. Успешная правка даёт версию `base.revision + 1` с родителем `base`, только если
голова всё ещё `base` (иначе `BASE_VERSION_CHANGED`).

Что держит база (MKT6): вставка только `QUEUED`; переходы §29.8 (триггер `generation_run_guard`); форма состояния
(CHECK `generation_runs_status_shape`: `QUEUED` без версии и конца, `RUNNING` с началом, `SUCCEEDED` с версией, концом и без
ошибки, `FAILED` с концом и кодом, `CANCELLED` с концом); токены целые, не меньше нуля, `tokens_cached <= tokens_input`,
сумма только растёт; `attempts` от 0 до 3 и только растёт; сайт, вид, ключ, бриф, команда, база, автор и первое начало
не меняются; `base_version_id` и `output_version_id` только версии своего сайта, итоговая ссылается на эту задачу.
UNIQUE (`site_id`, `request_key`), UNIQUE `output_version_id`.
Образец исполнения: очередь в Postgres с воркером, как `channel_outbox` (`apps/api/src/channels/outbox.worker.ts:35-70`).
Таблица `wizard_jobs` (`schema.prisma:1985-2000`) не переиспользуется: она про мастер продавца и кодом не используется.

### 29.8 Жизненные циклы (три отдельных, не одним статусом)

`MarketingSite.state`:

```
(создан) → DRAFT ──publish──→ PUBLISHED ──pause──→ PAUSED ──resume──→ PUBLISHED
                                  │  ↑ publish/rollback (меняют только указатель)
DRAFT | PUBLISHED | PAUSED ──archive──→ ARCHIVED (конечное)
```

«Сгенерирован», «превью», «правится черновик» не состояния сайта: это факты версий и задач. Сайт в `PUBLISHED`
продолжает получать новые черновые версии; рантайм их не видит до следующей публикации.

`GenerationRun.status`: `QUEUED → RUNNING → SUCCEEDED | FAILED`; `RUNNING → QUEUED` при повторной попытке;
`QUEUED → CANCELLED | FAILED` (`FAILED` без вызова модели, например при восстановлении). Конечные: `SUCCEEDED`, `FAILED`,
`CANCELLED`; переходы держит триггер `generation_run_guard`.

`SiteDomain.status`: платформенный поддомен `PENDING → ACTIVE` при публикации; свой домен
`PENDING → VERIFYING → VERIFIED → ACTIVE`, `VERIFYING → FAILED` (можно начать заново новой строкой);
`ACTIVE → REMOVED`, `PENDING|VERIFIED|FAILED → REMOVED`.

### 29.9 Изоляция (MKT3, MKT6, MKT7 и MKT8 сделано)

Все шесть таблиц в `RLS_TENANT_TABLES` (с MKT8 и `site_assets`). Политика через цепочку, как у Food (`20261005000058_food_service_domain/migration.sql:207-211`):
`EXISTS (locations l JOIN businesses b ON b.id = l.business_id WHERE l.id = <location_id строки> AND b.organization_id = app_current_org())`;
для дочерних таблиц через `marketing_sites`. Функции триггеров закрепляют `search_path` (`current_schema(), public, pg_temp`).
`marketing_site_publications` и `site_domains` (MKT7): политика через свой сайт, FORCE; журнал без UPDATE и DELETE,
домены без DELETE (снятие только переходом в `REMOVED`).
`site_assets` (MKT8): политика по цепочке Location → Business → организация, как у сайта, FORCE; `wetop_app` и
`wetop_service` без `DELETE`. Рантайм читает служебным путём только строки по id ссылок текущей или превью-версии.
`generation_runs` (MKT6): политика через свой сайт, FORCE; `wetop_app` только читает и ставит задачу (SELECT, INSERT),
состояние, расход и результат меняет воркер служебным путём; `wetop_service` без `DELETE`.
Публичному рантайму роль `wetop_app` не выдаётся: он читает через узкий служебный путь API только **текущую**
опубликованную версию сайта, разрешённого по хосту, и безопасные публичные факты его Location
(`docs/marketing/README.md` §4.2, §4.4). Чтения версии по `id`, в том числе ранее опубликованной, у служебного ключа
рантайма нет; откат переставляет `published_version_id` только через управление.

### 29.11 Канонический сайт брони филиала (Q-275, вариант Б; в базе с MKT7)

`locations.booking_tracked_site_id` UUID NULL FK → `tracked_sites` ON DELETE SET NULL, индекс. Один явный сайт брони
на филиал гостиницы; ИИ-продавец (`bookingSiteForAgent`) берёт только его и проверяет, что сайт принадлежит именно
объекту этого филиала, `ACTIVE`, с включённой бронью и тарифом брони; запасного пути «самый ранний сайт» нет, пустой
или негодный указатель значит «котировки нет». Триггер `location_booking_site_guard` не даёт указать сайт объекта
другого филиала. Начальное заполнение `location_booking_backfill()` ставит указатель только филиалу, у которого ровно
один подходящий сайт; ноль или несколько оставляют NULL. Первая публикация управляемого сайта занимает указатель, только
если он пуст и других подходящих сайтов у объекта нет; уже выбранный сайт (даже приостановленный) она не заменяет. Выбор вручную: страница
«Маркетинг → Публикация сайта» (`PUT /marketing/site/booking-source`).

### 29.12 `SiteBuilderEntitlement`: лицензия конструктора филиала (MKT9.2)

`site_builder_entitlements`: `location_id` PK и FK → `locations` ON DELETE RESTRICT; `status ExtensionStatus`
(`TRIAL`, `ACTIVE`, `OFF`); `active_until timestamptz NULL` (пусто: бессрочно; у `TRIAL` обязателен, CHECK
`site_builder_entitlements_trial_until`); `note varchar(300)` (номер счёта, без персональных данных); `updated_by` FK →
`users` ON DELETE SET NULL; `created_at`, `updated_at`. Триггер `site_builder_entitlement_guard`: только филиал
гостиничного бизнеса, филиал строки не меняется. Действует, если `TRIAL` или `ACTIVE` и срок не вышел (те же правила, что
у расширений организации §16.3). Выдаёт, продлевает и выключает только главный администратор платформы служебной ролью;
`wetop_app` только `SELECT`; удаления нет ни у кого, выключение это `OFF`. Заполнение миграцией: `ACTIVE` без срока
только филиалам, у которых сайт уже был. Запись в конструкторе (создание сайта, сохранение, восстановление, весь ИИ,
картинки, публикация, возобновление, откат, знания, закладки) требует действующей лицензии в той же транзакции; пауза,
архив и выбор сайта брони не требуют. Опубликованный сайт лицензия не выключает. Воркер ИИ перепроверяет лицензию перед
платным вызовом и без неё завершает задачу `LICENSE_UNAVAILABLE` (код добавлен в CHECK `generation_runs_error_code`).

### 29.13 `SiteAiRun`: разговор с ИИ сайта (MKT9.2)

`site_ai_runs`: режим `SiteAiRunMode` (`CHAT`, `PLAN`, `DESIGN`), состояние `SiteAiRunStatus` (`QUEUED`, `RUNNING`,
`SUCCEEDED`, `FAILED`), `request_key` (UNIQUE с `site_id`), `requested_by_id`, `base_version_id` (только версия этого
сайта, триггер), `brief_hash`, `user_text varchar(4000)` (не пустой), `assistant_text varchar(12000)`, `payload jsonb`
(проверенная структура ответа по режиму, до 32 КиБ, CHECK `site_ai_runs_payload_size`), модель, токены (как у
`generation_runs`, кэш часть входа), попытки до трёх, `next_attempt_at`, `dispatched_at`, код и текст ошибки (тот же
словарь плюс `LICENSE_UNAVAILABLE`), время создания, начала и конца. Триггер `site_ai_run_guard`: новая только в
`QUEUED`, переходы как у сборки без `CANCELLED`, конечное состояние не меняется, запрос человека, режим, ключ, база,
бриф и автор не меняются, токены и попытки только растут. **Версий не создаёт никогда**: колонки выходной версии нет,
сборка по плану идёт обычной задачей `generation_runs` с `request_key`, равным id плана (второй не будет). Промпт и сырой
ответ модели не хранятся. `wetop_app` `SELECT, INSERT`; воркер `UPDATE`; удаления нет. Общие правила с
`generation_runs`: одна активная задача ИИ на сайт, платные вызовы организации по одному, один дневной пул токенов
организации, неизвестный расход останавливает ИИ сайта организации до следующих суток UTC, 10 запросов в час на
человека в организации на все режимы. История разговора для модели (доводка 08.10) собирается из этих строк и успешных
`generation_runs` того же сайта при каждом вызове и нигде не хранится; ответ на вопросы плана хранит самодостаточный
`user_text` (исходная просьба, вопросы, ответы), связи с родительской задачей в схеме нет.

### 29.14 `MarketingSiteVersionBookmark`: закладка версии (MKT9.2)

`marketing_site_version_bookmarks`: `id`, `site_id` FK, `version_id` FK, `label varchar(120)` (не пустая),
`created_by_id`, `created_at`; UNIQUE `(site_id, version_id)`. Триггер `marketing_site_bookmark_guard`: версия этого
сайта, сайт и версия закладки не меняются, не больше 20 закладок на сайт (замок по сайту против гонки). Человек с правом
`settings` ставит, переименовывает и снимает при действующей лицензии.

### 29.15 Один филиал, один сайт; знания проекта (MKT9.2)

Частичный UNIQUE `marketing_sites_location_active_key` (MKT3) заменён полным `marketing_sites_location_id_key` без
условия: у филиала один сайт навсегда, архивный сайт филиал не освобождает, нового проекта, копии и ремикса нет;
эксперименты это новые версии того же сайта. Миграция сначала проверяет, что ни у одного филиала нет двух сайтов, и
иначе останавливается с перечнем филиалов, ничего не исправляя сама. В Prisma `Location.marketingSite MarketingSite?`.
`marketing_sites.builder_instructions varchar(5000) NULL`: знания проекта, постоянные указания ИИ этого сайта; это
данные для модели (старшинство: правила системы, правила SiteSpec, бриф, знания, запрос человека), в журнал пишется
только длина.

### 29.10 Чего в модели нет

Страниц и секций отдельными таблицами (они внутри `SiteSpec`), пользовательского CSS и JavaScript, отзывов, блога,
формы обратной связи, оплаты на сайте, изображений, созданных ИИ, сайтов Beauty и Food (возможны позже без смены
владельца, `docs/marketing/README.md` §8).
С MKT9.2 также нет: второго проекта, копии или ремикса сайта филиала, нескольких черновиков, параллельной очереди ИИ,
своего кода и своей базы у сайта, автопубликации ИИ, промптов и сырых ответов модели в базе.

## 31. Область доступа сотрудника, приостановка и данные приглашения (v2.15, УТВЕРЖДЕНО владельцем 09.10.2026 — «давай да делай дальше» на предложения по Q-286…Q-290; ADR-156)

Основание: ТЗ «Сотрудники и доступ 2.0» (аудит — `plans/staff-access-2-audit-2026-10-09.md`, план — `plans/staff-access-2-scopes-2026-10-09.md`).
Ответы владельца: Q-286 да (привязка к бизнесам и филиалам), Q-287 да (роль на назначение), Q-288 пока нет (новые роли «бухгалтер» и
«маркетолог» не вводятся), Q-289 да (приостановка вместо удаления), Q-290 да (имя, телефон, должность хранятся в приглашении).
Права ролей (§16.5, ADR-107) не меняются: роль остаётся готовым набором, меняется только **где** она действует.

### 31.1. Область доступа `membership_scopes`

| Колонка | Тип | Правило |
|---|---|---|
| `id` | uuid PK | |
| `organization_id` | uuid NOT NULL FK → `organizations` | чья запись; по нему RLS (§17.3) |
| `user_id` | uuid NOT NULL FK → `users` | вместе с организацией указывает на членство |
| `role` | `MembershipRole` NOT NULL | `MANAGER` или `STAFF`; `OWNER` не бывает (CHECK и триггер) |

Смысл: **нет строк, значит вся организация, как до §31** (поэтому данные существующих людей не переносятся и ничего не
меняется до первого назначения). Есть строки: человек работает только в этих бизнесах и филиалах, а роль в каждом месте
берётся из строки (`packages/domain/src/accounts/scopes.ts`: `roleAt`). Назначение на бизнес покрывает все его филиалы;
запрос уровня бизнеса без филиала открывает только назначение на весь бизнес. `memberships.role` у человека со строками
равна старшей из назначенных ролей (ведёт сервис) и нужна там, где решение организационное (управление командой).
Владелец области не имеет: ограничить владельца нельзя.

Уникальность (частичные индексы в миграции, Prisma их не описывает): `(organization_id, user_id, business_id) WHERE
location_id IS NULL` и `(organization_id, user_id, business_id, location_id) WHERE location_id IS NOT NULL`. Дополнительно
запрещено (проверка в домене и сервисе): филиальная строка внутри бизнеса, который назначен человеку целиком. Триггер
`membership_scope_guard` на INSERT/UPDATE: бизнес принадлежит организации строки, филиал принадлежит бизнесу, членство
`(user_id, organization_id)` существует, роль не `OWNER`.

Журнал: `membership.scope.added`, `membership.scope.removed` с `before`/`after` (роль, бизнес, филиал; без секретов).

### 31.2. Приостановка `memberships.status`

`MembershipStatus`: `ACTIVE` (по умолчанию, прежние строки), `SUSPENDED`. Колонки `suspended_at`, `suspended_by` (оба
NULL при ACTIVE; CHECK: оба заполнены или оба пусты). Приостановленный не входит и теряет сеансы организации в момент
приостановки; в местах по тарифу не считается; возврат одним действием. Владельца приостановить нельзя; последнего
владельца нельзя ни приостановить, ни понизить (правило §16.1 остаётся). Журнал: `membership.suspended`, `membership.resumed`.

### 31.3. Данные приглашения `invites`

Добавляются `first_name varchar(100) NULL`, `last_name varchar(100) NULL`, `phone varchar(16) NULL` (+E.164, как в
`memberships.phone`, CHECK), `position varchar(100) NULL`, `scopes jsonb NULL` (список `{role, businessId, locationId|null}`).
Принятие приглашения переносит имя в `users.name` (если у человека его ещё нет), телефон и должность в членство, список
в `membership_scopes`, а `memberships.role` ставит по старшей из ролей. Список проверяется при создании приглашения и ещё
раз при принятии (бизнес или филиал могли архивироваться). Пустой или отсутствующий список: вся организация.

### 31.4. Права приложения и RLS

`membership_scopes` — `organization_id = app_current_org()` (§17.3, `ENABLE`, без `FORCE`). `wetop_app`: SELECT, INSERT,
UPDATE, DELETE (человека с правом `owner` или `staff` по ролям API); отдельной миграцией, как у MKT9.2. Миграции:
`…072_membership_scopes` (колонки, таблица, индексы, триггер, политика), `…073_membership_scopes_grants` (права).

### 31.5. Чего в модели нет

Прав отдельного человека (роль остаётся готовым набором), пользовательских ролей, временных назначений со сроком,
ограничений владельца, области на уровне организации выше бизнеса (организация это вся организация).

### 31.6. Как область принуждается (S3, внедрено 09.10.2026)

Всё на сервере; стойка лишь не показывает то, что API откажет. У человека с областью (не владелец, есть назначения):
1. `AuthorInterceptor` для каждого маршрута с правом (`@Access`, кроме `self`, `platform`, `service` и `@Public`) требует выбранный
   и проверенный филиал (или бизнес, если назначен целиком): нет выбора — 403 «выберите доступный филиал»; филиал вне
   назначений — 403; в месте действует **роль назначения** (`roleAt`), и право маршрута проверяется по ней (`canAt`).
2. Права уровня организации (`staff`, `owner`, `journal`) закрыты полностью (`RoleGuard`, `ORGANIZATION_LEVEL_PERMISSIONS`):
   управляющий одного филиала не приглашает людей и не читает общий журнал.
3. Маршруты с `@ScopeAware` (`GET /branches`, `GET /branches/overview`) выполняются без выбора, но фильтруют ответ по назначениям;
   сводка отчётов ещё и по праву `reports` в каждом филиале.
4. `GET /auth/me` отдаёт роль выбранного места и `restricted: true`; стойка прячет организационные разделы.
5. Приостановленный не проходит ни вход, ни сессию (`AuthService`, §31.2).

**Границы, которые нужно знать.** RLS остаётся по организации (§17), сужение по филиалам делает код. Фоновые циклы,
служебные ключи и публичные пути сайтов области не имеют. **Не доказано тестами:** чтение по явному идентификатору объекта
другого филиала той же организации (бронь, гость, счёт) там, где репозиторий ищет по организации, а не по выбранному
филиалу; это проверяется отдельным обходом маршрутов и до него область нельзя называть полной границей безопасности данных
внутри организации. Доказано: выбор филиала и сводки, маршруты по выбранному месту, роль по месту, закрытые организационные
разделы, приостановка.

## 31. Карточка объекта: описание, правила проживания, удобства (v2.12, поручение владельца 09.10.2026 «сделай всё 1 в 1 как на верстке, логику всех полей, чтобы работало»; ADR-156, Q-293)

Экран «Настройки объекта» получает сведения, которых в `properties` не было. Всё добавляется **колонками той же
строки** `properties`: новых таблиц, прав и политик RLS этот срез не вводит (политика `rls_tenant` на `properties`
уже стоит и покрывает колонки). Миграция аддитивная, все колонки с умолчанием или NULL, откат `down.sql` их снимает.

### 31.1 Колонки `properties`

| Колонка | Тип | Смысл |
|---|---|---|
| `description` | `varchar(500)` NULL | краткое описание для сайта, каналов и разговора с гостем |
| `website` | `varchar(300)` NULL | адрес сайта объекта, только `http`/`https` (проверка в домене) |
| `public_name` | `varchar(200)` NULL | имя в договоре и счёте гостя; пусто, пока не задано, тогда печатается `name` |

| `late_check_out` | `boolean` NOT NULL DEFAULT false | поздний выезд возможен при наличии мест |
| `children_allowed` | `boolean` NOT NULL DEFAULT true | можно с детьми |
| `pets_allowed` | `boolean` NOT NULL DEFAULT false | можно с питомцами |

| `cancellation_rule` | `varchar(16)` NOT NULL DEFAULT `FREE_1D` | подпись правила отмены для карточки: `FREE_1D`, `FREE_3D`, `FREE_7D`, `NON_REFUNDABLE` |

| `min_guest_age` | `smallint` NOT NULL DEFAULT 18 | минимальный возраст гостя, 0..99 |
| `quiet_hours_from`, `quiet_hours_to` | `varchar(5)` NULL | тихие часы «ЧЧ:ММ», оба или ни одного |
| `house_rules_note` | `varchar(500)` NULL | дополнительные комментарии к правилам |

оба поля тихих часов заданы вместе или оба пусты. Остальное (формат адреса сайта, формат времени, состав каталога
удобств) проверяет домен: одна функция для API и стойки.

### 31.2 Чего срез НЕ делает

- **Деньги и бронирование не меняются.** `cancellation_rule` и `deposit_rule` это подписи для карточки объекта, сайта и
  разговора с гостем. Штраф за отмену по-прежнему считает тариф (`rate_plans.cancellation_penalty`, ADR-115, SET4), залог
  никуда не списывается и не удерживается. Что делать, если подпись и тариф разойдутся: **Q-293**.
- Ранний заезд и поздний выезд только отметка «возможно». Доплаты и ограничения по времени это отдельные правила
  (ссылка «Настроить» ведёт в тарифы), автоматически ничего не начисляется.
- В Channex, ARI и eQonaq ничего не уходит. Новые поля читает только стойка и ИИ-продавец (позже, отдельной задачей).
- «Количество номеров» и «Количество мест» не хранятся: считаются по активным единицам продажи (`ROOM` и `BED`,
  ADR-013) и на экране только читаются.
- Фото и договор (PDF) требуют закрытого хранилища и связи с библиотекой изображений: отдельный срез §31.3.

### 31.3 Фото и договор: `property_media` (ADR-156, вариант А из Q-294, поручение «продолжай что осталось» 09.10.2026)

Одна таблица на оба вида файлов объекта, физически те же закрытое хранилище и обработка изображений, что у библиотеки сайта
(MKT8), но **без связи с лицензией конструктора**: фото и договор нужны настройкам объекта, а не сайту.

`property_media`: `id` uuid PK, `property_id` FK (RESTRICT), `kind` varchar(8) CHECK `PHOTO` | `CONTRACT`, `position` int
(порядок фото, 0 у договора), `file_name` varchar(200) NULL (имя файла договора для показа), `mime_type` varchar(40),
`storage_ref` varchar(500) UNIQUE (ключ вида `property-media/<property_id>/<id>/<sha256>.webp|pdf`, CHECK выводит его из
строки целиком), `byte_size` int CHECK 1..10 485 760, `width`, `height` int NULL (у PDF пусто), `sha256` char(64),
`alt` varchar(200) NULL, `created_by_id` FK users SET NULL, `created_at`, `deleted_at` timestamptz NULL.
Живая запись это `deleted_at IS NULL`. Частичные UNIQUE: `(property_id, kind, sha256)` среди живых (повтор того же файла
это тот же файл), и один живой `CONTRACT` на объект (новый договор заменяет прежний: прежний получает `deleted_at`). Не
больше 20 живых фото на объект проверяет API. Физически запись не удаляется: удаление это `deleted_at`, объект в
хранилище остаётся (по образцу `site_assets`). Файл хранится только обработанным: фото WebP без EXIF (длинная сторона до
2400), договор как есть, но только если начинается с `%PDF-`. RLS `rls_tenant` по `app_property_visible(property_id)`;
права `SELECT, INSERT, UPDATE` без `DELETE` отдельной миграцией. Откат `down.sql` снимает таблицу, объекты в хранилище
остаются. Без `SITE_ASSET_STORAGE=s3` загрузка отвечает 503 словами «Хранилище файлов не включено», чтение отдаёт
`storage: OFF`.
