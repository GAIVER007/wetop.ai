# DECISIONS (ADR)

Формат записи: дата, проблема, варианты, решение, причина, последствия.
Незаписанное решение считается непринятым (AGENTS.md §3).

## ADR-001 — Single-property MVP

**Дата:** 2026-09-07
**Проблема:** строить ли сразу multi-tenant / multi-property.
**Варианты:** (a) сразу SaaS multi-tenant; (b) один объект, но сущность `Property` в схеме; (c) жёстко один отель без Property.
**Решение:** (b) — single-property MVP, сущность `Property` присутствует в модели.
**Причина:** сначала доказать работу на реальном объекте. Но база не должна содержать
предположение «в мире существует только один отель».
**Последствия:** UI работает с одним property; multi-property можно добавить позже
без переписывания схемы. Все запросы фильтруются по `property_id` с самого начала.

---

## ADR-002 — Modular monolith, не microservices

**Дата:** 2026-09-07
**Проблема:** архитектурный стиль backend.
**Варианты:** microservices; modular monolith; monolith без модулей.
**Решение:** modular monolith.
**Причина:** команда маленькая, MVP 8 недель, distributed complexity сейчас не нужна.
Для 88 номеров Kubernetes/Kafka — лишняя сложность.
**Последствия:** границы модулей поддерживаются дисциплиной пакетов
(`packages/domain`, `packages/integrations`), а не сетью.

---

## ADR-003 — PostgreSQL — source of truth

**Дата:** 2026-09-07
**Проблема:** какая система считается первичной по данным.
**Решение:** PostgreSQL PMS. Channex / Exely / eQonaq **не** являются основной БД PMS.
**Причина:** без единого source of truth сверка невозможна.
**Последствия:** любые внешние данные импортируются и хранятся локально;
внешние ID хранятся как ссылки, а не как замена собственных ключей.

---

## ADR-004 — Channels через adapter interface

**Дата:** 2026-09-07
**Проблема:** зависимость бизнес-логики от конкретного channel manager.
**Решение:** `ChannelProvider` — интерфейс. Первый adapter — Channex.
**Причина:** смена/добавление провайдера не должны затрагивать домен.
**Последствия:** бизнес-модель PMS не знает про Channex IDs; маппинг живёт
в `ChannelMapping`. Запрещён импорт Channex SDK вне `packages/integrations`.

---

## ADR-005 — Room и sellable inventory разделены

**Дата:** 2026-09-07
**Проблема:** dorm с койко-местами не укладывается в модель «номер = единица продажи».
**Решение:** `PhysicalRoom` (помещение) и `InventoryUnit` (ROOM | BED) — разные сущности.
Dorm содержит несколько bed inventory units.
**Причина:** самый дорогой возможный архитектурный промах — смешать их (риск №1).
**Последствия:** availability считается по `InventoryUnit`; private room — тоже
InventoryUnit (kind=ROOM), чтобы код был единообразным.

---

## ADR-006 — Reservation и Allocation разделены

**Дата:** 2026-09-07
**Проблема:** OTA продаёт категорию, физический номер назначается позже.
**Решение:** `Reservation` → `ReservationItem` (категория) → `Allocation` (юнит).
**Причина:** бронь категории должна существовать без назначенного физического номера.
**Последствия:** переселение = закрытие одной Allocation и открытие другой,
а не мутация брони. История переселений сохраняется.

---

## ADR-007 — Все внешние события идемпотентны

**Дата:** 2026-09-07
**Проблема:** повторный webhook может создать дубль OTA-брони.
**Решение:** `ExternalEvent` с UNIQUE (provider, external_event_id); обработка через
состояние + retry.
**Причина:** дубль или потеря брони — недопустимый отказ.
**Последствия:** любая интеграция сначала пишет событие, потом обрабатывает.
Обработчик обязан быть повторно-безопасным.

## ADR-008 — Финансы без float

**Дата:** 2026-09-07
**Решение:** деньги — integer minor units (тиын) либо decimal-safe представление.
**Причина:** JS floating point даёт расхождения в копейках, которые ломают сверку.
**Последствия:** все API отдают минорные единицы + код валюты; форматирование — только на UI.

## ADR-009 — Персональные данные в Казахстане

**Дата:** 2026-09-07
**Решение:** основная база персональных данных production размещается на территории
Казахстана. Передача данных зарубежным сервисам рассматривается отдельно.
**Причина:** законодательство РК о персональных данных.
**Последствия:** выбор хостинга БД ограничен; любой внешний сервис, получающий PII,
проходит отдельное решение. См. `SECURITY.md`.
**Открыто:** конкретный провайдер/регион ещё не выбран.

## ADR-010 — Реальные паспорта не попадают в dev/test

**Дата:** 2026-09-07
**Решение:** реальные документы гостей никогда не используются в development/test,
включая fixtures и prompts к AI-агентам.
**Причина:** утечка PII через тестовые данные и логи — реальный сценарий.
**Последствия:** нужен генератор synthetic-гостей; анонимизация при импорте
production-выгрузок в dev.

## ADR-012 — Порядок миграции OTA

**Дата:** 2026-09-07
**Решение:** каналы переключаются по одному, начиная с минимального по объёму;
Booking.com — последним. Следующий канал не подключается, пока предыдущий не прошёл
reconciliation с расхождением 0.
**Причина:** одновременное переключение всех каналов делает откат невозможным.
**Последствия:** cutover растягивается, но остаётся обратимым. См. `CUTOVER.md`.

## ADR-013 — Койко-место = единица продажи (модель Exely)

**Дата:** 2026-09-07
**Проблема:** в Exely койка — запись в справочнике номеров. Физической планировки нет:
какая койка в какой комнате, ярус, окно — таких полей не существует. `PhysicalRoom`
из ADR-005 при миграции нечем заполнить.
**Варианты:**

| | Вариант А — повторить Exely | Вариант Б — настоящая иерархия |
|---|---|---|
| Суть | каждая единица продажи — самостоятельная ячейка; `PhysicalRoom` = формальная обёртка 1:1 | собрать планировку замером, койки привязать к комнатам |
| Миграция | тривиальная, данные есть | требует работы на объекте |
| Что даёт | ничего сверх текущего | уборка по комнатам, «вся комната для группы», гендерное правило на комнату, ремонт комнаты целиком |
| Риск | воспроизводим ограничение Exely | задержка старта на время замера |

**Решение:** **вариант А.** Решение владельца 07.09.2026: «койко-место — это единица
продажи; у нас хостел, номер получается одна койка, как одна ячейка».
**Причина:** объект — хостел, все 88 единиц продаются и учитываются как отдельные ячейки,
включая 16 отдельных номеров. Данных для варианта Б не существует, замер задержал бы старт.
**Уточнение владельца в тот же день:** физически на объекте 12 одноместных комнат,
4 двухместных и 4 dorm-комнаты по 18 коек (2 мужские, 2 женские) — всего 20 комнат.
Это не отменяет решение (единица продажи — койка), но даёт чем заполнить `PhysicalRoom`.
**Последствия:**
- `InventoryUnit` — единственная рабочая сущность инвентаря: availability, шахматка,
  статус уборки, блокировки ведутся по ней. 88 записей = 16 ROOM + 72 BED.
- `PhysicalRoom` остаётся в схеме (ADR-005 не отменяется): 16 отдельных номеров
  заполняются 1:1 из единиц продажи, 4 dorm-комнаты — по явному списку «какие койки
  в какой комнате» от владельца (Q-095). Из номера единицы принадлежность не выводится.
  Иерархия «комната → койки» появляется данными, без изменения схемы.
  Q-095 отложен владельцем: до списка все 88 единиц импортируются 1:1.
- В MVP не строятся: уборка по комнатам, «вся комната для группы», гендерное правило
  на комнату, ремонт комнаты целиком. Группа = набор ячеек в одной брони (Q-005).
- Q-081 (замер планировки) закрыт: не требуется.
- Знаменатель загрузки: Q-092 отложен владельцем 07.09.2026 — считаем по 88, как Exely.
- Правило автоназначения ячейки для OTA-броней — отдельный вопрос Q-094.

## ADR-018 — В dev-БД только анонимизированные данные гостей

**Дата:** 2026-09-08
**Проблема:** БД для разработки — Supabase в Сингапуре (ADR-009: персональные данные production
только в Казахстане). Выгрузки Exely с бронями содержат ФИО, контакты, документы гостей.
**Варианты:** (а) грузить реальные выгрузки в dev как есть; (б) в dev — только анонимизированная
копия, реальные данные — только в production-БД в РК; (в) dev-БД тоже в РК.
**Решение:** **(б).** Владелец 08.09.2026: «да давай» на описание правила в `plans/roadmap-2026-09-08.md` §2.
**Причина:** ADR-009 + ADR-010; утечка ПД через dev/тесты/промпты — реальный сценарий (SECURITY.md §4).
**Последствия:**
- Реальные выгрузки лежат в `project-input/exely/*.xlsx|csv` — вне git, закрыты от чтения агентом;
  их читает только программа (профилировщик `scripts/imports/src/exely/profile-xlsx.ts` маскирует ПД).
- Импорт в dev идёт через `anonymize-reservations`: ФИО/контакты/документы → детерминированные
  вымышленные значения, даты/суммы/категории/единицы/статусы — без изменений. Обратимости нет.
- Реальный импорт без анонимизации — только в production-БД после Q-070, отдельным разрешением.
- Сверки Gate 2 (загрузка, суммы, статусы) на анонимизированных данных корректны: ПД в них не участвуют.
- **Дополнено 10.09.2026:** правило распространено на брони, приходящие из каналов живьём. Раньше
  ADR-018 закрывал только импорт из Exely, а приём Channex писал в ту же сингапурскую базу настоящие
  ФИО, телефон и почту. Теперь единственный переключатель — `PII_STORAGE`: `real` разрешает настоящие
  данные и ставится только на production-БД в РК (после Q-070), любое другое значение означает
  детерминированный псевдоним (`packages/shared/src/pii-residency.ts`). Соль `ANONYMIZE_SALT`
  больше не имеет умолчания в коде; если её нет, берётся `PII_ENCRYPTION_KEY`. Условие допуска
  канала к production вынесено в `CUTOVER.md`.

## ADR-019 — Это платформа: мультиарендность и вертикали помимо отелей (ПРИНЯТО ВЛАДЕЛЬЦЕМ 10.09.2026, модель не расписана)

**Дата:** 2026-09-10
**Проблема:** SPEC.md и бриф исключали SaaS и мультиобъектность; код построен под один объект
(`LUXX_APARTS_PROPERTY` зашит в репозиториях API, сущности `Tenant`/`Organization` нет). Владелец
10.09.2026 объявил цель иначе: SaaS-платформа с перепродажей подписки другим сервисам; помимо отелей —
рестораны, салоны красоты; «простраивай сразу логику для платформы, не только для отелей».
**Решение:** платформа. Ядро — бронирование ресурса на время: койка, номер, столик, кресло — один
механизм. Иерархия: арендатор (организация, подписка) → объект (отель, ресторан, салон) → ресурсы.
Всё, что сегодня работает для Luxx Aparts, становится первым арендатором, а не исключением.
**Причина:** решение владельца о продукте, а не техническое. Записано сразу, потому что оно меняет
модель данных, а модель переделывать дороже всего (бриф, часть 2).
**Последствия и что предстоит (не сделано):**
- `DATA_MODEL.md` v2: `Tenant` (организация, подписка, план), `Property.tenantId`, тип объекта
  (вертикаль), обобщение `InventoryUnit` до ресурса с типом; отельные поля остаются у отельной вертикали.
- Каждый запрос в API — через арендатора и объект, а не через имя объекта из константы; изоляция
  данных между арендаторами проверяется тестом, который читает чужого арендатора и получает пусто.
- Миграция без потери данных: Luxx Aparts переносится как первый арендатор, все сверки (Gate 1, Gate 2,
  цены, балансы) должны снова дать ноль на новой схеме.
- Роли и права (Q-024, Q-060…Q-064) перестают быть «потом»: у платформы это вход.
- SPEC.md «Out of Scope» п.1–3 отменяются этим решением; остальные пункты списка остаются в силе,
  пока владелец не скажет иначе.
- Подписка и биллинг — отдельный ADR после модели.

## ADR-014 — Уровень привязки Folio: на проживание (ПРИНЯТ 09.09.2026)

> **Реализован 09.09.2026:** DATA_MODEL §6, миграция `20260909000006_folio_payments`, домен `packages/domain/src/finance`,
> API `apps/api/src/finance`, раздел «Счета» на карточке брони, e2e `tests/e2e/finance.spec.ts`. Счёт создаётся вместе
> с проживанием (`ensureFolioWithAccommodation`), начисление за проживание = цене, переписывается при изменении и
> сторнируется при отмене/незаезде (штраф — вручную, Q-103). Оплаченное в Exely переносится платежом `EXTERNAL exely:<roomStayId>`.

**Проблема.** Черновик модели: `Folio.reservation_id`. Exely: счёт на **каждое проживание**
внутри брони — бронь на 2 единицы даёт счета `…-01` и `…-02`.

**Варианты.** (а) Folio на бронь, разделение через Charge; (б) Folio на ReservationItem,
как в Exely; (в) Folio на бронь + возможность разделить на несколько.

**Влияет на:** разделение счёта между гостями, перенос 209 будущих броней,
сверку на Gate 1 и Gate 8. **Связанный вопрос:** Q-091.

**Решение 09.09.2026.** Владелец на вопрос ответил «я хз, давай как правильно должно быть» — принята рекомендация
агента ниже: **вариант (б), счёт на проживание**. Слова владельца записаны дословно, чтобы было видно, что выбор
делегирован, а не сформулирован им.

**Рекомендация агента (09.09.2026).** Вариант **(б): Folio на проживание
(`ReservationItem`)**, как в Exely. Аргументы:
1. Так работает объект сегодня: настройка «общий счёт для брони на несколько номеров» выключена
   (живой сеанс 08.09), счета `…-01`/`…-02` — факт данных. Перенос 209 будущих броней и двойной ввод
   на неделе 6 сходятся строка к строке без пересчёта.
2. Статус, no-show и переселение уже ведутся на проживании (v0.3); счёт на том же уровне — одна
   логика, один срез.
3. Групповая бронь «одна оплата за две койки» решается **общим платежом**: `Payment` с распределением
   по счетам (`PaymentAllocation`), а не общим счётом. Это покрывает вариант (в) без второго уровня.

**Что изменится в DATA_MODEL §6 при принятии (готовый текст):** `Folio.reservation_item_id → ReservationItem`
(UNIQUE, один счёт на проживание, создаётся при создании проживания); `Payment` получает
`property_id` и таблицу `payment_allocations (payment_id, folio_id, amount)`; `Reservation.total_amount`
остаётся коммерческой суммой брони, баланс = Σ по счетам проживаний. Обратная сторона: отчёт «по брони»
считается агрегатом, не хранится.

## ADR-015 (история предложения) — Способ миграции данных из Exely

**Проблема.** У Exely есть открытый API. Аудит снят программно; ручные выгрузки XLSX
доступны частично (календарь цен и полную историю броней программно не забрать).

**Варианты.** (а) Только выгрузки XLSX; (б) только API; (в) API как основной канал,
выгрузки как контрольная сверка.

**Аргумент за API:** миграцию придётся прогонять многократно — на репетиции, на
параллельном дне, на cutover. Ручные выгрузки на каждом прогоне не воспроизводимы.

**Связанный вопрос:** Q-088.

## ADR-016 (ПРЕДЛОЖЕНО) — Что делать со справочниками при миграции

**Проблема.** Справочники Exely содержат дефекты: «Наличные через кассу» существует
в двух экземплярах (приход по одной записи, расход по другой), три тарифа без продаж,
два набора правил аннуляции, из которых один ни к чему не привязан.

**Варианты.** (а) Перенести как есть и чистить потом; (б) чистить при импорте
по согласованному списку; (в) завести справочники заново вручную.

**Аргумент против (а):** перенос дубля наличных сразу воспроизводит недостоверную
отчётность в новой системе.

**Связанные вопросы:** Q-082, Q-083, Q-093.

## ADR-017 (ПРЕДЛОЖЕНО) — Обязательность источника прямой брони
