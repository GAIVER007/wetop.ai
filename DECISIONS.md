## ADR-001 — Single-property MVP

**Дата:** 2026-09-07
**Проблема:** строить ли сразу multi-tenant / multi-property.
**Варианты:** (a) сразу SaaS multi-tenant; (b) один объект, но сущность `Property` в схеме; (c) жёстко один отель без Property.
**Решение:** (b) — single-property MVP, сущность `Property` присутствует в модели.
**Причина:** сначала доказать работу на реальном объекте. Но база не должна содержать
предположение «в мире существует только один отель».
**Последствия:** UI работает с одним property; multi-property можно добавить позже
без переписывания схемы. Все запросы фильтруются по `property_id` с самого начала.

## ADR-002 — Modular monolith, не microservices

**Дата:** 2026-09-07
**Проблема:** архитектурный стиль backend.
**Варианты:** microservices; modular monolith; monolith без модулей.
**Решение:** modular monolith.
**Причина:** команда маленькая, MVP 8 недель, distributed complexity сейчас не нужна.
Для 88 номеров Kubernetes/Kafka — лишняя сложность.
**Последствия:** границы модулей поддерживаются дисциплиной пакетов
(`packages/domain`, `packages/integrations`), а не сетью.

## ADR-003 — PostgreSQL — source of truth

**Дата:** 2026-09-07
**Проблема:** какая система считается первичной по данным.
**Решение:** PostgreSQL PMS. Channex / Exely / eQonaq **не** являются основной БД PMS.
**Причина:** без единого source of truth сверка невозможна.
**Последствия:** любые внешние данные импортируются и хранятся локально;
внешние ID хранятся как ссылки, а не как замена собственных ключей.

## ADR-004 — Channels через adapter interface

**Дата:** 2026-09-07
**Проблема:** зависимость бизнес-логики от конкретного channel manager.
**Решение:** `ChannelProvider` — интерфейс. Первый adapter — Channex.
**Причина:** смена/добавление провайдера не должны затрагивать домен.
**Последствия:** бизнес-модель PMS не знает про Channex IDs; маппинг живёт
в `ChannelMapping`. Запрещён импорт Channex SDK вне `packages/integrations`.

## ADR-005 — Room и sellable inventory разделены

**Дата:** 2026-09-07
**Проблема:** dorm с койко-местами не укладывается в модель «номер = единица продажи».
**Решение:** `PhysicalRoom` (помещение) и `InventoryUnit` (ROOM | BED) — разные сущности.
Dorm содержит несколько bed inventory units.
**Причина:** самый дорогой возможный архитектурный промах — смешать их (риск №1).
**Последствия:** availability считается по `InventoryUnit`; private room — тоже
InventoryUnit (kind=ROOM), чтобы код был единообразным.

## ADR-006 — Reservation и Allocation разделены

**Дата:** 2026-09-07
**Проблема:** OTA продаёт категорию, физический номер назначается позже.
**Решение:** `Reservation` → `ReservationItem` (категория) → `Allocation` (юнит).
**Причина:** бронь категории должна существовать без назначенного физического номера.
**Последствия:** переселение = закрытие одной Allocation и открытие другой,
а не мутация брони. История переселений сохраняется.

## ADR-007 — Все внешние события идемпотентны

**Дата:** 2026-09-07
**Проблема:** повторный webhook может создать дубль OTA-брони.
**Решение:** `ExternalEvent` с UNIQUE (provider, external_event_id); обработка через
состояние + retry.
**Причина:** дубль или потеря брони — недопустимый отказ.
**Последствия:** любая интеграция сначала пишет событие, потом обрабатывает.
Обработчик обязан быть повторно-безопасным.

## ADR-008 — Финансы без float

**Дата:** 2026-09-07
**Решение:** деньги — integer minor units (тиын) либо decimal-safe представление.
**Причина:** JS floating point даёт расхождения в копейках, которые ломают сверку.
**Последствия:** все API отдают минорные единицы + код валюты; форматирование — только на UI.

## ADR-010 — Реальные паспорта не попадают в dev/test

**Дата:** 2026-09-07
**Решение:** реальные документы гостей никогда не используются в development/test,

**Последствия:** нужен генератор synthetic-гостей; анонимизация при импорте
production-выгрузок в dev.

## ADR-012 — Порядок миграции OTA

**Дата:** 2026-09-07
**Решение:** каналы переключаются по одному, начиная с минимального по объёму;
Booking.com — последним. Следующий канал не подключается, пока предыдущий не прошёл
reconciliation с расхождением 0.
**Причина:** одновременное переключение всех каналов делает откат невозможным.
**Последствия:** cutover растягивается, но остаётся обратимым. См. `CUTOVER.md`.

## ADR-013 — Койко-место = единица продажи (модель Exely)

**Дата:** 2026-09-07
**Проблема:** в Exely койка — запись в справочнике номеров. Физической планировки нет:
какая койка в какой комнате, ярус, окно — таких полей не существует. `PhysicalRoom`
из ADR-005 при миграции нечем заполнить.
**Варианты:**

| | Вариант А — повторить Exely | Вариант Б — настоящая иерархия |
|---|---|---|
| Суть | каждая единица продажи — самостоятельная ячейка; `PhysicalRoom` = формальная обёртка 1:1 | собрать планировку замером, койки привязать к комнатам |
| Миграция | тривиальная, данные есть | требует работы на объекте |
| Что даёт | ничего сверх текущего | уборка по комнатам, «вся комната для группы», гендерное правило на комнату, ремонт комнаты целиком |
| Риск | воспроизводим ограничение Exely | задержка старта на время замера |

**Решение:** **вариант А.** Решение владельца 07.09.2026: «койко-место — это единица
продажи; у нас хостел, номер получается одна койка, как одна ячейка».
**Причина:** объект — хостел, все 88 единиц продаются и учитываются как отдельные ячейки,
включая 16 отдельных номеров. Данных для варианта Б не существует, замер задержал бы старт.
**Уточнение владельца в тот же день:** физически на объекте 12 одноместных комнат,
4 двухместных и 4 dorm-комнаты по 18 коек (2 мужские, 2 женские) — всего 20 комнат.
Это не отменяет решение (единица продажи — койка), но даёт чем заполнить `PhysicalRoom`.
**Последствия:**
- `InventoryUnit` — единственная рабочая сущность инвентаря: availability, шахматка,
  статус уборки, блокировки ведутся по ней. 88 записей = 16 ROOM + 72 BED.
- `PhysicalRoom` остаётся в схеме (ADR-005 не отменяется): 16 отдельных номеров
  заполняются 1:1 из единиц продажи, 4 dorm-комнаты — по явному списку «какие койки
  в какой комнате» от владельца (Q-095). Из номера единицы принадлежность не выводится.
  Иерархия «комната → койки» появляется данными, без изменения схемы.
  Q-095 отложен владельцем: до списка все 88 единиц импортируются 1:1.
- В MVP не строятся: уборка по комнатам, «вся комната для группы», гендерное правило
  на комнату, ремонт комнаты целиком. Группа = набор ячеек в одной брони (Q-005).
- Q-081 (замер планировки) закрыт: не требуется.
- Знаменатель загрузки: Q-092 отложен владельцем 07.09.2026 — считаем по 88, как Exely.
- Правило автоназначения ячейки для OTA-броней — отдельный вопрос Q-094.

## ADR-018 — В dev-БД только анонимизированные данные гостей

**Дата:** 2026-09-08
**Проблема:** БД для разработки — Supabase в Сингапуре (ADR-009: персональные данные production
только в Казахстане). Выгрузки Exely с бронями содержат ФИО, контакты, документы гостей.
**Варианты:** (а) грузить реальные выгрузки в dev как есть; (б) в dev — только анонимизированная
копия, реальные данные — только в production-БД в РК; (в) dev-БД тоже в РК.
**Решение:** **(б).** Владелец 08.09.2026: «да давай» на описание правила в `plans/roadmap-2026-09-08.md` §2.
**Причина:** ADR-009 + ADR-010; утечка ПД через dev/тесты/промпты — реальный сценарий (SECURITY.md §4).
**Последствия:**
- Реальные выгрузки лежат в `project-input/exely/*.xlsx|csv` — вне git, закрыты от чтения агентом;
  их читает только программа (профилировщик `scripts/imports/src/exely/profile-xlsx.ts` маскирует ПД).
- Импорт в dev идёт через `anonymize-reservations`: ФИО/контакты/документы → детерминированные
  вымышленные значения, даты/суммы/категории/единицы/статусы — без изменений. Обратимости нет.
- Реальный импорт без анонимизации — только в production-БД после Q-070, отдельным разрешением.
- Сверки Gate 2 (загрузка, суммы, статусы) на анонимизированных данных корректны: ПД в них не участвуют.
- **Дополнено 10.09.2026:** правило распространено на брони, приходящие из каналов живьём. Раньше
  ADR-018 закрывал только импорт из Exely, а приём Channex писал в ту же сингапурскую базу настоящие
  ФИО, телефон и почту. Теперь единственный переключатель — `PII_STORAGE`: `real` разрешает настоящие
  данные и ставится только на production-БД в РК (после Q-070), любое другое значение означает
  детерминированный псевдоним (`packages/shared/src/pii-residency.ts`). Соль `ANONYMIZE_SALT`
  больше не имеет умолчания в коде; если её нет, берётся `PII_ENCRYPTION_KEY`. Условие допуска
  канала к production вынесено в `CUTOVER.md`.

## ADR-019 — Платформа с несколькими объектами (ОТЛОЖЕНА до конца переезда хостела — решение 13.09.2026 по ответу ментора курса; историю статусов см. ниже)
**Решение 13.09.2026 (ментор курса, дословно по смыслу):** сначала довести переезд хостела до конца,
модель под рестораны и салоны сейчас **не закладывать**. Общее у вертикалей только ядро — ресурс,
календарь, бронь, счёт, — и оно уже написано. Всё трудное у хостела своё: Channex и сертификация,
койко-места, eQonaq, правила раннего заезда. У ресторана будут свои каналы и свои правила, заранее их
не угадать; ядро переписывается за неделю, когда появится первый ресторан, готовый платить, а хостел
на недоделанном переезде обойдётся дороже. **Что это значит для работы:** `Tenant`, вертикали и
обобщение `InventoryUnit` до ресурса не проектируем и в код не тащим; Q-104…Q-106 остаются снятыми.

**Дата:** 2026-09-10
**Проблема:** SPEC.md и бриф исключали SaaS и мультиобъектность; код построен под один объект
(`LUXX_APARTS_PROPERTY` зашит в репозиториях API, сущности `Tenant`/`Organization` нет). Владелец
10.09.2026 объявил цель иначе: SaaS-платформа с перепродажей подписки другим сервисам; помимо отелей —
рестораны, салоны красоты; «простраивай сразу логику для платформы, не только для отелей».
**Решение:** платформа. Ядро — бронирование ресурса на время: койка, номер, столик, кресло — один
механизм. Иерархия: арендатор (организация, подписка) → объект (отель, ресторан, салон) → ресурсы.
Всё, что сегодня работает для Luxx Aparts, становится первым арендатором, а не исключением.
**Причина:** решение владельца о продукте, а не техническое. Записано сразу, потому что оно меняет
модель данных, а модель переделывать дороже всего (бриф, часть 2).
**Последствия и что предстоит (не сделано):**
- `DATA_MODEL.md` v2: `Tenant` (организация, подписка, план), `Property.tenantId`, тип объекта
  (вертикаль), обобщение `InventoryUnit` до ресурса с типом; отельные поля остаются у отельной вертикали.
- Каждый запрос в API — через арендатора и объект, а не через имя объекта из константы; изоляция
  данных между арендаторами проверяется тестом, который читает чужого арендатора и получает пусто.
- Миграция без потери данных: Luxx Aparts переносится как первый арендатор, все сверки (Gate 1, Gate 2,
  цены, балансы) должны снова дать ноль на новой схеме.
- Роли и права (Q-024, Q-060…Q-064) перестают быть «потом»: у платформы это вход.
- SPEC.md «Out of Scope» п.1–3 отменяются этим решением; остальные пункты списка остаются в силе,
  пока владелец не скажет иначе.
- Подписка и биллинг — отдельный ADR после модели.

## ADR-020 — Ограничения продаж действуют и на стойке (принято по поручению владельца «выполняй сам», 11.09.2026)

**Дата:** 2026-09-11
**Проблема:** ограничения (стоп-продажа, минимальный и максимальный срок, закрытие заезда и выезда)
редактируются и уходят в каналы, но ручная бронь со стойки их не проверяла: администратор мог продать
дату со стоп-продажей или короче минимального срока, и канал с PMS расходились бы.
**Варианты:** (а) отказывать; (б) предупреждать и пропускать; (в) не проверять.
**Решение:** **(а)** — отказ с внятным сообщением, какое ограничение и на какую дату. Переопределение —
только правкой самого ограничения на экране «Цены и ограничения», а не обходом на форме.
**Причина:** одно правило для стойки и каналов; предупреждение, которое можно пропустить, через неделю
перестают читать. Владелец поручил решить самостоятельно.
**Последствия:** проверка в домене при создании, изменении дат и продлении брони; тест красный до правки.

## ADR-021 — Ранний заезд и поздний выезд: платные услуги на счёте по правилу объекта из Exely (11.09.2026)

> **Уточнено вечером 11.09.2026 по кабинету Exely** («Настройки гостиницы → Ранний заезд / Поздний выезд →
> Основное правило», привязано ко всем 6 тарифам): расчётный час заезда 14:00, выезда 12:00. Ранний заезд:
> 00:00–05:59 — 100 % цены ночи, 06:00–11:59 — 50 %, 12:00–13:59 — бесплатно; доплата входит в предоплату.
> Поздний выезд: 12:01–17:59 — 50 %, 18:00–23:59 — 100 %, до 12:00 — бесплатно; в предоплату не входит.
> В Exely обе доплаты помечены «выделять доступность: да» — соседняя ночь блокируется. В PMS так же:
> кнопка спрашивает время, считает долю ночи и ставит блок на койку на соседнюю ночь (ночь до заезда или
> ночь после выезда) командой ячейки — та откажет, если на эту ночь уже есть проживание, и разошлёт остаток
> в канал. Блок виден на шахматке и снимается как любой другой. Если доплату сторнируют, блок снимает стойка.

**Дата:** 2026-09-11
**Проблема:** бриф требует ранний заезд и поздний выезд на стойке, правила объекта не было записано;
в Exely за август поздний выезд применён у 3 проживаний из 1044, ранний заезд не встречается.
**Варианты:** (а) отдельные статусы и логика дат; (б) две услуги в справочнике с фиксированной ценой;
(в) две услуги с ценой, считаемой от цены ночи проживания.
**Решение:** **(в).** «Ранний заезд» и «Поздний выезд» — начисления вида «услуга» на счёт проживания,
одной кнопкой на карточке брони. Сумма по умолчанию — 50 % цены одной ночи этого проживания
(цена проживания ÷ число ночей ÷ 2, округление до целого тенге вниз, деньги в тиынах без дробей),
сумму можно поправить перед начислением. Даты и ячейка не меняются: гость занимает ту же койку,
ранний заезд не продлевает бронь на предыдущую ночь.
**Причина:** это оформление денег, а не другая модель проживания; половина ночи — обычная практика
хостелов, владелец правило не задал и поручил решить. Отдельные статусы усложнили бы шахматку и
сверки ради 3 случаев в месяц.
**Последствия:** кнопки на карточке, начисление с пометкой в описании, тест красный до правки;
если владелец назовёт другую цену или бесплатный порог по времени — меняется одна константа и ADR.

## ADR-022 — Предоплата канала после отмены: остаётся только штраф (по поручению владельца «сам реши», 11.09.2026)

**Дата:** 2026-09-11
**Проблема:** при отмене брони, оплаченной площадкой (`payment_collect = ota`), начисление за проживание
сторнировалось, а платёж канала оставался — на счёте «к оплате −9 000 ₸». Найдено прогоном шести
каналов 11.09 (`reports/channex-ota-cycle-2026-09-11.md`), вопрос Q-108.
**Варианты:** (а) снимать платёж канала вместе с начислением; (б) начислять штраф по политике тарифа и
снимать остаток; (в) держать минус как «долг перед каналом» до сверки с выпиской.
**Решение:** **(а) + (б) одним правилом.** После отмены или незаезда от предоплаты канала остаётся ровно
сумма начисленных штрафов на счёте проживания — эти деньги площадка перечислит объекту. Остальное
площадка возвращает гостю сама, в PMS оно не деньги объекта. Без штрафа предоплата снимается целиком.
**Причина:** деньги гостя держит площадка, а не объект; минус на счёте вводил бы стойку в заблуждение,
будто гостю что-то должны. Штраф при этом виден и покрыт. Владелец поручил решить самостоятельно.
**Последствия:** правило в домене (`channelPrepaymentToKeep`), применяется в отмене и незаезде со стойки и
в отмене из канала; тест красный до правки. Сверка с выпиской площадки — отдельная задача до переезда.

## ADR-024 — Подтянутые Channex брони сопоставляются с перенесёнными из Exely (принято по поручению владельца «выполняй сам», 11.09.2026; переписано после рецензии тем же днём)

**Дата:** 2026-09-11
**Проблема:** при подключении канала Channex подтягивает уже существующие будущие брони Booking.com,
Expedia и Trip.com (`load_future_reservations` — ответ Channex владельцу 11.09.2026,
`docs/channex/how-channex-works-for-us.md`) и присылает каждую как ревизию `booking_new`; для Agoda,
Hostelworld и Ostrovok подтяжки нет. В PMS эти брони уже перенесены из Exely: `source = OTA`, канал — имя по
Exely («booking.com», «Trip.com Group», «Expedia/Hotels.com»), `externalId` пуст — Универсальный API Exely номер
брони на стороне канала не отдаёт (`PmsApi_ReservationChannelInformation` содержит только `channelName`).
Приём ревизий искал бронь по `unique_id` → `ota_reservation_code` → номеру подтверждения и иначе создавал
новую: дубль и вторая занятая койка на каждой (Q-034, CUTOVER.md «Перенесённые брони канала не сопоставятся
автоматически»).

**Цифры из dev-БД на 11.09.2026** (кандидат: `source = OTA`, `external_id` пуст, бронь не отменена, есть живое
проживание с выездом после сегодняшнего дня по Алматы, без метки автотестов): Trip.com Group 82, booking.com 46,
Expedia/Hotels.com 12 — **140 броней подтягиваемых каналов**; Agoda 11, Ostrovok 6, Hostelworld 1 — без подтяжки,
правило к ним не применяется. Заметок нет ни у одной, валюта у всех KZT, многокомнатных: Trip.com 5, booking.com 6.
**Неоднозначных** (тот же канал и тот же состав проживаний у двух броней): Trip.com 7 групп — 14 броней,
booking.com 1 группа — 2 брони, Expedia 0; итого **16 из 140 (11%)**, в группе всегда ровно две. Признак
«канал + категории + даты» НЕ «практически однозначен», как утверждала первая редакция. Счета, уже оплаченные
из Exely (платёж `EXTERNAL exely:…`): 2 брони booking.com на 211 774,50 ₸.

**Канал ревизии — по коду из `unique_id`, а не по имени** (`docs/channex/site/api-v.1-documentation/channel-codes.md`: «save the first 3 letters to use for matching… match by the code, not by the name»): `BDC` → Booking.com, `EXP`/`HTL`/`EAN`/`EBS`/`EGN`/`AET`/`AHC`/`AHR`/`CHT` → Expedia, `CTP` → Ctrip (Trip.com), `AGO` → Agoda, `HWL` → Hostelworld, `OVK` → Emerging Travel Group (Ostrovok). Имена `ota_name` у Channex плавают — `"Booking.com"` и `"BookingCom"` (`bookings-collection.md:340`, `:1192`), `"A-Expedia"` и `"Expedia"` (`:1802`, `messages-collection.md:71`), `"Hostelworld Group"` на staging — поэтому имя используется только как запасной путь для кода, которого в списке объекта нет. Канал перенесённой из Exely брони — по её имени из Exely (`otaChannelKey`: «Trip.com Group» = `ctrip`, «Expedia/Hotels.com» = `expedia`, «Ostrovok.ru (Emerging Travel Group)» = `ostrovok`).

**Варианты:** (а) вести перенесённые брони руками до выезда последней (CUTOVER.md, как было); (б) сопоставлять по
каналу и составу проживаний автоматически, при неоднозначности ничего не решать самим — звать человека;
(в) сопоставлять по сумме и гостю (ненадёжно: суммы у каналов в своей валюте, гость в dev-БД анонимизирован);
(г) при неоднозначности связывать по порядку прихода ревизий — развилка по availability и по гостю на проживании,
решение владельца (QUESTIONS.md).
**Решение:** **(б)**, правило:
1. Применяется только к ревизии, которую иначе пришлось бы создать (все три поиска по ID пусты), только если
   ревизия не отменена и **только для каналов с подтяжкой** — ключи `bookingcom`, `ctrip`, `expedia`
   (`CHANNEX_PULLS_EXISTING_BOOKINGS`, `packages/integrations`). Бронь Agoda, Hostelworld или Ostrovok с тем же
   составом, что у перенесённой, — новая бронь, создаётся как обычно.
2. Кандидат — бронь: `source = OTA`; `externalId` пуст (`null` или `''`); статус не `CANCELLED`; заметки без метки
   автотестов `E2E-АВТОТЕСТ`; канал перенесённой брони (`otaChannelKey` от имени Exely) равен ключу ревизии (`channelKey` по коду `unique_id`, иначе по `ota_name`); число живых (не `CANCELLED`) проживаний равно числу комнат
   в ревизии; проживания сопоставляются 1:1 по (категория через маппинг канала, заезд, выезд) как мультимножество,
   порядок не важен. Суммы и валюта в сопоставлении не участвуют.
3. Ровно один кандидат → **связать**: `externalId := unique_id`, `channel := ota_name`, даты шапки — из ревизии;
   сумма шапки — из ревизии **только при той же валюте**, иначе не трогается и пишется предупреждение; заметка
   ревизии заменяет заметку Exely только если она есть (`null` заметку не стирает); статус шапки не трогается
   (выводится из проживаний); проживания и назначения ячеек **не трогаются** — ячейка из Exely сохраняется.
   Предоплата канала (Q-086, `payment_collect = ota`) записывается на счёт каждого проживания **только если по
   счёту ещё ничего не оплачено** (баланс не меньше цены комнаты в ревизии): на 2 счетах booking.com уже лежит
   платёж из Exely, второй платёж сделал бы счёт отрицательным — вместо платежа предупреждение «проверьте счёт
   вручную». Журнал `channex.booking.linked` с before/after; результат ревизии — `linked` (на `/channels` подпись
   «сопоставлена с перенесённой»).
4. Ноль кандидатов → создать, как раньше. **Два и больше → PMS не выбирает сама:** ревизия отклоняется — событие
   `FAILED` с текстом «перенесённых броней с таким же составом несколько — <номера>», ack не отправляется, бронь
   не создаётся, ячейка не занимается; перенесённые копии в PMS уже есть, гость не теряется. Первая редакция
   создавала бронь «как раньше» с предупреждением — это 16 дублей с занятой второй койкой и −1 в остатке канала
   на каждый, а предупреждение на webhook и фоновом опросе никто не читал.
5. **Канал PMS не знает** (ни код `unique_id`, ни имя не дают ключ из восьми каналов объекта), а перенесённая бронь с тем же составом есть →
   тоже отклонить, с именем канала и номерами кандидатов: так бронь нового канала под незнакомым кодом остановится с объяснением, а не создаст дубль. После добавления кода или имени в соответствия неподтверждённые
   ревизии подбирает следующий опрос ленты (пока попыток меньше шести, то есть полчаса; дальше — кнопка
   «Обработать заново» по событию). Незнакомое имя без совпадения состава — новый канал, бронь создаётся как обычно.
6. Предупреждения разбора любой ревизии («без ячейки», «предоплата не записана», «валюта не совпадает») пишутся в
   журнал процесса (`warn`) и сохраняются в `external_events.last_error` события со статусом `PROCESSED` с
   префиксом «Предупреждение:» — колонка «Ошибка» на `/channels`; отдельного поля у события нет, заявка на поле
   `warnings` — через `DATA_MODEL.md`. Кнопка «Опросить ленту» показывает отклонённые ревизии и предупреждения
   в ответе.
**Причина:** ручная сверка 140 броней в день переключения — источник ошибок; автоматика берёт на себя 124
однозначные (89%), а в 16 неоднозначных и при незнакомом имени канала ничего не решает сама: событие `FAILED`
с объяснением и кнопкой повтора уже есть, а дубль пришлось бы искать и отменять руками, причём его последующая
модификация из канала воскресила бы отменённый дубль (поиск по `externalId` статус не проверяет). Владелец
поручил решить самостоятельно.
**Последствия:** правило в домене (`matchImportedReservation`, `sameStaySet`), ключ канала и списки каналов в
`packages/integrations` (имена вендоров — только там, ADR-004), шаг 4 поиска в приёме ревизий; тесты красные до
правки (`channel-names.test.ts`, `inbound.controller.test.ts`). После связывания дальнейшие `modified`/`cancelled`
находят бронь по `unique_id`, как обычно. Q-034 этим решением закрывается; чек-лист CUTOVER.md для Booking.com,
Expedia и Trip.com меняется на «после подтяжки разобрать отклонённые ревизии и несвязанные остатки», ручная сверка
остаётся только для Agoda, Hostelworld и Ostrovok.
**Открыто:** (1) снято 12.09.2026 — код `CTP` для Trip.com есть в channel-codes.md, имя не нужно; (2) 16 неоднозначных броней — вариант (г) «связывать по порядку» или ручной разбор, Q-109; (3) правило «предоплату канала не писать на уже оплаченный счёт» — Q-110, финансовая логика; (4) остаточный риск: пока у канала с подтяжкой остаются
несвязанные перенесённые брони, новая бронь того же канала с точно таким же составом будет связана с ними, а не
создана — несвязанные остатки после подключения канала разбирать сразу.
**Ручной разбор неоднозначной группы** из N перенесённых броней и N отклонённых ревизий (до решения по (г)):
оставить в PMS одну перенесённую бронь, остальные N−1 отменить (ячейки освободятся), нажать «Обработать заново»
на ревизиях по очереди — первая свяжется с оставшейся, остальные создадутся заново со своими ячейками; гостя на
связанном проживании сверить с гостем ревизии.

## ADR-014 — Уровень привязки Folio: на проживание (ПРИНЯТ 09.09.2026)

> **Реализован 09.09.2026:** DATA_MODEL §6, миграция `20260909000006_folio_payments`, домен `packages/domain/src/finance`,
> API `apps/api/src/finance`, раздел «Счета» на карточке брони, e2e `tests/e2e/finance.spec.ts`. Счёт создаётся вместе
> с проживанием (`ensureFolioWithAccommodation`), начисление за проживание = цене, переписывается при изменении и
> сторнируется при отмене/незаезде (штраф — вручную, Q-103). Оплаченное в Exely переносится платежом `EXTERNAL exely:<roomStayId>`.

**Проблема.** Черновик модели: `Folio.reservation_id`. Exely: счёт на **каждое проживание**
внутри брони — бронь на 2 единицы даёт счета `…-01` и `…-02`.

**Варианты.** (а) Folio на бронь, разделение через Charge; (б) Folio на ReservationItem,
как в Exely; (в) Folio на бронь + возможность разделить на несколько.

**Влияет на:** разделение счёта между гостями, перенос 209 будущих броней,
сверку на Gate 1 и Gate 8. **Связанный вопрос:** Q-091.

**Решение 09.09.2026.** Владелец на вопрос ответил «я хз, давай как правильно должно быть» — принята рекомендация
агента ниже: **вариант (б), счёт на проживание**. Слова владельца записаны дословно, чтобы было видно, что выбор
делегирован, а не сформулирован им.

**Рекомендация агента (09.09.2026).** Вариант **(б): Folio на проживание
(`ReservationItem`)**, как в Exely. Аргументы:
1. Так работает объект сегодня: настройка «общий счёт для брони на несколько номеров» выключена
   (живой сеанс 08.09), счета `…-01`/`…-02` — факт данных. Перенос 209 будущих броней и двойной ввод
   на неделе 6 сходятся строка к строке без пересчёта.
2. Статус, no-show и переселение уже ведутся на проживании (v0.3); счёт на том же уровне — одна
   логика, один срез.
3. Групповая бронь «одна оплата за две койки» решается **общим платежом**: `Payment` с распределением
   по счетам (`PaymentAllocation`), а не общим счётом. Это покрывает вариант (в) без второго уровня.

**Что изменится в DATA_MODEL §6 при принятии (готовый текст):** `Folio.reservation_item_id → ReservationItem`
(UNIQUE, один счёт на проживание, создаётся при создании проживания); `Payment` получает
`property_id` и таблицу `payment_allocations (payment_id, folio_id, amount)`; `Reservation.total_amount`
остаётся коммерческой суммой брони, баланс = Σ по счетам проживаний. Обратная сторона: отчёт «по брони»
считается агрегатом, не хранится.

## ADR-015 (история предложения) — Способ миграции данных из Exely

**Проблема.** У Exely есть открытый API. Аудит снят программно; ручные выгрузки XLSX

## ADR-025 — Аналитика сайта: свой first-party счётчик, а не витрина Google Analytics (ПРИНЯТ 12.09.2026 по поручению владельца «давай внедряй делай»)

**Дата:** 2026-09-12
**Контекст:** владелец 12.09.2026 поручил добавить модуль «Аналитика сайта»: PMS выдаёт код, код вставляется на
сайт, PMS показывает посещения и источники. Это расширяет scope: SPEC.md «Out of Scope» п. 10 «Маркетинг» —
распоряжение владельца, SPEC.md уточняется при принятии этого ADR. Раздел «Аналитика» в Exely
(`docs/exely/analytics-2026-09-12.md`): своего счётчика нет, «Эффективность сайта» читает Google Analytics 4
(счётчик G-XLJ63SQTJ4), данных за сентябрь 2026 нет, модуль бронирования не подключён.

**Варианты:**
- **(а) Как Exely** — GA4 на сайте, PMS читает Google Analytics Data API. Плюсы: Google считает сам, отчётов
  много. Минусы: Google-аккаунт, сервисный аккаунт и квоты API; данные у Google с задержкой до суток и
  порогами конфиденциальности; ~30 % посетителей с блокировщиками не видны; код на сайт всё равно
  вставлять; собственного кода в PMS столько же (чтение API + отчёты).
- **(б) Свой first-party счётчик** — скрипт ~2 КБ, публичный приёмник в PMS, четыре таблицы, отчёты по
  определениям GA4. Плюсы: данные сразу и у нас, без ПД, без Google, ровно то, что поручил владелец
  («код, который генерирует система»). Минусы: писать и держать приёмник; нужен постоянный публичный
  адрес API (Q-112).
- **(в) Оба** — (б) сейчас, импорт GA4 по API позже, если понадобится история или сравнение.

**Решение:** **(б)** с открытой дверью в **(в)**. Определения метрик — GA4/Exely (сессия 30 минут,
просмотры с повторами), чтобы цифры были сравнимы. Персональные данные не собираются: IP и полный
User-Agent не сохраняются, ID посетителя случайный и к гостю не привязан (ADR-018 соблюдён). Модель —
`DATA_MODEL.md` §11, план — `plans/slice-8-web-analytics.md`.

**Принято:** владелец 12.09.2026 — «давай внедряй делай». Реализация в тот же день: домен, миграция, приёмник,
отчёты, экраны, e2e (`plans/slice-8-web-analytics.md` §10). Открытыми остаются Q-111 (сайт), Q-112 (постоянный
адрес — без него счётчик на настоящий сайт не ставится), Q-113 (баннер / GA4 параллельно).

## ADR-026 — Бронирование с сайта: виджет поверх тех же правил, что у стойки (ПРИНЯТ по поручению владельца 12.09.2026)

**Дата:** 2026-09-12
**Контекст:** владелец поручил: «код виджета на сайт, он показывает свободные даты, с сайта можно сразу
бронировать, бронь уходит в систему». Это расширяет scope (SPEC.md «Out of Scope» п. 6 «Booking engine для
сайта») — распоряжение владельца. В Exely модуль бронирования на объекте не подключён, 389 из 390 прямых
броней заводятся руками (аудит), онлайн-оплаты нет ни в Exely, ни у нас (Q-050).

**Варианты:** (а) отдельный «движок бронирования» со своей логикой доступности и цен; (б) виджет, который
только собирает форму, а доступность, ограничения, цену, ячейку, счёт, журнал и дельту в Channex делает
`ReservationsService.create` — тот же путь, что у стойки; (в) внешний booking engine (Exely, TravelLine) с
интеграцией — ещё один провайдер и ещё одна сертификация.

**Решение:** **(б).** Виджет — второй код на том же «сайте» (`TrackedSite`, ключ `pms_…`), публичные
`GET /w/availability` и `POST /w/book`, доступность как у канала (проданные проживания, Q-107), ограничения
ADR-020, цена `priceStay` по тарифу сайта, `autoAssign` — первая свободная ячейка как у канала (Q-094),
гость через `guestForStorage` (ADR-018). Умолчания до ответа владельца: **бронь `CONFIRMED` без предоплаты**
(как модуль Exely — место снимается сразу, двойной продажи между сайтом и стойкой нет; Q-114), тариф по
умолчанию — «Базовый тариф» Exely 10157482 (шёл на сайт и PMS), уведомлений гостю нет (Q-115), язык RU (Q-116).
Защита публичных адресов: домен сайта в Origin/Referer, CORS только для доменов сайта, honeypot, лимиты 5/час с
IP (IP только в памяти) и 30/час на сайт, окно 365 дней / 30 ночей.

**Связь с аналитикой:** `WebSession.reservation_id` — бронь виджета привязана к сессии счётчика, отчёт
показывает брони по источникам; поиск дат в виджете сам заполняет календарь спроса.

**Доказательства:** `reports/web-booking-2026-09-12.md`, e2e `tests/e2e/web-booking.spec.ts`.

## ADR-027 — Интерфейс стойки: токены и компоненты без CSS-фреймворка (ПРИНЯТ по поручению владельца 12.09.2026 «давай делай»)

**Дата:** 2026-09-12
**Контекст:** 18 экранов стойки работали и были покрыты e2e, но каждый был оформлен инлайн-стилями
по-своему (354 объекта стилей), у каждой страницы — свой набор ссылок «куда ещё», общей навигации не было.
Владелец спросил менторов 12.09, когда и как делать дизайн; ответа нет. 17.09 администраторы ведут смену
в двух системах одновременно — наша должна выглядеть одним приложением.

**Варианты:** (а) CSS-фреймворк (Tailwind) и библиотека компонентов — ещё зависимости, сборка, чужая
система классов, которую дизайнер потом будет переписывать; (б) CSS-модули на каждую страницу — стили
снова разъезжаются по страницам; (в) один файл токенов и классов-примитивов плюс полтора десятка
React-компонентов без клиентского JS; (г) дизайн сразу, с дизайнером или по шаблону.

**Решение:** **(в)** сейчас, **(г)** после параллельного дня. `apps/web/src/app/globals.css` — токены
(цвета, радиусы, шрифты; значения те же, что были в коде) и классы; `apps/web/src/components/` — `Page`,
`TopNav`, `Stat`, `Panel`, `Table`, `Button`, `Input`/`Select`/`Textarea`, `Field`, `Badge`/`StatusBadge`,
`Alert`/`Notice`, `Row`/`Stack`/`Grid`, `Legend`. Общая верхняя навигация на всех экранах, кроме печатных
форм. Тексты кнопок и заголовков, имена полей, `data-testid` и `role="alert"` не менялись — на них стоят
e2e. Настоящий дизайн делается по замечаниям смены 17.09: рисовать до них значит рисовать не те экраны
(PLAN.md «Чего не делаем»).

**Последствия:** страницы не содержат оформления — дизайнер меняет токены и компоненты, страницы и тесты
не трогаются; новые экраны собираются из тех же компонентов; экраны аналитики (`/analytics*`) переводятся
следующим шагом (их правила сессия среза 9); печатные формы не трогаются.

**Доказательства:** `reports/desk-ui-base-2026-09-12.md`, `reports/screenshots/ui-base-*.png`, полный e2e.

> **Дополнение 12.09.2026, вечер — визуальный дизайн применён (направление A «спокойная стойка»).** Владелец не стал
> ждать параллельного дня и ответа менторов («давай делай»). Макеты — artifact «Luxx PMS, дизайн стойки»
> (экран «Сегодня», шахматка, лист стиля; наброски направлений B «тёмная шапка, плотно» и C «карточки для
> планшета» — не выбраны). В код перенесено только через `globals.css` и `components/`, как и обещал ADR:
> шрифты Manrope (заголовки, числа) / IBM Plex Sans (текст) / IBM Plex Mono (номера броней) через `next/font`
> в `layout.tsx` — файлы в сборке, стойка не ходит в интернет; токены: фон `#f4f5f8`, текст `#16213a`, акцент
> `#1f4bd8`, статусы шахматки `#d7e6ff / #c3efd2 / #e6e8ec / #fbe7a3 / #f8c9c9`; шапка 52 px со знаком бренда;
> заголовок экрана 28/800; заголовки колонок заглавными 11,5 с разрядкой, строки 8×12, подсветка при наведении;
> контролы 34 px; плитки-показатели: жёлтая «не сделано», красная «долг», остальные белые. Тексты, поля,
> `data-testid` не менялись; сквозные тесты стойки зелёные; скриншоты `reports/screenshots/design-*.png`.
>
> **Гостевая часть в том же стиле (12.09.2026, вечер).** Виджет бронирования на сайте хостела
> (`apps/api/src/web-booking/widget.js`) и обе проверочные страницы (`/w/demo`, `/a/demo`) переведены на те же
> цвета. Виджет живёт на чужом сайте, поэтому правила отличаются от стойки: все селекторы под классом `.pmsw`;
> цвета — собственные переменные `--pmsw-accent`, `--pmsw-ink`, `--pmsw-radius` и т. д., владелец сайта может
> переопределить их своим CSS (описано в `docs/site/install-2026-09-12.md`); гарнитура не подгружается —
> системный шрифт, чтобы не замедлять чужую страницу; `color-scheme: light`, иначе поля дат чернеют на сайте
> с тёмной темой; поля и кнопки 44 px и одна колонка уже 460 px — гость бронирует с телефона. DOM-контракт
> (`data-pmsw-*`, классы `.cat`, `.n`, `.p`, `.msg`) не менялся, его держит `tests/e2e/web-booking.spec.ts`.
>
> **Вторая волна, по замечанию владельца «перегружено и колхозно» (12.09.2026, вечер).** Правило, которое
> из неё выведено и которого держимся дальше: **цвет — это сигнал, а не украшение**. Залита только главная
> кнопка экрана; остальные тона кнопок — белые с цветной подписью. Плитка-показатель всегда белая, цветом
> выделяется значение, и только когда требуется действие. Статус в таблице — точка плюс слово, не пилюля.
> Ссылка внутри таблицы цвета текста (в таблице ссылка почти каждая ячейка), синеет при наведении и
> подчёркивается при фокусе с клавиатуры. Заголовки колонок — обычным регистром: кириллица заглавными
> читается хуже. Плитками показываются только числа; даты, гости и заказчик — строка фактов. Заливки клеток
> шахматки бледные: занято 80 % сетки. Гарнитура одна (IBM Plex Sans), Manrope убран — две семьи на плотных
> экранах читаются как склейка. Подробный разбор и доказательства — `reports/desk-ui-base-2026-09-12.md`.

> **Третья волна: шахматка (12.09.2026).** Строки сгруппированы по категориям, у группы по каждой ночи —
> число свободных мест (берётся из `byCategory`, которое доска считала и раньше, но не показывала); шапка дат
> и колонка ячеек липкие; сегодняшняя колонка выделена, выходные подсвечены; пустая клетка ведёт на форму
> брони с этими датами (из обхода по Tab исключена: таких клеток больше тысячи, то же действие есть кнопкой);
> подсказки на клетках по-русски; переключатель окна 7 / 14 / 30 дней. Контракт сетки для тестов не менялся.
>
> **Ответ ментора 13.09.2026 о дизайне.** Оформлять экраны до того, как по ним отработал администратор, —
> строить наугад и потом переделывать: дизайн делается **после первой живой смены**, своими силами
> (агентом), по одному файлу правил и по замечаниям администраторов; сайт и дизайнер понадобятся со
> вторым объектом. Сделанное до этого ответа остаётся: каркас, токены и компоненты — это и есть «один
> файл правил», по которому правки после смены делаются за минуты (`globals.css` + `components/`).
> **Дальнейшие правки внешнего вида — только по замечаниям смены**, не по нашему вкусу.

## ADR-028 — Сторож системы и дежурный агент: одно место для неисправностей, починка только техники (ПРИНЯТ по поручению владельца 13.09.2026 «делай»)

**Дата:** 2026-09-13
**Контекст:** ментор 13.09 ставит условием переключения каналов ответ «кто чинит, если система встала при
заселении в 3 часа ночи» (Q-123). Владелец ответил: дежурит агент-сторож круглые сутки, все ошибки системы
собираются в одно место. К этому дню неисправности видны в пяти местах (плитка очереди на `/channels`,
журнал событий, память процесса API, файлы сверок, журнал тестов), а ответы API 500 не пишутся нигде;
ни одна неисправность не доходит до человека. Туннель за 11–12.09 умирал четыре раза, и каждый раз это
заметили руками.

**Варианты:** (а) агент Claude по расписанию делает всё — проверяет, чинит, будит; (б) сторож-код в API
плюс агент Claude вторым слоем; (в) внешний сервис мониторинга (Sentry, Grafana) — ещё поставщик, ещё
данные за границу, и он не умеет чинить.
Одно место: (1) таблица `system_incidents`; (2) сводка на лету из существующих таблиц плюс файл.

**Решение:** **(б) + (1)** — план `plans/slice-11-guardian.md`, модель `DATA_MODEL.md` §12.
Сторож — детерминированный код в API, раз в минуту: проверки, запись в одно место, починка **только
класса А** (техника, повтор безопасен) через те же пути, что кнопки на `/channels`, будильник.
Неисправности класса Б (бронь, место, деньги) не чинит никто, кроме человека; класса В (код) —
дежурный агент в отдельной ветке и рабочей копии, без выката.

**Почему не (а):** в 3 часа ночи первая линия должна срабатывать за секунды и одинаково каждый раз;
агент Claude живёт, пока открыт Claude и не спит Mac, и рассуждает там, где нужно заранее записанное действие.
**Почему таблица:** у повторов дедупликация в базе (частичный уникальный индекс по отпечатку), история ночи
переживает перезапуск API и переезд на сервер, экран и агент читают один запрос.

**Важная деталь починки очереди ARI.** Упавшую дельту остатков **нельзя** просто вернуть в очередь: после неё
уже ушли более свежие дельты, и повтор старой перезаписал бы в канале актуальный остаток устаревшим.
Поэтому починка `outbox.failed` — полная выгрузка (текущее состояние PMS на 500 дней перекрывает все
дельты), а неисправностью считается только FAILED-дельта **новее последней успешной полной выгрузки**.

**Последствия:** сторож выключается `GUARD=off`, починка — `GUARD_AUTOFIX=off` (только запись и будильник);
у каждой починки лимит попыток, дальше неисправность становится классом Б. Будильник — Telegram-бот, токен
и чат вписывает владелец в `.env`; до этого неисправности пишутся, но никого не будят, и экран `/incidents`
об этом говорит. Сверка остатков PMS ↔ Channex по расписанию (проверка 10 плана) в первый заход не входит:
она тратит лимит чтения Channex, а суточная полная выгрузка и проверка очереди закрывают тот же риск.

## ADR-029 — WETOP: единый фронтенд действующего хостела поверх текущего API

**Дата:** 2026-09-13. **Статус:** принят прямым поручением владельца «пока конкретно под хостелы» и «Сразу реализовать фронтенд».

**Контекст:** возможности стойки уже реализованы в Next.js/NestJS, но нуждаются в единой навигации,
мобильной компоновке и раскрытии поддержанных полей и групповых действий. Это новое поручение
разрешает текущую работу над интерфейсом после ограничения дальнейшего оформления в ADR-027.
План: `plans/hostel-frontend-2026-09-13.md`.

**Варианты:** переписать приложение и API; собрать отдельный демонстрационный dashboard; развивать
существующие серверные страницы и команды. **Решение:** третий вариант. Next.js Server Components

светлую основу ADR-027: IBM Plex, спокойные таблицы, цвет как сигнал. Боковое меню на компьютере,
модальное меню на телефоне, единые формы, независимая прокрутка таблиц, загрузка/ошибка/404.
Для групп раскрыты `CreateReservationDto.items[]` и существующие `Payment.allocations`.
Доступность в карточке запрашивается один раз на уникальный период, а не по запросу на каждое место.

**Совместная работа:** в ветку включён `main` до `8824974`; новый сторож и экран `/incidents`
сохранены и добавлены в навигацию. Службы launchd и реальные внешние команды в этом прогоне не запускались.

**Проверка и последствия:** изолированные браузерные сценарии идут через настоящий Next.js и
server actions, но отдельный синтетический HTTP API (`tests/ui`). Фикстуры не встроены в приложение.
Это позволяет проверять ошибочные и финансовые сценарии без реальных гостей и платежей. Живая БД,
доступы/роли, tenant isolation и высокая production-нагрузка требуют самостоятельных проверок и работ;
прохождение UI-тестов их не доказывает. Объём и доказательства: `reports/hostel-frontend/README.md`.

## ADR-030 — Разделы гостиницы и отчёт о продажах по каналам

**Дата:** 2026-09-13. **Статус:** реализация по прямому поручению владельца добавить разделы.
План: `plans/hotel-sections-2026-09-13.md`.

**Проблема:** плоская навигация не отражает управление номерами и гостиницей, а технический
экран Channex показывает события синхронизации, а не количество и стоимость заказов.
**Варианты:** перегрузить прежний экран интеграции; заменить его; сохранить его и добавить
отдельный отчёт. Выбран третий вариант: `/channel-manager` для продаж, `/channels` для интеграции.

**Решение:** единый типизированный каталог меню и страниц разделов. Родитель — ссылка на обзор,
отдельная кнопка раскрывает дочерние ссылки. Точный маршрут определяет один активный пункт;
открытый дочерний маршрут раскрывает родителя. Мобильное меню сохраняет dialog/Escape/focus.
Предзагрузка ссылок меню отключена, чтобы расширение меню не запускало все отчёты при открытии.
Страницы остаются Server Components; специфичные стили находятся в `management/hotel.css`.

`GET /hotel/settings` — проекция существующих Property и RatePlan, только чтение, без ключей API.
`GET /hotel/channel-report?from&to&status` — агрегат Reservation по источнику, каналу и валюте.
Диапазон включительный, по arrivalDate, до 366 дней; status=ALL или значение ReservationStatus.
Одна коммерческая бронь = один заказ независимо от числа мест или webhook-ревизий. Стоимость —
сохранённый totalAmount выбранных броней, в ALL включая CANCELLED/NO_SHOW. Отмены и незаезды
показаны отдельными счётчиками. Это не выручка и не оплаченная сумма. Суммы BigInt → строки,
валюты никогда не складываются. Отбор по индексу propertyId/arrivalDate, агрегация выполняется в БД.

Категории и услуги читаются из действующих API, тарифы ведут в действующий редактор.
Доступность читает существующий расчёт на весь срок; ссылка переносит даты и доступную единицу
в форму брони. Статистика использует шахматку, отдельно показывает неназначенные проживания.
Маркетинг отображает реальные настройки сайтов/виджета, подключения — независимые состояния API.

**Последствия:** модель/миграции и финансовые правила не меняются. Редактор реквизитов, расчётного
часа, каталога услуг и категорий пока отсутствует. Для акций, фото, удобств есть явные неподключённые
страницы; фиктивных Save/upload и localStorage-хранилища нет. Решения для следующего среза записаны
в QUESTIONS.md. Unit-тесты проекций без БД и UI-тесты с синтетическим API не доказывают работу
живой БД, авторизацию, доставку OTA или production-нагрузку.

## ADR-031 — Рабочие данные отдельно от тестовых; проверяемое соединение Channex

13.09.2026. Принято по поручению владельца убрать демонстрационные показатели, связать фронтенд
с Channex и проверить интерфейс.

**Проблема.** Локальный preview был запущен с синтетическим API тестов. Его брони и суммы выглядели
рабочими. В текущей копии нет настроенной БД, API или ключа Channex. Статус webhook сам по себе
не доказывает доступ к объекту провайдера.

**Варианты.** Показывать постоянные нули; продолжить демонстрационный режим; использовать только
рабочий источник и явно показывать отсутствие связи. Выбран последний: нули допустимы только
из успешно полученного пустого результата. Реальные брони/счета не удаляются.

**Решение.**

- Обычный frontend читает `APP_API_URL` либо локальный API на 3001. Синтетические ответы запрещены
  в production. UI-тесты требуют `APP_ALLOW_TEST_DATA=1` в отдельном Next dev процессе. Fixture API
  помечает ответы и требует тестовый заголовок до обработки команды; отдельные порты 3100/4311.
- HTTP-чтение ограничено 15 секундами, команды — 60 секундами. Автоматического повтора команды нет:
  при потере ответа операция уже могла сохраниться. Пользователь видит предложение проверить результат.
- Новый GET `/channels/channex/connection` проверяет ключ, локальные сопоставления и доступ к
  сопоставленному объекту через существующий `ChannexClient.getProperty`. Источник контракта:
  сохранённая документация `docs/channex/site/api-v.1-documentation/hotels-collection.md` и клиент пакета
  integrations. Запрос ограничен 8 секундами, без повторов, pull, ACK или записи ARI.
- Диагностика возвращает среду, доступность объекта, количество сопоставлений, время webhook/pull
  и понятные состояния ошибок. Не возвращает ключ, provider response body или данные гостей.
  Доступность объекта не доказывает доставку событий и правильность каждого тарифа.
- После импорта и повторной обработки обновляются связанные страницы; изменения сайта обновляют
  маркетинг и подключения. Ошибки справочников и периодов не подменяются пустыми данными.
- Пояснения перемещены в раскрывающуюся справку, формы и карточки выровнены. Определения денежных
  сумм и ограничения незавершённых функций сохранены.

**Последствия.** В этой копии до настройки API виден статус отсутствия связи. Нужен адрес рабочего
backend либо путь к его окружению; секреты в чат не передаются. Фактическая доставка Channex,
данные БД и нагрузка требуют отдельной проверки на доступном окружении. Схема БД, бизнес-правила
и авторизация данным изменением не меняются.

## ADR-032 — Автосинхронизация из Exely каждые 15 минут до переключения каналов (ПРИНЯТ владельцем 13.09.2026, Q-124 вариант (а))

**Дата:** 2026-09-13. План: `plans/wetop-live-data-2026-09-13.md`, D1.

**Проблема.** До переключения каналов источник правды — Exely, PMS его зеркало. Синхронизация суток
(`cli-sync-day.ts`) запускалась только руками, сторож будит лишь через 26 ч (`exely.stale`). Проверка
13.09.2026 16:50 UTC: последний импорт 08:59 UTC, после 13:13 UTC в PMS не изменилась ни одна бронь —
WETOP показывал утро. При этом скрипт на каждом запуске тянет карточки всех броней суток (~90–150 запросов)
и заканчивает полной выгрузкой ARI в Channex.

**Варианты.** (а) автоматически каждые 15 мин; (б) кнопка «Обновить из Exely»; (в) вручную, как было.

**Решение — (а):**
- задача launchd `kz.luxx.pms.exely-sync` раз в 15 мин запускает `cli-sync-day.ts --auto`; второй экземпляр,
  пока идёт первый, launchd не запускает;
- инкрементально: брони, изменённые в Exely (Active и Cancelled) с начала прошлого успешного прогона минус
  15 мин (не дальше 7 суток), **в местном времени объекта**: Exely понимает `modifiedFrom` во времени Алматы,
  а не в UTC — проверено `scripts/imports/src/cli-exely-modified-window.ts` 13.09.2026 (окно, записанное в UTC,
  вернуло брони пятичасовой давности; то же окно по Алматы — 8 броней за последние 6–65 минут); раз в час
  дополнительно все активные брони текущих суток — страховка от изменений, которых поиск по дате изменения не видит;
- импорт прежний и идемпотентный, гости обезличиваются (ADR-018);
- в Channex — **только дельта остатков** по затронутым категориям и ночам: категория, даты и «занимает место»
  проживаний до и после импорта (`scripts/imports/src/exely/auto-sync.ts`) → `POST /channels/channex/availability/changed`
  → `OutboxAriPublisher` и очередь ARI, как у брони со стойки; без изменений — ни одного запроса. Полная выгрузка
  остаётся ночной страховкой и после ручного массового импорта (сертификация Channex, п. 13: по расписанию
  не чаще раза в сутки — замечание сессии pms-lux-b4 13.09.2026);
- каждый успешный прогон пишет в `audit_logs` действие `exely.sync` (режим, окно, карточек, изменений,
  была ли выгрузка) — по нему сторож и экран свежести знают время последней синхронизации;
- выключатель на день двойного ввода: `scripts/ops/launchd/uninstall.sh exely-sync`, вернуть — `install.sh exely-sync`.

**Почему launchd, а не таймер в API.** Импорт — отдельный процесс со своим соединением и таймаутом транзакции:
долгий или упавший прогон не задевает стойку и сторожа, память освобождается после прогона.

**Последствия.** PMS отстаёт от Exely не больше чем на прогон. Лимиты API Exely в документации без чисел:
при `429` прогон завершается, следующий — через 15 мин. В день двойного ввода задачу снимают вручную,
иначе импорт спрячет расхождения. После переключения каналов задача снимается навсегда: брони приходят из Channex.

**Изменение 13.09.2026 (владелец, план `plans/plan-2026-09-13-live-db-clean.md`, шаг C): интервал 5 минут вместо 15.**
Поручение — новые брони в WETOP «сразу»; Exely сам о бронях не сообщает, поэтому быстрее только чаще опрашивать.
`install.sh`: `StartInterval` 300 (тест `tests/unit/launchd-install.test.ts` red → green). Перекрытие окна поиска
остаётся 15 минут — больше интервала, каждое изменение видят три прогона, импорт идемпотентен. Полный проход суток
раз в час идёт 3–4 минуты; следующий старт, пока идёт прогон, launchd пропускает. Нагрузка на Exely — около 12 прогонов
в час по 2 поиска плюс карточки изменённых броней; Channex по-прежнему получает только дельты при изменениях.
При `429` следующий прогон — через 5 минут.

## ADR-033 — Контент объекта для WETOP читается из Channex (ПРИНЯТ владельцем 13.09.2026, Q-125 вариант (а))

## ADR-034 — Стойка в launchd на production-сборке `next start` (ПРИНЯТ владельцем 13.09.2026, план D4)

**Дата:** 2026-09-13. План: `plans/wetop-live-data-2026-09-13.md`, D4.

**Проблема.** Mac с 8 ГБ памяти, своп 11–13 ГБ. `next dev` держит компилятор в памяти и компилирует экран
при первом открытии 17–71 с; при таймауте чтения 15 с (ADR-031) это даёт ложное «Нет связи с API».
13.09 процессы стойки и API выгружались в своп (STAT U), страница «Сегодня» грузилась до 115 с.

**Варианты.** Оставить `next dev` и закрывать тяжёлые приложения; `next start` на production-сборке.

**Решение.** Задача `kz.luxx.pms.web` запускает `next start` через node-обёртку: если production-сборки нет
(`apps/web/.next/BUILD_ID`), сначала `next build`. Next 16 держит dev-сборку в `.next/dev`, production —
в `.next`, поэтому сборка не мешает запущенному dev. Выкатка правки стойки:
`npm run build -w apps/web` → `launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.web`.
e2e (`playwright.config.ts`, `reuseExistingServer`) идёт на этой сборке.

**Последствия.** Правка в `apps/web` не видна без сборки и перезапуска — сессии и дежурный агент, которые
не выкатывают, стойку на экране не меняют. Сторож перезапускает стойку тем же `kickstart`.

**Реализация и что нашлось при переключении (13.09.2026, 17:05–17:24 UTC).** `scripts/ops/launchd/web-start.mjs`
запускает `next start` напрямую (без npm и sh), ждёт свободный порт; в сервер подгружается
`exit-with-parent.cjs`. Причина: `kickstart -k` добивает обёртку SIGKILL, группу процессов launchd не снимает,
и старый next-server оставался сиротой в памяти. В `install.sh` исправлены три ошибки, из-за которых стойка
дважды стояла по 1,5–3 мин: `--dry` снимал живую задачу; проверка доступа сдавалась на строке bash
«getcwd … Operation not permitted», не дождавшись node под свопом; переустановка не ждала, пока launchd снимет
прежний экземпляр и старый процесс отпустит порт (`bootstrap` — «5: Input/output error»). Тесты red → green:
`tests/unit/launchd-install.test.ts`, `tests/unit/launchd-web-start.test.ts`. Живая проверка: переустановка 14 с,
`kickstart -k` 10 с, сирот нет; процесс стойки ~130 МБ вместо компилятора `next dev`.

## ADR-035 — Общая дизайн-система WETOP и подключаемые UI-проекции

13.09.2026. Принято по прямому поручению владельца реализовать приложенное подробное ТЗ в текущем frontend.

**Проблема.** Разделы имели несколько несогласованных наборов цветов и размеров; не было полноценной тёмной темы, списка броней и карточки поверх шахматки.

**Варианты.** Отдельный макет, замена приложения или постепенная переработка общих компонентов. Выбрана переработка существующего Next frontend с сохранением server actions и DTO.

**Решение.**
- `tokens.css` — единая палитра light/dark, размеры, интервалы и радиусы. `premium.css` — компоненты, общие для всех разделов; существующие стили используют семантические переменные. Печать принудительно светлая.
- `ThemeProvider` хранит `light/dark/system` в `wetop.theme`, учитывает media query и работает при недоступном localStorage. Небольшой скрипт применяет тему до гидратации. Системный стек использует SF на macOS; внешней загрузки шрифтов нет.
- Shell остаётся клиентской оболочкой с серверными страницами-слотами. Сворачиваемая панель, мобильная навигация, глобальный поиск, предпочтения, сводка и уведомления используют реальные элементы управления.
- Booking drawer реализован через parallel/intercepting routes Next. Прямая ссылка открывает полную карточку. В обоих случаях используются те же ReservationActions/FinancePanel и существующие команды; Escape/Back закрывают overlay, revalidation обновляет серверные данные.
- GET `/hotel/reservations` — ограниченная read-only проекция существующих Reservation/Guest/Folio: 25 броней на страницу, стабильный порядок, период до 366 дней, фильтр статуса/поиска и привязка к объекту. Деньги остаются BigInt/string; баланс рассчитывается существующим `folioBalance`, отменённые начисления и voided-платежи исключаются. Модель БД и правила не меняются.
- Список гостей по умолчанию показывает заказчиков броней на сегодня из этой проекции; поиск по всей базе продолжает работать через существующий guests API. Кнопки в номерах открывают существующие карточки и команды уборки/блокировок.
- Помощник формирует оперативную сводку из DeskDay, без LLM-запросов и самостоятельных действий. Экран входа готов к подключению auth, но не создаёт фиктивную сессию. Сообщения позволяют подготовить черновик в памяти текущей вкладки, отправка наружу отсутствует.

**Демо — уточнение ADR-031 по новому поручению владельца.** Пользователь разрешил временные mock data. `npm run dev:demo` явно запускает frontend на 3000 и синтетический источник на 4312. Нужны `NODE_ENV=development`, `APP_DEMO_MODE=1` и точный loopback URL; ответы помечены `demo`, запросы требуют отдельного заголовка. В интерфейсе постоянно видна маркировка. Production и обычный запуск отклоняют такие ответы и команды. Нет автоматической подмены недоступного API. Тесты используют другой процесс/порт/заголовок; общие fixtures размещены в `scripts/preview`, без DB/provider credentials. Для изоляции параллельного preview и UI-тестов используется `.next-ui`, игнорируемый Git/ESLint как generated build.

**Последствия.** Дизайн и UI-сценарии проверяются в браузере. Демо и тестовый API не доказывают работу БД, авторизации, реальную доставку сообщений или интеграций. Live Channex и production-нагрузка требуют настроенного backend. Неподключённые редакторы акций/фото/удобств остаются явно обозначены; существующие операции сохранены.

**Источники.** Установленная документация Next `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/intercepting-routes.md`, `.../01-getting-started/11-css.md`; [Lucide](https://lucide.dev/guide/packages/lucide-react), [Recharts](https://recharts.github.io/api/AreaChart/).


## ADR-036 — Проверка UI, обработка параметров и восстановление форм

13.09.2026. Принято в рамках прямого поручения владельца провести полную проверку интерфейса и исправить дефекты.

**Проблема.** В Next повторяющийся query-параметр является массивом, хотя старые страницы ожидали строку. Некорректные ссылки могли обрушить раздел. У команд без формы отсутствовало состояние ожидания. React мог сбросить неконтролируемые поля после server action, возвращающего ошибку, вместо сохранения неотправленного ввода.

**Варианты.** Локальные исправления в каждом обработчике, замена библиотеки форм или небольшие общие функции с сохранением текущих server actions. Выбран последний вариант.

**Решение.** Страницы принимают фактический тип `SearchParams` и нормализуют повторения по первому значению. Невалидные значения проверяются до API, пользователь сохраняет фильтры и путь сброса. Максимальное окно шахматки берётся из существующего domain. `useCommand` синхронно блокирует повтор через ref, отображает pending и обрабатывает обрыв ответа без автоматического повторения. Формы возвращают только известные введённые поля и номер неудачной попытки; ключ формы восстанавливает эти значения после сброса React. После успеха возвращаются актуальные серверные данные и поля очищаются.

**Проверка.** Добавлен dev-only axe в изолированный Playwright-набор, без отключённых правил и исключённых проблемных узлов. Контраст проверяется для обеих тем, desktop/mobile, а команды — через настоящий Next и синтетический API. Набор `tests/ui` включён в отпечаток e2e-журнала; scripts/preview — в TypeScript. Документы в reports/ui-quality отделяют реальные интерфейсные проверки от отсутствующих backend-подключений.

**Демонстрация.** Списки, доска, карточки, уборка/блокировки и платежные строки используют устойчивые идентификаторы и общий набор записей в памяти. Ответ создания не подменяет новую бронь существующей. Неподдержанные операции дают явную ошибку; fixture не заменяет бизнес-правила PMS и не вызывается production-клиентом.

**Последствия.** Бизнес-модель, API-маршруты, правила денег/бронирования и интеграции не изменены. Клиентская защита от двойного клика не заменяет серверную идемпотентность. Системные шрифты остаются локальными; основные подписи premium UI увеличены до 12px, текст управляющих элементов — до 13px, поля на телефоне — до 16px. Неподключённые auth/роли, редакторы и транспорты не заявлены рабочими.

## ADR-037 — Календарный месяц в шахматке

13.09.2026. Прямое поручение владельца: видеть весь месяц с первого числа на одном экране.

**Проблема.** По умолчанию доска показывала 14 дней от сегодня. Даже переключение на 30 суток оставляло фиксированную ширину колонок и длинную горизонтальную прокрутку.

**Варианты.** Уменьшать масштаб всей страницы, сохранять произвольные 30 суток или отображать календарный месяц с адаптивными колонками. Выбран календарный месяц, без изменения масштаба остального интерфейса.

**Решение.** Начальный период — первое/последнее число месяца по существующей дате объекта (Алматы). Стрелки месячного режима переходят между целыми месяцами, включая февраль и границу года. Произвольный период и режимы 7/14 дней сохранены. Формы дат пересоздаются при смене периода. Таблица растягивается на доступную ширину, подписи броней зависят от фактической ширины их непрерывного участка. Существующие ссылки, перетаскивание, категории и статус на первую дату периода сохранены.

**Адаптивность.** Колонка дня и зона нажатия имеют минимум 24px: ссылка включает границу ячейки. На 760–1279px заголовки номеров переносятся над строками, освобождая ширину для всех дат. Все 31 число помещаются на 768/812/1024/1280/1440/1920px; закрывать боковое меню не требуется. На телефоне прокручивается только таблица, доступная и с клавиатуры. Такое размещение выбрано после проверки фактической панели Codex на 812px: стандартная боковая колонка оставляла часть дней вне экрана, а дальнейшее сжатие нарушало axe target-size. Проверки доступности не ослабляются.

**Последствия.** Изменяется только представление окна существующего chessboard API, до прежнего лимита 62 дня. Данные, API, даты заезда/выезда, доступность, денежная логика и интеграции не меняются. Доказательства — reports/chessboard-month и журнал тестов.

## ADR-038 — Подключение интерфейса к базе существующего проекта

> При слиянии в main 14.09.2026: описание, фото и удобства объекта в `main` уже читаются из Channex (ADR-033,
> `GET /channels/channex/content`), свежесть данных Exely и очереди ARI — `GET /system/freshness` (ADR-032).

14.09.2026. Прямое поручение владельца отображать данные backend/Supabase вместо демонстрации.

**Проблема.** В этой копии проекта запущен `dev:demo`, настройки БД не переданы. При этом основные страницы уже используют NestJS API. В каркасе оставалось название объекта из макета; экран подключений проверял Channex, но не показывал отдельно состояние базы PMS.

**Решение.** Сохраняется цепочка Next.js → NestJS → Prisma → существующий PostgreSQL/Supabase. Прямого доступа браузера к таблицам и новых схем нет. Read-only `GET /system/connection` читает объект по тому же условию, что inventory/hotel API, и агрегирует только его записи. Контракт `DataConnection` не содержит секретов, адресов БД, идентификаторов и данных гостей. `READY`, `PROPERTY_MISSING` и `DATABASE_UNAVAILABLE` различимы, ошибка не выдаётся за нулевой отчёт. Проверка не создаёт инцидентов и не вызывает провайдеров. HTTP 200 означает успешное получение диагностического состояния, готовность определяется полем `state` и `database.connected`.

**Интерфейс.** `/connections` показывает источник PMS и состояние базы отдельно от Channex. Fixture всегда помечает себя `demo`/`synthetic`, даже при успешной загрузке интерфейса. Каркас и обзор читают название объекта из `/hotel/settings`. Suspense ограничен текстовыми слотами названия/адреса: весь интерактивный каркас не заменяется после ответа. Проверкой воспроизведена потеря введённого имени при замене общего fallback; после разделения слотов поле и открытое меню сохраняются, исправлена ошибка hydration выбранной темы. React.cache объединяет чтение сведений об объекте только внутри одного серверного запроса, без кеша между запросами. Ошибка связи показывает отсутствие объекта, не подставляет данные макета. Существующие server actions и отказ от постоянного кеширования API сохранены.

**Запуск.** `npm run dev` читает конфигурацию корня, запускает backend либо использует явный `APP_API_URL`, проверяет базу и только затем запускает frontend. `npm run check:connection` выполняет только GET-проверку существующего API. Новый запуск выключает фоновые pull/outbox/full-sync/webhook-health/guard, не создаёт туннель, не импортирует записи и не применяет миграции. Это не cutover. Прежние API/workspace и launchd-команды не изменены. На другой машине нужны собственные настройки окружения, секреты через Git не передаются.

**Проверка и ограничения.** Контроллер тестируется в настоящем AppModule с подменённым Prisma; браузер — настоящий Next с изолированным API. Отдельно проверен отказ настоящего backend при недоступной локальной тестовой БД. Эти проверки не доказывают подключение Supabase: доступы этой копии ещё ожидаются. Auth/роли, доставка сообщений, акции, фото и удобства требуют отсутствующих backend-возможностей; новая диагностика их не реализует.

**Источники.** Установленные документы Next `01-app/02-guides/environment-variables.md` и `01-app/01-getting-started/05-server-and-client-components.md`; [официальная инструкция Supabase для Prisma](https://supabase.com/docs/guides/database/prisma). Новые роли БД и миграции из примеров документации не выполнялись.

## ADR-039 — Недельный вид шахматки по умолчанию

14.09.2026. Владелец пересмотрел запрос на месячное начальное окно: семь дней должны помещаться на одном экране.

**Варианты.** Скользящие семь суток от сегодня или календарная неделя. Выбрана неделя понедельник–воскресенье, включая прошедшие дни этой недели, в существующей дате объекта (Алматы). Стрелки переключают целые недели; «Сегодня» возвращает текущую. «Месяц», 14 дней и произвольные даты сохранены. Переключение «Неделя» использует неделю, содержащую начало выбранного периода. Ссылки с явными датами по-прежнему воспроизводят этот период после обновления страницы.

**Размещение.** Любое семидневное окно равномерно занимает ширину панели. Номера остаются слева; отдельные стили месяца с переносом названий над строками не применяются к неделе. На узком экране сокращаются вспомогательные подписи, полные даты и загрузка сохраняются в доступных названиях. Минимум на день — 24px, текст и масштаб остального приложения не уменьшаются.

**Последствия.** Меняется только представление существующего chessboard API; новых запросов, зависимостей, изменений схемы, денежной логики и провайдеров нет. Планы, тесты и доказательства — `plans/chessboard-week-2026-09-14.md`, `tests/ui/chessboard-week.spec.ts`, `reports/chessboard-week`.

**Конфигурация.** По дополнительному поручению переданные Supabase API-настройки сохранены в корневой `.env`, права 600, файл игнорируется Git. В шаблоне окружения только пустые имена. `service_role` не экспортируется в клиентское окружение. Следом владелец передал `DATABASE_URL` и остальные настройки сервера. Они также сохранены приватно; PostgreSQL проверен запросом SELECT 1 в read-only транзакции, Prisma нашёл утверждённую гостиницу, а `/system/connection` вернул database / supabase / READY. Ключи Supabase REST не используются вместо Prisma. Фоновые Channex-задачи, guard и уведомления при этом запуске отключены; миграции и загрузка тестовых данных не выполнялись.

## ADR-040 — Сохранение ввода оплаты при обновлении счёта и проверка реальных коммитов

14.09.2026. Владелец поручил проверить всю цепочку интерфейс → backend → Supabase. В сквозной проверке синтетического счёта обнаружено: изменение баланса меняло React key формы оплаты, уничтожало введённое примечание и заменяло сумму полным долгом. В изолированном RED-сценарии введённые 1,25 заменились на 15 000,00 после другого платежа по тому же счёту.

**Решение.** Изменение баланса не пересоздаёт форму. Пока оператор не редактировал сумму, поле получает текущий остаток; после первого ввода сохраняет черновик, включая пустую строку. Своя успешная отправка/ошибка по-прежнему сбрасывает или восстанавливает поля существующим action state. Поля оплаты недоступны во время незавершённой операции этого счёта. Правила расчёта и записи финансов не изменены.

**Проверка.** Помимо синтетических UI/контрактных тестов добавлен отдельный opt-in `tests/live-system`: настоящий Next, Nest и Prisma, независимое чтение закоммиченных строк в общей Supabase. В тестовом Nest заменяется только ARI publisher, отключены внешние команды/ключи и фоновые задачи. Уборка ограничена уникальной меткой и собственными связями; существующие данные и API audit trail сохраняются. Обычный запуск и default e2e не переводятся в этот режим. Подробности и ограничения — `tests/live-system/README.md` и `reports/system-audit/README.md`.

## ADR-041 — Единый выключатель исходящего ARI для отката (ПРИНЯТ владельцем 13.09.2026, Q-126 вариант «б»)

> Номер: в коммите e4299ea и сообщениях сессий 13.09 это решение записано как ADR-035, в 37b3766 — как ADR-037,
> в b748448 (слияние PR #2–#4) — как ADR-038. Перенумеровано в ADR-039 при слиянии PR #5 с GitHub: там ADR-038 занят
> подключением интерфейса к базе, а ADR-035…037 — решениями о дизайн-системе WETOP, проверке UI и календарном месяце шахматки.
> Перенумеровано в ADR-041 при слиянии PR #6–#7 с GitHub (14.09.2026): там ADR-039 занят недельным видом шахматки,
> ADR-040 — сохранением ввода оплаты. Номера, уже отправленные на GitHub, не меняются; сдвигается неотправленное локальное.

**Дата:** 2026-09-13. План: `plans/plan-2026-09-13-rollback-drill.md`.

**Проблема.** Шаг 1 полного отката (`CUTOVER.md` ROLLBACK) — «остановить исходящий ARI». Был только
`CHANNEX_OUTBOX_WORKER=off`: он выключал фоновую очередь, а остатки в Channex уходили ещё четырьмя путями —
починкой сторожа «очередь стоит» (`flush(true)`), починкой полной выгрузкой (`outbox.failed`, `sync.missing`,
`ari.oversell`), кнопками «Отправить сейчас» и «Полная выгрузка». Второе: при откате одного канала глобальная
остановка ARI оставила бы остальные каналы без остатков.

**Варианты** (Q-126). (а) запись в базе с кнопкой на экране — правка модели данных; (б) переменная окружения,
проверяемая в шлюзе, — без правки модели, применяется перезапуском API; (в) файл-флаг на сервере — вне базы.

**Решение.** (б). `CHANNEX_ARI=off` проверяется **в шлюзе Channex** перед `updateAvailability` и
`updateRestrictions` (`apps/api/src/channels/ari-switch.ts`), поэтому его не обходит ни один нынешний и будущий
путь. Дополнительно: очередь при остановке не тратит попытки и не трогает строки (изменения ждут включения);
полная выгрузка отвечает 503 с объяснением, расписание и починка сторожа — «не запущена»; сторож не наблюдает
`outbox.failed`, `sync.missing`, `ari.oversell` и не чинит ничего отправкой, а стоящую очередь показывает с
пометкой «исходящий ARI остановлен вручную» и будит. Приём броней (лента, webhook) выключатель не трогает.
Одна команда: `scripts/ops/ari.sh stop|start|status` — `launchctl setenv` + `kickstart -k` API + проверка, что
запущенный процесс видит выключатель; `start` сразу отправляет накопленную очередь.

**Последствия.** `CUTOVER.md` ROLLBACK разделён: откат одного канала — без остановки ARI; полный откат — с неё.
`launchctl setenv` не переживает перезагрузку машины: после перезагрузки ARI снова включён, поэтому при полном
откате каналы в Channex отключаются сразу вторым шагом. Кнопки в интерфейсе нет — состояние видно в журнале

## ADR-043 — Сроки ожидания соединений с базой: мёртвое соединение закрывается, а не ждёт вечно

> Номер: следующий свободный на `main` 1cb30bb (14.09.2026).

**Дата:** 2026-09-14. Код: `packages/database/src/pool.ts`; тесты `pool-timeouts.test.ts`, `pool.test.ts`.

**Проблема.** 14.09 Mac уснул на батарее (00:01–00:24 PDT). После пробуждения API под launchd не ответил на
`GET /system/connection` за 30 с, свежий процесс достучался до базы за 2 с, зависших транзакций в `pg_stat_activity` не
было; помог только `kickstart -k`. `createPrismaClient` создавал пул pg без единого срока: подключение, ожидание места в
пуле и ответ на запрос — бесконечно, TCP keepalive выключен. Соединение, убитое во сне, само не закрывается: запрос ждёт
ответа, место не освобождается. В транзакции хуже: Prisma ставит ROLLBACK в очередь за зависшим запросом, и `finally`,
возвращающий соединение пулу, не наступает. В журнале API процесс 42210: P2028 в 14:22, шесть `Connection terminated
unexpectedly` с 14:55 до 19:38 PDT (одна — из таймера транзакции Prisma на ROLLBACK), дальше тишина до перезапуска.

**Варианты.** (а) встроенный `query_timeout` pg — отвергнут тестом: запрос получает ошибку, но соединение остаётся
открытым с зависшим запросом, `PgTransaction.rollback()` адаптера отдаёт его пулу без ошибки, и следующий запрос встаёт
за зависшим, а на живом медленном сервере выполнился бы внутри чужой открытой транзакции; (б) `statement_timeout` на
сервере — по мёртвому соединению ответ об отмене не дойдёт; (в) закрывать сокет, если на отправленный запрос база молчит
дольше срока: обрыв сети pg, pg-pool, адаптер и Prisma уже обрабатывают — запросы получают ошибку, пул выбрасывает
соединение, сервер откатывает транзакцию.

**Решение.** (в) вместе со сроками pg-pool и keepalive, во всех процессах через `createPrismaClient`:

| Переменная | По умолчанию | Что ограничивает |
|---|---|---|
| `DATABASE_CONNECT_TIMEOUT_MS` | 30 000 | подключение и ожидание места в пуле; не меньше самого длинного `maxWait` в коде (30 с у импорта) |
| `DATABASE_QUERY_TIMEOUT_MS` | 30 000 | молчание базы на отправленный запрос — соединение закрывается; простой свободного соединения не в счёт |
| `DATABASE_KEEPALIVE_DELAY_MS` | 10 000 | TCP keepalive: через столько тишины система проверяет, жив ли собеседник |

Срок — на ответ, а не на транзакцию: транзакции импорта (до 900 с) состоят из коротких запросов и работают как раньше.
`0` выключает защиту явно, для разовой долгой операции; пусто или ошибка в значении — значение по умолчанию.

**Последствия.** Запрос без ответа 30 с (мёртвое соединение после сна, обрыв сети, долгое ожидание блокировки) падает с
`Database did not answer for 30000 ms; connection closed`, транзакция откатывается, место в пуле освобождается. Худший
случай запроса к API — около 60 с (место + ответ), в пределах 60 с, которые ждёт стойка. Одиночная запись без транзакции,
ждавшая блокировку, может выполниться на сервере уже после закрытия соединения — та же неопределённость, что при обрыве
сети. Свой пул pg без этих сроков остаётся у `tests/tools/test-schema.ts` (копия схемы долгими запросами). Срок опирается
на внутреннее свойство pg `readyForQuery`; если новая версия pg его переименует, упадёт тест простоя, а не API молча.

**Проверено 14.09.2026.** `pool-timeouts.test.ts` — фальшивый сервер PostgreSQL, который принимает соединение и молчит:
на прежнем коде 4 из 5 красные (запрос и ожидание места не завершаются), на варианте (а) красный тест транзакции
(соединение переиспользовано: 1 вместо 2), на (в) 5 из 5. Полные прогоны: unit, typecheck, lint — `tests/runs/JOURNAL.md`.
Живьём 14.09.2026 в 08:47 UTC: `main` перенесён на f39eff9, `kickstart -k` API (pid 46974 → 69197), `GET /system/connection`
— 200 за 1,4 с (`READY`, 88 единиц); через 2,5 мин `/system/connection`, `/inventory/summary`, `/guard/status` — 200,
ошибок в журнале API нет. Настоящий пулер Supabase: `DATABASE_QUERY_TIMEOUT_MS=1 npx tsx
scripts/reconciliation/src/cli-db-activity.ts` падает за 2 с с `Database did not answer for 1 ms; connection closed`,
без переменной — выполняется за 1 с.
Учения `scripts/ops/db-dead-connection-drill.ts` (отчёт `reports/db-dead-connection-drill-2026-09-14.md`): прокси перед
настоящим пулером, в момент «сна» открытые соединения пула молча перестают доставлять байты, одно держит транзакцию.
С выключенными сроками (`--control`, как до ADR-043) через 90 с висят 35 из 35 запросов — поломка 14.09 повторена.
Со сроками по умолчанию четыре прогона: запросы на мёртвых соединениях и в очереди падают на +30 с, первый ответ через
30,9–31,0 с, висящих 0, дальше ~170 мс на запрос. Не проверено: TCP keepalive (на пробы отвечает локальный прокси) и
сон самой ОС — его проверит следующее пробуждение Mac. Попутно: соединение с пулером идёт **без TLS** (клиент шлёт
StartupMessage без SSLRequest; вход SCRAM, пароль по сети не передаётся, запросы и ответы — открытым текстом).
Прежняя запись здесь про «TLS-соединение» была ошибкой; решение о шифровании — за владельцем (строка подключения).

## ADR-044 — Посадка из Exely с одним переездом внутри срока (ПРИНЯТ владельцем 14.09.2026, Q-120)

**Дата:** 2026-09-14. Ответ владельца на Q-120: «даю добро, делай».

**Проблема.** Импорт сажал проживание на одну ячейку на весь срок. Два случая, где это расходится с объектом:
(1) свободная ячейка есть каждую ночь, но каждую ночь разная — проживание оставалось без ячейки и пропадало с шахматки
(13.09, `reports/unseated-stays-2026-09-13.md`); (2) гость переехал посреди проживания — Exely хранит одну комнату на весь
срок, новая койка в прошедшие ночи была занята другим гостем, и PMS держала гостя на старой койке (14.09: 12–13 проживаний
не на своих койках, `reports/system-trace-2026-09-14.md`). Цепочки обменов упирались в такие прошлые ночи целиком.

**Решение.** При синхронизации из Exely проживание может сидеть на двух ячейках **своей категории с одним переездом**
(стык по ночи; как «переселить с даты» на стойке, ADR-006):
1. Место из Exely свободно на весь срок — весь срок на нём (как было).
2. Место из Exely занято только в первые ночи срока и освобождается не позже сегодняшней ночи (переезд уже был) — до
   этой ночи проживание остаётся на своей нынешней ячейке, с неё — на месте из Exely. Будущий переезд не придумывается:
   если место из Exely освобождается только завтра или позже, проживание остаётся на своей ячейке, конфликт в отчёте.
3. Иначе своя нынешняя ячейка на весь срок, если она своей категории и свободна (как было).
4. Ячейки нет или она не годится: при переезде, который уже был (п. 2), — свободная ячейка категории на первые ночи и
   место из Exely дальше; иначе первая свободная ячейка на весь срок (как было); нет такой — две ячейки: та, что свободна
   с первой ночи дольше других (при равенстве — меньший номер), и с ночи переезда — место из Exely, если оно свободно,
   иначе первая свободная по номеру. Блокировки и неактивные ячейки учитываются. Нет и такой пары — без ячейки (Q-119).
5. Больше одного переезда система не назначает; категорию посреди срока не меняет.

**Границы.** Только импорт из Exely (Q-120 — «при синхронизации из Exely»). Автоназначение броням каналов и сайта (Q-094)
сажает по-прежнему на весь срок; расширить — отдельным решением. Числа суток, остатки и ARI не меняются: они считаются по
проживаниям, а не по ячейкам. Модель данных не меняется: проживание и раньше могло иметь несколько `Allocation`.

**Последствия.** В отчёте импорта у конфликта появляется `split` — с какой ночи и на какую ячейку переезд; журнал
`exely-sync` печатает «до даты на X, с даты на Y». Сквозная сверка считает проживание на месте, если среди его ячеек есть
ячейка из Exely, и отдельно показывает проживания с переездом.

## ADR-045 — WETOP на домене wetop.ai: адреса, вход через Cloudflare Access, главная на Cloudflare Pages (ПРИНЯТ владельцем 14.09.2026)

**Дата:** 2026-09-14. План: `plans/wetop-domain-2026-09-14.md` (подтверждён «Делай по плану»). Ответы на развилки:
адреса — «делай как надо»; главная — отдельная страница о платформе с блогом, «Регистрация (пробный период)» и «Войти»;
DNS домена пустой; стойка — порядок и надёжность без смены дизайна.

**Проблема.** Домен wetop.ai куплен (Spaceship). Стойка и API работают на Mac и слушают 127.0.0.1 без входа (ADR-023);
наружу до сих пор ходил быстрый туннель, который открывал всё API и менял адрес. Нужны постоянные адреса, вход в стойку и
главная страница платформы.

**Варианты.** Вход: (а) Cloudflare Access перед стойкой — без правки модели, почта по коду из списка; (б) свои учётные
записи в PMS — правка `DATA_MODEL.md`, отдельный срез, дни. Главная: (а) Cloudflare Pages, статический сайт; (б) тот же
туннель с Mac. Публичные пути API: (а) отдельный хост с белым списком путей; (б) весь порт, как у быстрого туннеля.

**Решение.** Вход (а), главная (а), API (а).
- `wetop.ai` — главная `apps/site` (статическая сборка Next.js, блог на файлах Markdown), выкладка на Cloudflare Pages —
  не зависит от Mac. Данные владельца — один файл `apps/site/src/site.config.ts`.
- `app.wetop.ai` — стойка через именованный туннель (служба launchd `domain`, конфиг `~/.cloudflared/wetop.yml`, образец
  `scripts/ops/cloudflared-wetop.example.yml`), за Cloudflare Access; `cloudflared` сам проверяет токен Access
  (`originRequest.access`). `/login` показывает почту из `cf-access-authenticated-user-email` и «Выйти».
- `api.wetop.ai` — только `/a/pms.js`, `/a/hit`, `/w/widget.js`, `/w/availability`, `/w/book`, `POST /channels/channex/webhook`;
  демо-страницы и остальное — 404. Лимиты виджета считают посетителя по `CF-Connecting-IP` (только от loopback).
- Постоянный адрес — `PUBLIC_API_URL=https://api.wetop.ai`: API отвечает 409 на регистрацию webhook на любой другой адрес,
  сторож считает webhook недоставленным, если в Channex зарегистрирован не он; редирект входа и проверка на бота больше не
  засчитываются как «адрес жив». Быстрый туннель и `domain` одновременно не ставятся (`install.sh`).

**Почему.** Access закрывает стойку сразу и без правки модели (роли и свои учётки — отдельный этап, ADR-023); главная на
Pages переживает сон Mac (14.09 ночью Mac на батарее уснул); белый список путей не открывает брони и счета наружу.

**Последствия.** Шаги владельца (`plans/wetop-domain-2026-09-14.md` §8): аккаунт Cloudflare, NS в Spaceship, Zero Trust
(Cloudflare может попросить карту для бесплатного плана), почты для входа, `cloudflared tunnel login`, `PUBLIC_API_URL` в
`.env`. Для настоящих данных гостей по-прежнему нужен сервер в Казахстане (условие 1 `CUTOVER.md`): при переезде адреса
`app` и `api` не меняются, туннель запускается на сервере. Регистрация с пробным периодом — Q-129.

## ADR-046 — Свои учётные записи, регистрация и пробный период (принято по поручению владельца «делай регистрацию», 15.09.2026)

**Дата:** 2026-09-15

**Проблема.** Поделиться WETOP нельзя. Единственный вход это Cloudflare Access (ADR-045): список почт,
который владелец ведёт руками. Человек не может ни зарегистрироваться, ни получить доступ сам. Экран
входа `apps/web/src/app/login/login-form.tsx` нарисован, но обработчик формы отвечает «Вход в рабочий
аккаунт ещё не подключён». Кнопка «Попробовать бесплатно» на `wetop.ai` ведёт в раздел «Как начать»,
потому что вести её некуда (Q-129).

**Что этим отменяется.** ADR-023 выносил вход по пользователям в «отдельный этап после переезда».
Ментор курса 13.09 велел модель под платформу не закладывать до конца переезда хостела. Владелец
15.09.2026 решил иначе и принял последствие: **переезд хостела на время этого среза отодвигается**.
Ролей и разграничения прав ADR-023 это решение не отменяет: все пользователи внутри организации
по-прежнему равноправны, контролем остаётся журнал.

**Варианты.** Вход: (а) почта плюс одноразовый код; (б) почта плюс пароль. Арендность: (а) `organization_id`
сразу во всех таблицах броней, гостей, счетов и тарифов; (б) учётные записи и организации заводятся,
данные существующего объекта не трогаются, разделение данных отдельным срезом позже.
Пробный период: (а) пустой объект; (б) демо-объект с вымышленными бронями.

**Решение.** Вход (а), арендность (б), пробный период (б).

- Вход по одноразовому коду на почту, шесть цифр, 10 минут, три попытки. Паролей не храним: нет хешей,
  нет восстановления, меньше поверхность атаки. Пароль можно добавить позже, убрать позже нельзя.
- Регистрация создаёт организацию, первого пользователя и пробный период на 7 дней.
- На время пробного периода человек видит **демо-объект с вымышленными данными**, а не Luxx Aparts:
  разделения данных по организациям ещё нет, и пускать чужих в живой объект нельзя.
- По истечении 7 дней организация переходит в режим только чтение; продление руками владельца.
- Приглашения администраторов в организацию по почте. Каждый под своей учёткой, `audit_logs` получает
  автора действия (это прямо предусмотрено ADR-023).
- Стойка Luxx Aparts до конца переезда остаётся за Cloudflare Access. Два входа сосуществуют.

**Последствия.**
- Новый раздел §13 `DATA_MODEL.md`: `organizations`, `users`, `memberships`, `login_codes`, `sessions`,
  `invites`. Существующие таблицы не меняются.
- Нужен отправитель почты (Resend, Postmark или SES) и записи SPF, DKIM, DMARC на `wetop.ai`. Без него
  коды слать нечем. Аккаунт заводит владелец.
- Почты пользователей это персональные данные. `PII_STORAGE` и условие допуска `CUTOVER.md` касаются
  гостей, не пользователей системы, но хранение почт в текущей базе надо проговорить отдельно.
- Пока не сделано разделение данных по организациям, продавать доступ к живому объекту нельзя.
  Это следующий срез, и он тяжелее этого.

**План:** `plans/slice-13-accounts-2026-09-15.md`. Развилки Д1–Д6 закрыты этим ADR.

## ADR-047 — «Главная» как дашборд собственника за период; списки дня уходят с главной (принято по поручению владельца, 16.09.2026)

**Проблема.** Экран «Обзор дня» показывал одну дату: пять карточек и три списка «Заезды / Выезды /
Живут» под ними. Владелец 16.09.2026: главная — экран собственника и управляющего, на ней должны быть
главные показатели с удобным периодом (сегодня, вчера, этот месяц, прошлый месяц, свой отрезок), а блок
«Работа с гостями» внизу «не к чему в этом разделе».

**Варианты.** (а) Оставить «Обзор дня» и сделать отдельный раздел «Отчёты»; (б) главная становится
дашбордом за период, а полоса стойки на сегодня остаётся на ней же внизу; (в) дашборд с прогнозами
и планом продаж.

**Решение.** (б). Маршрут `/today` и пункт меню «Главная» те же. Сверху период, шесть показателей
со сравнением с предыдущим отрезком той же длины, столбики загрузки по дням (на один день — по
категориям), источники броней, категории, оплаты по способам. Ниже — «На стойке» на сегодня (или на

(`/reservations?date=`), ссылка «Все брони дня» ведёт туда. (в) отклонён: прогнозов и целей в данных
нет, придумывать их запрещено (AGENTS.md §15).

**Определения показателей — только из того, что уже посчитано в системе.**

| Показатель | Как считается | Совпадает с |
|---|---|---|
| Загрузка | занятые клетко-ночи шахматки / (единиц × ночей); без ячейки — отдельно, в загрузку не входят | «Статистика», кольцо прежнего «Обзора дня» (Q-107) |

| Средняя цена ночи (ADR) | начислено за проживание / занятые клетко-ночи, целочисленно в тиынах | — |
| Доход на место (RevPAR) | начислено за проживание / (единиц × ночей) | — |
| Заезды, выезды, гости | проживания по дате заезда / выезда, без отменённых и незаездов; отмены и незаезды отдельно | «Обзор дня» |

Период до 366 дней (как отчёт по каналам). Отрезок, заходящий в будущее, подписан «включая будущие
брони». Расчёт — `packages/domain/src/dashboard`, API — `GET /desk/dashboard?from&to` (`apps/api/src/dashboard`),

**Последствия.** Модель данных не меняется. `data-testid` полосы стойки (`c-inhouse`, `c-arrivals`,

сверка `cli-system-trace.ts`. Заголовок экрана «Обзор дня» → «Главная»; тесты приведены. Платежи,
перенесённые из Exely, датированы днём переноса (`paid_at`), поэтому «Получено оплат» за сентябрь
включает предоплаты августовских броней — это свойство переноса, не расчёта (см. Q-134).

## ADR-050 — Доступная шахматка на узком экране (принято 19.09.2026)

## ADR-049 — Вход по логину и паролю: сделан 15.09.2026, способ входа спорит с ADR-046 (Q-146)

**Дата:** 2026-09-15. План: `plans/slice-13-accounts-saas.md`. Развилки — Q-134…Q-140.
**Решение владельца 15.09.2026:** «шаг 1 сейчас» (Q-134 закрыт). Делается вход по логину и паролю, роли и автор
действия в журнале; организации, подписки и регистрация самообслуживанием ждут первой живой смены на объекте.
Cloudflare Access не снимается: свой вход не отменяет замок на периметре, пока PMS живёт на Mac владельца.

**Проблема.** Владелец 15.09 нажал «Войти» на `wetop.ai` и не нашёл формы логина. Причина не в вёрстке: входа по
паролю в системе нет. Стойку закрывает Cloudflare Access (ADR-045), а он пускает по одноразовому коду на почту и
своих паролей не хранит; форма на `/login` — заглушка от фронтенда, она честно говорит «вход не подключён».
На вопрос о способе входа владелец ответил шире: WETOP делается как SaaS — партнёры-компании, у каждой своя
регистрация, логин и пароль, и провайдер видит статус их оплат. В модели на сегодня нет ни `User`, ни
`Organization`, ни подписки; `AuditLog.user_id` есть, но всегда `NULL` (ADR-023).

**Варианты входа.** (а) оставить Access с кодом на почту — работает, паролей никто не хранит, но администратору
на смене раз в сутки ловить код, и партнёрам так систему не продать; (б) Access с внешним провайдером (Google,
Microsoft) — привычный экран «почта и пароль», паролей мы не храним, настройка в дашборде Cloudflare за минуты,
но у каждого сотрудника должен быть рабочий аккаунт Google, и мультиарендности это не даёт; (в) свои учётные
записи в PMS — правка `DATA_MODEL.md` (§13), сессии, роли, сброс пароля; журнал наконец знает автора действия;
это первый камень SaaS, но пароли (хеши) храним мы, и это дни работы плюс переделка всех сквозных тестов, которые
сейчас ходят по стойке без входа.

**Предложение.** (в), но по шагам, и Access **не снимать**: свой вход не отменяет замок на периметре, пока PMS
живёт на Mac владельца. Шаг 1 — пользователи, сессии, роли, автор в журнале (объекту нужен и без SaaS: журнал без
автора бесполезен). Шаг 2 — организации и изоляция данных двумя замками (RLS в Postgres плюс обёртка Prisma).
Шаг 3 — планы, подписки, счёт и статус оплаты, кабинет провайдера. Шаг 4 — регистрация самообслуживанием и
приглашения. Шаги 2–4 — это другой продукт, и на них уйдут недели.

**Почему не сразу всё.** Переезд хостела не закончен: сервера в Казахстане нет, каналы не переключены, живых суток
в новой системе не было ни одних — а это и есть определение готовности первой версии (PLAN.md). Ментор 13.09 велел
довести переезд и не закладывать модель вперёд (ADR-019 отложен). Отсюда Q-134: начинать SaaS сейчас или после
первой смены. Шаг 1 этому не мешает — он не касается ни одной брони.

**Дополнение 15.09.2026 (вечер), решение владельца по Q-137: письма через сервис отправки (Resend).**
Сотрудник задаёт пароль сам по одноразовой ссылке из письма — владелец пароля не знает. Приглашение и сброс
пароля — одна дорога и одна таблица `password_resets`: новая учётная запись создаётся со статусом `INVITED`
и пустым хешем (CHECK базы это допускает только для приглашённого), ссылка живёт 24 часа и работает один
раз, новая ссылка гасит прежние. Отправитель живёт в `packages/integrations/src/mail` (ADR-004), описание
внешнего API — `docs/mail/README.md`. Без `RESEND_API_KEY` система работает: приглашение печатает ссылку в
консоль CLI, а запрос сброса отвечает «отправка писем не настроена». Наружу это ничего не открывает:
`/auth/password-reset/*` доступны без входа по построению, но ответ на запрос сброса всегда одинаков, и по
нему нельзя узнать, есть ли такая почта в системе. Supabase Auth не берём: почты и пароли сотрудников —
персональные данные и должны жить в базе Казахстана (ADR-018, Q-140), а роли и журнал всё равно наши, вышло
бы два набора пользователей.

**Последствия, если принято.** Утверждение §13 `DATA_MODEL.md`; миграция с `down.sql`; проверка сессии в API
(сегодня он слушает `127.0.0.1` без входа, ADR-023), служебный ключ для сторожа и скриптов сверки; публичные пути
`/a/*`, `/w/*` и webhook остаются без входа (SECURITY.md §11); вход в фикстуры 23 сквозных и 25 UI-проверок; почта
сотрудника — персональные данные, значит тот же `PII_STORAGE` и граница РК (ADR-018, Q-140).

## ADR-050 — Проживание, исчезнувшее из карточки Exely, отменяется импортом (ПРИНЯТ владельцем 15.09.2026, Q-127 вариант «а», «делай сам»)

**Дата:** 2026-09-15. Разбор: `plans/q127-q128-2026-09-15.md`.

**Проблема.** Импорт обновлял только проживания, которые есть в карточке брони Exely. Проживание, удалённое из брони
или перенесённое в другую (бронь `20260921-513903-1261675666`, 13.09.2026), оставалось в PMS активным: сутки расходились
на одно проживание, стойка и канал видели на место меньше, в день двойного ввода это ложный FAIL гейта.

**Варианты.** (а) отменять как отмену; (б) удалять вместе со счётом; (в) не трогать, показывать в сверке.

**Решение.** (а) с предохранителями. Карточка брони всегда приходит целиком (и по периоду, и по окну изменений), поэтому
проживание с `exely_room_stay_id`, которого в карточке нет, — удалено в Exely. Импорт переводит его в `CANCELLED`, снимает
ячейку, сторнирует начисление за проживание, штраф не начисляет, пишет в журнал `reservation.item.vanished` с причиной и
называет в отчёте (`report.vanished`, строки в выводе `cli-sync-day`). Предохранители: карточка не пустая; проживание ещё не
закончилось (`departure_date >= сегодня` в Алматы — прошлое уже прожили, его не трогаем); уже отменённые, незаезды и
выехавшие не трогаются; повтор ничего не делает. Удаление строк (б) отвергнуто: след нужен сверке и стойке.

**Последствия.** `scripts/imports/src/exely/import-reservations.ts`; тест `tests/integration/reservations-import.test.ts`
«Q-127 / Q-128» — красный до правки, зелёный после. Если Exely вернёт проживание в карточку, повторный импорт восстановит
его как обычное изменение статуса (те же ключи).

**Уточнение по ревью 15.09.2026 (вечер).** (1) Правило включается только для живых карточек — `cancelVanished: true`
передаёт `cli-sync-day`; снимок с диска (`cli-import-reservations`) так не считается: повтор старого снимка снёс бы
проживания, добавленные позже. (2) Заселённого гостя (`CHECKED_IN`) и проживание, у которого на счёте есть оплата,
импорт не отменяет, а называет в отчёте (`vanishedKept`, строка «ИСЧЕЗЛО ИЗ EXELY, НЕ ТРОНУТО») — это к человеку, как у
сторожа с классом Б; развилка по деньгам записана как Q-147. (3) Освободившиеся ночи исчезнувших проживаний попадают в
дельту остатков Channex (`withVanished`), иначе канал видел бы на место меньше до ночной полной выгрузки.

## ADR-051 — Оплата, удержанная в Exely при отмене, переносится начислением (ПРИНЯТ владельцем 15.09.2026, Q-128 вариант «а», «делай сам»)

**Дата:** 2026-09-15. Разбор: `plans/q127-q128-2026-09-15.md`.

**Проблема.** В Exely отменённое и оплаченное проживание без возврата держит начисление: total = paid, balance 0. У нас
начисление за проживание при отмене сторнируется, платёж `EXTERNAL exely:<stay>` остаётся — баланс −сумма, будто отель
должен гостю (бронь `20260902-513903-1262702198`, единственное расхождение среди 169 отменённых сентября).

**Варианты.** (а) удержание начислением на оплаченную сумму — баланс 0, как в Exely; (б) сторнировать и платёж — в кассе
Exely возврата нет, разойдётся; (в) минус на счёте, стойка разбирает руками.

**Решение.** (а), только при импорте и только для перенесённых проживаний: если проживание отменено или незаезд, оплачено
в Exely (`amount − toPay > 0`) и возврата нет (`toRefund = 0`), на счёте держится ровно одно активное начисление
`PENALTY` «Удержано в Exely при отмене (перенос)» на сумму оплаты. Вернулось в активное, сумма изменилась или появился
возврат — удержание сторнируется (voided_at) и, если нужно, создаётся заново. Модель не меняется: `ChargeKind.PENALTY`
уже есть; правило штрафа Q-103 к перенесённым проживаниям по-прежнему не применяется (тарифа на проживании Exely не
отдаёт). Отмены, сделанные уже в PMS, идут по Q-103/ADR-022 и сюда не попадают.

**Последствия.** Сверка балансов с Exely сходится и на отменённых оплаченных; в отчёте импорта `retained`. Тот же тест, что
у ADR-050. Механизм «ровно одно активное начисление» вынесен в `ensureSingleActiveCharge` (`packages/database/src/folio.ts`)
и общий с начислением за проживание.

**Оговорка (ревью 15.09.2026, Q-148).** `toRefundAmount` в документации Exely — «сумма, доступная к возврату», а не
«возвращено». Условие «возврата нет» = `toRefund = 0` верно, если после исполненного возврата Exely обнуляет и оплату
(`toPay` растёт); это не проверено на настоящем возврате. До проверки правило действует как записано; проверка — Q-148.

## ADR-053 — Вход только по логину и паролю; Cloudflare Access снимается (ПРИНЯТ владельцем 19.09.2026)

**Дата:** 2026-09-19
**Решение владельца:** «не хочу входить через этот экран [Cloudflare Access], хочу входить через авторизацию
логин-пароль самого приложения; так будут входить и все остальные».
**Что сделано:** на сервере включены `AUTH_REQUIRED=1` (API) и `APP_AUTH_REQUIRED=1` (стойка), выписан
`SERVICE_API_KEY` для сторожа и скриптов, заведена первая учётная запись владельца (`accounts create`).
Проверено: `/today` без сессии уводит на `/login`, владелец вошёл, экраны работают.
**Закрывает Q-146 (20.09.2026).** На прямой вопрос «оставляем оба способа или только пароль» владелец
ответил: «давай без Cloudflare Access, а по паролю». Сотрудники входят почтой и паролем.

**Cloudflare Access снят 20.09.2026.** Приложение `wetop-desk` (`app.wetop.ai`, политика `wetop-desk-allow`)
удалено в Cloudflare Zero Trust; проверено: `app.wetop.ai/today` без сессии ведёт прямо на `/login` PMS,
экрана Access больше нет. ADR-045 (Access как внешний замок) этим отменён — единственный замок теперь свой.

**Экран приведён к решению 20.09.2026.** Вход по коду с экрана снят: на `/login` остались почта и пароль,
рядом кнопка «Регистрация». Регистрация переписана на три поля — почта, имя, пароль (владелец на вопрос
про четвёртое поле «логин» ответил: «давай почта пароль»). Письма в этом пути больше нет: `/auth/register`
переехал с `AccountsController` на `AuthController`, заводит организацию, человека и членство одной
транзакцией и сразу отдаёт ключ сессии — тот же отпечаток и срок, что у обычного входа. Прежний
`AccountsService.register` снят как мёртвый.

Отдельного поля «название организации» в форме нет: владелец назвал три поля, а `organizations.name`
пустым быть не может — рабочее пространство называется именем человека и переименовывается в настройках.

Занятый адрес форма регистрации называет прямо («уже зарегистрирован»), и это осознанная разница с формой
входа, где ответ один на все отказы: иначе человеку, который регистрируется второй раз, нечего ответить.

**Приглашения переведены на пароль (20.09.2026, тем же днём).** Принятие приглашения больше не шлёт код:
`POST /auth/invites/:token/accept` заводит членство и отдаёт в ответе одноразовый ключ, по которому человек
сразу задаёт себе пароль (`/login/set-password`). Письма в этом пути нет намеренно — сама ссылка-приглашение
и есть доказательство, что перед нами приглашённый, а почтовая служба может быть не настроена, и тогда
приглашение просто не работало бы. Если пароль у человека уже есть (позвали во вторую организацию), ключ
не выдаётся: он входит своим паролем. Ключ живёт в `password_resets` — той же таблицей, что и «забыли пароль»,
в базе только отпечаток.

**Код на почту удалён (20.09.2026, третьей правкой того же дня).** Сняты: маршруты `/auth/code` и
`/auth/verify`, выдача и проверка кода в `AccountsService`, пределы на перебор, методы репозитория
(`saveLoginCode`, `latestLoginCode`, `markCodeAttempt`, `markCodeUsed`, счётчики), доменный модуль
`login-code`, письмо с кодом, `requestCode`/`verify` в стойке и шаг ввода кода на экране входа.
Приведение почты (`normalizeEmail`, `isEmailShaped`) жило в том же модуле, хотя к коду отношения не
имело, — переехало в `accounts/email.ts`.

Попутно нашлось и снято ещё одно: `GET /auth/me` и `POST /auth/logout` были объявлены **дважды** —
в `AuthController` и в `AccountsController`. Отвечал только первый (AuthModule подключён раньше), и
второй, понимавший лишь отпечаток сессии по коду, не отвечал никому ни разу. Тесты его при этом
проверяли: в их модуле он был единственным.

**Таблица `login_codes` оставлена в базе.** Кода, который в неё пишет, больше нет; снос таблицы —
боевая миграция, её делает владелец руками (AGENTS.md §15). Отдельным решением, не этой правкой.

**Продление сессии при работе (PR #29) стало недостижимым.** Оно касалось только сессий входа по коду:
смена по паролю кончается через 12 часов намеренно (ADR-049). Ветка убрана, чтобы не выглядеть
работающей; `shouldRenewSession` в домене остался. Продлевать ли смену по паролю — **Q-153, вопрос
к владельцу**.
**Следующий шаг:** снять приложение `wetop-desk` в Cloudflare Zero Trust (или политику Bypass) — тогда
`app.wetop.ai` ведёт прямо на экран входа PMS. Сотрудники заводятся `accounts invite` (письмо со ссылкой,
пароль задаёт сам человек) — нужен ключ почтовой службы в `.env`.

## ADR-054 — Независимые исполнители браузерной приёмки (20.09.2026)

**Проблема:** 181 UI-сценарий в CI занял 23,3 минуты при лимите задания 25 минут.
Последовательное получение одного расхождения снимков за прогон замедляло диагностику.
**Варианты:** поднять таймаут; ослабить набор; распределить полный набор по изолированным
исполнителям. **Решение:** три Playwright shard на трёх GitHub runners, каждый с одним
worker и собственным синтетическим API. Общая проверка с прежним именем успешна только
при успехе всех частей; fail-fast выключен, чтобы собрать все доказательства.
Для снимков используется soft assertion: она собирает все отличия, но любое отличие
по-прежнему проваливает тест, порог 0,002 не меняется. Отдельный небольшой артефакт
изображений позволяет проверять отличия без скачивания всех трасс.
**Последствия:** набор и критерии приёмки сохранены; база Supabase и внешние сервисы
в этих заданиях не используются. Референсы обновляются только после просмотра.

## ADR-055 — Единая настройка самостоятельной регистрации (20.09.2026)

**Текущее решение:** владелец прямо отменил закрытие: «почему регистрация закрыта … сделай норм».
Регистрация доступна по умолчанию, без зависимости от настройки почтовой доставки.
Отсутствующий или пустой `REGISTRATION_OPEN`, а также `1` после trim разрешают регистрацию;
`0` и нераспознанные непустые значения запрещают её. `.env.example` задаёт `1`.
Стойка получает настройку от API через `/auth/options`; второго APP-флага нет.
При недоступности API регистрация не предлагается, форма входа сохраняется.

**Варианты:** включить только локальную переменную; вернуть рабочее поведение по умолчанию
в репозитории. Выбран второй вариант, чтобы новый экземпляр не наследовал неожиданное
закрытие. Явный выключатель сохранён для оператора.

**Последствия:** схема, существующие аккаунты, приглашения и правила сессий не меняются.
Q-152 об изоляции организаций остаётся OPEN; это изменение не реализует изоляцию.
План: `plans/reopen-registration-2026-09-20.md`. Прежнее ограничение и запрет его отката
ниже отменены этим прямым поручением.

### История отменённого временного ограничения

**Проблема:** Q-152: новая организация получает доступ к общим данным объекта.
**Варианты:** сначала построить изолированное демо; временно закрыть самостоятельную
регистрацию. **Решение владельца:** «делай» на предложение второго варианта.

API использует `registrationOpen()` и `REGISTRATION_OPEN=1` после trim перед обработкой регистрации;
без явного разрешения возвращает 403, не обращается к БД и не выдаёт сессию.
`GET /auth/options` публично возвращает только `{ registrationEnabled: boolean }`.
Стойка получает флаг без кэша с того же API; сбой или отсутствие настройки означает
закрытую регистрацию. Прямые `/register` и `/login?mode=register` показывают вход
и объяснение ограничения. Ранее открытая форма тоже получает отказ от API.

Вход сотрудников, приглашения и восстановление пароля продолжают работать.
Явное разрешение оставлено для изолированных проверок прежнего сценария; на
рабочем экземпляре оно остаётся выключенным до отдельного решения по изоляции.
**Последствия:** схемы и существующие учётные записи не меняются; мера не исправляет
tenant isolation и не отзывает сессии ранее зарегистрированных организаций.
Для выкладки сначала обновляется API, затем стойка; включать регистрацию при
откате или возвращать прежний открытый API без дополнительного ограничения нельзя.

В том же `main` появился вариант с парой `REGISTRATION_OPEN` / `APP_REGISTRATION_OPEN`.
При объединении сохранены серверное имя `REGISTRATION_OPEN` и его проверка; отдельный
флаг стойки убран. Стойка получает настройку API, поэтому два процесса не могут
разойтись из-за разных переменных окружения.

## ADR-056 — Номерной фонд как каталог существующих мест (20.09.2026)

**Проблема:** владелец не может быстро прочитать техническую таблицу /inventory.
**Варианты:** уплотнить старую таблицу; собрать категории и места в каталог с двумя видами.
**Решение:** по поручению владельца выбран каталог. Сервер получает прежние summary/units
один раз; клиент фильтрует загруженный состав. Поиск, категория, тип и вид сохраняются в URL
через Native History API, связанный с useSearchParams; перезапрос на каждую букву не нужен.
Основание: https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api.

Используются существующие Page, Input, Select, Button, Table, EmptyState, LoadingState и Icon.
Область новых стилей — только .inventory-*. Вместимость размещения берётся из capacityAdults
категории, физическая комната — из roomNumber. Вместимость комнаты не выдаётся за число гостей
на одной койке. Каталог не обозначает места свободными: доступность остаётся отдельным экраном.
**Последствия:** маршруты ?category= и /units/[code] сохраняются; схема, API, данные, уборка,
блокировки и интеграции не меняются. Префетч ссылок 88 карточек отключён, чтобы не нагружать API.


## ADR-056 — Одна установка обслуживает одну гостиницу (20.09.2026)

**Основание:** приёмка 20.09.2026 (Q-152) показала фактом, что новая организация видит объект этой
гостиницы. Разбор — `reports/isolation-2026-09-20.md`. Владелец на вопрос «каким путём» ответил:
«делай как надо, мы готовимся уже к аттестации и к работе».

**Что выяснилось при разборе и должно быть сказано прямо:** данные не знают про организации вообще.
Организация живёт только в слое учётных записей; восемь таблиц несут `property_id`, а какой это
объект — решает поиск по захардкоженному имени в 14 файлах API. Ключи Channex и почты лежат в
`.env`, то есть на установку, а не на организацию. Это одноместная система, к которой сбоку пришили
многопользовательский вход.

**Решение:** так и считать. Одна установка — одна гостиница: своя база, свой `.env`, свои ключи
каналов. Самостоятельной регистрации в продукте нет; сотрудников заводит владелец приглашением,
каждый задаёт себе пароль сам. Выключатель `REGISTRATION_OPEN` (ADR-055) остаётся закрытым.

**Что из этого следует для сайта:** «Попробовать бесплатно» вело на `/register`, то есть на экран
«Регистрация закрыта», а раздел «Как начать» обещал регистрацию, код из письма и 7 дней в
демо-объекте. Ни одного из этих трёх нет. Кнопка переименована в «Оставить заявку» и ведёт в раздел
«Как начать» (штатное поведение при пустом `trialHref`), тексты приведены к факту. Свою ссылку на
заявку — форму, WhatsApp, `mailto:` — владелец вписывает в `site.config.ts`.

**Что НЕ делается и почему.** Пробный период, организации и приглашения из схемы не выпиливаются:
они работают, ничего не обещают наружу и понадобятся, если владелец выберет путь Б (отдельное демо)
или В (разделение по организациям). Выпиливать рабочий код ради чистоты — риск без выгоды.

**Когда пересматривать:** когда понадобится продавать систему другим объектам. Пути и их цена —
в разборе; путь В идти только с Row Level Security, дисциплиной такое не держат.

## ADR-057 — Единая структура боковой навигации (20.09.2026)

**Проблема:** владелец просит упорядочить меню: заголовки перемешаны со ссылками
и маленькими стрелками, на телефоне много прокрутки. Глобальные .is-collapsed
стили скрывают подписи mobile-меню после сворачивания desktop-панели.
**Варианты:** только уменьшить отступы; сгруппировать существующие маршруты по
задачам и унифицировать раскрытие. **Решение:** шесть групп — Работа с гостями,
Номерной фонд, Продажи, Финансы и отчёты, Настройки, Контроль. Заголовки — кнопки
раскрытия, внутри — ссылки без дополнительных уровней вложенности. Одна группа
открыта; смена маршрута открывает его группу. В compact нажатие группы раскрывает
панель. Состояние compact принадлежит конкретному Sidebar, а не всему приложению.

`sidebarSections` ссылается на общий реестр маршрутов: описания и дочерние ссылки,
которые используют страницы /rooms, /hotel-settings и поиск, сохраняются. Новая
группировка не меняет заголовки/данные страниц. Все прежние маршруты в меню ровно
по одному разу. Свой файл CSS после premium.css; устаревшие стили вложенных ссылок
удалены. Шапка окна и профиль закреплены, прокручивается только список разделов.
**Последствия:** маршруты, API, роли и база не меняются. Тесты проверяют состав
меню, переходы, active, Back, клавиатуру, compact→mobile, обе темы и ширины экранов.

Уточнение владельца к ADR-057: без линий между группами и слева от подразделов.
Для разделения достаточно отступов и веса заголовка.

## ADR-058 — Управление периодом и читаемая сетка шахматки (20.09.2026)

**Проблема:** над календарём много разрозненных элементов, расшифровка статусов
скрыта в инструкции, на телефоне календарь начинается слишком низко.
**Варианты:** менять только цвета; упорядочить управление и плотность существующей сетки.
**Решение:** по поручению владельца выбран второй вариант. Заголовок содержит главное
действие «Новая бронь». Период, стрелки, «Сегодня» и виды образуют отдельную планку.
Ручной период раскрывается кнопкой «Даты», сохраняет нативную GET-форму и сбрасывает
несохранённый ввод при смене периода через существующий ключ from/to. Инструкция
раскрывается отдельно. Легенда статусов постоянно доступна под сеткой.

Поиск, категория, тип и статус сгруппированы над календарём. Шапка каждого дня
показывает свободные и занятые места; на узких экранах подписи компактны, полная
расшифровка сохранена в aria-label/title. Новые стили ограничены шахматкой и используют
действующие токены. Неделя остаётся видом по умолчанию; календарные границы, месяц,
14 дней, произвольные даты, фильтры, меню, drag и переходы к броням сохраняются.
**Последствия:** API, данные, схема и правила размещения не меняются. Проверки действий
выполняются на синтетическом API; они не являются повторной проверкой Supabase.

## ADR-059 — Читаемый список броней и мобильный выбор статуса (20.09.2026)

**Проблема:** форма и статусы разрознены, мелкая таблица плохо читается, на
промежуточной ширине семь колонок требуют горизонтальной прокрутки.
**Варианты:** только увеличить шрифт; сгруппировать управление и адаптировать
таблицу. **Решение:** по поручению владельца выбран второй вариант. На desktop
статусы — ссылки с aria-current, на телефоне — select в существующей GET-форме.
Даты, статус, поиск и пагинация сохраняют прежние параметры URL и API.

Те же семь полей таблицы складываются в карточки на ширине до 1200 px: две

**Последствия:** нет изменений схемы, финансовой логики и API. Новых клиентских
состояний и зависимостей нет. Проверяются формы, переходы, ошибки/пустота,
мобильные цели управления, обе темы и отсутствие боковой прокрутки.
## ADR-060 — Регистрация с подтверждением почты (20.09.2026)

**Проблема:** регистрация открыта (ADR-055), но заводила рабочую сессию сразу по факту заполнения
формы. Значит: зарегистрироваться можно на чужой адрес; опечатка в своём оставляет учётную запись,
у которой нельзя восстановить пароль — письмо уйдёт в никуда; а владелец объекта не может отличить
живого человека от случайного посетителя. Прямое поручение владельца 20.09.2026: «ввожу имя, почту
и пароль, нажимаю Создать, вылазит окошко подтвердите вашу почту… нажимаю ссылку — авторизация».

**Варианты.**
А. Оставить как было — вход сразу. Дёшево, но все три беды выше остаются.
Б. Подтверждение кодом из письма. Ещё одна форма и ещё один срок жизни; человек переписывает цифры
руками. Отличается от ссылки только в худшую сторону.
В. Подтверждение по одноразовой ссылке из письма, как уже сделано для сброса пароля.

**Решение: В.** Регистрация заводит организацию, человека и членство, но сессию не открывает:
`users.email_verified_at` пуст, вход отвечает 403 «Почта не подтверждена». Письмо со ссылкой
(72 часа, одноразовая, в базе только хеш) уводит на `/login/verify`; там кнопка — не автоматическое
подтверждение по открытию страницы: почтовые службы ходят по ссылкам сами, проверяя их. После
нажатия сессия открывается сразу, пароль второй раз не спрашивается.

Повторный переход по уже использованной ссылке уже подтверждённого человека впускает, а не отказывает:
письмо открывают дважды, и «ссылка использована» на этом месте выглядит поломкой.

«Забыли пароль» отдельной правки не потребовал: он был сделан раньше (ADR-049) и работает той же
дорогой — письмо, одноразовая ссылка на сутки, новый пароль, все сессии отозваны.

**Миграция 20260920000015** проставляет `email_verified_at = now()` всем заведённым ранее: иначе
сотрудники объекта, заведённые до этой правки, потеряли бы вход. Применяет владелец руками (AGENTS.md §15).

**Последствия.** Регистрация теперь зависит от `MAIL_API_KEY`: без него письма нет, и стойка честно
говорит «обратитесь к владельцу» вместо «проверьте почту». Приглашения сотрудников (ADR-049) идут
прежней дорогой и подтверждения не требуют: сама ссылка-приглашение уже доказывает, что адрес живой.

**Чего это НЕ решает.** Подтверждённая почта — не разделение данных. Пока запросы не фильтруются по
организации (ADR-056), любой подтвердившийся видит данные объекта. До этого момента на боевом сервере
регистрация должна стоять закрытой: `REGISTRATION_OPEN=0`.

## ADR-061 — Объект принадлежит организации (20.09.2026)

**Проблема:** ни один запрос не фильтровался по организации. Вошедший видел данные единственного
объекта, кем бы он ни был: сверка 20.09.2026 показала 88 упоминаний `organizationId` в коде API и
все — в учётных записях, ни одного в бронях, шахматке, тарифах и финансах. Вместе с открытой
регистрацией (ADR-055) это значит, что любой зарегистрировавшийся попадал в данные Luxx Aparts.

**Варианты.**
А. Закрыть регистрацию и жить как есть. Владелец 20.09.2026 прямо потребовал обратного.
Б. Row Level Security в Postgres: замок в базе, обойти нельзя даже своим запросом. Правильная цель,
но это отдельная работа — политики на три десятка таблиц и проверка каждой роли подключения.
В. Замок в единственном месте, где имя объекта превращается в идентификатор.

**Решение: В, как шаг к Б.** У `properties` появилась колонка `organization_id`. Резолвер объекта
(`apps/api/src/database/property-ref.ts`) после поиска сверяет организацию объекта с организацией
вошедшего и отвечает 403 «Объект не настроен для вашей организации», если они разные. Это работает
на всё API сразу: шахматка, брони, тарифы, финансы, сверка, каналы — все начинают запрос отсюда.
Три места, читавшие объект своим запросом (брони, каналы, состояние связи), зовут ту же проверку.

Организация вошедшего берётся из контекста запроса (`AsyncLocalStorage`), куда её кладёт тот же
перехватчик, что уже подставлял автора в журнал. Ни один репозиторий ради этого не переписан.

**Служебные ходоки проходят.** За скриптом владельца, сторожем и импортом нет человека — они и есть
владелец. Различаем не по пустой организации (у вошедшего без членства она тоже пуста), а по
наличию человека в контексте.

**Объект без организации не виден никому из вошедших.** Так безопаснее: забытая привязка — это
отказ, а не молчаливый общий доступ.

**Миграция 20260920000016** привязывает существующие объекты к самой старой организации. В её
шапке стоит «ADR-059» — номер, под которым это решение было записано сначала; переименовать нельзя,
миграция уже применена, а Prisma сверяет применённые файлы по контрольной сумме. На боевой
базе она одна — та, под которой работает владелец. Применяет владелец руками (AGENTS.md §15).

**Чего это НЕ делает.** Это замок в приложении, а не в базе: свой запрос мимо резолвера его обойдёт.
Настоящее разделение — Row Level Security (вариант Б), и ADR-056 в этой части в силе: пока RLS нет,
продавать установку второму объекту нельзя. Зарегистрировавшийся человек получает не чужую
гостиницу, а пустые экраны с текстом «объект не настроен для вашей организации» — это правда: у его
организации объекта нет.

## ADR-063 — Мелкие правки по сверке 20.09.2026

Четыре замечания из полной сверки кода. По отдельности каждое невелико, но все — про то, что
система рассказывает наружу и что теряет при чужом сбое.

**Служебный ключ сравнивался посимвольно** (`presented === serviceKey`). Обычное сравнение строк
выходит на первом несовпавшем знаке, и по времени ответа ключ подбирается знак за знаком. Теперь
`timingSafeEqual` из `node:crypto`; разную длину гасим заранее, иначе `timingSafeEqual` бросит —
а это само по себе подсказка.

**Письма слались без `try/catch`.** Сброс пароля: новая ссылка гасит прежние, потом уходит письмо.
Если почтовая служба отказала, человек остаётся без обеих ссылок, а повтор упирается в «не чаще
одного письма в пять минут». Теперь при отказе свежая ссылка гасится сразу, отправка не
запоминается, и следующая попытка выдаёт новую. Приглашение при отказе возвращает ссылку владельцу
с пометкой «не отправлено» — ровно как при ненастроенной отправке.

**Текст ошибки Channex уходил наружу как есть.** Он собирается из их ответа и несёт до 300 знаков
JSON: внутренние идентификаторы объекта, тарифов, брони. Наружу теперь идёт путь без строки запроса,
код HTTP и код ошибки — по ним отказ узнаётся и ищется; полный текст пишется в журнал сервера.

**Номерной фонд на экране «Номера» звался без защиты.** Отказ уносил экран целиком. Теперь отказ
показывается подписью с текстом API — он говорит по-человечески, в том числе «объект не настроен
для вашей организации» (ADR-059).

**Отдельно: таблица `login_codes` снята** (миграция 20260920000017). Вход по коду снят 20.09.2026
(ADR-053), новых строк не появляется, а таблица хранит почту и IP запросившего. Персональные
данные, которые больше ни для чего не нужны, храниться не должны. Единственная разрушающая

## ADR-062 — Независимая загрузка блоков и один фоновый опрос (20.09.2026)

**Проблема:** главная ждёт настройки перед запуском данных; стойка последовательно
читает независимые данные дня и шахматку. Мобильное меню заводит второй опрос
свежести, а одновременные промахи минутного кэша настроек повторяют SQL.
**Варианты:** общий кэш данных всех экранов, увеличение пула БД или устранение
конкретных лишних ожиданий/запросов. **Решение:** третий вариант по запросу владельца.

Настройки имени/часов главной передаются отдельными серверными Suspense-блоками;
показатели и стойка начинают запросы независимо. Данные дня и шахматка запрашиваются
вместе. Существующая React.cache для настроек и дня остаётся в рамках запроса.
Верхняя оболочка содержит один provider свежести на активное приложение: обе версии
меню читают одно состояние. Следующий опрос запускается через минуту после завершения
предыдущего, незавершённое чтение отменяется при размонтировании. При ошибке остаются
предупреждение и возможность следующего опроса.

HotelService разделяет один незавершённый Promise чтения настроек в рамках существующего
экземпляра сервиса. TTL 60 секунд и однопредметная область старого кэша не расширяются;
ошибка сбрасывает Promise. Это не кэш броней, денег, доступности или прав пользователей.
**Последствия:** нет изменений модели, API, интеграций и финансовых правил. Ускорение
управления ожиданием проверяется с задержанным synthetic API; рабочие read-only замеры
и ограничения локальной машины фиксируются отдельно в отчёте.

## ADR-067 — Дежурный агент на сервере и ключ только на чтение сторожа (21.09.2026)

**Проблема:** второй слой сторожа — агент Claude — живёт на маке владельца и работает, пока открыт
Claude и мак не спит. Ночью, когда он нужнее всего, его может не быть вовсе (срез 12, §12.3). Перенести
его на сервер мешало другое: чтобы разбирать неисправности, агенту нужен доступ к API, а единственный
служебный ключ `SERVICE_API_KEY` открывает весь API — переселения, платежи, учётки. Класть такой ключ в
контейнер с ИИ нельзя.

**Варианты:** (1) отдать агенту служебный ключ и понадеяться на инструкцию; (2) не давать API вовсе и
читать только числа из сигнала сторожа — но по числам класс Б не разберёшь; (3) завести отдельный ключ,
который умеет ровно одно.

**Решение:** третий. `GUARD_READ_KEY` пускает только `GET /guard/status` и `GET /guard/incidents`;
всё остальное, включая «принято», «решено» и `/guard/tick`, отвечает отказом — закрывать неисправность
класса Б по-прежнему обязан человек. Проверка стоит в том же замке, что и служебный ключ, сравнение
за постоянное время, тесты красный → зелёный. Сам ключ агенту не достаётся: список снимает запускающий
скрипт и кладёт файлом. Агенту отобрана команда `git push` — пушит скрипт и только ветки `guard/*`.

**Вход агента:** отдельный платный ключ Anthropic не обязателен. `claude setup-token` выдаёт токен
подписки владельца на год (`CLAUDE_CODE_OAUTH_TOKEN`), и агент работает по ней. Плата за это — общие
лимиты: ночной разбор и дневная работа владельца делят один счёт, поэтому в скрипте стоит тихий час, а
токену нужен календарь на продление. Ключ остаётся вторым вариантом, когда лимиты делить нельзя.

**Причина:** право должно быть отобрано механизмом, а не обещанием агента. **Последствия:** появляется
новая переменная окружения и отдельный проект Docker `pms-lux-guard`; миграций нет. Честное ограничение:
ключ развёртывания GitHub не ограничивается по веткам — третий замок держит защита ветки `main`, и без
неё его нет (`scripts/ops/guard/README.md`).

## ADR-068 — Цикл уборки: выезд открывает его, заселение в непроверенную ячейку предупреждает (22.09.2026)

**Проблема:** статус уборки ячейки (DATA_MODEL §4: `DIRTY | CLEAN | INSPECTED`) вёлся без порядка — любой
переход, значок только у грязной, «убрано» неотличимо от «проверено». Владелец по снимку живой шахматки
попросил чёткую логику: «требует уборки → убрано → проверено → после проверено номер становится доступным».
Открытыми оставались два правила смены: кто ставит «требует уборки» после выезда (Q-155) и что делать при
заселении в непроверенную ячейку (Q-156).
**Варианты:** (1) цикл только в интерфейсе, API по-прежнему пускает всё; (2) цикл в домене, API отказывает
перепрыгнуть проверку; для выезда — руками / автоматически / автоматически с исключением; для заселения —
молчать / предупреждать / запрещать.
**Решение:** цикл живёт в `@pms/domain` (`housekeeping/flow.ts`) и один на стойку, API и фикстуру: вперёд
только на шаг, назад — только в «требует уборки», перепрыгнуть проверку нельзя (API — 409 словами); «проверено»
— конец цикла, ячейка названа доступной, значка в строке шахматки у неё нет. **Выезд сам переводит ячейку в
«требует уборки»** (Q-155, вариант А), запись журнала называет причину. **Заселение в непроверенную ячейку
предупреждает, но не запрещает** (Q-156, вариант А): окно со статусом словами и кнопкой «Заселить всё равно»;
API заселение не проверяет. Умолчание схемы `DIRTY` для новой ячейки сохранено: новая ячейка проходит цикл.
**Причина:** DATA_MODEL §4 — в Exely при включённом «заселять только в убранные» статусы не велись вообще (85
«Грязно» из 88), запрет «в лоб» парализует смену; предупреждение сохраняет правило, не останавливая работу.
Автоматическое «требует уборки» после выезда — единственный способ, при котором список уборки живёт сам, а не
только когда смена о нём помнит. **Последствия:** схема не менялась; availability для каналов и заселение по
API от уборки не зависят; `HousekeepingEvent` пишется и при автоматическом переходе; живые сквозные
(`tests/e2e/check-in-out.spec.ts`, `full-day.spec.ts`) подтверждают предупреждение при заселении, потому
что ячейки живого сида не проверены.

## ADR-064 — Переходный период: импорт будущих броней из Exely и досинхронизация до последнего канала (23.09.2026; ОТМЕНЁН владельцем 23.09.2026)

«Убрать всё». Решение стояло на записи ADR-052 от 19.09 «хостел продолжает работать в Exely», а к 23.09 это уже не так:
брони каналов приходят в экстранеты каналов, стойка заводит их в WETOP руками, остатки правят в экстранетах. Снято тем
же днём (есть в истории git, `0c5b7225`…`5fbfb56a`): досинхронизация `cli-sync-day.ts` и `exely/auto-sync.ts`, метка

`plans/transition-exely-sync-2026-09-23.md` и лист смены `plans/desk-sheet-transition-2026-09-23.md`. **Остались** правила
разового импорта Q-162, Q-164, Q-165 (`exely/import-screen.ts`, `import-reservations.ts`, `manual-seat.ts`) и
`importPiiSalt()` — они нужны при любом повторном переносе дампа; Q-163 не сделан, ждёт Q-148. ADR-052 снова действует
полностью. Q-167 открыт снова с новыми исходными. Ниже — текст как был принят, для истории.

**Проблема (Q-167).** Каналы переходят с Exely на Channex по одному, это недели, а койки общие. После ADR-052 в PMS нет
ни одной брони и нет досинхронизации, поэтому процедура на канал в `CUTOVER.md` не выполнима: PMS не знает будущих
броней, а каждая новая бронь должна уменьшать остаток в обеих системах — брони Exely-каналов и прямые в PMS (иначе PMS

**Варианты.** А — разовый импорт будущих броней и досинхронизация Exely → PMS до последнего канала. Б — без импорта,
всё руками в обе стороны (в начале перехода около 40 броней в день в PMS). В — сжать переход: пилот Hostelworld на
несколько дней, остальные каналы за 1–2 дня; отступление от условия ментора «по одному».

**Решение владельца 23.09.2026: А** (выбор в чате после разбора вариантов).

- Разовый импорт будущих броней и досинхронизация включаются **только на базе в Казахстане** (A1), с настоящими
  данными гостей; на Supabase — нет.
- Досинхронизация — только чтение из Exely, каждые 5 минут, как было по ADR-032 после 13.09; код слоя А, снятый 20.09 (`a1e9719c`),

- Стойка до переключения последнего канала работает в Exely — это следствие варианта: Exely остаётся главной для

  каналов смена заводит в Exely руками;
  чтобы они не приехали в PMS второй раз, импорт узнаёт их по метке `WETOP <номер брони PMS>` в
  комментарии брони в Exely (форма утверждена владельцем 23.09.2026) и пропускает с записью в отчёт прогона.
- После переключения последнего канала (Booking.com) досинхронизация выключается и снимается; ADR-052 действует

**Правила импорта — решения владельца 23.09.2026** (были Q-162…Q-165, открыты как актуальные «только при повторном
импорте дампа»; при досинхронизации импорт повторяется каждые 5 минут):

**Реализация 23.09.2026 (шаги 2–6 плана, поручение владельца «начинай»).** Досинхронизация возвращена в код и

## ADR-069 — Стеклянное направление в стойке: свет, стекло у панелей, градиент у главной кнопки (23.09.2026)

**Проблема:** 23.09 главная wetop.ai переведена в стеклянное направление (ADR-064). Владелец на вопрос,
что применять дальше, ответил: «давай все страницы делай так» — то есть перенести направление на весь
продукт. Прямо этому мешали два собственных правила стойки: §5 («тень только у слоя над страницей,
блок отделяется рамкой») и §15 («градиент, свечение, шар — это ИИ-слоп, а не стойка»), а также
сторож `tests/unit/design-slop.test.ts`.

**Варианты:** (1) переписать экраны по одному под новое оформление — недели работы и 322 UI-теста
под переделку; (2) снять §5 и §15 целиком и разрешить стекло везде; (3) добавить оформление слоем
поверх собранных блоков и снять запреты точечно, закрытым списком.

**Решение:** третий. `apps/web/src/app/glass.css` подключается последним в `app/layout.tsx` и кладёт
на существующие блоки свет за страницей, размытие, кромку и мягкую тень; заливка блоков переведена
с `--surface` на новый токен `--glass-panel` в 37 правилах 14 файлов. Значения — в
`design/tokens.json` (`--glass-panel`, `--glass-edge`, `--glass-blur`, `--surface-solid`,
`--glow-1…3`, `--star`, `--accent-1/2`, `--shadow-glass`, слои `--layer-glass-*`), CSS генерируется
как и раньше. §5 и §15 не отменены, а получили **именованное исключение**: тень и радиус `--radius-lg`
— только у блоков из закрытого списка DESIGN.md §20.3; градиент — только у главной кнопки и знака
(§20.4). Список записан дважды — в §20.3 и в `glass.css`, — и сторож `tests/unit/desk-glass.test.ts`
не даёт им разойтись.

**Что намеренно осталось непрозрачным:** сетка шахматки с шапкой и колонкой номеров, тело таблицы и
её липкая шапка, поля ввода, меню действий, окно подтверждения и уведомление. Причина — §1.1: статус
брони читается за секунду и с расстояния; размытие под 88 строками мешает читать и стоит кадров.
Режим повышенного контраста и печать свет за стеклом выключают целиком.

**Причина:** оформление — решение владельца, и спорить с ним не о чем; но запрет §15 писался против
бессмысленного украшательства, и снимать его «везде» значит через месяц получить градиент на каждой
кнопке. Закрытый список со сторожем сохраняет и новое направление, и прежнюю дисциплину.

**Последствия:** смысловые цвета, размеры, отступы, плотность и тексты не менялись — контраст §10 и
цели нажатия §11 прежние. Эталонные снимки страницы компонентов (`design/reference/kit`) пересняты
заново: 36 снимков `-linux`; снимки `-darwin` снимаются только на Mac владельца и до этого остаются
прежними. Свет в светлой теме намеренно тихий: на фоне страницы лежит текст, и яркое пятно уронило бы
контраст.

## ADR-070 — Главная wetop.ai в стеклянном направлении (23.09.2026)

**Проблема:** владелец принёс два снимка чужой посадочной страницы (светлая и тёмная тема одного
направления: матовое стекло на подсвеченном фоне, металлическая надпись первого экрана, полоса чисел,
витрина карточек, три колонки, плита призыва с контактами) и поручил перенести это оформление на WETOP,
кроме портрета человека на первом экране. Главная до этого была обычной светлой страницей на плотных
карточках; правила стойки (`DESIGN.md`) на неё не распространяются — §1 прямо выводит `apps/site`
из-под них, — то есть решения о её облике нигде не записано.

**Варианты:** (1) скопировать снимок целиком, включая разделы, которых у нас нет (годы опыта, число
клиентов, награды, отзыв с именем, QR); (2) перенести только оформление, а содержание оставить своё;
(3) отказаться и оставить прежний вид.

**Решение:** второй. Переносится язык оформления — стекло (`--glass-*`, один примитив `.glass`),
подсвеченный фон с пятнами и звёздной пылью, металлическая надпись первого экрана, круглый знак с
надписью по кругу, полоса чисел, витрина из трёх карточек с номерами, три стеклянные колонки и плита
призыва с контактами. Содержание остаётся прежним, и разделы, которым нет опоры в продукте, не
переносятся совсем:

- вместо «5+ лет опыта / 40+ проектов / 25+ клиентов / 18 наград» — числа, которые названы на этой же
  странице: 6 каналов, 9 способов оплаты, 3 среза шахматки, 0 расхождений при сверке;
- вместо отзыва с именем — правило проекта о нулевом расхождении, подписанное проектом, а не человеком;
- вместо процентов владения навыком — состояние «в системе» у каждого модуля: доли готовности никто не
  считал, и придумывать их нельзя;
- вместо логотипов чужих сервисов — буквенные плитки каналов;
- вместо QR-кода — ссылка на стойку словами: её видно и её можно проверить глазами;
- вместо портрета человека на первом экране — макет шахматки (прямое условие поручения).

Тема по-прежнему одна на две: светлая и тёмная берутся из настройки системы, переключателя нет.
Цвета текста и акцента остались прежними (`--text`, `--text-2`, `--muted`, `--primary`): их контраст
проверен, и сайт со стойкой остаются одним целым. Стеклянные токены — только оформление, текст ими
не красится. Где браузер не умеет `backdrop-filter` или человек просит больше контраста
(`prefers-contrast: more`), панель становится непрозрачной.

**Причина:** оформление — вкус владельца, и спорить с ним не о чем; числа и обещания — не оформление.
Страница, обещающая награды и клиентов, которых нет, ломает единственное правило текстов сайта
(«только то, что есть в продукте на самом деле») и подводит первого же, кто придёт по ней.

**Последствия:** правила стойки не тронуты — направление живёт только в `apps/site`
(`tokens.css`, `globals.css`); `DESIGN.md` §1 по-прежнему выводит сайт из-под правил стойки, и сторож
ИИ-слопа (`tests/unit/design-slop.test.ts`) читает только `apps/web/src`. Доказательства: набор главной
7/7 (доступность по axe на обеих страницах, отсутствие горизонтальной прокрутки на 390 px), снимки
обеих тем — `reports/site-glass-2026-09-23/`.

**Номер:** решение было записано как ADR-064 и в тот же день перенумеровано в 070 при слиянии: номер 064
одновременно взяла параллельная сессия под переходный период (Q-167), и её решение ушло в `main` первым.
Переименован младший и менее связанный из двух — десять ссылок в документах этой же ветки; в сообщениях
коммитов `dac32aa`, `9561437`, `96cd197` он ещё назван ADR-064.

## ADR-071 — Переход каналов без Exely: номер брони канала в ручной брони (Q-167, 23.09.2026)

**Проблема (Q-167, исходные владельца 23.09).** В Exely объект больше не работает: брони каналов приходят в экстранеты,
стойка вводит их в WETOP руками, места и цены правят в экстранетах. При подключении Booking.com, Expedia и Trip.com
Channex присылает все их будущие брони (ADR-024). Приём ревизий ищет бронь по `unique_id`, по номеру брони на стороне
канала (`ota_reservation_code` против `externalId`) и по номеру PMS, а сопоставление ADR-024 — только среди броней OTA с
именем канала. У ручной брони нет ни канала, ни номера: каждая копия стала бы дублем и заняла вторую койку.

**Варианты.** А — поля «Канал» и «Номер брони в канале» в ручной брони. Б — стойка отменяет свои копии перед
подключением, Channex присылает их заново (посадки, оплаты, заметки теряются; для Agoda, Hostelworld, Ostrovok не
работает). В — сжать переход (отступление от «по одному», ADR-012).

**Решение владельца 23.09.2026: А** (выбор в чате после разбора в `QUESTIONS.md`, Q-167).

- «Новая бронь» и карточка брони: для источника «OTA (вручную)» — «Канал» (каналы объекта) и «Номер брони в канале»
  (как в экстранете). Хранятся в `channel` и `externalId` — поля в базе есть, схема не меняется.
- Номер записывается без пробелов; тот же номер у другой неотменённой брони — отказ с номером этой брони.
- При подключении канала ревизия находит бронь по номеру брони в канале (шаг 2 приёма) и связывается с ней; по той же
  дороге потом идут изменения и отмены Agoda, Hostelworld и Ostrovok.
- Каналы по одному, порядок прежний (ADR-012). Перед каналом — сверка его будущих броней в WETOP со списком в
  экстранете и цен экстранета с ценами WETOP: полная выгрузка при подключении отдаёт каналу цены WETOP.

**Последствия.** Процедура на канал в `CUTOVER.md` переписывается под экстранет вместо «живого Exely»; отчёт
`cutover:channel` — под список для сверки. Предусловия прежние: A1 (данные гостей — ADR-072) и блок B (приём ревизий меняет
найденную бронь по правилам Q-158…Q-161).

**Реализация 23.09.2026.** API: `channel` и `externalId` у `POST /reservations` и `PATCH /reservations/:number` — только
для OTA и для OTA обязательны при создании; канал — из восьми каналов объекта, хранится каноническим именем
(`otaChannelLabel`); номер — без пробелов, 3–64 символа; тот же номер у другой брони или бронь, которую Channex уже
прислал (`channexUniqueIdOf`: `BDC-<номер>`), — 409 с номером той брони. Приём ревизий: `booking_new`, найденная по
`ota_reservation_code`, **связывается** (`linkExisting`, общий с ADR-024) — проживания, статус, ячейки и заметка стойки не
трогаются; `modified` по той же дороге — как раньше. Поиск броней находит и по номеру брони в канале. Стойка: поля в
«Новой брони» и в правке карточки при источнике OTA; у брони из Channex номер показывается, но не правится. Процедура
на канал в `CUTOVER.md` переписана под экстранет; `cutover:channel` ещё сравнивает с Exely — переделать.
Red → green: `reservations.controller.test.ts`, `inbound.controller.test.ts`, `reservation-directory.test.ts`,
`channel-names.test.ts`; `tests/ui/channel-booking-number.spec.ts` — в CI.

## ADR-072 — Пока база не в Казахстане, WETOP обезличивает данные гостей, введённые руками (23.09.2026)

**Проблема.** ADR-018: настоящие ФИО, телефоны и почта гостей — только в базе в Казахстане. Рабочая база — Supabase в
Сингапуре (`PII_STORAGE` не `real`). Приём каналов и бронь с сайта гостя обезличивают (`guestForStorage`), а ручной ввод
стойки — новая бронь, правка гостя, документы — сохраняет всё как введено. Владелец 23.09: стойка работает в WETOP.
Проверка базы 23.09 (только счётом, без чтения данных): ручных броней 4, во всех именах слово «тест», телефонов, почты и
документов нет — настоящих гостей в базе нет, разовое обезличивание не понадобилось.

**Варианты.** WETOP обезличивает сам; стойка вводит без ФИО по договорённости; оставить до переезда (против ADR-018).

**Решение владельца 23.09.2026: WETOP обезличивает сам**, пока `PII_STORAGE` не `real`:

- новая бронь со стойки — гость записывается псевдонимом, как гость канала (`guestForStorage`);
- правка гостя — ФИО, телефон, почта, дата рождения и заметки не принимаются, с объяснением; гражданство и пол — как
  раньше (их хранит и обезличенный импорт);
- документ гостя не принимается;
- стойка видит это в форме и карточке заранее, а не после сохранения.

С `PII_STORAGE=real` (база в РК, A1) всё сохраняется как введено.

**Последствия.** Гостя на стойке находят по номеру брони канала (ADR-071), датам и ячейке; личность на заселении
сверяют по документу, в WETOP документ до A1 не вносится. Главное лекарство — A1.

**Реализация 23.09.2026.** `deskGuestForStorage` и `piiStorageMode` (`packages/shared/src/pii-residency.ts`):
вне режима `real` — «Гость Стойка-<6 hex>» со случайной меткой, соль не нужна. `ReservationsService.create` пишет гостя
через неё (бронь с сайта передаёт уже обезличенного — `guestPrepared`); имя обязательно только в режиме `real`.
`GuestsService.update` отвечает 422 на новое значение личного поля (прежнее и пустое — можно, форма присылает профиль
целиком), `addDocument` — 422. `GET /system/pii-storage` → `{ storage: 'real' | 'pseudonymized' }`; «Новая бронь» и
карточка гостя по нему прячут поля и объясняют почему; не прочиталось — считается «не хранятся». Изолированный стенд
e2e и живой аудит пишут введённое как есть (`PII_STORAGE: 'real'`): гости там только вымышленные (ADR-010).
Red → green: `pii-residency.test.ts`, `guests.controller.test.ts`, `reservations.controller.test.ts`;
`tests/ui/pii-storage.spec.ts` — в CI (в VM Cowork нет Chromium).

## ADR-074 — Защита данных и production по проверке SECURITY.md: Q-169, Q-170, Q-171 (24.09.2026)

**Дата:** 2026-09-24
**Проблема:** проверка проекта по `SECURITY.md` (`reports/security-check-2026-09-24.md`) нашла, что три правила держатся
на дисциплине, а не на коде:
- в заметки брони (стойка, канал, комментарий с сайта) и в свободный текст начислений и блокировок пишутся телефоны и
  почта гостей, пока база не в РК;
- автотесты на Mac берут из `.env` рабочую базу;
- Channex production вызывается любым процессом, у которого в `.env` окажутся адрес и ключ production.

**Решение владельца:** «давай решай проблемы делай что надо» на рекомендации агента из `QUESTIONS.md`:

- **Q-170, вариант А.** `integration` и `e2e` (`ensureTestSchema`) отказывают, если `DATABASE_URL` не на
  `127.0.0.1` или `localhost`. Осознанно — `PMS_TEST_REMOTE_DB=1`. На Mac тесты идут на `npm run db:local`.
- **Q-171, вариант А.** Клиент Channex отказывает до сети на любом хосте channex.io, кроме staging, пока не задано
  `CHANNEX_PRODUCTION=1`. Переменную ставит владелец шагом переключения (`CUTOVER.md`).

**Сделано тем же днём в рамках уже принятых решений, без нового выбора:**
- ревизия Channex хранится без данных заказчика (ADR-018);
- тексты ошибок и `last_error` — без почты и телефонов (SECURITY §7);
- журнал закрывает пробелы §6;
- замок организаций (ADR-061) покрывает гостей, журнал и поиск счетов по id (Q-152).

План и состояние по пунктам — `plans/security-fixes-2026-09-24.md`.

**Последствия:**
- ошибка в `.env` больше не превращается в отправку ARI в production;
- прогон тестов на Mac без `db:local` отказывает словами, а не пишет в рабочую базу;
- заметка с телефоном хранится с маской. Если телефон нужен смене — он в экстранете канала или у гостя; после переезда
  в РК маска снимается сама.

## ADR-075 — Журнал не ведёт на удалённую бронь (24.09.2026)

**Проблема.** Audit trail живёт дольше операционных тестовых данных. После гарантированной очистки синтетической
брони её номер остаётся в журнале, а ссылка на карточку открывает 404. Полный пользовательский обход обнаружил две
такие ссылки после live-аудита.

**Варианты.** Удалять audit trail вместе с бронью; проверять карточку отдельным запросом из каждой строки; одним
SQL-запросом вернуть признак доступности цели и показывать ссылку только для существующей брони.

**Решение.** `GET /audit` возвращает `targetAvailable` для строк `Reservation`. Признак считается `LEFT JOIN` в том
же запросе, которым загружается журнал. Номер удалённой брони и само действие остаются в истории, но выводятся текстом
с пометкой «удалена», без ссылки.

**Последствия.** Audit trail не теряется, журнал не содержит заведомо битых переходов, дополнительных запросов к
Supabase на строку нет. Контракт `/audit` расширен одним read-only полем; схема БД не меняется.

## ADR-076 — Продление за правый край шахматки (24.09.2026)

Проблема: имя гостя конкурирует с каналом и долгом в короткой плашке; для продления нужно открывать карточку.
Решение: имя занимает основную строку (две строки в однодневной плашке), подробности — вторую;
легенда раскрывается по запросу. Правый край последней ночи выбирает дополнительные ночи на той же строке.
Выбранный день включается в проживание, выезд — следующий день. Перетягивание в другую строку не продлевает.
Сокращение срока не добавляется. Предпросмотр и сохранение используют существующие previewAction / extendStayAction,
без изменения API, модели, тарификации и защиты от пересечения. При недоступной цене сохранение не предлагается.
Клавиатура: стрелки выбирают 1–30 ночей, Enter подтверждает выбор, Escape сбрасывает его; затем общее окно с ценой.
В месяце и на узком телефоне ручка скрыта, чтобы не перекрывать карточку; продление остаётся в карточке.
Альтернатива — собственный расчёт/запись с фронта — отклонена: расчёт и конфликт должны оставаться на сервере.
