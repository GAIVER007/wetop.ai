# DECISIONS (ADR)

Формат записи: дата, проблема, варианты, решение, причина, последствия.
Незаписанное решение считается непринятым (AGENTS.md §3).

---

## ADR-001 — Single-property MVP

**Дата:** 2026-09-07
**Проблема:** строить ли сразу multi-tenant / multi-property.
**Варианты:** (a) сразу SaaS multi-tenant; (b) один объект, но сущность `Property` в схеме; (c) жёстко один отель без Property.
**Решение:** (b) — single-property MVP, сущность `Property` присутствует в модели.
**Причина:** сначала доказать работу на реальном объекте. Но база не должна содержать
предположение «в мире существует только один отель».
**Последствия:** UI работает с одним property; multi-property можно добавить позже
без переписывания схемы. Все запросы фильтруются по `property_id` с самого начала.

## ADR-002 — Modular monolith, не microservices

**Дата:** 2026-09-07
**Проблема:** архитектурный стиль backend.
**Варианты:** microservices; modular monolith; monolith без модулей.
**Решение:** modular monolith.
**Причина:** команда маленькая, MVP 8 недель, distributed complexity сейчас не нужна.
Для 88 номеров Kubernetes/Kafka — лишняя сложность.
**Последствия:** границы модулей поддерживаются дисциплиной пакетов
(`packages/domain`, `packages/integrations`), а не сетью.

## ADR-003 — PostgreSQL — source of truth

**Дата:** 2026-09-07
**Проблема:** какая система считается первичной по данным.
**Решение:** PostgreSQL PMS. Channex / Exely / eQonaq **не** являются основной БД PMS.
**Причина:** без единого source of truth сверка невозможна.
**Последствия:** любые внешние данные импортируются и хранятся локально;
внешние ID хранятся как ссылки, а не как замена собственных ключей.

---

## ADR-004 — Channels через adapter interface

**Дата:** 2026-09-07
**Проблема:** зависимость бизнес-логики от конкретного channel manager.
**Решение:** `ChannelProvider` — интерфейс. Первый adapter — Channex.
**Причина:** смена/добавление провайдера не должны затрагивать домен.
**Последствия:** бизнес-модель PMS не знает про Channex IDs; маппинг живёт
в `ChannelMapping`. Запрещён импорт Channex SDK вне `packages/integrations`.

---

## ADR-005 — Room и sellable inventory разделены

**Дата:** 2026-09-07
**Проблема:** dorm с койко-местами не укладывается в модель «номер = единица продажи».
**Решение:** `PhysicalRoom` (помещение) и `InventoryUnit` (ROOM | BED) — разные сущности.
Dorm содержит несколько bed inventory units.
**Причина:** самый дорогой возможный архитектурный промах — смешать их (риск №1).
**Последствия:** availability считается по `InventoryUnit`; private room — тоже
InventoryUnit (kind=ROOM), чтобы код был единообразным.

## ADR-006 — Reservation и Allocation разделены

**Дата:** 2026-09-07
**Проблема:** OTA продаёт категорию, физический номер назначается позже.
**Решение:** `Reservation` → `ReservationItem` (категория) → `Allocation` (юнит).
**Причина:** бронь категории должна существовать без назначенного физического номера.
**Последствия:** переселение = закрытие одной Allocation и открытие другой,
а не мутация брони. История переселений сохраняется.

## ADR-007 — Все внешние события идемпотентны

**Дата:** 2026-09-07
**Проблема:** повторный webhook может создать дубль OTA-брони.
**Решение:** `ExternalEvent` с UNIQUE (provider, external_event_id); обработка через
состояние + retry.
**Причина:** дубль или потеря брони — недопустимый отказ.
**Последствия:** любая интеграция сначала пишет событие, потом обрабатывает.
Обработчик обязан быть повторно-безопасным.

## ADR-008 — Финансы без float

**Дата:** 2026-09-07
**Решение:** деньги — integer minor units (тиын) либо decimal-safe представление.
**Причина:** JS floating point даёт расхождения в копейках, которые ломают сверку.
**Последствия:** все API отдают минорные единицы + код валюты; форматирование — только на UI.

## ADR-009 — Персональные данные в Казахстане

**Дата:** 2026-09-07
**Решение:** основная база персональных данных production размещается на территории
Казахстана. Передача данных зарубежным сервисам рассматривается отдельно.
**Причина:** законодательство РК о персональных данных.
**Последствия:** выбор хостинга БД ограничен; любой внешний сервис, получающий PII,
проходит отдельное решение. См. `SECURITY.md`.
**Открыто:** конкретный провайдер/регион ещё не выбран.

## ADR-010 — Реальные паспорта не попадают в dev/test

**Дата:** 2026-09-07
**Решение:** реальные документы гостей никогда не используются в development/test,
включая fixtures и prompts к AI-агентам.
**Причина:** утечка PII через тестовые данные и логи — реальный сценарий.
**Последствия:** нужен генератор synthetic-гостей; анонимизация при импорте
production-выгрузок в dev.

## ADR-011 — Стек MVP

**Дата:** 2026-09-07
**Решение:**

| Слой | Выбор |
|---|---|
| Frontend | Next.js + TypeScript + React |
| Backend | NestJS + TypeScript |
| DB | PostgreSQL (production — регион Казахстан) |
| ORM | Prisma |
| Jobs/queue | Redis + BullMQ |
| Files | S3-compatible object storage |
| Tests | unit + integration + Playwright E2E |
| Архитектура | Modular monolith |

**Причина:** один язык на всём стеке, быстрый найм, зрелые инструменты миграций.
**Не берём:** Kubernetes, microservices, Kafka.
**Последствия:** очереди BullMQ используются для Channex sync, retry, eQonaq,
fiscal, reconciliation. Документы гостей в S3 — только после решения ADR-009.

## ADR-012 — Порядок миграции OTA

**Дата:** 2026-09-07
**Решение:** каналы переключаются по одному, начиная с минимального по объёму;
Booking.com — последним. Следующий канал не подключается, пока предыдущий не прошёл
reconciliation с расхождением 0.
**Причина:** одновременное переключение всех каналов делает откат невозможным.
**Последствия:** cutover растягивается, но остаётся обратимым. См. `CUTOVER.md`.
