## 1. Классификация данных

| Класс | Примеры | Правило |
|---|---|---|
| **Особо чувствительные** | номер паспорта/удостоверения, скан документа, дата выдачи | шифрование at rest, доступ по роли, логируется каждый просмотр |
| **Персональные** | ФИО, дата рождения, гражданство, телефон, email, пол | доступ по роли, не попадает в логи |
| **Финансовые** | платежи, refund, фискальные чеки | audit trail на каждое изменение |
| **Операционные** | номера, даты, статусы | обычный доступ |

Реквизиты банковских карт в PMS **не хранятся** ни в каком виде. Проверено 24.09.2026: из ревизии Channex объект
`guarantee` и исходное сообщение площадки `raw_message` (в нём может быть карта) вырезаются до записи — в том числе
из копии брони внутри других событий и при `PII_STORAGE=real` (`sanitizeRevision`, `sanitizeWebhookPayload`).

**Документ гостя на 24.09.2026.**
- Номер шифруется: AES-256-GCM, `packages/shared/src/pii-crypto.ts`, ключ `PII_ENCRYPTION_KEY`.
- Дата выдачи, срок действия и страна выдачи лежат открытым текстом.
- С 24.09.2026 каждый просмотр карточки гостя с документом пишется в журнал: `guest.document.view`, какие документы,
  без номера. Добавление и удаление документа — с его id и типом. Доступа по роли нет (§5).
- Пока база не в РК, документы не принимаются вовсе (§2). До `PII_STORAGE=real` — шифрование дат выдачи и срока:
  предложено в `DATA_MODEL.md` v1.7 §3, ждёт утверждения (Q-172). Страна выдачи остаётся открытой, как гражданство.

## 2. Персональные данные и юрисдикция

ADR-009: основная база персональных данных production размещается на территории
Казахстана. Передача данных зарубежным сервисам рассматривается отдельным решением.

Открытые вопросы: Q-070а (провайдер и база в РК; Q-070 закрыт 11.09.2026), Q-071 (регистрация ИС), Q-072 (хранение
сканов), Q-073 (бэкапы).

**Что показал аудит архивный источник 07.09.2026:**

| Факт | Следствие |
|---|---|
| `personalDataShelfLife = 0` — срок хранения ПД **не настроен** | Политику хранения задать явно в новой системе |
| Гражданство у OTA-броней не заполняется | Данные для eQonaq берутся из паспорта вручную на check-in |
| ~1000 иностранных гостей в месяц, подача в eQonaq ручная | Объём обрабатываемых ПД высокий; журнал доступа обязателен |
| Учётка с наибольшим оборотом (18,2 млн ₸/мес) отсутствует в списке пользователей объекта | Вероятна работа под общим логином — Q-060 |
| Копии документов гостей: место хранения неизвестно | Q-072, вопрос 18 опросника |

**До ответа на Q-070 нельзя разворачивать production-БД.**

Состояние на 24.09.2026:
- Q-070 закрыт 11.09: база будет в РК, провайдер — Q-070а, открыт.
- До переезда рабочая база стойки — Supabase в Сингапуре (ADR-052, §12), и держит она только обезличенные данные
  гостей — правило ниже.

**Пока база не в Казахстане (`PII_STORAGE` не `real`), настоящие данные гостей в неё не попадают ни одним путём**
(ADR-018, ADR-072 от 23.09.2026): гостей каналов и сайта приём обезличивает (`guestForStorage`); гость, введённый
стойкой, записывается «Гость Стойка-…» без отчества и контактов (`deskGuestForStorage`); правка гостя не принимает
нового имени, контактов, даты рождения и заметок (стереть можно), документы не принимаются; формы стойки эти поля
не показывают — режим читается у API (`GET /system/pii-storage`). `PII_STORAGE=real` ставится только на базе в РК.

**Что нашла проверка 24.09.2026 и что с этим стало:**
1. **Ревизия Channex.**
   - Было: `external_events.payload` хранил её целиком, кроме `guarantee` — имя, фамилию, телефон, почту и адрес
     заказчика, имена гостей, заметку.
   - С 24.09.2026, пока база не в РК, ревизия хранится по разрешённому списку полей: номера, даты, суммы, занятость,
     канал, страна заказчика. События не о брони — только идентификаторы.
   - 15 тестовых ревизий staging в рабочей базе очищены тем же правилом; проверка — только подсчётом.
2. **Свободный текст.** Заметка стойки, заметка канала, комментарий гостя с сайта, назначение начисления, заметка
   платежа, причины возврата и блокировки — пока база не в РК, почта и телефоны в них заменяются на `<почта>` и
   `<телефон>` (Q-169, ADR-074). В журнал ложится текст уже с маской. Имена так не поймать — у поля подсказка «без
   имён и телефонов гостя».
3. **Почта сотрудника** копируется в журнал при приглашении и подтверждении почты и остаётся там после удаления
   учётной записи. Это сотрудник, не гость; пересмотреть при переезде в РК.

## 3. Секреты

Запрещено помещать в код, Git, логи, скриншоты, чат с AI:

- API keys (Channex, eQonaq, fiscal, S3)
- пароли, access tokens, refresh tokens
- паспортные данные
- платёжные credentials

Только environment variables / secret storage. Шаблон — `.env.example`,
в нём **только имена переменных без значений**.

`.env*` в `.gitignore`. Если секрет попал в Git — ротировать, а не удалять коммит.

**Запрет на чтение агентом (с 07.09.2026).** `.claude/settings.json` в корне проекта
запрещает инструменту чтения агента открывать `.env`, `.env.*`, `secrets/**` и табличные
выгрузки в `project-input/retired-source/`, а также прямой `cat` этих файлов. Проверено на
существующем файле: оба способа отказывают со ссылкой на настройки. Граница честная:
это защита от случайного попадания ключа в переписку, не от умысла — программа, которую
агент запускает, читает файл сама. Поэтому: значения в `.env` вписывает только владелец,
production-ключи на машине разработки не живут, ключ в чат не диктуется никогда.

**Граница правил (проверка 24.09.2026).**
- До проверки правила `Read` закрывали только корневые `.env` и `.env.*`, правила `Bash` — только буквальные
  `cat .env…` и `source .env…`, из выгрузок — `*.xlsx`, `*.csv`, `exports/**`, `api/**`.
- С 24.09.2026 (решение владельца «делай что надо», план П6) добавлены:
  - вложенные `**/.env`, `**/.env.*`, `**/secrets/**`;
  - `head`, `tail`, `less`, `more`, `grep`, `rg`, `sed`, `awk`, `xxd`, `base64`, `cat -n`, `. .env` на `.env`;
  - `docker compose … config` (печатает значения переменных);
  - выгрузки `.xls`, `.xlsm`, `.ods`, `.tsv`, `.json` в любой подпапке `project-input/retired-source/` и `backups/`.
- Цена: правило Bash сравнивает всю строку команды, поэтому `grep`, `rg`, `sed`, `awk` отказывают на любой команде,
  где встречается `.env`, — и на поиске `process.env`. Искать инструментом Grep: он подчиняется правилам `Read`.
- Полной защиты это не даёт — граница та же, что выше: программа, которую агент запускает, читает файл сама.
- `.env.*` закрывает и шаблон `.env.example`, поэтому «в нём только имена» агент проверить не может. Команда для
  владельца — в отчёте проверки.

`secrets/` добавлен в `.gitignore` 24.09.2026, до этого его закрывал только `.dockerignore`. Вся история git
(989 коммитов) проверена 24.09.2026: секретов нет.

## 5. Доступ и роли

Role-based access — требование SPEC (non-functional).

**С 27.09.2026 — три роли с правами** (решение владельца, ADR-107; `DATA_MODEL.md` §16.5). Роль — готовый набор прав:
владелец — всё; управляющий — всё, кроме владельческого (приглашать управляющих, менять роли, платные расширения);
администратор — работа с гостями, «Оплаты» и «Статистика» на просмотр, диалоги ИИ-продавца, неисправности. Возврат
оплаты, сторно (и снятие штрафа) и корректировку счёта на уменьшение делают владелец и управляющий (Q-024). Права
проверяет API на каждом маршруте: замок ролей `RoleGuard` сверяет право маршрута (`@Access`) с ролью вошедшего, а
маршрут без записанного права вошедшему закрыт — и не проходит тест `route-access.test.ts`. Стойка прячет чужие пункты
и кнопки, но защитой не считается. Журнал действий с автором остаётся. До 27.09 действовало решение 11.09 (ADR-023):
ролей нет, администраторы равноправны.

Q-061 («кто видит паспорт»): паспорт видят все три роли — администратор ведёт гостей и заселение (ADR-107).

Просмотр документа гостя — событие аудита. С 24.09.2026 выполняется: `guest.document.view` на каждую карточку гостя
с документами, с id документов и автором.

**Уровни доступа** (ADR-083, ADR-107, `DATA_MODEL.md` §16). Каждое отличие проверяет API, а не только меню:

| Кто | Что может | Как получает | Чего не может |
|---|---|---|---|
| владелец организации (`memberships.role = OWNER`) | всё на стойке; приглашает управляющих и администраторов, меняет роль между ними, отключает их; напоминание о продлении расширения | регистрация организации; у существующих — самый ранний участник (миграция `20260925000020`); команда `accounts -- role` | снять себя, если он последний владелец |
| управляющий (`MANAGER`, с 27.09) | всё на стойке, включая возвраты, тарифы, каналы, настройки, журнал и настройки ИИ-продавца; приглашает и отключает администраторов | приглашение владельца; смена роли владельцем | приглашать управляющих, менять роли, платные расширения (403 словами) |
| администратор (`STAFF`) | работа с гостями, оплаты и начисления в счёт, «Оплаты» и «Статистика» на просмотр, диалоги ИИ-продавца, неисправности | приглашение | возврат, сторно, корректировка на уменьшение, тарифы, каналы, настройки, журнал, сотрудники (403 словами) |
| главный администратор платформы (`platform_admins`) | «Платформа → Организации»: названия, сроки, число людей, почты владельцев и расширения всех организаций | только команда на сервере `accounts -- platform-admin`; из интерфейса не выдаётся | видеть брони, гостей, счета и переписку чужих гостиниц — их в ответах `/platform/*` нет по построению |

Служебный ключ и выключенный замок (`AUTH_REQUIRED=0`) раздел «Платформа» не открывают: нужен вошедший человек с
отметкой.

**«Платформа → Техподдержка» (ADR-083, ADR-084).** API ходит в панель помощника по внутренней сети с ключом
`ASSISTANT_SERVICE_KEY` (у помощника — `SELLER_SERVICE_KEY`); адрес и ключ живут только в окружении API и в ответы не
попадают. Ключ помощника открывает его диалоги, знания, сводку, а с ADR-084 — правила (системный промпт) и выбор модели;
правила и модель — только при явном `BOT_ROLE=support`, у продавца ключу они закрыты. Правка правил — строка
`audit_logs` с длиной, без текста. Ключ утёк — им можно переписать правила помощника: менять сразу (оба `.env`, затем
перезапуск `api` и помощника). Роль и отметка читаются на каждом запросе — снятие действует сразу, без выхода. Каждое изменение роли,
отметки и расширения — строка `audit_logs` с автором. Второй фактор для главного администратора — до первого
платящего партнёра (Q-184).

## 6. Audit trail

`AuditLog` обязателен для: изменения дат брони; изменения цены; room move;
cancellation; payment; refund; ручного изменения availability; изменения guest document.

Записывается: кто, что, когда, before/after.

**Сверка 24.09.2026.** В той же транзакции, с автором и before/after пишутся: смена дат, переселение, отмена и незаезд
со стойки, платёж, возврат, ручные начисления.

Пробелы закрыты тем же днём (план П3, ADR-074):
- цены и ограничения (`/rates/bulk`) — с `before`: прежние значения тех же дат, диапазонами;
- отмена каналом — карточка до и после;
- предоплата канала (записана, изменена, уменьшена до штрафа, снята) и штрафы — своими строками с суммами;
- онбординг — одна строка;
- документ гостя — с id и типом;
- блокировка и снятие — в одной транзакции с записью журнала.

Осталось:
- **неизменяемость журнала в самой базе** — отобрать `UPDATE`/`DELETE` у роли приложения, уборку тестовых данных
  перевести на отдельную роль. Предложено в `DATA_MODEL.md` v1.7 §10 (Q-172) для базы в РК; на Supabase роль одна.

## 7. Логи и наблюдаемость

Observability without PII leakage:

- запрещено логировать номер документа, полный телефон, email, скан;
- в логах — только внутренние ID;
- ошибки интеграций логируются с external ID, а не с телом, содержащим PII;
- поле `last_error` во внешних событиях очищается от PII перед сохранением. **Выполняется с 24.09.2026:**
  - `last_error` входящих событий и очереди исходящих пишется через `redactText` — секреты, почта, телефоны;
  - через него же идут тексты неисправностей и журнал API;
  - Prisma печатает ошибки без аргументов вызова (`errorFormat: 'minimal'`).

С 24.09.2026 текст ошибки отправки письма не содержит адресов почты (`resend.ts`), а маскировщик логов тестов скрывает
и значения переменных `*SALT*` и `*COOKIE*`.

## 8. Бэкапы

Каждая production migration: backup → migration → validation → rollback procedure (AGENTS.md §14).
Бэкапы содержат PII, значит подчиняются тем же требованиям юрисдикции и доступа.
Ответственный и место хранения — Q-073.

**Сверка 24.09.2026.** Процедуры «бэкап → миграция → проверка → откат» нет ни в одном документе, Q-073 открыт.
Единственный снимок базы — `/root/backups/luxx-before-reset-2026-09-19.dump` на Hostinger: та же машина, что стойка,
одна копия, восстановление не проверялось. Хуже того: организация Supabase — на бесплатном плане, а ежедневные копии
Supabase делает только с плана Pro (документация Supabase, «Database Backups»). Рабочая база с бронями с 19.09 не
копируется вовсе.

**Сделано вечером 24.09.2026** (`docs/ops/backups.md`):
- `scripts/ops/db-backup.sh` — ночная копия схемы `public`: проверка копии, права 600, ротация 14 суток;
- `scripts/ops/db-restore-check.sh` — пробное восстановление на локальной PostgreSQL. Первая же проба показала, что
  наивный `pg_restore` такой копии в новую базу падает на `CREATE SCHEMA public`: скрипт это обходит;
- порядок «бэкап → миграция → проверка → откат» записан там же.

Тем же вечером владелец установил копию на сервере.

## 11. Публичные адреса и счётчик сайта (срез 8, 12.09.2026)

С 15.09.2026 у стойки есть свой вход по логину и паролю (ADR-049): пароли лежат в нашей базе хешами
`scrypt`, в cookie у человека — токен сессии (`httpOnly`, `SameSite=Lax`), в базе только его sha-256.
Замок непубличных маршрутов API — `AUTH_REQUIRED=1`. На сервере он включён с 19.09.2026 (ADR-053), в
`deploy/compose.yml` включён по умолчанию (`${AUTH_REQUIRED:-1}`, выключить можно только явным `0`). Cloudflare Access
снят 20.09.2026, так что этот замок единственный.

Приглашения и сброс пароля идут письмом через `RESEND_API_KEY` (`docs/mail/README.md`). Ключ живёт только в заголовке
запроса, в письме нет пароля, а адрес получателя не попадает в тексты ошибок — почта сотрудника это персональные данные
(ADR-018). Служебные ходоки (сторож, импорт, скрипты сверки)
приходят с `SERVICE_API_KEY`, и их записи в журнале остаются без автора.

API на Mac слушает `127.0.0.1`, на сервере — сеть compose без проброса портов (`expose`, а не `ports`): снаружи к нему
ведёт только туннель. Наружу нужны три группы адресов: `/a/*`, `/w/*` и webhook. Демо-страницы наружу не выходят —
см. ниже.

| Адрес | Кто вызывает | Защита |
|---|---|---|
| `GET /a/pms.js`, `GET /a/demo` | браузеры посетителей сайта | публичные по назначению; скрипт без секретов |
| `POST /a/hit` | счётчик на сайте | ключ сайта (не секрет, стоит в HTML) + домен из Origin/Referer + лимиты 60/мин на посетителя и 600/мин на сайт; всегда 204, чужое не сохраняется |
| `GET /w/widget.js`, `GET /w/config` | браузеры посетителей сайта | публичные по назначению; `/w/config` отдаёт только публичный ключ Turnstile, секрета в ответе нет (MKT1B BOOK-3: без него в туннеле обязательная проверка отказывает каждой брони). `GET /w/demo` наружу не выходит, только локально |
| `GET /w/availability`, `POST /w/book` | виджет бронирования (срез 9) | ключ сайта + домен из Origin/Referer + CORS только для доменов сайта; honeypot; лимиты 5 броней в час с IP (IP только в памяти) и 30 в час на сайт; бронь идёт через те же правила, что со стойки; гость — по ADR-018 |
| `POST /channels/channex/webhook` | Channex | секрет в заголовке `X-Channex-Webhook-Secret` |

У продавца (отдельный экземпляр бота, свой адрес `SELLER_PUBLIC_URL`) наружу открыт вебхук WhatsApp
`GET/POST /channels/whatsapp/webhook/{организация}` (С3): GET отвечает только правильному проверочному слову
этой гостиницы, POST принимает лишь тела с подписью `X-Hub-Signature-256` секретом ЕЁ приложения Meta,
чужой `phone_number_id` под верной подписью молча пропускается. Токены и секреты Meta лежат в базе бота
шифрованными (`LLM_KEYS_SECRET`) и в ответах не появляются. На краю туннеля к продавцу пропускается только этот
путь с uuid организации (`deploy/cloudflared.example.yml`, проверяет `tests/unit/deploy-server.test.ts`): кривой адрес
получает 404 до бота, а чат продавца, панель и `/internal/*` наружу не выходят — чат на сайт объекта только когда
база бота в РК (ADR-009).

Дверь котировки ИИ-продавца `GET /bot/availability` (ADR-085) наружу **не выходит**: продавец зовёт её по
внутренней сети `wetop-internal` со своим узким ключом `SELLER_QUOTE_KEY` (`x-wetop-service-key`), ключ открывает
ровно этот адрес и только чтение. В туннель и ingress она не добавляется — правило Q-112 ниже не меняется.

Бронь из чата ИИ-продавца (ADR-144, DATA_MODEL §25) идёт по той же внутренней сети отдельным ключом записи
`SELLER_BOOK_KEY` (у бота `INTEGRATION_BOOK_KEY`): он открывает только `POST /bot/booking-intents` и
`POST /bot/booking-intents/confirm`, ключ котировки туда не пускается, ключ записи не читает. Наружу двери не выходят.
Согласие гостя проверяет сервер бота по точной фразе в сообщении этого хода, а не модель.

Публичный рантайм сайтов `apps/sites` (MKT4, Cloudflare Worker, Q-269) ходит в API своим ключом `SITES_RUNTIME_KEY`
(`x-wetop-service-key`). Ключ открывает ровно `GET /sites-runtime/current` и отдаёт только текущую опубликованную версию
сайта, разрешённого по хосту: ни управления сайтом, ни черновиков, ни версии по id. Общий `SERVICE_API_KEY` на этот путь не
пускается. В Worker ключ живёт только секретом (`wrangler secret put SITES_RUNTIME_KEY`), в API только в `.env`
сервера; в репозитории и в `wrangler.toml` значения нет. Разрешение хостов в production выключено до MKT7, поэтому
путь `/sites-runtime/*` в MKT4 наружу не выводится: правило Q-112 ниже не меняется, расширение туннеля и ingress на
этот путь решается вместе с MKT7 (`apps/sites/README.md`).

Публикация и превью (MKT7, `docs/marketing/site-publication-v0.md`). Тот же ключ `SITES_RUNTIME_KEY` открывает ещё
`GET /sites-runtime/preview`, но сам по себе ничего там не читает: нужен действующий токен превью. Токен подписывает
API секретом `SITE_PREVIEW_SECRET` (HMAC-SHA256, не короче 32 байт, только в `.env` сервера; нет секрета или он
короткий, превью выключено с 503, а не подписывается пустым ключом); в токене `siteId`, `versionId` и срок (60 минут,
не дальше 24 часов вперёд), сравнение подписи за постоянное время. Токен выдаёт только управление (`POST
/marketing/site/preview`, право `settings`, строгий scope филиала) и только для версии своего сайта; стойка открывает
ссылку сразу в новой вкладке и не хранит её. Ответ превью: `noindex, nofollow`, `Cache-Control: private, no-store`,
`Referrer-Policy: no-referrer`, без брони, без счётчика и без цены «от»; `robots.txt` превью запрещает всё. Хосты сайтов
клиентов живут на отдельном registrable domain `SITES_BASE_DOMAIN` (Q-271 RESOLVED OWNER 07.10.2026), не под
`wetop.ai`: куки, репутация и граница безопасности основного домена, стойки и API с ними не делятся. `SITES_BASE_DOMAIN`
задаёт инфраструктура: в исходниках конкретного apex нет, значение `wetop.ai` и его поддомены API отвергает. Боевое
значение и вывод `/sites-runtime/*` наружу (туннель, ingress) делает владелец при выкладке; MKT7 этого не делал.

Бриф сайта (MKT5, `docs/marketing/site-brief-v0.md`): `GET /marketing/site/brief` только для вошедших с правом
`settings` и только в строгом scope одного филиала гостиницы; публичного пути нет. Выборки берут белый список полей:
данных гостей, броней, денег, людей и членств бриф не читает, инструкцию ИИ-продавца (`prompt_text`, запреты,
приветствие, «когда звать человека», профиль агента, мастер) не выбирает из базы вовсе, адресов фото и id провайдера
не отдаёт. Тексты Channex и владельца в брифе это непроверенные данные: генерация MKT6 передаёт модели только `input`
отдельным блоком DATA и не строит из них инструкцию. Сторожевые строки держит `tests/integration/site-brief.test.ts`.

Генерация сайта (MKT6, `docs/marketing/site-generation-v0.md`): вход бота `POST /internal/site-generation` открыт только
служебному ключу `SELLER_SERVICE_KEY` (сессия панели, ключ виджета и ключ живости дают 403 до разбора тела), тело строгое,
ключ модели только платформы: ключ партнёра (`OrganizationLlmKey`) этот путь не читает, организацию не принимает
(Q-274). Модели уходит только `input` брифа отдельным блоком данных; правила промпта в коде бота. Ответ модели
проверяет платформа тем же валидатором SiteSpec и правилами генерации (без ассетов, без выдуманных контактов,
юридических данных и ссылок); неверный ответ нигде не сохраняется, в журнале и логах только id, коды и счётчики.
Задачу ставит человек с правом `settings` в строгом scope; `wetop_app` не меняет и не удаляет задачи, воркер ходит
служебным путём. Неизвестный расход токенов останавливает генерацию организации до следующих суток UTC.

**Правило для постоянного адреса (Q-112):** наружу выходят только `/a/*`, `/w/*` и webhook; остальное API — только из
локальной сети или через вход (есть с 15.09.2026, ADR-049). Быстрый туннель Cloudflare (`scripts/ops/channex-tunnel.sh`)
пробрасывает **весь порт 3001** — это допустимо только на время разработки и не для настоящего сайта.
Сюда же относятся служебные адреса сторожа `/guard/*` (срез 11): наружу им не нужно; через быстрый туннель они
доступны так же, как остальное API. Проход сторожа по запросу не умножает починки — лимиты попыток хранятся в базе;
пробное сообщение будильника — не чаще раза в минуту. Токен Telegram-бота — только в `.env`, в текст ошибок не попадает.

**Домен wetop.ai (14.09.2026, ADR-045).** Правило выше исполнено адресами:
- `app.wetop.ai` — **с 20.09.2026 вход — пароль приложения, Cloudflare Access снят (ADR-053).** Было: стойка только после входа Cloudflare Access; `cloudflared` проверяет токен Access до передачи запроса
  на Mac. Заголовок `cf-access-authenticated-user-email` стойка использует только для показа, права по нему не выдаются.
  После снятия Access этот заголовок может прислать кто угодно. С 24.09.2026 стойка его не читает: подпись «Access
  пропустил» и подстановка почты убраны (план П9).
- `api.wetop.ai`: только `/a/pms.js`, `/a/hit`, `/w/widget.js`, `/w/config`, `/w/availability`, `/w/book` и webhook; `/a/demo` и
  `/w/demo` наружу не выходят (бронь с демо-страницы настоящая), остальное — 404 на краю туннеля.
- Адрес посетителя для лимитов — `CF-Connecting-IP`, и только если запрос пришёл от туннеля: с loopback (Mac) или из
  частной сети compose (сервер). До 24.09.2026 учитывался только loopback. На сервере все посетители сайта шли одним
  адресом контейнера туннеля, и лимит «5 броней в час с адреса» был общим на всех.
- Секрет webhook сравнивается за постоянное время. При заданном `PUBLIC_API_URL` webhook регистрируется только на него.
  С 24.09.2026 то же правило у проверки webhook (`POST /channels/channex/webhook/test`): другой адрес — 409, секрет
  на чужой сервер не уходит (план П5).
- Быстрый туннель (`tunnel`) и постоянный (`domain`) вместе не запускаются.

**Счётчик не собирает персональных данных** (план среза 8 §9): не сохраняются IP-адрес и полный User-Agent,
нет cookies, содержимое форм не читается, параметры событий проходят через allow-list ключей
(`arrival`, `departure`, `adults`, `children`, `category`, `rate`, `step`). ID посетителя — случайное число в
`localStorage` браузера, к гостю и брони не привязано. Поэтому таблицы `web_*` могут жить в dev-БД в Сингапуре
(ADR-018). Сырые сессии хранятся 13 месяцев. С 24.09.2026 их раз в сутки после 04:00 Алматы удаляет API
(`apps/api/src/analytics/retention.service.ts`, следом за полной выгрузкой ARI; выключается `ANALYTICS_RETENTION=off`).
Вручную — `npm run analytics:retention` (`--dry` — только посчитать). Первые данные (12.09.2026) дойдут до срока в
октябре 2027.


## 12. База Supabase и Data API (найдено 22.09.2026)

Рабочая база стойки до переезда в РК — Supabase. Советник безопасности Supabase 22.09.2026: ERROR «RLS Disabled in
Public» на всех 41 таблице схемы `public`; роли `anon` и `authenticated` имеют права на них (в том числе `SELECT` на

Закрыть до живого дня и до того, как в базу попадут настоящие данные: выключить Data API в панели или отобрать права у
`anon`/`authenticated` — решение и действие владельца; варианты и проверка — `plans/a0-server-and-supabase-2026-09-22.md`
§4. Состояние: **закрыто 22.09.2026 вечером — владелец выключил Data API** (вариант А). Проверено агентом в 20:45 UTC:
советник больше не показывает «RLS Disabled in Public» (в 18:45 UTC — 41 ERROR; этот линт считает только схемы, открытые
через PostgREST), хотя RLS по-прежнему выключен на 41 таблице из 41 и `SELECT` у `anon` на `users` и `guests` на месте, —

(A1) Data API нет. Перепроверено 24.09.2026 в 09:01 UTC: советник показывает только WARN «Extension in Public»

## 13. ИИ-помощник и ИИ-продавец (ТЗ ред. 1 от 24.09.2026, ADR-079)

Контракт с ботом — `docs/assistant/README.md`. Что держит платформа:

**Ключи — только в `.env` API, ни одного в браузере:**
- `WIDGET_IDENTITY_SECRET` — общий с помощником, им подписывается вошедший;
- `ASSISTANT_READ_KEY` — узкий ключ помощника: ровно `GET /assistant/errors` и `GET /guard/status`, остальное — 403;
- `SELLER_SERVICE_KEY` — ключ, с которым API платформы ходит к продавцу. Продавец не знает, кто из сотрудников
  действовал, поэтому перехват, возврат, ответ гостю и загрузка знаний пишутся в `audit_logs` платформы с автором —
  без текста переписки. С Э4 (ADR-083) продавец обслуживает все гостиницы: каждый вызов панели идёт с заголовком
  `X-Organization`, и продавец отдаёт строки ровно этой организации — изоляция доказана его тестом
  `tests/test_orgs_isolation.py`. Публичный ключ гостиницы в теге чата (`data-key="sk_…"`) — не секрет: он выводится
  как HMAC-SHA256 от служебного ключа и uuid организации (первые 24 hex), нигде не хранится, и восстановить из него
  служебный ключ нельзя. Сменили `SELLER_SERVICE_KEY` — сверка за минуту разошлёт гостиницам новые ключи, а тег на
  сайте нужно заменить из «Код для сайта».

**Подпись вошедшего** (`user_id|email|org_id|role|issued_at`, HMAC-SHA256, 12 часов) живёт в атрибуте `data-identity`
тега виджета и в заголовке `X-Widget-Identity` — никогда в адресе: адреса оседают в журналах привратника, а в подписи
почта человека. `GET /assistant/identity` отвечает с `Cache-Control: no-store` и только человеку: служебный ключ подписи
не получает. После входа и выхода стойка один раз перезагружает страницу, чтобы следующий за стойкой не видел чужой
диалог (ключ хозяина — короткий отпечаток сессии с приставкой, не `sessions.token_hash`).

**`GET /assistant/errors` открыт только ключу — всегда.** Контроллер сверяет ключ сам: без `AUTH_REQUIRED=1` замок
пускает всех, а вошедший человек проходит его сессией и прочёл бы чужие ошибки, подставив `userId`.

**Журнал ошибок человека** (`user_errors`, DATA_MODEL §14): шаблон маршрута, код, текст ответа API с маской почты,
телефонов и секретов, номер запроса. Тела запроса, значений из адреса и данных гостей нет по построению. Хранение
30 суток, уборка в API (`USER_ERRORS_RETENTION=off` — выключить).

**Продавец привязан к одной организации** (`SELLER_ORGANIZATION_ID`): платформа мультиарендная, и вошедший из другой
организации получает отказ до любого вызова продавца. Переписка гостей с продавцом — персональные данные: платформа её
не хранит, только показывает в разделе; база бота стоит там же, где база платформы с настоящими данными (ADR-009, Q-174).

**Наружу у экземпляров бота — только `/widget/*` и `/health`.** Туннель платформы не меняется: помощник и продавец
ходят к API по внутренней сети. Если бот встанет на другом сервере — два пути помощника открываются в туннеле
отдельным решением (Q-174).

**Служебный вход в продавца** (Б5, сверено с кодом бота 24.09): ключ `X-Service-Key` бот пускает ровно на маршруты
раздела (диалоги, знания, сводка, профиль, факты — `SERVICE_ROUTES`) и на песочницу в корне (`/internal/sandbox`);
правка промпта целиком (`PUT /prompt`) ключу закрыта — ядро правил владелец объекта не перепишет. Если у панели бота
задан список адресов (`DASHBOARD_ALLOWED_IPS`), в нём должен быть адрес сервера платформы: иначе продавец отвечает 403
«Доступ с этого адреса закрыт», и раздел показывает эти слова. Список действует на маршруты панели; песочница его не
сверяет — её закрывает внутренняя сеть (`/internal/*` наружу не открыт).

**Скрипт виджета — со стороннего адреса.** С 29.09.2026 у стойки есть политика безопасности контента (SEC-4, §14):
`frame-ancestors 'none'` действует, полная политика пока в режиме report-only, адрес помощника внесён в `script-src` и
`connect-src`. Предел тела серверного действия стойки поднят до 11 МБ — ради
документа знаний продавца (продавец принимает до 10 МБ); API раздела режет файл тем же пределом.


## 14. Что закрыто по аудиту 29.09.2026 (SEC-1…SEC-4)

Аудит кода и защиты 29.09.2026 разбит на небольшие изменения; у каждого свой план в `plans/` и своё решение.

- **Row Level Security в базе (ADR-103, DATA_MODEL §17).** Запросы организации идут ролью `wetop_app` без `BYPASSRLS`, на
  таблицы действует политика `rls_tenant` (43 политики на 43 таблицах из 53; 10 таблиц без RLS перечислены в DATA_MODEL §17: `users`, `password_resets`,
  `email_verifications`, `platform_admins`, `wizard_*`, `external_events`, `channel_outbox`, `system_incidents`).
  Пути, где организация ещё не известна (вход, приглашения, система), используют служебную роль явно —
  `withServiceDatabase(...)`. Включение и откат — `docs/ops/rls.md`.
- **Старт API без RLS-настройки невозможен (SEC-1a).** В production API до приёма запросов проверяет, что
  `DATABASE_APP_URL` задан и подключение идёт ролью `wetop_app`, не суперпользователем и не `BYPASSRLS`; иначе завершается
  с ошибкой. Выход — `RLS_DISABLED=1`, только для отката, с предупреждением в журнале.
- **Права роли на учётные данные (SEC-1b, ADR-124).** Миграция `20260929000033_rls_credential_grants` отзывает у `wetop_app`
  все права на `password_resets`, `email_verifications`, `wizard_sessions`, `wizard_events`, `wizard_surveys`; на `users` оставлено
  чтение пяти колонок (`id, email, name, status, email_verified_at`), на `platform_admins` — двух (`user_id, revoked_at`).
  Пароли и токены читает и пишет только служебная роль. Стадия B (`external_events`, `channel_outbox`, `system_incidents`) —
  решение владельца 30.09.2026 (Q-222, вариант б\*): запрос остаётся на `wetop_app` + RLS, данные только интеграции — узкий
  репозиторий на служебной роли, у `wetop_app` на `channel_outbox` только `INSERT`; код не начат, план —
  `plans/sec1b-stage-b-2026-09-30.md`. Применение миграции на рабочей базе — действие владельца.
- **Объект интеграции Channex — по идентификатору (SEC-2, ADR-125).** `INTEGRATION_PROPERTY_ID` в `.env`; без него API
  откатывается к сопоставлениям Channex, затем к названию и пишет предупреждение. Определять оператора интеграции по
  названию объекта небезопасно: первый зарегистрировавшийся с таким названием мог им стать (Q-223, решение владельца 30.09.2026:
  в production переменная станет обязательной, а путь по названию и по сопоставлениям Channex для владения исчезнет; вне production
  они временно остаются и помечены DEPRECATED. Инвариант: сопоставления Channex не источник владения в production).

  report-only; кука `wetop_scope` разбирается строгим форматом; лимит тела запроса читается потоком до разбора; счётчик
