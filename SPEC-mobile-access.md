# SPEC-mobile-access

Дата: 24.10.2026. Статус: план принят владельцем, локальная реализация выполнена; публикация отдельно. Модуль mobile-access из утверждённой карты plans/mobile-app-start-2026-10-24.md. Зависимость: mobile-foundation.

## Цель и допущения

Войти существующей учётной записью WETOP и попасть в защищённый рабочий кабинет. Под админкой понимается кабинет владельца/сотрудника по его серверным правам, а не выдача platformAdmin. Регистрация нового бизнеса и перенос всех рабочих разделов не входят в этот модуль. Сегодня с реальными операционными данными остаётся mobile-today.

Первый экран без сессии: логотип WETOP, «Войти в WETOP», подписанные поля «Почта» и «Пароль», показать/скрыть пароль, «Войти», «Забыли пароль?». Нет рабочего меню до подтверждения сессии. Пароль можно вставлять и заполнять менеджером; email-клавиатура, отсутствие автокапитализации, подходящие autofill hints. Ошибки около формы, нажатие блокируется на время запроса, повтор не отправляется автоматически. Цели нажатия минимум 48 logical px, существующие цвета и обе темы.

## Проверенный существующий контракт

- POST /auth/login: { email, password } -> { token, expiresAt, user }. Реализован apps/api/src/auth/auth.controller.ts:101.
- Authorization: Bearer поддерживается apps/api/src/auth/auth.guard.ts:16.
- GET /auth/me: user, organization, expiresAt, sessionIssuedAt, access, beautyAccess, context. Контроллер:216.
- POST /auth/logout отзывает сессию, контроллер:273.
- GET /auth/organizations и POST /auth/organization переключают организацию существующим серверным механизмом.
- GET /branches возвращает доступные филиалы. X-Wetop-Scope выбирает контекст, не выдаёт права. docs/auth-identity-contract.md и apps/web/src/lib/scope-resolve.ts остаются источниками правил.
- whoami продлевает сессию на 12 часов от текущего запроса; стабильная идентичность использует sessionIssuedAt. apps/api/src/auth/auth.service.ts:604-636.
- POST /auth/password-reset/request уже существует; экран запроса восстановления использует одинаковый ответ для существующих и отсутствующих адресов. Подтверждение из письма пока завершается существующим веб-процессом, без передачи native токена браузеру.

## Граница сервера, требующая утверждения

API по умолчанию слушает loopback; контейнерный API не публикуется наружу (apps/api/src/listen-address.ts). Существующий /api/site-auth/[action] предназначен для браузера: проверяет Origin и ставит HttpOnly cookie, токен в JSON не отдаёт. Поэтому этот маршрут не переиспользуется как нативный вход.

Предлагается узкий шлюз apps/web/src/app/api/mobile/v1/[action]/route.ts на существующем HTTPS-хосте приложения. Это новый API-контракт, но без новых таблиц, миграций, ролей и правил входа. Никаких произвольных proxy URL, пути и методы только из статического списка:

| Action | Method | Внутренний маршрут |
|---|---|---|
| login | POST | /auth/login |
| me | GET | /auth/me |
| organizations | GET | /auth/organizations |
| organization | POST | /auth/organization |
| branches | GET | /branches |
| logout | POST | /auth/logout |
| password-reset | POST | /auth/password-reset/request |

Шлюз использует пользовательский Bearer, не браузерную cookie. Не импортирует cookie-bound backendFetch; отдельный узкий серверный транспорт. Пересылает только нужные поля и заголовки; не принимает service-key, произвольный upstream URL или чужой forwarded IP. Лимиты входа API сохраняются, доверенный адрес клиента определяется существующим серверным контрактом прокси. Ограничения размера тела, схемы запросов, таймаут, no-store и очистка ошибок обязательны. Токены/пароли не журналируются. Ответ login содержит токен только этому клиенту через HTTPS; остальные ответы имеют явные DTO. Origin не используется как доказательство права, защиту обеспечивает серверная сессия. Для web preview реальные credentials не сохраняются в localStorage; контракт проверяется на отдельном fixture, без ослабления CORS ради preview.

Локальная реализация/тестирование разрешается отдельно от публикации. Публичный staging URL и публикация шлюза должны быть проверены до реального входа на устройстве; внутренний API не открывается наружу.

## Клиентская сессия и кабинет

- Добавить expo-secure-store совместимой версии SDK 58. Сохранять только token; пароль не сохранять. Использовать отдельный ключ для окружения и приложения. Документация: https://docs.expo.dev/versions/latest/sdk/securestore/.
- При запуске: loading -> чтение storage -> GET me -> получение доступного контекста -> кабинет. При ошибке storage закрыть доступ и показать понятное восстановление; не делать вид, что сохранение удалось.
- 401/пустой user: очистить токен, контекст и данные, вернуть вход. Сетевая ошибка не приравнивается к неверному паролю; показывается повтор без открытия кабинета по одному наличию токена.
- Организации и филиалы выбираются только из серверного списка. Один доступный филиал выбирается автоматически; несколько: валидный предыдущий выбор этого пользователя либо выбор человеком. Не выбирать первый молча. Сохранять различие personal/no-branches/onboarding согласно существующему контракту. Незавершённая настройка не выдаётся за готовый рабочий кабинет.
- После выбора повторно получить me со scope. Кабинет показывает настоящее имя, бизнес/филиал, доступный контекст; меню строится по правам. Нет заглушек бронирований/выручки. Незавершённые рабочие модули не представлены как работающие.
- При смене организации/филиала сразу скрыть предыдущие данные; поздние ответы от старого контекста игнорировать. Использовать поколение запроса/AbortController. Передавать новый токен, если сервер его ротирует.
- Выход блокирует защищённые маршруты и очищает локальные данные. Серверный отзыв вызывается явно. Если сеть отсутствует, не утверждать, что удалённая сессия отозвана; новый вход возможен только после проверки сервера.
- Возврат назад после входа не возвращает парольную форму; после выхода и по deep link нельзя открыть защищённый кабинет. Не переносить native токен в URL веб-админки.

## Структура и стиль

apps/mobile/src/auth: DTO, транспорт, storage adapter, session provider. src/app: вход, восстановление, выбор контекста, защищённая группа кабинета. tests: проверки состояния, формы, переходов и гонок. apps/web/src/lib: отдельный транспорт шлюза и тесты; app/api/mobile/v1: allowlist route. Архитектурное решение после утверждения записывается в docs/decisions/2026-10-24-mobile-access.md.

Пример контракта: `type AccessState = { kind: 'signed-out' } | { kind: 'loading' } | { kind: 'ready'; context: VerifiedContext };`. Никаких `any`, импорта Next.js в mobile или доверия к роли, записанной на телефоне.

## Проверки и команды

Сначала red-тесты, затем реализация. Проверить: успешный и неверный вход, 429, сеть/таймаут, двойное нажатие, storage failure, восстановление сессии, истечение, серверный отзыв, deep link без входа, смена контекста и поздний ответ, пустой список филиалов, неизменность web-cookie авторизации. Шлюз: запрет неизвестного action/method, cookie-only запроса к protected action, service-key, некорректного scope, утечки токена в ошибки/логи.

```sh
npm run test:status
npm run test:record -- mobile
npm run test:record -- mobile-types
npm run test:record -- unit apps/web/src/lib/mobile-gateway.test.ts
npm run test:record -- lint
cd apps/mobile
npx expo install --check
npx expo export --platform all
```

mobile-gateway.test.ts пока не создан, команда является будущим контрактом. Тесты изолированы от общей dev-базы. Native запуск и storage проверяются на iOS/Android после появления SDK; fixture-прохождение не является доказательством реального входа production. Отчёт reports/mobile-access-2026-10-24/REPORT.md разделяет component, gateway, web preview, native и реальное окружение.

## Критерии готовности и границы

Готово: подтверждённый вход -> серверный контекст -> защищённый кабинет -> выход, с тестами ошибок и отсутствия утечки между контекстами. Дизайн на 375 px, клавиатура и увеличенный текст проверены либо native-пробел явно указан. API-сбой не заменяется демонстрационным успехом.

Всегда: существующие права/сессии, HTTPS для нелокального окружения, red-green, ограниченный gateway, no-store. Согласовать: данный новый публичный контракт и SecureStore, production-публикацию через установленный процесс. Никогда: служебные секреты в приложении, реальные учётные данные в fixtures, обход auth, выдача административных прав, миграции или полная офлайн-авторизация.

## Решение владельца

Модуль включён в принятый владельцем план; ограниченный HTTPS-шлюз и SecureStore реализованы локально. Предпочтение: нативный вход и нативный кабинет на существующей модели. Полный перенос рабочих экранов продолжается отдельными модулями утверждённой карты.
