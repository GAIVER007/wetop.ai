# ТЕСТИРОВАНИЕ: что доказано и как не гонять одно и то же дважды

Здесь собрано знание о тестах проекта: какие наборы есть, что каждый доказывает, на какие грабли уже
наступали и как их обходить. Каждый прогон с логом записывается сам в [`tests/runs/`](tests/runs/JOURNAL.md)
и едет в репозиторий вместе с кодом — новая сессия и вторая машина видят то же, что видела эта.

Раскладка тестов, окна дат сквозных тестов и список критичных сценариев — [`tests/README.md`](tests/README.md).

---

## 1. Три команды

| Когда | Команда | Что даёт |
|---|---|---|
| Перед любым прогоном | `npm run test:status` | По каждому набору: последний полный прогон, менялся ли с тех пор код набора, гонять или нет |
| Прогон | `npm run test:record -- <набор> [аргументы раннера] [--note "зачем"]` | Вывод на экран как обычно, плюс лог без секретов и строка журнала |
| Упало | лог из `test:status` или последняя строка [`JOURNAL.md`](tests/runs/JOURNAL.md) | Имя теста, файл и текст ошибки — без повторного прогона |

Наборы: `unit`, `integration`, `e2e`, `typecheck`, `lint`. Один спек или отбор по имени:
`npm run test:record -- e2e tests/e2e/finance.spec.ts` — такой прогон записывается как частичный и весь набор
не доказывает.

**Тесты гонять только через `test:record`.** Прогон мимо журнала — знание, которое уйдёт вместе с сессией.
Лог и строки журнала коммитятся вместе с правкой, которую они доказывают.

**Пулер Supabase — 15 клиентов на проект.** API держит 5, задача `exely-sync` — 1 (в её plist вписан
`DATABASE_POOL_MAX=1`). Разовый скрипт с пулом по умолчанию переполняет пулер, и запросы стойки падают
в 500 («Connection terminated due to connection timeout» в журнале API). Запускайте такие скрипты как
`DATABASE_POOL_MAX=1 npm run <скрипт>`.

**Один прогон на дерево.** `e2e` и `integration` берут **общий** замок (`tests/runs/.locks/dev-database.lock`):
второй прогон любого из них отказывается и называет набор, pid и время первого. Два прогона на общей dev-базе рвут друг другу `test-results/`
и занимают койки в чужих окнах дат — 15.09.2026 это стоило трёх ложных падений и получаса разбора
(`tests/README.md`, «Один прогон на дерево»). Замок от убитого прогона перехватывается.

## 2. Когда прогон можно не повторять

`test:record` запоминает отпечаток содержимого всех файлов, от которых зависит набор: код, тесты, настройки,
`package-lock.json` — вместе с незакоммиченными правками. `test:status` считает отпечаток заново и сравнивает.

| Состояние | Что значит | Что делать |
|---|---|---|
| ✅ доказано | Последний полный прогон зелёный, код набора с тех пор не изменился ни на байт | Не гонять, ссылаться на строку журнала |
| 🟡 код изменился | После прогона менялись файлы набора — `test:status` покажет какие | Гонять |
| 🟡 больше суток | Только `integration` и `e2e`: они зависят от живой dev-БД и от дат «от сегодня» | Гонять |
| 🔴 падает | Последний полный прогон красный на этом же коде | Чинить; прогон без правки даст то же самое |
| ⚪ нет прогона | Полного прогона набора в журнале нет | Гонять |

Не считается доказательством: частичный прогон, прерванный прогон, прогон без единого найденного теста и прогон,
во время которого код набора менялся (правила параллельная сессия).

Коммит отпечаток не меняет: закоммитили те же файлы — доказательство в силе. Документы в корне, `docs/`, `reports/`,
`plans/` и любые `README.md` в отпечаток не входят: правка документации тесты не обесценивает. Остальной
Markdown внутри кода входит — тесты импорта читают фикстуры `scripts/imports/src/exely/__fixtures__/*.md`.

## 3. Наборы

| Набор | Что внутри | Что проверяет | Нужно для запуска | Годность |
|---|---|---|---|---|
| `unit` | `vitest run --project unit` | Всё, что без базы: `apps`, `packages`, `scripts`, `tests/unit` | `npm run generate -w @pms/database` после установки; больше ничего. Набор `tests/unit/launchd-install.test.ts` идёт только на macOS | пока не изменится код |
| `integration` | `vitest run --project integration` | Схема `pms_test` проекта «hotel» (ADR-042): импорт фонда, цен и броней, запрет овербукинга, ручная бронь, CHECK гражданства, аналитика сайта, неисправности, прямой SQL в тестовой схеме | `DATABASE_URL` — в `.env` (dev-БД, как раньше) или переменной окружения на любой PostgreSQL 16; схему догоняет `tests/integration-setup.ts`, пустую заполняет сидом (`TEST_DATA`, `tests/README.md`) | сутки |
| `e2e` | `playwright test --workers=2` | Стойка целиком в изолированном стенде: браузер → web :3100 → API :3101 → `pms_test`; первым идёт `schema-guard`. Сертификация Channex — только `E2E_CHANNEX_LIVE=1` на рабочем стенде | `DATABASE_URL` (dev-БД или любой PostgreSQL 16 — сид), production-сборка `apps/web`; серверы Playwright поднимает сам; без браузеров Playwright — `CHROMIUM_PATH` | сутки |
| `typecheck` | `typecheck`, `typecheck:api`, `typecheck:web` — все три до конца | Типы корня, API и стойки | ничего | пока не изменится код |
| `lint` | `eslint .` | Правила кода, включая ADR-004: Channex только в `packages/integrations` | ничего | пока не изменится код |
| стойка без базы | `e2e --config tests/ui/playwright.config.ts` | Браузер → `next dev` → подставной API (`tests/ui/fixture-api.ts`): доступность всех разделов (axe, две темы, две ширины), шахматка по неделям и месяцам, drawer, черновики, вход за Access. Не доказательство работы с базой | ничего: ни базы, ни ключей; без браузеров Playwright — `CHROMIUM_PATH` | пока не изменится стойка |
| главная | `e2e --config tests/site/playwright.config.ts` (`npm run site:check`) | Статическая сборка wetop.ai: страницы, доступность (axe), телефон без горизонтальной прокрутки, карточка ссылки с картинкой, адреса из `sitemap.xml` | ничего: ни базы, ни ключей, ни стойки | пока не изменится сайт |

`npm test` — это **оба** проекта vitest, то есть и база (схема `pms_test`). Только модульные — `npm run test:record -- unit`.

**Обход стойки по экранам и кнопкам (`npm run ui:walkthrough`)** — не набор тестов, а сверка живого стенда:
открывает каждый экран из меню, нажимает на нём каждую кнопку, вкладку и раскрывашку, проходит по ссылкам (по две
на образец адреса), отправляет GET-формы фильтров и **сверяет числа на экране с ответом API за тот же период** —
шесть показателей главной на всех пяти отрезках и своих датах, полосу «На стойке», деньги за период, отчёт по
каналам, список броней, занято по дням шахматки, свободно в доступности, сессии аналитики. Кнопки, которые пишут
(заселить, отправить очередь, сохранить…), не нажимаются и перечисляются отдельно; окна подтверждения закрываются
«Оставить». Пишет `reports/ui-walkthrough-<дата>.md`, код выхода 1 при любом FAIL. На машине стойки — просто
`npm run ui:walkthrough` (живые 3000 и 3001 по умолчанию); на стенде сквозных тестов —
`WEB_URL=http://127.0.0.1:3100 APP_API_URL=http://127.0.0.1:3101 npm run ui:walkthrough`; без браузеров
Playwright — `CHROMIUM_PATH`.
**После ADR-053 стойка просит войти** (`APP_AUTH_REQUIRED=1`), и без учётных данных обходить нечего: обход говорит об этом одной строкой «пропуск» и пишет отчёт, а не выдаёт замок за поломку экранов. Чтобы он снова ходил по экранам, владелец вписывает в `.env` `WALKTHROUGH_EMAIL` и `WALKTHROUGH_PASSWORD` (учётная запись стойки; скрипт её не заводит и пароль не придумывает). API за замком обход зовёт служебным ключом `SERVICE_API_KEY`, как сторож и сверки.

**Пустая база — отдельный режим фикстуры.** `POST /__test/control {"noBookings": true}` оставляет фонд, категории, тарифы и цены, но убирает все брони: это состояние боевой PMS после очистки 19.09.2026 (ADR-052). Его проверяет `tests/ui/empty-base.spec.ts` — 17 экранов открываются и говорят, что записей нет. Режим `{"empty": true}` жёстче: он убирает и фонд.

**Рабочие данные тесты не трогают (ADR-042, 14.09.2026).** Интеграционные и сквозные тесты работают в схеме `pms_test`
того же проекта Supabase: копия рабочих таблиц, в которую можно писать. Создать или догнать миграции — `npm run test:schema`,
освежить копию данных — `npm run test:schema -- --refresh` (не во время чужого прогона). Новый прямой SQL в коде
(`$queryRaw`) пишите без имени схемы — `search_path` соединения направит его в `pms_test`; явное `public.` сломает изоляцию.

**Своя база вместо dev — `npm run db:local` (17.09.2026).** Интеграционные тесты доказывают то, что делает сама
база: запрет овербукинга, CHECK гражданства, частичный уникальный индекс неисправностей, прямой SQL журнала.
До сих пор их можно было прогнать только на машине владельца — единственная база была dev в Сингапуре, ключ к ней
агенту закрыт (`SECURITY.md` §3), а Session pooler даёт 15 клиентов на проект. `scripts/ops/local-db.sh` поднимает
рядом пустую PostgreSQL (порт 55432, каталог в `TMPDIR`), накатывает миграции и схему `pms_test`, засевает
вымышленный объект той же формы, что настоящий (`tests/tools/seed-local.ts`, ADR-010; состав ниже). Дальше:

```
npm run db:local                      # поднять, миграции, засев; печатает DATABASE_URL
DATABASE_URL='postgresql://postgres@127.0.0.1:55432/pmslocal' npm run test:record -- integration
npm run db:local -- stop              # остановить; reset — снести и поднять заново
```

Прогон занимает **9 секунд** против минут через пулер (первый: 32 из 32, 17.09). Засев отказывается работать,
если `DATABASE_URL` не локальный, — чужую базу этим не задеть (`tests/unit/seed-local.test.ts`).

20.09.2026: `test:schema` уже заполняет `pms_test`; повторно вызывать для неё
`seed-local` нельзя — размещения пересекаются. `db:local` отдельно засевает только
`public`. Для выбора версии PostgreSQL добавьте её `bin` в начало PATH; для своего
стенда задайте `PMS_LOCAL_PGDATA` и `PMS_LOCAL_PGPORT`. При включённом `E2E_AUTH=1`
изолированный API использует тестовый `SESSION_SECRET` (переопределяется через
`E2E_SESSION_SECRET`), не требует production-секрета. На Mac при нехватке ресурсов
запускайте unit с `--maxWorkers=2` отдельно от браузерного набора. Приёмка и
RED/GREEN: `reports/current-release-acceptance-2026-09-20/report.md`.

**Чего локальная база не доказывает:** данных настоящего объекта в ней нет, поэтому сверки с Exely, живой Channex
и всё, что смотрит на реальные брони, по-прежнему идут на машине стойки. Локальный прогон доказывает поведение
схемы и SQL — этого хватает для правок кода, но не для гейтов по числам.

**Сквозные (`e2e`) на локальной базе: 23 из 23 (18.09.2026, лог `tests/runs/logs/2026-09-18T10-49-56Z-e2e-f077.log`).** Кодов объекта в спеках
больше нет — категорию выбирает `tests/e2e/pick-category.ts` так же, как администратор: смотрит
`GET /availability` и берёт категорию с наибольшим запасом мест (`roomiestCategory`), а тариф — по политике
штрафа, а не по коду (`ratePlanWithPenalty`). Это же убрало привязку спеков к одному объекту вообще.

Что было нужно, чтобы весь набор прошёл на пустой машине (17.09 проходило 11 из 23, три помехи):

1. **Стенд повторяет форму объекта.** Засев даёт 88 единиц = 16 номеров + 72 койки по тем же диапазонам
   номеров, что у Exely (1–4, 5–40, 41–48, 49–84, 85–88), пять категорий 4 / 8 / 4 / 36 / 36 (одноместные с
   окном и без, двухместные, мужская и женская общие), вместимость номера — из категории (двухместный — 2, койка
   — 1; раньше каждая единица считалась за двоих, и «92 гостя максимум» в `inventory.spec.ts` не сходилось),
   цена за ночь своя у каждой категории (12 000 / 9 000 / 15 000 / 6 000 / 5 500 ₸ — переселение в другую
   категорию должно менять цену, `desk-tasks`), услуги из справочника Exely той же фикстурой, что импорт
   (`spravochniki.md`, 9 позиций — без них форма начисления услуги пуста). Форму стенда сторожит
   `tests/unit/seed-local.test.ts`.
2. **На стенде кто-то живёт.** Шесть выселенных вымышленных проживаний на 06–10.09.2026 (койки 5, 6, 7, 49, 50
   и номер 1) и четыре живущих «вчера → послезавтра» (8, 51, 41, 85): `chessboard.spec.ts` ждёт `occupied > 0`
   на зашитой дате, печатные формы и журнал — существующую бронь. Номера `STAND-0001…0010` не похожи на номера
   автотестов, уборка после прогона их не трогает; будущие окна спеков начинаются с «сегодня + 4» и не задеты.
3. **Двойники элементов при переходе.** Next держит уходящую страницу в DOM, и `getByTestId(...)` по всей
   странице находит два экземпляра — строгий режим Playwright отказывается. В 16 спеках поиск переведён внутрь
   `page.getByRole('main')` (`cancel-reservation`, `check-in-`/`check-out-`/`no-show-`/`extend-`, `availability`,
   `folio-balance`, `guest-form`, `c-arrivals`, `kpi-*`, `period-caption`, «Период: с/по», `unassigned-stays`)
   или ждёт `toHaveCount(1)` (печатные формы). Правило на будущее: после `page.goto` одиночный элемент ищите
   внутри `main`, списки — через `.first()` или `toHaveCount`.

Локальный прогон нашёл и настоящие дефекты живых спеков, которые на машине стойки просто не запускались:
`unit-blocks.spec.ts` снимал блокировку без подтверждения, хотя окно появилось 17.09 (PR #19), — спек упал бы
и на стойке; `inventory.spec.ts` держал код категории `exely-5074687` — теперь берёт двухместную из
`GET /inventory/summary`; помощник `tests/e2e/confirm.ts` ищет открытое окно (`dialog[open]`), а не любое из
нескольких на карточке. Семь спеков, изменённых 17–18.09 (деньги, `datetime`, окна), на машине стойки ещё не
гонялись — `npm run test:record -- e2e` там остаётся за владельцем: локальный стенд доказывает код, а не данные.

Как гонять локально (сборка стойки нужна — Playwright поднимает `next start`):

```
npm run db:local -- reset            # чистый стенд: миграции, pms_test, засев
npm run build -w apps/web
DATABASE_URL='postgresql://postgres@127.0.0.1:55432/pmslocal' \
E2E_BROWSER_EXECUTABLE=/opt/pw-browsers/chromium-1194/chrome-linux/chrome \
npm run test:record -- e2e --workers=1
```

**Сквозные (`e2e`) на локальной базе — 25 из 25 с сидом (17–19.09.2026).** Две работы шли параллельно и
слиты 19.09: сид `tests/tools/test-seed.ts` (`TEST_DATA=seed` — настоящий фонд из аудита, вымышленные цены и
~330 броней через боевой импорт, занятость вокруг «сегодня») и спеки без кодов объекта — категорию выбирает
`tests/e2e/pick-category.ts` так же, как администратор: смотрит `GET /availability` и берёт категорию с наибольшим
запасом мест (`roomiestCategory`), а тариф — по политике штрафа, а не по коду (`ratePlanWithPenalty`). На пустом
локальном PostgreSQL 16 без `.env`: `DATABASE_URL=… TEST_DATA=seed npm run test:record -- e2e` — 25/25 за ~50 с
(на Mac — 13 мин). Три препятствия, названные 17.09 (пустой стенд, двойники элементов при переходе, теснота
засеянных категорий), сидом и фикстурой `tests/e2e/fixtures.ts` сняты. **Сид живёт вокруг «сегодня»** (−10…+2
ночей, с +3 — окна спеков): позавчерашний сид сегодня пуст, и 19.09 `chessboard.spec` увидел занято 0 на сиде
от 16.09. Теперь `ensureTestSchema` сверяет день отметки `refreshed_at … (сид)` с сегодняшним по Алматы и засевает
заново сам (`seedIsStale`, `tests/unit/test-data-source.test.ts`, red → green); копия рабочих данных не стареет.

Локальный прогон показывает настоящие дефекты: так нашёлся строгий режим у окна подтверждения — на карточке брони
`<dialog>` несколько (по одному на панель), и помощник `tests/e2e/confirm.ts` ищет открытое окно (`dialog[open]`),
а не любое.

На машинах, где сборка Chromium отличается от той, что ждёт Playwright (контейнер без `playwright install`),
браузер задаётся так же, как в UI-наборе и на главной: `CHROMIUM_PATH=/путь/к/chrome` (у e2e принимается и
`E2E_BROWSER_EXECUTABLE`, у UI-набора — `UI_BROWSER_EXECUTABLE`).

Покрытие не измеряется: пакета `@vitest/coverage-*` в проекте нет, и цель 80% из `tests/README.md` сейчас ничем
не проверяется.

## 4. Грабли, на которые уже наступили

Каждая строка стоила часов. Прежде чем разбирать «плавающее» падение, сверьтесь здесь.

| Когда | Симптом | Причина | Как обходим | Где сторож |

## 7. Как устроен журнал

| Файл | Что внутри | Кто читает |
|---|---|---|
| `tests/runs/journal.jsonl` | Строка JSON на прогон: набор, аргументы, итоги, упавшие тесты с текстом ошибки, коммит, изменённые файлы, отпечаток, путь к логу, машина | `npm run test:status` |
| `tests/runs/JOURNAL.md` | Та же история таблицей | люди, в том числе на GitHub |
| `tests/runs/logs/<время>-<набор>-<xxxx>.log` | Весь вывод прогона; длиннее 512 КБ — середина вырезается, начало и конец остаются | тот, кто разбирает падение |

- Оба журнала только дописываются, старые строки не правятся: неудачный прогон — тоже знание. В `.gitattributes`
  для них `merge=union`: две машины или ветки дописали одновременно — при слиянии остаются обе строки. Для
  остальных файлов так нельзя: union молча склеил бы две версии одной исправленной строки.
- **Что вычищается из лога и журнала перед записью:** значения переменных `.env` и окружения, в имени которых
  KEY, SECRET, TOKEN, PASSWORD, DATABASE_URL; JWT; ключи вида `sk-…`, `ghp_…`; пароль в адресе
  (`postgres://user:***@host`); заголовки `Authorization` и `api-key`; email и телефоны. Проверено тестом
  `tests/unit/test-journal.test.ts`. Маскировка — страховка, а не разрешение печатать секреты в тестах.
- Журнал общий для всех сессий в этом дереве и для всех машин. Коммит файла журнала захватывает и строки
  чужих прогонов — это нормально: строка сама говорит, чей прогон (машина, время, заметка). Свой лог
  коммитить сразу вместе со своей строкой, иначе ссылка «лог» в `JOURNAL.md` на GitHub поведёт в пустоту.
- Время в `JOURNAL.md` — Алматы, в `journal.jsonl` — UTC. «+N» у коммита — столько файлов набора было не
  закоммичено в момент запуска.
- Код журнала: `tests/tools/journal.ts` (логика, покрыта тестом), `git-state.ts` (только чтение git),
  `cli-record.ts`, `cli-status.ts`.
