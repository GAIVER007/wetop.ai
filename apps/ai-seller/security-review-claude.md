# Security review в Claude Code — гайд по аудиту проекта

> AI-код ускоряет разработку, но добавляет новый класс рисков (XSS, небезопасные ссылки на объекты, утечки секретов). Перед деплоем прогоняй проверку безопасности.
> Три уровня: широкий промпт аудита (быстро) → 7 целевых промптов (глубоко) → GitHub Action (на каждый PR).

---

## 1. Широкий аудит одним промптом

⚠️ Проверено: встроенная команда `/security-review` в Claude Code **есть**. Она сравнивает текущую ветку с основной веткой удалённого репозитория, у нас это GitHub. Без подключённого репозитория не запускается и смотрит только изменения, не проект целиком. Первый полный аудит ставим промптом ниже, он работает у всех и видит весь код; `/security-review` пригодится потом, перед каждым коммитом.

**Как использовать:**
1. Открой проект в редакторе с Claude Code.
2. В чате дай задачу словами: «Проведи полный аудит безопасности проекта: вход, доступ к данным, проверка ввода, секреты, защита от перебора, выкладка. По каждой находке: уровень опасности, где в коде, как чинить. Начни с самого опасного. Не чини сам — сначала покажи список.»
3. Claude проанализирует кодовую базу и выдаст отчёт.
4. По каждой найденной уязвимости — попроси исправить.

**Что ловит:** SQL-инъекции, XSS, проблемы аутентификации/авторизации, небезопасную обработку данных, уязвимости зависимостей.

> Широкий промпт находит очевидное, но может пропустить специфику стека (дырявые RLS-политики, утечка токенов в боте). Для глубины — целевые промпты ниже.
> Рекомендация: запускай перед каждым значимым коммитом.

## 2. Семь целевых промптов (copy-paste в чат Claude Code)

### Промпт 1 — Аутентификация
```
Выступи в роли старшего инженера по безопасности. Проведи аудит аутентификации проекта.
Проверь и исправь:
1. Пароли хешируются надёжно (bcrypt/argon2, не md5/sha1)
2. Сессии имеют срок жизни и инвалидируются при логауте
3. Email-верификация включена для новых аккаунтов
4. Токены сброса пароля одноразовые, истекают через ~1 час
5. Login-эндпоинт имеет rate limiting (макс. 5 попыток/мин)
6. Auth-секреты (JWT_SECRET, service keys) не попадают в клиентский код
7. OAuth-редиректы валидируются (нет open redirect)
8. Middleware проверяет сессию на защищённых маршрутах
Для каждой проблемы: опиши уязвимость, покажи где в коде, предложи фикс.
```

### Промпт 2 — Авторизация и IDOR
```
Проверь все API-эндпоинты и запросы к БД. Убедись, что каждый запрос проверяет,
является ли текущий пользователь владельцем запрашиваемых данных.
Найди и исправь:
1. Эндпоинты, где ID берётся из URL/body без проверки ownership
2. SELECT без WHERE user_id = auth.uid()
3. UPDATE/DELETE без проверки принадлежности записи
4. API-роуты, доступные без аутентификации (если должны быть закрыты)
5. RLS-политики: покрывают ли все таблицы и все операции (SELECT/INSERT/UPDATE/DELETE)
6. Server Actions / Route Handlers: проверяется ли пользователь перед каждой операцией
Для каждой проблемы: какой эндпоинт уязвим, как получить чужие данные, конкретный фикс.
```

### Промпт 3 — Валидация ввода
```
Найди каждое место, где пользовательский ввод попадает в систему:
формы, API, загрузка файлов, query/URL-параметры.
Для каждой точки входа проверь и исправь:
1. Есть ли серверная схема-валидация (Zod или аналог)
2. SQL-запросы параметризованы, не конкатенация строк
3. HTML-вывод экранирует пользовательский контент (нет сырого innerHTML)
4. Загрузка файлов: проверяются MIME-тип, размер, расширение
5. Redirect URL валидируется (нет open redirect)
6. JSON-поля имеют схему, не принимают произвольную структуру
7. Числовые параметры (limit, offset, page) имеют верхнюю границу
Отклоняй невалидные данные с понятными ошибками. Строгие типы на каждом входе.
```

### Промпт 4 — Секреты и API-ключи
```
Просканируй проект на секреты и учётные данные. Проверь и исправь:
1. API-ключи, database URLs, service keys не захардкожены
2. .env в .gitignore; .env.example содержит только плейсхолдеры
3. Серверные ключи (service_role и т.п.) используются ТОЛЬКО на сервере
4. Публичные переменные (NEXT_PUBLIC_* и аналоги) не содержат секретов
5. Платёжные секреты (ЮKassa/Stripe secret key) не попадают на клиент
6. Git-история не содержит ранее закоммиченных секретов
7. Токены хранятся в httpOnly cookies, не в localStorage
Перенеси все секреты в переменные окружения, только серверное использование.
```

### Промпт 5 — Rate limiting и защита от ботов
```
Добавь защиту от злоупотреблений. Реализуй и проверь:
1. Rate limiting на login: макс. 5 попыток/мин на IP
2. Rate limiting на регистрацию: макс. 3 аккаунта/час на IP
3. Rate limiting на дорогие операции (AI-генерация и т.п.) — лимит по плану
4. Rate limiting на API: макс. ~100 запросов/мин на пользователя
5. Защита от перебора ID: UUID вместо последовательных числовых
6. CAPTCHA/proof-of-work или honeypot на публичных формах
7. Проверка подписи вебхуков (HMAC/signature/secret token)
8. Лимиты на размер запроса (body size limit)
Для реализации: Redis-ratelimit для serverless или middleware для MVP.
```

### Промпт 6 — Деплой и мониторинг
```
Настрой безопасный деплой и мониторинг. Проверь и настрой:
1. HTTPS принудительный (редирект с HTTP, HSTS-заголовок)
2. Секреты — в env-хранилище платформы, не в коде
3. Прямой доступ к БД закрыт из публичного интернета
4. CORS настроен строго: только твой домен, не '*'
5. Security-заголовки: X-Frame-Options, X-Content-Type-Options, CSP
6. Логирование: auth-попытки (успех/провал), API-ошибки (4xx/5xx)
7. Мониторинг аномалий: резкий рост запросов, много 401/403 с одного IP
8. Бэкапы БД настроены
9. Preview-деплои не имеют доступа к продакшн-БД
10. 🔴 Публичные эндпоинты не раскрывают внутреннее устройство: проверь
    /health и любые служебные адреса. Наружу не должны уходить имена
    сервисов (postgres, redis), имя окружения (production/staging),
    версии библиотек и фреймворка, внутренние пути и адреса, тексты
    ошибок от БД. Публичный /health отдаёт только {"status":"ok"}.
    Подробную диагностику вынеси на отдельный адрес, закрытый по сети
    или ключом.
Реализуй структурированное логирование для подозрительных событий.
```

⚠️ **Пункт 10 добавлен из живого случая:** открытый наружу `/health`
отдавал `app_env: production` вместе с именами сервисов. Это первое, что
собирает автоматический сканер, — дальше по именам и версиям подбираются
известные уязвимости.

### Промпт 7 — Полный аудит (финальный)
```
Проведи полный аудит безопасности проекта. Ты — senior security engineer.
Проверь ВСЕ аспекты:
- Аутентификация: хеширование, сессии, rate limiting на login
- Авторизация: ownership checks в API, RLS на каждой таблице
- Ввод: серверная валидация, защита от SQL/XSS/command injection
- Секреты: нет ключей в коде, .env в .gitignore, серверные ключи только на сервере
- Rate limiting: auth, API, дорогие операции, регистрация
- Деплой: HTTPS, CORS, security headers, логирование
- Зависимости: audit, нет известных CVE в пакетах
- Edge cases: что если внешний API недоступен, что если webhook придёт дважды
Формат по каждой проблеме:
Уровень: КРИТИЧНО / ВАЖНО / РЕКОМЕНДАЦИЯ
Файл: путь:строка · Проблема: что не так · Риск: что может случиться · Фикс: конкретный код
```

## 3. GitHub Action — автопроверка PR

Anthropic предоставляет Action, который проверяет каждый Pull Request на уязвимости (анализирует только изменённые файлы, комментирует находки).

1. Добавь API-ключ в секреты репозитория: `Settings → Secrets → Actions → New secret → CLAUDE_API_KEY`.
2. Создай `.github/workflows/security-review.yml`:

```yaml
name: Security Review
permissions:
  pull-requests: write
  contents: read
on:
  pull_request:
jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}
          fetch-depth: 2
      - uses: anthropics/claude-code-security-review@main
        with:
          comment-pr: true
          claude-api-key: ${{ secrets.CLAUDE_API_KEY }}
```

> Action не защищён от prompt injection — используй только для доверенных PR. Включи «Require approval for all external contributors». Для этого пути нужен API-ключ (отдельно от подписки).
> ⚠️ Проверь актуальность имени экшена и синтаксиса перед использованием — детали могут меняться.

## 4. Своя команда под проект

`/security-review` универсален, но можно заточить под стек. Положи `.claude/commands/security-review.md` в проект и добавь свои проверки — например для российского контура (152-ФЗ, ЮKassa-вебхуки):
- RLS включена и протестирована на КАЖДОЙ таблице;
- серверные ключи не в клиентском коде;
- ЮKassa: подпись уведомлений проверяется (HMAC от секретного ключа);
- секреты платежей — только в серверных переменных окружения;
- preview-деплои не подключены к продакшн-БД.

Закоммить файл — вся команда получит одинаковую проверку.

## 5. Чеклист готовности перед продакшном

**Аутентификация:** пароли bcrypt/argon2 · сессии с TTL и инвалидацией · rate limiting на login · email-верификация · OAuth-редиректы валидируются.

**Авторизация:** RLS на каждой таблице (все 4 операции) · ownership check в каждом API · проверка пользователя на сервере, не на клиенте · нет лишних запросов в обход RLS.

**Ввод и данные:** серверная валидация на каждом эндпоинте · параметризованные SQL · HTML-экранирование · лимиты на размер загрузок · UUID вместо последовательных ID.

**Секреты:** .env в .gitignore · .env.example без реальных значений · серверные ключи только на сервере · публичные переменные без секретов · токены в httpOnly cookies · git-история чиста.

**Rate limiting:** auth 5/мин · API ~100/мин на пользователя · дорогие операции — лимит по плану.
