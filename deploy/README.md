# `deploy/` — образ и службы PMS на сервере

Что здесь: `Dockerfile` (один образ для приложения), `compose.yml` (`api`, `web` и `cloudflared`),
`cloudflared.example.yml` (образец конфига
туннеля для сервера), `server-bootstrap.sh` (первичная настройка сервера одной командой).
Порядок команд для владельца — `docs/ops/server-setup-2026-09-18.md`; общее ТЗ — `plans/server-kz-tz-2026-09-18.md`.

Правила, которые легко нарушить (все закреплены в `tests/unit/deploy-server.test.ts`):

- **`.env` — только в корне клона.** Оттуда его читают и compose (`../.env`), и `main.ts`, и `cli-check-env.ts`,
  и `prisma migrate deploy`, и скрипты сверки. Значения вписывает владелец (`SECURITY.md` §3).
- **Порты наружу не публикуются.** Наружу смотрит только туннель Cloudflare. Проверять службы
  изнутри сети compose: `docker compose -f deploy/compose.yml exec api ...`.
- **`API_HOST=0.0.0.0` и `--hostname 0.0.0.0` только внутри контейнера.** На машине владельца умолчание
  прежнее — `127.0.0.1`. Стойка ходит в API по имени службы (`APP_API_URL=http://api:3001`).
- **Сумма пулов меньше предела базы.** API — 5 соединений по умолчанию. При пределе меньше 20
  вписать `DATABASE_POOL_MAX=3` в `.env`.
- **Боевую миграцию делает владелец** (`AGENTS.md` §15), не образ и не служба: `migrate deploy`
  в `command` намеренно нет.
- **Выключатель ARI** — `scripts/ops/ari.sh stop|start|status` (сам понимает, что он под Docker;
  `ari-server.sh` — та же команда с явным режимом). Состояние — файл `deploy/ari.env`, переживает перезагрузку.
- Сборка образа и живая работа служб на сервере **не доказаны** до первого запуска — это записано в ТЗ.
