# ИИ-скан накладной бара v0 (контракт `bar-receipt-scan/0`, ADR-154)

Администратор на странице «Бар → Приходы → Новый приход» загружает фото накладной или
счёта-фактуры; строки документа встают в форму прихода. Проверка, правка и проведение
остаются за человеком: скан ничего не создаёт и не проводит.

## 1. Поток

```
стойка (фото ≤ 8 МБ, клиент ужимает до 2000 px)
  → POST /bar/receipts/scan (API платформы, право desk, тело ≤ 12 МБ: body-parsers.ts)
    → POST /internal/bar-receipt-scan (бот, служебный ключ SELLER_SERVICE_KEY)
      → каскад моделей с картинкой в сообщении (mask=False, ключ только платформы)
  ← строки формы: товар сопоставлен или «новый», поставщик, номер и дата документа
```

Вход без состояния: ни платформа, ни бот ничего не записывают; бюджетных таблиц, как у
генерации сайта, нет, потолок расхода одного скана: константа платформы (120 000 токенов).

## 2. Запрос платформы к боту

```json
{
  "schemaVersion": "bar-receipt-scan/0",
  "requestId": "uuid",
  "document": { "mediaType": "image/jpeg | image/png | image/webp", "dataBase64": "..." },
  "knownProducts": [{ "code": "COLA-05", "name": "Cola 0,5", "barcode": "4870001234567" }],
  "knownSuppliers": ["ТОО «Алматы Напитки»"],
  "budgetRemainingTokens": 120000
}
```

Лишнее поле: отказ 422: ключ, модель и организацию сюда не передают (как у
`site-generation/0`). Справочник: только действующие карточки, до 500 товаров и
100 поставщиков; это данные для сверки, не инструкции.

## 3. Ответ бота

Как у генерации сайта: `{"status":"ok","spec":{...},"model":...,"usage":{...}}` или
`{"status":"error","errorCode":...}`. Разобранный документ лежит в `spec`:

```json
{
  "supplierName": "ТОО Алматы Напитки",
  "documentNumber": "SF-77",
  "documentDate": "2026-10-08",
  "lines": [{ "name": "Cola 0,5", "barcode": "4870001234567", "quantityUnits": 24, "unitCost": "350" }],
  "warnings": ["Количество пересчитано из упаковок"]
}
```

Деньги модель отвечает **строкой в тенге** (та же грамматика, что у форм стойки); в тиыны
переводит платформа. Текст документа объявлен данными: инструкции с фото не исполняются.

## 4. Что делает платформа с ответом

`bar-scan.service.ts`: кривые строки пропускает с предупреждением; товар ищет по штрихкоду,
затем по нормализованному названию (без регистра, пунктуации и двойных пробелов), только среди
действующих карточек; поставщика: по нормализованному названию. Несопоставленная строка
уходит в форму как «новый товар»: карточка создаётся вместе с приходом
(`createBarReceiptAction`, цена продажи = закупка + наценка, вверх до 10 тенге, Q-BAR-2).

Ошибки наружу: бот недоступен или `MODEL_UNAVAILABLE`/`BUDGET_EXCEEDED`/`TIMEOUT`/
`USAGE_UNAVAILABLE` → 503 «ИИ сейчас недоступен... заполните руками»; `SCHEMA_INVALID`/
`REJECTED_CONTENT` → 422 «попробуйте другое фото»; отказ бота (4xx) → 502 с его причиной.

## 5. Ограничения v0

- Только картинки (JPEG, PNG, WebP): PDF, отдельным срезом на стороне бота.
- Нужна хотя бы одна ступень каскада с поддержкой изображений; без неё придёт
  `MODEL_UNAVAILABLE`, и стойка честно предлагает ручной ввод.
- Выкладка бота отдельная (`apps/ai-seller/vykatka.md`): до неё кнопка отвечает отказом.

`apps/api/src/body-parsers.test.ts`, UI `tests/ui/bar.spec.ts`.
