# Как Channex будет работать с нашей PMS — простыми словами

Источник: `site/guides/pms-integration-guide.md`, `site/api-v.1-documentation/{ari,bookings-collection,webhook-collection,channel-api}.md`
(скачано 07.09.2026). Написано 08.09.2026 для владельца. Технические детали — в Slice 4 плана.

## Одна картинка

```
   Booking.com   Trip.com   Agoda   Expedia   Hostelworld   Ostrovok
        │           │         │        │           │           │
        └───────────┴─────────┴────┬───┴───────────┴───────────┘
                                   │  (у каждого OTA свой язык; Channex говорит на всех)
                              ┌────┴────┐
                              │ Channex │  ← один посредник вместо шести интеграций
                              └────┬────┘
        ┌──────── 2. цены, остатки, ограничения (мы → Channex → OTA) ────────┐
        │                                                                     │
        │  ┌────── 3. брони, изменения, отмены (OTA → Channex → мы) ──────┐  │
        ▼  ▼                                                               │  │
   ┌───────────────┐   1. соответствие: наши категории и тарифы ↔ их комнаты и тарифы
   │  наша PMS     │
   │  88 ячеек     │   Правило проекта: домен про Channex не знает, с ним говорит
   │  тарифы       │   только пакет `packages/integrations/channex` (ADR-004).
   │  шахматка     │
   └───────────────┘
```

Сегодня ровно эту роль выполняет Exely Channel Manager. Мы меняем посредника, а не логику.

## Три потока, и что делаем мы

### 1. Настройка: «кто есть кто» (один раз, потом при изменениях)

- В Channex мы создаём **наш объект** (property), **5 категорий** (room types) и **тарифы**
  (rate plans) — прямо из нашей PMS по API, не руками в их кабинете.
- Channex запоминает соответствие: наша «Общая мужская комната» = их room type такой-то.
  Мы храним это в таблице `ChannelMapping`.
- Затем каждый OTA подключается к Channex через **Channel API**: создать соединение,
  указать ID нашего объекта в этом OTA (они известны, OBJECT.md §4), сопоставить тарифы,
  проверить, активировать. Соединение создаётся выключенным и ничего не шлёт, пока не
  нажали «активировать» — это и есть момент переезда канала (CUTOVER.md).

### 2. Наружу: цены, остатки, ограничения (ARI)

- Когда в нашей PMS что-то меняется — появилась бронь, освободилась койка, изменилась цена
  или стоп-продажа — мы **сразу** отправляем в Channex обновление, а Channex рассылает его
  во все подключённые OTA.
- Channex просит слать **остатки отдельно от цен**: остатки они обрабатывают первыми.
  Если изменений много — собирать пакетами раз в 30–60 секунд. Плюс **раз в ночь полная
  выгрузка** всего календаря, чтобы ничто не разошлось.
- Остаток по категории считаем мы: 36 коек мужского dorm минус занятые минус заблокированные
  на дату. Это и есть «availability». Из-за этого расчёт доступности (шаг 3.3 плана) должен
  быть готов раньше Channex.
- Цены: у нас на объекте отдельный тариф на канал («+35% для OTA»). В Channex это либо
  отдельные rate plans, либо один базовый с правилом наценки на соединении (`derived_option`).
  Выбор — при маппинге, решение владельца.

### 3. Внутрь: брони из OTA

- Гость бронирует на Booking.com → Booking.com сообщает Channex → Channex присылает нам
  **webhook** «есть новая ревизия брони».
- Мы забираем бронь из **Booking Revision Feed** (список всех ещё не подтверждённых нами
  ревизий), записываем её в журнал входящих событий (`ExternalEvent`, ADR-007) и только потом
  создаём/меняем бронь в нашей базе: категория, даты, гость, цена, а ячейку назначаем по правилу
  Q-094.
- После успешной обработки мы отправляем Channex **acknowledge** — «получили». Пока мы не
  подтвердили, Channex будет отдавать ревизию снова. Это защита от потери брони при сбое:
  сообщение сначала записано, потом обработано, и его можно обработать повторно.
- Изменение и отмена приходят тем же путём как новые ревизии той же брони.
- Дубль невозможен: у каждой ревизии свой ID, у нас на него уникальный ключ в базе.

### Что Channex делает сам при подключении канала

- Для Booking.com, Trip.com и Expedia — **подтянет уже существующие будущие брони**
  (`load_future_reservations`), это 157 из 182 наших будущих проживаний в OTA.
- Для Agoda, Hostelworld и Ostrovok — не подтянет; эти 25 проживаний мы берём из своего
  импорта из Exely и держим в базе до заезда.
- Bronevik и OneTwoTrip в Channex нет вообще — Q-096.

### Чего Channex не делает

- Не считает остатки и не решает, какую койку дать гостю — это наша PMS.
- Не хранит наших гостей и счета — только брони как пришли из OTA.
- Не переносит цены и ограничения из Exely — их мы загружаем сами (Slice 3).

## Порядок в нашем плане (Slice 4, неделя 4)

1. Клиент Channex в `packages/integrations/channex` по `api-reference.md`: ключ в заголовке
   `user-api-key`, JSON:API, 503 → повтор, `x-ratelimit-*`.
2. Создать на staging объект, 5 категорий, тарифы → сохранить ID в `ChannelMapping`.
3. Отправить полный ARI и увидеть его в кабинете staging.
4. Принять тестовую бронь (у Channex есть тестовые аккаунты Booking.com), пройти
   webhook → feed → запись в журнал → бронь в шахматке → acknowledge. Повторить с изменением
   и отменой. Доказать тестом: повторный webhook не создаёт дубль.
5. Прогнать сертификационные сценарии из интерфейса PMS (`pms-certification-tests.md`),
   отправить результаты в support@channex.io, дождаться созвона.

## Вопросы владельцу, которые здесь всплывают

- Q-094 — кто и по какому правилу назначает койку OTA-брони.
- Наценка OTA: отдельные тарифы (как сейчас в Exely) или правило `derived_option` в Channex.
- Судьба Bronevik и OneTwoTrip (Q-096).
- Redis для очереди отправки ARI и приёма webhooks в dev (BullMQ, ADR-011).
