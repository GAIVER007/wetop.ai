# Вход клиента бизнеса: предложение модели и подтверждения (Q-AUTH-1)

Статус: **ПРЕДЛОЖЕНИЕ, НЕ УТВЕРЖДЕНО.** Кода и миграций нет. Ответ владельца 16.10.2026: «клиенту нужен свой вход».
Подготовлено 17.10.2026 по `main` `1f9f39c3` и ветке `claude/auth-identity-1016`. Решения, которые нужны от владельца,
собраны в §7; до них ничего не строится.

## 1. Что есть сейчас

- Клиент салона и ресторана это `Customer` (`customers`), гость гостиницы это `Guest` (`guests`). Обе записи живут **внутри
  организации** (RLS по `organization_id`). Один и тот же человек в двух салонах разных владельцев это две разные записи.
- У `customers` телефон уникален в организации (частичный индекс `customers_organization_id_phone_key`), почта необязательна.
  У `guests` телефон и почта необязательны и не уникальны; у гостя есть паспортные данные (§3, §9).
- Входа у клиента нет. Он видит только публичные страницы: виджет брони гостиницы (`/w/book`), запись в салон и бронь стола
  с сайта (`/w/beauty/book`, `/w/food/reserve`), заявку (`/w/lead`), страницу мастера (`/specialists/:slug`), оценку
  официанта по QR (`/public/order-rating/:token`).
- Каналы, которыми платформа уже умеет писать: **почта** (Resend, письма входа и подтверждение брони гостиницы).
  **SMS-провайдера в проекте нет.** WhatsApp есть только у организаций с подключённым ИИ-продавцом, это номер самой
  организации, не платформы.
- Учётная запись сотрудника (`users`, `memberships`, `sessions`) отдельная, с паролем, куки `wetop_session`.

## 2. Главный принцип

Клиентский вход это **отдельный контур**, а не ещё одна роль сотрудника:

- отдельная таблица людей, отдельные сессии, отдельная кука и отдельный адрес;
- клиентская сессия никогда не проходит замок стойки (`SessionGuard`) и не получает членства в организации;
- сотрудник, который сам стрижётся в своём салоне, имеет два разных входа; автоматически они не склеиваются;
- клиент видит только **свои** записи и брони, только в белой проекции (как публичная страница мастера), без заметок
  бизнеса, меток VIP, паспортов, внутренних статусов и чужих людей.

## 3. Предлагаемая модель (названия предварительные)

```
client_accounts ──< client_links >── customers  (салон, ресторан; организация из карточки)
       │                       └──── guests     (гостиница; только брони, без документов)
       ├──< client_login_codes (одноразовые коды и ссылки, только хеши)
       └──< client_sessions    (свой ключ, своя кука)
```

### `client_accounts`: человек-клиент, один на всю платформу

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid | создаёт сервер |
| `phone` | varchar(16) NULL | E.164, уникален среди действующих |
| `email` | varchar(320) NULL | нижний регистр, уникален среди действующих |
| `phone_verified_at`, `email_verified_at` | timestamptz NULL | хотя бы один контакт подтверждён (CHECK) |
| `name` | varchar(200) NULL | как зовут, для приветствия |
| `locale` | varchar(5) | `ru`, `kk`, `en` |
| `status` | `ACTIVE`, `BLOCKED`, `DELETED` | удаления строки нет; `DELETED` обнуляет контакты |
| `privacy_version` | varchar | версия согласия на обработку данных |
| `created_at` | timestamptz | |

Без пароля: вход по одноразовому коду или ссылке (§4). Пароль клиенту не нужен и создаёт поддержку «забыл пароль».

### `client_links`: «эта карточка бизнеса моя»

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid | |
| `client_account_id` | uuid FK | |
| `organization_id` | uuid FK | по нему RLS: бизнес видит только свои связи |
| `customer_id` / `guest_id` | uuid NULL | ровно одно из двух (CHECK) |
| `linked_by` | `CLIENT_MATCH`, `STAFF_INVITE`, `BOOKING` | как связали (§5) |
| `created_at`, `revoked_at` | timestamptz | разрыв связи не удаляет строку |

Уникально: одна действующая связь на карточку. Карточка бизнеса (`Customer`, `Guest`) не меняется и остаётся данными
бизнеса; связь только открывает клиенту чтение.

### `client_login_codes` и `client_sessions`

- Код: 6 цифр, хеш, 10 минут, 5 попыток, одноразовый; ссылка-вход: случайный ключ, хеш, 15 минут, одноразовая.
- Пределы как в §13: 5 запросов в час на контакт, 20 в час с адреса; ответ на запрос кода всегда один и тот же
  (не раскрывает, есть ли такой клиент).
- Сессия: ключ только хешем, срок 30 суток с продлением при активности (клиент заходит редко, просить код каждый раз
  неудобно), «выйти везде», отзыв при блокировке и удалении.

## 4. Способ подтверждения

| Вариант | Что нужно | Плюсы | Минусы |
|---|---|---|---|
| **А. Код на почту** (рекомендую для первого этапа) | ничего нового: почта уже отправляется | без нового провайдера и денег, работает сразу | у клиентов салонов почта есть не всегда |
| Б. Код по SMS | выбрать провайдера в Казахстане (договор, цена за сообщение, отправитель) | телефон есть почти у всех карточек | новый провайдер и расходы: решение владельца |
| В. Код в WhatsApp | шаблон «authentication» в Meta, номер платформы | привычный канал | новый номер платформы, модерация шаблона, оплата Meta |
| Г. Ссылка из подтверждения брони | письмо брони (есть у гостиницы) | ноль лишних шагов: «Мои брони» из письма | только для тех, кто бронировал с почтой |

**Рекомендация:** этап 1: А и Г (почта, без новых провайдеров). Этап 2: Б после выбора провайдера владельцем, тогда
телефон станет основным контактом. Подтверждение по телефону без SMS (звонок, мессенджеры) не предлагаю: нет основы в проекте.

## 5. Как клиент получает свои записи (связывание)

Связь появляется только одним из трёх путей, и всегда **внутри одной организации**:

1. **Совпадение контакта** (`CLIENT_MATCH`): клиент вошёл и открыл сайт или виджет конкретного бизнеса; если в этой
   организации ровно одна действующая карточка с тем же подтверждённым телефоном или почтой, связь создаётся. Две и
   больше карточек: связи нет, клиент видит «обратитесь в салон», бизнес объединяет карточки сам.
2. **Приглашение из карточки** (`STAFF_INVITE`): сотрудник нажимает «Пригласить в личный кабинет», ссылка уходит на
   контакт из карточки.
3. **Новая запись** (`BOOKING`): клиент записался, будучи вошедшим: карточка создаётся или находится и сразу связывается.

Никогда: по имени, по совпадению в **другой** организации без захода клиента в этот бизнес, по номеру организации или
карточки из адреса. Так человек с чужим (переданным оператором) номером не увидит список всех салонов, где этот номер
когда-то был.

## 6. Что клиент видит и делает

| Направление | Видит | Делает (этап 1) |
|---|---|---|
| Салон | свои записи: дата, время, услуга, мастер (публичное имя), филиал, цена, статус | записаться снова тем же путём, что сайт |
| Ресторан | свои брони столов: дата, время, гостей, филиал, статус | забронировать снова |
| Гостиница | свои брони: даты, категория, сумма, статус оплаты | забронировать снова |
| Все | профиль: имя, контакты, язык; «выйти везде»; удалить кабинет | |

Не видит никогда: заметки бизнеса, VIP, дату рождения из карточки (если сам не указал), паспорт и документы гостя,
сотрудников кроме публичного имени мастера, чужих гостей брони, внутренние причины отмены.
Отмена и перенос из кабинета: этап 2, только по уже существующим правилам отмены направления (новых правил не вводить).

Бизнес видит в карточке метку «есть личный кабинет» и может разорвать связь; контактов кабинета сверх карточки не видит.

## 8. Что изменится в коде после утверждения (для оценки, не делается сейчас)

- `DATA_MODEL.md`: новый раздел с таблицами §3 (после утверждения), миграции с `down.sql`, RLS для `client_links`;
  остальные таблицы `ENABLE` без доступа `wetop_app`, как `users`. Миграции на рабочей базе применяет владелец.
- API: свой модуль `client-auth` (запрос кода, вход, выход, сессии) и `client-portal` (мои записи), своё право `client`
  в таблице прав маршрутов; замок стойки клиентские ключи не принимает (тест на это).
- Стойка сотрудников не меняется; карточка клиента получает метку и кнопку «Пригласить» (чат №1).
- Проверки: разные контексты браузера для клиента, сотрудника и владельца; клиент А не читает записи клиента Б по
  номеру; клиентский ключ не проходит ни один маршрут стойки; повтор кода, просрочка, перебор, удаление.
