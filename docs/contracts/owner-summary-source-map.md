# Карта источников общей главной: проверено по исходникам

Статус: инженерная карта источников, не production acceptance. Фактические revenue/receipts/workload уже читаются адаптерами owner-money и workload; недоступность и неполное покрытие остаются явными. Точный текущий DTO и ограничения — `owner-summary.md`.

## Расходы

Новый `apps/api/src/finance/owner-summary.ts` читает COMPLETED EXPENSE из restaurantCashOperation для BEAUTY/FOOD_SERVICE и cashOperation для HOSPITALITY. Нельзя добавлять бюджеты маркетинга, суммы приёмок, себестоимость или выплаты повторно. В гостиничной кассе историческая валюта не доказана: текущее значение Property/Location не заменяет immutable snapshot, потому ответ PARTIAL честнее ложной суммы.

При EXPENSE_LINKS_ENABLED=1 сводка обогащает эти же источники статьёй через settlement/document/category, с tenant/location scope; сумма документа не участвует. Архивные статьи читаются с текущим именем. При выключенном флаге таблицы связей не запрашиваются. Неклассифицированные суммы остаются «Без статьи». Категории каждой доказанной валюты в сумме равны каноническому итогу; связанный гостиничный cash с недоказанной валютой остаётся unresolved. Реальный локальный PostgreSQL-проход: `tests/runs/logs/2026-10-16T09-39-06Z-integration-f79b.log`, 5/5, exit0, без изменения кода во время прогона. Это не production reconciliation и не полный integration-набор.

## Ресторан

`apps/api/src/food-service/restaurant.service.ts::periodReport`:
- Выручка заказов: restaurantOrder.total, status CLOSED, дата closedAt.
- Выручка бара: barSale.totalRevenue, status POSTED, дата createdAt, отдельное поле barRevenueMinor по ADR-182.
- Оплаты заказов: restaurantPayment.amount, status COMPLETED, дата paidAt.
- Себестоимость: kitchenStockMovement CONSUMPTION/SHORTAGE/CONSUMPTION_RETURN, отдельно от денежных расходов.

Не вызывать periodReport как универсальный адаптер без проверки валют: он выдаёт s.currency и агрегирует заказы суммарно, поэтому новый общий контракт обязан сохранять доказанную историческую валюту источника. Не складывать barRevenueMinor с поступлением кассовой операции той же barSale повторно. Текущий день ограничивать generatedAt, не будущей полуночью; предыдущий период сравнивать на равной отсечке.

## Салон

`apps/web/src/app/today/beauty-today.tsx` ссылается на `loadBeautyToday` и канон Q-252: сумма снимков цен завершённых записей DONE. Это не фактические оплаты, не ресторанные CLOSED заказы и не сумма всех записей. Текущий экран использует дневной ответ appointments, его нельзя выдавать за полную неделю/месяц без доказанной полноты выборки. Мастер на смене не равен фактической исторической доступной мощности.

## Гостиница

`apps/api/src/dashboard/dashboard.repository.ts::charges` описывает начисления без сторно по service_date. `payments` описывает COMPLETED по дате события. Текущий private propertyId()/timezone() привязан к LUXX_APARTS_PROPERTY.name. Для общей главной этот адаптер нельзя переиспользовать неизменённым: нужен явно проверенный scope Property выбранного Location. Та же проблема относится к chessboard вызову, если он не принимает проверенный объект.

`apps/api/src/hotel/organization-summary.ts` полезен как пример tenant/visibleLocations/canAt фильтрации, но НЕ готовая универсальная главная:
- BEAUTY возвращает UNAVAILABLE.
- Гостиничные расходы присваиваются текущей валюте Location, что не доказывает историческую валюту.
- Оплаты гостиницы группируются по payment.currency.
- Ресторанные поступления составляются из restaurantPayment и POSTED barSale, а не суммы всех кассовых входов.

## Приёмочные равенства

1. Расходы каждой валюты = сумма уникальных действующих EXPENSE; сумма категорий = этот итог. Все периоды и графики используют один набор источников и одну отсечку.
2. Оплата поставщику в старом экране и settlement нового документа должны ссылаться на одну кассовую операцию; долг приёмки и документа совпадает.
3. Выручка и поступления могут различаться законно; одинаковые подписи не должны скрывать разные определения.
4. Итог графика равен карточке той же валюты. Не делать график нулевым там, где источник UNAVAILABLE/PARTIAL.
5. Нет универсального процента загрузки для разных единиц мощности. Внутри одной сопоставимой группы: сумма занятой мощности / сумма доступной, не среднее процентов. История неполная обозначается явно.
6. Нельзя возвращать данные первого попавшегося филиала, объекта по константе или другого tenant, даже если числа выглядят правдоподобно.

Документ отражает чтение исходников, не результаты production reconciliation. Следующий проход должен подтвердить строки источников → API → карточки/график на изолированной базе и браузере.
