# TZ2.1 D: общий resolver рабочего времени

17.10.2026. Срез от frozen `0766123d`, без схемы, миграций и новых ролей.

## Контракт

`resolveWorkingTime` принимает UTC instant, необязательный конец услуги, timezone выбранного филиала, supported/employeeActive/worksHere, все интервалы недельного шаблона и общие календарные TimeOff сотрудника. Приоритет отказов: UNSUPPORTED, EMPLOYEE_INACTIVE, NOT_ASSIGNED, TIME_OFF, NO_SCHEDULE, OUTSIDE_WORKING_HOURS. Начало интервала включительно, конец невключительно для присутствия; услуга может закончиться ровно при закрытии. Полное окно услуги должно поместиться в один интервал одного локального дня. Перерыв не склеивается. Порядок интервалов не влияет. Отсутствия включают обе календарные даты в timezone конкретного филиала.

Реальные потребители: Food employees/onShift использует все интервалы, назначения, статус и TimeOff; Beauty fitsSchedule и существующий freeBeautySlots используют общий resolver. Подсчёт затронутых отсутствием записей использует timezone собственного филиала Appointment, включая исторические назначения. Существующие appointments не перемещаются, не отменяются и не обновляются.

## Сохранение недели

Beauty, Food и Employee Portal требуют исходный expectedRevision, включая пустую неделю. Общий SHA-256 token вычисляется из точного employees.updated_at (6 microseconds) и упорядоченных исходных строк WorkingHours, включая id, в одном SQL snapshot. Каждое успешное сохранение, в том числе пустая неделя, транзакционно продвигает существующий timestamp. Это предотвращает empty ABA; контактные и межфилиальные недельные формы консервативно конфликтуют после изменения этого сотрудника. Проверка выполняется в существующей транзакции writer до замены строк. Невалидный/отсутствующий token отклоняется, устаревший даёт conflict. Остальные legacy revision-контракты не изменены. Fixtures передают token исходного чтения.

Food передаёт token через форму, server action и API client, comparison перечитывает Food, а не Beauty. Beauty/Food и Portal сохраняют локальный черновик при отказе. Чтение для сравнения не заменяет token; отдельная кнопка принятия серверной недели заменяет черновик. Portal server action не подменяет исходный token свежим token предварительного чтения. Beauty loader возвращает строковый fallback ошибки без ослабления exactOptionalPropertyTypes.

## Ограничения

Frontend wire tests проверяют исходный код, не заменяют интерактивный browser concurrency test. Поведение DST/невалидных timezone отдельно не расширялось. Resolver не поддерживает overnight интервалы и не задаёт Hotel staffing. Подсчёт отсутствий выполняет запросы по филиалам для каждого TimeOff; это корректность, не оптимизация больших историй. После успешного Portal save используется token именно принятой транзакции, соответствующий локальным controlled days; последующий чужой save приводит к409. При конфликте сравнение не меняет ввод/token, отдельное принятие серверной недели меняет оба. Не изменены Employee contact/C methods, payroll formulas и production.
