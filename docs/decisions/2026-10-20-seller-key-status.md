# Ключ модели ИИ-продавца: состояние и расход вместо баланса

Дата: 20.10.2026. Ветка `claude/seller-key-status`. Основание: поручение владельца «при настройке ИИ-продавца
должно быть поле для ввода ключа и там должен отображаться баланс».

**Проблема.** 20.10.2026 живой диалог через песочницу показал: продавец на каждый вопрос гостя отвечал
«администратор свяжется». Причина: на ключе OpenAI организации кончились деньги (HTTP 429
`insufficient_quota`, код `credit_balance_exhausted`), ключ платформы при этом работал. Проверка ключа в стойке
этого не видела: она спрашивала только список моделей, а он отвечает 200 и на пустом счёте. Алерт `llm_down`
уходил на платформу без кода ответа, владельцу гостиницы ничего не показывалось. Поле для ключа в стойке уже
было («ИИ-продавец → Подключения → Модель ИИ»).

**Варианты.**
1. Показать баланс счёта поставщика. У OpenAI нет API, который отдаёт остаток для обычного ключа: эндпоинты
   кабинета требуют сессию браузера, а API расходов требует ключ администратора и даёт только траты.
2. Показать состояние ключа (работает, закончились деньги, ключ не принят, предел запросов) по последнему ходу
   модели и по проверке, плюс расход за месяц по собственному учёту ответов продавца.
3. Владелец вводит «пополнил на N долларов», а остаток считается как N минус наш расход. Оценка расходится со
   счётом поставщика (чужие траты с того же ключа, цены, кэш), и её легко принять за точную.

**Решение.** Вариант 2. Проверка ключа делает ещё и вызов модели в 1 токен, поэтому пустой счёт виден до
сохранения и по кнопке «Проверить» с пустым полем (проверка сохранённого ключа). Каждый ход модели пишет
состояние ключа организации; смена или снятие ключа его сбрасывает. На экране: бейдж состояния, что делать,
время последней проверки и строка «Расход за месяц: ответов, токенов» с пометкой, что это учёт продавца, а не
счёт провайдера. Стоимость показывается, только если у продавца заданы цены `LLM_PRICES`; без цен в долларах не
пишется ничего. В алерте `llm_down` появилась причина словами («на счёте провайдера закончились деньги»).

**Причина.** Владельцу нужно знать одно: отвечает ли продавец гостям и почему нет. Состояние ключа отвечает на
это точно, а «баланс» по варианту 3 был бы выдумкой с видом точной цифры.

**Последствия.** Модель данных стойки и бота не меняется: состояние лежит в Redis бота (`llm:keystate:<org>`,
30 суток), расход считается запросом по сообщениям (`src/jobs/usage_report.collect`). Новый маршрут бота
`GET /seller/organizations/{org}/llm-usage` (служебный ключ платформы) и стойки `GET /ai-seller/llm-usage`
(право `seller`). Проверка ключа стоит доли цента за вызов и уже ограничена часовым пределом. Алерт по-прежнему
уходит на платформу, оповещение владельца гостиницы в стойке (бейдж или письмо при «нет денег») не сделано:
это следующий срез, если понадобится. Остаток денег владелец смотрит в кабинете провайдера.
