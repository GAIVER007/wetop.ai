# 2026-10-22 Модификаторы блюд и деление счёта в ресторане

Статус: УТВЕРЖДЕНО владельцем 22.10.2026 (ответ «Да, оба: план + миграция + экраны»).
Ветка `hermes/fmod-20261022`. Модель: DATA_MODEL §33.7, миграция 144 (`20261022000144_menu_modifiers_split`).
План: `plans/menu-modifiers-split-2026-10-22.md`.

## Проблема

1. Гость заказывает «Капучино, большой, на овсяном, без сахара». Сейчас размер и добавки пишут текстом в комментарий
   строки, цена не меняется, кухня и бар читают свободный текст, отчёт не знает, сколько принесли добавки.
2. Компания из четырёх гостей платит каждый за себя или поровну. Сейчас частичная оплата есть, но сумму каждого гостя
   кассир считает в уме, и ничто не мешает принять оплату за одно и то же блюдо дважды.

## Варианты

Модификаторы:

- А) Только текст в `restaurant_order_items.notes` (как сейчас). Цена не меняется. Отклонено.
- Б) Группы модификаторов бизнеса + связь с блюдом + снимок выбора у строки заказа отдельной таблицей.
- В) То же, но снимок выбора jsonb-полем в строке заказа.

Деление счёта:

- 1) Только «поровну на N» через существующую частичную оплату (без изменения БД).
- 2) Оплата по позициям: связь платёж ↔ строка заказа с запретом второй оплаты строки.
- 3) Оба режима.

## Решение

**Б + 3.**

- Группа модификаторов принадлежит **бизнесу** (`business_id`), как категории и блюда меню (§33.1: меню общее для
  сети). В предложенной модели было `location_id`; по коду меню живёт на уровне бизнеса, поэтому группа тоже.
- `menu_modifier_groups`: имя, `min_select`, `max_select`, порядок, `active`. Отдельного `required` нет:
  «обязательная» = `min_select >= 1`, одно правило вместо двух, которые могут разойтись. Радио в окне выбора, когда
  `max_select = 1`, иначе галочки.
- `menu_modifiers`: имя, `price_delta` (bigint minor, может быть отрицательной: «Маленький −200»), порядок, `active`.
  Модификаторы не удаляются, только выключаются (снимок строки сохраняет ссылку).
- `menu_item_modifier_groups`: какие группы у блюда и в каком порядке (PK блюдо+группа).
- **Снимок выбора отдельной таблицей** `restaurant_order_item_modifiers` (`order_item_id`, `modifier_id` NULL,
  `group_name`, `name`, `price_delta`), а не jsonb. Причины: FK и CHECK на значения, RLS через строку заказа как у
  соседей, отчёт «сколько продали добавок» одним запросом без разбора JSON, кухня получает список, а не строку.
- Цена строки = цена блюда + сумма `price_delta` выбранных, **заморожена в `restaurant_order_items.price`** при
  добавлении строки (как цена блюда сейчас). Цена строки не может стать отрицательной (400 по-русски).
- Комментарий к позиции: существующий `restaurant_order_items.notes varchar(500)`, новой колонки нет.
- Одинаковое блюдо с разными добавками или комментарием это разные строки заказа. Ключ строки при правке состава
  (дозаказ) = блюдо + выбранные модификаторы + комментарий.
- Обязательная группа без выбора, больше `max_select`, модификатор не из групп этого блюда (в том числе чужого
  бизнеса или выключенный) = 400 с текстом по-русски («Выберите: Размер»).
- **Оплата по позициям**: `restaurant_payment_items` (`payment_id`, `order_item_id`, `amount`, `released_at`). Сумма
  платежа = сумме строк (цена × количество). Строка оплачивается целиком. Частичный уникальный индекс
  `(order_item_id) WHERE released_at IS NULL`: одна строка не может быть в двух действующих платежах, это держит база,
  а не только API. Аннулирование платежа (возврат до закрытия) триггером ставит `released_at`, строки снова свободны.
  Оплаченную строку нельзя убрать из заказа (триггер на удаление действующей связи + понятный отказ API).
- **Поровну на N**: без новых таблиц. Домен `splitEvenly(остаток, N)`: N сумм, остаток тиынов первому гостю. Каждая
  часть проводится обычной частичной оплатой. После оплаты части остаток делится на оставшихся гостей.
- Режимы можно смешивать: оплата по позициям проверяет и свободные строки, и общий остаток (`orderPayment`).
- Права: группы и модификаторы меняет право `property` (как меню). Видят все, у кого есть меню на чтение (`orders`),
  в том числе официант: блюдо в меню отдаёт свои группы. Оплата по позициям под `desk` (как оплата).
- Склад: модификаторы техкарты не имеют и склад не списывают (вне объёма, отдельный вопрос при необходимости).

## Последствия

- Миграцию 144 на рабочей базе применяет владелец (backup, `migration.sql`, проверка, затем выкладка кода). Миграция
  смешанная (DDL + GRANT/REVOKE): строки прав скопированы в `scripts/ops/restore-mixed-domain-grants.sql`.
- Откат `down.sql`: снимает таблицы и триггеры. Теряются группы модификаторов и разбивка платежей по строкам; цены строк
  уже заморожены в `restaurant_order_items.price`, суммы заказов и платежи остаются верными.
- Пункт меню не нужен: вкладка «Добавки» внутри экрана «Меню».
