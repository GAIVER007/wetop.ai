# 2026-10-22 Официант с телефона, бар и кухня по станциям

Статус: УТВЕРЖДЕНО владельцем 22.10.2026 (голосом 21.10.2026 постановка, 22.10.2026 «да» на изменения БД и прав).
Ветка `hermes/pwait-20261022`. Модель: DATA_MODEL §33.6, миграция 142. План: `plans/waiter-stations-2026-10-22.md`.

## Проблема

Владелец: «Официант через своё приложение, через личный кабинет, с телефона: подошёл к столику, принимает заказ,
вбивает сразу в приложении, выбирает напиток, чай, еду, закуски, нажимает отправить. Отправка идёт сразу в разные
категории: бар получает бармен свой заказ, кухня получает свой заказ».

Сейчас: заказ принимает только STAFF («администратор», видит кассу и отчёты), статус один на весь заказ (напиток готов =
весь заказ «Готово»), бар узнаёт напитки по регулярке названия категории, кухня видит и напитки. У брони стола нет
ответственного (Q-CALENDAR-2026-10-17).

## Варианты

- Права: А) новое право `orders` для EMPLOYEE в ресторане; Б) должности с правами как в салоне (большой модуль).
- Станции: 1) регулярка по названию (как было); 2) поле станции у категории + снимок и статус у строки заказа.

## Решение

- А + 2. Миграция 142: `menu_categories.station` KITCHEN|BAR (BAR заполнен по прежней регулярке),
  `restaurant_order_items.station/status/ready_at`, `restaurant_reservations.employee_id`.
- Статус заказа выводится из строк; кухня и бар двигают свои строки, склад списывается по строке при «Готово» один раз.
  Прежнее действие со статусом заказа целиком двигает все строки.
- Право `orders`: у всех ролей стойки и у EMPLOYEE. EMPLOYEE в ресторане: экран «Принять заказ» `/waiter` (столы →
  меню → корзина → «Отправить»), свои открытые заказы со статусом позиций, «Подано», бронь стола. Официант заказа
  принудительно = свой сотрудник (по `employees.user_id`), чужие заказы ему недоступны. Касса, оплата, отчёты,
  зарплата других, гости остаются закрыты.
- `/kitchen` показывает только строки KITCHEN, `/drinks` только BAR, кнопки «Принять / Готово» по строке, обновление
  каждые 15 секунд. В «Меню» у категории выбор «Кухня / Бар».

## Последствия

- Миграцию 142 на рабочей базе применяет владелец (backup, `migration.sql`, проверка, затем выкладка кода). Откат
  `down.sql` теряет станции и статусы строк, статус заказа остаётся.
- Q-CALENDAR-2026-10-17 закрыт.
