# 2026-10-23 Способы оплаты филиала салона и ресторана

Статус: принято владельцем 23.10.2026 («Да, делай по этой схеме»). Ветка `task/branch-payment-methods-20261023`.

## Проблема

Аудит вертикалей 22.10.2026: «Добавить способ оплаты» есть только у гостиницы (§21.6, таблица привязана к объекту).
У салона и ресторана способы зашиты списком из шести (`FOOD_PAYMENT_METHODS`), убрать ненужный (например Halyk)
нельзя, кассир видит все шесть в каждой форме.

## Варианты

1. Привязать `payment_method_settings` к филиалу вместо объекта: правка таблицы гостиницы, её RLS и всего кода §21.6.
2. Своя таблица филиала `branch_payment_method_settings`, гостиница не трогается.
3. Настройка в JSON у `locations`: без истории, без CHECK, без RLS отдельной строки.

## Решение

Вариант 2. Таблица (филиал, способ, включён, порядок), шесть способов, умолчания без строк, экран тот же, что у
гостиницы (`PaymentMethodsForm`, «Убрать», «Выше/Ниже», «Добавить способ оплаты»), адрес `/branch-payment-methods`,
карточка «Система → Способы оплаты» в хабе `/settings`. Доменные функции общие с §21.6, набор передаётся параметром.

## Причина

Гостиница работает и проверена (§21.6, ADR-185), её не трогаем. Аддитивная миграция откатывается удалением таблицы,
деньги не меняются. Умолчания без строк дают нулевое изменение поведения после выкладки.

## Последствия

- Выключенный способ отклоняется сервером в местах приёма денег; формы показывают только включённые. Расход и
  перевод «из» способа, возвраты и сверка работают по любому способу.
- Миграция 151 применяется владельцем на рабочей базе до выкладки кода (без таблицы новый API отвечает ошибкой).
- Новые способы со своими названиями (вариант Б Q-295) не входят: набор системный.
