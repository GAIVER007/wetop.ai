# Голосовая бронь: ответы владельца по салону и ресторану (23.10.2026)

Продолжение `docs/decisions/2026-10-23-voice-booking-answers.md`. План: `plans/voice-booking-slices-2-3-2026-10-23.md`.

## Проблема
План срезов 2 и 3 ждал четырёх ответов (стол в ресторане, «любой мастер» в салоне, порядок, статус и лимит по телефону у гостиницы).

## Решение (слова владельца 23.10.2026)
1. **Ресторан.** Агент бронирует, если видит, что место свободно. В бронь вносит данные гостя: имя, номер телефона и комментарий.
   Моё уточнение «видит, что место свободно»: есть период обслуживания, подходят правила брони филиала (горизонт, максимум гостей),
   и есть хотя бы один стол нужной вместимости без пересечения по времени с учётом буфера. Стол агент гостю не назначает и не называет,
   стол назначает администратор.
2. **Салон.** Запись либо к свободному мастеру, либо к тому, к кому хочет гость. Агент должен знать, какой мастер какие услуги оказывает
   (справочник «мастер и его услуги» в API голоса). Данные клиента: имя, телефон, комментарий.
3. **Порядок.** Салон, ресторан, гостиница (гостиница сделана: PR 791).
4. **Гостиница.** Q-VOICE-9: оставляем пометку «Ожидает подтверждения администратора» вместо `TENTATIVE`. Q-VOICE-10: хэш телефона для суточного лимита
   добавляется предложением в `DATA_MODEL.md` (утверждение отдельно).

## Причина
Салон и ресторан не требуют нового статуса: бронь по умолчанию `BOOKED`, то есть «ожидает подтверждения»; стол в ресторане и так назначает администратор.

## Последствия
- Срез 3 (салон) и срез 2 (ресторан) строятся тонким слоем поверх путей форм сайта (`site-forms`), с источником `VOICE` и таблицей котировок `voice_booking_quotes`.
- Отклонение от утверждённой модели: `voice_booking_quotes` хранит внешний идентификатор звонка текстом, а не внешним ключом на `voice_calls`, потому что события звонка
  уходят из воркера через очередь и могут прийти позже первой котировки. Связь со звонком по паре (агент, внешний ID звонка).
