# Закрытие предоплаченного ресторанного заказа

Дата: 25.10.2026. Срез принятого mobile-product-roadmap, пункт 5 restaurant-completion.

Проблема: полная оплата до подачи не закрывает заказ автоматически после последующей подачи. Существующий сервер разрешает desk-переход SERVED -> CLOSED при точной полной оплате.

Варианты: автоматически повторять закрытие с новой версией; явно запросить закрытие с версией показанного заказа. Выбран второй вариант: после потерянного ответа нужно обновить заказ и проверить результат, а не незаметно выполнять новую команду.

Gateway food/close принимает только orderId и expectedUpdatedAt. Фиксирует expectedStatus=SERVED и status=CLOSED, передаёт исходные bearer/scope в существующий orders/:id/status. Сервер остаётся источником прав, проверки полной оплаты и актуальности версии. Отдельный MOBILE_ORDER_CLOSE_ENABLED выключен по умолчанию. Клиент не может выбрать иной переход или передать дополнительные поля. Не включает production gateway и не меняет финансовых правил.

Доказательства: RED 2026-10-25T15-34-25Z-unit-e85d (3 новых теста получают 404); GREEN 2026-10-25T15-35-03Z-unit-2682 (38/38). Проверены исходная версия, фиксированный переход, bearer/scope, сохранение 403/409, отключённый флаг, запрет GET/лишних полей и отсутствие повтора после потери ответа. Это unit-доказательство, не проверка реальных RLS или базы.

Следующий шаг: подключить AccessApi/session и явное подтверждение в карточке полностью оплаченного SERVED-заказа. Затем проверить весь цикл на изолированной синтетической базе. Этот коммит добавляет только gateway; пользовательская кнопка ещё не подключена.
