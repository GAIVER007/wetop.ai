# Подготовка мобильного платежа

Продолжение утверждённого ресторанного плана. Серверные финансовые правила, модель БД и права не меняются.

Способы оплаты читаются через существующий GET food-service/payment-methods с bearer и scope. Mobile gateway отдаёт только method/enabled/sortOrder, не добавляет методы по умолчанию и отвергает некорректные/повторяющиеся методы. Клиент предлагает только enabled в серверном порядке. Доступ остаётся серверным desk, обычный EMPLOYEE не становится кассиром из-за названия должности.

Введённая сумма разбирается строкой в bigint minor units с двумя десятичными знаками по существующему контракту. Дробный float не используется. Перед JSON числом проверяются положительность, остаток и Number.MAX_SAFE_INTEGER. Это предварительная проверка формы, окончательную сумму и возможность оплаты проверяет сервер внутри транзакции.

Платёж хранится отдельно от попытки создания заказа. PendingPaymentStore сохраняет orderId, amount, method, idempotencyKey и ожидаемую валюту. Один слот на окружение, аккаунт, организацию, бизнес и филиал. Native adapter использует UUID v5 namespace и UUID v4 ключ, SecureStore WHEN_UNLOCKED_THIS_DEVICE_ONLY. Запись ограничена 1500 ASCII символами, записывается одной операцией и перечитывается до разрешения отправки. Web fallback в память отсутствует. Результат неизвестен: исходная запись сохраняется. Неверный контекст, повреждённая запись и незавершённый платёж запрещают новую попытку. Операции экземпляров одного слота сериализованы в процессе.

Освободить слот можно только совпадающим acknowledge после валидного серверного подтверждения; удаление перечитывается. Сам store сетевых действий не выполняет. В этом срезе контроллер платежа, POST gateway и UI ещё не подключены. Проверки синтетические, они не заменяют испытание реального Keychain/Keystore, перезапуска ОС и полного денежного сценария. Никакие деньги не проводились, публичные флаги не включались.

Доказательства: RED списка методов 2/31 (2026-10-25T14-52-07Z-unit-99b6), RED отсутствующих модулей payment-input/pending-payment (2026-10-25T14-52-33Z-mobile-2011 и 2026-10-25T14-54-23Z-mobile-8d07). GREEN gateway 31/31, mobile 84/84 (2026-10-25T14-56-06Z-mobile-fa9d), mobile/web types и lint. Проверены предел безопасного целого, запрет округления, переплата, пустые серверные настройки, параллельные экземпляры, неудачная запись, чужой контекст и непрошедшее удаление.

## Денежный шлюз

POST mobile/v1/food/pay передаёт только валидный orderId и существующий parseFoodPayment в food-service/orders/:id/payments. Отдельный MOBILE_ORDER_PAYMENT_ENABLED выключен по умолчанию. Шлюз не назначает кассовые права: исходные bearer/scope доходят до серверного desk. Разрешённый метод, остаток, закрытие SERVED и повтор по ключу по-прежнему проверяет существующий API. Сумма после shared parser остаётся safe integer при сериализации. GET для денежной команды запрещён, неизвестные поля и произвольный путь не допускаются. Автоматических повторов нет; потерянный или некорректный ответ остаётся unknown, без объявления платежа успешным. AccessApi/SessionController используют тот же проверенный контекст и отсечение поздних ответов. Контроллер подтверждения и интерфейс оплаты подключаются отдельным следующим срезом.
