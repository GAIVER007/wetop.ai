# Мобильная подача готовой позиции

Продолжение утверждённого ресторанного сценария, без новых серверных прав, финансовой логики или модели данных.

Проблема: после создания заказа официанту нужно отметить готовую позицию поданной, сохранив проверку принадлежности и версии заказа.

Решение: узкий POST mobile/v1/food/serve принимает orderId, itemId и исходный expectedUpdatedAt. Статус всегда SERVED; передать READY, COOKING или произвольный путь нельзя. Запрос передаёт только bearer и scope в существующий orders/:id/items/:itemId/status. Сервер сохраняет waiterSelf, scope, блокировку заказа и optimistic concurrency. Gateway не назначает права по названию сотрудника.

Операция отдельно выключена по умолчанию через MOBILE_ORDER_SERVE_ENABLED. Никакие публичные флаги не включались. В UI действие доступно у READY-позиций незавершённого заказа. Одновременно выполняется одна команда. При ошибке или неизвестном результате повтор запрещён до явного обновления списка и открытия заказа. После подтверждения проверяются ID заказа и SERVED целевой позиции. Новый статус и версия приходят с сервера. Устаревший ответ другого контекста отбрасывает SessionController.

Альтернатива автоматического повторения с новой версией отклонена: она скрывает конфликт с другим сотрудником. Новый механизм идемпотентности не требуется для этого среза, поскольку версия защищает существующую команду, а клиент не повторяет её автоматически. Подача не является оплатой или фискализацией.

Проверки: RED gateway 4/28 (2026-10-25T14-38-44Z-unit-6e05), RED UI отсутствующего компонента (2026-10-25T14-39-46Z-mobile-9c0f). GREEN gateway 29/29, mobile 78/78, типы web/mobile, lint, Expo export iOS/Android/Web. Тесты gateway используют mock upstream и проверяют сохранение отказа 403; они не заменяют отдельную интеграционную проверку RLS или запуск на физическом устройстве.
