## Текущая серверная выкладка: порядок проверки и отката

1. Проверить SSH-host key, адрес сервера и метки работающих контейнеров WETOP.
   Не отключать проверку подлинности и не выбирать соседний проект по похожему имени.
2. В найденном клоне проверить чистое дерево; сохранить SHA предыдущей версии,
   ID образов API/web и резервные теги образов. `.env` и конфигурацию туннеля
   сохранить в закрытой серверной резервной копии, не выводя значения в журнал.
3. Получить одобренный `main` через `git fetch` и fast-forward. Сверить SHA с
   проверенным CI, убедиться, что нет новых неприменённых миграций. Эта приёмка
   не разрешает production migration, изменение схемы или переключение каналов.
4. Собрать `deploy/Dockerfile`, затем обновить **только API/web** существующего
   Compose project. Туннель, `.env`, выключатель ARI и фоновые настройки сохранить.
   Запуск посторонних Compose-проектов не входит в выкладку.
   Регистрация: по ADR-147 публичная self-service регистрация открыта. На сервере должно быть явное
   `REGISTRATION_OPEN=1`. Проверка после выкладки: `/auth/options` отвечает `registrationEnabled: true`, а на wetop.ai
   «Получить доступ» показывает форму создания аккаунта. Сайт не обещает срок или условия trial.
   Приглашения работают при любом значении. Отдельный `APP_REGISTRATION_OPEN` не нужен.
   API в production при старте проверяет роль базы (SEC-1a): без `DATABASE_APP_URL` или с ролью `postgres`/суперпользователем
   он не запускается. Осознанный выход — `RLS_DISABLED=1` (только откат по `docs/ops/rls.md`, в журнал пишется предупреждение).
   Окно входа и регистрации на wetop.ai (ADR-100) ходит на `app.wetop.ai/api/site-auth/*`. Стойка отвечает только
   источникам из `SITE_ORIGINS` (через запятую); пусто — `https://wetop.ai` и `https://www.wetop.ai`, для боевого
   сервера этого хватает. Проверка после выкладки: `curl -si -X OPTIONS -H 'Origin: https://wetop.ai'
   https://app.wetop.ai/api/site-auth/login` → 204 и `access-control-allow-origin: https://wetop.ai`; с чужим `Origin` — 403.
5. Доказать версию по SHA клона, ID запущенных образов и `BUILD_ID` Next из
   контейнера, затем проверить внутренний `/health` с базой, публичный вход,
   отказ анонимному запросу и чтение основных экранов под сотрудником.
   HTTP 200 без проверки содержимого или перенаправления недостаточен.
6. При неуспехе вернуть предыдущий commit и сохранённые образы, пересоздать
   API/web без новой сборки, повторить health и вход. Поскольку миграций нет,
   данные БД не откатываются. Старый Mac-туннель не используется для отката.

Регистрация и разделение организаций (история): с 21.09 новая организация получает свой пустой объект — замок в
приложении (ADR-061). 22.09.2026 регистрацию закрыли (`REGISTRATION_OPEN=0`, ADR-060, `reports/deploy-2026-09-22.md`),
27.09 на час открывали (ADR-101) и снова закрыли до RLS (ADR-102). RLS введён в строй 27–28.09 (ADR-103), 29.09 регистрацию
оставили открытой (ADR-123), 04.10 кратко закрыли (ADR-146) и вернули self-service по уточнению владельца (ADR-147). Изоляция теперь держится и в базе, не только в приложении (статус
[Q-152](../QUESTIONS.md) в самом файле вопросов записан противоречиво — сверить отдельно). Права роли `wetop_app` на таблицы учётных данных урезаны миграцией
`20260929000033_rls_credential_grants` (SEC-1b, ADR-124) — порядок применения в `docs/ops/rls.md`, раздел «SEC-1b».

Обновление 04.10.2026 (ADR-146/147): каналы продаж выбирают текущий филиал пользователя, фоновые
задания и webhook выбирают объект по проверенному сопоставлению `channel_mappings`. Служебный
аккаунт общий, сопоставления и данные разделены по объектам. `INTEGRATION_PROPERTY_ID` сохраняется
для прежних служебных путей установки; он больше не ограничивает настройку каналов других филиалов.
Глобальная диагностика без поля организации остаётся доступна главному администратору; при единственном
сопоставленном объекте её может читать его организация. Перед подключением нового объекта заполнить
страну, город и тип размещения в настройках, создать фонд и выбрать тариф с положительной ценой
для каждой активной категории. Выключатель production ARI и разрешение на подключение OTA не меняются.

Объект интеграции Channex (SEC-2, ADR-125, 29.09.2026): в серверном `.env` задать `INTEGRATION_PROPERTY_ID` — идентификатор
объекта установки (Luxx). Взять его в SQL-редакторе базы: `SELECT id, name, organization_id FROM properties ORDER BY created_at;`
(строка объекта Luxx, `id` — UUID). Без переменной API определяет объект по сопоставлениям Channex, а пока их нет — по названию
«Luxx Aparts» и пишет предупреждение при старте в production. Значение не UUID — API не запускается; UUID несуществующего
объекта закрывает разделы каналов и сторожа всем, кроме главного администратора, поэтому после правки проверить вход в
«Каналы продаж». Откат — убрать строку из `.env` и пересоздать API.

Капча перед бронью с сайта (BOOK-SEC1, ADR-129, 29.09.2026): без неё публичный `POST /w/book` создаёт подтверждённую бронь
любому, кто знает ключ сайта. Что сделать один раз: в Cloudflare → Turnstile создать виджет (режим Managed), в «Hostname
management» вписать домены сайтов гостиниц и хост API (демо-страница `/w/demo`); в серверный `.env` вписать
`TURNSTILE_SITE_KEY` (публичный ключ), `TURNSTILE_SECRET_KEY` (секретный) и `WEB_BOOKING_TURNSTILE_REQUIRED=1`, пересоздать API.
В production режим задаётся только явно: `1` — обязательна, без любого из ключей API не запустится; `0` — выключена осознанно
(при старте предупреждение); **не задан или любое другое значение — API не запустится, даже если оба ключа есть** (защита
не выводится косвенно из наличия секрета: потеряв переменные, нельзя тихо открыть бронь). Вне production `1` без ключей тоже
отказывает, а без режима проверка включается, если есть секрет (удобство dev и тестов). **Порядок выкладки: сначала ключи и режим в `.env`, потом код** — на новом коде без них production не
стартует. Проверка: `curl -s https://<API>/w/config` — `{"turnstileSiteKey":"…"}` (секрета в ответе нет); на
`/w/demo?k=…` кнопка «Подтвердить бронь» активна только после проверки. Если у сайта гостиницы строгая CSP, ей нужно
разрешить `https://challenges.cloudflare.com` в `script-src` и `frame-src`. Откат — `WEB_BOOKING_TURNSTILE_REQUIRED=0` (проверка выключится, виджет вернётся к прежней форме).

Один файл на все три части системы. Порядок проверен 17.09.2026; сборки и наборы тестов
перед выкладкой прогоняются в облачной сессии, сама выкладка идёт **только с машины стойки**
(Mac владельца): там `.env`, ключи Cloudflare и службы launchd.

## 1. Стойка `app.wetop.ai` и API `api.wetop.ai`

Живут на Mac под launchd (`scripts/ops/launchd/`), код берут из рабочей копии репозитория.

```bash
cd ~/путь/к/wetop.ai
git fetch origin && git checkout main && git pull        # или нужная ветка
npm install                                              # заодно перегенерирует клиент базы
npm run generate -w @pms/database                        # если ставили не через npm install

# API: перечитать код
launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.api

# Стойка: сначала сборка, потом перезапуск — next start держит манифест в памяти
npm run build -w apps/web
launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.web
```

Проверить, что встало:

```bash
bash scripts/ops/launchd/status.sh                       # все шесть служб
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/inventory/summary   # 200
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/today               # 200
npm run ui:walkthrough                                   # обход экранов и кнопок, сверка чисел с API
```

Этот раздел описывает только снятый Mac-контур. Не запускайте его параллельно серверному контуру:
две копии туннеля делят запросы и делают рабочий адрес нестабильным.
Если `status.sh` пишет «не загружен», поднять:

```bash
bash scripts/ops/launchd/install.sh domain
bash scripts/ops/launchd/install.sh awake
```

Команды выше оставлены только для аварийной диагностики старого контура и не являются инструкцией по выкладке.

**Туннель может держать не наша задача.** 17.09.2026 `tunnel` и `domain` оба числились «не загружен», а
туннель `wetop` при этом работал: его держала системная служба cloudflared от root, поставленная
`cloudflared service install` 15.09, и адрес снаружи отвечал 200. Поднятая «на всякий случай» вторая копия
того же туннеля первую не заменила — Cloudflare стал делить запросы между ними, и `api.wetop.ai` начал
отвечать через раз. Поэтому `status.sh` теперь после ярлыков спрашивает сам адрес, а `install.sh domain`
отказывается ставить службу, если адрес уже отвечает 200 без неё (осознанный обход — `ALLOW_SECOND_TUNNEL=1`)
или если в `~/.cloudflared/wetop.yml` остались заглушки `<…>` из образца.

Кто держит туннель на самом деле:

```bash
cloudflared tunnel info wetop                              # коннекторы, их версия, архитектура и IP
pgrep -x cloudflared                                       # процессы этого пользователя
ls /Library/LaunchDaemons | grep -i cloudflare             # системная служба от root
sudo launchctl list | grep -i cloudflare
```

Версия коннектора в `tunnel info`, не совпадающая с `cloudflared --version` в терминале, означает, что
туннель поднят другим двоичным файлом или с другой машины.

**Клиент базы обязан знать схему.** Он генерируется из `schema.prisma`, а не из самой базы: пока
`prisma generate` не выполнен, сервер обращается к полям, которых клиент не знает, и отвечает 500 —
17.09.2026 так падал журнал действий («Unknown field `user` for include statement on model `AuditLog`»),
хотя все миграции были применены. Теперь генерация идёт сама при `npm install` (`postinstall`), а
после ручной правки схемы — `npm run generate -w @pms/database` и перезапуск API.

**Миграции базы применяет владелец вручную** (`DATA_MODEL.md`, `CUTOVER.md`): агент production migration
не делает. Сначала миграция, потом перезапуск API.

## 1а. Сервер в Казахстане (переезд идёт)

Всё, что описано выше, — это Mac владельца, и это временно. Боевой контур переезжает на сервер в
Казахстане: этого требует условие допуска №1 `CUTOVER.md` и правило, что данные гостей живут в РК
(ADR-009, ADR-018). Порядок переезда, доказательства и откат — `plans/server-kz-2026-09-17.md`,
выбор площадки — `docs/ops/server-kz-2026-09-16.md`, команды первых шагов на ps.kz по порядку —
`docs/ops/server-setup-2026-09-18.md`.

На сервере нет launchd: службы `api`, `web` и `cloudflared` поднимает Docker Compose,
так же как сторожа на Hostinger. На Hostinger к `compose.yml` добавляется серверное наложение
`compose.hostinger.yml`, которого нет в git: перед переездом на ps.kz его снять —
`docs/ops/server-setup-2026-09-18.md` §6а.

```bash
cp deploy/cloudflared.example.yml deploy/cloudflared/wetop.yml   # подставить TUNNEL-ID (Access снят ADR-053)
docker compose -f deploy/compose.yml up -d --build
docker compose -f deploy/compose.yml ps
docker compose -f deploy/compose.yml logs -f api
```

Обновление кода — `git pull` и та же команда `up -d --build`: образ один на API и стойку, поэтому
собранная стойка и клиент базы заведомо от одного кода. Отдельного `npm run build` и отдельной
генерации клиента, как на Mac, здесь нет.

### Скрипты на сервере берут код из образа, а не из клона

Грабля, на которую наступили дважды 20.09.2026. Разовые скрипты (`scripts/reconciliation/…`)
запускают так:

```bash
cd /root/wetop/deploy && docker compose -f compose.yml -f compose.hostinger.yml exec -w /app api   node --import tsx scripts/reconciliation/src/cli-…ts
```

`/app` внутри контейнера — это **слепок кода на момент сборки образа**, а не папка `/root/wetop`.
Клон на сервере в контейнер не смонтирован. Значит, `git pull` сам по себе скрипт не обновляет:
запустится прежняя версия, молча и без предупреждения. Порядок такой:

```bash
cd /root/wetop && git pull
cd deploy && docker compose -f compose.yml -f compose.hostinger.yml up -d --build api web
docker compose -f compose.yml -f compose.hostinger.yml exec -w /app api node --import tsx scripts/…
```

Второй сюрприз того же семейства: внутри контейнера API `127.0.0.1:3000` — это он сам, а не стойка.
Стойка — соседний контейнер, её адрес `http://web:3000`; скриптам, которые ходят на экраны, его
передают через `-e WEB_URL=http://web:3000`.

Секреты в образ не попадают: `.env` подаётся через `env_file`, ключ туннеля монтируется только на
чтение (`SECURITY.md` §3). Процесс стойки при этом видит не весь `.env`, а только свои пять переменных:
команда службы `web` чистит окружение через `env -i` (INFRA-ENV, 30.09.2026; список — в `deploy/compose.yml`
и `deploy/README.md`). Проверки этих правил — `tests/unit/deploy-server.test.ts`.

**Живость контейнеров меряет `GET /health`**, а не рабочий маршрут. Он публичный, поэтому отвечает и с
включённым `AUTH_REQUIRED=1`, и обязательно трогает базу: 14.09.2026 Mac уснул, соединения пула умерли, и
API отвечал на запросы, ни один из которых не доходил до базы. Наружу маршрут не выходит — туннель
пропускает только шесть публичных путей.

Что красный healthcheck даёт, а чего нет — чтобы не ждать от него лишнего. Он виден в `docker compose ps`
и не даёт зависимым службам подняться раньше API. **Контейнер он не перезапускает:** `restart: unless-stopped`
срабатывает только на выход процесса. Мёртвые соединения пула лечит сам пул (ADR-043): ответ базы ждётся не
дольше 30 с, потом сокет закрывается. Зависшую стойку на Mac перезапускал сторож через launchd; на сервере
эта починка честно отвечает «не настроено» и уходит к человеку — `docker compose restart web` руками.

**Выключатель ARI работает и здесь:** `scripts/ops/ari.sh stop|start|status`. На сервере он кладёт и убирает
файл `deploy/ari.env` и пересоздаёт контейнер API, поэтому состояние переживает перезагрузку, в отличие от
`launchctl setenv` на Mac. Порядок полного отката — `CUTOVER.md` ROLLBACK.

**Туннель поднимается на сервере только после того, как снят с Mac.** Две копии одного туннеля друг
друга не заменяют, см. предупреждение выше. Порядок: поднять на сервере, убедиться в
`cloudflared tunnel info wetop`, что коннектор один, затем снимать с Mac.

## 1б. Вторая копия PMS рядом с боевой: два обязательных условия

Проверено на сервере Hostinger 18–19.09.2026 (`reports/hostinger-mirror-2026-09-19.md`). Копию PMS можно
поднять рядом с боевой — для проверки, показа или обкатки переезда, — но **только на этих условиях**, иначе
она ломает боевую.

1. **Явный маленький пул.** Session pooler Supabase даёт 15 клиентов на проект, и их уже делит рабочая
   машина. Копия с умолчанием (5) выбирает остаток, и боевая стойка начинает отвечать 500 с
   `(EMAXCONNSESSION) max clients reached in session mode`. Лёгкие запросы при этом проходят, поэтому
   выглядит это не как «база упала», а как «часть экранов не грузится». За сутки такой работы в
   `system_incidents` открылось 11 неисправностей, 609 отказов на одной карточке брони.
   Копии задавать `DATABASE_POOL_MAX=3` и меньше.
2. **Выключить всё фоновое.** У копии не должно быть ни сторожа, ни опроса ленты Channex, ни очереди ARI,
   ни полной выгрузки, ни проверки webhook: `GUARD=off`, `CHANNEX_PULL=off`, `CHANNEX_OUTBOX_WORKER=off`,
   `CHANNEX_FULL_SYNC=off`, `CHANNEX_WEBHOOK_HEALTH=off`, `ANALYTICS_RETENTION=off` (суточная очистка счётчика сайта,
   с 24.09.2026), плюс `deploy/ari.env` с `CHANNEX_ARI=off`.
   Иначе две копии тянут одну ленту, сторожат один адрес и чинят наперегонки.

Фоновые задачи у копии не поднимать: две копии на одной базе создают гонки за одни и те же записи.

## 1в. Переменные-предохранители (ADR-074, 24.09.2026)

| Переменная | Где | Что делает |
|---|---|---|
| `CHANNEX_PRODUCTION=1` | `.env` сервера, **только шагом переключения** (`CUTOVER.md`, шаг 0) | Без неё клиент Channex отказывает до сети на любом хосте channex.io, кроме staging. Адрес и ключ production в `.env` сами по себе ничего не отправят |
| `PMS_TEST_REMOTE_DB=1` | в команде прогона, не в `.env` | Разрешает `integration` и `e2e` нелокальную базу. Без неё прогон на Mac с рабочей базой в `.env` отказывает словами; обычный путь — `npm run db:local` |

В `.env.example` их вписывает владелец (агенту шаблон закрыт от чтения, `SECURITY.md` §3): только имена, без значений.
Остальные правки проверки 24.09.2026 — маски почты и телефонов, журнал, замок организаций — новых переменных
не требуют и включаются вместе с образом.

## 1г. Бэкапы рабочей базы (Q-073)

Ночная копия, пробное восстановление и порядок «бэкап → миграция → проверка → откат» — `docs/ops/backups.md`.
Supabase на бесплатном плане сам копий не делает. Ночная копия стоит в cron Hostinger с 24.09.2026 (23:30 UTC).

За копией следит сторож стойки (ADR-078). Скрипт копии пишет статус в `/root/backups/status`. У `api` в
`deploy/compose.yml` эта папка смонтирована только на чтение, путь к файлу — в `GUARD_BACKUP_STATUS`. Самих копий в
контейнере нет.

На новом сервере без ночной копии сторож скажет «статус копии не найден». Там, где копии делает провайдер базы, проверку
выключает `GUARD_BACKUP=off`.

## 1д. Автовыкладка: сервер сам забирает ветку `release` (ADR-080, 24.09.2026)

Сервер раз в две минуты смотрит на GitHub ветку **`release`** и, если она ушла вперёд, выкладывает её сам:
`scripts/ops/auto-deploy.sh` из cron. Ни GitHub Actions (бюджет $0), ни SSH агенту не нужны.

**Что выкладывать, решает ветка.** В `main` сливается и непроверенное. `release` перематывают на коммит `main` только
при зелёных проверках GitHub (`checks`) и наборах (unit, typecheck, lint, integration, живые сквозные, полный UI)
и только по «да» владельца на эту выкладку (AGENTS.md §18, ADR-137): `git push origin <коммит>:release`.
Откат ветки (перемотка назад) скрипт не выкладывает: это ручной откат, §4.

**Что скрипт делает на каждой новой вершине:**

1. `git fetch`; вершина та же — выходит молча.
2. Не выкладывает и пишет в Telegram дежурным (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` из `.env`, как у сторожа), если:
   в клоне локальные правки отслеживаемых файлов (`deploy/compose.hostinger.yml` не в git — не мешает); новая вершина не
   продолжает текущую; **в обновлении новые миграции** — их применяет владелец (AGENTS.md §15), затем выкладка руками по
   §1а. Об одной вершине пишет один раз.
2а. CI-раннер (`scripts/ops/ci-runner`, проект compose `pms-lux-ci`) выполняет задачу (процесс `Runner.Worker` в
   `docker top`) — сборку откладывает: строка в журнале один раз на вершину, повтор следующим запуском cron. Дольше
   30 минут (`DEPLOY_CI_MAX_WAIT`) не ждёт: выкладывает и пишет дежурным. Причина — сбой 03.10.2026: сборка образа и
   проверки на одном сервере съели 8 ГБ, туннель 4–7 минут отвечал 530 (`plans/deploy-build-outage-2026-10-03.md`).
   Там же у `api`, `web` и `cloudflared` `oom_score_adj: -500`, а у `next build` потолок кучи 2 ГБ.
3. Точка отката: прежний образ как `pms-lux:rollback-<коммит>`, коммит — в `/var/lib/wetop-deploy/previous`.
4. `git checkout -B release <вершина>` и `up -d --build api web`; `.env` не трогается, `cloudflared` тоже.
5. Проверка до трёх минут: `/health` API `ok`, `/login` стойки — 200, `/today`, `/chessboard`, `/reservations` — не 5xx.
   Страницы без входа отвечают 200, а переход на вход приходит в теле — поэтому проверка не требует 307.
6. Не прошло — прежний коммит, прежний образ, `up -d api web` без сборки, сообщение в Telegram. Сломанную вершину
   повторно не пробует: следующая попытка — на следующем коммите `release`.

Журнал — `/var/log/wetop-deploy.log`, состояние — `/var/lib/wetop-deploy/` (`deployed`, `previous`, `refused`).
Проверки скрипта — `tests/unit/auto-deploy.test.ts` (исполняет его на временных репозиториях с подставным `docker`).

**Установка — один раз, в веб-терминале сервера.** Скрипт ставится отдельным файлом `/usr/local/sbin/wetop-auto-deploy`,
а не запускается из клона: `release` может стоять на коммите, где скрипта ещё нет (первая вершина — 3da7a2c6, она
уже на сервере), а выкладка не меняет сам исполняемый файл. Обновить скрипт — повторить вторую строку.

```bash
cd /root/wetop && git fetch origin && git status --short          # пусто или только ?? deploy/compose.hostinger.yml
git show origin/main:scripts/ops/auto-deploy.sh > /usr/local/sbin/wetop-auto-deploy && chmod +x /usr/local/sbin/wetop-auto-deploy
git checkout -B release origin/release                            # клон теперь на ветке выкладки; HEAD тот же коммит
( crontab -l 2>/dev/null | grep -v 'wetop-auto-deploy'
  echo "*/2 * * * * /usr/local/sbin/wetop-auto-deploy >> /var/log/wetop-deploy.log 2>&1" ) | crontab -
crontab -l | grep wetop-auto-deploy                               # строка на месте
/usr/local/sbin/wetop-auto-deploy; echo "код $?"                   # вершина та же — молча, код 0
```

**Первая выкладка через `release` — с миграциями ИИ-помощника и продавца.** В `main` с 24.09 лежат
`20260924000018_user_errors` и `20260924000019_seller_profiles`; `DATA_MODEL.md` v1.8 утверждён 24.09 (Q-177 закрыт,
ADR-081). Скрипт такой коммит не выложит и напишет, какие миграции ждут. Порядок (весь путь включения —
`docs/assistant/README.md` §6): `release` перематывается на
проверенный коммит `main`; скрипт отказывает и называет миграции; владелец применяет их (бэкап → миграция → проверка —
`docs/ops/backups.md`) и запускает `/usr/local/sbin/wetop-auto-deploy --migrations-applied <вершина из отказа>` — скрипт сверяет её с
`origin/release` (перемотали после отказа — откажет снова; ТЗ аудита 25.09, С-1) и выкладывает эту
вершину без проверки миграций, остальные проверки и откат остаются. Следующие вершины снова проверяются.

**Миграции без Node на сервере** — Prisma CLI есть в образе стойки, миграции берутся из той вершины `release`, на
которой скрипт отказал (здесь `afe82ab9`). Строка подключения — сессионная (`BACKUP_DATABASE_URL`, как у копии), иначе
`DIRECT_URL`; на экран не печатается:

```bash
cd /root/wetop && V=afe82ab9
rm -rf /tmp/wetop-mig && mkdir -p /tmp/wetop-mig && git archive "$V" packages/database/prisma | tar -x -C /tmp/wetop-mig
# DIRECT_URL — из окружения, а не аргументом: аргументы `docker run` видны в `ps` любому процессу на сервере
mig() { ( set -a; . ./.env; set +a
  export DIRECT_URL="${BACKUP_DATABASE_URL:-${DIRECT_URL:-$DATABASE_URL}}"
  docker run --rm -e DIRECT_URL \
    -v /tmp/wetop-mig/packages/database/prisma:/app/packages/database/prisma:ro \
    -w /app/packages/database pms-lux:latest npx prisma migrate "$@" ); }
mig status     # ждём: две не применены — 20260924000018_user_errors, 20260924000019_seller_profiles
mig deploy     # только после свежей копии ($BACKUP, docs/ops/backups.md)
mig status     # ждём: Database schema is up to date
/usr/local/sbin/wetop-auto-deploy --migrations-applied "$V"
```

Выключить — убрать строку из `crontab -e`. Ручная выкладка по §1а остаётся рабочей: перед ней убрать строку cron, чтобы
два процесса не собирали образ одновременно (скрипт держит замок, но о ручной сборке он не знает).

Бот «ИИ-продавец» (`apps/ai-seller`) автовыкладкой не выкладывается: он собирается своим `compose.yml` из своей папки.

## 2. Главная `wetop.ai`

Статическая сборка `apps/site`, выкладывается прямой загрузкой в Cloudflare Pages: приватный репозиторий
к Cloudflare не подключается (`SECURITY.md` §4).

```bash
npm run site:build     # собрать в apps/site/out
npm run site:check     # 6 проверок: страницы, доступность, телефон, карточка ссылки, sitemap
npm run site:deploy    # сборка + wrangler pages deploy на проект wetop-site
```

`site:deploy` спросит вход в Cloudflare при первом запуске. Ключей нет ни в репозитории, ни в облачной сессии.

**Грабля 23.09.2026: у владельца два аккаунта Cloudflare, и wrangler по умолчанию берёт не тот.**
Проект `wetop-site` (домены `wetop.ai`, `www.wetop.ai`) живёт в аккаунте Cloudflare владельца
`aa05d3443b086b6c6e6b3392ee17ab56`; вход `wrangler` был под другой почтой владельца, где Pages-проектов нет
вовсе. В этом случае wrangler не ошибается, а **предлагает создать проект** — соглашаться нельзя:
появится новый пустой проект без домена, сайт не обновится. Правильно — назвать аккаунт явно:

```bash
CLOUDFLARE_ACCOUNT_ID=aa05d3443b086b6c6e6b3392ee17ab56 npx wrangler@4.141.0 pages project list
CLOUDFLARE_ACCOUNT_ID=aa05d3443b086b6c6e6b3392ee17ab56 npm run site:deploy
```

Проверка после выкладки — по строке, которой в прежней версии страницы не было:

```bash
curl -s https://wetop.ai/ | grep -c "Три экрана"   # 1 и больше — на домене новая главная
```

Идентификатор аккаунта секретом не является (он стоит в адресах панели), ключей и токенов здесь нет.
