# Выкладка: что и как обновляется

> **Актуальное состояние на 20.09.2026.** Публичные `app.wetop.ai` / `api.wetop.ai`
> обслуживает Linux-коннектор туннеля на `187.77.145.152`. Старые Mac-службы
> `domain`, `api`, `web`, `exely-sync` отключены после обнаружения двух источников
> одного домена. **§1 ниже — прежняя схема, не инструкция для текущей выкладки.**
> Не поднимать Mac-туннель и не возвращать Exely: ADR-052 отменил синхронизацию.
> Проверка текущего состояния и ограничения —
> [отчёт приёмки](../reports/current-release-acceptance-2026-09-20/report.md).
>
> GitHub Actions здесь проверяет код, но не выкладывает его. `git push` и merge
> не доказывают обновления сервера. Для текущего серверного обновления нужны
> подтверждённый SSH-доступ, фактические каталог клона и Compose project.
> Старый профиль `hostinger` этого Mac относится к другому серверу с n8n.

## Текущая серверная выкладка: порядок проверки и отката

1. Проверить SSH-host key, адрес сервера и метки работающих контейнеров WETOP.
   Не отключать проверку подлинности и не выбирать соседний проект по похожему имени.
2. В найденном клоне проверить чистое дерево; сохранить SHA предыдущей версии,
   ID образов API/web и резервные теги образов. `.env` и конфигурацию туннеля
   сохранить в закрытой серверной резервной копии, не выводя значения в журнал.
3. Получить одобренный `main` через `git fetch` и fast-forward. Сверить SHA с
   проверенным CI, убедиться, что нет новых неприменённых миграций. Эта приёмка
   не разрешает production migration, изменение схемы или переключение каналов.
4. Собрать `deploy/Dockerfile`, затем обновить **только API/web** существующего
   Compose project. Туннель, `.env`, выключатель ARI и фоновые настройки сохранить.
   Повторный запуск Exely и `up` чужих Compose-проектов не входят в выкладку.
   Регистрация: `REGISTRATION_OPEN` в серверном `.env` не менять. С 22.09.2026 там `0` —
   на боевом сервере регистрация закрыта, пока нет Row Level Security (ADR-060, ADR-061,
   Q-152); что обещать снаружи — Q-157. Пустое или отсутствующее значение регистрацию
   **открывает** (ADR-055), поэтому при переносе `.env` на другую машину строку переносить
   явно. Открыть — только отдельным решением владельца, записанным в Q-157.
   Сначала обновить API: внутренний `/auth/options` должен вернуть
   `registrationEnabled: false`. Затем обновить web и проверить: на `/login` нет кнопки
   «Регистрация», а `/register` и `/login?mode=register` показывают «Самостоятельная
   регистрация временно закрыта». Приглашения остаются доступны. Отдельный
   `APP_REGISTRATION_OPEN` не нужен.
5. Доказать версию по SHA клона, ID запущенных образов и `BUILD_ID` Next из
   контейнера, затем проверить внутренний `/health` с базой, публичный вход,
   отказ анонимному запросу и чтение основных экранов под сотрудником.
   HTTP 200 без проверки содержимого или перенаправления недостаточен.
6. При неуспехе вернуть предыдущий commit и сохранённые образы, пересоздать
   API/web без новой сборки, повторить health и вход. Поскольку миграций нет,
   данные БД не откатываются. Старый Mac-туннель не используется для отката.

Регистрация и разделение организаций (сверка 22.09.2026): в `main` с 21.09 новая организация получает свой
пустой объект — замок в приложении (ADR-061), а не в самой базе (Row Level Security нет), поэтому
[Q-152](../QUESTIONS.md) открыт. 22.09.2026 на сервер выложен `20eac505`, регистрация на сервере закрыта
(`REGISTRATION_OPEN=0`, ADR-060) — `reports/deploy-2026-09-22.md`. Что обещать снаружи — Q-157.

Один файл на все три части системы. Порядок проверен 17.09.2026; сборки и наборы тестов
перед выкладкой прогоняются в облачной сессии, сама выкладка идёт **только с машины стойки**
(Mac владельца): там `.env`, ключи Cloudflare и службы launchd.

## 1. Стойка `app.wetop.ai` и API `api.wetop.ai`

Живут на Mac под launchd (`scripts/ops/launchd/`), код берут из рабочей копии репозитория.

```bash
cd ~/путь/к/wetop.ai
git fetch origin && git checkout main && git pull        # или нужная ветка
npm install                                              # заодно перегенерирует клиент базы
npm run generate -w @pms/database                        # если ставили не через npm install

# API: перечитать код
launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.api

# Стойка: сначала сборка, потом перезапуск — next start держит манифест в памяти
npm run build -w apps/web
launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.web
```

Проверить, что встало:

```bash
bash scripts/ops/launchd/status.sh                       # все шесть служб
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/inventory/summary   # 200
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/today               # 200
npm run ui:walkthrough                                   # обход экранов и кнопок, сверка чисел с API
```

**Служб должно быть шесть, не две.** `api` и `web` держат сервер и стойку, но снаружи объект живёт
только с остальными: `domain` — именованный туннель Cloudflare (`app.wetop.ai`, `api.wetop.ai`, webhook
Channex), `exely-sync` — синхронизация с Exely раз в 15 минут (ADR-032), `awake` — Mac не засыпает.
Если `status.sh` пишет «не загружен», поднять:

```bash
bash scripts/ops/launchd/install.sh domain
bash scripts/ops/launchd/install.sh exely-sync
bash scripts/ops/launchd/install.sh awake
```

Без `domain` брони из каналов доходят только опросом ленты, а не webhook'ом; без `exely-sync` данные
в PMS устаревают. В день двойного ввода `exely-sync` снимают намеренно (`CUTOVER.md`, условие 2).

**Туннель может держать не наша задача.** 17.09.2026 `tunnel` и `domain` оба числились «не загружен», а
туннель `wetop` при этом работал: его держала системная служба cloudflared от root, поставленная
`cloudflared service install` 15.09, и адрес снаружи отвечал 200. Поднятая «на всякий случай» вторая копия
того же туннеля первую не заменила — Cloudflare стал делить запросы между ними, и `api.wetop.ai` начал
отвечать через раз. Поэтому `status.sh` теперь после ярлыков спрашивает сам адрес, а `install.sh domain`
отказывается ставить службу, если адрес уже отвечает 200 без неё (осознанный обход — `ALLOW_SECOND_TUNNEL=1`)
или если в `~/.cloudflared/wetop.yml` остались заглушки `<…>` из образца.

Кто держит туннель на самом деле:

```bash
cloudflared tunnel info wetop                              # коннекторы, их версия, архитектура и IP
pgrep -x cloudflared                                       # процессы этого пользователя
ls /Library/LaunchDaemons | grep -i cloudflare             # системная служба от root
sudo launchctl list | grep -i cloudflare
```

Версия коннектора в `tunnel info`, не совпадающая с `cloudflared --version` в терминале, означает, что
туннель поднят другим двоичным файлом или с другой машины.

**Клиент базы обязан знать схему.** Он генерируется из `schema.prisma`, а не из самой базы: пока
`prisma generate` не выполнен, сервер обращается к полям, которых клиент не знает, и отвечает 500 —
17.09.2026 так падал журнал действий («Unknown field `user` for include statement on model `AuditLog`»),
хотя все миграции были применены. Теперь генерация идёт сама при `npm install` (`postinstall`), а
после ручной правки схемы — `npm run generate -w @pms/database` и перезапуск API.

**Миграции базы применяет владелец вручную** (`DATA_MODEL.md`, `CUTOVER.md`): агент production migration
не делает. Сначала миграция, потом перезапуск API.

## 1а. Сервер в Казахстане (переезд идёт)

Всё, что описано выше, — это Mac владельца, и это временно. Боевой контур переезжает на сервер в
Казахстане: этого требует условие допуска №1 `CUTOVER.md` и правило, что данные гостей живут в РК
(ADR-009, ADR-018). Порядок переезда, доказательства и откат — `plans/server-kz-2026-09-17.md`,
выбор площадки — `docs/ops/server-kz-2026-09-16.md`, команды первых шагов на ps.kz по порядку —
`docs/ops/server-setup-2026-09-18.md`.

На сервере нет launchd: службы (`api`, `web`, `cloudflared`; `exely-sync` снят ADR-052) поднимает Docker Compose,
так же как сторожа на Hostinger. На Hostinger к `compose.yml` добавляется серверное наложение
`compose.hostinger.yml`, которого нет в git: перед переездом на ps.kz его снять —
`docs/ops/server-setup-2026-09-18.md` §6а.

```bash
cp deploy/cloudflared.example.yml deploy/cloudflared/wetop.yml   # подставить TUNNEL-ID (Access снят ADR-053)
docker compose -f deploy/compose.yml up -d --build
docker compose -f deploy/compose.yml ps
docker compose -f deploy/compose.yml logs -f api
```

Обновление кода — `git pull` и та же команда `up -d --build`: образ один на API и стойку, поэтому
собранная стойка и клиент базы заведомо от одного кода. Отдельного `npm run build` и отдельной
генерации клиента, как на Mac, здесь нет.

### Скрипты на сервере берут код из образа, а не из клона

Грабля, на которую наступили дважды 20.09.2026. Разовые скрипты (`scripts/reconciliation/…`)
запускают так:

```bash
cd /root/wetop/deploy && docker compose -f compose.yml -f compose.hostinger.yml exec -w /app api   node --import tsx scripts/reconciliation/src/cli-…ts
```

`/app` внутри контейнера — это **слепок кода на момент сборки образа**, а не папка `/root/wetop`.
Клон на сервере в контейнер не смонтирован. Значит, `git pull` сам по себе скрипт не обновляет:
запустится прежняя версия, молча и без предупреждения. Порядок такой:

```bash
cd /root/wetop && git pull
cd deploy && docker compose -f compose.yml -f compose.hostinger.yml up -d --build api web
docker compose -f compose.yml -f compose.hostinger.yml exec -w /app api node --import tsx scripts/…
```

Второй сюрприз того же семейства: внутри контейнера API `127.0.0.1:3000` — это он сам, а не стойка.
Стойка — соседний контейнер, её адрес `http://web:3000`; скриптам, которые ходят на экраны, его
передают через `-e WEB_URL=http://web:3000`.

Секреты в образ не попадают: `.env` подаётся через `env_file`, ключ туннеля монтируется только на
чтение (`SECURITY.md` §3). Проверки этих правил — `tests/unit/deploy-server.test.ts`.

**Живость контейнеров меряет `GET /health`**, а не рабочий маршрут. Он публичный, поэтому отвечает и с
включённым `AUTH_REQUIRED=1`, и обязательно трогает базу: 14.09.2026 Mac уснул, соединения пула умерли, и
API отвечал на запросы, ни один из которых не доходил до базы. Наружу маршрут не выходит — туннель
пропускает только шесть публичных путей.

Что красный healthcheck даёт, а чего нет — чтобы не ждать от него лишнего. Он виден в `docker compose ps`
и не даёт зависимым службам подняться раньше API. **Контейнер он не перезапускает:** `restart: unless-stopped`
срабатывает только на выход процесса. Мёртвые соединения пула лечит сам пул (ADR-043): ответ базы ждётся не
дольше 30 с, потом сокет закрывается. Зависшую стойку на Mac перезапускал сторож через launchd; на сервере
эта починка честно отвечает «не настроено» и уходит к человеку — `docker compose restart web` руками.

**Выключатель ARI работает и здесь:** `scripts/ops/ari.sh stop|start|status`. На сервере он кладёт и убирает
файл `deploy/ari.env` и пересоздаёт контейнер API, поэтому состояние переживает перезагрузку, в отличие от
`launchctl setenv` на Mac. Порядок полного отката — `CUTOVER.md` ROLLBACK.

**Туннель поднимается на сервере только после того, как снят с Mac.** Две копии одного туннеля друг
друга не заменяют, см. предупреждение выше. Порядок: поднять на сервере, убедиться в
`cloudflared tunnel info wetop`, что коннектор один, затем снимать с Mac.

## 1б. Вторая копия PMS рядом с боевой: два обязательных условия

Проверено на сервере Hostinger 18–19.09.2026 (`reports/hostinger-mirror-2026-09-19.md`). Копию PMS можно
поднять рядом с боевой — для проверки, показа или обкатки переезда, — но **только на этих условиях**, иначе
она ломает боевую.

1. **Явный маленький пул.** Session pooler Supabase даёт 15 клиентов на проект, и их уже делит рабочая
   машина. Копия с умолчанием (5) выбирает остаток, и боевая стойка начинает отвечать 500 с
   `(EMAXCONNSESSION) max clients reached in session mode`. Лёгкие запросы при этом проходят, поэтому
   выглядит это не как «база упала», а как «часть экранов не грузится». За сутки такой работы в
   `system_incidents` открылось 11 неисправностей, 609 отказов на одной карточке брони.
   Копии задавать `DATABASE_POOL_MAX=3` и меньше.
2. **Выключить всё фоновое.** У копии не должно быть ни сторожа, ни опроса ленты Channex, ни очереди ARI,
   ни полной выгрузки, ни проверки webhook: `GUARD=off`, `CHANNEX_PULL=off`, `CHANNEX_OUTBOX_WORKER=off`,
   `CHANNEX_FULL_SYNC=off`, `CHANNEX_WEBHOOK_HEALTH=off`, плюс `deploy/ari.env` с `CHANNEX_ARI=off`.
   Иначе две копии тянут одну ленту, сторожат один адрес и чинят наперегонки.

Синхронизацию Exely у копии не поднимать вовсе: два синхронизатора на одной базе — это гонка за одни и те же
брони.

## 2. Главная `wetop.ai`

Статическая сборка `apps/site`, выкладывается прямой загрузкой в Cloudflare Pages: приватный репозиторий
к Cloudflare не подключается (`SECURITY.md` §4).

```bash
npm run site:build     # собрать в apps/site/out
npm run site:check     # 6 проверок: страницы, доступность, телефон, карточка ссылки, sitemap
npm run site:deploy    # сборка + wrangler pages deploy на проект wetop-site
```

`site:deploy` спросит вход в Cloudflare при первом запуске. Ключей нет ни в репозитории, ни в облачной сессии.

**Грабля 23.09.2026: у владельца два аккаунта Cloudflare, и wrangler по умолчанию берёт не тот.**
Проект `wetop-site` (домены `wetop.ai`, `www.wetop.ai`) живёт в аккаунте `Zapoinov95@gmail.com`
`aa05d3443b086b6c6e6b3392ee17ab56`; вход `wrangler` был под `a555tzn@gmail.com`, где Pages-проектов нет
вовсе. В этом случае wrangler не ошибается, а **предлагает создать проект** — соглашаться нельзя:
появится новый пустой проект без домена, сайт не обновится. Правильно — назвать аккаунт явно:

```bash
CLOUDFLARE_ACCOUNT_ID=aa05d3443b086b6c6e6b3392ee17ab56 npx wrangler@latest pages project list
CLOUDFLARE_ACCOUNT_ID=aa05d3443b086b6c6e6b3392ee17ab56 npm run site:deploy
```

Проверка после выкладки — по строке, которой в прежней версии страницы не было:

```bash
curl -s https://wetop.ai/ | grep -c "Три экрана"   # 1 и больше — на домене новая главная
```

Идентификатор аккаунта секретом не является (он стоит в адресах панели), ключей и токенов здесь нет.

## 3. Что прогнать перед выкладкой

С любой машины, включая облачную сессию (`TESTING.md`):

```bash
npm run test:status                        # что уже доказано на этом коде
npm run test:record -- typecheck
npm run test:record -- lint
npm run test:record -- unit
npm run test:record -- e2e --config tests/ui/playwright.config.ts   # стойка на синтетическом API
```

С базой (машина стойки или локальный PostgreSQL 16 с сидом):

```bash
npm run test:record -- integration
npm run build -w apps/web && npm run test:record -- e2e
```

## 4. Откат

- Стойка и API: `git checkout <прошлый коммит>`, затем сборка и `kickstart` по §1.
- База: `down.sql` рядом с миграцией (`scripts/ops/check-migrations.sh` проверяет их на чистом PostgreSQL).
- Каналы: `scripts/ops/ari.sh stop` останавливает отправку остатков в Channex, порядок — `CUTOVER.md` ROLLBACK.
- Главная: `npx wrangler@latest pages deployment list --project-name wetop-site` и откат на прошлую выкладку
  в панели Cloudflare.
