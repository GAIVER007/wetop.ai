**Проверки GitHub с 21.09 не шли ни разу.** Владелец выложил разбор ментора (ADR-137), а у коммита в main не было
ни одной проверки. Разбор: в Settings → Actions → Runners пусто, все задачи на свой раннер (`wetop`) стояли в очереди и
отменялись следующим пушем; последний зелёный прогон был 20.09, ещё на раннерах GitHub. В логе контейнера раннера
«Request headers must contain only ASCII characters»: в `.env` раннера стоял образец `RUNNER_TOKEN=…` из README,
многоточие ушло в заголовок запроса, регистрация падала на первом шаге. Владелец взял новый токен, `down -v` и
`up -d --build`: раннер Active, задача `бот · pytest` на нём впервые прошла (4 мин). Исправлено, чтобы не повторилось:
образец в README и `compose.yml` без многоточия, `entrypoint.sh` до регистрации проверяет токен (только латиница и
цифры) и адрес и отказывает словами. Вторая причина пустого main: `cancel-in-progress: true` на main, при частых
слияниях каждый прогон отменял следующий пуш, и ни одна вершина не получала итога. Теперь отменяются только прогоны
запросов на слияние, прогон main доходит до конца, следующий ждёт. Девятнадцать устаревших прогонов (слитые запросы,
старый main, четыре открытых запроса от 1–2.10) отменены с разрешения владельца. Попутно: защиту веток GitHub на
бесплатном тарифе для приватного репозитория не применяет («won't be enforced… until you move to GitHub Team»), поэтому
правило «release только на зелёных проверках» держат скрипт выкладки и агент; запуск проверок из форков выключен.

`playwright install chromium` без `--with-deps`, sudo из образа убран. (2) lint на main красный из-за правки REP3

**Письмо Channex 03.10.2026 (Evan): «You don't need to pull webhooks on a constant basis».** Разбор: сторож webhook
(`webhook-health.service.ts`) на каждой пробе, раз в пять минут, спрашивал у Channex список webhook (`GET /webhooks`),
288 запросов в сутки, чтобы узнать адрес, который меняется только нашей же регистрацией. Теперь `ChannexSyncService`
помнит последний ответ Channex; сторож берёт адрес из памяти и спрашивает Channex не чаще раза в сутки, регистрация
webhook (кнопка и починка сторожа) сразу кладёт в память новый адрес, страница каналов спрашивает Channex как раньше и
заодно освежает память. Проба нашего собственного адреса остаётся раз в пять минут: она идёт на наш сервер. Если
Channex не ответил, повтор со следующей пробой, а не на каждом тике. Тем же письмом проверена сверка смены: правило
Channex «не выкачивать все брони объекта на всякий случай» (`best-practices-guide.md`), поэтому сверка читает не
список броней, а ленту неподтверждённых ревизий (тот же запрос, что приём, без подтверждения) и журнал приёма WETOP.

**Второй ответ Channex 03.10 (Evan).** Интервалы приняты: лента ревизий раз в 1–5 минут и чаще, пока webhook молчит;
`GET /webhooks` при регистрации, по открытию страницы и раз в сутки; ARI очередью и полная выгрузка раз в сутки.
Остатки читать раз в сутки, изменения между чтениями через webhook, PMS остаётся источником того, что шлёт. Сделано:
сторож читает остатки у Channex раз в сутки вместо раза в час; отметка чтения пишется в журнал
(`channex.availabilityRead`), и перезапуск API лишнего чтения не даёт; если Channex не ответил, повтор через час;
вне очереди только пересверка после починки расхождения полной выгрузкой. Red
`tests/runs/logs/2026-10-03T13-17-01Z-unit-69f0.log` (3 из 35) → green `…13-20-10Z-unit-096d.log` 242 из 242
(guard и channels), typecheck `…13-18-08Z-typecheck-27d1.log` чисто, сторож на настоящей базе
`…13-19-22Z-integration-f048.log` 4 из 4. Ещё из ответа: объект, категории и тарифы в production создаём сами
через API, Channex только заводит аккаунт; тестовых объектов в production не заводить, staging остаётся для
разработки и нагрузочного теста (записано в `CUTOVER.md`, шаг 0); аккаунт заводится после подписки и ответа Evan.
