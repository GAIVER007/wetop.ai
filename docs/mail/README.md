# Письма WETOP: куда смотреть

Отправитель в системе один — порт `MailSender` в `packages/integrations/src/mail` (ADR-004).
Вендор за ним: Resend, по документации `docs/mail/resend-api.md`; настройка домена и ящиков —
`docs/mail/setup-2026-09-16.md`, записи DNS — `docs/mail/dns-wetop-ai-2026-09-16.md`.

Переменные окружения (вписывает владелец, `SECURITY.md` §3): `MAIL_PROVIDER`, `MAIL_API_KEY`,
`MAIL_FROM`, `MAIL_FROM_NAME`. Пусто хотя бы одно — система работает, письма не уходят.
Контрольное письмо: `npm run mail:check`.

## Какие письма есть

| Письмо | Когда | Откуда текст |
|---|---|---|
| Код входа | вход по одноразовому коду (ADR-046) | `packages/integrations/src/mail/login-code-letter.ts` |
| Приглашение сотрудника | владелец завёл человека командой `npm run accounts -- invite` (ADR-049) | `packages/domain/src/accounts/reset.ts` |
| Сброс пароля | человек нажал «Забыли пароль?» на `/login` (ADR-049) | там же |

Два первых относятся к разным способам входа, и это намеренно: какой способ остаётся, решает
владелец (Q-146). Письма гостям о брони с сайта (Q-115) пойдут той же дорогой.

## Что важно помнить

- Ключ уходит только в заголовок запроса и никогда — в текст ошибки, в журнал и на экран.
- Ссылка на пароль живёт 24 часа, работает один раз, новая гасит прежние; в письме нет пароля.
- Запрос сброса отвечает одинаково для любой почты: по ответу нельзя узнать, есть ли такой адрес.
- Одно письмо на адрес в пять минут — иначе чужой ящик можно завалить.

**История:** 16.09.2026 две сессии независимо написали клиент Resend. Остался тот, что проверен
живым письмом; мой удалён, а приглашение и сброс переведены на общий порт.
