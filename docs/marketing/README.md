## 1. Что строим и чего не строим

**УТВ.** Управляемый сайт филиала: человек открывает «Маркетинг → Сайт и SEO», ИИ собирает бриф из данных WETOP,
предлагает структуру, создаёт черновик `SiteSpec`, человек правит его командами и руками, смотрит превью, публикует
на платформенный поддомен, позже на свой домен. Бронь на сайте это существующий движок `/w/*`, аналитика это
существующий счётчик `/a/*`. Первая вертикаль только Hospitality.

**Не строим:** второй движок брони; генерацию и исполнение кода сайта (Option A отклонён); пользовательский
JavaScript и CSS; замену режима «внешний сайт».

## 2. Границы приложений

| Приложение | Роль в MKT | Чего не делает |
|---|---|---|
| `apps/web` (стойка, `app.wetop.ai`) | раздел «Маркетинг», редактор, бриф, запуск генерации, публикация, домены; всё за входом и правами | не показывает публичные сайты клиентов |
| `apps/api` | хозяин данных: `MarketingSite`, версии, публикации, ассеты, домены, задачи генерации; проверка `SiteSpec`; узкий служебный путь для рантайма; публичные `/w/*` и `/a/*` как сейчас | не рендерит сайты |
| `apps/sites` (новое, рабочее имя) | публичный рантайм: хост → опубликованная версия → компоненты; SEO-выход (meta, JSON-LD, sitemap, robots) | не знает сессий стойки, не читает черновики, не принимает выбор организации, не исполняет код клиента |
| `apps/site` (`wetop.ai`) | сайт самого WETOP, статическая сборка, как сейчас | не становится мультитенантным рантаймом |
| `apps/ai-seller` (бот) | модели ИИ: каскад с маской ПД, ключом партнёра и учётом токенов (`apps/ai-seller/src/ai/llm.py:209-413`); новый узкий вход генерации `SiteSpec` | не пишет в базу WETOP и не решает, что опубликовать |
| `packages/domain` | схема и валидатор `SiteSpec`, правила жизненных циклов, нормализация хостов | |

Место хостинга `apps/sites`: **Cloudflare Workers** (Q-269 RESOLVED владельцем 06.10.2026). Worker сам является
origin публичного сайта; не на сервере Hostinger, не в `apps/web` или `apps/api`, не через Cloudflare Tunnel. Реализация
MKT4: `apps/sites`, план `plans/mkt4-public-site-runtime-2026-10-06.md`, выкладка `apps/sites/README.md`.

Бриф сайта (MKT5): `GET /marketing/site/brief`, детерминированная сводка фактов филиала для будущей генерации, без ИИ и
без хранения. Контракт, белые списки, граница с ИИ и `briefHash`: `docs/marketing/site-brief-v0.md`.

Генерация первой версии (MKT6): `POST /marketing/site/generations` ставит задачу `GenerationRun` (она же очередь в
Postgres), воркер API зовёт узкий вход бота `POST /internal/site-generation` ключом модели платформы, проверяет ответ
тем же валидатором SiteSpec и сохраняет версию `source = AI`; публикация не трогается. Бюджет Q-274, расход, повторы и
граница с ИИ: `docs/marketing/site-generation-v0.md`.

Публикация, превью и домены (MKT7): предпросмотр по подписанной ссылке на `preview.<SITES_BASE_DOMAIN>` (HMAC, 60 минут,
без индексации, брони и счётчика), публикация только головы черновика с повторной проверкой, платформенный поддомен
`<slug>.<SITES_BASE_DOMAIN>` строкой `site_domains`, свой `TrackedSite` управляемого сайта, пауза, возобновление, откат
на ранее опубликованную версию, архив; канонический сайт брони филиала для ИИ-продавца (Q-275, вариант Б). Хосты сайтов
клиентов на отдельном registrable domain, не под `wetop.ai` (Q-271 RESOLVED OWNER 07.10.2026). Контракт:
[`site-publication-v0.md`](site-publication-v0.md).

## 3. Два режима сайта

| Режим | Что есть у филиала | Что делает WETOP |
|---|---|---|
| Внешний сайт (как сейчас) | `TrackedSite` с доменами Tilda, WordPress, своего сайта | выдаёт сниппеты счётчика и виджета, считает аналитику, принимает брони (ADR-025, ADR-026, ADR-117) |
| Управляемый сайт (новое) | `MarketingSite` + связанный `TrackedSite` | хранит версии, рендерит, публикует; сам ставит счётчик и виджет, сам пишет хост в `TrackedSite.hosts` |

Оба режима могут жить у одного филиала одновременно (старый внешний сайт и новый управляемый): у каждого свой
`TrackedSite`. Экран `/website` и его сценарии сохраняются.

## 4. Публичный рантайм: контракт

### 4.1 Поток запроса

```
браузер → Host: hotel.<домен-поддоменов> или свой-домен.kz
  → apps/sites: нормализовать Host (как normalizeHost, packages/domain/src/web-analytics/source.ts:75-81, но без срезания www)
  → разрешить хост: SiteDomain в статусе ACTIVE → MarketingSite в состоянии PUBLISHED
       нет такого хоста или сайт PAUSED / ARCHIVED → нейтральная страница 404 (410 для ARCHIVED), без имени сайта
       хост не основной → 301 на основной хост с тем же путём
  → в том же ответе API: текущая опубликованная версия (published_version_id, spec_hash, spec) и publicFacts
       документ берётся из кэша, если spec_hash не изменился; другой версии по id рантайм не получает
  → проверить schemaVersion: рендерер этой версии есть? нет → 503 и тревога, не «как получится»
  → найти страницу по пути; нет → 404 сайта
  → отрендерить компоненты из реестра; текст экранируется; ассеты по публичным адресам
  → вставить счётчик и виджет WETOP с публичным ключом связанного TrackedSite (если включены в integrations)
```

### 4.2 Граница данных `apps/sites` ↔ `apps/api` (ФАКТ с MKT4 для `current`, с MKT7 для превью)

**ФАКТ MKT4 (06.10.2026).** Путь `GET /sites-runtime/current` и ключ `SITES_RUNTIME_KEY` есть
(`apps/api/src/sites-runtime/`). Отличия от кандидата ниже: `SiteDomain` ещё нет, поэтому хост разрешает только карта
dev и test (`SITES_RUNTIME_DEV_RESOLVER=1` и `SITES_RUNTIME_DEV_HOSTS`, вне `production`), `primaryHost` всегда `null`;
`assets` всегда `{}`; неверный документ даёт 503 `spec_invalid`; цены в ответе нет: цена «от» живая, браузер берёт её у `/w/from-prices` (Q-276).

**ФАКТ MKT7 (07.10.2026).** Хост разрешает строка `site_domains` в `ACTIVE` (карта dev и test остаётся только для
стендов), `primaryHost` настоящий, неосновной хост сайта Worker уводит 301 на основной; архивный и неизвестный хост дают
одинаковый нейтральный 404. Превью: `GET /sites-runtime/preview?token=` тем же ключом плюс действующий токен (HMAC-SHA256
секретом `SITE_PREVIEW_SECRET`, 60 минут, не дальше 24 часов вперёд); без секрета превью выключено (503), просроченный
токен 410, чужой или испорченный 404. Контракт: [`site-publication-v0.md`](site-publication-v0.md).

**ФАКТ MKT9 (07.10.2026).** Редактор сайта в стойке (`/marketing/site/editor`): ручная правка формами, ИИ-правки
`PATCH` и `SECTION`, история версий, смысловая разница и восстановление старой версии как нового черновика; всё одной
цепочкой неизменяемых версий, публикация не меняется. Чтение версии по id есть только у управления (вошедший,
`settings`), рантайм по-прежнему видит только опубликованную версию и превью. Контракт:
[`site-editor-v0.md`](site-editor-v0.md).

**ФАКТ MKT8 (07.10.2026).** `assets` больше не пустой: подписанный GET приватного S3 в Казахстане (Q-270) на час для
каждой ссылки этой версии на ассет филиала сайта нужного вида; отдельного чтения ассета по id нет. Хранилища нет:
пусто. Контракт и библиотека: [`site-assets-v0.md`](site-assets-v0.md).

Рантайм ходит в API по узкому служебному ключу (кандидат `SITES_RUNTIME_KEY`), тем же образцом, что узкие ключи
помощника и сборщика (`apps/api/src/auth/auth.guard.ts:60-113`, сравнение `timingSafeEqual` :39-46).

**Главный инвариант R1.** Служебный ключ рантайма сам по себе **не читает историю содержимого сайтов**. По хосту он
получает ровно одну версию: ту, на которую **сейчас** указывает `published_version_id` сайта, разрешённого по этому
хосту. Чтения версии по её `id` у рантайма нет вообще: ни текущей, ни ранее опубликованной, ни черновой.

| Кандидат | Ответ | Правило |
|---|---|---|
| `GET /sites-runtime/current?host=<host>&knownSpecHash=<hash>` | `siteId`, `primaryHost`, `state`, `locale`, `versionId` и `specHash` текущей опубликованной версии; `spec` (опускается, если `knownSpecHash` совпал: рантайм берёт документ из своего кэша); публичный ключ связанного `TrackedSite` и флаг `bookingEnabled`; публичный адрес API для `/w/*` и `/a/*`; карта `assetId → публичный адрес` только для ассетов этой версии; `publicFacts` (§4.4) | только `SiteDomain` в `ACTIVE` и сайт в `PUBLISHED`; версия всегда берётся по указателю `published_version_id` в той же транзакции чтения, что и сайт; `knownSpecHash` служит только проверкой свежести кэша и ничего не открывает: другая версия в ответ не попадает |
| `GET /sites-runtime/preview?token=<t>` | то же для одной версии из токена, `noindex` | отдельный механизм, не правило «текущей версии»: токен подписан API, содержит `siteId`, `versionId`, срок (до 24 часов) и выдаётся только в управлении после проверки строгого scope (§5); один служебный ключ без действующего токена здесь ничего не получает; ответ с `X-Robots-Tag: noindex, nofollow`, не кэшируется публично; срез MKT7 |

**Откат не открывает истории рантайму.** Откат делает только API управления: проверяет, что выбранная версия
принадлежит тому же сайту и раньше была опубликована (журнал `marketing_site_publications`), прошла проверку схемы и
ссылки на ассеты и категории сейчас годны; затем одной транзакцией переставляет `published_version_id` и пишет строку
журнала. Только после этого рантайм увидит её как текущую через тот же `/sites-runtime/current`.

Бронь (`B-BOOK`) браузер посетителя берёт напрямую у публичного API существующими путями `/w/config`,
`/w/availability`, `/w/book`; цену «от» (`B-FROMPRICE`) узким публичным контрактом `GET /w/from-prices?k=` (MKT4, Q-276 RESOLVED OWNER 07.10.2026: тариф брони сайта, 30 ночей, полная вместимость, без стоп-продажи; подсказка тарифа, а не обещание мест). Рантайм не
проксирует бронь и не держит у себя данные гостей. `B-CATEGORY` и `B-CHECKINOUT` приходят в `publicFacts` (§4.4).

### 4.3 Обязательные свойства рантайма

- нет сессии стойки, нет куки `wetop_scope`, нет `X-Wetop-Scope`; организация, Business и Location определяются только
  хостом через `SiteDomain`;
- никогда не читает `latest_version_id`; только `published_version_id` или подписанное превью;
- не исполняет код клиента: в HTML только скрипты WETOP (`/a/pms.js`, `/w/widget.js`, Turnstile от
  `challenges.cloudflare.com`), JSON-LD как `application/ld+json` (не исполняется);
- заголовки: CSP без `unsafe-inline` для скриптов, `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`;
- кэш: документ версии по `specHash` (содержимое неизменяемо), но право его показывать каждый раз подтверждает
  ответ `/sites-runtime/current`; сам этот ответ живёт коротко (кандидат 60 с) и сбрасывается при публикации,
  откате, паузе и снятии домена; `publicFacts` живут не дольше того же срока;
- превью: отдельный хост превью, `noindex` всегда, не кэшируется публично, токен с коротким сроком;
- SEO: `robots.txt` и `sitemap.xml` строятся по хосту из опубликованной версии; на хосте превью `robots.txt`
  запрещает всё; canonical только на основной хост.

### 4.4 Безопасные публичные факты: источник `B-CATEGORY` и `B-CHECKINOUT` (ПРЕДЛ; поправка владельца 06.10.2026)

Публичный `/w/availability` требует дат заезда и выезда (`packages/domain/src/web-booking/request.ts:87-149`) и для
первого рендера страницы не годится. Поэтому живые факты сайта приходят рантайму в ответе `/sites-runtime/current`,
полем `publicFacts`:

```
publicFacts: {
  loadedAt: <момент чтения>,
  checkInTime: "14:00" | null,
  checkOutTime: "12:00" | null,
  categories: [ { code, active, capacityAdults } ]   // только коды, на которые ссылается текущая опубликованная версия
}
```

Правила:
- объект (`Property`) берётся из `MarketingSite.location_id` (Location → Property, `properties.location_id`), а не из
  запроса браузера; архивный Location, архивный Business или чужая цепочка не разрешаются вовсе (сайт не отвечает);
- в `categories` попадают только коды из секций `accommodations` и `pricing` текущей опубликованной версии; неизвестный
  объекту код возвращается как `active: false`, без других полей;
- только перечисленные поля: без внутренних заметок, идентификаторов базы, цен и внутренностей тарифов, ПД и секретов;
  новое поле в `publicFacts` добавляется только решением, как поле публичного контракта;
- срок жизни короткий, тот же, что у ответа `current` (кандидат 60 с);
- не загрузилось: старые значения не выдумываются; карточка категории прячет живые поля (вместимость, цену) и
  остаётся с текстом снимка, строка времени заезда скрывается; форма брони работает своим путём `/w/*`;
- для Beauty и Food набор фактов будет своим (часы филиала, услуги) по тому же правилу.

Реализация контракта входит в MKT4: **сделано** (`apps/api/src/sites-runtime/sites-runtime.service.ts`). Если факты не
прочитались, `publicFacts` равен `null`, а сайт всё равно отвечает.

## 5. Управление: scope и права (УТВ принцип, ПРЕДЛ детали)

Каждая операция управления (создать сайт, сохранить версию, запустить генерацию, загрузить ассет, опубликовать,
откатить, приостановить, добавить домен) проходит **строгий scope филиала**:

1. есть вошедший человек и его членство в организации;
2. указатель `X-Wetop-Scope` (кука `wetop_scope`, `apps/web/src/lib/scope-pointer.ts:6-39`) разобран
   (`apps/api/src/auth/scope.ts:31-74`) и дал scope `LOCATION`;
3. Business этой организации в статусе `ACTIVE`, Location этого Business в статусе `ACTIVE`;
4. вертикаль Business совпадает с ожидаемой (v0: `HOSPITALITY`);
5. в транзакции изменения строки организации, Business и Location берутся под блокировку и перепроверяются, как в
   `foodTransaction` (`apps/api/src/food-service/scope.ts:56-73`) и `beautyTransaction` (`apps/api/src/beauty/scope.ts:94-113`).

Любой сбой это отказ (403 или 409 со словами), а **не** откат в `ORGANIZATION`: сегодняшний `resolveScope` молча
откатывается (`apps/api/src/auth/scope.ts:7-11`), а `organizationPropertyRef` и `organizationLocationRef` берут самый
ранний объект или филиал без проверки статуса (`apps/api/src/database/property-ref.ts:124-152`,
`apps/api/src/database/location-ref.ts:198-228`). Управление сайтом этими путями не пользуется. `organizationId`,
`businessId`, `locationId` из тела запроса не принимаются; сайт, версия, ассет и домен ищутся только внутри
проверенного Location.

**Сделано в MKT3 (API `/marketing/site`, `apps/api/src/marketing-site/scope.ts`).** Ответы строгого scope:
указатель прислан, но сервер его не подтвердил (устаревший, чужой, архивный филиал или бизнес) → 403; указателя нет
или выбрана организация либо только бизнес → 409 «Выберите филиал»; бизнес не гостиница → 403 «Сайт и SEO пока доступны
только гостиницам». Тело принимает только свои поля, любое лишнее (в том числе `organizationId`, `businessId`,
`locationId`) → 400. Метка направления `@RequiresBusinessCapability` у маршрутов намеренно не стоит: без указателя она
проверяла бы гостиничный путь по умолчанию вместо ответа 409.

Права: кандидат прежнее `settings` (`packages/domain/src/accounts/permissions.ts:18`, OWNER и MANAGER), как у `/website`
сейчас. Нужна ли администратору (STAFF) хотя бы аналитика сайта, отдельный вопрос (Q-273), MKT1B и MKT2 от него не
зависят.

## 6. Маршруты стойки и совместимость (ПРЕДЛ, реализация в MKT2 и позже)

```
/marketing/site/builder    бриф и ИИ-команды
/marketing/site/pages      страницы и секции, ручная правка
/marketing/site/seo        SEO сайта и страниц
/marketing/site/booking    бронь с сайта (сегодняшняя вкладка /website/booking)
/marketing/site/analytics  аналитика (сегодняшняя /website/analytics)
/marketing/site/settings   домены, внешний сайт, пауза (сегодняшняя /website/settings)
```

**ФАКТ, сегодня:** `/website`, `/website/booking`, `/website/analytics`, `/website/settings`
(`apps/web/src/app/website/*`, вкладки `apps/web/src/lib/website.ts:15-20`), пункт меню в группе «Продажи»

`/analytics/setup` → `/website/settings` (`apps/web/next.config.ts:12-17`).

Путь без поломок:
1. MKT2: группа меню «Маркетинг» с пунктом «Сайт и SEO», который ведёт на **существующий** `/website`; адреса не
   меняются. **Сделано в ветке 06.10.2026, ждёт ревью владельца** (`plans/mkt2-marketing-hub-2026-10-06.md`):
   вкладка «Маркетинг» после «Продаж» (право `settings`, своего права нет, Q-273 открыт), пункт «Сайт и SEO» ведёт в
   хаб `/marketing`, карточка «Сайт и SEO» на хабе кнопкой «Открыть» ведёт в `/website`; из «Продаж» пункт сайта снят,
   страница `/website` осталась в реестре ради прав и заголовка; `activeMenuRoute` отдаёт `/marketing` для
   `/website/*`, поэтому подсвечена «Маркетинг»; над заголовком страниц сайта ссылка «Маркетинг» (`crumbs`). Хаб
   ничего не спрашивает у API. Ссылки на `/website` из отчётов, продавца и филиалов не менялись: они ведут прямо в
   функции сайта и остаются верными.
2. Когда появятся новые страницы `/marketing/site/*`, вкладки переезжают туда, а `/website/*` получают временные
   редиректы 307 тем же приёмом, что `/analytics` (постоянный 308 браузер запоминает навсегда).
3. Вместе с переездом обновляются ссылки, которые сегодня ведут в `/website`: `apps/web/src/app/reports/page.tsx:252-260`,
   `apps/web/src/app/ai-seller/[[...section]]/page.tsx:503`, `apps/web/src/lib/branch-destination.ts:33,40`, и спеки
   (`tests/ui/website.spec.ts`, `workspace.spec.ts`, `navigation.spec.ts`, `top-menu.spec.ts`, `requests.spec.ts`,
   `reports-hub.spec.ts`, `tests/e2e/web-analytics.spec.ts`, `tests/e2e/web-booking.spec.ts` и другие из отчёта MKT0 §4.1).
4. Редиректы держатся не меньше одного релиза после переезда; тест сверяет каждую пару.

**Решение о совместимости (MKT3, 06.10.2026).** Хаб `/marketing` открывается только в гостиничном филиале
(`requireVertical(['HOSPITALITY'])`; салон уводится в свой календарь, ресторан в план зала). Страницы `/website/*`
по направлению **не меняются**: они работают с `TrackedSite` объекта и живут по прежним правилам, пока вкладки не
переедут в `/marketing/site/*` (п. 2). Сайт в MKT3 не заводит `TrackedSite`: связь появится при первой публикации (MKT7).

Зарезервированные слаги платформенного поддомена (кандидат): `www`, `app`, `api`, `assistant`, `seller`, `admin`,
`mail`, `status`, `preview`, `static`, `assets`, `cdn`, `help`, `support`, `wetop`, `docs`, `blog`, слова из 1–2 букв.

## 7. Жизненный цикл: полный сценарий

Три отдельных статуса (`DATA_MODEL.md` §29.8): сайт, задача генерации, домен. Версия статуса не имеет: она либо
черновая, либо на неё указывает `published_version_id`.

| Шаг | Сайт | Версия | Задача | Домен |
|---|---|---|---|---|
| Новый сайт | создан в `DRAFT`, версий нет | | | |
| Бриф и генерация | `DRAFT` | | `QUEUED → RUNNING → SUCCEEDED`, результат проверен схемой | |
| Сгенерирован | `DRAFT` | v1 (`AI`), `latest = v1` | `SUCCEEDED`, `output_version_id = v1` | |
| Превью | `DRAFT` | v1 по подписанной ссылке, `noindex` | | |
| Публикация | `PUBLISHED` | `published = v1`; журнал `PUBLISH v1` | | платформенный поддомен `PENDING → ACTIVE`; хост в `TrackedSite.hosts` |
| Правка черновика | `PUBLISHED` (рантайм показывает v1) | v2 (`MANUAL`, родитель v1), `latest = v2` | при ИИ-правке: новая задача `PATCH` | |
| Повторная публикация | `PUBLISHED` | `published = v2`; журнал `PUBLISH v2` | | |
| Откат | `PUBLISHED` | `published = v1` (из журнала публикаций); `latest` не меняется; журнал `ROLLBACK v1` | | |
| Пауза | `PAUSED` | указатели не меняются; журнал `PAUSE` | | хост остаётся, рантайм отдаёт 404 |
| Возобновление | `PUBLISHED` | журнал `RESUME` | | |
| Архив | `ARCHIVED` | версии хранятся; журнал `ARCHIVE` | активные задачи `CANCELLED` | все домены `REMOVED`, хосты убраны из `TrackedSite.hosts` |
| Сбой генерации | без изменений | новой версии нет | `FAILED` с кодом и замаскированным текстом | |

Опубликованная версия неизменяема всегда. Публикация проверяет документ заново (ассеты `READY`, категории
существуют) и при сбое ничего не переключает.

## 8. Будущие вертикали (проверка архитектуры, не реализация)

Ничто в контракте не привязано к `Property`: владелец `Location`, ссылки на данные в `SiteSpec` типизированы
привязками, реестр секций зависит от `site.vertical`.

| Вертикаль | Чем станет сайт | Что добавится | Что не меняется |
|---|---|---|---|
| Beauty | сайт салона филиала | реестр `beauty`: секции `services` (каталог `BeautyService` и `LocationService`, живые цена и длительность), `masters` (`Employee` через `EmployeeLocation`), `appointment-booking` (публичная запись, отдельный будущий контракт, не `/w/*`) | `MarketingSite`, версии, публикация, домены, ассеты, рантайм, SEO |
| Food | сайт заведения | реестр `food`: `venue` (часы из `ServicePeriod`), `menu` (будущая модель), `table-booking` (публичная бронь стола, будущий контракт поверх `RestaurantReservation`) | то же |

Общие секции (`hero`, `about`, `features`, `gallery`, `contacts`, `faq`, `cta`) переиспользуются всеми вертикалями.
Для Beauty и Food `MarketingSite.tracked_site_id` остаётся NULL, пока `TrackedSite` висит на `property_id`; аналитика
для них потребует владения `TrackedSite` через Location (отдельное решение модели). Ни одна секция Beauty или Food в
реестр v0 не добавляется.
