# Изображения управляемого сайта, v0 (MKT8)

Статус: **07.10.2026, срез MKT8, в ветке, ждёт ревью владельца.** План: `plans/mkt8-site-assets-2026-10-07.md`. Модель:
`DATA_MODEL.md` §29.5, §29.9. Решение владельца: Q-270 (RESOLVED OWNER 07.10.2026, `QUESTIONS.md`). Выкладка и
хранилище: [`docs/ops/site-assets-storage.md`](../ops/site-assets-storage.md). Общая архитектура: [`README.md`](README.md).

Поток: загрузка или фото Channex → тип по содержимому → декодирование → снятие EXIF → поворот → уменьшение и
перекодирование → SHA-256 → приватный S3 в Казахстане → `SiteAsset` → проверка ссылок SiteSpec → превью → публикация →
`apps/sites` выводит картинку по подписанному адресу.

## 1. Хранилище (Q-270)

- Origin: приватный S3-совместимый бакет физически в Казахстане. Первый рабочий поставщик PS Cloud Object Storage, после
  письменного подтверждения, что проект, реплики и резервные копии только в Казахстане; без него Cloud24 S3 (Алматы).
  Cloudflare R2, Supabase Storage, AWS вне Казахстана, иностранный CDN как origin и диск API не используются.
- Поставщик не виден ни в базе, ни в коде домена: интерфейс `SiteAssetStorage` (`put`, `delete`, `signedGet`, `exists`),
  реализация `S3SiteAssetStorage` на AWS SDK v3 (`@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`), своей подписи
  нет. Переезд с одного поставщика на другого: переменные окружения и перенос объектов, схема та же.
- В базе только `storage_ref`: ключ `site-assets/<locationId>/<assetId>/<sha256>.webp` (`.png` у фавиконки). Не адрес,
  не подпись, не имя файла пользователя. CHECK в базе выводит ключ из строки целиком.
- Переменные: `SITE_ASSET_STORAGE=off|s3` (по умолчанию `off`), `SITE_ASSET_S3_ENDPOINT` (только `https:`, `http:` лишь
  на localhost), `SITE_ASSET_S3_REGION`, `SITE_ASSET_S3_BUCKET`, `SITE_ASSET_S3_ACCESS_KEY_ID`,
  `SITE_ASSET_S3_SECRET_ACCESS_KEY`, `SITE_ASSET_S3_FORCE_PATH_STYLE=0|1`, `SITE_ASSET_SIGNED_URL_TTL_SECONDS` (3600, от
  900 до 86 400). Значения только в `.env` сервера API.
- Закрыто по умолчанию: `off`, неполная или неверная настройка значит «хранилища нет». Тогда библиотека читается
  (метаданные без адресов), загрузка и импорт 503 `ASSET_STORAGE_UNAVAILABLE`, публикация, возобновление, откат и
  превью версии со ссылками на картинки 503 тем же кодом. Запасного диска, R2 или Supabase нет.
- Браузер не получает ни ключей, ни адреса бакета: только подписанный GET одного объекта на срок. Presigned PUT в v0 нет:
  файл идёт браузер → API в Казахстане → обработка → S3.

## 2. Обработка (`apps/api/src/marketing-site/asset-image.ts`, `sharp`)

1. Предел 10 МиБ (двоичных) на маршрут загрузки: multer держит файл в памяти, не на диске; общий JSON-парсер API не
   меняется. Больше: 413.
2. Тип только по сигнатуре: JPEG, PNG, WebP. SVG (без попыток очистки), GIF, AVIF, HEIC, TIFF, BMP, PDF, HTML, XML и всё
   прочее: 415 `UNSUPPORTED_MEDIA_TYPE`. Формат, который увидел декодер, обязан совпасть с сигнатурой.
3. Анимация и многостраничность: 415. Сторона больше 12 000 или больше 40 000 000 точек: 422 `IMAGE_TOO_LARGE` (по
   заголовку, до декодирования, и ещё раз пределом `limitInputPixels` декодера). Обрезанный и битый файл: 422
   `IMAGE_DECODE_FAILED`.
4. Ориентация EXIF переносится в пиксели; метаданные на выходе не сохраняются: ни EXIF (камера, серийный номер, время,
   GPS), ни XMP, ни ICC.
5. `IMAGE` → WebP качества 82, длинная сторона до 2400 без увеличения; `LOGO` → WebP 82 до 1600 с прозрачностью;
   `FAVICON` → PNG 512×512: вписать без растяжения и без увеличения, поля прозрачные.
6. SHA-256 от готовых байтов (не от сырого файла): один и тот же снимок с разным EXIF это одна картинка.

Сырой файл не сохраняется нигде: ни в S3, ни в базе, ни во временном файле, ни в резервной копии.

## 3. Маршруты управления

Все под входом, право `settings`, строгий scope одного филиала гостиницы (как MKT3). Филиал, бизнес, организация и
сайт из тела не принимаются (лишние поля 400).

| Маршрут | Что делает |
|---|---|
| `GET /marketing/site/assets` | библиотека филиала без `DELETED` (до 500): id, вид, тип, размер, стороны, sha256, состояние, ALT, источник, время, `previewUrl` (подписанный GET); `storage: READY|OFF` |
| `POST /marketing/site/assets` | `multipart/form-data`: `file`, `kind` (`IMAGE`, `LOGO`, `FAVICON`), необязательно `defaultAlt` (JSON). Новый 201, повтор той же картинки того же вида 200 с тем же ассетом |
| `PATCH /marketing/site/assets/:id` | только `{ defaultAlt }`: объект `ru`, `kk`, `en` до 150 знаков обычного текста или `null` |
| `DELETE /marketing/site/assets/:id` | логическое удаление (§5), ответ `{ deleted, retainedForPublishedHistory }` |
| `GET /marketing/site/assets/channex` | фото Channex объекта этого филиала: `photoId` (sha256 адреса), описание, «для номера», порядок; адресов и id объекта у поставщика нет |
| `POST /marketing/site/assets/channex/import` | `{ photoIds }` от 1 до 20; ответ `{ imported, failed: [{ photoId, code }] }` |

Ассета по id для чтения нет ни у управления, ни у рантайма. Предел 30 загрузок и импортов на человека и организацию в
час (429). Повтор находит готовый ассет до записи в хранилище; гонка двух одинаковых загрузок упирается в частичный
UNIQUE `(location_id, kind, sha256) WHERE status <> 'DELETED'`, проигравший отдаёт ассет победителя и удаляет только свой
лишний объект (ключ содержит id). Запись в хранилище не удалась: строки нет, 503 `ASSET_STORAGE_FAILED`. Строка не
записалась после хранилища: свой объект удаляется, сбой удаления пишется в лог без ключа.

## 4. Ссылки версии SiteSpec

`siteSpecAssetRefs(spec)` (`packages/domain/src/marketing/assets.ts`) собирает ссылки по схеме, а не по любым ключам:
`site.brand.logo` → `LOGO`, `site.brand.faviconAssetId` → `FAVICON`, `pages[].seo.og.imageAssetId` и картинки секций
`hero`, `about`, `cta`, `gallery`, `accommodations` → `IMAGE`.

| Где | Правило |
|---|---|
| сохранение версии | каждая ссылка: ассет этого филиала, `READY`, ожидаемый вид; иначе 409 `ASSET_UNAVAILABLE` с путями (`unavailable` или `wrong_kind`); версия не сохраняется |
| публикация новой версии | то же, строки ассетов `FOR SHARE` |
| публикация уже публиковавшейся головы, возобновление, откат | версия историческая (есть запись журнала `PUBLISH`, `ROLLBACK`, `RESUME`): годится и удержанный `DELETED`, если объект есть в хранилище (`exists` только для них); нет объекта: 409 `ASSET_UNAVAILABLE` с кодом `missing_object` |
| выдача ссылки превью | обычная версия только `READY`; историческая и удержанные `DELETED` |

Чужой и несуществующий ассет неотличимы: один код, владельца ответ не называет. Общий отказ MKT7 `MEDIA_NOT_READY`
снят. Генерация MKT6 не меняется: ИИ по-прежнему не ставит ссылок на картинки.

## 5. Удаление и история публикаций

`DELETE` переводит ассет в `DELETED` под замком строки `FOR UPDATE`. `assetUsedByPublishedHistory` разбирает версии
сайтов этого филиала (в том числе архивных) с записью журнала публикации приложением, а не поиском строки в JSON.

- Ассет хоть раз опубликованной версии физически остаётся: библиотека его не показывает, текущий сайт и откат видят.
  В новую версию его не вставить (409).
- Ассет только из черновиков: после записи `DELETED` объект удаляется; сбой удаления не возвращает ассет и пишется в лог.
- Гонка с публикацией: публикация берёт ассеты `FOR SHARE`, удаление `FOR UPDATE`. Публикация раньше: удаление видит её
  запись в журнале и объект оставляет. Удаление раньше: публикация видит `DELETED` и отказывает.

## 6. Рантайм и Worker

- `GET /sites-runtime/current` и `preview` отдают `assets: { "<assetId>": "<подписанный GET>" }` только по ссылкам этой
  версии, только ассетов филиала сайта нужного вида: у текущей версии `READY` и удержанные `DELETED`, у превью обычной
  версии только `READY`. Хранилища нет или выборка упала: пусто, сайт отвечает без картинок.
- Подпись 3600 с: заметно дольше кэша страницы (60 с) и устаревшей копии контракта Worker (10 мин). В базе подписей нет.
- Worker принимает адрес картинки только `https:` с именем хоста, без логина, не localhost и не IP; иначе адрес
  выбрасывается и пишется событие `sites.asset_url_rejected` (id ассета, без адреса). `img-src` получает ровно origin-ы
  фактических адресов (ни `https:`, ни `*`); в `script-src`, `connect-src`, `frame-src` они не попадают. Без картинок
  политика прежняя.
- Выводятся картинки секций, логотип в шапке, `<link rel="icon">` и `og:image`. В превью картинки есть, брони, счётчика и
  цены «от» по-прежнему нет.

## 7. Импорт из Channex

Объект только этого филиала (то же сопоставление, что у брифа MKT5). Браузер присылает только `photoId`, адрес берёт
сервер из свежего ответа Channex. Загрузчик (`asset-fetch.ts`): только `https:`, без логина, порт 443, IP-адрес в адресе
не принимается; имя разрешается до соединения, все его адреса обязаны быть публичными (не loopback, не RFC 1918, не
link-local, не CGNAT, не ULA, не служебные, не документационные); соединение идёт ровно на проверенный адрес (своя
функция `lookup`); до 3 переадресаций, каждая проверяется заново; 10 с на путь; тело до 10 МиБ; `Content-Type` не
учитывается, дальше та же обработка, что у загрузки. Ошибки по фото кодом (`UNKNOWN_PHOTO`, `HOST_NOT_PUBLIC`,
`URL_REJECTED`, `UNSUPPORTED_MEDIA_TYPE` и прочие) без тела ответа и адреса. Описание фото становится подсказкой ALT на
языке сайта, только если проходит правила ALT. Импорт в документ сайта ничего не вставляет (MKT9).

## 8. Журнал и логи

`marketing.site.asset.uploaded`, `.imported`, `.alt_changed` (языки, без текста), `.deleted`
(`retainedForPublishedHistory`): id, вид, источник, тип, размер, стороны, sha256. Никогда: байты, EXIF, подписанный
адрес, ключ объекта, секреты, адрес Channex.

## 9. Стойка

«Маркетинг → Изображения сайта» (`/marketing/site/assets`, ссылки с хаба и со страницы публикации): загрузка с выбором
назначения и подсказкой 10 МиБ (больше на сервер не уходит), карточки с картинкой, размером, сторонами и источником,
подпись ALT, удаление с вопросом и честным итогом, импорт фото менеджера каналов по выбору. Редактора страниц и выбора
картинки для секции нет (MKT9). CSP стойки пока report-only, поэтому картинки с хранилища в ней не ломаются; когда
политику включат принудительно, в `img-src` стойки добавляется origin хранилища.

## 10. Чего в MKT8 нет

Рабочего бакета и ключей, миграций на рабочей базе, выкладки, переноса настоящих фото. Presigned PUT и загрузки частями,
нескольких размеров и `srcset`, AVIF, кадрирования и точки фокуса, выбора картинки в редакторе (MKT9), своих доменов
(MKT10).
