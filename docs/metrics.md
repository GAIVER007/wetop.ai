# Каталог метрик отчётов (RPT2.3a, предложение от 09.10.2026)

Статус: **принято владельцем 09.10.2026** (ADR-154, `Q-282…Q-288` закрыты умолчаниями). Код приводится к каталогу срезами RPT2.3b и RPT2.4; до среза экран может считать по-старому, расхождение названо в подписи.
Основа: аудит `reports/reports-2-0-rpt2-1-2026-10-09/README.md`. Здесь одна формула на показатель, источник, дата и
граничные случаи. Любой экран и любая выгрузка берут цифру из одной серверной функции; формулу в вебе не повторять.

## 0. Общие правила

| Правило | Решение |
|---|---|
| Деньги | integer minor units (`bigint`), наружу строкой `...Minor`. Float запрещён (AGENTS §12) |
| Проценты | целая арифметика: `(часть × 1000 + знаменатель / 2) / знаменатель`, один знак после запятой, половина вверх. Одна общая функция для дашборда, юнитов и рынка (сегодня их три с разным округлением) |
| Деление денег | ADR, RevPAR, средний чек: округление до тиына, половина вверх |
| Нулевой знаменатель | `null`, на экране прочерк. Процент изменения при нулевой или неизвестной базе не показывается |
| Период | `[from, to]` включительно, даты по часовому поясу объекта (`Property.timezone`). События (платежи, возвраты, операции) отбираются по суткам объекта, `[начало from, начало to+1)` |
| Предел | не больше 366 дней за запрос, везде одинаково |
| Гранулярность | день, неделя (ISO, с понедельника), месяц. Неполные крайние недели и месяцы помечаются |
| Сравнение | предыдущий период той же длины, сразу перед текущим; для месяца допустим тот же месяц год назад |
| Филиалы | у каждого филиала свой пояс и своя валюта. Итог по организации только по одной валюте, разные валюты раздельными строками, без курса |
| Живой расчёт | отчёт пересчитывается на каждый запрос, закрытых периодов нет. В выгрузке печатается время формирования. «На дату» умеют только долги и остатки кассы (формулы ниже) |
| Подпись базы | у каждой цифры в интерфейсе видна база: «по дате услуги», «по дате заезда», «по дате платежа» |

## 1. Фонд и загрузка

| Метрика | Формула | Источник |
|---|---|---|
| Доступные единицы-ночи | `Σ по дням периода (активные единицы − единицы под блокировкой в эту ночь)` | единицы фонда, блокировки шахматки |
| Занятые единицы-ночи | ночи размещений проживаний не CANCELLED и не NO_SHOW; ночь выезда не занята; CHECKED_OUT входит | размещения |
| Загрузка | `занятые / доступные` | |
| ADR | `выручка за ночи / занятые единицы-ночи` | п. 2 |
| RevPAR | `выручка за ночи / доступные единицы-ночи` (то же, что `ADR × загрузка`) | п. 2 |

Правила:
- **Блокировки вычитаются** из знаменателя: MAINTENANCE, OUT_OF_ORDER, MANAGEMENT, OTHER. Блок ставится только в
  свободную клетку, поэтому числитель и блок не пересекаются. В отчёте отдельной строкой «закрыто для продажи, ночей»,
  чтобы падение загрузки объяснялось.
- **Номера и койки не смешиваются.** Каждая метрика загрузки, ADR и RevPAR считается отдельно для номеров (`fund=rooms`)
  и койко-мест (`fund=beds`). При `fund=all` на экране два значения рядом, общего процента нет. Деньги, брони, гости при
  `all` суммируются: это не знаменатель единиц-ночей.
- **Проживания без места** (Q-107) в загрузку не входят, показываются отдельной строкой.
- **Деактивированная единица** выпадает только с даты деактивации. Пока истории деактивации нет, она выпадает из всего
  периода: ограничение, помечается в подсказке.
- Day-use в модели не заведён, в расчёт не входит. Продление и переселение идут по размещениям: каждая ночь считается
  там, где она занята, один раз. Ранний выезд: занята ровно ночами по размещению. Групповая бронь: каждая бронь отдельно.

## 2. Деньги: четыре разных показателя

| Показатель | Формула | Дата | Источник |
|---|---|---|---|
| **Начислено** | `Σ Charge.amount` без `voidedAt`, все виды (проживание, услуги, штрафы, корректировки) | `serviceDate` | начисления |
| **Поступления** | `Σ Payment.amount` со статусом COMPLETED | `paidAt` по суткам объекта | платежи |
| **Возвраты** | `Σ Refund.amount` | `createdAt` по суткам объекта | возвраты |
| **Чистые поступления** | `Поступления − Возвраты` | | |
| **Расходы** | `Σ CashOperation` вида EXPENSE, статус COMPLETED, переводы между кассами исключены | `occurredAt` по суткам объекта | кассовые операции |
| **Остаток кассы на дату D** | `Σ платежей (живые способы) − возвраты + приход − расход ± переводы` по всем операциям до конца дня D | | касса |
| **Денежный поток за период** | по дням: `поступления в кассу − возвраты в кассу + прочий приход − расходы`; переводы между кассами в потоке не показываются | | |
| **Долг на дату D** | см. ниже | | |
| **Прибыль** | **не показывается** | | |

Правила:
1. Начислено, Поступления, Возвраты, Расходы, Остаток никогда не складываются друг с другом и не выводятся друг из друга.
   Поле `balanceMinor` из `/finance/report` (начислено минус оплачено плюс возвраты за период) в интерфейсе называется
   **«Разница периода»** и не называется долгом.
2. В поступления входят все способы. Способы вне кассы (EXTERNAL оплата в OTA, DEPOSIT, CARD_GUARANTEE) показываются
   отдельной строкой «вне кассы». В остаток кассы и денежный поток они не входят.
3. **Долг на дату D.** Для каждой брони, у которой есть начисление с `serviceDate ≤ D`:
   `долг = Σ начислений (serviceDate ≤ D, не аннулированных на конец D) − Σ платежей (paidAt ≤ конец D, COMPLETED) + Σ возвратов (createdAt ≤ конец D)`.
   Положительные остатки суммируются. Отдельно «просрочено»: не CANCELLED/NO_SHOW и выезд не позже D. На «сейчас»
   формула даёт то же число, что нынешние `/finance/debts`. Возрастная разбивка: 0-7, 8-30, 31-90, больше 90 дней
   от даты выезда. Если для аннулирования нет даты `voidedAt`, расчёт «на прошлую дату» недоступен и интерфейс говорит об этом.
4. **Прибыль не считается**, пока нет достоверных себестоимости и расходов по проживанию. Единственное исключение: валовая
   прибыль бара (`выручка − себестоимость по проведённым продажам`), подписана именно так.
5. При `fund=rooms` или `beds` деньги по оплатам, возвратам и расходам нельзя разделить по фонду: эти карточки скрываются
   с пояснением «деньги считаются по объекту». Начислено делится по виду размещения.

### Выручка проживания: три разные базы, три разные подписи

| Название на экране | Формула | Где |
|---|---|---|
| Начислено за проживание | `Charge` вида ACCOMMODATION по `serviceDate` (заезд) | Финансы, KPI «Начислено» |
| Стоимость броней по заездам | `Σ ReservationItem.price` действующих мест, заезд в периоде | разрезы по категориям, источникам, каналам |
| Выручка за ночи | цена места, разнесённая по ночам проживания поровну, остаток копеек на последнюю ночь; берутся ночи внутри периода | только ADR и RevPAR |

Сверка: на экране строка «разница между начислением и стоимостью броней» (корректировки, ручные правки, сторно). Для
проживаний, целиком лежащих в периоде, «Выручка за ночи» равна «Стоимости броней по заездам». Это решение заменяет
оговорку Q-208 только для ADR и RevPAR; график «Выручка по заездам» остаётся.

## 3. Брони, отмены, гости

| Метрика | Формула |
|---|---|
| Брони | число броней с заездом в периоде, не CANCELLED и не NO_SHOW |
| Отмены | число броней с заездом в периоде, статус CANCELLED. Подпись «по дате заезда» |
| Незаезды | то же, NO_SHOW |
| Доля отмен | `отмены / (брони + отмены + незаезды)` |
| Гости | `Σ (взрослые + дети)` по действующим броням с заездом в периоде |
| Средний чек | `Σ ReservationItem.price действующих мест / число действующих броней` |
| Новые и повторные гости | **не показываются**, пока нет сквозной идентификации гостя (Q-281) |
| Отмены по дате отмены, срок до заезда | **недоступно**: даты отмены в модели нет. Требует изменения DATA_MODEL.md, отдельным предложением |

## 4. Источники и каналы

- Слово «доля» без уточнения запрещено. Есть **«Доля броней»** (`брони источника / все действующие брони`, дашборд)
  и **«Доля выручки»** и **«Доля ночей»** (каналы).
- Единственный источник правды по каналам: `GET /desk/dashboard/channels` (действующие места, заезд в периоде, право `reports`).
  Отчёт `GET /hotel/channel-report` по умолчанию перестаёт брать отменённые и незаезды (`status` по умолчанию
  «действующие»); отменённые остаются доступны явным выбором статуса и подписаны.
- ADR канала считается как у отеля: выручка за ночи в периоде / ночи в периоде.

## 5. Бар и услуги

- Продажа на счёт создаёт начисление с `serviceDate = дата продажи по суткам объекта`. Ранее созданные без даты:
  разовое дописывание даты по дате создания (финансовая операция, решает владелец, Q-284).
- Выручка бара за период: `Σ BarSale.totalRevenue` проведённых продаж по `createdAt` за сутки объекта. Продажа за наличные
  одновременно даёт приход в кассе: это разные показатели, их нельзя складывать. Себестоимость и валовая прибыль по тем
  же продажам. Отчёт бара получает параметры периода.
- «Услуги»: `Charge` вида SERVICE по `serviceDate`, группировка по услуге (уже есть).

## 6. Доступ и вертикали

- Право: `reports` для операционных метрик (шесть KPI, загрузка, брони, каналы). Деньги (поступления, возвраты, расходы,
  касса, долги, форма 910) пока под тем же `reports`; отдельное право «финансы» предложено, не вводится (Q-285).
- Экспорт повторяет права экрана и тот же серверный расчёт.
- Показатели гостиницы (загрузка, ADR, RevPAR, номера, койки) не показываются в салоне и ресторане. Для них отдельные
  блоки: у салона записи по статусам и выручка DONE, у ресторана статусы. Организация сравнивает филиалы по денежному
  итогу в одной валюте и по числу операций, но не складывает загрузку гостиницы с загрузкой мастеров.
- Отчёты филиала и отчёты организации: два уровня. Организация видит строки по филиалам и итог по валюте.

## 7. Контрольные проверки на одном числе

Для любого периода обязаны совпадать:
1. KPI на «Обзоре» = сумма строк детализации = итог выгрузки (одна серверная функция).
2. `Поступления − Возвраты` (в кассе) = изменение остатка кассы за период ± переводы и расходы, разница показана.
3. Сумма «Долга» на сегодня = итог `/finance/debts`.
4. Сумма выручки по категориям и по источникам = «Стоимость броней по заездам»; с «Начислено за проживание» расхождение объяснено строкой.
5. Сумма недельной и месячной раскладки = итог периода.
6. Граница месяца: проживание 30.09 → 02.10 даёт 1 ночь в сентябре и 1 ночь в октябре в «Выручке за ночи», начисление целиком в сентябре.
