# Бэкапы рабочей базы (Q-073)

**Почему это срочно.** Рабочая база — Supabase в Сингапуре, в ней с 19.09.2026 брони объекта (ADR-052). Организация
Supabase «hotel» — на бесплатном плане. По документации Supabase («Database Backups») ежедневные копии делаются только
на планах Pro, Team и Enterprise, а бесплатным проектам советуют выгружать данные самим и держать копию вне площадки.
До 24.09.2026 рабочая база не копировалась вовсе. Единственный снимок — `/root/backups/luxx-before-reset-2026-09-19.dump`
на той же машине, что стойка (проверка SECURITY.md, §8).

**Состояние на 24.09.2026, вечер — установлено и проверено на сервере.**
- Первая копия снята в 15:08 UTC: `/root/backups/wetop-20260924T150829Z.dump`, 203 КБ, права 600.
- Статистика рабочей базы (`pg_stat_statements`) показывает выгрузку всех 41 таблицы.
- Строка в cron стоит на 23:30 UTC.
- Проба восстановления на сервере — 41 таблица из 41, 9 751 строка, `inventory_units` 88, броней 16, миграций 19.
  Это ровно столько же, сколько в рабочей базе в тот момент (проверено запросом только на счёт). Расхождение ноль.

**Первая ночная по cron прошла (проверено 25.09.2026 по `pg_stat_statements`).** С контрольной точки 24.09 17:00 UTC
счётчик выгрузок у всех 41 таблицы вырос ровно на 2: ночной cron 23:30 UTC — единственный автоматический запуск в
окне — плюс одна ручная копия вечером. Времени запуска статистика не хранит; при сомнении время видно по именам
файлов: `ls -lt /root/backups | head -4`.

**Сторож копий выложен и проверен на сервере (25.09.2026, утро).** Владелец снял копию (`$BACKUP`, статус 06:36 UTC:
`wetop-20260925T063557Z.dump`, 205 КБ, 41 таблица), пересобрал `api` и `web`; `exec api cat /backup-status/last.json`
вернул этот статус из контейнера — том и переменная на месте. Клон на сервере — ветка `release` на `3da7a2c6`, она
старше ADR-078: перематывать `release` только вперёд (за `46d5daf9`), пересборка по прежней точке молча сняла бы
том статуса.

**Сторож стойки знает о копии (ADR-078, 24.09.2026, вечер).** Сторож
поднимает неисправность «Ночной копии базы нет», если:
- удачной копии нет 26 часов;
- статуса копии нет;
- статус не читается.

Она видна на экране «Неисправности». Сообщение в Telegram уходит днём, а если неисправность висит сутки — и ночью.

Вторая копия вне сервера (Q-073): владелец выбрал Cloudflare R2 02.10.2026 (ADR-137, замечание ментора). Скрипт
`scripts/ops/db-backup-offsite.sh` готов и проверен тестами; включает его владелец по разделу «Вторая копия вне
сервера» ниже.

Инструменты:

| Скрипт | Что делает |
|---|---|
| `scripts/ops/db-backup.sh` | `pg_dump -Fc` схемы `public`: таблицы, данные и журнал миграций. Проверяет копию `pg_restore --list` и кладёт её с правами 600 в `/root/backups/wetop-<UTC>.dump`. Затем пишет статус для сторожа `/root/backups/status/last.json`: время, имя, размер и число таблиц, без адреса базы (ADR-078). Копии старше 14 суток удаляет, чужие файлы в папке не трогает. Строку подключения не печатает, пароль в сообщении `pg_dump` маскирует |
| `scripts/ops/db-restore-check.sh` | Пробное восстановление: разворачивает копию в новую базу на **локальном** сервере PostgreSQL и сверяет таблицы и строки. Рабочую базу не трогает: нелокальный адрес получает отказ |
| `scripts/ops/db-backup-offsite.sh` | Вторая копия вне сервера (ADR-137): последнюю ночную копию шифрует публичным ключом age владельца и кладёт в бакет Cloudflare R2, сверяет размер, пишет статус `/root/backups/status/offsite.json`. Наружу только шифротекст; закрытого ключа на сервере нет. Сбой: ненулевой код и сообщение дежурным в Telegram |

Тесты: `tests/unit/db-backup.test.ts` (заглушки `pg_dump` и `pg_restore`), `tests/unit/db-backup-offsite.test.ts`
(R2 подменён папкой; настоящий `age` проходит круг до расшифровки, если он установлен) и
`tests/integration/db-backup-restore.test.ts` (вся цепочка на настоящей PostgreSQL; пропускается, если в PATH нет
`pg_dump` и `psql`).

## Что входит в копию

- Схема `public` целиком: все таблицы WETOP, данные и `_prisma_migrations`.
- Не входит схема автотестов `pms_test` и служебные схемы Supabase (`auth`, `storage` и т. д.): WETOP ими не пользуется.
- Не входит расширение `btree_gist`: копия одной схемы расширений не несёт. При восстановлении его ставят первым.

В копии то же, что в базе. Данные гостей обезличены (ADR-018, ADR-072), но в `users` лежат настоящие почты сотрудников и
хеши паролей. Поэтому копия хранится как сама база: права 600, папка только для root.

## Установка на сервере — владелец, один раз

Hostinger, `/root/wetop`. **Клиента PostgreSQL на сервере нет.** 24.09.2026 `pg_dump --version` ответил
«Command 'pg_dump' not found». Раньше здесь ошибочно стояло «клиент уже стоит, им снимали дамп 19.09». Ставить
его не нужно: копию снимает официальный образ `postgres:17`, в нём `pg_dump` 17 — той же версии, что Supabase. В
контейнер монтируются только три вещи: скрипт из клона, `.env` клона (только чтение) и папка копий. Поэтому скрипт
обновляет `git pull`, а пересобирать образ стойки не нужно.

```bash
cd /root/wetop && git pull                 # после слияния PR с этим скриптом
mkdir -p /root/backups && chmod 700 /root/backups
BACKUP='docker run --rm -v /root/wetop/scripts/ops/db-backup.sh:/db-backup.sh:ro -v /root/wetop/.env:/wetop.env:ro -v /root/backups:/root/backups -e ENV_FILE=/wetop.env postgres:17 bash /db-backup.sh'
$BACKUP                                    # первая копия руками; первый раз Docker скачает образ
# ждём строку: db-backup: wetop-…Z.dump — …, таблиц с данными: 41; копий в /root/backups: 1

# каждую ночь в 04:30 по Алматы (23:30 UTC) — после полной выгрузки ARI (03:00) и очистки счётчика (04:00)
( crontab -l 2>/dev/null | grep -v 'db-backup.sh'
  echo "30 23 * * * $BACKUP >> /var/log/wetop-db-backup.log 2>&1" ) | crontab -
crontab -l | grep db-backup                # строка на месте
```

Строка подключения берётся из `.env`: сначала `BACKUP_DATABASE_URL`, затем `DIRECT_URL`, затем `DATABASE_URL`.
Параметры Prisma (`pgbouncer`, `connection_limit`, `schema` и т. п.) скрипт срезает: `pg_dump` на них падает. Для
`pg_dump` нужно прямое подключение или сессионный режим пулера Supabase (порт 5432), а не транзакционный (6543). Если
первая копия упадёт на подключении, владелец вписывает в `.env` строку `BACKUP_DATABASE_URL=` с сессионным адресом из
панели Supabase (Connect → Session pooler) и повторяет `$BACKUP`.

С клиентом PostgreSQL 17 на хосте (`docs/ops/server-setup-2026-09-18.md` §2.1) то же самое делает просто
`cd /root/wetop && scripts/ops/db-backup.sh`.

### Сторож копий — владелец, один раз после слияния PR с ADR-078

Строку cron менять не нужно: скрипт берётся из клона, а статус он кладёт в ту же папку копий. Нужно только обновить
клон, один раз снять копию, чтобы появился статус, и пересобрать API с новым томом:

```bash
cd /root/wetop && git pull
BACKUP='docker run --rm -v /root/wetop/scripts/ops/db-backup.sh:/db-backup.sh:ro -v /root/wetop/.env:/wetop.env:ro -v /root/backups:/root/backups -e ENV_FILE=/wetop.env postgres:17 bash /db-backup.sh'
$BACKUP                                    # копия, а заодно статус /root/backups/status/last.json
ls -l /root/backups/status                 # last.json, права -rw-r--r--
cd deploy && docker compose -f compose.yml -f compose.hostinger.yml up -d --build api web
docker compose -f compose.yml -f compose.hostinger.yml exec api cat /backup-status/last.json   # статус виден в API
```

В последней строке ждём одну строку JSON: время, имя копии, размер и `"tables":41`. Через минуту на экране «Неисправности»
не должно быть «Ночной копии базы нет».

Если API пересобрать раньше, чем появится статус, сторож честно скажет «статус копии не найден». Неисправность
закроется сама после первой удачной копии.

Выключатель — `GUARD_BACKUP=off` в `.env` (например, на сервере, где копии снимает провайдер базы).

В контейнер API монтируется только папка `status` и только на чтение (`deploy/compose.yml`). Самих копий API не видит:
в них хеши паролей и почты сотрудников, а API смотрит в интернет через туннель. Это держит проверка в
`tests/unit/deploy-server.test.ts`.

## Вторая копия вне сервера (Cloudflare R2, ADR-137)

Копия на том же сервере спасает от ошибок в базе, но не от потери сервера или аккаунта хостинга. Вторая копия каждую
ночь уходит в бакет Cloudflare R2 зашифрованной: публичным ключом age владельца. Закрытый ключ хранит только владелец,
вне сервера. Утечка бакета или ключа R2 не раскрывает данных, а потеря сервера не уносит копии.

Копия схемы `public` содержит почты сотрудников и хеши паролей, данные гостей обезличены (раздел «Что входит в
копию»). Вопрос размещения данных тот же, что у самой базы в Сингапуре: после переезда в РК (Q-070а) решить заново.

### Включение: владелец, один раз (значения в чат не диктуются, SECURITY.md §3)

1. **Ключ шифрования, на маке.** `brew install age`, затем `age-keygen -o ~/wetop-backup-key.txt`. Команда печатает
   публичный ключ `age1…`: он пойдёт на сервер. Файл `~/wetop-backup-key.txt` это закрытый ключ: сохранить его ещё
   и в менеджер паролей. Без него ни одну копию из R2 не расшифровать, а на сервер он не кладётся никогда.
2. **Бакет.** Панель Cloudflare → R2 → Create bucket, имя например `wetop-db-backups`. Номер аккаунта (Account ID)
   виден на странице R2.
3. **Ключ R2.** R2 → Manage API tokens → Create API token: права Object Read & Write, только бакет
   `wetop-db-backups`. Панель покажет Access Key ID и Secret Access Key один раз.
4. **Срок хранения**, в настройках бакета: правило жизненного цикла (Object lifecycle rules) удалять объекты
   старше 60 дней. По желанию блокировка бакета (Bucket lock) на 30 дней: тогда копии не удалить даже ключом
   с сервера.
5. **Сервер.** `apt install -y age rclone`, затем `rclone version`: нужна 1.59 или новее (Cloudflare: со старыми
   R2 отвечает 401). В Ubuntu 22.04 из apt приходит 1.53, тогда пакет `.deb` с rclone.org.
6. **Настройки**, в `/root/wetop/.env` строками:

   ```
   OFFSITE_AGE_RECIPIENT=age1…            публичный ключ из шага 1
   OFFSITE_R2_ACCOUNT_ID=…
   OFFSITE_R2_BUCKET=wetop-db-backups
   OFFSITE_R2_ACCESS_KEY_ID=…
   OFFSITE_R2_SECRET_ACCESS_KEY=…
   ```

   Закрытый ключ (`AGE-SECRET-KEY-…`) скрипт в этой строке не примет: откажется и сообщит дежурным.
7. **Первый запуск руками**, когда скрипт уже на сервере (клон `/root/wetop` обновляет автовыкладка):

   ```bash
   /root/wetop/scripts/ops/db-backup-offsite.sh
   # ждём: db-backup-offsite: в R2 wetop-db/wetop-…Z.dump.age, … байт, зашифровано для age1…
   ```

   В панели R2 в бакете появится папка `wetop-db` с этим файлом.
8. **Каждую ночь**, через 15 минут после ночной копии (23:30 UTC):

   ```bash
   ( crontab -l 2>/dev/null | grep -v 'db-backup-offsite.sh'
     echo "45 23 * * * /root/wetop/scripts/ops/db-backup-offsite.sh >> /var/log/wetop-db-backup.log 2>&1" ) | crontab -
   crontab -l | grep db-backup-offsite
   ```

### Проба восстановления из R2: сразу после включения и раз в месяц

Копия, которую ни разу не расшифровали, тоже не копия. На маке:

```bash
# файл скачать в панели R2 (бакет → wetop-db → файл → Download)
age -d -i ~/wetop-backup-key.txt -o wetop.dump ~/Downloads/wetop-…Z.dump.age
```

Получится обычная копия `pg_dump`; проверить её тем же `db-restore-check.sh`, что и ночную (раздел «Пробное
восстановление»). Числа таблиц и строк должны совпасть с копией той же ночи на сервере.

## Проверка раз в неделю — минута

```bash
ls -lt /root/backups | head -4             # свежие wetop-….dump за последние сутки
tail -3 /var/log/wetop-db-backup.log       # последняя строка — «db-backup: wetop-… таблиц с данными: 41»
cat /root/backups/status/offsite.json      # вторая копия: время за последние сутки, объект wetop-db/….dump.age
```

Сбой скрипт пишет в тот же журнал и завершается с ненулевым кодом. После выкладки ADR-078 о нём узнаёт и сторож
стойки. Если удачной копии нет 26 часов или статус не найден или не читается, появляется неисправность «Ночной копии
базы нет»: на экране «Неисправности» и в Telegram днём, а если висит сутки — и ночью.

Недельная проверка при этом остаётся. Сторож видит только то, что копия свежая, а не то, что она восстанавливается —
для этого есть проба ниже.

## Пробное восстановление — раз в месяц и перед каждой миграцией

Копия, которую ни разу не разворачивали, — не копия. Проба делается в отдельной PostgreSQL в Docker на том же сервере.
Контейнер живёт минуту, наружу портов не открывает. `psql` и `pg_restore` берутся из него же, так что клиент на хосте
не нужен:

```bash
docker run -d --rm --name wetop-restore-check -e POSTGRES_HOST_AUTH_METHOD=trust \
  -v /root/backups:/root/backups:ro -v /root/wetop/scripts/ops/db-restore-check.sh:/db-restore-check.sh:ro postgres:17
until docker exec wetop-restore-check pg_isready -h 127.0.0.1 -q; do sleep 1; done   # сервер принял TCP
docker exec -e RESTORE_CHECK_URL=postgresql://postgres@127.0.0.1:5432/postgres wetop-restore-check \
  bash /db-restore-check.sh "$(ls -t /root/backups/wetop-*.dump | head -1)"
docker rm -f wetop-restore-check
```

Ждём строку вида (первая проба на сервере, 24.09.2026):

```
restore-check: wetop-20260924T150829Z.dump восстановлена — таблиц 41 из 41, строк 9751, inventory_units: 88, reservations: 16, _prisma_migrations: 19
```

Числа сверяются с рабочей базой запросом только на счёт: сразу после снятия копии они должны совпасть.

`inventory_units` должно быть 88 — контрольное число объекта (CLAUDE.md §6).

**Почему не просто `pg_restore`.** Копия схемы `public` начинается с `CREATE SCHEMA public`, а в новой базе схема уже
есть. Наивный `pg_restore` падает на первой строке: «schema "public" already exists». Это нашла первая же проба
24.09.2026. Скрипт пропускает по оглавлению копии схему и комментарий к ней, а `btree_gist` ставит до таблиц.

## Восстановление рабочей базы из копии (ступень 2 отката, ADR-137)

Решает и делает только владелец (CUTOVER.md, раздел ROLLBACK). Всё, что записано после копии, пропадает. До запуска:
стойка в ручном режиме, API и web остановлены, свежая копия испорченной базы снята (`$BACKUP`), копия, из которой
восстанавливаем, прошла пробу (`db-restore-check.sh`, раздел выше).

```bash
cd /root/wetop
RESTORE='docker run --rm -v /root/wetop/scripts/ops/db-restore-prod.sh:/db-restore-prod.sh:ro -v /root/wetop/packages/database/prisma/migrations:/migrations:ro -v /root/wetop/.env:/wetop.env:ro -v /root/backups:/root/backups:ro -e ENV_FILE=/wetop.env -e RESTORE_MIGRATIONS_DIR=/migrations postgres:17 bash /db-restore-prod.sh'
$RESTORE /root/backups/wetop-<время>.dump --yes-replace-production
# ждём: db-restore-prod: wetop-….dump восстановлена, таблиц с данными в копии: …; права повторены миграциями: 026 033 034 038 042
```

**Почему не просто `pg_restore`** (проба 02.10.2026 на локальной PostgreSQL со всей цепочкой миграций и правами
по умолчанию как у Supabase, `reports/mentor-review-2026-10-02/`). Копия снимается без прав (`--no-privileges`), а
таблицы при восстановлении создаются заново и получают права по умолчанию из миграции 026. Наивный `pg_restore`
давал роли стойки `wetop_app` 286 лишних прав: полный доступ к `users` с хешами паролей, к `password_resets`,
`channel_outbox` и ещё семи таблицам. Откат молча снимал бы SEC-1b. Скрипт после данных повторяет по порядку все
миграции, которые выдают или отзывают права (они повторяемы), и права совпадают с рабочими по всем 10 104 проверкам
(таблицы, столбцы, функции, последовательности, политики, RLS). Данные и права идут одной транзакцией: при любой
ошибке база остаётся как была. После восстановления скрипт сам проверяет, что `wetop_app` не читает `users` целиком.

Миграции прав берутся из клона. Если копия старше последней миграции прав и восстановление откатилось с ошибкой
вида «relation … does not exist», взять папку миграций коммита, выложенного во время копии:
`git archive <коммит> packages/database/prisma/migrations | tar -x -C /tmp/mig-<коммит>` и смонтировать её вместо
`/root/wetop/packages/database/prisma/migrations`.

Время: на копии схемы со всеми миграциями восстановление с правами заняло меньше секунды локально; по сети до базы
оценка 1–3 минуты. На рабочей базе скрипт ещё не запускался: учение на отдельном проекте Supabase до тихих суток.

Тесты: `tests/unit/db-restore-prod.test.ts` (подтверждение, пароль не в аргументах, порядок миграций прав) и
`tests/integration/db-restore-prod.test.ts` (настоящая PostgreSQL: копия, порча, восстановление, права до столбца).

## Бэкап → миграция → проверка → откат (AGENTS §14)

Production-миграцию делает только владелец (CLAUDE.md §3). Порядок:

1. **Бэкап** — `$BACKUP` (команда из установки) прямо перед миграцией, не полагаясь на ночную копию.
2. **Проба этой копии** — `db-restore-check.sh`, как выше. Не восстановилась — миграцию не начинать.
3. **Миграция** — `npm run migrate:deploy -w @pms/database` на сервере, по `docs/deploy.md`.
4. **Проверка** — `/health`, вход, «Сегодня», шахматка, карточка брони. Число строк в затронутых таблицах сверяется
   до и после запросом только на счёт.
5. **Откат.** Схема: `down.sql` этой миграции, он есть у каждой. Повреждённые данные: восстановление из копии шага 1
   скриптом `db-restore-prod.sh` (раздел «Восстановление рабочей базы из копии»). Оно заменяет рабочую базу целиком и
   теряет всё, что записано после копии, поэтому решает только владелец, и только после успешной пробы.

## Решение владельца — Q-073

Копия на той же машине спасает от ошибок в базе: неудачная миграция, скрипт, удаление. От потери сервера или
аккаунта Hostinger она не спасает. Поэтому нужна вторая копия вне сервера и ответственный за неё.

| Вариант | Что даёт | Цена | Что нужно |
|---|---|---|---|
| **А. Supabase Pro** | Supabase сам хранит 7 ежедневных копий и восстанавливает из панели | $25 в месяц | перевести организацию «hotel» на Pro |
| **Б. Копия ночного дампа наружу** | тот же файл уходит в другое хранилище, например Cloudflare R2 (аккаунт Cloudflare уже есть) или диск владельца | в пределах бесплатного объёма: схема `public` рабочей базы на 24.09 — 5,2 МБ вместе с индексами, сжатая копия меньше | ведро и ключ записи; команда отправки в cron после `db-backup.sh` |
| **В. После переезда в РК** | управляемый PostgreSQL на ps.kz с копиями провайдера (`docs/ops/server-kz-2026-09-16.md`) | в тарифе | переезд (Q-070а) |

Рекомендация: ночная копия на сервере — сейчас, одной командой выше. Вторая копия — А или Б до переезда в РК, затем В.
Ответственный — владелец: только у него есть доступ к серверу и аккаунтам.

раздел «Вторая копия вне сервера».
