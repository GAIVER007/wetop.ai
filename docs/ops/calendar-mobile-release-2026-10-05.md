# Выпуск мобильного календаря, 05.10.2026

Календарь не меняет модель данных. Однако main включает изменения бара, поэтому общий выпуск требует применения существующих миграций. Агент не применяет их без отдельного разрешения владельца по AGENTS.md §15 и §18.

## Предмет разрешения

Применить на production WETOP три существующие миграции: `20261004000051_bar_inventory`, `20261005000053_bar_function_search_path`, `20261005000054_bar_force_rls`. Первая создаёт товарный учёт бара, вторая закрепляет search_path защитной функции, третья включает FORCE RLS на десяти таблицах бара. SQL не изменять. Onboarding `20261004000052` уже applied по read-only проверке.

## Последовательность

1. Зафиксировать точный кандидат SHA и дождаться зелёного GitHub release-checks именно для него. Проверить текущие deployed/release, отсутствие чужой сборки и migration status. Если набор ожидающих миграций изменился, пересмотреть объём.
2. Создать свежую закрытую резервную копию существующим scripts/ops/db-backup.sh по docs/ops/backups.md. Проверить успешный код, непустой dump и чтение оглавления через pg_restore. Не выгружать dump с сервера и не выводить данные/секреты.
3. Архивировать Prisma из точного SHA. Выполнить документированные mig status, mig deploy, mig status по docs/deploy.md §1б с URL из окружения. Не менять внешний production ARI, fiscal receipts или eQonaq.
4. Проверить applied для всех трёх миграций, существование десяти таблиц бара, их RLS/FORCE RLS и закреплённый search_path защитной функции. Не создавать продажи или брони для проверки.
5. Перемотать release на проверенный SHA. Если auto-deploy отказал из-за миграций, выполнить wetop-auto-deploy --migrations-applied с точным SHA по документации.
6. Подтвердить deployed SHA, образы и health, затем открыть календарь на рабочем адресе и проверить мобильные размеры без изменения реальных записей. Проверка физической клавиатуры телефона остаётся отдельной проверкой на устройстве.

## Откат

При неуспешной миграции не перематывать release и сохранить предыдущую работающую версию. При неуспешной сборке использовать документированный откат приложения на предыдущий SHA. Откат схемы выполняется владельцем: 20261004000051_bar_inventory/down.sql удаляет весь учёт бара и допустим только после проверки отсутствия новых данных и свежей копии. Автоматически его не запускать. Если записи уже появились, остановить изменения и восстановить проверенную копию по процедуре docs/ops/backups.md; это затрагивает всю базу и требует отдельного решения владельца.

Пока не выполнены эти шаги, main push и локальные проверки не означают обновление app.wetop.ai.
