# Отложенные миграции: папка `migrations-held`

Разбор 01.10.2026 (`reports/order-2026-10-01`, пункт 4). Миграция `20260930000039_seller_profile_agent_key` была
помечена «отдельный релиз» (`docs/ops/sa25-agent-scope.md` §4), но лежала в общей цепочке
`packages/database/prisma/migrations`. Обычная команда `npm run migrate:deploy -w @pms/database` применила бы её
вместе с остальными, то есть раньше кода, а код до SA2.5 на схеме после 039 не работает. Такие миграции теперь
лежат отдельно.

## Правило

Миграция, которую можно применять **только после выкладки кода** (сужение ключа, снятие колонки, отзыв прав, которые
старый код ещё использует), до своего релиза живёт в `packages/database/prisma/migrations-held/<то же имя>/` с теми же
`migration.sql` и `down.sql`. В цепочку она переезжает отдельным PR, когда код, которому она нужна, выложен и
смоуки зелёные.

Что это даёт и чего требует:

| Кто | Что делает с папкой |
|---|---|
| `prisma migrate deploy` и `migrate status` | не видят: на рабочую базу отложенная не уезжает, пока её не вернули в цепочку |
| `scripts/ops/auto-deploy.sh` | правки в `migrations-held` за миграции не считает: код выкладывается первым, как и задумано. Но перенос папки **из** цепочки он видит как изменение в `migrations/` и откажет один раз, как при новой миграции: владелец сверяет `_prisma_migrations` (ниже) и выкладывает `--migrations-applied <sha>`, ничего не применяя |
| `scripts/ops/check-migrations.sh` | сверяет `schema.prisma` с базой «цепочка + отложенные» и проверяет откат каждой отложенной поверх всей цепочки |
| `tests/tools/test-schema.ts` | строит схему автотестов из цепочки вместе с отложенными: клиент Prisma уже ждёт новую схему |
| `tests/unit/migrations-rollback.test.ts` | у отложенной есть `down.sql`, имя не повторяет имя из цепочки, 039 отложена, пока её релиз не пришёл |

Два следствия, о которых надо помнить:

1. **Код обязан работать на обеих схемах**: до отложенной и после неё. Это и есть смысл «расширить → переключить →
   сузить»: 035 и 036 расширили, код переключён, 039 сужает. Проверка на обеих схемах: интеграционные тесты идут на
   схеме с отложенной (так строит `test-schema.ts`); схему без неё даёт `check-migrations.sh` шагом «вся цепочка легла
   на пустую базу».
2. **`prisma migrate dev` с отложенной миграцией не запускать**: он увидит разницу между `schema.prisma` и цепочкой и
   впишет её в новую миграцию. Миграции в проекте пишутся руками, с `down.sql`, по `DATA_MODEL.md`.

## Как вернуть отложенную в цепочку (её релиз)

1. Убедиться, что код, читающий новую схему, выложен и смоуки зелёные (для 039: `docs/ops/sa25-agent-scope.md` §3).
2. Предпроверка на рабочей базе, только чтение (для 039: `SELECT count(*) FROM seller_profiles WHERE agent_id IS NULL`
   должно быть 0).
3. `git mv packages/database/prisma/migrations-held/<имя> packages/database/prisma/migrations/<имя>`, отдельный PR,
   `check-migrations.sh` зелёный.
4. `release` на этот коммит: `auto-deploy.sh` увидит новую миграцию и откажет, как положено; владелец снимает копию
   (`docs/ops/backups.md`), применяет `migrate:deploy`, затем `--migrations-applied <sha>`.

## Если отложенная уже применена на рабочей базе

Тогда её место в цепочке, а не здесь: `migrate deploy` при миграции, которая есть в `_prisma_migrations`, но
отсутствует в папке, предупреждает, и порядок в журнале базы перестаёт совпадать с репозиторием. Проверка, только чтение:

```sql
SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY migration_name DESC LIMIT 5;
```

Есть строка `20260930000039_seller_profile_agent_key`: вернуть папку в цепочку шагом 3 выше, без применения.
