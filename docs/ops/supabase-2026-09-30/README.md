# Supabase: подготовленный переход 034 → 037

30.09.2026. Для проекта, который использует WETOP. Перед подготовкой рабочая база проверена чтением: последняя успешная миграция 034; `public.reservations.promo_code_id` отсутствует. Это причина HTTP 500 локального API новой ветки. На домене release `6c604192` совместим со старой схемой.

## Что вставить

1. Открыть проект WETOP в Supabase → SQL Editor → New query, роль `postgres`.
2. Вставить **полное содержимое** [apply-035-037.sql](apply-035-037.sql) и выполнить один раз.
3. Ожидаемый последний результат: `WETOP migrations 035-037 applied`.
4. Выполнить [verify.sql](verify.sql): три миграции 035/036/037 должны иметь `applied = true`, ниже должны быть три новых поля. `seller_scope_assert` завершится без ошибки.
5. Передать результат проверки для последующего обновления API/frontend. Применение SQL само по себе не выкладывает новую версию сайта.

Файл содержит исходные миграции проекта без изменения их SQL, транзакционную оболочку и запись точных SHA-256 в `_prisma_migrations`. Повторное исполнение уже применённых миграций с тем же checksum пропускается. При несовпадении или незавершённой миграции выполнение останавливается. Если Supabase сообщает об ошибке — не удалять проверки и не запускать фрагменты отдельно; выполнить `ROLLBACK;`, передать текст ошибки без персональных данных.

035/036 добавляют связь ИИ-продавца с филиалом и выполняют предусмотренный проектом перенос старого профиля. 037 добавляет таблицу промокодов, поля производных тарифов и связь брони с промокодом, ограничения и RLS. Обычные брони и тарифы не удаляются.

**038 не входит:** изменение прав интеграционных таблиц требует сначала выкладки совместимого API (docs/ops/rls.md). Не добавлять её к этому файлу самостоятельно.

## Проверка пакета

На отдельной локальной PostgreSQL создана база `wetop_sql_audit_20260930` с исходными миграциями до 034. Пакет применён дважды: оба выполнения успешны, повтор не дублирует миграции. Проверка новых полей, RLS `promo_codes` и `seller_scope_assert` успешна. Это проверка SQL на пустой исходной схеме, а не репетиция переноса рабочих данных; реальные данные защищены встроенными предпроверками миграций.

## Откат

- Ошибка до COMMIT: вся транзакция отменяется, не отмечать миграции применёнными вручную.
- После COMMIT прежде всего вернуть совместимый release приложения: расширения 035–037 оставляют прежние поля доступными.
- Схему назад автоматически не удалять: down.sql 037 уничтожает новые промокоды и связи тарифов, down.sql 035 удаляет перенесённых агентов. После появления новых записей нужен отдельный разбор и новая копия.
- При необходимости полного восстановления остановить записи приложения и фоновые workers, сохранить текущий дамп, восстановить указанную копию по `docs/ops/backups.md`, проверить `_prisma_migrations` (034), счётчики бронирований/гостей/платежей и только затем вернуть трафик. Не восстанавливать старый дамп поверх новых рабочих операций без сверки.
- Исходные обратные миграции хранятся рядом с каждой migration.sql: применять 037 → 036 → 035 только после проверки потери новых данных, в транзакции, с согласованным восстановлением журнала Prisma. Это операция администратора, не часть обычного SQL-файла выше.
