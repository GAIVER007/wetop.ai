## 2. Ключ приёма событий

Один новый секрет `VOICE_INGEST_KEY`: им воркер пишет события звонков и читает профиль агента. Сгенерировать на сервере:

```bash
openssl rand -hex 32
```

Результат не пересылать. Вписать в `.env` API (`VOICE_INGEST_KEY=...`) и в `.env` воркера (шаг 6). Строку `VOICE_INGEST_KEY=` без
значения добавьте и в `.env.example` репозитория (агенту этот файл закрыт). Перезапустить API.

## 3. Агент ИИ-продавца филиала (любое направление)

Голос работает от агента ИИ-продавца филиала; направление (гостиница, салон, ресторан) платформа определяет сама. Он должен быть в состоянии `active` и иметь филиал. Узнать идентификаторы
(Supabase SQL Editor, только чтение):

```sql
select a.id as agent_id, a.organization_id, a.name, a.lifecycle, l.name as location
from seller_agents a left join locations l on l.id = a.location_id
order by a.created_at desc;
```

Нужны `agent_id` и `organization_id` нужного объекта. Профиль голоса (хвост приветствия, имя голоса, номер администратора)
по умолчанию берётся из бизнеса: голос `Leda`, перевода звонка нет. Свой профиль появится строкой в `voice_profiles`
(экран настройки профиля впереди; пока строкой в базе, по запросу).

## 4. VideoSDK

1. Аккаунт на https://app.videosdk.live, токен из раздела API keys: это `VIDEOSDK_AUTH_TOKEN`.
2. SIP номер (Telephony): шлюзы входящий и исходящий создаются вместе с номером. Адрес для приёма звонков от провайдера:
   `sip:<ORG_ID>.sip.videosdk.live` (ORG_ID вашей организации в VideoSDK; регион можно закрепить `in1` или `us2`).
3. Правило маршрутизации (Telephony, Routing rules): шлюз, номер, комната `dynamic`, агент «Self Hosted». В поле Agent ID
   то же значение, что `VOICE_AGENT_ID` воркера. В metadata правила (это поле определяет, чей это звонок):

```json
{ "organization_id": "<UUID организации из шага 3>", "agent_id": "<UUID агента из шага 3>" }
```

   Одно правило на один номер объекта. Несколько объектов, в том числе разных направлений: по правилу на каждый, воркер один.

## 5. SIP-провайдер (для пробы Twilio)

1. Номер у провайдера, Elastic SIP Trunk.
2. Origination: адрес `sip:<ORG_ID>.sip.videosdk.live` из шага 4 (Origination SIP URI).
3. Termination: создать Termination SIP URI и завести его в исходящем шлюзе VideoSDK (адрес, логин и пароль транка, транспорт TLS).
4. Для перевода звонка на администратора включить в транке **Transfer to PSTN**, иначе перевод не сработает.

## 6. Воркер на сервере

Каталог `apps/ai-seller/voice` на сервере, файл `.env` рядом с `compose.yml` (образец `env.example`, права 0600). Переменные:

| Переменная | Что вписать |
|---|---|
| `VIDEOSDK_AUTH_TOKEN` | токен VideoSDK из шага 4 |
| `GOOGLE_API_KEY` | ключ Gemini (https://aistudio.google.com/app/apikey) |
| `VOICE_AGENT_ID` | любое уникальное имя воркера, например `wetop-voice`; то же в Agent ID правила маршрутизации |
| `VOICE_WORKER_PORT` | порт воркера внутри контейнера, по умолчанию 8081 |
| `VOICE_WETOP_BASE_URL` | публичный адрес API платформы по `https://` (тот же, которым пользуется сайт). Адрес `localhost` из контейнера не годится (там `localhost` это сам воркер), имена соседних контейнеров тоже, а `http://` воркер отвергает при запуске. Проверка до запуска: `docker compose run --rm voice-worker python -c "import os,httpx; print(httpx.get(os.environ['VOICE_WETOP_BASE_URL'] + '/health', timeout=10).status_code)"` (ждём 200) |
| `VOICE_WETOP_SERVICE_KEY` | значение `SELLER_QUOTE_KEY` из `.env` API: узкий ключ чтения каталога услуг |
| `VOICE_INGEST_KEY` | ключ из шага 2 |
| `VOICE_BOOK_KEY` | необязательно: ключ записи брони по телефону из шага 10. Пусто: бронь по телефону не работает, остальное как прежде |
| `VOICE_OUTBOX_DIR` | в compose уже `/data/calls.outbox` (том), менять не нужно |
| `VOICE_JOURNAL_PATH` | в compose уже `/data/calls.jsonl` (том) |
| `VOICE_NUMBER_MAP` | необязательно: JSON-список разрешённых пар `{"+7...": {"organization_id": "...", "agent_id": "..."}}`; пусто = любая пара из metadata, а агента и организацию проверяет платформа |
| `VOICE_VERTICAL` | необязательно, запасной профиль: `HOSPITALITY`, `BEAUTY` или `FOOD_SERVICE` (по умолчанию `BEAUTY`); с платформы направление приходит само |
| `VOICE_OBJECT_NAME`, `VOICE_NAME`, `VOICE_HANDOFF_NUMBER` | запасной профиль, если платформа недоступна; работает только когда в `VOICE_NUMBER_MAP` ровно один маршрут |

Нужен Docker 23 и новее с BuildKit (по умолчанию в Compose v2): без него файл `voice/Dockerfile.dockerignore` не читается. Защита `.env` дублирована в `apps/ai-seller/.dockerignore`, но проверьте, что после сборки `docker run --rm --entrypoint ls <образ> -a /app/voice` не показывает `.env`. Каталог тома `/data` принадлежит пользователю `app`; именованный том `voice-data` из compose это учитывает, при замене на каталог хоста выдайте ему права владельцу uid 1000.

Запуск:

```bash
cd apps/ai-seller/voice && docker compose --env-file .env up -d --build
docker compose logs -f voice-worker
```

В журнале должно быть, что воркер зарегистрирован в VideoSDK под `VOICE_AGENT_ID`. Порт воркера наружу не публикуется.

## 7. Расписание догона очереди

Если платформа была недоступна, события лежат в очереди на диске и уходят со следующим звонком. Чтобы не ждать звонка,
раз в 15 минут (cron хоста; полный путь к каталогу, флаг `-T` обязателен без терминала, вывод в файл):

```bash
cd /полный/путь/apps/ai-seller/voice && docker compose run --rm -T voice-flush >> /var/log/voice-flush.log 2>&1
```

Код выхода 2 значит, что в очереди ещё остались события. В `rejected/` (том `/data/calls.outbox/rejected`) попадают события,
которые платформа отвергла; каждая такая запись пишет `ERROR` в журнал. После исправления причины вернуть их в очередь:
`docker compose run --rm -T voice-flush python -m voice.flush --requeue-rejected`. Оповещение при появлении файлов в `rejected/`
настраивается на стороне сервера.

## 8. Пробный звонок: что проверить

Позвоните на номер объекта с обычного телефона.

| Что проверить | Ожидаемо |
|---|---|
| Приветствие | «Здравствуйте, это ИИ-помощник, <имя объекта>. Разговор записывается. ...» |
| Вопрос про справочник | салон: услуги и цены из каталога; ресторан: часы работы по дням; гостиница: говорит, что администратор уточнит. Суммы не складывает |
| «Запишите меня» / «Забронируйте» | собирает имя и номер, говорит, что просьба записана; в разделе «Голосовой агент» появляется просьба с номером |
| «Соедините с администратором» | переводит на номер `handoffPhone`, если он задан; иначе говорит, что администратор перезвонит |
| Журнал в стойке | звонок виден с маской номера, состоянием и длительностью |
| Звонок на номер без правила | вежливый отказ без разговора |
| Остановить API на минуту во время звонка | звонок идёт, события лежат в очереди и доходят после запуска (проверить `python -m voice.flush`) |

Результат записать в `docs/status/` (AGENTS.md §10): без записи задача не закрыта.

## 9. Откат и аварийная остановка

Откат: снять правило маршрутизации в панели VideoSDK (звонки перестанут идти на воркера), `docker compose down` в
`apps/ai-seller/voice`. Данные не удаляются: журнал и очередь остаются на томе `voice-data`. Откат миграции 145 возможен,
только пока таблицы пусты (`down.sql` в каталоге миграции); после первого звонка выгрузить данные и решать правкой вперёд.
Ключ `VOICE_INGEST_KEY` при подозрении на утечку заменить: сгенерировать новый (шаг 2), обновить `.env` API и воркера,
перезапустить оба.

## 10. Бронь по телефону, гостиница (по умолчанию выключена)

Решение и границы: `docs/decisions/2026-10-23-voice-booking-answers.md`, `docs/decisions/2026-10-23-voice-booking-salon-restaurant.md`. Работает у гостиницы, салона и ресторана. Салон: агент знает, какой мастер какие услуги оказывает, ищет свободное время (у любого мастера или у названного), записывает с именем, телефоном и комментарием клиента; запись создаётся со статусом «забронирована» (ждёт подтверждения администратора), источник «голос». Ресторан: агент проверяет, что на дату, время и число гостей есть период обслуживания, подходят правила брони филиала и есть свободный стол (номер стола агент не называет и не назначает), и бронирует на имя и телефон гостя с комментарием; бронь BOOKED ждёт подтверждения, стол назначает администратор.

1. Миграции `20261023000149_voice_booking_settings` (права стойки на выключатель), `20261023000147_voice_booking` (источник брони «голос», выключатель и лимиты в `voice_profiles`, канал `voice` у котировок) и `20261023000148_voice_booking_quotes` (котировки салона и ресторана):
   порядок и откат в README каждой миграции. Применять так же, как в шаге 1, до выкладки API.
2. Второй секрет `VOICE_BOOK_KEY`, отдельный от ключа приёма событий (`openssl rand -hex 32`). Вписать в `.env` API и в `.env` воркера, перезапустить оба.
   Ключ пускает на два адреса: `POST /voice/booking-quotes` и `POST /voice/booking-quotes/confirm`.
3. Включить на объекте: страница «Голосовой агент», вкладка «Бронь по телефону» (миграция `20261023000149_voice_booking_settings`, право `marketing`): выключатель и лимит за звонок. Включить можно, только когда агент действует и у направления есть данные для брони, иначе вкладка называет причины. Запасной путь без стойки (SQL Editor); строка профиля может быть ещё не создана:

```sql
insert into voice_profiles (agent_id, organization_id, business_id)
select a.id, a.organization_id, l.business_id
from seller_agents a join locations l on l.id = a.location_id
where a.id = '<agent_id>'
on conflict (agent_id) do update set booking_enabled = true;
```

   По умолчанию бронь ждёт подтверждения администратора (`booking_needs_approval = true`), лимит 3 брони за звонок. Выключить обратно: `booking_enabled = false`.
4. У гостиницы должен быть сайт с включённым бронированием и тариф (тот же, что для брони из чата): цены и места агент берёт оттуда. Нет сайта: бронь по телефону отвечает отказом. У салона и ресторана сайт не нужен: салону нужны услуги с мастерами и графики мастеров; ресторану периоды обслуживания, правила брони и столы с вместимостью; обоим включённый выключатель.
5. Пробный звонок по сценариям (таблица шага 8) плюс: свободные даты, занятая категория, бронь с явным «да», отказ без «да», повтор «да».

### Суточный лимит на телефон

Миграция `20261023000153_voice_phone_limit` (хэш телефона у подтверждённой брони) и секрет `VOICE_PHONE_HASH_KEY` в `.env` API (`openssl rand -hex 32`, значение вписывает владелец, перезапустить API). Лимит считается на агента за скользящие 24 часа по значению `booking_max_per_phone_day` (по умолчанию 5), хэш обнуляется через 7 дней. Без секрета лимит выключен, API пишет об этом при запуске; остаётся лимит за звонок. Номер в таблицах не хранится, только HMAC с секретом; при смене секрета старые хэши перестают совпадать (лимит за прошедшие сутки обнулится, это безопасно).
