## Вердикт: NO-GO, нужен CORE-SECURITY-FIX

- **U2-1, CONFIRMED рантаймом (P1, кросс-организация):** `POST /channels/channex/events/:revisionId/retry`
  сбрасывает `external_events` чужой организации: `resetExternalEventAttempts` пишет по
  (provider, externalEventId) без привязки (`reservations.repository.ts:1408`), а `retryEvent` выполняет
  его служебной ролью мимо RLS; модель несёт `propertyId` (ADR-100 §17.2), фильтровать обязан код.
  Репродукция задокументирована тестом `tests/integration/core-01-repro.test.ts` (`it.fails`: зелёный пока
  дефект жив; инверсия прогнана, чужая строка стала RECEIVED/0).
- **CONFIRMED кодом (границы назначений внутри организации):** гости организации целиком видны
  назначенному на один филиал (`guests.repository.ts:303-309`, граница признавалась недостроенной ещё в
  STAFF2.3b); `PUT beauty/employees/:id/locations` не сверяет филиалы тела с назначениями;
  `GET /onboarding` (self) отдаёт черновик любого филиала; `POST /hotel/onboarding` на орг-скоупе создаёт
  гостиничный бизнес правом `settings` (минуя владелец-only `/branches`).
- **FALSE POSITIVE (доказано):** кросс-вертикальная утечка через гостиничный API (Food/Beauty-скоуп
  получает 403/404); «fallback на ранний Property ведёт в чужую вертикаль»; двойная бронь стола
  (mv6-food 19/19 с двумя параллельными репродукциями); дубль клиента по точной строке телефона
  (частичный уникальный индекс организации).
- **CONFIRMED не-блокеры:** один номер в разных форматах создаёт дубли клиентов (живой прогон: три формата
  → три клиента; нормализации у Customer нет); у назначений столов нет EXCLUDE-подстраховки в базе
  (защита держится на READ COMMITTED); тихий ORGANIZATION-fallback пишет в ранний отель при протухшем
  заголовке (целостность, не конфиденциальность).
