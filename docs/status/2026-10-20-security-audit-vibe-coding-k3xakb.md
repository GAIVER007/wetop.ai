**Лимит Cloudflare оформлен скриптом и инструкцией, применяет владелец.**
- `scripts/ops/cloudflare-widget-ratelimit.sh status|apply|remove` — одно правило rate limiting в фазе `http_ratelimit` зоны `wetop.ai` через Rulesets API: четыре записывающих пути виджета (`/widget/session`, `/widget/consent`, `/widget/message`, `/widget/attachment`), 20 запросов за 10 с с одного IP, блок 10 с. GET-пути (`widget.js`, `demo`, опрос `messages`) не входят: их частоту задаёт сам виджет. Умолчания под план Free (одно правило, только путь, только 10 с); на Pro и выше `CF_RL_HOST=assistant.wetop.ai`, порог и окно — `CF_RL_REQUESTS`, `CF_RL_PERIOD`, `CF_RL_TIMEOUT`.
- Своё правило узнаётся по `ref = wetop-widget-ratelimit`: повтор `apply` заменяет, а не добавляет; чужие правила фазы (например, лимит на `/login` из рекомендаций комиссии 26.09) остаются с их `id`; `remove` снимает только своё. «Фазы ещё нет» (ошибка 10002) — пустой список, а не отказ. Номер зоны ищется по имени, если `CLOUDFLARE_ZONE_ID` не задан. Токен (`CLOUDFLARE_API_TOKEN`, права Zone WAF: Edit и Zone: Read на зону) берётся из окружения или `.env` клона и уходит в curl только через `--config -` на stdin: в аргументах процесса его нет (аудит 25.09, `ps`). Разбор JSON — `python3 -I`, без jq.
- Инструкция `docs/ops/cloudflare-widget-ratelimit.md`: зачем второй слой при счётчиках бота (60 в час на посетителя и IP считаются уже в контейнере, поток доходит до Redis), таблица правила, токен, `status` → `apply` → живая проверка (25 быстрых POST на `/widget/session` → 429 от Cloudflare, через 10 с снова проходят, обычный чат на `wetop.ai` работает) → запись в `SECURITY.md` §14; откат `remove`. `SECURITY.md` §14 дополнен абзацем.
- Решения не нужно: правило внешней панели, модель данных, API и бот не менялись.
