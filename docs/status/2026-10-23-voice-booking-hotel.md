# Голосовая бронь, срез 1 (гостиница) (23.10.2026)

Ветка `claude/voice-booking-hotel-20261023`, основана на ветке PR 772 (голосовой агент). Модель данных утверждена владельцем 23.10.2026
(DATA_MODEL `VOICE-BOOKING-OWNER-APPROVAL-20261023`), ответы на вопросы плана: `docs/decisions/2026-10-23-voice-booking-answers.md`.

## Что сделано
- **Миграция 147** `voice_booking`: значение `VOICE` в `ReservationSource`, `RestaurantReservationSource`, `AppointmentSource`; поля `booking_enabled`
  (false), `booking_needs_approval` (true), `booking_max_per_call` (3), `booking_max_per_phone_day` (5) в `voice_profiles` с CHECK 1..20;
  канал `voice` у `seller_booking_intents`. Откат `down.sql`, README.
- **API** (`apps/api/src/marketing-voice/voice-booking.*`): `GET /voice/availability` (ключ приёма событий), `POST /voice/booking-quotes` и
  `POST /voice/booking-quotes/confirm` (новый ключ `VOICE_BOOK_KEY`, вид ключа `voice-book` в `SessionGuard`). Цены и места считает прежний путь
  брони из чата (`WebBookingService`, `BookingIntentsService`); голос добавляет проверки: выключатель, только гостиница, звонок связывает
  котировку (`conversation = ID звонка`), подтверждается только котировка этого же звонка и агента, лимит броней за звонок, лимит котировок за
  звонок (втрое выше), без промокода, пометка «Бронь по телефону, голосовой ИИ-агент». Ключ продавца бронь с каналом `voice` создать не может
  (проверка каналов в `BookingIntentsService`).
- **Воркер**: клиент `booking_client.py`, инструменты `check_availability`, `quote_stay`, `confirm_booking`. Бронь только из последней выдачи этого
  звонка, идентификатор котировки хранится в воркере и модели не виден, подтверждение требует явного `customer_agreed`, гость: имя, фамилия, телефон.
  Профиль и инструкции меняются только у гостиницы с включённой бронью; без `VOICE_BOOK_KEY` воркер сам выключает бронь и не обещает невозможного.
- **Стойка**: подпись источника «Голосовой агент» (`VOICE`) в реестре источников брони.
- **Документы**: runbook `docs/ops/voice-release.md` раздел 10 (ключ, миграция, включение на объекте SQL, пробный звонок), образец окружения.

## Чего нет и почему
- **Статус «ожидает подтверждения» как `TENTATIVE` не сделан.** Создание брони жёстко ставит `CONFIRMED` (`reservations.service.ts`), `TENTATIVE`
  в API нигде не обрабатывается. Менять статусы и занятость значит трогать логику бронирования (AGENTS.md §15). Сейчас бронь создаётся
  `CONFIRMED` с пометкой в заметке «Ожидает подтверждения администратора». Вопрос владельцу: QUESTIONS.md, Q-VOICE-9.
- **Лимит «5 в сутки на телефон» не действует.** Телефон гостя в базе хранится псевдонимом, у котировки его нет, посчитать нечем. Нужно отдельное
  поле хэша телефона (изменение модели, нужно утверждение): QUESTIONS.md, Q-VOICE-10. Лимит за звонок (3) действует. Поле `booking_max_per_phone_day` пока без применения.
- **Сквозной звонок и бронь на настоящем сайте с тарифом не прогонялись:** нужен гостиничный сайт с включённой бронью, тарифом и остатками.
  Доказано по частям: unit сервиса, схема и подсчёты на базе, клиент и инструменты воркера. Сквозную проверку лучше сделать с владельцем на тестовом объекте.
- Уведомление администратору и отметка в календаре: срез 4.
