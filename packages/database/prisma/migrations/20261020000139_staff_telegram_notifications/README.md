# 139 staff_telegram_notifications: уведомления сотрудникам в Telegram (STAFF-TG-20261020)

Модель утверждена владельцем 20.10.2026 («да» на три таблицы), раздел `STAFF-TG-20261020` в `DATA_MODEL.md`, план
`plans/staff-telegram-notifications-2026-10-20.md`. Номер 138 занят параллельной задачей персонала.

Обычная аддитивная миграция, метки «ОТДЕЛЬНЫЙ РЕЛИЗ» нет: старый API новые таблицы не читает, новый API без них не
запускается (запись брони с сайта пишет очередь в той же транзакции). Поэтому порядок: миграция, затем API.

## Применение

1. Свежая резервная копия рабочей базы (`docs/ops/backups.md`), проверка, что она читается.
2. `migration.sql` в собственной транзакции (`/root/wetop-mig.sh deploy`).
3. Проверка:
   - три таблицы есть, у каждой `relrowsecurity` и `relforcerowsecurity` = true, политика `rls_tenant`;
   - `wetop_app` с чужой организацией видит 0 строк каждой таблицы; без организации тоже 0;
   - `wetop_app` не может удалять строки ни одной из трёх таблиц и не может вставить привязку;
   - повторная вставка строки очереди с тем же (`kind`, `source_id`, `recipient_user_id`) отклоняется;
   - `tests/integration/staff-telegram-storage.test.ts` и `tests/integration/rls-isolation.test.ts` зелёные на копии.
4. Выкладка API. Пока `TELEGRAM_STAFF_BOT_TOKEN` не задан, отправщик молчит, строки очереди копятся со статусом
   `PENDING`; после включения бота старые не досылаются (только новые, план).

## Откат

`down.sql` берёт эксклюзивный замок и отказывает, если есть хоть одна привязка, строка очереди или использованный код.
Выданные и не использованные коды (никто не нажал ссылку) откату не мешают и удаляются вместе с таблицей. После первой
привязки откат не делается: история уведомлений по AGENTS.md §11 не удаляется. Дальше допустимы совместимая
forward-правка или восстановление проверенной копии в отдельно согласованное окно. Перед откатом схемы откатить API
(старый API таблиц не читает).
