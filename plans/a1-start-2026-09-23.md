# A1 — старт: сервер и база на ps.kz (первый блокер переезда)

Короткий порядок действий с чекпойнтами. **Полные команды, грабли и таблица ошибок — `docs/ops/server-setup-2026-09-18.md`** (обновлён 22.09) и план `plans/server-kz-2026-09-17.md`. Здесь — только последовательность и что вставлять в чат.

**Кто что делает:** панель ps.kz, SSH, ключи, `.env` и оплата — **владелец**; вывод каждой команды владелец вставляет в чат, агент разбирает. Агент до ps.kz не достаёт ни с одной стороны (проверено 18.09). Ключи и пароли в чат не диктуются.

**Ничего боевого до шага 8 не трогается.** До переключения туннеля старая машина (Hostinger) работает как есть; откат на шагах 0–7 — просто не продолжать.

## Шаг 0 · Решения владельца (2 минуты)
- Провайдер — **ps.kz** ✓, управляемая база (DBaaS) ✓ (закрывает и бэкапы, Q-073).
- Версия PostgreSQL: **17** ✓ — ps.kz её даёт (сверено 26.09, шаг 1); источник Supabase — 17.6.
- **Кто платит** — владелец лично ✓ (Q-070а закрыт 26.09).

## Шаг 1 · Панель ps.kz (владелец) — сверено с документацией PS Cloud 26.09.2026
«Облачные базы данных» PS Cloud дают PostgreSQL 12, 14, 16, 17 и 18; расширения **`btree_gist`**, **`vector`**
(pgvector) и **`pg_trgm`** есть во всех этих версиях и ставятся командой `CREATE EXTENSION`
([матрица расширений PS Cloud](https://trove-api.object.pscloud.io/postgresql-extensions.html)). Регионы — Алматы,
Астана, Ташкент. Цен на сайте нет — они видны в консоли при заказе.

Всё — в **одном регионе (Алматы)** и в **одной частной сети**:
- **Частная сеть** — создаётся на шаге «Сеть» при создании первого кластера («Добавить» → «Создать»: имя, подсеть,
  пул адресов). Второй кластер и сервер подключаются к ней же.
- **Кластер базы PMS:** структура «Мастер»; PostgreSQL **17**; конфигурация — наименьшая, но не меньше 2 ГБ памяти;
  диск NVMe 20 ГБ; сеть — частная; **«Плавающий IP» выключен** (он открывает базу в интернет, а сервер ходит к ней
  по частной сети); «Расписание резервного копирования» → «Добавить»: ежедневно, 03:00, часовой пояс Алматы, хранить
  14 копий. Затем в кластере — база и пользователь приложения; пароль — в менеджер паролей, в чат не присылать.
  `btree_gist` (защита от овербукинга) ставит миграция сама; не хватит прав — строка таблицы ошибок в
  `docs/ops/server-setup-2026-09-18.md`.
- **Кластер базы бота:** то же, но PostgreSQL **18** (бот работает на 18 с pgvector) и диск NVMe 10–20 ГБ. Нужен
  до переключения (шаг 8, переезд бота — `plans/kz-move-2026-09-26.md` §3); заказать можно сразу или позже.
- **Облачный сервер:** Ubuntu 24.04 LTS, 2 vCPU, **8 ГБ** (на той же машине будет ИИ-продавец), NVMe 40–60 ГБ;
  та же частная сеть **и** публичный (плавающий) IP — для SSH и выхода в интернет; вход по SSH-ключу, если консоль
  его предлагает.
- **✅ В чат (без паролей):** регион; по каждому кластеру — версия, внутренний адрес и порт, имя базы и пользователя,
  предел подключений (`max_connections` — в карточке кластера или группе параметров); у сервера — публичный
  и внутренний IP; месячная сумма из консоли.

## Шаг 2 · Подготовка сервера (владелец, SSH)
```bash
curl -fsSLo /tmp/bootstrap.sh https://raw.githubusercontent.com/GAIVER007/wetop.ai/main/deploy/server-bootstrap.sh
sudo bash /tmp/bootstrap.sh --branch main
```
Первый запуск остановится и напечатает публичный ключ → добавить его в GitHub → репозиторий → Settings → **Deploy keys** → Add, **без** «Allow write access» → запустить команду второй раз.
Затем поставить **Docker** и **postgresql-client-17** (раздел §2.1 доки — репозитории PGDG и Docker).
- **✅ В чат:** вывод второго запуска bootstrap; `docker compose version` (ждём ≥ 2.24); `psql --version` (ждём 17.x).

## Шаг 3 · `.env` в корне клона (владелец)
Источник — `.env` **действующего сервера Hostinger** (`/root/wetop/.env`), не с Mac. Перенести своим путём, значения в чат не печатать. Правки: `DATABASE_URL` → ps.kz; `REGISTRATION_OPEN=0` явно; фоновые Channex-флаги (`CHANNEX_PULL`, `CHANNEX_OUTBOX_WORKER`, `CHANNEX_FULL_SYNC`, `CHANNEX_WEBHOOK_HEALTH`) и `GUARD` = `off`; **`PII_STORAGE` не трогать** (включается на шаге 8).
```bash
chmod 600 ~/wetop/.env
cd ~/wetop && npm ci --ignore-scripts && npx tsx scripts/imports/src/cli-check-env.ts
```
- **✅ В чат:** вывод `cli-check-env` (без значений — он их не печатает).

## Шаг 4 · Схема на пустой базе (владелец делает, агент читает)
```bash
cd ~/wetop && set -a && . ./.env && set +a
psql "$DATABASE_URL" -c "select version(), current_setting('TimeZone'), (select count(*) from pg_tables where schemaname='public') as tables"
npm ci
npx prisma migrate deploy --schema packages/database/prisma/schema.prisma
npx prisma migrate status --schema packages/database/prisma/schema.prisma
psql "$DATABASE_URL" -c "select extname from pg_extension where extname='btree_gist'"
```
- **✅ В чат:** версия/таймзона/таблиц=0; все миграции применены; `btree_gist` в списке.

## Шаг 5 · Данные (владелец; пустая база без архивный источник, ADR-052)
Копируются: объект, фонд (88 единиц, 5 категорий), тарифы, цены по дням, политики штрафа, сопоставление с Channex, счётчик сайта, организации и учётные записи. Броней/гостей/оплат в источнике нет (стёрты 19.09). Команды `pg_dump` 17 → `pg_restore` — §5 доки.
- **✅ В чат:** результат сверки строк `diff` — ждём «**строки сошлись**».

## Шаг 6 · Пул соединений
Предел базы ≥ 20 → ничего не менять. Меньше → `DATABASE_POOL_MAX=3` в `.env`. Разовые скрипты — с `DATABASE_POOL_MAX=1`.

## Шаг 7 · Первый запуск «вторая копия», без туннеля (владелец)
Всё Channex выключено, туннель НЕ поднимаем (боевая копия пока на Hostinger).
```bash
cd ~/wetop && printf 'CHANNEX_ARI=off\n' > deploy/ari.env
docker compose -f deploy/compose.yml up -d --build api web
docker compose -f deploy/compose.yml ps
docker compose -f deploy/compose.yml exec -T api node -e "fetch('http://127.0.0.1:3001/health').then(r=>r.text()).then(console.log)"
bash scripts/ops/ari.sh status
```
- **✅ В чат:** `ps` (api+web `healthy`); `/health` → `ok, database up`; сводка фонда 88; стойка 200; `ari.sh status` → `машина: docker, CHANNEX_ARI=off`.

## Шаг 8 · Переключение (владелец + агент)
1. Остановить запись на Hostinger (api, web) и снять копию базы **заново** по §5 — первая устарела.
2. Туннель — **ровно один коннектор**: на Hostinger остановить, на ps.kz поднять `cloudflared` (`deploy/cloudflared.example.yml`, без блока Access — ADR-053). Проверка: `cloudflared tunnel info wetop` = один коннектор, IP ps.kz.
3. Включить в `.env` то, что было `off` (шаг 3), проверить webhook Channex на `api.wetop.ai` → 200.
4. **`PII_STORAGE=real`** — только на этой базе (условие допуска CUTOVER.md).
5. Сторож/дежурный агент — на ps.kz; внешний сторож `pms-lux-watch` оставить **на другой машине** (Hostinger), `GUARD_HEARTBEAT_URL/SECRET` в `.env` ps.kz указывают на него.

## Критерий готовности A1
`cloudflared tunnel info wetop` — один коннектор (ps.kz); webhook отвечает 200 с нового адреса; `/health` = ok на боевом; `PII_STORAGE=real` только на базе в РК, на остальных пусто (`cli-check-env` подтверждает); сутки прожиты без вмешательства (сторож молчит, неисправностей нет); отчёт о переезде в `reports/`. Это закрывает условие допуска №1 из `CUTOVER.md`.
