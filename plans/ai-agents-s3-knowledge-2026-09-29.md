## 1. Что есть сейчас

  Движок кладёт ближайшие чанки в каждый ход сам (`src/ai/engine.py`, `retriever.search`), статусов, версий, видимости

- Диалоги, сообщения, вложения и знания живут в базе бота (`apps/ai-seller`), а не в базе стойки: `DATA_MODEL.md` не
  меняется (граница из плана §3). Миграции бота — `apps/ai-seller/migrations` (последняя `0005`).
- Кабинет техподдержки (S1, PR #154) ходит к боту служебным ключом: `packages/integrations/.../bot-panel-client.ts` →
  `apps/api/src/platform/support.*` → `apps/web/src/app/platform/support`.

## 2. Что строим

### 2.1 Запись знания (база бота, миграция `0006`)

Таблица `support_knowledge`:

| Поле | Значение |
|---|---|
| `id` | uuid |
| `title` | до 200 знаков |
| `category` | `PRODUCT`, `HOW_TO`, `TROUBLESHOOTING`, `BILLING`, `INTEGRATIONS`, `SECURITY`, `KNOWN_ISSUE`, `RUNBOOK` (CHECK) |
| `visibility` | `PUBLIC_SUPPORT`, `INTERNAL_SUPPORT`, `PLATFORM_ADMIN_ONLY` (CHECK) |
| `status` | `DRAFT`, `ACTIVE`, `OUTDATED`, `ARCHIVED` (CHECK) |
| `version` | целое, с 1; растёт при каждом изменении текста, названия, категории или видимости |
| `source` | откуда знание: `manual`, `conversation:<id>` (из закрытого обращения), имя документа; текст до 200 знаков |
| `content` | текст, до 20 000 знаков |
| `updated_at`, `created_at` | UTC |
| `approved_by`, `approved_at` | кто из главных администраторов опубликовал; пусто, пока не публиковали |

Таблица `support_knowledge_versions` — снимок при каждой смене версии (запись, версия, поля, кто и когда сохранил):
история для оператора и для отката вручную. Таблица `support_knowledge_chunks` — чанки и векторы **активной версии**
записи (чанкер и эмбеддер прежние). Таблица `support_knowledge_usage` — какие знания легли в ответ: диалог, запись,
версия, видимость, оценка, время.

### 2.2 Правила состояния

- **Отвечает только `ACTIVE`.** `DRAFT`, `OUTDATED`, `ARCHIVED` в поиск агента не попадают.
- **Публикует только главный администратор платформы.** Перевод в `ACTIVE` ставит `approved_by` (id администратора из
  сессии стойки, подставляет API, а не клиент) и `approved_at`; без него запись остаётся черновиком. Агент и оператор
  поддержки публиковать не могут: у бота нет такой команды, а маршрут закрыт правом «платформа».
- **Правка активной записи возвращает её в `DRAFT`** с новой версией: вчерашний текст не отвечает клиенту после того,
  как его переписали, и не отвечает с текстом, которого никто не утвердил. Пока черновик не опубликован, темы для агента
  нет — он честно говорит «не знаю» (умолчание; развилка Q-S3-1).
- **`OUTDATED`** ставит администратор вручную (интерфейс поменялся): запись видна в каталоге, агентом не используется.
- **Индекс живёт только у `ACTIVE`:** при публикации чанки строятся, при любом другом статусе — удаляются.

### 2.3 Видимость

Поиск получает `audience`. Для ответа клиенту (`client`, единственный путь в S3):

| Видимость | Что видит модель |
|---|---|
| `PUBLIC_SUPPORT` | текст записи; можно пересказывать |
| `INTERNAL_SUPPORT` | текст записи с пометкой «внутреннее: объясни своими словами, не цитируй» |
| `PLATFORM_ADMIN_ONLY` | **не попадает к модели вовсе** в разговоре с клиентом (строже, чем «не цитировать»: что модель не получила, она не пересказала) |

`audience = platform_admin` (песочница S9, помощник оператора) — позже; в S3 закладывается параметром и тестом.

### 2.4 Поиск и метаданные

Инструмент бота `search_knowledge(query)`: аргументы «кто/где» отсутствуют (как в S4). Ответ модели — до трёх записей;
у каждой: название, категория, видимость словом, версия, оценка близости и уровень уверенности `HIGH / MEDIUM / LOW`,
текст. Идентификаторы записи модель получает как `knowledgeId` только внутри инструмента; клиентский ответ их не
показывает (правило промпта и тест: в ответе движка нет ни id, ни слов «версия», «knowledgeId» из служебных полей).
Уверенность — по порогам из настроек (`support_kb_high`, `support_kb_medium`). Если лучшая запись `LOW` или ничего нет —
инструмент отвечает «не знаю: уточнит человек», а не подсовывает слабое совпадение (ответ «не уверен» лучше выдумки).

Каждый вызов, вернувший записи, пишет строки в `support_knowledge_usage` (`conversation_id` из `conversation_id_var`).
Оператор видит их в кабинете: у диалога — «На основании: …» (название, версия, видимость, оценка); клиент — нет.

### 2.5 Агент не учится сам

- В боте нет команды «создать/опубликовать знание». Закрытый кейс **ничего не пишет**.
- В кабинете у закрытого обращения — действие «Создать знание из обращения»: создаёт `DRAFT` (`source =
  conversation:<id>`, название — «Знание из обращения от <дата>», тело — шаблон «Симптом / Причина / Что делать»), который
  главный администратор дописывает, сохраняет и, если согласен, публикует. Само обращение в текст не копируется
  (в нём чужие данные). Возможное «предложение» от модели — не в S3.

### 2.6 Каталог у главного администратора (стойка)

«Платформа → Техподдержка → Знания»: каталог с поиском и чипами по категории, статусу и видимости; строка —
название, категория, видимость, статус, версия, обновлено; панель записи — текст, история версий, кем утверждено;
действия: создать, сохранить, «Опубликовать» (только у `DRAFT`, с подтверждением), «Пометить устаревшим», «В архив»,
вернуть в черновик. Старые документы вкладки «Знания» остаются как есть (Q-S3-2).
Партнёру и обычному пользователю каталога нет: маршруты за правом «платформа» (`@Access('platform')`).

## 4. Тесты (red до кода)

Бот: только `ACTIVE` находится; `DRAFT/OUTDATED/ARCHIVED` нет; `PLATFORM_ADMIN_ONLY` не доходит до модели, `INTERNAL`
идёт с пометкой; правка активной записи → `DRAFT` и запись пропала из поиска, версия выросла, снимок сохранён;
публикация без `approved_by` невозможна; повторная публикация не дублирует чанки; смена статуса с активного убирает
чанки; уверенность `LOW` даёт «не знаю»; метаданные (`knowledgeId`, версия, видимость, оценка) в результате поиска;
использование пишется с диалогом; клиентский ответ не содержит служебных полей; у инструмента нет аргументов
tenant/user; агент не имеет пути создать или опубликовать запись; закрытие обращения не создаёт знаний.
API: публикует только главный администратор (роль ниже — 403), `approvedBy` берётся из сессии, а не из тела.
Стойка: каталог виден только администратору платформы; «Опубликовать» с подтверждением; «На основании» у диалога.

## 6. Что не делаем

Автоматическое обучение, публикация без человека, чтение репозитория как базы, показ идентификаторов клиенту, цитирование
`PLATFORM_ADMIN_ONLY`, правка схемы `user_errors`, диагностические инструменты.
