# S4 — Requester Context для WETOP Support (2026-09-29)

Родитель: `plans/ai-agents-wetop-support-2026-09-29.md` §4 (порядок S0 ✅ → S1 ✅ → **S4** → S3 → S5).
Решения владельца 29.09: контекст строит сервер на существующем `RequestActor` (ADR-120), второй tenant-контекст
не создаём; scope задаёт сервер, модель `organizationId` выбрать не может. S3 и S5 не начинаем.

## 1. Что строим

Три инструмента WETOP Support **без параметров** — модель им ничего не передаёт:

| Инструмент | Отвечает на |
|---|---|
| `get_requester_context` | кто пишет: имя, скрытая почта, роль, организация, бизнесы и филиалы (название, направление, статус) |
| `get_account_status` | статус организации и подписки: организация, расширение «ИИ-продавец» (действует / истекло / не подключено, срок) |
| `get_permissions` | что этой роли можно и нельзя, словами `PERMISSIONS`; что решает только человек |

Данные — один серверный вызов `GET /assistant/requester-context`, три инструмента показывают его срезы.

## 2. Архитектура

- **Личность** берёт бот из подписи виджета (`Visitor.signed`, `user_id`, `org_id`) — так же, как `my_recent_errors`.
  Аноним и неподписанный получают «не могу посмотреть: вы не вошли», в API запрос не уходит.
- **API** `GET /assistant/requester-context?userId&organizationId`, только узкий ключ помощника
  (`assistant-read`) и служебный; адрес добавляется в `ASSISTANT_READ_ALLOWED` и в таблицу прав (`@Access('service')`).
- **Сервер не верит подписанной роли.** Он читает членство `(userId, organizationId)` из базы: нет членства — 404,
  роль берётся из строки членства. Подпись говорит только «кого искать».
- **Один контекст запроса.** Чтение идёт внутри `withSignedInUser({ userId, organizationId, role, scope: 'ORGANIZATION' })` —
  тот же `RequestActor`, что у запроса человека: под `wetop_app` действует RLS (DATA_MODEL §17), выборка не может выйти за
  организацию, даже если в коде забыт фильтр. Ни второго хранилища контекста, ни параметров `businessId`/`locationId`
  от бота: scope сервер вычисляет сам — ORGANIZATION; бизнесы и филиалы перечисляются из организации.
  (Когда переключатель P3 положит scope в подпись, сервер проверит его тем же `auth/scope.ts` — здесь не делаем.)
- **Расчёт — в домене**, чистой функцией (`packages/domain/src/accounts/requester-context.ts`): маска почты, слова
  роли, списки прав из `can`/`PERMISSIONS`, сборка ответа. Ни Prisma, ни Nest.
- **Минимум данных.** В ответе нет: пароля и хэша, сессий, телефона, ID пользователя и токенов, гостей, броней, денег,
  ключей и настроек продавца, внутренних ID сверх нужных (ID организации бот уже знает из подписи). Почта — маской.

## 3. Файлы

- `packages/domain/src/accounts/requester-context.ts` (+ тест) — сборка и маска;
- `apps/api/src/assistant/requester-context.{repository,service}.ts`, метод в `assistant.controller.ts`, регистрация в модуле;
- `apps/api/src/auth/auth.guard.ts` — адрес в `ASSISTANT_READ_ALLOWED`; тест таблицы прав;
- `apps/ai-seller/src/integrations/wetop_support.py` (+`providers.py`) — метод `requester_context`;
- `apps/ai-seller/src/ai/support_context.py` — три инструмента; подключение в `support_tools.build_registry`.

Модель данных, миграции, деньги, Channex, стойка не меняются.

## 4. Проверки (red → green)

1. Домен: маска почты; права роли (администратор не может возвраты — как `ROLE_PERMISSIONS`); ответ не содержит запрещённых полей.
2. Интеграция API (`tests/integration`, база `pms_test`): свой человек → контекст; чужая пара (пользователь без членства
   в организации) → 404; роль берётся из базы, а не из запроса; чужая организация в ответ не попадает; без ключа помощника
   и с чужим узким ключом — отказ.
3. Бот (pytest): инструменты без параметров; аноним → «не вошли», провайдер не вызван; сбой платформы → «не знаю»,
   без исключения; `org_id` берётся только из посетителя.
4. Затем typecheck, lint, unit, integration и pytest бота целиком.

## 5. Вне среза

База знаний и видимость (S3), диагностика и здоровье филиала (S5), запись любого рода, выдача прав, переключатель
scope (P3). Инструменты только читают.
