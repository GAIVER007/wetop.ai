# S5 — диагностика для WETOP Support (29.09.2026)

Поручение владельца 29.09 («давай делай» после S3 и калибровки). Опирается на `plans/ai-agents-wetop-support-2026-09-29.md`
§4, §9 (Q-A3), S4 (контекст обратившегося) и S3 (знания). Не входит: действия и их матрица (S6), Telegram (S7),
инциденты-склейки (S8), автоматические исправления, запись чего-либо в базу PMS.

## 1. Что уже есть (аудит)

- **Журнал ошибок человека** — `user_errors`, DATA_MODEL §14 (v1.8, ADR-081): `at`, `user_id`, `organization_id`,
  `method`, `route` (шаблон), `status`, `message` (после маски), `request_id`; хранение 30 суток с уборкой; пишет
  `ApiErrorFilter`, читает `GET /assistant/errors` узким ключом; у бота — инструмент `my_recent_errors`. Решение Q-A3
  описывало ровно такую таблицу и ещё три поля: `businessId?`, `locationId?`, `errorCode`. Сейчас область запроса —
  вся организация (`scope = ORGANIZATION`, переключателя P3 нет), заполнить `businessId`/`locationId` нечем; кодов
  ошибок у платформы нет (`find_error` ищет по тексту). Значит, миграция дала бы три пустые колонки — Q-S5-1.
- **Состояние платформы** — `GET /guard/status` (сторож), инструмент `platform_status`: «всё работает» / «критических
  неисправностей: N» / «база недоступна». Неисправности `system_incidents` (§12) — на всю установку, без организации.
- **Состояние Channex** — `ChannelConnectionService.status()` (живой вызов Channex), `FreshnessService.snapshot()` (только
  база: последнее событие, очередь ARI), `WebhookHealthService.snapshot()` (подозрение на webhook, проба адреса),
  `ChannelsRepository.mappings()` (сопоставление объекта, категорий, тарифов — по объекту вошедшего). Интеграция одна на
  установку: раздел открыт организации подключённого объекта и главному администратору (`isIntegrationActor`).
- **Карточка брони** — `loadReservationCard(db, propertyId, number)`: статус, даты, источник, канал, проживания с
  категорией и ячейкой, уборка ячейки; там же имя и телефон гостя, заметки — модели их отдавать нельзя.
- **Контекст обратившегося** — S4: пара «человек, организация» из подписи, сверка с членством, чтение от имени
  организации (`withSignedInUser`), белый список полей в домене.

## 2. Что строим

Три инструмента бота без аргументов «кто/где» (как S4) и два новых адреса узкого ключа помощника. Модель данных
не меняется, миграций нет, запись в базу PMS не появляется.

| Инструмент | Аргументы | Источник | Что получает модель |
|---|---|---|---|
| `get_integration_health` | нет | `GET /assistant/integrations?userId&organizationId` | подключены ли каналы; состояние словом (`READY` / `NO_KEY` / `NO_MAPPING` / `ATTENTION`); категорий сопоставлено N из M; тарифов сопоставлено; сколько минут назад последнее событие; очередь ARI (ждут, сбои, самая старая ждёт N мин); webhook (под подозрением, адрес недоступен); список проблем кодами |
| `get_reservation_status` | `number` — номер брони, который назвал человек (1–40 знаков: буквы, цифры, `-`, `_`) | `GET /assistant/reservation?userId&organizationId&number` | статус, даты и ночи, источник и канал, взрослые/дети, проживания (категория, статус, ячейка назначена или нет, код ячейки, уборка), проблемы кодами |
| `get_workspace_health` | нет | сборка на стороне бота из уже существующих провайдеров: контекст S4 (аккаунт), `platform_status`, `get_integration_health`, число своих ошибок за окно | одна сводка «с чего начать»: аккаунт, платформа, каналы, ошибки за N ч; каждая часть может быть «не знаю» отдельно |

### 2.1 Чего модели не отдаём (по построению)

Имя, телефон, гражданство и документы гостя, заметки брони (`notes`), суммы и оплаты, идентификаторы (брони — только
номер, который человек сам назвал; объекта, ячейки, категорий — нет, только коды/названия), ключи и адреса Channex,
адреса получателей оповещений, чужие организации. Ответ API собирает доменная функция по белому списку; бот делает текст
тоже по белому списку — лишнее поле сервера до модели не доходит (тест как в S4).

### 2.2 Правила области

- `userId`/`organizationId` — только из подписи посетителя; сверка с членством как в S4 (`RequesterContextRepository.facts`
  → `null` → 404). Чтение — `withSignedInUser({userId, organizationId})`: репозиторий каналов сам берёт объект
  организации, под RLS база режет чужое.
- Каналы: если организация не та, к которой подключена интеграция (`isIntegrationActor` без прав администратора), ответ
  `{ channex: null }` — «каналы не подключены», без проверки сопоставлений. Живого вызова Channex нет: только база и
  снимок сторожа webhook (лимиты Channex и время ответа чата).
- Бронь: ищется среди объектов организации (`reservation.findFirst({ confirmationNumber, property: { organizationId } })`);
  чужая или несуществующая — 404 «брони с таким номером нет», без различения.
- Неисправности сторожа по брони (`system_incidents.subject_type = reservation`) в S5 не подмешиваются: таблица общая на
  установку, номер брони уникален только внутри объекта — пришлось бы доказывать принадлежность; отложено (Q-S5-3).

### 2.3 Коды проблем (домен, `packages/domain/src/support/diagnostics.ts`)

Каналы: `KEY_MISSING`, `PROPERTY_NOT_MAPPED`, `CATEGORIES_UNMAPPED`, `RATE_PLANS_UNMAPPED`, `WEBHOOK_SUSPECT`,
`WEBHOOK_UNREACHABLE`, `OUTBOX_FAILED`, `OUTBOX_STUCK` (самая старая ждёт дольше 30 мин), `NO_EVENTS_24H` (объект
сопоставлен, а событий сутки нет). Состояние: `NO_KEY` → `NO_MAPPING` → `ATTENTION` (есть проблемы) → `READY`.

Бронь: `CANCELLED`, `NO_SHOW`, `UNASSIGNED_ITEMS` (есть проживание без ячейки), `ARRIVAL_PASSED_NOT_CHECKED_IN` (дата
заезда прошла по часам объекта, статус не «заселён/выехал»), `DEPARTURE_PASSED_NOT_CHECKED_OUT`,
`UNIT_NOT_INSPECTED_BEFORE_ARRIVAL` (заезд сегодня или впереди, уборка ячейки не «проверено»). Пороги новые не вводятся:
всё — из существующих статусов и дат.

## 3. Слои и порядок

1. **Домен:** `buildIntegrationHealth(facts, now)`, `buildReservationDiagnostics(card, today)` — чистые функции,
   тесты red → green.
2. **API:** `DiagnosticsService` в `assistant/`, два маршрута в `AssistantController` (`@Access('service')`, ключ
   `assistant-read`/`service`, uuid-параметры), `ASSISTANT_READ_ALLOWED` и таблица `route-access`. Тесты контроллера
   (ключ, id, чужая организация, отсутствие ПД в теле) и integration на базе (две организации: своя бронь находится,
   чужая — 404; организация без интеграции — `channex: null`).
3. **Бот:** `DiagnosticsProvider` (Protocol) и методы в `WetopSupportMixin`; `src/ai/support_diagnostics.py` с тремя
   инструментами; `build_registry` их регистрирует; списки инструментов в тестах. Тесты: нет аргументов области, чужой
   аргумент отвергнут, отказы словами, в тексте нет id/почты/телефона/имён, лишние поля сервера не доходят, сводка
   собирается при частичных сбоях, номер брони проверяется.
4. **Документация:** `docs/assistant/README.md` (два адреса), план §13, отчёт `reports/ai-agents-s5-2026-09-29/`,
   CLAUDE.md §2. **Стоп: S6 без отдельного подтверждения не начинать.**

## 4. Вопросы владельцу — закрыты владельцем 30.09.2026

| № | Вопрос | Умолчание |
|---|---|---|
| Q-S5-1 | Q-A3 просил поля `businessId?`, `locationId?`, `errorCode` в журнале ошибок. Область запроса сейчас — вся организация, кодов ошибок у платформы нет: колонки были бы пустыми. Добавлять сейчас (DATA_MODEL → ADR → миграция) или когда появятся переключатель филиала (P3) и коды? | **Решение: нет.** §14 как есть; пустые колонки создали бы ложную модель. Вернуться при Location-скоупе (P3) и нормализованном `errorCode` |
| Q-S5-2 | Q-A3 называл инструмент `get_recent_user_errors`; в боте он уже есть как `my_recent_errors`. Переименовать? | **Решение: оставить `my_recent_errors`** — внутреннее имя, переименование даёт только churn тестов и промпта |
| Q-S5-3 | Подмешивать ли к брони открытые неисправности сторожа по ней (`system_incidents`, например «событие канала не обработано»)? Таблица общая на установку, нужна проверка принадлежности объекта | **Решение: нет.** По номеру брони сопоставлять нельзя; вернуться, когда у `system_incidents` будет стабильная связь `reservationId` + проверка принадлежности объекта на сервере — тогда `incidents[]` отдельным полем |
| Q-S5-4 | Показывать ли модели оплату брони словом («оплачена / частично / не оплачена», без сумм)? Требует чтения счетов | **Решение: нет.** Даже `PAID / PARTIAL / UNPAID` не показывать: расширяет финансовую поверхность агента без конкретного случая. При задаче «почему висит долг» — отдельный типизированный инструмент с минимальным перечнем, без сумм и реквизитов |

## 5. Что не делаем

Живые вызовы Channex из чата, запись в `user_errors` или `system_incidents`, любые действия по брони и каналам (S6),
показ идентификаторов и ПД, диагностику чужих организаций, изменение модели данных.
