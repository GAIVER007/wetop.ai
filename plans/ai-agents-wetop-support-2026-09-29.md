# «ИИ-агенты» и WETOP Support — целевая схема и порядок срезов (29.09.2026)

Статус: **план утверждён владельцем 29.09 (§9); S0 сделан, дальше — по отдельной команде.** Источник — постановка владельца 29.09 (67 пунктов). Ниже: что из неё уже есть в
репозитории, что нового, в каком порядке строить и что до старта надо решить. Решения по данным, деньгам и правам —
не мои: развилки записаны как вопросы, умолчание указано.

## 1. Что решено в постановке

1. Верхний уровень раздела: «ИИ-продавец» → **«ИИ-агенты»**. Внутри агенты с разными задачами: «ИИ-продавец»
   (область — Партнёр/Бизнес/Филиал) и **WETOP Support** (глобальный агент платформы).
2. Настройки WETOP Support видит только главный администратор платформы. Пользователь партнёра открывает
   «Техподдержка → Написать в поддержку» и говорит с этим же агентом, экрана агента у него нет.
3. Агент не ходит в базу. У него типизированные инструменты; каждый принимает `organizationId` (и при необходимости
   `businessId`, `locationId`), а сервер сам проверяет доступ. Ни shell, ни SQL, ни файловой системы.
4. Две памяти: каталог знаний WETOP (управляемый, с версиями и видимостью) и состояние клиента прямо сейчас
   (runtime-контекст через инструменты).
5. Действия трёх видов: SAFE (сам), CONFIRM (после «да» клиента), HUMAN_ONLY (только эскалация).
6. Обучения модели на чатах нет. RAG по одобренным знаниям плюс инструменты.

## 3. Границы, которые держим при любом срезе

- **Изоляция:** каждый инструмент получает scope от сервера (`RequestActor`), а не от модели. Модель не может
  подставить чужой `organizationId`: значение берётся из сессии, параметром инструмента оно не передаётся.
- **Минимум данных:** инструмент возвращает то, что нужно для ответа. Паспорт, платёжные реквизиты, токены,
  env, URL базы, секреты вебхуков, полный stack trace — никогда, ни в ответ, ни в Telegram, ни в журнал вызовов.
- **Видимость знаний:** `PUBLIC_SUPPORT`, `INTERNAL_SUPPORT`, `PLATFORM_ADMIN_ONLY`. Последнюю агент клиенту
  не цитирует; внутренние документы пересказываются языком пользователя.
- **Недоверенный ввод:** текст со скриншота, из файла и из чата — данные, а не команды.
- **Деньги и права:** возвраты, тариф подписки, отключение организации, права Owner, удаление данных, массовые
  правки броней — `HUMAN_ONLY`. Агент никому не выдаёт права.
- **База PMS не смешивается с базой сервиса агента:** диалоги, знания, вызовы инструментов, версии живут в базе
  `apps/ai-seller`; бизнес-данные бот читает только через API.
- **Read-only пока не доказано обратное:** первые инструменты только читают. `retry_channel_job` и подобное — S6,
  с проверкой tenant, статуса, лимита и идемпотентности на стороне API.

## 5. Что нужно от WETOP, а не от агента (зависимости)

1. **Телеметрия ошибок пользователя** (п. 13): API пишет код ответа, маршрут, код ошибки, `userId`, время — без тела
   запроса. Сейчас `my_recent_errors` читает то, что есть у бота; для ошибок PMS нужна запись на стороне API.
   Схема данных меняется → сначала `DATA_MODEL.md` и решение владельца (Q-A3).
2. **Права как данные:** `get_permissions` опирается на таблицу прав ролей (DATA_MODEL §16.5, ADR-107). Инструмент
   только отдаёт вердикт «есть/нет права X», сами права не меняет.
3. **Состояние подписки:** `TRIAL/ACTIVE/READ_ONLY/SUSPENDED` уже считается платформой (ADR-102); инструмент читает
   готовое слово.
4. **Здоровье филиала и интеграций:** есть сторож Channex/webhook и `cli-day-selfcheck`; нужен API-слой, который
   отдаёт их результат по scope без инфраструктурных деталей.
5. **Telegram:** бот уже шлёт тревоги (`src/alerts/messenger.py`); формат карточки эскалации без ПД — отдельная
   договорённость.

## 9. Решения владельца 29.09 — Q-A1…Q-A6 закрыты

- **Q-A1.** S1 (WETOP Support Desk: очередь, передача человеку, закрытие, статусы) — PR #154, уже влит в `main`
  (слияние #155). Повторно не строить. Зависимые срезы идут поверх него.
- **Q-A2.** Раздел зовётся «ИИ-агенты». Партнёр видит агентов своего бизнеса (сейчас — AI-продавец). WETOP Support в
  каталоге партнёра нет: настройки, знания, инструменты и версии — только главному администратору; пользователь
  говорит с ним через «Техподдержка → Написать в поддержку».
- **Q-A3.** Отдельная минимальная модель телеметрии ошибок, хранение 30 дней. Поля: `id`, `organizationId`,
  `businessId?`, `locationId?`, `userId`, `requestId?`, `routeTemplate` (`/reservations/:id`, не живой URL),
  `method`, `statusCode`, `errorCode`, `occurredAt`. Не хранить: тела запроса и ответа, URL с ID и ПД, query,
  cookies, `Authorization`, токены сессии, email, телефон, документы, ПД гостей, stack trace, секреты. Перед кодом:
  `DATA_MODEL.md` → ADR → миграция → чистка по сроку. Агент читает это только инструментом
  `get_recent_user_errors`; scope — с сервера из `RequestActor`, не от модели.
- **Q-A4.** Настройки WETOP Support остаются в настройках платформы (ADR-084). В `apps/ai-seller` не переносить.
  `AgentDefinition`, `AgentVersion`, `PromptVersion`, `ToolSchemaVersion` — в S9.
- **Q-A5.** Первая версия Telegram-эскалации: получатель — главный администратор WETOP; ID и имя не в коде, а в
  существующей конфигурации alert/messenger. Виды: `CRITICAL`, `SECURITY`, `SUBSCRIPTION_CANCELLATION`, `BILLING`,
  `HUMAN_REQUIRED`, `LOW_CONFIDENCE`, `SYSTEM_OUTAGE`. В Telegram никогда: секреты, документы, платёжные данные,
  stack trace, лишние ПД.
- **Q-A6.** Минимизация данных. Модель по умолчанию не получает email и телефон. Контекст запроса для модели:
  псевдонимный id пользователя, `displayName` только когда нужен, роль, названия организации, бизнеса и филиала,
  сводка прав, статус подписки, текущий маршрут. Контакты остаются внутри WETOP. Если инструменту понадобится email —
  отдельное решение и security review.

**Архитектурное правило.** В интерфейсе оба агента — «ИИ-агенты», но классы разные:
- Business Agent (AI-продавец): область — организация, бизнес, филиал.
- Platform Agent (WETOP Support): вся платформа; контекст клиента — только на конкретное обращение.

**Порядок после S0:** сверить S1 с `main` → S4 → S3 → S5 → S6 → S7 → S8 → S9 → S10. Новый срез без отдельного
подтверждения владельца не начинать.
