# Аналитика v2 — срез AN1: модуль «Аналитика» и экран «Обзор» (27.09.2026)

**Основание:** ТЗ владельца «WETOP Hospitality · Аналитика v2» от 27.09.2026 (35 разделов, передано облачной
сессии задачей). ТЗ само задаёт порядок: сначала аудит (§31), потом **AN1 — Обзор**, после него **стоп и
снимки** (§33–34); AN2–AN6 — отдельными PR после визуального «да» владельца. Решение — **ADR-114**.

Коротко о смысле. Сейчас пункт «Статистика» отвечает на один вопрос: сколько мест занято в выбранный день.
ТЗ просит модуль, который отвечает на другой: как работал объект за период — загрузка, выручка, брони,
отмены, категории, и стало ли лучше или хуже. Старый экран не выбрасываем: он становится вкладкой
«Загрузка».

## 1. Аудит перед кодом (§31–32 ТЗ)

| Вопрос ТЗ | Что в коде сейчас |
|---|---|
| Что считает экран «Статистика» | `management/[[...section]]/page.tsx`: `GET /chessboard?from=d&to=d` (один день) + `GET /inventory/summary` (названия категорий). Четыре плитки (занято, свободно, заблокировано, без места) и таблица по категориям. Своего эндпоинта у статистики нет |
| Откуда загрузка | `ChessboardService.board` → `summary[date]` и `byCategory[date]`: занятые, свободные и закрытые ячейки. Та же шахматка, что на экране, — разойтись они не могут |
| Что такое unit-night | Одна ячейка (номер или койка, ADR-013) на одну дату. Номер = 1 единица, койка = 1 единица |
| Блокировки в знаменателе | **Входят.** «Загрузка = занятые / весь фонд категории, включая блокировки» (подсказка «Статистики») и ADR-047 («занятые клетко-ночи / (единиц × ночей)»). По §32 ТЗ правило не меняется: AN1 считает так же, в подсказке это сказано словами |
| Выручка | Начисления счетов по `service_date` без сторно (ADR-047, «Деньги за период»). Начисление за проживание **одно на проживание и датировано днём заезда** (`scripts/imports/src/cli-backfill-charge-dates.ts`, `finance.service`). Следствие для графика «Выручка по дням»: столбик дня — стоимость заехавших в этот день проживаний, а не проданные в этот день ночи. Разнести стоимость по ночам — новое правило денег, это вопрос владельцу (**Q-208**) |
| ADR | начислено за проживание / занятые клетко-ночи, целочисленно в тиынах (ADR-047) |
| RevPAR | начислено за проживание / (единиц × ночей) (ADR-047) |
| Источники броней | Дашборд: проживания по дате заезда, `source`/`channel` (имя канала Channex приведено к одному), сумма — стоимость проживаний. «Менеджер каналов»: брони (`Reservation`) по дате заезда брони, `groupBy source/channel/currency/status`, отмены и незаезды входят в счёт |
| Отмены и незаезды | Дашборд: статус проживания `CANCELLED` / `NO_SHOW` по дате заезда, отдельно от заездов. «Менеджер каналов»: статус брони |
| Один запрос без N+1 | Уже так: `GET /desk/dashboard?from&to` — шахматка кусками по 62 дня (4 запроса на кусок) и четыре выборки параллельно (проживания, начисления, платежи, возвраты); то же за предыдущий отрезок. Запросов на строку нет |
| Что есть на `/today` | `kpi.tsx` (6 плиток со сравнением), `daily-bars.tsx` (загрузка по дням с подписью дня), `dashboard-panels.tsx` (категории по дням, источники, таблица категорий, оплаты по способам), `period-bar.tsx`. По ADR-105 всё это уходит с Главной; PR A1 (#103, ждёт гейта) переносит блок на временный экран `/management/dashboard` «Показатели за период» |
| Что переиспользуем | Расчёт `packages/domain/src/dashboard` (`buildDashboard`, `previousPeriod`, `resolvePeriod`), API `GET /desk/dashboard`, форматтеры `lib/dashboard-format.ts` (при нулевой базе `deltaPercent` уже отвечает «нет базы»), классы `.kpi*`, `.bars*`, `.dash-*`, `.sources`, `.settings-tabs`. «Оплаты по способам» уже есть в «Оплатах» (`finance/page.tsx`) — в аналитику не переносятся (§20 ТЗ: аналитика не второй раздел финансов) |
| Номера и койки | `InventoryUnit.kind`: `ROOM` / `BED` (строка шахматки несёт `unit.kind`). Категория однородна: `AccommodationType.kind` `PRIVATE_ROOM` / `APARTMENT` — номера, `DORM_BED` — койки. Фильтр «Номера / Койки» строится на данных, ничего не выдумывая |

## 2. Что входит в AN1

1. **Меню.** «Статистика» → **«Аналитика»** (`/management/analytics`) в группе «Финансы и отчёты» после «Оплат».
   Пункт `/analytics` в реестре меню называется «Аналитика сайта» — как в меню и в заголовке его экрана: два
   пункта «Аналитика» в поиске ⌘K путали бы.
2. **Вкладки модуля:** «Обзор» (`/management/analytics`) и «Загрузка» (`/management/analytics/occupancy`).
   Вкладка «Загрузка» — нынешний экран «Статистика» как есть (AN2 переделает его); `data-testid` прежние.
   `/management/statistics?date=…` перенаправляет туда с той же датой. Вкладки «Брони», «Продажи», «Категории»
   появятся в AN3–AN5; пустых вкладок-заглушек нет.
3. **Верх «Обзора»:** подпись периода («1 сент. — 30 сент. 2026 · 30 дней»), готовые отрезки
   «Сегодня · 7 дней · Этот месяц · Прошлый месяц» ссылками (применяются сразу), «Период» раскрывает
   «С / По» (родной `<details>`, без JavaScript). По умолчанию — этот месяц. Рядом — тип фонда
   «Все / Номера / Койки» и переключатель «Сравнивать с предыдущим периодом» (по умолчанию включён).
   Большой кнопки «Показать» больше нет; «Применить» живёт только внутри «Периода».
4. **Шесть плиток** (§5): Загрузка (п.п.), Выручка проживания, Продано ночей, Брони, Отмены (доля, п.п.),
   Средний чек брони. Рост отмен красный, падение зелёный — у остальных наоборот.
5. **ADR / RevPAR по типу фонда** (§6): при «Номерах» — «Средняя цена номера (ADR)» и «Доход на номер
   (RevPAR)», при «Койках» — «Средняя цена койки» и «Доход на койку». При «Всех» средней цены нет —
   вместо неё строка «Средняя цена считается отдельно для номеров и для коек» со ссылками на оба вида.
6. **Графики:** «Загрузка по дням» (подпись дня: загрузка, занято, свободно, закрыто — §7) и «Выручка
   проживания по дням» (§8) с пояснением, что начисление датировано заездом. На один день вместо столбиков —
   полосы по категориям.
7. **Источники** (схема §28) — компактный список долей рядом с выручкой, ссылка на полный отчёт.
8. **Категории** (§9): Категория · Мест · Продано ночей · Загрузка · Выручка · Ср. цена за ночь.
   Средняя цена по категории не смешивает номера и койки — категория однородна.
9. **Сравнение честное** (§17, §27): предыдущий отрезок той же длины вплотную к текущему
   (1–30 сент. → 2–31 авг.). База сравнения ноль — «нет данных для сравнения», никаких «+100 %».
10. **Пусто, загрузка, сбой** (§25–26): «Недостаточно данных за выбранный период. Выберите другой период.»;
    скелетон плиток и графика; отказ API — `LoadError` без потери полосы периода.

## 3. Определения новых чисел

Все — из того, что уже считает `buildDashboard` (ADR-047); новые правила денег не вводятся.

| Показатель | Как считается |
|---|---|
| Выручка проживания | начисления `ACCOMMODATION` без сторно, `service_date` в периоде (день заезда) |
| Продано ночей | занятые клетко-ночи шахматки за период (`occupiedNights`) |
| Брони | проживания с заездом в периоде, **все статусы** — вместе с отменёнными и незаездами. Считаются проживания, как «Заезды» ADR-047: групповая бронь на три койки — три брони (**Q-209**) |
| Отмены | отменённые / брони, %; незаезды — в подписи плитки своим числом и долей |
| Средний чек брони | стоимость проживаний без отмен и незаездов / их число, целочисленно в тиынах; та же база, что у «Источников» |
| Выручка по дням | начисления за проживание по `service_date` = день заезда |
| Тип фонда | номера — категории из единиц `ROOM`, койки — из `BED`; всё выше считается только по категориям выбранного типа. Проживания без ячейки тоже делятся по категории |
| Сравнение | тот же расчёт за предыдущий отрезок той же длины; п.п. для долей, % для остального; база сравнения — прошлое количество (занятые ночи, брони, деньги): ноль — «нет данных для сравнения» |

## 4. Что меняется в коде

- `packages/domain/src/dashboard/metrics.ts`: у категории `kind`, у начисления `serviceDate`, проживания
  без ячейки — по категориям; `buildDashboard(input, fund)` сужает всё до типа фонда; в ответе
  `fund`, `funds` (сколько номеров и коек в фонде), `bookings`, `daily[].revenueMinor`, `categories[].kind`.
  Прежние поля не меняются: Главная и «Показатели за период» из A1 работают как раньше.
- `apps/api/src/dashboard`: `GET /desk/dashboard?from&to&fund=all|rooms|beds`, неизвестный `fund` — 400;
  репозиторий отдаёт тип категории из шахматки и дату начисления.
- `apps/web/src/app/management/analytics/`: страницы «Обзор» и «Загрузка», `analytics.css`, общий
  график по дням `components/day-bars.tsx` (строка в DESIGN.md §8).
- `management/[[...section]]`: остались только перенаправления.
- Фикстура `scripts/preview/fixture-api.ts`: тип категории, дата начисления, параметр `fund`.
- Тесты, в которых стоял адрес или заголовок «Статистики», — на новый адрес.

## 5. Чего в AN1 нет

AN2 (вкладка «Загрузка» v2), AN3 (брони, отмены, незаезды, окно бронирования), AN4 (источники продаж —
перенос отчёта «Менеджера каналов», согласуется с ТЗ «Каналы продаж v2», PR #110), AN5 (категории
подробно), AN6 (переходы из каждой плитки, экспорт, телефон, полировка). Business- и Organization-scope
(§22–23) — после фаз платформы (ADR-104). Модель данных, финансовая логика и команды не трогаются.

## 6. Параллельные PR

- **#103 (A1 Главной)** переносит блоки периода на `/management/dashboard`. AN1 их не трогает и файлов из
  `today/` не импортирует. Кто сольётся вторым: `/management/dashboard` становится перенаправлением на
  `/management/analytics`, пункт «Показатели за период» уходит из меню — «Обзор» его покрывает целиком,
  кроме «Оплат по способам» и «Получено оплат», которые живут в «Оплатах».
- **#110 / #111 (каналы)** уносят отчёт по источникам в аналитику — это AN4; в AN1 «Менеджер каналов» не
  меняется, «Обзор» ссылается на его отчёт.

## 7. Доказательства

- red → green: модульные тесты домена (тип фонда, выручка по дням, брони и отмены) и контроллера (`fund`).
- typecheck, lint, unit, UI-набор стойки в один поток (`--workers=1`), живые e2e на локальной базе.
- Снимки для стопа §34 — `reports/analytics-v2-an1-2026-09-27/`: тёмная и светлая темы на компьютере,
  месяц с данными, прошлый месяц, рост и падение, база сравнения ноль, «Все / Номера / Койки», телефон.

## 8. Вопросы владельцу

- **Q-208** — разносить ли выручку проживания по ночам в графике «по дням» (сейчас — день заезда).
- **Q-209** — «Брони»: считать проживания (как сейчас «Заезды») или брони целиком; по дате заезда или по
  дате создания брони. AN1 считает проживания по дате заезда — это действующие определения ADR-047.
