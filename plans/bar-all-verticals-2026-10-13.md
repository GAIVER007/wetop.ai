# Бар для всех направлений: переезд с объекта гостиницы на филиал (Q-REST-9, Q-AI-MV-BAR)

Поручение владельца 13.10.2026: «бар относится и к ресторанам, и к гостиницам, и к салонам, может быть и там,
и там». Статус плана: **УТВЕРЖДЁН владельцем 13.10.2026** («Да, делай по плану»), развилки решены ниже (ADR-178).

## Что есть сейчас (аудит 13.10.2026)

- 10 таблиц `bar_*`, у семи верхних `property_id` NOT NULL (FK `properties`), уникальности по `property_id`
  (код и штрихкод товара, имя категории и поставщика, документ прихода, ключ повтора продажи).
- Пять миграций защиты (051, 053–057): владение по `property_id` неизменно, дочерние строки обязаны совпадать
  с родителем, продажа в счёт гостя сверяется с бронью, кассой и начислением гостиницы, обратные триггеры на
  `cash_operations`, `charges`, `folios`, `reservation_items`, `reservations`.
- Деньги бара: продажа за наличные пишет `cash_operations` (касса гостиницы, на Property), «в счёт гостя» пишет
  `charges` в счёт брони, оплата поставщику пишет `cash_operations` расходом.
- API выбирает объект гостиницы по имени (`propertyIdRef`), без бизнеса и филиала из запроса; у салона и
  ресторана объекта нет, поэтому сейчас бар им отвечает «объект не настроен».
- Экраны `/bar` закрыты `requireVertical(['HOSPITALITY'])`, пункт меню только у гостиницы.

## Цель

Бар как модуль филиала: у гостиницы, ресторана и салона свой бар со своим каталогом, приходами, остатками,
списанием, инвентаризацией и продажами. Продажа «в счёт гостя» остаётся только гостиничной: счёт брони есть
только у гостиницы.

## Развилки владельца: решены 13.10.2026

1. **Куда идут деньги бара в ресторане. РЕШЕНО: в кассу ресторана.** Было предложено: в кассу ресторана (§35): продажа за наличные или картой
   это приход кассы ресторана, оплата поставщику это расход. Альтернатива: бар ресторана продаёт только через
   заказы (меню и POS), а модуль бара ведёт только склад напитков.
2. **Куда идут деньги бара в салоне. РЕШЕНО: сделать кассу салона сейчас** (этап 0 ниже). Было предложено: в салоне бар сначала ведёт только склад
   (приход, остаток, списание, инвентаризация), а продажи включаются вместе с кассой салона отдельным срезом.
   Альтернатива: завести кассу салона сейчас (это новый денежный модуль, больше срез).

## Этапы (каждый своим PR, красный тест до зелёного)

0. **Касса салона** (решение владельца по развилке 2): по образцу кассы ресторана §35 (платежи, приход, расход,
   перевод, сверка, остатки по способам), своя модель в DATA_MODEL отдельным разделом и своё ADR, затем бар
   салона продаёт в неё. Делается после этапов 1–3, до продаж бара в салоне. **Сделано 16.10.2026** касса филиала §35.2 открыта салону (§48, миграция №113, ADR-BRANCH-CASH-20261016).

1. **Модель (DATA_MODEL §44, миграции №102 и №103).** `location_id` NOT NULL у семи верхних таблиц бара с
   заполнением из `properties.location_id` (у каждого объекта филиал есть, аудит подтвердил); уникальности
   переходят с `property_id` на `location_id`; `property_id` становится необязательным (только у бара
   гостиницы) с проверкой «объект принадлежит этому филиалу»; RLS `rls_tenant` через `locations → businesses`;
   охранные триггеры переписываются на филиал, гостиничные проверки счёта и кассы остаются как есть для строк
   с объектом. Предварительная проверка в миграции: остановиться, если хоть одна строка не сводится.
2. **API.** Область запроса по филиалу (как `foodScope`, но для всех направлений), право по-прежнему `desk` и
   `settings`; «в счёт гостя» только при направлении гостиницы; деньги по ответам на развилки 1 и 2.
3. **Экраны.** `/bar` во всех трёх меню; у ресторана и салона без «в счёт гостя»; права и подписи прежние. **Сделано 15.10.2026** (PR #557).
4. **Излишек при инвентаризации бара (Q-BAR-9, ADR-175)**: по средней себестоимости остатка, как у кухни. **Сделано 16.10.2026** (§47, миграция №112).
5. **Тесты.** Перенос интеграционных проверок владения (bar-ownership, bar-property-guard, populated-rls,
   external-parent, concurrency) на филиал; UI бара на стендах ресторана и салона; гостиничный набор бара
   без изменений поведения. **Сделано 16.10.2026:** прежний набор владения зелёный на филиале (386 из 457, 71 за флагами
   аудита); новый `bar-location-children` проверяет дочерние строки и кассу между рестораном и салоном одной
   организации, каждая из шести охран подтверждена мутацией; UI бара ресторана и салона в `tests/food-ui`.
   **План бара закрыт.**

## Риски

- Рабочие данные бара гостиницы: миграция переносит их с проверкой, откат возвращает `property_id` как был.
- Пять миграций защиты денег: переписываются только части про владение, связи со счётом гостя и кассой
  гостиницы остаются строгими. Проверяется тем же набором интеграционных тестов на чистой PostgreSQL.
- Объём: 2–3 рабочих сессии; выкладка после миграций владельца.
