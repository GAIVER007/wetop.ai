# План: формы бара берут способы оплаты из настройки объекта (продолжение ADR-185)

Дата: 15.10.2026. Ветка `claude/youthful-wozniak-vin0pp` (перезапущена от `main` `ab72d159` после PR #271).
Поручение владельца: «давай продолжай» после слияния PR #271; в ADR-185 и в PR #271 формы бара с их
собственными списками способов отложены «отдельной правкой». Код по этому плану начинается после «да» владельца
(AGENTS.md §1: срез меняет проверку в API и сценарий продажи).

## 1. Что есть сейчас (аудит по коду `main` `ab72d159`)

| Где | Список способов | Откуда |
|---|---|---|
| `apps/web/src/app/bar/sale-form.tsx` («Быстрая продажа») | CASH, CARD_TERMINAL, KASPI, HALYK, BANK_TRANSFER_PERSON | зашит в разметке |
| `apps/web/src/app/bar/supplier-payment-form.tsx` (оплата поставщику) | те же плюс BANK_TRANSFER_LEGAL | зашит в разметке |

Деньги бара (DATA_MODEL §44, §45; `bar.repository.ts` `scope()`): бар живёт на филиале; у бара гостиницы есть
объект (`location.property`), и его продажи и оплаты поставщикам идут в кассу объекта (§21); у бара ресторана
деньги идут в кассу ресторана (§45, свои `restaurant_cash_operations`); бар салона без объекта денег не проводит
(`no_cash`). Настройка способов `payment_method_settings` (§21.6) привязана к объекту, то есть к гостинице.

Домен уже умеет: `resolvePaymentMethodSettings`, `enabledPaymentMethods`, `assertPaymentMethodEnabled`
(`packages/domain/src/finance/payment-methods.ts`); API стойки отдаёт `GET /hotel/payment-methods`; формы
оплаты брони, запросов оплаты и кассы объекта берут список оттуда (ADR-185).

## 2. Что сделать

1. **API бара (гостиница).** `sellRetail` и `payReceipt`: после проверки «способ из поддерживаемых баром» (список
   остаётся: бар не принимает депозит, гарантию картой и внешний канал) для филиала с объектом вызывать
   `assertPaymentMethodEnabled` по настройке этого объекта; выключенный способ даёт 400 теми же словами, что у
   кассы: «Способ оплаты «Kaspi» выключен в настройках объекта». Ответы `GET /bar/stock` (продажа) и
   `GET /bar/receipts` (оплата поставщику) получают `paymentMethods: string[]`, порядок по настройке, только
   поддерживаемые баром. У бара без объекта (салон, ресторан) поле отдаёт прежний полный список бара.
2. **Формы бара.** `sale-form.tsx` и `supplier-payment-form.tsx` строят `<option>` из `paymentMethods` ответа,
   подписи из одного источника `PAYMENT_METHOD_RU` (домен; слово «Карта» вместо «карта (терминал)» остаётся
   подписью бара, см. п. 4). Первый включённый способ становится значением по умолчанию; если включённых
   способов бара нет (объект оставил только депозит и гарантию, чего CHECK не запрещает), форма показывает
   «В настройках объекта нет способа оплаты, который принимает бар» и кнопку продажи не рисует.
3. **Подставной API** (`scripts/preview/fixture-api.ts`, `tests/ui/fixture-api.ts`): `paymentMethods` в ответах
   бара из той же настройки, что у кассы объекта.
4. **Подписи.** Бар подписывает CARD_TERMINAL как «Карта», BANK_TRANSFER_PERSON как «Перевод»; у домена «карта
   (терминал)» и «перевод от физлица». Оставляю подписи бара как в макете владельца 09.10 (короткие слова в одной
   строке), но беру их из одной карты `BAR_METHOD_RU` в `apps/web/src/app/bar/labels.ts` вместо двух разметок;
   сводить с доменом не буду без слова владельца: это текст экрана, утверждённый макетом.
5. **Модель данных и миграции не меняются.** Касса ресторана (§35) и `FOOD_PAYMENT_METHODS` не трогаются: Q-296.

## 3. Чего не делаю и почему (Q-296)

У ресторана и салона объекта нет, настройка §21.6 к ним не относится. Чтобы ресторан мог выключить Halyk в
своей кассе, нужна настройка на филиале (новая таблица или `location_id` в `payment_method_settings`), это
изменение модели (AGENTS.md §15, CLAUDE.md §3). Вопрос записан как Q-296 с умолчанием «пока как есть».

## 4. Доказательства (red → green)

- unit API `apps/api/src/bar/bar.service.test.ts`: продажа и оплата поставщику выключенным способом у бара
  гостиницы → 400 словами; у бара без объекта тот же способ проходит; `paymentMethods` в ответах.
- integration `tests/integration/bar-payment-methods.test.ts` на локальной базе: строка настройки объекта с
  выключенным KASPI, продажа KASPI → 400, продажа CASH → POSTED; порядок в `paymentMethods` по `sort_order`.
- UI `tests/ui/bar-payment-methods.spec.ts` на подставном API: выключенный способ не в списке, порядок по
  настройке, пустой список даёт подсказку без кнопки; axe, две темы, 1440 и 390.
- Полные наборы: typecheck, lint, unit, integration; UI бара и соседей в один поток.

## 6. Итог (15.10.2026, владелец влил план PR #543: «да»)

Сделано по §2 с двумя отступлениями. (1) Списки форм отдаёт отдельный маршрут `GET /bar/payment-methods`
(`{ sale, supplier }`, право `desk`), а не поля в ответах `/bar/stock` и `/bar/receipts`: те ответы массивы, и поле
в них потребовало бы менять форму ответа у всех читателей. (2) У оплаты поставщику счёт организации остаётся
значением по умолчанию, пока объект его не выключил: так было в форме, менять привычку поставщика незачем.
