## Решения владельца

- Один мастер одновременно выполняет одну услугу. Одна услуга может выполняться разными мастерами одновременно.
- Валюта зависит от региона и выбора при настройке. Ввод сумм в основных единицах выбранной валюты; хранение точно в минимальных единицах.
- Возврат выполняет администратор. Не распространять новое разрешение на гостиницу и ресторан без отдельного решения.
- Мастер видит свой график, предстоящие и выполненные записи, их стоимость, свою зарплату, свой рейтинг и отзывы клиентов о нём.
- Импорт сопоставляет клиентов по имени и телефону. Конфликт имени при совпавшем телефоне требует отчёта, а не незаметной перезаписи.
- Структура меню, группировки, порядок, вкладки и формы соответствуют zapis.kz. Оформление и компоненты соответствуют DESIGN.md WETOP.

## Порядок выполнения

1. Сверить каждый пункт с актуальным кодом. Существующие оплаты/возвраты и кабинет мастера не дублировать.
2. E3, часть A4/H1/N2: корректный валютный ввод ставки, оплаты и возврата. RED/GREEN без базы.
3. E1/E5/E4/F2: единая карточка, независимые состояния занятости и активности, доступ без ручного ID. Собственный кабинет и серверная изоляция.
4. D1/D2/A5: ручной клиент, карточка, импорт с предпросмотром, сопоставлением и отчётом; поиск. Существующий Customer сохраняется.
5. A1/A2/A3/E2: модель строк услуг и цен мастера, совместимость старых записей/онлайн-записи, блокировки от пересечений и гонок, затем интерфейс.
6. M1 и остальные P0: работа филиала, готовность хранилища, валюты и тексты, полный проход записи до оплаты и возврата.
7. P1 по зависимостям: права, реестр/история, финансы, склад/техкарты, зарплата, уведомления и аналитика.
8. P2: группы/ресурсы, лояльность, отзывы, справочники, экспорт и плотность сетки.

## Проверки и доказательства

Для каждого дефекта: воспроизводимый RED, исправление, GREEN через npm run test:record. Unit без базы; integration только на собственном локальном PostgreSQL/порту; UI на собственных портах, один worker. Проверить права в API, чужой бизнес/филиал, повтор запросов и гонки. UI: клавиатура, ошибки формы, 390 и 1440 px, обе темы; визуальное соответствие скриншотам PDF. Сохранить неделю, шесть статусов, сверку кассы, приход по фото и честные состояния отсутствующих данных.

P&L не приравнивать к сумме кассовых операций: переводы, авансы, возвраты и признание доходов требуют отдельных контрольных примеров. Имя и телефон клиента не помещать в URL ради сохранения поиска (действующий Q ТЗ1.1 F03).

## Следующий срез F1/F2: критерии проверки должностей

Утверждённая схема не включает автоматическую выдачу новых прав старым аккаунтам. Сначала отдельные должности, матрица и безопасное назначение внутри существующей области пользователя; затем сквозная серверная проверка и меню.

Проверки перед включением:

1. Название «Администратор» само не даёт возврат. Нужна явная finance.refund BUSINESS. «Мастер» по шаблону его не получает.
2. Изменение тела запроса, вызов API напрямую и переключение филиала не расширяют права. Чужие бизнес/филиал/членство/должность отклоняются.
3. OWN даёт только свои записи, график, зарплату и отзывы. Общий список клиентов, касса и чужая зарплата не выдаются через тот же endpoint.
4. Права проверяются перед выполнением и повторно в транзакции. Отзыв или смена должности между открытием формы и сохранением блокирует команду.
5. Параллельное редактирование матрицы принимает одну revision. Архивация назначенной должности запрещена до переназначения.
6. Существующие ограничения MembershipScope сохраняются. Владельческие, платформенные и другие вертикали не делегируются этой матрицей.
7. Меню, кнопки, прямой URL и API проверяются одной согласованной моделью. Скрытая кнопка не считается защитой.

Ответ владельца 18.10.2026: доступ только по назначениям. После перехода остальные Beauty-бизнесы и филиалы закрыты, включая отзыв последнего назначения без восстановления старой роли.
