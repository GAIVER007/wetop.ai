# SA1.6 — личность агента и перенос существующего продавца

Дата: 30.09.2026. Ветка `claude/charming-heisenberg-ainaqm`. Основание: `DATA_MODEL.md` §20 (v2.8, утверждён владельцем
30.09.2026 с поправками), ADR-127 и его дополнение от 30.09, поручение владельца «SA1.6 — Agent identity + migration».
Порядок владельца: BUG-WA-1 (Q-SA-7) → **SA1.6** → стоп → SA2 только после регрессии и отдельного «да».

## 1. Что входит и что нет

Входит (только фундамент):
- `seller_agents.location_id`, тип и состояния по §20.2–20.3;
- перенос существующего продавца в агента с `id = organization_id` и всей историей (§20.4);
- таблица `agents` в базе бота и `agent_id` в знаниях, диалогах, клиентах, подключении WhatsApp и журнале действий (§20.5);
- проверки принадлежности: агент ↔ организация ↔ Business ↔ Location (§20.10);
- совместимость с сегодняшним Luxx: ключ виджета, адрес вебхука, `phone_number_id`, ответы бота не меняются;
- миграции с `down`, проверка up → down → up, integration-тесты.

Не входит (владелец: «никакого мастера, prompt builder и нового WhatsApp UI»): SA2 и мастер создания, конструктор поведения,
интерфейс WhatsApp, перевод ключа модели на платформу (Q-SA-10 — отдельный срез), `X-Agent` в панельных вызовах платформы
(протокол 20.6 — после SA1.6, когда у агентов появятся отличия от организации), несколько агентов на организацию в интерфейсе.

## 2. Уточнения к §20, которые нужны для безопасной выкладки

1. **`seller_profiles`: первичный ключ на SA1.6 не меняется.** §20.2 говорит «первичный ключ — `agent_id`». Смена ключа при
   выкладке «миграция до кода» сломала бы прежний API (он ищет по `organization_id`). Поэтому SA1.6 добавляет `agent_id`
   (unique, NOT NULL, FK) и оставляет `organization_id` ключом; переключение ключа — в «сужении» (§20.7 п. 6). В §20.2 внесена пометка.
2. **В базе бота `agent_id` сначала NULL-able, с заполнением по умолчанию.** Новые строки получают `agent_id` из
   `organization_id` на уровне ORM (значение по умолчанию модели), старые заполняет миграция. `NOT NULL` — сужением позже (§20.7 п. 6).
3. **Тип агента — существующее `scenario`** (`sales` = AI Seller). Отдельной колонки нет; будущий тип добавляется в CHECK своим ADR.

## 3. PMS: миграция `20260930000034_business_agent_identity`

Расширение, потом перенос, потом ограничения — в одной миграции, с проверками до изменений:

1. **Предпроверки (останов без изменений):** нет строк `seller_agents` с `lifecycle` вне `draft`; нет двух организаций, у которых
   `id` совпал бы с уже существующим `seller_agents.id` (коллизия UUID); у каждой организации с продавцом есть хотя бы владелец
   (нужен `created_by`).
2. `seller_agents.location_id uuid NULL` → FK `locations(id)` ON DELETE RESTRICT; индекс по `location_id`.
3. CHECK `lifecycle IN ('draft','active','paused','archived')` (старый CHECK снимается; значений `preparing/ready/error` в данных нет).
4. CHECK «у `active` и `paused` филиал обязателен».
5. Частичный уникальный индекс: `(location_id) WHERE location_id IS NOT NULL AND scenario='sales' AND lifecycle <> 'archived'`.
6. Триггер `BEFORE INSERT OR UPDATE OF organization_id, location_id`: филиал принадлежит Business той же организации
   (`locations → businesses.organization_id`); иначе исключение. Тот же триггер для `seller_profiles.agent_id`: организация профиля
   равна организации агента.
7. `seller_profiles.agent_id uuid` (unique, FK → `seller_agents(id)` ON DELETE RESTRICT).
8. **Перенос (идемпотентен):** для каждой организации со строкой `seller_profiles` или расширением `AI_SELLER` и без агента с
   `id = organization_id` создаётся агент по правилам §20.4; `seller_profiles.agent_id = organization_id`. Существующие
   `wizard_drafts`/`seller_agents` мастера не трогаются.
9. `NOT NULL` на `seller_profiles.agent_id` — после заполнения, в той же транзакции.
10. RLS: политика на `seller_agents` уже есть (ADR-103); проверить, что перенос идёт под ролью владельца таблиц, а новые колонки
    политику не ослабляют.

`down.sql`: снять триггеры, `seller_profiles.agent_id`, индексы, CHECK-и, `location_id`; удалить созданных переносом агентов
(`id = organization_id`, нет `wizard_drafts`); вернуть прежний CHECK `lifecycle`. Историю бота не касается.

## 4. База бота: миграция `0008_agents`

1. Таблица `agents`: `id` (PK), `organization_id` (FK → `organizations`), `location_id` (справочно), `name`, `public_key` (unique),
   `hosts` (json), `system_prompt`, `active`, `created_at`, `updated_at`.
2. Заполнение из `organizations`: `agents.id = organizations.id`, остальные поля копируются (`public_key`, `hosts`, `system_prompt`,
   `active`). `organizations` и её колонки не удаляются.
3. `agent_id` (NULL-able, FK → `agents`) в `documents`, `clients`, `conversations`, `whatsapp_connections`, `owner_actions`;
   заполняется `= organization_id` там, где организация задана. У экземпляра-помощника строки без организации, `agent_id` у них NULL, поведение не меняется.
4. Уникальность клиента расширяется до `(agent_id, channel, external_id)` **рядом** со старой (старая снимается в «сужении»).
5. `downgrade`: удалить `agent_id` и `agents`; исторические данные остаются.

Код бота: модели получают `agent_id` со значением по умолчанию из `organization_id`; поиск знаний, выбор клиента, диалогов и
подключения WhatsApp работает как раньше (агент = организация); проверка «агент принадлежит организации» —
на входе панельных вызовов при наличии `X-Agent` (нет заголовка — агент с `id = organization_id`).

## 5. Код PMS (минимум)

- `SellerCatalogRepository`: расположение агента берётся из `seller_agents.location_id`, если он задан, иначе прежним правилом (самый
  ранний объект организации) — каталог SA1 и котировка не меняются для Luxx.
- Схема Prisma и `DATA_MODEL`-сверка; тест сверки миграции со схемой.
- Ничего из мастера, интерфейса, протокола `X-Agent` со стороны платформы.

## 6. Проверки (красные до кода, зелёные после)

PMS (integration, чистая PostgreSQL 16):
- предпроверка останавливает миграцию на подделанной строке и ничего не меняет;
- перенос: на базе Luxx-подобных данных агент с `id = organization_id`, `location_id` = филиал самого раннего объекта, `lifecycle`
  по правилу, профиль связан; повторный запуск ничего не дублирует;
- организация без объекта → агент `draft` без филиала; активным без филиала стать нельзя (CHECK);
- второй неархивный продавец на филиале — отказ индекса; архивный не мешает; агент другого типа не считается (когда добавится тип — тест на CHECK-совместимость);
- чужой филиал (другая организация) — отказ триггера, и при `INSERT`, и при `UPDATE`; цепочка Agent ↔ Business ↔ Location;
- `widgetOrgKey` для перенесённого агента совпадает с прежним (ключ виджета не изменился);
- **up → down → up** на данных с историей: после `down` прежний код работает, после второго `up` перенос не дублируется;
- каталог SA1 (`tests/integration/seller-catalog.test.ts`) зелёный без правок ожиданий.

Бот (pytest, без сети):
- миграция `0008` вверх/вниз на данных с диалогами, знаниями, клиентами и подключением WhatsApp; счётчики на агента = прежним на организацию;
- реплика из виджета и вебхук WhatsApp Luxx-подобной организации работают как до миграции (прежние тесты бота зелёные целиком);
- клиент создаётся с `agent_id`; два агента одной организации не смешивают клиентов и диалоги (уникальность по агенту);
- агент чужой организации в `X-Agent` — 403; без заголовка — агент с `id = organization_id`.

Регрессия целиком: typecheck, lint, unit, integration, набор бота, UI-спек `ai-agents` и связанные.

## 7. Выкладка и откат (всё делает владелец, кроме кода)

Порядок — §20.7: копии баз → миграция PMS (до кода) → API и стойка → миграция бота (при старте образа) → образ бота →
проверки до/после (числа диалогов, документов, клиентов; `phone_number_id`; ключ виджета Luxx; активных без филиала — 0) →
«сужение» отдельным решением. Откат: прежние образы, `down.sql` PMS, `downgrade` бота; историю не удаляем.

## 9. Что получилось иначе, чем в плане (30.09.2026, по ходу работы)

1. **`seller_profiles.agent_id` остаётся NULL-able** (не «NOT NULL после заполнения»): прежний код вставляет профиль без агента.
   Триггер при вставке сам заводит агента с `id = organization_id` и связывает; у организации без участников агент не заводится,
   сохранение профиля не падает. `NOT NULL` — в «сужении».
2. **Перенос — функции БД `seller_agent_ensure` и `seller_agents_backfill`** (идемпотентны), а не только разовый SQL: их зовёт
   миграция, тесты и триггер профиля.
3. **Предпроверка миграции PMS** останавливает её, если у организации с продавцом нет ни одного участника (некому быть автором) или
   есть агенты в `preparing/ready/error`.
4. **Редактор мастера (`/seller-agents`) и каталог SA1 не показывают перенесённого агента** (`id = organization_id`): он рабочий
   продавец, а не черновик мастера; правка мимо публикации переписала бы его тип и профиль.
5. **Бот:** `agent_id` NULL-able; `owner_actions` в срез не вошёл (SA8/SA9); зеркало `agents` ведёт слушатель модели, а не
   обработчики; «два агента одной организации не смешивают клиентов» проверить нельзя, пока живёт старая уникальность по
   организации, — этот тест появится в «сужении». Проверка `X-Agent` сделана в `request_org`.
6. **Проверки:** миграция PMS — `check-migrations` OK (36 миграций, схема ↔ `schema.prisma`, откат снимок в снимок) и сценарий
   up → down → up на данных (`reports/business-ai-seller-sa16-2026-09-30/README.md`); миграция бота — SQLite-тестами и на
   настоящей PostgreSQL (up → down → up с данными).
