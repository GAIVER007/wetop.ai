## 1. Что SA2 делает

1. Каталог `/ai-agents`: кнопка «+ Подключить AI-продавца» по состояниям (ниже); карточки черновиков с филиалом показывают
   Business · Location и ведут на страницу агента.
2. `/ai-agents/new` — форма: «Название агента», «Business», «Location» (занятый филиал виден, не выбирается, причина рядом),
   «Создать черновик», «Отмена».
3. `/ai-agents/[id]` — страница агента: название, Business · Location, статус «Черновик», блок «Настройка» со списком:

```
✓ Основное
○ Поведение          — появится в следующих срезах
○ Знания
○ Данные WETOP
○ WhatsApp
○ Тестирование
○ Запуск
```

Пункты после «Основного» — статусы, а не ссылки и не шаги; подпись «Пока недоступно». «Запуск» не активируется.

## 2. Чего SA2 не делает

Не включает агента, не собирает промпт (SA3), не трогает знания (SA4), WhatsApp (SA6), песочницу (SA7), бота, миграции и схему
(всё нужное дала SA1.6). «Весь Business» вместо филиала не предлагается. Языки не входят: профиль с языками лежит в
`seller_profiles`, ключ которого пока организация (закроется в SA2.5/SA3).

## 3. API (server authoritative)

Контекст Business Agent (ADR-126), отдельно от гостевого `/seller-agents`:

| Маршрут | Право | Что делает |
|---|---|---|
| `GET /ai-seller/agents/options` | `dialogs` | Business организации → Location; у каждого `free` и причина занятости. Только чтение. Если у вошедшего выбран scope Business или Location — показывает только его. |
| `POST /ai-seller/agents` | `seller` | Тело `{ name, businessId, locationId }` + заголовок `Idempotency-Key: <uuid>`. Создаёт черновик. |
| `GET /ai-seller/agents/:id` | `dialogs` | Карточка агента с филиалом (для страницы состояния). Рабочий продавец `id = organization_id` сюда не попадает: он открывается в `/ai-seller`. |
| `POST /ai-seller/agents/:id/activate` | `seller` | **Всегда 409** «Запуск агента появится позже», состояние не меняется. Нужен, чтобы запрет активации жил на сервере и был проверяем тестом. |

Сервер сам определяет: организацию и автора — из `RequestActor`; расширение «ИИ-продавец» действует (нет / истекло — 403 словами);
право `seller`; «только чтение» (общий запрет записи в `AuthGuard` до контроллера); филиал принадлежит Business, а Business —
организации; Business и Location действующие; scope вошедшего не шире выбора; на филиале нет другого неархивного AI-продавца
(409). `organizationId` из тела не читается вовсе.

**Идемпотентность.** Общего механизма в API нет (у помощника — память процесса на 15 минут). Используется тот же приём, что у
гостевого мастера (`SellerAgentsService.create`): значение `Idempotency-Key` (UUID) становится идентификатором агента, запись идёт
под advisory-замком на ключ. Повтор тем же человеком и той же организацией возвращает того же агента и не пишет второй
`agent.created`; тот же ключ у другой организации — 404 как несуществующий. Ключ без UUID — 400. Это переживает рестарт и
несколько экземпляров API, в отличие от памяти процесса.

Журнал: `audit_logs`, `entity_type = 'seller-agent'`, `agent.created`: Business, Location, `lifecycle: draft`; название не пишется.
Гонка двух создателей на один филиал решается частичным уникальным индексом SA1.6; проигравший получает тот же 409.

Домен: `parseAgentInput` (название 1–80 знаков, без переводов строк и служебных слов; идентификаторы — UUID) и
`AGENT_SETUP_ITEMS` (список настройки, единый для сервера и страницы) в `packages/domain/src/ai-agents/`.

## 4. Кнопка «+ Подключить AI-продавца»: состояния

| Состояние | Кнопка | Причина словом |
|---|---|---|
| Расширение не подключено или истекло | неактивна | «Расширение «ИИ-продавец» не подключено» / «Срок расширения вышел» |
| Нет права `seller` или режим «только чтение» | неактивна | «Создавать агентов могут владелец и управляющий» / общая фраза «только чтения» |
| Нет свободного филиала | неактивна | «Нет свободного филиала. Для этого филиала AI-продавец уже создан.» (для нескольких — «Во всех филиалах…») |
| Есть свободный филиал | активна, ведёт в `/ai-agents/new` | — |

Свободный филиал определяет сервер (`options`), интерфейс не считает сам.

## 5. Проверки

- домен: `parseAgentInput`, список настройки;
- API (фейки): без расширения / истёкшее — 403; роль без `seller` — 403; чужой Business, чужой Location, Location не этого Business,
  архивный — 404; занятый — 409; повтор с тем же ключом — тот же агент без второго журнала; ключ чужой организации — 404; ключ не UUID —
  400; `organizationId` в теле игнорируется; `activate` — 409 и состояние не меняется; таблица прав `route-access`; «только чтение» —
  `writeBlocked` для `POST /ai-seller/agents`;
- integration (PostgreSQL): два одновременных создания на один филиал — один агент, второй 409; повтор по ключу — один агент и один
  `agent.created`; агент организации А не виден организации Б; архивный агент освобождает филиал; scope Location не даёт создать на
  чужом филиале;
- UI: форма и ошибки словами; занятый филиал; страница агента; каталог с новой карточкой; кнопка по четырём состояниям; роли (сотрудник
  смены без кнопки), режим «только чтение», desktop и 390, light и dark, axe.

Снимки — `reports/business-ai-seller-sa2-2026-09-30/`. Полные наборы (typecheck, lint, unit, integration, связанные UI) и стоп.

## 6. SA2.5 — «runtime → Agent scope» (следующий, обязательный; отдельный план)

Цель: перестать определять продавца через организацию. Входящий запрос → `agent_id` → организация, Business, Location → профиль,
знания, диалоги, каналы, инструменты. Проверить agent-scoped: профиль, виджет, WhatsApp-маршрут, знания, диалог, клиент, подключение
канала, PMS-scope (`agent.location`). Легаси-агент Luxx сохраняет `id = organization_id`, ключи виджета и вебхука не меняются.
**`seller_profiles` становится agent-scoped до SA3** (ключ — `agent_id`, «сужение» §20.7 п. 6). Отдельным планом и с его «да».
