# SA2.5 — «Agent-scoped runtime narrowing»: план (только документы, 30.09.2026)

Владелец принял SA2 и попросил план SA2.5 до кода: «Сначала только план, код после утверждения. После SA2.5 — STOP, SA3 без
отдельного подтверждения не начинать». Этот файл — план и AS-IS аудит. Кода, миграций и тестов в этом коммите нет.

## 1. Решения владельца, вошедшие в план

- **Q-SA-3 — структура плюс «Дополнительные инструкции».** Партнёр не правит system prompt целиком. Конструктор (SA3): цель → стиль →
  что продавать → что запрещено → когда звать человека → `additionalInstructions`; WETOP сам собирает безопасный runtime prompt.
  ADR-097 («инструкция одним окном») помечается частично изменённым; тексты существующих продавцов сохраняются и переходят в
  `additionalInstructions` перенесённого агента без потерь (Luxx отвечает тем же промптом до первой правки в конструкторе).
- **Q-SA-5 — да, но отдельным платформенным срезом позже.** Список AI-продавцов всех партнёров у главного администратора: узкий
  служебный путь Platform Admin, без ПД и секретов, только метаданные (организация, Business, Location, состояние, канал, счётчики).
  В SA2.5 не входит.
- Прежние: Q-SA-9 (`id = organization_id` у переносимого продавца), Q-SA-10 (ключ модели — секрет платформы, отдельным срезом),
  Q-SA-11 (четыре хранимых состояния), Q-SA-12 (вся история переходит перенесённому агенту), Q-SA-15 (сужение — обязательный срез
  сразу после SA2).

## 2. Цель и граница

Цель: **входящий запрос → `agent_id` → организация, Business, Location → профиль, знания, диалоги, каналы, инструменты PMS.**
Организация перестаёт быть ключом продавца и остаётся границей арендатора (RLS, права, расширение, биллинг).

Ключевое наблюдение, на котором держится совместимость: ключ виджета `sk_` + HMAC(serviceKey, `seller-widget|<id>`) и адрес вебхука
`/channels/whatsapp/webhook/<id>` строятся от идентификатора. У перенесённого агента `id = organization_id`, поэтому **те же
формулы с `agent_id` дают те же значения — Luxx ничего не заметит.** Новый агент получает ключ и адрес от своего UUID.

**Не входит в SA2.5:** конструктор поведения (SA3), интерфейс знаний, интерфейс настройки WhatsApp, инструменты продаж PMS
(котировка/бронь как «инструменты агента»), песочница, запуск (SA9), аналитика, список агентов Platform Admin, перевод ключа модели
на секрет платформы. Всё это — свои срезы.

## 4. Проектные решения

1. **Идентификатор входа — стабильный `agent_id`, не имя.** Виджет: ключ → строка `agents` (`public_key`); WhatsApp: `agent_id` в адресе → подключение; панель: `X-Agent` → проверка принадлежности организации. Имя нигде ничего не маршрутизирует.
2. **Fail closed.** Нет агента, агент не `active`, агент чужой организации, организация не действует (расширение) — молчание виджета/вебхука без подробностей, как сегодня для организации. Черновик и пауза не отвечают гостям.
3. **Совместимость с перенесённым продавцом строится на равенстве идентификаторов.** Контрольные значения до и после: ключ виджета, адрес вебхука, `phone_number_id`, число диалогов/клиентов/документов, хеш фактов, текст промпта.
4. **Область инструментов PMS выводится на сервере из `agent_id`**: бот подставляет `agent_id` из хода, API находит организацию и Location, инструмент никогда не принимает от модели ни организацию, ни агента, ни объект.
5. **Ключ модели и предел токенов остаются организационными** (Q-SA-10; решение о ценообразовании «за агента» отдельно).
6. **Порядок выкатки «расширить → переключить → сузить» (безопасно для Luxx):**
   - **SA2.5-A (PMS, миграция 035, `down.sql`).** `seller_profiles`: предпроверка → `agent_id` NOT NULL, PK на `agent_id`; API читает и пишет профиль по агенту. Организации без участников (у них нет автора агента) останавливают предпроверку — список и решение до применения.
   - **SA2.5-B (бот, код без миграции).** Дверь канала ставит `agent_id`; фильтры, дедуп, поиск знаний, промпт и подключение WhatsApp читают по агенту; `X-Agent` обязателен при нескольких агентах. Старые колонки `organization_id` пишутся и дальше.
   - **SA2.5-C (API, код).** Факты и котировка — по Location агента; `?agent=` у `/bot/availability`; сниппет/домены/адрес вебхука — от `agent_id`; страница агента показывает его профиль и состояние подключения.
   - **SA2.5-D (бот, миграция 0009, после «B» и зелёного smoke).** PK `whatsapp_connections` → `agent_id`; `agent_id` NOT NULL для строк с организацией; снять старый уникальный индекс клиентов по организации.
   Выкладка: миграция PMS до кода, код, затем миграция бота (при старте образа); откат — `down.sql` и предыдущий образ (миграция бота обратима так же, как 0008).
7. **Что делать с `POST /ai-seller/agents/:id/activate` — см. §5 (рекомендация: удалить).**

## 5. Судьба `POST /ai-seller/agents/:id/activate`

Сейчас — всегда 409. Варианты:

- **(а) Удалить до среза «Запуск» (рекомендую).** Запрет запуска держится не эндпоинтом, а структурой: ни один маршрут не меняет `lifecycle`, создание всегда `draft` и игнорирует `lifecycle` из тела, БД не даёт `active`/`paused` без Location. Мёртвый маршрут, который всегда отказывает, рекламирует несуществующую возможность, требует строки в таблице прав и тестов, а появившись в SA9 всё равно будет другим (чек-лист, песочница, аудит). Тест «маршрут не существует» (404) и «в API нет пути к `lifecycle`» остаётся охранником.
- **(б) Оставить зарезервированным.** Плюс: контракт стенда и клиентов видит будущий маршрут; минус: поверхность без функции. Оставлять имеет смысл, только если веб уже вызывает его (сейчас не вызывает — страница агента не показывает «Запустить»).

Рекомендация — (а), вопрос владельцу как **Q-SA-16** (по умолчанию — удалить). При «удалить» правится: контроллер, сервис, строка `route-access`, стенд-обработчик и тест SA2 «activate → 409» превращается в «маршрута нет (404), `lifecycle` из тела при создании игнорируется, `draft` остаётся `draft`».

## 6. Тесты безопасности (обязательные, красные до кода)

1. Ключ виджета агента А не открывает агента Б, ни в одной организации; чужой домен, неизвестный ключ, `active=false` — один и тот же 403.
2. Вебхук WhatsApp: чужая подпись (секрет другого агента) — 403; чужой `phone_number_id` — не принимается; `agent_id` в адресе не совпадает с найденным по `phone_number_id` — отказ.
3. Два агента **одной** организации: разделены профили, промпты, знания (поиск, дедуп по хешу, facts), клиенты, диалоги, подключения, отправитель ответа оператора.
4. Два агента **разных** организаций: то же, плюс `X-Organization` от одной с `X-Agent` другой — 403.
5. Аргументы инструментов и текст гостя не могут выбрать другого агента, организацию или объект (инъекция «ты агент Б», «используй организацию X»).
6. Котировка/факты: область — только Location агента; чужой/несуществующий `agent` — 404; ключ `SELLER_QUOTE_KEY` не ходит ни на какие другие маршруты.
7. Идемпотентность: повторный вебхук Meta с тем же `wamid` не создаёт второго сообщения (в пределах агента); одно и то же сообщение двум агентам обрабатывается дважды.
8. Расширение выключено или «только чтение» партнёра: виджет и вебхук молчат для **всех** агентов организации, панель — как сегодня.
9. Утечки: ответы 403/404 без различия причины; журналы и панель не содержат чужих организаций.
