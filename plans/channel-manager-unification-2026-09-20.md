# Менеджер каналов: единый отчёт и синхронизация

Запрос владельца 20.09.2026: статистика по каждому каналу Channex — брони,
отказы, отмены, стоимость броней и оплаты; убрать дублирующие блоки.

|---|---|---|

В браузере открыты `/channel-manager` и переход к `/channels`: отчёт отобразился
с пустым выбранным периодом, статус webhook — «активен, события booking», блок
ошибки загрузки очереди отсутствовал. Это проверка отображения локального
экземпляра, не доказательство полноты поступления броней из всех OTA или выплат.
Ни одна кнопка отправки ARI, повтора события или изменения подключения не нажималась.

## Источники Channex

Документация проекта: `docs/channex/site/api-v.1-documentation/bookings-collection.md`.
Ревизии описаны как `new`, `modified`, `cancelled`; ревизия и коммерческая бронь —
разные сущности. `amount` — стоимость брони; `payment_collect` — кто собирает
оплату, `payment_type` — способ. Эти поля не являются универсальным реестром
перечислений гостинице. Комиссия описана не для всех OTA; не выводить её как
полное покрытие всех каналов без отдельной проверки источников.

В проекте нет универсального события «отказ». Значение запрошенной колонки
запрошено у владельца в Q-154; до ответа не заменять её незаездами или ошибками.

## Предлагаемый интерфейс

Один пункт бокового меню **Менеджер каналов**, две вкладки:

- **Статистика** — одна панель периода и статуса, компактная общая сводка,
  основная таблица по каналам. Отдельный повторный блок стоимости убрать.
- **Синхронизация** — существующие подключения/сопоставления, состояние обмена,
  очередь и события. Сохранить диагностику, страницы деталей и действия, но убрать
  повторный пункт «Синхронизация каналов» из главного меню.

Таблица: канал, брони, отмены, незаезды, стоимость выбранных броней,
оплачено по счетам, возвращено. «Отказы» добавляются после определения Q-154.
Строка канала может содержать раздельные строки валют: USD и KZT не складывать
и не конвертировать по придуманному курсу. Вместо повторных графиков — сортировка
и поиск по каналам; подробности открываются из строки по точному фильтру.

Текущая база периода сохраняется: **по дате заезда**. Подпись оплаты:
«Оплачено по счетам выбранных броней». Это все учтённые оплаты этих броней,
а не кассовые поступления за календарный период. Данные из Channex поступают
через существующий журнал событий в PMS; отчёт читает сохранённые данные,
а не загружает историю OTA заново при каждом открытии.

## Расчёты на существующей модели

1. Считать шапки Reservation один раз независимо от числа проживаний, счетов,
   распределений платежа и ревизий Channex. Текущую семантику стоимости сохранить
   и подписать включение отмен/незаездов при фильтре «Все».
2. Приводить известные алиасы каналов к утверждённым ключам ADR-024. Не склеивать
   неизвестные названия по пустому ключу. Канал продажи и провайдер получения
   брони различаются: одна бронь после сопоставления архивный источник/Channex не становится двумя.
3. Оплату брать из PaymentAllocation → Folio → ReservationItem → Reservation,
   только по Payment.status=COMPLETED. Один общий платёж разделён на счета;
   полную Payment.amount нельзя повторять для каждой распределённой части.
4. Возвраты агрегировать по счёту в отдельном запросе/подзапросе, исключая
   размножение сумм через JOIN с несколькими платежами и проживаниями.
5. Все суммы integer minor units / bigint, наружу строки. Валюта сохраняется
   на каждом шаге. Долг не вычислять как стоимость брони минус оплата: баланс
   в проекте определяется начислениями и возвратами по счетам.
6. EXTERNAL-предоплата Channex входит в уже учтённую оплату счёта, но отмечается
   как «Собрано площадкой». Не называть сумму таких платежей «Перечислено отелю».
7. Ошибка загрузки отличается от достоверного нуля. Наличие прошлых броней канала
   не доказывает, что он сейчас подключён. Статус подключения читается независимо.

## Выполнение и приёмка

- После снятия блокировки §17 — ветка, ADR для проекции и навигации, RED/GREEN
  для агрегации оплат, валют, алиасов и отсутствия задвоения. Изменение API
  согласованно на сервере и фронте; таблицы БД и финансовые правила не менять.
- Проверить несколько проживаний в одной брони, платёж на несколько счетов,
  частичную оплату, возврат, VOIDED-платёж, отмену с удержанием, незаезд,
  неизвестный канал, две валюты, повторную ревизию, пустой период и отказ API.
- Детализация должна реально фильтровать те же брони и тот же период. Текущий
  каталог броней не имеет точного фильтра канала и использует пересечение дат
  проживания; не делать ссылку, которая обещает точную детализацию без реализации.
- Проверить URL-фильтры, reload/back, вкладки, мобильный экран, клавиатуру,
  обе темы, загрузку и повторную попытку. Сверить сводку с суммой строк.
- Read-only сверку базы запускать только при свободном дереве/БД; использовать
  агрегаты без персональных данных. Тестовые записи — только синтетические.
- Typecheck, lint, build, релевантные API/UI-тесты, обзор diff, push/PR.
  Deploy подтверждать отдельно через SHA, health и рабочий адрес.
