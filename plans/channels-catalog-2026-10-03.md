## 2. Откуда что берётся (документация — `docs/channex/site/api-v.1-documentation/channel-api.md`, `channel-iframe.md`)

| Колонка / вкладка на снимке | Источник у нас |
|---|---|
| «Все доступные каналы» | `GET /channels/list` — каталог адаптеров Channex: `code`, `title`, `kind` (`ota`/`meta`/`cm`), `params` (поля формы), `mapping_mode`, `actions`, `property_mapping` |
| «Подключённые N» | `GET /channels?filter[property_id]=<объект в Channex>` — соединения объекта (постранично по 100) |
| Канал (имя, логотип) | `channel` соединения (код адаптера) → `title` из каталога; логотипов Channex по API не отдаёт — свои значки на известные коды, иначе буква |
| ID в канале | `settings` соединения: поле из `params` адаптера, означающее ID объекта на стороне OTA (у Booking.com `hotel_id`); какое поле — из дескриптора адаптера, не угадываем |
| Название подключения | `title` соединения (Channex генерирует сам, если не задали) |
| Брони за 30 дней | наша база: брони с `source = OTA` и ключом канала = коду адаптера (`BDC` → `bookingcom`), созданные за 30 дней по часам объекта, без отменённых — правило Q-254 |
| Статус | `is_active`, `expected_removal_date`; готовность — `POST /channels/{id}/check_readiness` (только в карточке, не в списке) — см. §4 |
| «2 новых» | разница каталога с прошлым снимком — см. §5, этап 3 |

## 3. Где раздел живёт

Предлагается **вкладка «Каналы» первой в модуле «Каналы продаж»** и открываться по умолчанию:
`/channels` → «Каналы» (две подвкладки «Подключённые N» и «Все доступные»), дальше Сопоставление,
Синхронизация, События. Нынешний «Обзор» (полоса здоровья Channex, отчёт по источникам) уходит вниз той же
страницы: полоса «Связь с Channex · очередь · ошибки · приём событий» остаётся над таблицей, отчёт по
источникам — отдельной вкладкой «Отчёт». Вкладка «Подключения» (настройка самого Channex: объект, webhook) —
это Q-220, переименовать в «Настройка Channex» или перенести в «Интеграции». Вопрос — **Q-252**.

Новых пунктов меню нет; адреса `/channels/*` и `data-testid` сертификации Channex сохраняются (ADR-112).

## 4. Статусы — честно (ADR-112, дополнение)

PMS не видит, принимает ли Booking.com наши цены: Channex отдаёт только `is_active`. Поэтому слова:

| Состояние | Когда | Тон |
|---|---|---|
| **Включён** | `is_active = true` | нейтральный |
| **Не готов** | `is_active = false`, проверка готовности вернула проблемы (нет сопоставления тарифа…) | warning, причина словами |
| **Выключен** | `is_active = false`, без даты удаления | нейтральный |
| **Удаляется DD.MM** | есть `expected_removal_date` (Channex удалит через 30 дней после выключения) | warning |
| **Нет связи с Channex** | список не загрузился — показываем последний снимок с «на DD.MM HH:MM» | critical на полосе |

Подсказка у «Включён»: «последняя бронь DD.MM» (из нашей базы) и число ошибок входящих по каналу за сутки.
Слово «Работает», как на снимке, — только если владелец примет правило «Включён + бронь или успешное событие
за N дней + нет ошибок» (**Q-253**); до ответа — «Включён».

## 5. Как подключать — две дороги

**А. Окно Channex внутри WETOP (Channel IFrame).** Сервер берёт одноразовый токен
`POST /auth/one_time_token {property_id, username}` (живёт 15 мин, одноразовый), стойка открывает панель с
`…/auth/exchange?oauth_session_key=…&app_mode=headless&redirect_to=/channels&property_id=…&lng=ru`. Всё
подключение — форма канала, проверка, сопоставление комнат и тарифов, Airbnb-OAuth — делает Channex, и для
каждого из ~60 каналов это уже отлажено. Можно ограничить список (`available_channels=BDC,AGO,…`). После
закрытия окна WETOP перечитывает `GET /channels`. Минусы: интерфейс Channex, режима «только чтение» нет
(давать только праву `channels`), токен даёт права пользователя ключа.

**Б. Свой мастер по Channel API.** Каталог → форма по `params` → `test_connection` → `mapping_details` →
сопоставление тарифов по `rate_params` → `POST /channels` (создаётся выключенным) → `check_readiness` →
`activate`. Полностью наш вид, но у каждого канала свои шаги (документация: «всегда читать гайд конкретного
канала»), это недели работы и отдельный разбор на каждый канал.

**Рекомендация: А для подключения и правки, наш список — по API.** Таблица, статусы, брони, поиск, «Все
доступные» — наши (как на снимке); кнопка «Подключить» у канала и «Настроить» в меню строки открывают окно
Channex сразу на этом канале. Свой мастер — позже и только для 2–3 главных каналов, если владелец захочет.
Решение — **Q-255**.

**Включение канала (`activate`) — момент переезда реального OTA** (CUTOVER.md, CLAUDE.md §3, Q-232):
кнопка «Включить» только у владельца, с вопросом «Booking.com начнёт получать цены и остатки WETOP и
присылать брони. Включить?», журнал `channel.connection.activated`. На staging — свободно, на production —
только после одобрения Channex.

## 6. Действия в меню строки (≡)

| Действие | Вызов | Кто |
|---|---|---|
| Брони этого канала | ссылка `/reservations?channel=<ключ>` | все с `reservations` |
| Настроить (сопоставление, ID) | окно Channex на соединении | право `channels` |
| Проверить готовность | `POST /channels/{id}/check_readiness` → проблемы словами | право `channels` |
| Включить / Выключить | `activate` / `deactivate` + подтверждение, журнал | владелец |
| Подтянуть будущие брони | `POST /channels/{id}/execute/load_future_reservations` — только если действие есть в `actions` адаптера | владелец, один раз, с подтверждением |
| Удалить | **не даём**: необратимо, стирает сопоставления (документация) — только в окне Channex | — |

## 7. Чтобы «подтягивалось» само

- **Снимок подключений у нас**: новая таблица `channel_connections` (объект, провайдер, id соединения
  Channex, код адаптера, название, ID в канале, `is_active`, `expected_removal_date`, число сопоставленных
  тарифов, `synced_at`). Зачем: список виден, когда Channex недоступен; брони и события привязываются к
  соединению; журнал «кто включил». **Это изменение модели — сначала `DATA_MODEL.md`, решение владельца (Q-256).**
  Без таблицы — читать Channex на каждом открытии с кэшем 1–5 мин (этап 1 можно и так).
- **Обновление**: при открытии вкладки (старше 5 минут — перечитать), после закрытия окна Channex, раз в
  сутки фоном вместе с ночной полной выгрузкой. Webhook на изменения соединений в документации нет.
- **Каталог адаптеров**: раз в сутки `GET /channels/list` в кэш; «N новых» — коды, которых не было в прошлом
  снимке (нужно хранить список виденных кодов — та же Q-256), плашка «Channex добавил каналы: …».
- **Новый канал в броне без соединения** (пришла бронь с кодом, которого нет среди подключённых) — строка
  «Брони идут, подключения в списке нет» вместо молчания.
- **Каналы вне Channex** (Bronevik, OneTwoTrip — их в каталоге Channex нет, Q-096; сайт, стойка) — отдельный
  блок «Источники вне Channex» под таблицей: только брони за 30 дней, без статуса и действий.
- **Мультиаренда**: всё строго по объекту текущего scope (`providerPropertyId` из `channel_mappings`); у
  объекта без Channex — пустое состояние «Сначала подключите Channex» со ссылкой на «Интеграции → Channex».
- **Ошибки**: 503 Channex — повтор, на экране последний снимок; `success:false`/422 — причина словами у
  действия; 401/403 — «ключ Channex не даёт доступа к каналам» (проверить, открыт ли нашему ключу Channel API
  и `one_time_token` — **за владельцем, вместе с Q-232**).

## 9. Этапы (каждый — red → green, снимки, стоп на визуальное «да»)

1. **CH-L1 «Подключённые» только на чтение.** Клиент: `listChannels(propertyId)`, `listAdapters()` (по
   документации, тесты на разбор ответа); API `GET /channels/connections` (право `channels`): соединения +
   названия из каталога + брони за 30 дней из базы; вкладка с таблицей как на снимке, поиск, честные статусы,
   «Источники вне Channex», ссылка «Брони этого канала». Модель не меняется.
2. **CH-L2 «Все доступные».** Каталог плитками/таблицей: имя, тип (OTA / метапоиск), «Подключён» или
   «Подключить»; поиск; фильтр «только OTA».
3. **CH-L3 Подключение окном Channex** (после Q-255 = А): `POST /channels/connect-session` → одноразовый
   токен, панель с окном, перечитывание после закрытия; проверка на staging с тестовым Booking.com.
4. **CH-L4 Действия**: готовность, включить/выключить, подтянуть будущие брони — с подтверждением и журналом.
5. **CH-L5 Снимок и «новые каналы»** (после Q-256): миграция `channel_connections`, фоновое обновление,
   плашка новых адаптеров, связь броней с соединением.

Production (настоящий Booking.com Luxx) — только после одобрения Channex и решения по Q-232, по CUTOVER.md.
