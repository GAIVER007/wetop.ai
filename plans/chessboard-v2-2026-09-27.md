## А. Аудит текущего (ТЗ §67)

### Чтение

| Endpoint | Где | Что отдаёт |
|---|---|---|
| `GET /chessboard?from&to` | `apps/api/src/chessboard/` | Вся сетка одним батчем (≤ 62 дней; по умолчанию сегодня + 14): строки-места с `housekeepingStatus`; клетки FREE/OCCUPIED/BLOCKED; у занятой — `itemId`, `itemStatus`, `confirmationNumber`, `guestLabel`, `guestPhone`, `source`, `channel`, `balanceMinor`, `isArrival`/`isLastNight`; свод по датам (свободно/занято), свободно по категориям на каждую ночь; список броней без ячейки |
| `GET /availability?arrival&departure` | там же | Свободные места по категориям на проживание, с ограничением остатка канала (Q-107) |
| `GET /reservations/:number` | там же | Полная карточка брони |
| `GET /reservations/:number/items/:itemId/preview` (`action=move\|extend\|cancel\|no_show`), `…/move-preview`, `…/extend-preview`, `…/cancel-preview` | `apps/api/src/reservations/` | Сумма действия до подтверждения (срез 7.3, Д5) — теми же функциями, что сама команда |
| `GET /rate-plans` | там же | Активные тарифы для формы брони |

### Команды

`apps/api/src/reservations/`: `POST /reservations`; `PATCH :number/dates`; `PATCH :number`;
`PATCH :number/items/:itemId`; `POST …/cancel`, `…/check-in`, `…/check-out` (`withDebt`),
`…/no-show`, `…/extend` (`nights`, `ratePlanCode`), `…/assign` (`unitCode`, `fromDate`).
`apps/api/src/units/`: `POST :code/blocks`, `DELETE :code/blocks/:blockId`, `POST :code/housekeeping`.
`apps/api/src/finance/`: платежи, начисления, возвраты.

Всё уже command-oriented и транзакционно, аудит пишется внутри команд — §48 и §70 ТЗ
выполняются текущей архитектурой, фронт ничего не пишет мимо. DB-guard от пересечений
Allocation существует (§50). Типы блокировок в схеме — `MAINTENANCE`, `MANAGEMENT`,
`OUT_OF_ORDER`, `OTHER` — совпадают с §33 дословно.

### UI сейчас (`apps/web/src/app/chessboard/`)

`page.tsx` (server) + `board-grid.tsx` (client) + `board.css`. Уже есть: неделя / 14 дней /
месяц и произвольный период; «Сегодня»; поиск по месту, гостю, брони, категории; фильтры
(категория, номера/койки, статус на первую дату, уборка со счётчиком); сворачивание
категорий; прилипшие шапка дат и колонка мест; выделение сегодня и выходных; DnD-переселение
с предпросмотром суммы и подтверждением; продление правым краем (`StayResize`) и из меню;
меню действий на плашке (карточка, продлить, переселить, отменить); клик по пустой клетке →
форма брони с датой и местом; блокировки; значок и меню уборки; блок «Без ячейки» с
`ResolveMenu`; легенда; помощь; плашки овербукинга и неразобранных ревизий Channex.

То есть скелет v2 в основном стоит; ТЗ — про плотность, иерархию, quick preview, drawer
и качество состояний, а не про новую механику.

## Б. Развилки и ограничения

1. **§17 упирается в Q-095** (список PhysicalRoom отложен, импорт 1:1). Группируем по тому,
   что в базе; после закрытия Q-095 вид улучшится без правок кода. Новых вопросов не заводим.
2. **§30 сокращение** — только существующими командами и предпросмотрами; правил не
   придумываем (AGENTS.md §4). Чего команда не разрешает — того нет и в UI.
3. **§15, §38, §52 предпочтения** (плотность, свёрнутые категории, вид) — localStorage.
   В модель данных не лезем; кросс-устройство — отдельное решение владельца, если понадобится.
4. **§47 права** — роли v1.9 §16 утверждены; в UI проверять способности (`can*`), не имя роли.
5. **§7 «Месяц»** уходит из сегмента в «Даты» (rolling 7/14/30). Тесты
   `tests/ui/chessboard-month.spec.ts` переориентируются на путь через «Даты», не удаляются.
6. **Новые компоненты** (drawer, floating card, переключатель плотности) — сначала строка в
   DESIGN.md §8 и показ на `/design-system` (ADR-048). Цвета — только токены (§20, §55).
7. **§45 mobile fallback** в восьми PR ТЗ §72 не значится — предлагаю отдельным PR 9 после
   PR 8, по слову владельца.
8. **§28 «быстрое переселение» без подтверждения** — не делаем: любое переселение может
   менять деньги или категорию, подтверждение с суммой остаётся всегда (это и сейчас так).
9. **§49 optimistic UI** — только там, где откат тривиален; сервер остаётся источником
   правды, DB-guard не обходим.

**PR 4 — DnD/resize UX (§26–30), команды прежние.** Что входит и что нет:

- §26: во время перетаскивания каждая строка помечена — можно бросить или нет; над строкой призрак
  брони, над закрытой — причина («Занято с …», «Недоступно с …: ремонт»); закрытая строка drop не
  принимает. Проверка — по клеткам уже загруженной сетки, без запросов на строку (§69); сервер
  проверяет ещё раз (§50).
- Правило домена, которое сетка теперь учитывает заранее: в другую категорию переезжает только всё
  проживание (`assign`: «Переселение в другую категорию возможно только на всё проживание»). Поэтому
  при броске в другую категорию переселение идёт с первой ночи плашки, а не с взятой клетки; если
  заезд раньше окна, строка другой категории закрыта (весь срок на экране не проверить).
- §27: окно подтверждения — гость, «R05 → R07», даты отрезком и ночи, «Стоимость не изменится» или
  «Разница стоимости: +15 000 ₸»; заголовок с номером брони (DESIGN.md §14). Суммы — тот же
  предпросмотр API.
- §29: при продлении за край — «До 27 сент., +3 ночи, +75 000 ₸» до отпускания (сумма — предпросмотр
  продления API на выбранное число ночей); поверх чужой брони или блокировки — конфликт виден до
  отпускания, команда не уходит.
- §49 в облегчённом виде: после подтверждения призрак стоит на новом месте с «Сохраняем…», при отказе
  исчезает; данные сетки не подменяются — источник правды сервер.
- §54: ошибки словами — «Не удалось переселить: …», «Не удалось продлить проживание: …».
- **Не входит:** §28 мгновенное переселение без вопроса — по Б-8; §30 сокращение — gap: команда
  смены дат (`PATCH :number/dates`) меняет даты всей брони, не работает для заселённых и
  переселённых проживаний и не имеет предпросмотра суммы, а §30 требует показать изменение стоимости
  до commit. Нужен предпросмотр смены дат в API — решение владельца.
