# Сервер «ложится» на время выкладки: план

03.10.2026, сессия «Раздел отчёты». Поручение владельца «давай» на предложение подготовить план после сбоя.

## 1. Что случилось

03.10.2026 около 11:58–12:02 UTC, сразу после перемотки `release` на `c861e1ea`, `app.wetop.ai`,
`api.wetop.ai` и `assistant.wetop.ai` 4–7 минут отвечали 530: Cloudflare не доставал до сервера.
Главная `wetop.ai` (Cloudflare Pages) работала. Сам сервер был жив: пинг шёл, порт SSH открывался, но SSH
не успевал поздороваться (`Connection timed out during banner exchange`), то есть машина была перегружена.
В 12:02 всё вернулось само, в 12:05 поднялась новая сборка; отката не было.

## 2. Почему (гипотеза, подтвердить шагом 3)

`scripts/ops/auto-deploy.sh` выкладывает командой `docker compose up -d --build api web`: образ собирается
прямо на рабочем сервере (`npm ci` и `next build`). Сервер один на всё, 8 ГБ памяти:

| Кто | Сколько может взять |
|---|---|
| CI-раннер `pms-lux-ci` (lint, typecheck, unit, три части UI с `next dev`) | до 3 ГБ, 1,5 ядра (`mem_limit`) |
| сборка образа `pms-lux` (`npm ci`, `next build`) | без предела |
| api, web, cloudflared | без предела |
| бот: app, Postgres, Redis | без предела |
| сторож, чужие `vilkabot2` и `traefik` | без предела |

За несколько минут до перемотки `release` в `main` ушёл коммит, и раннер начал проверки. Сборка образа
пришлась на их середину. Две тяжёлые сборки Node сразу съедают память, ядро уходит в подкачку или убивает
процессы, туннель `cloudflared` перестаёт отвечать Cloudflare. Этого я не видел своими глазами: SSH-ключа у
сессии нет. Признаки (сбой всех трёх поддоменов разом, включая бот, которого выкладка не касалась; таймаут
приветствия SSH; самовосстановление после конца сборки) указывают на нехватку памяти, а не на код.

## 3. Диагностика (владелец, только чтение, 2 минуты)

```bash
free -m; swapon --show
journalctl -k --since "2026-10-03 11:50" --until "2026-10-03 12:10" | grep -iE "oom|killed process"
grep -n "c861e1ea" /var/log/wetop-deploy.log | head
docker logs --since 2026-10-03T11:50:00 --until 2026-10-03T12:10:00 pms-lux-cloudflared-1 2>&1 | tail -20
```

Что ищем: была ли подкачка вообще (`swapon` пусто — её нет), убивал ли ядро процессы (строки `Killed
process` с именами), во сколько скрипт начал и закончил сборку. Имя контейнера туннеля сверить по `docker ps`.

## 4. Меры, от самой простой

**А. Выкладка ждёт, пока раннер свободен** (код, `scripts/ops/auto-deploy.sh`, ~10 строк). Перед сборкой
скрипт смотрит, выполняет ли раннер задачу: процесс `Runner.Worker` живёт внутри контейнера только во время
задачи (`docker exec <раннер> pgrep -f Runner.Worker`). Занят — скрипт выходит молча, cron повторит через две
минуты, как сейчас при той же вершине. Ничьих проверок не убивает. Ограничение: если проверки идут непрерывно,
выкладка ждёт; потолок, после которого скрипт выкладывает всё равно и пишет об этом в Telegram, например 30
минут. Тест: `tests/unit/auto-deploy.test.ts`, red на «раннер занят — не выкладывает» → green.

**Б. Подкачка на сервере** (владелец, системная настройка, без кода). Если `swapon --show` пуст: файл подкачки
на 4 ГБ (`fallocate -l 4G /swapfile`, `mkswap`, `swapon`, строка в `/etc/fstab`). Пик сборки тогда уйдёт
в подкачку: медленнее, но без падения. Изменение системы, поэтому только руками владельца.

**В. Боевые службы последними под удар** (код, `deploy/compose.yml`). `oom_score_adj: -500` у `api`, `web` и
`cloudflared`: если памяти всё же не хватит, ядро убьёт сначала сборку или проверки, а не туннель и стойку.
Плюс `NODE_OPTIONS=--max-old-space-size=1536` на шаге `next build` в `deploy/Dockerfile`, чтобы сборка не
раздувала кучу без предела. Тест: `tests/unit/deploy-server.test.ts` сверяет обе строки.

**Г. Не собирать на рабочем сервере** (крупно, отдельным решением). Образ собирается заранее (на Mac или на
GitHub, когда вернутся минуты Actions) и уходит в реестр образов (GHCR), сервер делает только `pull` и
перезапуск. Нужны токен реестра на сервере и решение владельца; своего Docker у раннера нет намеренно
(`scripts/ops/ci-runner/README.md`), поэтому собрать на нём нельзя. Делать, только если А–В не хватит.

## 5а. Второй сбой и наведение порядка 03.10, 13:00 UTC (сессия «Финансовый раздел», владелец «наведи порядок на сервере»)

Около 12:55 UTC `app.wetop.ai` снова отвечал 530: средняя нагрузка 144 на двух ядрах, свободно 65–123 МБ памяти, подкачки нет, ядро
убило стойку (`Out of memory: Killed process … next-server`). Виновник тот же: раннер CI гонял проверки с Chrome на рабочем
сервере (107 % процессора, 1,7 ГБ), а скрипт выкладки на сервере был старой копией без проверки занятого раннера, мера А из §5
в репозитории была, на сервер не попала. Сделано руками владельца по блоку команд сессии (агенту остановку раннера и
системные правки отклонил классификатор):

| Мера | Проверено после |
|---|---|
| раннер остановлен, затем запущен снова | 0 % процессора, 107 МБ в покое |
| Б: подкачка `/swapfile` 4 ГБ, строка в `/etc/fstab`, `vm.swappiness=10` в `/etc/sysctl.conf` | `swapon --show`: 4G |
| скрипт `/usr/local/sbin/wetop-auto-deploy` обновлён из `origin/main` (вторая строка установки §1д) | `grep -c ci_busy` = 2 |
| `cloudflared` пересоздан, чтобы получить `oom_score_adj: -500` из compose (выкладка трогает только `api web`) | `oom_adj=-500` у api, web, cloudflared |
| `docker builder prune -f`, `docker image prune -f` (тома не трогались) | диск 83 % → 68 %, освобождено ~15 ГБ |
| автозапуск раннера возвращён (`restart=unless-stopped`) | после ручной остановки сам не поднимается |
| под нагрузкой раннера 13:13–13:18 | подкачка приняла 1,7 ГБ, сайт всё время 200, OOM не было; в 13:18:19 раннер снова остановлен вручную |

**Решено 03.10, 13:30 UTC (владелец «делай сам, решай»):** проверки CI на рабочий сервер больше не ходят совсем, все задачи на
раннерах GitHub (`50da83d9`, дополнение к ADR-139); раннер `pms-lux-ci-runner-1` остановлен и не нужен. Перезагрузка ради
обновлений ядра назначена `shutdown -r` на **03.10 21:00 UTC (02:00 Алматы)**: у всех служб `unless-stopped`, Docker и cron в
автозагрузке, подкачка в `fstab`, копия базы в 23:30 UTC не пересекается; прерванную выкладку скрипт доведёт следующим запуском.
Отменить: `ssh hostinger 'shutdown -c'`.

Итог 13:13 UTC: нагрузка 1,3, `app.wetop.ai` 200, api и web `healthy`. **За владельцем:** перезагрузка сервера ради ожидающих
обновлений ядра («System restart required»), в тихое время, около двух минут простоя; вынос раннера CI на отдельную машину
(мера Г для проверок, а не только для сборки): 2 ядра и 8 ГБ впритык на стойку, двух ботов, чужие `vilkabot2` и `traefik` и проверки сразу.
