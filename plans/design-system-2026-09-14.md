**Статус: подтверждён владельцем 14.09.2026** (поручение «ознакомься и выполняй всё по порядку» с инструкцией
`design-system-2026-09-14-start.md`; развилки Д1–Д7 раздела 11 — по рекомендациям плана). Записано: ADR-046,
Q-130…Q-133, блок 10 опросника. План обязателен по AGENTS.md §1: работа меняет общие компоненты, ответ API
шахматки и сценарии стойки. Шаг 2.2 и шаг 7 — каждый со своим подтверждением, как записано в шагах.
**Ход:** шаги 0, 1, 2 выполнены 14.09.2026 (план 2.1 подтверждён «да и да»); доказательства — `CLAUDE.md` §2,
`design/README.md`, журнал тестов. Шаг 3 — отчёт `reports/design-system-gaps-2026-09-14.md` (34 дыры, закрыты в тот же день). Шаг 4 выполнен 14.09:
`/design-system`, пять компонентов, `tests/ui/design-system.spec.ts`, строка в `CLAUDE.md` §1.

29 страниц, у владельца в «Загрузках»), части 2–7. Сверка с кодом — три проверки только на чтение 14.09:

## 1. Зачем и что изменилось

- **13.09, ответ ментора:** дизайн после первой живой смены, правки только по замечаниям администраторов
  (дополнение к ADR-027).
- **14.09, документ ментора:** порядок пересобран. Шаг 1 из 8 до переезда — дизайн-система, шаг 2 — макеты,
  шаг 3 — экраны в коде по макетам. Причина: экран нужен сейчас — администратору и для живого показа
  Channex. На этапе 4 сертификации проверяющий смотрит наш экран и просит сделать действия из сценариев и
  произвольные («поменяй цену на 250 и min stay на 3»). Без записанных правил через месяц у экранов
  разойдутся кнопки, отступы и оттенки. Полировка оформления и сайт WETOP (в документе «Vtop») — по-прежнему
  после первой смены.
- **Дизайн у нас уже есть** — WETOP (ADR-029, ADR-035…039): `tokens.css`, светлая и тёмная тема, боковое
  меню, карточка брони панелью сбоку, проверки axe. Поэтому план **не рисует интерфейс заново**:
  1. записывает действующий дизайн как свод правил по документу — `DESIGN.md` и `design/tokens.json`;
  2. приводит код к этим правилам точечными правками там, где он их нарушает (раздел 3);
  3. по макетам доделывает недостающее: три рабочих экрана для показа Channex и четыре действия из списка
     управляющего.

## 3. Сверка текущего интерфейса с правилами документа

## 4. Где документ упирается в модель данных — сами не решаем

| Что просит документ | Что есть в системе | Как поступаем |
|---|---|---|
| Бронь из канала «не подтверждена» — видна на клетке, продать место второй раз нельзя | Брони канала создаются сразу `CONFIRMED`; `TENTATIVE` бывает только у перенесённых из Exely. Ревизия, которую не удалось сопоставить (ADR-024, Q-109), остаётся событием `FAILED` без брони и без подтверждения в Channex. Второй раз место не продаётся: пересечения запрещены в базе, остаток категории учитывает брони без ячейки (Q-107) | **Q-130, Д4.** Предложение (а): `TENTATIVE` на клетке словом «не подтверждена» и плашка «входящая бронь требует разбора» для ревизий с ошибкой. ## 5. Решение — ADR-046, записать в `DECISIONS.md` после подтверждения

- **Проблема.** Правила интерфейса разбросаны по ADR-027, ADR-029 и ADR-035 и расходятся с кодом: в документах
  записан IBM Plex, в коде системный стек; «залита только главная кнопка» — в коде залиты все варианты.
  Ментор 14.09 поменял порядок работ. Экраны для показа Channex нужны до созвона.
- **Варианты.**
  - (а) Ждать первой смены, как решено 13.09.
  - (б) Рисовать дизайн заново в Claude Design.
  - (в) Записать действующий дизайн как свод правил по документу 14.09, привести код к правилам по
    нарушениям, новые экраны делать по макетам.
- **Решение: (в).**
- **Последствия.**
  - `DESIGN.md` и `design/tokens.json` — единственный источник правил интерфейса.
  - `tokens.css` только генерируется.
  - Правило меняется сначала в репозитории, потом в Claude Design.
  - Дальнейшая полировка — по замечаниям смены, как в ADR-027.
- **Номер.** В `main` ADR-045 и Q-129 заняты адресами wetop.ai (коммит `d9a97e7`). Ветка про защищённое
  соединение с базой держит те же номера под другую тему и при слиянии возьмёт следующие. Номера сверить
  перед записью.

   - важное только под наведением;
   - цели нажатия меньше 24 px;

**Отличия от промптов документа:**

- «Без ячейки» вместо «Без номера»;

## 8. Чего не делаем

- Не рисуем интерфейс с нуля и не меняем «по вкусу». Меняем только по правилам документа, по макетам после
  разбора и по замечаниям смены.
- Не меняем модель данных, правила бронирования и денег. В API — только новые поля и эндпоинты чтения из
  существующих данных, перечисленные в шаге 7.
- Не делаем экран «для сертификации».
- Не трогаем печатные формы, виджет бронирования на сайте, сайт WETOP и мобильное приложение.
- Не загружаем в Claude Design скриншоты Exely, весь репозиторий, данные гостей и ключи.
- Не включаем сочетания клавиш без согласования с администраторами.
- Не выкатываем изменения стойки (`npm run build -w apps/web` и перезапуск в launchd) в день двойного ввода.

## 9. Риски и правила работы

- **Параллельные сессии.** Сейчас другая сессия правит карточку брони:
  `reservations/[number]/actions-panel.tsx`, `page.tsx`, `lib/api.ts`. Общие компоненты правлю после её
  коммита. Коммит — только своих файлов, явным списком.
- **Next.js в проекте новее памяти модели.** Перед кодом — документация из `node_modules/next/dist/docs/`
  (`apps/web/AGENTS.md`): страница только для разработки, `next/font`.
- **Память Mac.** 8 ГБ, своп занят на 14,4 из 15,4 ГБ. UI-набор поднимает `next dev` и синтетический API.
  Перед прогоном проверить своп, работать на зарядке, прогон в один воркер.
- **Перевод отступов в шкалу меняет плотность.** 12 px встречается 100 раз, 10 px — 71. Переводим по экрану со
  сравнением скриншотов, а не заменой по всему CSS.
- **Смена шрифта ломает эталонные снимки.** Её делаем отдельной правкой; эталоны пересобираются вместе с ней и
  попадают в журнал.
- **Claude Design — внешний сервис.** Загружаем только правила, токены, код компонентов и синтетические снимки.
  Список файлов утверждается до загрузки.
- **Fable 5.1 дорогая.** Для мелких правок — усилие medium, как советует документ.

## 10. Найдено попутно — в этом плане не чиним

1. **Фильтр «Уборка» на шахматке всегда пуст.** Он ищет блокировку типа `CLEANING`, а такого типа в базе нет
   (`apps/web/src/app/chessboard/board-grid.tsx:105`; `packages/database/prisma/schema.prisma:374-379`).
   Статуса уборки в ответе шахматки тоже нет. Чинится в срезе 7.1.
2. **У ссылки «перейти к содержимому» серый текст на синем:** `color: var(--muted)` на
   `background: var(--primary)` (`workspace.css:531-532`). По расчёту контраст около 1,1:1 при норме 4,5:1.
   Ссылка видна только при навигации с клавиатуры.
3. **Штриховку блокировки перекрывает инлайн-фон клетки.** Штриховка задана в CSS (`workspace.css:794-802`),
   фон — в `board-grid.tsx:481`. Вывод по коду, в браузере не проверено.
4. **Подсказка блокировки для `OUT_OF_ORDER` и `MANAGEMENT` показывает сырой код** (`board-grid.tsx:24-28`).
5. **Синтетические данные UI используют несуществующий вид неисправности `booking.unassigned`**
   (`scripts/preview/fixture-api.ts:217`). В домене он называется `stay.unassigned`.
6. **Время входящих событий Channex — UTC без пометки.** По правилу нужно время объекта.
7. **Протокол сертификации 09.09 и пакет 11.09 расходятся** по ночной полной выгрузке (сценарий 13).
8. **Правила пересчёта цены** при переселении в другую категорию и при продлении записаны только в JSDoc
   `apps/api/src/reservations/reservations.service.ts`. В `DATA_MODEL.md` и `DECISIONS.md` их нет.
9. **Перетаскивание на шахматке работает только мышью** — с планшета переселить нельзя.
10. **На телефоне кнопки и поля 38 px:** правило 44 px (`workspace.css:665-669`) перекрыто
    `premium.css:77,88`.
11. **Мёртвый CSS:** `.topbar*` (`globals.css:55-124`), `.record-nav`, `.desk-board-card`, `.mini-board`.
