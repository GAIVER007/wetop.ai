# План «Касса»: объединение «Финансов за период» с кассой старой системы (02.10.2026)

Поручение владельца 02.10.2026: «найди раздел финансы, сделай там всё удобно» — со снимками
кассы старой системы (операции, новая операция, перевод между способами, статьи расходов).
Финансовая логика и модель данных меняются только решением владельца (CLAUDE.md §3, Q-207 п. 2),
поэтому сначала этот план и черновик модели `DATA_MODEL.md` §21 — код после «утверждаю».

---

## 1. Что есть сейчас

**WETOP «Финансы за период»** (ADR-113, F1–F2): только деньги броней — плитки
«Начислено / Оплачено / Возвращено / К сбору», вкладки «Обзор | Операции | Долги»,
выгрузка CSV. Оплаты и возвраты приходят из счетов гостей (`payments`, `refunds`),
способ оплаты у платежа уже есть (`PaymentMethod`: Наличные, Kaspi, Halyk, терминал…).

**Касса старой системы** (снимки владельца): остаток «Всего» и по способам оплаты;
произвольные операции «поступление / расход» со статьями («Зарплата», «Бытовые расходы»,
«Таргет/СММ», «Комиссия Банка»…); перевод между способами (Kaspi → Наличные) с комиссией;
привязка поступления к брони; фильтры по автору, типу, способу, статье, комментарию.

**Чего в WETOP нет совсем:** расходы, поступления мимо брони, переводы между способами,
остатки по способам, справочник статей. Q-207 п. 2 прямо говорит: для этого нужна
своя модель — правка `DATA_MODEL.md` и отдельный ADR.

---

## 2. Идея объединения

Один раздел «Финансы», одна лента денег, ничего не вводится дважды:

1. **Гостевые оплаты в кассу не переносятся руками.** Остаток по способу — вычисляется:
   оплаты гостей (COMPLETED) − возвраты + поступления кассы − расходы ± переводы.
   В старой системе администратор проводил оплату брони *и* операцию кассы — у нас это
   одна запись `Payment`, касса видит её сама.
2. **Одна форма «Новая операция»** с переключателем: привязана к брони → это обычный
   платёж по счёту (существующий поток, идёт в «К сбору» и баланс брони); без брони →
   операция кассы со статьёй. Администратор не думает, «куда» проводить — форма одна.
3. **Перевод** — отдельная команда «со способа на способ», комиссия (если есть) —
   связанный расход со статьёй «Комиссия банка», одной транзакцией.
4. **Вкладка «Операции»** становится общей лентой: оплаты и возвраты броней + операции
   кассы + переводы, с фильтром «Источник: брони | касса | все» и прежними фильтрами
   по типу и способу. CSV-выгрузка — та же лента.
5. **Новая вкладка «Касса»**: плитки остатков («Всего» и по способам), кнопки
   «Поступление», «Расход», «Перевод», управление статьями (панель, право `settings`).

## 3. Модель данных — черновик `DATA_MODEL.md` §21 (не утверждено)

Две таблицы и один enum; `payments`/`refunds` не меняются.

```prisma
enum CashOperationKind { INCOME EXPENSE TRANSFER }

/// Статья кассы: справочник объекта. Удаления нет — архив через active (как Service).
model CashCategory {
  id         String  @id @default(uuid()) @db.Uuid
  propertyId String  @db.Uuid
  kind       CashOperationKind            // INCOME или EXPENSE; для TRANSFER статей нет
  name       String
  active     Boolean @default(true)
  @@unique([propertyId, kind, name])
}

/// Движение денег мимо счетов гостей: поступление, расход, перевод между способами.
model CashOperation {
  id          String            @id @default(uuid()) @db.Uuid
  propertyId  String            @db.Uuid
  kind        CashOperationKind
  method      PaymentMethod                 // для TRANSFER — «откуда»
  methodTo    PaymentMethod?                // только TRANSFER — «куда»
  amount      BigInt                        // тиын, > 0 (ADR-008)
  categoryId  String?           @db.Uuid    // статья INCOME/EXPENSE; у перевода — null
  note        String?
  relatedId   String?           @db.Uuid    // комиссия → своя операция/перевод
  status      PaymentStatus     @default(COMPLETED) // VOIDED — аннулирование, прошлое не правится
  occurredAt  DateTime          @db.Timestamptz(6)
  createdById String?           @db.Uuid
  createdAt   DateTime          @default(now()) @db.Timestamptz(6)
}
```

Правила:
- **Остаток по способу** = Σ `payments` COMPLETED(method) − Σ `refunds` (по способу платежа)
  + Σ INCOME − Σ EXPENSE − переводы-откуда + переводы-куда. Валюта — валюта объекта.
- **Начальный остаток** — обычное поступление со служебной статьёй «Начальный остаток»,
  отдельной таблицы нет.
- **Комиссия** (операции или перевода) — отдельная операция EXPENSE со статьёй, связанная
  `relatedId`, в одной транзакции с основной. Процент — удобство формы, в базе только
  сумма целыми тиынами.
- **Аннулирование** вместо правки: `status = VOIDED` + запись в журнал (как у `Payment`);
  аннулирование комиссии — вместе с основной.
- **Касса — не каждый способ оплаты:** `EXTERNAL`, `DEPOSIT`, `CARD_GUARANTEE` — не живые
  деньги объекта, в остатках не показываются (Q-237).
- RLS — как у остальных таблиц организации (§17).

## 4. Интерфейс

Вкладки: **Обзор | Операции | Долги | Касса** (стили и панели — DESIGN.md, компоненты
с `/design-system`).

**«Касса»:** плитки «Всего в кассе» и по способам (Наличные, Kaspi, Halyk, терминал —
набор Q-237); кнопки «Поступление», «Расход», «Перевод» — панель справа; ниже — движения
за выбранный период (общая лента, отфильтрованная «только касса»); строка «Статьи» —
панель со справочником (добавить, выключить; право `settings`).

**Форма операции** (панель): тип (поступление/расход), сумма, способ, статья,
комиссия (необязательно: сумма или %, статья расхода — по умолчанию «Комиссия банка»),
«Привязать к брони» (поиск по номеру или фамилии — тогда проводится обычный платёж
по счёту, поля статьи скрываются), комментарий. Ошибки — словами у поля, введённое
не теряется; «только чтение» — без кнопок.

**Форма перевода:** откуда, куда, сумма, комиссия (необязательно), комментарий.

**«Операции»:** прежний экран + фильтр «Источник» и типы «Поступление / Расход / Перевод»;
CSV — те же строки (статья и автор добавляются колонками, имён гостей по-прежнему нет).

**«Обзор»:** без изменений, кроме необязательной плитки «В кассе сейчас» (Q-239).

## 5. Вопросы владельцу (QUESTIONS.md)

- **Q-236** — стартовый набор статей: перенести ли список старой системы
  (Зарплата, Бытовые расходы, Ремонтные работы, Таргет/СММ, Минибар, Чай/вода/сахар,
  бытовая химия, Мероприятия, Комиссия Банка, Расходы Хостел №2) как сид справочника?
  Умолчание — да, кроме «Расходы Хостел №2» (это другой объект).
- **Q-237** — какие способы показывать плитками остатков. Умолчание — CASH, KASPI,
  HALYK, CARD_TERMINAL + любой способ с движениями за период.
- **Q-238** — права: проводить операции и переводы — любой со стойкой (`desk`),
  аннулировать — право `refunds`, статьи — `settings`. Так?
- **Q-239** — показывать ли «В кассе сейчас» на «Обзоре» (остаток не зависит от
  выбранного периода — может путать рядом с периодными плитками). Умолчание — нет,
  остатки живут на вкладке «Касса».
- Q-207 п. 2 (кассовые смены, «наличные требуют проверки») — **не входит**: модель
  остатков и операций — фундамент, сверка смен — отдельным решением позже.

## 7. Чего сознательно нет

- Кассовых смен и сверки наличных (Q-207 п. 2) — отдельный ADR позже.
- Мультивалютности кассы — валюта объекта.
- «Получателей» из фильтров старой системы — это были сотрудники; у нас автор операции
  пишется сам (учётная запись), отдельного справочника получателей не заводим.
- Привязки операции к номеру/месту («если выбрано несколько номеров…») — в старой
  системе это дробило одну операцию на копии; расход объекта в WETOP не делится по
  комнатам, аналитика расходов — по статьям.

## 8. K4 — сверка наличных (02.10.2026, «давай продолжай»; остаток Q-207 п. 2)

Старое «наличные требуют проверки» без модели было запрещено (Q-207). Модель:

**`cash_reconciliations`** — запись пересчёта: `method` (кассовый способ, обычно CASH),
`expected` (остаток по системе в момент сверки — снимок, задним числом не восстановить),
`counted` (фактически пересчитано, ≥ 0), `note`, автор, время. Аннулирования нет: сверка — факт,
ошиблись — сверили заново. RLS как у кассы. Миграция `20261002000041_cash_reconciliations`.

**Расхождение** — не хранится (counted − expected); по галочке «выровнять поправкой» API создаёт
обычную операцию кассы той же транзакцией: излишек — INCOME «Излишек кассы», недостача — EXPENSE
«Недостача кассы» (статьи создаются по требованию). Лента остаётся единственным источником движений.

**API:** `GET /finance/cash` дополняется `reconciliations` (последняя по каждому способу);
`POST /finance/cash/reconciliations` `{method?, counted, note?, adjust?}` — право `desk` (сверяет
смена, как в старой системе), журнал. **UI:** на вкладке «Касса» — кнопка «Сверить» (панель: способ,
«по системе», «фактически», галочка поправки, комментарий) и строка состояния «Наличные: сверено
<когда>, расхождение …» / «ещё не сверялись». На «Обзор» не выносится (дух Q-239).

Умолчания (владелец — «давай продолжай», отдельных вопросов нет): сверка любого кассового способа,
по умолчанию наличные; галочка поправки включена; «требует проверки» — только текст давности на
вкладке, без порогов и предупреждений.
