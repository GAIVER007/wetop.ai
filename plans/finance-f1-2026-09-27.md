# Финансы за период — срез F1: иерархия экрана и список долгов (27.09.2026)

**Основание:** ТЗ владельца «Финансы / Деньги за период» от 27.09.2026 (передано облачной сессии задачей).
ТЗ само делит работу: **F1** — шапка и фильтры, четыре KPI в ряд, «Требует внимания», структура денег,
список «Брони с остатком к сбору»; **F2** — последние оплаты и возвраты, drill-down, фильтры по способам,
экспорт, сверка, касса. Этот план фиксирует, что входит в F1, на каких данных, и что откладывается.

Решение — **ADR-113**. Вопросы, которые F1 не решает сам, — **Q-206**, **Q-207**.

---

## 1. Аудит перед правкой

**Экран:** `apps/web/src/app/finance/page.tsx` («Деньги за период», в меню — «Оплаты»). Сверху форма
«С / По / Показать» отдельной панелью, под ней отдельной строкой готовые отрезки, под ними строка
про период. Дальше три панели одинакового веса: «Начислено гостям» (плитка + две таблицы),
«Деньги на руках» (две плитки + таблица), «Остаток к сбору» (одна плитка и абзац). Долгов поимённо
нет — экран говорит «взыскать можно только на счёте брони: найдите её».

**API:** `GET /finance/report?from&to` (`finance.service.ts` `periodReport`, репозиторий
`finance.repository.ts`): начисления по видам и по категориям (по `serviceDate`), оплаты по способам
(по `paidAt` в поясе объекта), возвраты (по `createdAt`), итоги; предел — 366 дней.
«Остаток» = начислено − оплачено + возвращено **за период** — это поток денег периода, а не сумма
долгов броней.

**Что важно для F1:**
- начисление за проживание — **одно на проживание** (`ensureSingleActiveCharge`), дата услуги — дата
  заезда. Значит «штук» в разрезе категорий — это число проживаний, а не ночей. Колонка будет
  называться «Проживаний»; ночей в отчёте нет, выдумывать их не будем;
- остаток одной брони уже считается везде одинаково — `folioBalance` из `@pms/domain`
  (список броней, шахматка, карточка). Список долгов берёт его же;
- приём оплаты — только на счёте брони (§7.3 прежнего плана). Кнопки «Добавить оплату» без брони
  не будет: ТЗ это допускает («если логика только через бронь — оставить одну кнопку»).

## 2. Что входит в F1

1. **Шапка.** Заголовок «Финансы за период» (слова ТЗ), подзаголовок `1 сент. → 30 сент., 30 дней` (в ТЗ через «·»; DESIGN.md §14 разделитель-точку запрещает, сторож `design-slop`),
   справа одна кнопка «Найти бронь для оплаты».
2. **Период — одной компактной строкой:** «С» [дата] «По» [дата] · «Сегодня / 7 дней / Этот месяц /
   Прошлый месяц» чипами 30 px · «Показать». Под строкой мелко: «Начисления — по дате услуги, оплаты и
   возвраты — по дате операции». GET-форма работает без JavaScript, адрес `?from&to` не меняется.
3. **Четыре KPI одним рядом, одной высоты:** Начислено («проживание, услуги, штрафы»), Оплачено
   («всеми способами оплаты»), Возвращено («возвраты за период»), К сбору («начислено − оплачено +
   возвращено»). «К сбору» — тон внимания при сумме > 0 и ссылка на список долгов (`#debts`). Числа —
   те же поля `/finance/report`, `data-testid` `charged`/`paid`/`refunded`/`balance` сохраняются
   (на них стоит `ui:walkthrough`).
4. **«Требует внимания»** — строки из фактов, каждая со ссылкой, где есть куда вести:
   - «N ₸ к сбору — K броней» → список долгов;
   - «K броней: гость выехал, остаток не оплачен — N ₸» → список долгов с отбором «выехали»;
   - «K возвратов за период на N ₸» — справкой (списка операций в F1 нет, он в F2);
   - пусто — «За период проблем не найдено».
   Двух строк из примера ТЗ не будет, пока их нечем считать: «просроченный долг» (у брони нет срока
   оплаты) и «оплаты наличными требуют проверки» (в модели нет отметки проверки наличных) — **Q-207**.
5. **Структура денег — две колонки:**
   - слева «По видам начислений» — всегда четыре строки (Проживание, Услуги, Штрафы, Корректировки),
     нулевые приглушены, строка «Итого» = KPI «Начислено»; ниже «Проживание по категориям»
     (Категория / Проживаний / Сумма, по убыванию суммы);
   - справа «Оплаты по способам» (Способ / Операций / Сумма, по убыванию, «Итого» = KPI «Оплачено»).
6. **«Брони с остатком к сбору»** (`#debts`): Бронь / Гость / Проживание / Начислено / Оплачено /
   Остаток / Статус / Действие («Открыть», «Принять оплату» → счёт брони `#booking-finance`; в режиме
   «только чтение» ADR-102 второй ссылки нет). Отбор «Все / Выехали» чипами, первые 20 строк и
   «Показать все N».

## 3. Новый запрос: `GET /finance/debts?from&to`

Только чтение, без схемы и без команд. Ответ:

```
{ from, to, currency,
  count, balanceMinor,                 // брони с остатком > 0 и сумма их остатков
  checkedOut: { count, balanceMinor }, // из них гость уже выехал (CHECKED_OUT)
  rows: [{ confirmationNumber, status, arrivalDate, departureDate, guestLabel,
           chargedMinor, paidMinor, refundedMinor, balanceMinor }],
  truncated }                          // строк не больше 500
```

- **Какие брони:** те, у которых за период есть действующее начисление (дата услуги в периоде) —
  та же база, что у KPI «Начислено». Отбор по объекту — как у отчёта.
- **Остаток брони:** по всем её счетам и за всё время — `folioBalance` (начислено − оплачено
  (`COMPLETED`) + возвращено). Это то же число, что «к оплате» в списке броней и на карточке.
- **Порядок:** остаток по убыванию, затем дата заезда, затем номер брони.
- **Запрос:** один SQL с подзапросами по счетам (без N+1 и без загрузки всех начислений в память) в
  репозитории финансов; предел периода — тот же 366 дней.

**Почему сумма списка может не совпасть с «К сбору».** Плитка считает деньги периода (оплата в
прошлом месяце за проживание в этом месяце в неё не входит), список — полный остаток брони. Когда
числа расходятся, под списком это сказано словами. Какое из двух чисел владельцу нужно на плитке —
**Q-206**; до ответа плитка считается как раньше (формулу ТЗ повторяет).

## 5. Что не входит в F1 (F2 и позже)

Последние оплаты и возвраты, drill-down по плиткам (кроме «К сбору» → список), отбор по способам
оплаты, экспорт, сверка, касса, переплаты «к возврату» списком, «просроченный долг» и проверка наличных
(ждут Q-207). Модель данных, финансовая логика и команды не меняются.

## 6. Стоп-гейт

Как у «Броней v2» (ADR-106): после F1 — снимки владельцу; F2 начинается после его «да».
