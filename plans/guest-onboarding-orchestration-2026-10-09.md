## 1. Поправки к плану (обязательны для всех срезов)

| # | Было в плане | Решение | Почему |
|---|---|---|---|
| П1 | Общий лимит «в Redis» в API (O2, O6) | В API Redis не заводим. Платные вызовы (скан, генерация, чат) идут через бот, а у бота Redis уже есть: лимиты по IP и сессии и суточный бюджет `wizard` живут там. В API остаются квота сессии в базе (`testMessagesUsed`, уже есть) и Turnstile. Грубый лимит по IP на `/wizard/*` делается правилом Cloudflare | Проверено: в `apps/api/src` нет ни `ioredis`, ни `redis`. Новая инфраструктура ради одного счётчика не нужна |
| П2 | Неясно, где безопасный загрузчик сайта | Загрузчик живёт **в боте** (`apps/ai-seller`), рядом с `scan_document`, маской ПД и бюджетом. API в чужой интернет не ходит. Точка: `POST /internal/wizard/scan` (служебный ключ), она скачивает, чистит и извлекает поля одним вызовом | Одна граница с чужим контентом вместо двух. Контейнер бота изолирован от базы PMS |
| П3 | Регистрация на `wetop.ai`, связь через сервер, токен «не дойдёт» | Шаг 6 «Регистрация» рисуется **внутри `/create`** на `app.wetop.ai` и зовёт тот же `POST /auth/register`, что и форма стойки. `wizardToken` уходит в теле запроса, в адрес не попадает никогда. Связь «подтверждение почты и черновик» на сервере остаётся (письмо можно открыть на другом устройстве) | Форма регистрации на стойке уже есть (регистрация v2, 29.09). Переход между доменами убирает проблему, а не обходит её |
| П4 | Отдельный воркер заданий | Отдельного процесса нет. `WizardJob` забирается через `SELECT … FOR UPDATE SKIP LOCKED` таймером в процессе API (по образцу `wizard-retention.service.ts`) и при опросе статуса. Задание, зависшее дольше 2 минут, возвращается в очередь (`attempt + 1`, максимум 3) | Ещё один контейнер ради одной очереди не оправдан. `SKIP LOCKED` переживает рестарт |
| П5 | Q-O3: 150 000 токенов в сутки | Цифру не берём на глаз. В O4 замеряем цену одного гостя (скан, генерация, 5 сообщений) и пишем её в отчёт. Потолок = цена гостя × 100 гостей в сутки. Владелец утверждает итоговое число. До замера: аварийный выключатель (`WIZARD_DAILY_TOKENS`), при превышении ручной ввод | 150 000 токенов хватит примерно на 3–5 гостей в сутки: воронка задохнётся в первый же день |
| П6 | Скан до трёх соседних ссылок (Q-O6) | O2 сначала делает **одну страницу**. Ссылки (до 3, тот же регистрируемый домен, общий предел 100 000 знаков) идут отдельным коммитом внутри O2, после зелёных SSRF-тестов на одной странице | Каждая лишняя ссылка добавляет SSRF-поверхность. Сначала доказываем основу |
| П7 | Номера ADR, Q, миграций | Вопросы Q-O1…Q-O7 при вливании получают свободные номера `QUESTIONS.md` (ADR-052). Миграция O5 берёт следующий свободный номер **на момент слияния с `main`**, а не на момент написания | В §2 CLAUDE.md номера 044 и 141 уже заняты дважды |

```
Волна 1 (параллельно):  O1 интерфейс и опрос      |  O2a загрузчик в боте (без UI, без LLM)
Волна 2 (параллельно):  O2b скан целиком           |  O3 генерация (вход: ручные поля, скан не нужен)

Волна 4:                O5b регистрация и перенос (нужны O3, O4 и «да» по O5a)
```

Стоп-гейты владельца: снимки O1; SSRF-отчёт O2; замер цены в O4; миграция O5 на рабочей базе; включение `WIZARD_ENABLED` в O6.

Общие правила для каждой сессии: своя ветка от свежего `main`; red → green через `npm run test:record`; коммит только своих файлов явным списком; `WIZARD_ENABLED` не включать; тексты без длинного тире; запись в CLAUDE.md §2 и отчёт в `reports/guest-onboarding-<срез>-<дата>/`.

## 4. ТЗ по срезам (раздавать сессиям целиком)

### ТЗ-O1. Интерфейс мастера и опрос

Ветка `claude/wizard-o1-ui`. Схема не меняется, LLM не вызывается.
1. Первый экран `/create`: заголовок, переключатель сценария (Q-O2: «Поддержка» пока «скоро»), поле «Адрес сайта», «Создать бота по сайту», ссылка «Настроить вручную без сайта», строка согласия (Q-O7).
2. Шапка с прогрессом из 4 точек (Источник, Проверка, Тест, Регистрация), «← В начало», баннер «Продолжить с шага N» по существующему токену.
3. Шаг «Проверка»: ниша выбором («Хостел», «Мини-отель», «Апарт-отель», «Гостевой дом», «Салон красоты», «Другое» со свободным вводом); обязательны только название и ниша; поле умеет пометку «найдено на сайте» (в O1 пометка приходит из фикстуры); валюта и пояс по `navigator.language` и домену `.kz`.
4. Шаг «Сборка» с опросом из 3 вопросов (цель, лидов в день, откуда узнали), «Пропустить» одним нажатием; кнопка «Протестировать» в O1 неактивна с подписью «Скоро».
5. API: `POST /wizard/survey` (upsert по сессии), `POST /wizard/event` (allowlist из ТЗ эталона §4, ключ дедупликации). Обе строки в `route-access.test.ts` как `public`.
6. Все строки в одном словаре `apps/web/src/app/create/strings.ts`. Новые компоненты (чек-лист стадий, пометка источника поля) сначала строкой в `DESIGN.md` §8.
7. Готово, когда: UI-спек red → green; поля восстанавливаются после перезагрузки; опрос и события пишутся (integration); axe в светлой и тёмной темах, 1440 и 390 px; снимки в отчёте. **Стоп: снимки владельцу.**

### ТЗ-O2a. Безопасный загрузчик в боте

Ветка `claude/wizard-o2a-fetcher`. Только `apps/ai-seller`, без LLM и без UI.
1. Модуль `wizard_fetch.py`: только `http`/`https`, порты 80 и 443; резолв DNS и проверка **каждого** адреса (loopback, private, link-local, CGNAT 100.64/10, 0.0.0.0/8, 169.254.169.254, multicast, IPv6: `::1`, `fc00::/7`, `fe80::/10`, IPv4-mapped); соединение на уже проверенный IP с правильным `Host` и SNI (защита от DNS-ребайндинга); каждый редирект проверяется заново, не больше 3; ответ до 2 МБ (обрыв потока, не `Content-Length`), таймаут 10 с на всё, только `text/html`; вычистка `script`/`style`/`noscript`, текст до 100 000 знаков.
2. Проверка адресов стандартной `ipaddress` (`is_private`, `is_loopback`, `is_link_local`, `is_reserved`, `is_multicast` плюс явный список выше). Новых зависимостей не добавлять, если хватает установленных.
3. Готово, когда: **сначала красные** тесты на `localhost`, `127.0.0.1`, `10.x`, `192.168.x`, `169.254.169.254`, `[::1]`, `0x7f000001`, редирект на внутренний адрес, домен, который на второй резолв отдаёт `127.0.0.1`, файл 3 МБ, `application/pdf`, порт 8080; затем зелёные на локальной публичной заглушке. Отчёт `reports/guest-onboarding-o2a-*/ssrf.md` с таблицей «атака → результат». **Стоп: SSRF-отчёт владельцу.**

### ТЗ-O2b. Скан сайта целиком

Ветка `claude/wizard-o2b-scan`, после O1 и O2a.
1. Бот: `POST /internal/wizard/scan` (служебный ключ): загрузчик O2a → `scan_document` → маска ПД → модель → поля (название, ниша, описание, до 8 частых вопросов). Лимиты по IP и сессии и суточный бюджет `wizard` в Redis бота (П1); бюджет исчерпан → 503, API уводит в ручной ввод.
2. API: `WizardJob(kind=scan)`, забор через `SKIP LOCKED` (П4), маскированная ошибка в задании; Turnstile на `POST /wizard/session` и запуск скана (переиспользовать `web-booking/turnstile.ts`, не копировать).
3. UI: реальные стадии из статуса задания, без таймеров и «осталось N сек»; «Заполнить вручную, пока ждём»; любая ошибка ведёт на «Проверку» с пометкой «не удалось прочитать сайт».
4. Вторым коммитом: до 3 ссылок того же домена (П6).
5. Готово, когда: e2e на заглушке (скан → поля с пометкой «найдено на сайте»), ошибка скана → ручной ввод без тупика, рестарт API посреди задания не теряет его (integration).

### ТЗ-O3. Генерация промпта и знаний

Ветка `claude/wizard-o3-generate`, после O1 (скан не нужен: вход это поля «Проверки»).
1. `WizardJob(kind=generate, revision)`: проход 1 промпт продавца, проход 2 знания по разделам (услуги, цены, правила, частые вопросы). **Переиспользовать** `generate-instruction` и `seller_prompt.py` бота; вторую копию генератора не писать.
1а. Сценарий `support` (Q-O2): свой промпт поддержки (отвечает по условиям, зовёт человека, не продаёт); после зелёного теста снять «скоро» с переключателя `/create`.
2. Защитные правила продавца (не считает суммы, не обещает за администратора, зовёт человека) добавляются всегда, независимо от ответа модели.
3. Результат с ревизией, не равной текущей, не отдаётся; правка полей запускает новую ревизию; не больше 5 ревизий на сессию.
4. Готово, когда: из набора полей выходят промпт и непустые разделы; повторная правка даёт новую ревизию; устаревший результат не выдаётся (unit и integration).

### ТЗ-O4. Гостевой тест-чат и замер цены

Ветка `claude/wizard-o4-chat`, после O3.
1. Бот: режим песочницы без организации: промпт и знания из `generatedPrompt`/`generatedKnowledge`, поиск по разделам в памяти, в базу бота ничего не пишется. Ответ возвращает названия разделов, по которым построен.
2. API: `POST /wizard/message {text, requestId}`: атомарное резервирование квоты одним `UPDATE … WHERE test_messages_used < 5 RETURNING`, идемпотентность по `requestId`, технический отказ освобождает резерв, шестое сообщение даёт 402, история не больше 10 реплик.
3. UI: подсказки вопросов, «осталось N из 5», свёрнутая строка «Ответ построен по разделам: …», «Поправить данные» возвращает на «Проверку».
4. Готово, когда: тест гонки двух сообщений на последней единице квоты, тест повтора `requestId` (оплачен один раз), тест 402; **замер цены одного гостя** (скан + генерация + 5 сообщений, токены и тенге) в отчёте. **Стоп: владелец утверждает суточный потолок (П5).**

### ТЗ-O5a. Предложение модели (только документ)

Ветка `claude/wizard-o5a-model`, параллельно с волной 2. Кода нет.
1. `DATA_MODEL.md`: колонка `email_verifications.wizard_session_id` (nullable FK на `wizard_sessions`, `ON DELETE SET NULL`), правило «одна живая связь на сессию», RLS как у `email_verifications`.
2. Запись ADR со следующим свободным номером: регистрация внутри `/create` (П3) и присвоение после подтверждения на сервере.
3. Готово, когда: документ в PR и «да» владельца.

### ТЗ-O5b. Регистрация и перенос бота

Ветка `claude/wizard-o5b-handoff`, после O4 и «да» по O5a.
1. Миграция (номер на момент слияния, П7) с `down.sql`; `check-migrations` OK.
2. `POST /auth/register` принимает необязательный `wizardToken` (`^wz_[a-f0-9]{64}$`) в теле; сервер сверяет хэш и пишет связь. `POST /auth/email/verify` сам зовёт `claim` идемпотентно.
3. `claim`: промпт в `seller_profiles.promptText` агента, разделы знаний в очередь индексации бота через outbox, идемпотентно по хэшу; существующего продавца организации не перезаписывает.
4. UI: шаг 6 внутри `/create` (П3), имя организации подставлено; после подтверждения карточка агента, шаг «Каналы»; токен из `localStorage` удаляется после входа.
5. Готово, когда: подтверждение в другом браузере даёт ровно одного агента; повтор письма и повторный вход второго не дают; чужой пользователь черновик не получает (integration). **Стоп: миграцию на рабочей базе применяет владелец.**

### ТЗ-O6. Запуск

Ветка `claude/wizard-o6-launch`, после O5b.
1. Аварийный выключатель по суточному потолку: мастер говорит «Сейчас не принимаем новые тесты, заполните вручную» и пускает в ручной поток.
2. Вход с главной `wetop.ai` на `/create?ref=…`; `noindex` на всех шагах, кроме первого.
3. Воронка (открыл, скан, генерация, тест, регистрация) в отчёт «Платформы» из `WizardEvent`.
4. Правило Cloudflare на `/wizard/*` (П1): текст правила в `docs/ops/`, включает владелец.
5. Готово, когда: полный путь e2e на staging; **`WIZARD_ENABLED=1` на рабочем домене только по слову владельца.**
