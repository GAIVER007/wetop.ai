# «Гости и бронирования»: один экран по макету владельца (09.10.2026)

**Основание.** Поручение владельца 09.10.2026 с картинкой: «смотри вот тебе фото, сделай всё чётко как на фото
раздел гости и брони». До этого он просил объединить «Брони» и «Гости» в одну вкладку; ряд вкладок
«Брони | Гости» (PR #319) его не устроил, нужен экран из макета: плитки показателей, чипы, таблица гостей с
проживанием и оплатой, панель выбранного гостя справа.

Макет и есть ТЗ на вид. Всё, что в нём нельзя сделать без новых правил (деньги, статус гостя, новые
сценарии), вынесено в QUESTIONS.md и не придумывается. Модель данных не меняется (CLAUDE.md §3).

## Что строим

Экран `/guests` (адрес прежний, заголовок «Гости и бронирования»). Одна строка таблицы всё так же один гость
(решение «Гости v2», ТЗ 27.09), но к строке добавляется его **основное проживание**: заселён сейчас, иначе
ближайшее будущее, иначе последнее состоявшееся.

```
Гости и бронирования                          [Список броней] [+ Новая бронь]
Единая база гостей, бронирований и проживаний

[Проживают 24] [Заезды сегодня 5] [Выезды сегодня 3] [Ожидают заезд 7] [Требуют внимания 4] [Без активного проживания 182]

[🔎 Поиск по гостю, брони, номеру, телефону…] [Статус ▾] [Источник ▾] [Период ▾]
[Все 32][Сегодня 8][Проживают 24][Ожидают 7][Выезды 3][Проблемные 4]   ○ Только с долгом ○ Только новые ○ Только без контакта
☐ Гость │ Контакты │ Бронь │ Проживание/статус │ Даты │ Номер │ Гостей │ Оплата │ Источник │ Последний визит │ ⋯
…                                                                              │ Панель гостя справа:
Выбрано 1 из 32  [Заселить][Выселить][Продлить][Добавить услугу][⋯]  Показать по 10 ▾  1 2 3 4 →   │ имя, бейдж, вкладки, контакты,
                                                                                  │ бронь, оплата, история, кнопки
```

Только готовые примитивы DESIGN.md §8.1–8.2: `Stat` (плитка, ссылка-фильтр, `delta`), `ChipGroup` и `Chip`
ссылками, `Toolbar`, `Table`, `StatusBadge` (реестры `hospitality`, `payment`, `source`), `Tabs` локально
для панели, `Segmented` не нужен. Новых примитивов нет; свои стили раздела только на окружение (сетка
«таблица + панель», аватар с инициалами).

## Откуда данные (сервер, только чтение)

`GET /guests/directory` получает **дополнительные** поля, старые остаются:

- у строки `stay` (основное проживание): номер брони, статус проживания, даты, ночей, ячейка, категория,
  взрослых и детей, источник и канал, валюта, начислено, оплачено, возвращено, остаток по счёту (`Folio`,
  формула `folioBalance`, как в «Бронях»); `null`, когда проживаний нет или только отменённые.
- `kpi` (не зависит от отборов): проживают, заезды сегодня, выезды сегодня, ожидают, требуют внимания,
  без активного проживания, плюс заезды и выезды вчера для сравнения.
- `views`: числа чипов (все, сегодня, проживают, ожидают, выезды, проблемные) при текущих отборах.
- новые параметры: `view`, `source`, `debt=1`, `fresh=1`, `nocontact=1`, `period` (`today|7d|30d`) и
  `periodFrom`/`periodTo`; `pageSize` как был (до 100).

`GET /guests/:id/preview` получает `stay`, `visits` (последние визиты), `services` (услуги основного
проживания) и `notes`. Документов в предпросмотре по-прежнему нет: их показ пишется в журнал.

SQL один на справочник: основное проживание гостя выбирается `LATERAL` с тем же приоритетом, что
`summarizeGuestStays` (заселён, затем ближайшее ожидаемое, затем последнее выехавшее), поэтому отбор по
источнику, долгу и периоду всегда про ту же бронь, что видна в строке.

## Определения (по существующим правилам, ничего нового)

| Что | Определение | Откуда |
|---|---|---|
| Проживают / Ожидают | состояния `INHOUSE`, `EXPECTED` справочника | «Гости v2» |
| Заезды сегодня | основное проживание ожидаемое, дата заезда сегодня | даты брони |
| Выезды сегодня | заселён, дата выезда сегодня | даты брони |
| Сегодня (чип) | заезд или выезд сегодня | сумма двух выше |
| Требуют внимания / Проблемные | у гостя есть проживание: без ячейки (активное); заезд просрочен; долг при заселённом или выехавшем; деньги к возврату | те же четыре факта, что «Требуют внимания» в «Бронях» (R2) |
| Без активного проживания | состояние `NONE` | «Гости v2» |
| Долг | остаток по счёту основного проживания больше нуля | `folioBalance` |
| Оплата в строке | слово и сумма из `financeState` (оплачено, долг, не оплачено, к возврату) | «Брони v2» |
| Только новые | визитов не больше одного | факт `staysCount` |
| Только без контакта | нет ни телефона, ни почты | поля гостя |

## Что из макета не делаем и почему

| В макете | Решение | Почему |
|---|---|---|
| «+ Новый гость» | **не рисуем**, на этом месте «Список броней» | гость заводится только вместе с бронью, ADR-072 и ТЗ «Гости v2» §5; решение владельца после переезда базы в РК (Q-GB-1) |
| «Постоянный гость» и «Новый гость» под именем | **подпись по числу визитов**: два и больше «Постоянный», иначе «Новый» | в модели такого статуса нет; правило взято из самого макета, пороги за владельцем (Q-GB-2) |
| «+2 к вчерашнему дню» у «Проживают» | **нет сравнения**, подпись «Сейчас в доме» | истории статусов в модели нет, число за вчера считалось бы другим способом, чем сегодняшнее; у заездов и выездов сравнение есть, там считается по датам (Q-GB-3) |
| «Долги, вопросы, особые отметки» под «Требуют внимания» | подпись по факту: «Долг, без номера, не заехал» | «вопросов» и «особых отметок» в данных нет |
| Групповые действия «Заселить», «Выселить» по нескольким броням сразу | **у каждой кнопки один сценарий: одна выбранная бронь** открывает карточку на нужной вкладке; при нескольких отмеченных кнопки неактивны с подсказкой | массовое заселение и выселение с деньгами это новая бизнес-логика (Q-GB-4); карточка уже умеет всё с подтверждениями сумм |
| «⋯» в нижней панели | «Снять выделение» | больше действий нет |
| Колонка-шестерёнка (выбор колонок) | не делаем | своего хранилища настроек нет; вне среза |
| «Написать в WhatsApp» | ссылка `wa.me` из существующего `messengerLinks` | внешней интеграции нет, как и сейчас в предпросмотре |

## Меню и соседние экраны

- В шапке один пункт **«Гости и бронирования»** (адрес `/guests`), как просил владелец (одна вкладка). Классический
  список броней со всеми отборами и экспортом остаётся: кнопка «Список броней» в шапке экрана, а на
  `/reservations` кнопка «Гости и бронирования». Адреса `/reservations/*` и `/guests/*` не меняются.
- Ряд вкладок «Брони | Гости» из PR #319 снимается (`section-tabs.tsx`), чипы «Проживают/Ожидают/…» заменены чипами макета.
- Нижняя панель телефона: «Гости и брони» (короткая подпись) на месте «Брони».

## Чего не меняем

Модель данных, миграции, права (`desk`), деньги, правила брони. Карточка гостя `/guests/[id]` и дни рождения
остаются. Шторка предпросмотра `/guests/[id]/preview` (перехватывающий маршрут `@drawer` и страница) удалена: на неё
больше никто не ссылается, её роль выполняет панель справа; ответ API `/guests/:id/preview` панель использует сама.

## Как вышло при сборке (отличия от замысла выше)

- Точки перелома только из договора (DESIGN.md §4.1): панель стыкуется справа от 1280 px, ниже она листом поверх
  списка. Колонки «Гостей» и «Источник» прячутся не по ширине окна, а по ширине самого списка (запрос контейнера
  `gb-list`, меньше 1400 px): открытая панель отнимает 376 px, и на 1440 они не помещаются, на 1920 помещаются.
- Подписи без разделителя «·» (сторож §14): номер выделен жирным, категория приглушена; пустая ячейка это короткое
  тире, длинное запрещено правилом проекта.
- Скрытая подпись «Действия» у последней колонки тянула страницу вбок на планшете (абсолютное позиционирование
  вне прокручиваемой обёртки); ячейкам таблицы задан опорный блок. Нашёл тест ширины на 1024 px.
- Размер страницы по умолчанию 10 (как «1–10 из 32» на макете), варианты 10, 25, 50.
