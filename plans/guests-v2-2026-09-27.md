# «Гости v2» — G1+G2 по ТЗ владельца (27.09.2026)

**Основание.** ТЗ владельца «WETOP Hospitality · Гости v2» от 27.09.2026 (52 пункта): раздел `/guests`
должен отвечать «кто этот человек и какая у него история», а не повторять список броней. Сейчас экран
показывает брони на сегодня со статусом брони в колонке «Статус» — то самое смешение сущностей,
которое ТЗ называет главной проблемой (§3, §15).

**Рамка этого среза — G1+G2 из §51 ТЗ:** раскладка, компактный поиск, новая guest-центричная таблица
и агрегация «сейчас / ближайший / последний визит + число визитов». По §51 **после G1 — визуальный
стоп**: скрины light/dark едут в `reports/guests-v2-2026-09-27/`, дальнейшие ступени — после разбора
владельцем. Не в этом срезе: G3 (быстрый предпросмотр панелью), G4–G5 (перестройка карточки гостя,
финансовый свод — карточка с вкладками «Информация / Проживания / Счета и услуги» остаётся как есть),
G6 (бронь из гостя), расширенные фильтры и сортировки §28–§30, мобильные карточки сверх текущего
приёма складывания строк, «Есть долг» (§29 — считать из Folio, отдельная ступень).

## Ответы на проверки, которые ТЗ требует от разработчика

## API — `GET /guests/directory` (новый, рядом с прежним `GET /guests?q=`)

Прежний `GET /guests?q=` остаётся: им пользуется глобальный поиск ⌘K. Новый эндпойнт объявляется
до `GET /guests/:id`, параметры: `state` (`ALL | INHOUSE | EXPECTED | RECENT`), `q` (те же правила,
что у поиска: имя/фамилия/email подстрокой, телефон от 4 цифр; плюс номер брони), `page`,
`pageSize` (по умолчанию 25, потолок 100).

Ответ: `{ total, page, pageSize, counts: {ALL, INHOUSE, EXPECTED, RECENT}, rows }`. Строка:

```
id, firstName, lastName, middleName, phone, email,
staysCount            — визиты: проживания CHECKED_IN + CHECKED_OUT (отменённые и незаезды — не визит)
state                 — INHOUSE | EXPECTED | RECENT | NONE (вычисляется, статус брони наружу не идёт — §15 ТЗ)
current               — CHECKED_IN-проживание: { unitCode, accommodationTypeName, departureDate } | null
next                  — ближайшее CONFIRMED/TENTATIVE с departureDate ≥ сегодня:
                        { arrivalDate, departureDate, accommodationTypeName } | null
                        (просроченный заезд — arrival в прошлом — остаётся «ожидается», как в «Требуют внимания»)
last                  — последнее CHECKED_OUT: { arrivalDate, departureDate, unitCode } | null
lastCancelledAt       — дата заезда последней отменённой/незаезда, только когда визитов нет (§16 ТЗ)
```

Состояния взаимоисключающие (бейдж = фильтр, суммы чипов сходятся):
`INHOUSE` — есть CHECKED_IN; `EXPECTED` — не INHOUSE и есть CONFIRMED/TENTATIVE с выездом ≥ сегодня;
`RECENT` — не первые два и есть CHECKED_OUT с выездом за последние 30 дней; иначе `NONE`.
«Недавние» = 30 дней — умолчание представления (гость трёхлетней давности ≠ выехавший сегодня, §7 ТЗ);
на данные и деньги не влияет, меняется строкой кода.

Всё считается по `StayGuest → ReservationItem` (одним `findMany` со `include` на страницу — без N+1);
все три пути создания брони (стойка, канал, импорт Exely) пишут `StayGuest`, покрытие полное.
`counts` — четыре `count` по тем же условиям. Сортировка: фамилия, имя (как сейчас). «Сегодня» — по
поясу объекта (`propertyToday`, С-13). Порог «двух символов» на `q` здесь не нужен: пустой `q` — это
просто список.

## Стойка — `/guests` (Next.js, серверная страница)

По §4, §47 ТЗ и образцу «Броней» (реестр DESIGN.md §8, чипы `.chips` из `globals.css` — четвёртую
копию не заводим, стекло `.reservations-controls` уже в списке §20.3 — блок фильтров переиспользует
тот же класс):

```
Гости                                        [+ Новая бронь]
База гостей объекта и история проживаний

[Все 1248] [Проживают 74] [Ожидаются 31] [Недавние 126]      ← чипы со счётчиками до нажатия
[🔎 Имя, телефон, email или номер брони………]                   ← автопоиск, кнопки «Найти» нет
────────────────────────────────────────────────────────────
N гостей по запросу…  Сбросить фильтры
Таблица │ Гость │ Контакты │ Сейчас / ближайший визит │ Последний визит │ Визитов │ Статус │
Страница 1 из 50  [Назад] [Далее]
```

- Одна строка = один гость (не бронь). Имя — ссылка на карточку тем же приёмом `.dir-guest`.
- «Контакты»: телефон + WA, почта строкой ниже мелким.
- «Сейчас / ближайший визит»: живёт — ячейка и «до 30 сент.»; ожидается — «заезд 4 окт.»
  (просроченный — «заезд был 25 сент.») и категория мелким; иначе «—».
- «Последний визит»: «12 сент. → 15 сент.» в `<time>`; не было — «—», а при отменённой последней
  брони — «бронь на 24 сент. отменена» мелким (§16 ТЗ).
- «Статус» — слово о госте: «живёт» (ok) / «ожидается» (info) / «выехал недавно» (neutral) / «—».
  Статус брони (`отменена`) в строке гостя больше не появляется.
- Поиск — клиентское поле с debounce (350 мс, `router.replace`), внутри обычной GET-формы: Enter
  и работа без JS сохраняются; при вводе сбрасывается `page`. Подсказка «не менее 2 символов» остаётся.
- URL: `/guests?state=inhouse|expected|recent&q=…&page=N` (§31 ТЗ). Старые адреса
  `?status=CHECKED_IN|CONFIRMED|CHECKED_OUT` молча читаются как соответствующий `state`.
- Ссылка «Все бронирования» уходит (§32 ТЗ), большая карточка поиска с кнопкой «Найти» уходит (§48).
- Состояния: `loading.tsx` со скелетоном таблицы; отказ API — `LoadError` с «Повторить», заголовок и
  фильтры остаются (приём B5); пусто — два текста: база пуста («Гостей пока нет — появятся после
  первой брони», кнопка «Новая бронь») и пустой результат отбора («Ничего не найдено», «Сбросить»).
- Телефон: строки складываются в карточку тем же приёмом `@media (max-width: 600px)`, что у броней;
  старые блоки CSS `--guests`/`--guests-today` заменяются одним для новой таблицы.
- `GuestDirectory` (список броней на сегодня) удаляется вместе со своим спеком-ожиданиями — его
  вопрос («какие брони сегодня») уже отвечает `/reservations?from=сегодня`.

## Чего не делаем без владельца

Модель данных не меняется. Дубли/merge (§27), «Добавить гостя» (§5), долг в списке (§29), панель
предпросмотра (G3), перестройка карточки (G4–G5), бронь из гостя (G6) — следующие ступени, порядок
за владельцем после визуального стопа.

## Дополнение вечером 27.09 — синхронизация с Phase 1/RLS (поручение владельца)

Аудит выше был верен для базы ветки (`6440f99`): колонки у гостя тогда не было. К вечеру в `main`
въехали ADR-102 (пробный период) и **ADR-103 (RLS, DATA_MODEL v1.13 §17)**: `guests.organization_id
NOT NULL` — backfill из броней в миграции `20260927000027` (гость в бронях двух организаций —
остановка миграции), `DEFAULT app_current_org()`, FK и индекс; `createGuest` штампует организацию
объекта у стойки и у канала. Отдельная ветка `claude/hopeful-thompson-2v8v8a` несёт параллельную
реализацию «Phase 1» (nullable-вариант с fallback) — в `main` она не влита, следуем `main`.

Сделано по указанию владельца:
- `origin/main` влит в ветку G1 merge-коммитом; конфликтов не было — main `guests/*` не трогал.
- `visible()` гостей: **`organization_id` — канонический и единственный признак**
  (`{ organizationId: currentOrganizationId() }`; вошедший без организации — отказ, как в
  property-ref). Fallback через брони **снят** вторым решением владельца 27.09: гостя без колонки
  не существует (NOT NULL + backfill миграции `…027`, все пути создания штампуют), а условие шире
  колонки расходилось бы с RLS — база под `wetop_app` режет ровно по колонке, и гость чужой
  организации не должен открываться из-за связи через бронь. Через `visible()` ходят search,
  directory, byId и — через byId — update и документы.
- Интеграционные доказательства (red → green на каждом шаге):
  1) гость, проштампованный колонкой **без единой брони**, виден своей организации (справочник и
     byId) и невиден чужой — red `…15-09-13Z-integration-2d43.log`, green `…15-11-07Z-…-d418.log`;
  2) **снятие fallback**: гость организации B со `StayGuest`-связью в объект A организации A
     **не виден** (ни справочник, ни byId), B — виден; red на коде с fallback
     `…15-30-35Z-integration-6dbc.log`, green `…15-31-25Z-integration-2826.log`, итог
     `…15-37-39Z-integration-898b.log` — **107/107**, включая rls-isolation 6/6 (на локальном
     стенде ролям включён LOGIN — шаг владельца из `docs/ops/rls.md`, этап 2).
- Пути создания гостя — все штампуют организацию, доказано тестами:
  стойка, канал Channex и сайт зовут один `PrismaReservationsRepository.createGuest`
  (`reservations.service.ts:461`, `inbound.service.ts:866`, web-booking →
  `ReservationsService.create`) — проверка в `manual-reservation.test.ts` (гость созданной брони
  несёт организацию объекта; ищется через бронь — вне РК имена обезличены, ADR-072); импорт Exely
  штампует сам (`import-reservations.ts:142→284`) — проверка в `reservations-import.test.ts`;
  сид локальной базы обновлён RLS-сессией (иначе NOT NULL его бы не пустил).
- «Только чтение» после пробного периода — **общий механизм, своей trial-логики у гостей нет**:
  запрет записи — метод-базированный в `SessionGuard` (`writeBlocked`, ADR-102), guard-тест
  расширен путями гостей (GET `/guests/directory` проходит, PATCH гостя и документы — 403
  словами); UI — общая полоса `read-only-banner` из `top-nav`, `trial-read-only.spec.ts` расширен
  экраном `/guests` (список, поиск и карточка читаются).
- Кейсы фикстуры `POST /__test/guest-cases` (вымышленные, ADR-010): «Возвращающийся» — три
  проживания, живёт; «Отменившийся» — только отменённая бронь; «Давний» — выезд 40 дней назад;
  «Задолжавший» — живёт, его счёт покажет панель предпросмотра. **Долг в таблицу G1 не выводим**
  (решение владельца 27.09) — сначала в предпросмотре.
- Верхнее действие остаётся «+ Новая бронь»: самостоятельного создания гостя нет, ADR-072 не
  разрешает; «+ Добавить гостя» не показываем (подтверждено владельцем).

## G3 — панель предпросмотра гостя (визуальное «да» владельца получено 27.09, «Давай продолжай»)

Рамка — ТЗ §17 + решение владельца «долг не колонкой, сначала в предпросмотре»:
- **API `GET /guests/:id/preview`** (объявлен до `:id`): контакты, состояние из `summarizeGuestStays`
  (теперь факты несут `confirmationNumber` — для «Открыть бронь»), `nightsTotal` — ночи по визитам
  (`countGuestNights` в `@pms/domain`), `hasFolios` и `debtMinor` — тем же `folioBalance` по счетам
  проживаний гостя, что список броней (ТЗ §24: источник правды — Folio, «денег гостя» не заводим).
  Изоляция — тот же `visible()`; **документов в ответе нет**: их показ — событие журнала
  (SECURITY.md §1), предпросмотр журнал не трогает.
- **Панель**: перехват `/guests/[id]/preview` в корневом слоте `@drawer` (тот же `RouteDrawer`
  480 px, что у брони; заголовок «Гость»); щелчок по имени в таблице открывает панель, Escape и
  крестик возвращают в `/guests` с сохранёнными фильтрами; прямой заход и без JS — redirect на
  полную карточку. Внутри: имя, контакты полосой фактов, «Сейчас» (бейдж-слово, ячейка/заезд,
  «Открыть бронь» текущей или ближайшей брони), «История» (визитов, ночей, последний визит),
  «Финансы» («к оплате …» плашкой / «оплачено» / «Счетов пока нет»), внизу «Открыть гостя» и
  «Новая бронь» (предзаполнение гостя — G6). КАПС-заголовки из макета ТЗ заменены обычными
  `SectionTitle` — DESIGN.md §14 капс запрещает.
- Подставной API: `/guests/:id/preview` из карточек; долг — суммой «счетов» не-отменённых броней
  (отменённые счёта не строят — их «долг» не долг гостя).
- Проверки: юнит домена (номер брони в фактах, `countGuestNights`), юнит API (предпросмотр без
  документов и без записи в журнал, 404 чужому), UI-спек панели (должник «к оплате 4 000 ₸» и
  «Открыть бронь»; Возвращающийся — визитов 3, ночей 8; Отменившийся — «Счетов пока нет» и подпись
  про отменённую бронь; Escape; «Открыть гостя» → карточка; axe с открытой панелью); обновлены
  сценарии щелчка в `quality.spec` и `trial-read-only.spec` (предпросмотр — тоже чтение).
- DESIGN.md §8, строка «Панель сбоку»: гость — предпросмотр панелью с 27.09.

## G3 — финальный стоп-гейт владельца (27.09, «G3 по направлению подтверждаю»)

Владелец подтвердил направление G3 и дал чек-лист из семи пунктов; G4 (полная карточка) — только
после отдельного «да». Что изменилось против первой сборки панели:

1. **Возвраты** — щелчок открывает панель, Escape, крестик («Закрыть: Гость») и «Назад» браузера
   возвращают тот же список с теми же фильтрами и страницей (спек: открытие из
   `/guests?state=inhouse`, Escape и Back возвращают ровно этот адрес).
2. **Состав панели** — только имя, контакты (маскировка как везде), «Сейчас»/ближайший визит,
   последний визит, визитов/ночей, долг, «Открыть гостя», «+ Новая бронь». Слово о состоянии
   переехало из блока «Сейчас» к имени: блок «Сейчас» есть не у всякого гостя, а состояние — у всякого.
3. **Документов, ИИН и журнала в панели нет** (спек проверяет отсутствие текстом).
4. **Финансы — только при долге**: раздел рисуется лишь когда по счетам проживаний есть остаток
   («к оплате …» из Folio/Payment, ТЗ §24); строк «Долга нет» и «Счетов пока нет» не существует —
   без долга раздел не занимает место (пересмотр первой сборки, где раздел был всегда).
5. **Гость только с отменёнными бронями** — ложного «Сейчас»/«Следующий визит» нет вовсе: блок
   «Сейчас» не рисуется, подпись «бронь на … отменена» живёт в «Истории» в строке «Последний визит»
