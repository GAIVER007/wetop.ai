## Что можно сделать сразу, без вопросов (срез F1, только `apps/web`)

1. Шесть плиток с иконками, «В продаже» и «Требует уборки» из списка.
2. Фильтры одной строкой, вкладки со счётчиками «Недоступные» и «Требуют уборки».
3. Таблица: флажки, колонки «Тип», «Вместимость», «Статус продажи», «Уборка», меню действий; сворачивание групп.
4. Панель места по макету: заголовок со статусом, вкладки, поля информации, быстрые действия на существующих командах (редактировать, статус, создать бронь).
5. Тёмная тема и телефон по токенам DESIGN.md, без нового компонента вне `/design-system`.

## Что без решения владельца делать нельзя

1. **Динамика в плитках (+2%, −4%).** Нужна история фонда по дням, а это модель данных. Предлагаю не рисовать стрелки совсем: выдуманные числа в сводке хуже, чем их отсутствие.
2. **Колонка «Проживание / бронь» и фильтр «Занятость».** Нужен ответ API «кто в месте сегодня и кто заезжает» одним запросом на весь список. Данные уже есть в календаре, нужен новый эндпоинт чтения без записи и без изменения модели. Прежний план каталога (20.09) прямо запрещал статусы занятости, поэтому нужно «да».
3. **Колонка «Каналы» и значки на панели.** В `ChannelMappingRow` каналы привязаны к категории, а не к месту. Значки Booking, Airbnb, Яндекс можно показывать по категории места. Per-unit настройки каналов не нужно придумывать.
4. **Фото места и галерея.** В схеме нет фото места. Варианты: заглушка без фото, фото категории (если оно есть у категории), либо новая сущность (правка DATA_MODEL.md).
5. **Массовые действия.** Смена статуса, назначение уборки и перенос в категорию: проверить, какие команды есть в API пачкой. «Удалить» делать только как архив с подтверждением (удаление мест с бронями недопустимо).

## Решения владельца (09.10.2026) и уточнённый план

1. **Динамика по периодам, вверх или вниз.** Новая таблица истории не нужна: прошлое состояние восстанавливается из того, что уже пишется. Места на дату: `inventory_units.created_at` (дату выхода из продажи модель не хранит, поэтому архивные места в прошлое не вычитаются, это оговорка в подсказке). Недоступно на дату: пересечение с `inventory_blocks`. Требует уборки на дату: последнее `housekeeping_events.to_status` не позже даты. Новый эндпоинт чтения `GET /inventory/trend?days=7|30|90`, право `desk`, модель не меняется. Периоды в интерфейсе: 7, 30, 90 дней, стрелка и процент считаются от значения на начало периода.
2. **Занятость.** Новый эндпоинт чтения `GET /inventory/occupancy` (кто проживает, кто заезжает сегодня, по месту), без записи. Колонка «Проживание / бронь», фильтр «Любая занятость», вкладка «Свободные».
3. **Фото.** Владелец будет добавлять фото номеров. Сущности фото в схеме нет, поэтому это отдельный срез F3 с предложением в `DATA_MODEL.md` (v2.5) и миграцией, которую применяет владелец. В F1 блок фото рисуется как на снимке с нейтральной заглушкой и подписью «Фото ещё не добавлены».
4. **Каналы** по категории места (маппинг Channex привязан к категории), значки как на снимке.

Срезы: F1 интерфейс и два эндпоинта чтения, F2 массовые действия, F3 фото.
