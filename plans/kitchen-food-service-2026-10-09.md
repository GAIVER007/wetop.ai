# План: модуль «Кухня» для ресторанной вертикали (срезы FS1-FS7)

Дата: 09.10.2026. Статус: **УТВЕРЖДЁН владельцем 09.10.2026** ответом «да ох давай продолжай»
(согласие с рекомендованными вариантами Q-KITCHEN-1…8; ADR-KITCHEN-FS, модель FS1 в `DATA_MODEL.md` §33).
Поручение: ТЗ владельца от 09.10.2026 «Кухня + Калькуляция для ресторанов» с макетами
(десктопная «Кухня», мобильное меню, экран калькуляции, KDS). Кода по этому плану нет.

Прежнее решение владельца (ADR-MV1, QUESTIONS.md «Multi-vertical») выносило
POS/Orders/Kitchen/Menu/Warehouse за границы Food v1, поэтому модуль требует нового
решения владельца и нового раздела `DATA_MODEL.md`. Этот план и есть такое предложение.

## 1. Аудит: что уже есть (проверено по коду 09.10.2026, main `7ef9dd14c`)

**Есть и переиспользуется:**

| Что | Где | Как используем |
|---|---|---|
| Вертикаль `FOOD_SERVICE`, реестр возможностей | `schema.prisma:26`, `packages/domain/src/verticals/registry.ts:45` | Новая возможность `food.kitchen` тем же механизмом |
| Food Service v1: залы, столы, периоды, брони столов | `schema.prisma:2692-2798`, `apps/api/src/food-service/`, `apps/web/src/app/food/` | Scope-паттерн (`foodScope`, `foodTransaction`), столы для заказов кухни |
| Товарный учёт бара: партии, FIFO, лента движений, 7 инвариантов §27 | `schema.prisma:976-1200`, `packages/domain/src/bar/bar.ts` (`allocateFifo`), `apps/api/src/bar/` | Инварианты и доменная логика FIFO как образец для склада кухни (сами таблицы переиспользовать нельзя, см. Q-KITCHEN-1) |
| Паттерн каталога Beauty: справочник на Business, переопределения на Location, снимок цены в документе | `BeautyService` / `LocationService` (`schema.prisma:2558-2597`), `Appointment` со снимком цены | Та же схема для меню блюд |
| Навигация по вертикалям, `requireVertical`, пилотный доступ | `apps/web/src/lib/navigation.ts:507` (`foodMenuSections`), `vertical-guard.ts` | Пункт «Кухня» в меню ресторана |

**Нет нигде (ни в схеме, ни в API, ни в UI, ни в модели):** меню блюд, техкарты, рецептуры,
ингредиенты, склад кухни, заказы кухни, KDS, калькуляция. Поиск по
kitchen/recipe/ingredient/блюд/техкарт дал только посторонние совпадения.

**Ключевое препятствие для «общего справочника с баром» из ТЗ:** весь бар привязан к
`propertyId` (`bar.repository.ts:79`), Property есть только у HOSPITALITY, у ресторанного
Business его нет вовсе. ADR-MV6 прямо фиксирует «BAR is a separate Hospitality module».
Плюс Q-BAR-7: бар считает только штуки и упаковки, кухне нужны граммы.

## 2. Развилки владельцу (Q-KITCHEN-1…Q-KITCHEN-8)

Записаны в `QUESTIONS.md` с рекомендациями. Коротко:

| № | Развилка | Рекомендация |
|---|---|---|
| Q-KITCHEN-1 | Склад кухни: (А) свой домен на Location по образцу Food, доменная логика FIFO переиспользуется из `packages/domain`; (Б) обобщать таблицы `bar_*` с Property на Location | **А.** Б трогает работающий гостиничный модуль и его триггеры принадлежности (ремонты 053-057) ради чужой вертикали |
| Q-KITCHEN-2 | Единицы кухни: граммы, миллилитры, штуки; количества decimal-safe; закупка в упаковках с пересчётом в базовую единицу | **Да.** Q-BAR-7 остаётся правилом бара и кухню не ограничивает |
| Q-KITCHEN-3 | Уровень каталога меню: (А) Business с переопределениями филиала (как BeautyService + LocationService); (Б) каталог на каждом филиале отдельно | **А**, готовый проверенный паттерн, сеть ресторанов получает общее меню бесплатно |
| Q-KITCHEN-4 | Источник заказов для KDS: своего POS нет. (А) минимальный заказ в стойке: сотрудник создаёт заказ (стол, позиции, комментарий), без оплат и фискализации; (Б) отложить KDS до появления POS | **А**, иначе KDS и списание ингредиентов повисают без источника. Оплата заказа в v1 не делается вовсе |
| Q-KITCHEN-5 | Момент списания ингредиентов: одно настроенное событие, по умолчанию отметка «Готово» на KDS; строго один раз (ключ повтора); отмена до готовности не списывает ничего, после готовности создаёт сторно | **Да**, это прямое требование ТЗ §5 |
| Q-KITCHEN-6 | Нехватка остатка при отметке «Готово»: (А) списать до фактического остатка, недостачу записать отдельным движением в журнал, кухню не останавливать; (Б) запрет, как продажа в минус у бара (Q-BAR-8) | **А.** Повар уже приготовил блюдо физически, запрет в учёте создаст враньё в остатках; недостача видна в отчёте |
| Q-KITCHEN-7 | Модификаторы позиций и произвольные цены: вне v1, комментарий к позиции свободным текстом | **Подтвердить.** Модификаторы умножают рецептуры, в первом срезе только целые блюда |
| Q-KITCHEN-8 | Объединение номенклатуры бара и кухни (рекомендация ТЗ §7): целевая линия или никогда | **Отложить как целевую.** В FS1-FS7 не делается; когда у гостиницы появится Location-слой бара, объединение станет отдельным предложением модели |

НДС не считается и не показывается, как у бара (Q-BAR-6), это граница, не развилка.

## 3. Предлагаемая модель данных (черновик нового раздела DATA_MODEL.md)

После «да» владельца раздел переносится в `DATA_MODEL.md` (следующий свободный номер,
сейчас последний §31, причём §31 занят дважды, нумеровать внимательно). Все деньги
integer minor units, количества Decimal(14,3), события UTC timestamptz. Scope всех
таблиц через `locationId` или `businessId` по цепочке Organization → Business → Location,
RLS в `RLS_TENANT_TABLES`, триггеры принадлежности по образцу Food v1.

### 3.1 Меню (FS1)

| Сущность | Ключевые поля | Правила |
|---|---|---|
| `menu_categories` | businessId, name, sortOrder, active | Шаблоны категорий из ТЗ §2 это сид подсказок в UI, не отдельная таблица |
| `menu_items` | businessId, categoryId, name, sku, description, price (minor units), currency, outputWeightGrams, prepTimeMinutes, allergens text[], tags text[] (хит, новинка), active | Цена без налогов реализации; фото отдельным срезом (FS7, вопрос хранилища) |
| `location_menu_items` | PK (locationId, menuItemId), enabled, priceOverride, доступность «в наличии / стоп-лист» | Точная копия паттерна `LocationService`; стоп-лист живёт на филиале |

### 3.2 Ингредиенты и склад кухни (FS2, Q-KITCHEN-1 вариант А)

Зеркало §27 со scope Location вместо Property и весовыми единицами:
`food_products` (единица G/ML/PCS, упаковка, минимальный остаток), `food_suppliers`,
`food_receipts` + `food_receipt_lines` (количество Decimal, цена за базовую единицу),
`food_stock_lots` (партия, остаток, себестоимость, срок годности),
`food_stock_movements` (неизменяемая лента: RECEIPT, CONSUMPTION, WRITE_OFF,
REVERSAL, INVENTORY_ADJUSTMENT, SHORTAGE), `food_supplier_payments` (если касса
филиала доступна вертикали; иначе оплата поставщику уходит в FS6, вопрос при реализации).

**Семь инвариантов §27 действуют дословно** (проведённый приход только сторнируется,
движение с источником и автором, остаток сходится с лентой и партиями, приход отделён
от оплаты, minor units и decimal-safe, снимок себестоимости; «ниже нуля нельзя» с
поправкой Q-KITCHEN-6 для списания по готовности).

### 3.3 Техкарты и калькуляция (FS3-FS4)

| Сущность | Ключевые поля | Правила |
|---|---|---|
| `recipes` | businessId, цель: menuItemId XOR prepProductId (полуфабрикат = `food_products.isPrepared`), currentVersionId | У блюда и полуфабриката не больше одной активной техкарты |
| `recipe_versions` | recipeId, number, outputQty + unit, technology text, status DRAFT/ACTIVE/ARCHIVED, createdBy | **Версии неизменяемы после активации**; историческая себестоимость не переписывается |
| `recipe_lines` | versionId, productId (ингредиент или полуфабрикат), bruttoQty, nettoQty | Потери выводятся из брутто/нетто, не хранятся; циклы вложенных рецептур запрещены проверкой на сохранении |
| `cost_snapshots` | versionId, locationId, расчётная себестоимость, basis (из каких партий), computedAt | Плановая (по техкарте и текущим партиям FIFO) и фактическая (по реальным списаниям) раздельно, требование ТЗ §3 |

### 3.4 Заказы кухни и KDS (FS5)

| Сущность | Ключевые поля | Правила |
|---|---|---|
| `kitchen_stations` | locationId, name, sortOrder, active | Горячий цех, холодный цех, бар как станции |
| `kitchen_orders` | locationId, number (счётчик филиала), tableId?, reservationId?, comment, status, creationKey, createdBy | Статусы NEW → ACCEPTED → COOKING → READY → SERVED, отмена из нетерминальных; переходы по образцу `foodNext` |
| `kitchen_order_items` | orderId, menuItemId, qty, stationId, status, **снимок** price, recipeVersionId, cost | Списание ингредиентов одним событием по Q-KITCHEN-5, идемпотентно, со сторно |

Оплат, фискализации, связи с кассой и доставкой в v1 нет.

| Срез | Содержание | Доказательства приёмки |
|---|---|---|
| **FS1 Меню** | Модель §3.1, миграция, CRUD API (`/food-service/menu/*`, возможность `food.kitchen`, чтение `desk`, запись `settings`), раздел «Кухня» в меню ресторана, вкладка «Меню»: категории, карточки блюд, стоп-лист, поиск | unit домена, integration на настоящей PostgreSQL (RLS, триггеры, down), UI-спек с axe в двух темах 1440/390, red до реализации |
| **FS2 Склад** | Модель §3.2, приход/партии/движения/списание/инвентаризация, вкладки «Ингредиенты» и «Склад» | те же классы тестов плюс мутации инвариантов (минус, повторное проведение, сторно) |
| **FS3 Техкарты** | Модель §3.3 без снимков себестоимости: версии, брутто/нетто, полуфабрикаты, запрет циклов, редактор техкарты | red/green на цикл, неизменяемость активной версии, пересчёт выхода |
| **FS4 Калькуляция** | `cost_snapshots`, экран калькуляции (себестоимость, фудкост, наценка, маржа, как на макете), пересчёт при новых приходах | сверка расчёта на фикстуре из ТЗ (Стейк Рибай), план/факт раздельно |
| **FS5 Заказы и KDS** | Модель §3.4, минимальный заказ в стойке, экран KDS по станциям, списание по «Готово» строго один раз, сторно при отмене | конкурентные тесты двойного списания, идемпотентность по ключу, статусная машина |
| **FS6 Отчёты** | Фудкост за период, валовая прибыль, топ блюд, списания и недостачи; в разделы отчётов вертикали (ADR-MV9) | сверка контрольных сумм с лентой движений, ноль расхождений |
| **FS7 Печать и доводка** | PDF техкарты, экспорт Excel, журнал изменений, фото блюд (вопрос хранилища решается тут), мобильная полировка по макету | печатная форма тестом, визуальные эталоны |

Порядок жёсткий: FS2 не начинается до приёмки FS1, FS5 требует FS1 (меню) и FS3 (списание
по рецептуре), но может идти без FS4. Каждому срезу свой ADR при утверждении.

## 5. Границы (что НЕ делается в FS1-FS7)

- Оплата заказов, касса, фискализация, счета: заказ кухни не создаёт денежных документов.
- Доставка, агрегаторы, онлайн-заказ гостя, НДС, модификаторы, весовые продажи.
- Гостиничный бар не трогается ни полем, ни триггером (Q-KITCHEN-1 А, Q-KITCHEN-8).
- Property, фонд 88, тарифы, Channex, eQonaq не затрагиваются вовсе.
- Миграции на рабочей базе применяет владелец (AGENTS.md §15, §18).

## 6. Риски

- Два раздела модели уже носят номер §31: новый раздел нумеровать по факту на день правки.
- `food_supplier_payments` зависит от того, есть ли касса у ресторанного филиала; если нет,
  оплата поставщику откладывается внутрь FS6 отдельным вопросом, приход работает без неё
  (инвариант 4 §27 это и позволяет).
- Фото блюд: единое хранилище сейчас только у конструктора сайта (лицензия) и
  `property_media` (гостиница); для кухни вопрос решается в FS7, FS1 живёт без фото.
