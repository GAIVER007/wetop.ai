## 1. Чеки и файлы расходов (Q-MKT-FILES, ТЗ §8.6)

**Вопрос владельцу:** хранить ли чеки в том же закрытом хранилище, что фото объекта и фото блюд.

| Вариант | Что это | За | Против |
|---|---|---|---|
| **А (рекомендую)** | Та же связка, что `property_media` (§32.3) и фото блюд (§37): закрытое хранилище `SITE_ASSET_STORAGE=s3`, обработка `processSiteImage` | Готово и проверено дважды; один выключатель хранилища на всё | Без включённого хранилища на сервере загрузка честно отвечает «Хранилище файлов не включено» |
| Б | Своё отдельное хранилище документов | Можно разные сроки хранения | Новый ключ, новая настройка сервера, вторая копия того же кода |

### 1.1 Таблица `marketing_expense_files` (вариант А)

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid PK | |
| `expense_id` | FK → marketing_expenses (**CASCADE**) | расход, к которому приложен файл |
| `location_id` | FK → locations (RESTRICT) | филиал расхода; RLS той же цепочкой, что §41.1 |
| `file_name` | `varchar(200)` | имя файла для показа |
| `mime_type` | `varchar(40)` | `image/webp` или `application/pdf` |
| `storage_ref` | `varchar(500)` UNIQUE | `marketing-expense-files/<location_id>/<id>/<sha256>.webp\|pdf`, CHECK выводит из строки целиком (как §32.3) |
| `byte_size` | `int` CHECK 1..10 485 760 | до 10 МБ |
| `width`, `height` | `int` NULL | у PDF пусто |
| `sha256` | `char(64)` | |
| `created_by_id` | FK users SET NULL | |
| `created_at` | `timestamptz` | |

- Принимается фото (JPEG, PNG, WebP → WebP без EXIF, длинная сторона до 2400; HEIC с iPhone общая обработка
  `processSiteImage` не узнаёт, его телефон обычно отдаёт как JPEG при загрузке) и PDF (только если начинается с
  `%PDF-`), как у договора объекта.
- UNIQUE `(expense_id, sha256)`: повтор того же файла к тому же расходу это тот же файл. Не больше 10 файлов
  на расход проверяет API.
- **Почему CASCADE, а не `deleted_at`, как у §32.3:** сам расход по §41.1 удаляется физически (это учётная запись
  оператора, не финансовый документ), и строки файлов без расхода не имеют смысла. Удаление файла и расхода
  пишется в журнал аудита; объект в хранилище при этом остаётся (как у `site_assets` и §32.3), так что чек
  восстановим по журналу. Отдельное удаление одного файла тоже физическое, с записью в журнал.
- RLS `rls_tenant` через филиал → бизнес → организация (`app_current_org()`), права
  `SELECT, INSERT, DELETE` без `UPDATE` (файл не правится, только заменяется) отдельной миграцией.
- Откат `down.sql` снимает таблицу, объекты в хранилище остаются.

### 1.2 Экран и API (после утверждения)

`POST /marketing/expenses/:id/files` (multipart, право как у расходов) и `DELETE .../files/:fileId`. Файлы приходят
в ответе месяца `GET /marketing/budget` с подписанными адресами на время, как у фото объекта (§32.3): отдельного
чтения нет (уточнено при реализации 16.10.2026). В форме расхода блок «Чеки и файлы»: список, «Добавить
файл», удаление с подтверждением; в журнале у строки значок скрепки с числом файлов.

## 2. План бюджета по каналам (этап МКТ-В7, «план по каналам»)

Сейчас план один на месяц (`marketing_budgets`, §41.2). ТЗ просит план по каналам и «план против факта».

### 2.1 Таблица `marketing_budget_lines`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uuid PK | |
| `location_id` | FK → locations (RESTRICT) | |
| `month` | `DATE` CHECK (первое число месяца) | |
| `platform` | enum `MarketingPlatform` | тот же список каналов, что у расходов |
| `amount` | `bigint` CHECK > 0 | план канала в валюте отчётности, minor units |
| `created_at`, `updated_at` | `timestamptz` | |

UNIQUE `(location_id, month, platform)`. RLS как §41.1; права `SELECT, INSERT, UPDATE, DELETE` (канал можно
убрать из плана).

### 2.2 Как сочетается с общим планом месяца (развилка, нужен ответ)

| Вариант | Правило |
|---|---|
| **А (рекомендую)** | Общий план месяца остаётся главным. Планы каналов это его разбивка: экран показывает «распределено N из M» и «не распределено», превышение суммы каналов над общим планом **предупреждает, но не запрещает**. Без общего плана сумма каналов и есть план месяца |
| Б | Общий план считается только как сумма каналов; отдельная строка `marketing_budgets` перестаёт вводиться |

Вариант А не ломает ничего уже сделанного (обзор, прогноз, рекомендация считаются от общего плана) и не
заставляет расписывать каналы тем, кому это не нужно.

### 2.3 Что считается из этого (не хранится)

План против факта по каждому каналу: учтённый расход канала (`counted_in_budget`) против плана канала, остаток,
прогноз конца месяца канала тем же правилом, что у месяца. Копирование плана с прошлого месяца одной кнопкой.

## 3. Права маркетинга (Q-MKT-ROLES, ТЗ §3)

Сейчас маркетинг закрыт правом `settings` (44 маршрута API; ещё 2 маршрута диалогов на праве `dialogs`), то есть
владелец и управляющий. Отдельной роли маркетолога нет:
нанятому маркетологу пришлось бы давать роль управляющего, а с ней тарифы, номерной фонд, сотрудников.

| Вариант | Что меняется | За | Против |
|---|---|---|---|
| **А (рекомендую сейчас)** | Новое **право** `marketing` в таблице §16.5 (не роль): весь раздел «Маркетинг» и «Продвижение» переходит с `settings` на `marketing`. У владельца и управляющего оно есть, у администратора нет. Схема базы не меняется | Одна строка в домене и замена права на маршрутах; поведение для людей сегодня не меняется | Маркетолога по-прежнему некуда пригласить отдельно |
| Б | Вариант А **плюс новая роль** `MARKETER` «маркетолог» в §16.1: права `self`, `marketing`, `reports`. Меняется CHECK `memberships.role` и `invites.role`, миграция | Можно пригласить маркетолога без доступа к броням, тарифам и деньгам | Правка ролей организации: миграция, приглашения, экран сотрудников |
| В | Ничего не менять | | Маркетолог только через роль управляющего |

«Оператор» из ТЗ §3 у нас уже есть: это администратор (диалоги ИИ-продавца и работа с гостями). Рекомендую А
сейчас и Б, когда появится первый маркетолог, которого нужно пригласить: тогда это одна строка права роли.

## 4. Порядок после утверждения

1. Перенос разделов в `DATA_MODEL.md`, ADR в `DECISIONS.md`, закрытие Q-MKT-FILES и Q-MKT-ROLES.
2. Право `marketing` (если А или Б): домен, маршруты, `route-access.test.ts`, меню; без миграции.
3. Миграции `marketing_expense_files` и `marketing_budget_lines` с правами отдельными миграциями; на рабочей базе
   применяет владелец.
4. API и экран: чеки в форме расхода, план по каналам на обзоре бюджета.
5. Доказательства: unit домена и сервиса, integration на PostgreSQL (RLS, CASCADE, UNIQUE), UI-спек с axe.
