# MKT5: бриф сайта (Site Brief v0), план и итог

Ветка `claude/sharp-dirac-6s46fw`, перезапущена от `main` `012c06d8` (PR #262). MKT4 (PR #260) влит: голова
`a8d78c9f` и слияние `f79281ff` входят в историю `main`. ТЗ владельца «WETOP MKT5, Site Brief» от 07.10.2026.

## 1. Что делаем

Детерминированный бриф будущего сайта филиала. Он собирается на чтении из того, что уже есть в WETOP, и станет входом
MKT6 (генерация `SiteSpec` моделью). В MKT5 модель не вызывается, ничего не сохраняется, сайт не создаётся.

Поток: строгий scope филиала → данные платформы → белый список профиля продавца → контент Channex (если подключён) →
нормализация и происхождение → найдено, нет, источник недоступен, расхождения → предлагаемая структура → `briefHash`.

## 2. Не делаем

ИИ и `apps/ai-seller`, `GenerationRun`, очередь, генерацию `SiteSpec`, версию сайта, публикацию, превью, домены,
`SiteAsset`, импорт фото, редактор, выкладку Worker, DNS. Модель данных не меняется: ни `schema.prisma`, ни миграций,
ни RLS, ни таблицы для брифа. Q-274 остаётся открытым.

## 3. Источники

| Источник | Откуда | Чтение |
|---|---|---|
| Платформа | филиал scope → его Business → его объект (`properties.location_id`) | одна транзакция чтения |
| Категории | активные `accommodation_types` этого объекта + число активных `inventory_units` | та же транзакция |
| Профиль продавца | `seller_agents` той же организации, `location_id` = филиал scope, `scenario = 'sales'`, не `archived`; его `seller_profiles` | та же транзакция, `select` только полей белого списка |
| Channex | `channel_mappings` этого объекта, провайдер `channex` → `providerPropertyId` | id читается в транзакции, HTTP после её закрытия |

Никакого «первого объекта организации», `agentId = organizationId`, первого агента организации, мастера-черновика,
`LUXX_APARTS_PROPERTY`. Строка `MarketingSite` не нужна и не читается.

## 4. Белые списки

- **Location:** `name`, `address`, `phone`, `email`, `timezone`, `currency`.
- **Property:** `name`, `address`, `city`, `countryCode`, `channexPropertyType`, `timezone`, `currency`, `checkInTime`,
  `checkOutTime`. Не берутся: id, `organizationId`, `legalName`, `bin`, даты, связи. `phone` и `email` объекта в бриф не
  попадают вовсе: это контакты печатных форм, а не утверждённые публичные контакты сайта.
- **Категория:** `code`, `name`, `kind`, `capacityAdults`, `activeUnits` (число активных мест). Без id, комнат, мест,
  уборки, блокировок, броней. `activeUnits` это вместимость фонда, а не свободные места сейчас.
- **Профиль продавца:** `languages` (подсказка языков сайта: пересечение с `ru`, `kk`, `en` в порядке продавца),
  `includedInPrice`, `extraCharges`, `houseRules`, `faq`.
- **Channex, объект:** `title`, `description`, `importantInformation`, `phone`, `email`, `website`, `address`, `city`,
  `country`. **Правила:** `checkInTime`, `checkOutTime`, `maxGuests`, `pets`, `smoking`, `internet`, `parking`.
  **Удобства:** `title`, `category`. **Фото:** только сводка `photoSummary { total, propertyPhotos, roomTypePhotos,
  descriptions }`, адресов фото нет.

## 5. Что исключено

Профиль продавца: `promptText`, инструкция агента, `botName`, `addressForm`, `emoji`, `replyLength`, `greeting`,
`prohibitions`, `callHumanWhen`, служебные поля (`profileAppliedAt`, `factsHash`, `factsAppliedAt`, `lastError`,
`lastErrorAt`, `updatedBy`), `seller_agents.profile`, мастер (`description`, источники, `generatedPrompt`,
`generatedKnowledge`), диалоги и сообщения. Эти колонки репозиторий не выбирает вовсе. Инструкция продавца не контент
сайта, даже если похожа на описание.

Channex: id провайдера и сопоставлений, ключ, заголовки, сырой ответ, адреса фото, тексты ошибок провайдера.

Не читаются никогда: гости, документы, брони, счета, платежи, возвраты, касса, членства, пользователи, сотрудники,
диалоги продавца и поддержки.

## 6. Старшинство

- Платформа главная: имя филиала, объект, пояс, валюта, время заезда и выезда, категории, вместимость, `activeUnits`.
- Телефон и почта: филиал; Channex только если поле филиала пустое.
- Адрес: филиал → объект → Channex.
- Город: объект → Channex. Страна: объект → Channex (только код из двух латинских букв).
- Кандидат названия `displayNameCandidate`: название Channex, иначе филиал, иначе объект. Это кандидат, а не
  переименование; при заметном расхождении с обоими названиями платформы пишется расхождение.
- Тексты Channex и профиля продавца хранятся отдельными блоками и не перезаписывают друг друга.

## 7. Расхождения

Только детерминированное сравнение: обрезка краёв, схлопывание пробелов, нижний регистр; телефон по цифрам; время в виде
`ЧЧ:ММ`. Коды: `address_mismatch`, `checkin_mismatch`, `checkout_mismatch`, `email_mismatch`, `name_mismatch`,
`phone_mismatch`. Значение платформы остаётся главным, Channex попадает в `otherValue`. Если поле филиала пустое и
взято из Channex, расхождения нет.

## 8. Найдено, нет, источник недоступен

`found`, `missing`, `sourceUnavailable` и `conflicts` сортируются по коду. Состояния Channex `NO_KEY` и `NO_MAPPING`
означают «Channex не подключён»: то, что мог дать только он, честно отсутствует. `DENIED`, `NOT_FOUND`,
`RATE_LIMITED`, `UNREACHABLE` означают «не проверить сейчас»: такие факты не попадают в `missing`, а источник уходит в
`sourceUnavailable`. Ответ при этом 200, данные платформы на месте.

## 9. Предлагаемая структура

Не `SiteSpec` и не текст. Одна главная страница, секции в порядке: `hero` (всегда), `about` (есть описание или важная
информация Channex), `accommodations` (есть активные категории), `pricing` (есть категории; привязка `B-FROMPRICE`),
`amenities` (есть удобства Channex или «что входит в цену» продавца), `gallery` (есть фото; требует
`MKT8_MEDIA_IMPORT`), `faq` (есть вопросы продавца), `booking` (способность гостиницы; требует `MKT7_TRACKED_SITE`),
`contacts` (есть адрес, телефон или почта), `cta` (всегда). `features` в v0 не предлагается: отдельного источника
преимуществ, кроме удобств, нет, а сочинять «Преимущества» нельзя.

## 10. `briefHash`

`sha256(canonicalJson({ schemaVersion, input, missing, conflicts, proposedStructure }))`, нижний регистр, тот же
`canonicalJson`, что у хэша версии сайта. Не входят: `collectedAt`, `checkedAt` Channex, тексты ошибок, состояния
источников, `sourceUnavailable`, `found` (выводится из `input`), сведения об усечении.

## 11. Пределы текстов

Описание 4000, важная информация 2000, удобств 50, название удобства 120, категория удобства 60, подписей фото 20 по
200, сайт 300, название Channex 200, адрес 500, город 100, строки правил 200. Поля продавца режутся по его же пределам
(`SELLER_PROFILE_LIMITS`). Усечение по символам, детерминированное; в метаданных `truncations` поле, источник и
исходная длина, сам исходный текст не хранится.

## 12. Граница с ИИ

`input` это только данные, которые MKT6 может передать модели как DATA. `collectedAt`, состояния, ошибки,
`truncations` и прочая диагностика вне `input`. MKT6 не сериализует ответ целиком в промпт и не строит из этих строк
системную инструкцию: текст Channex и владельца это непроверенные данные (в том числе «ignore previous instructions»).

## 13. API

`GET /marketing/site/brief`, право `settings`, строгий scope MKT3 (`siteScope`, `siteTransaction` на чтение):
без филиала 409 «Выберите филиал», чужой, устаревший или архивный указатель 403, салон и ресторан 403. `?refresh=1`
только обходит кэш Channex на 10 минут. Ничего не пишет, журнал на чтение не ведётся.

## 14. Тесты

Red → green: домен (нормализация, белые списки, сторожевые строки, языки, Channex, фото, старшинство, расхождения,
`found`/`missing`/`sourceUnavailable`, структура, сортировка, хэш, усечение); API unit (форма, `refresh`, отказ
Channex); integration (scope, чужой филиал, чужой продавец, чужой Channex, сторожевые строки ПД, без записи, без
`MarketingSite`). Затем typecheck, lint, полный unit и integration, регрессия MKT4.
