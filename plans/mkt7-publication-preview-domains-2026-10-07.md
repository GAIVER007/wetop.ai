# MKT7: превью, публикация, домены и откат управляемого сайта (07.10.2026)

ТЗ владельца 07.10.2026 «WETOP MKT7 — PUBLICATION» после слияния MKT6 (PR #274, `df0af4b0`). Ветка
`claude/sharp-dirac-6s46fw` заново от свежего `main` `867a3914` (#278, только главная wetop.ai; MKT6 внутри). Последняя
миграция на `main`: `20261007000063_generation_run_grants`, значит MKT7 берёт **064** (схема и данные) и **065** (права).

Поток: `MarketingSiteVersion → превью → SiteDomain платформы → TrackedSite → публикация → рантайм Worker → пауза и
возобновление → новый черновик и повторная публикация → откат → архив`. Заодно закрываются Q-271 и Q-275 (решения
владельца 07.10.2026). После черновика PR стоп: MKT8, MKT9, MKT10 не начинаются.

## 1. Решения владельца, которые срез записывает

**Q-271 RESOLVED OWNER 07.10.2026.** Сайты клиентов живут на отдельном регистрируемом домене `SITES_BASE_DOMAIN`, не
под `wetop.ai`. Платформенный адрес `<slug>.<SITES_BASE_DOMAIN>`, превью `preview.<SITES_BASE_DOMAIN>`. Worker
Cloudflare сам origin; wildcard DNS и маршрут это инфраструктура, а не действие публикации. Свои домены клиентов в
MKT10 через Cloudflare for SaaS (Custom Hostnames); своего ACME нет.

**Q-275 RESOLVED OWNER 07.10.2026, вариант B.** У филиала гостиницы один явный канонический сайт брони
`locations.booking_tracked_site_id`. ИИ-продавец берёт только его и проверяет: тот же объект, `ACTIVE`, бронь включена,
тариф задан. Иначе котировки нет, запасного «самого раннего» нет. Перенос ставит указатель только при ровно одном
подходящем сайте. Публикация управляемого сайта никогда молча не заменяет уже выбранный внешний.

## 2. Модель (DATA_MODEL §29.4, §29.6 становятся «в базе с MKT7», новый §29.11 указатель брони)

Миграция `20261007000064_marketing_publication_domains` (с `down.sql`):

- enum `SitePublicationAction` (`PUBLISH`, `ROLLBACK`, `PAUSE`, `RESUME`, `ARCHIVE`), `SiteDomainKind`
  (`PLATFORM_SUBDOMAIN`, `CUSTOM`), `SiteDomainStatus` (`PENDING`, `VERIFYING`, `VERIFIED`, `ACTIVE`, `FAILED`,
  `REMOVED`), `SiteDomainVerificationMethod` (`DNS_TXT`, `HTTP_FILE`);
- `marketing_site_publications` по §29.4. CHECK формы: `PUBLISH`, `ROLLBACK`, `RESUME` с версией, `PAUSE` и
  `ARCHIVE` без. Триггер `marketing_site_publication_guard`: версия и прежняя версия только своего сайта. Триггер
  `marketing_site_publication_immutable`: `UPDATE` и `DELETE` запрещены, кроме обнуления `actor_id` по
  `ON DELETE SET NULL` (тот же узкий проход, что у версий);
- `site_domains` по §29.6. CHECK: хост в нормальном виде (нижний регистр, без порта и точки в конце, до 253 знаков),
  у платформенного поддомена нет способа проверки, токена и `verified_at`, `ACTIVE` с `activated_at`, `REMOVED` с
  `removed_at`. Частичные UNIQUE: хост среди строк не `REMOVED` и не `FAILED`; один основной на сайт среди не
  `REMOVED`. Триггер `site_domain_guard`: сайт, хост и вид не меняются, переходы по §29.8 (у платформы только
  `PENDING → ACTIVE`, `ACTIVE | PENDING → REMOVED`), `REMOVED` конечный;
- `locations.booking_tracked_site_id` UUID NULL → `tracked_sites` `ON DELETE SET NULL`. Триггер
  `location_booking_site_guard`: сайт брони только объекта этого же филиала;
- перенос: каждому филиалу `HOSPITALITY` ставится единственный подходящий сайт объекта (`ACTIVE`, бронь, тариф); ноль
  или больше одного оставляют NULL; «самый ранний» не выбирается;
- RLS FORCE на обе таблицы через сайт (как версии), функции с закреплённым `search_path`.

Миграция `20261007000065_marketing_publication_grants`: только GRANT и REVOKE (её повторяет восстановление копии).
Журнал публикаций: `SELECT, INSERT` у `wetop_app` и `wetop_service`, `UPDATE, DELETE` отозваны. Домены: `SELECT,
INSERT, UPDATE`, `DELETE` отозван (снятие это `REMOVED`).

## 3. Домен (`packages/domain/src/marketing/`)

- `host.ts`: один нормализатор хоста для API управления, рантайма и Worker (Worker импортирует файл напрямую, в нём
  нет зависимостей): нижний регистр, без схемы и порта, без точки в конце, IDN в punycode через WHATWG `URL`, до 253;
  `normalizeSiteHost` из `runtime.ts` переезжает сюда без смены поведения для ASCII;
- `parseSitesBaseDomain`: только имя хоста, не `wetop.ai` и не его поддомен; `platformHost(slug, base)`,
  `previewHost(base)`;
- `siteSpecMediaPaths(spec)`: ссылки на медиа (`assetId`, `imageAssetId`, `faviconAssetId`, `logo`, `image`,
  `images`, секция `gallery`), публикация до MKT8 их отклоняет кодом `MEDIA_NOT_READY`.

## 4. API управления (`/marketing/site/*`, право `settings`, строгий scope MKT3)

| Маршрут | Что делает |
|---|---|
| `POST /preview` `{ versionId }` | подписанная ссылка на 60 минут: `https://preview.<base>/?token=…`; без секрета или базы 503 |
| `POST /publish` `{ expectedVersionId, bookingRatePlanId? }` | публикует только `latest_version_id`; повтор той же версии без второй строки журнала |
| `POST /pause`, `POST /resume` | только из `PUBLISHED` и только из `PAUSED`; возобновление перепроверяет версию, категории, домен и тариф |
| `POST /rollback` `{ versionId }` | только ранее опубликованная версия своего сайта; `latest_version_id` не меняется |
| `POST /archive` | из любого неархивного; домены `REMOVED`, сайт счётчика `PAUSED`, хосты сняты, указатель брони снят, если был на нём |
| `GET /publications` | журнал без документа |
| `GET /booking-source`, `PUT /booking-source` `{ trackedSiteId }` | канонический сайт брони филиала: варианты только точного объекта, выбрать можно только подходящий, `null` снимает |

Порядок тарифа для `WETOP_WIDGET` (публикация): явный `bookingRatePlanId` (только точный объект и активный) → тариф уже
связанного управляемого сайта → тариф канонического сайта брони филиала → 409 `BOOKING_RATE_PLAN_REQUIRED`. Первый
активный, самый дешёвый, `BASE` и `defaultBookingRatePlan()` не используются. Заданный, но уже недействующий тариф
даёт 409, а не переход к следующему источнику. Откат и возобновление идут тем же порядком без явного тарифа.

Первая публикация одной транзакцией под замком филиала и сайта: проверка версии (валидатор, схема, хэш, медиа,
категории точного объекта активны), домен платформы `PENDING → ACTIVE`, новый `TrackedSite` (новый ключ `pms_…`,
никогда не чужой внешний), хосты, бронь по документу, указатель брони только если его нет и других подходящих сайтов
у объекта нет, `published_version_id`, состояние, строка журнала, `audit_logs`. Публикация на паузе меняет версию,
но сайт остаётся на паузе.

## 5. Превью

Токен без JWT-библиотеки: `base64url(JSON {v:1, siteId, versionId, exp}) + "." + base64url(HMAC-SHA256)`, секрет
`SITE_PREVIEW_SECRET` (не короче 32 байт; нет или короткий: превью закрыто), сравнение подписи `timingSafeEqual`, срок
ровно 60 минут, в будущем не дальше 24 часов. `GET /sites-runtime/preview?token=` только ключом рантайма и только с
действующим токеном: читает ровно `versionId` из токена, сайт не в архиве, цепочка филиала действует. Ответ без
публичного ключа, `bookingEnabled = false`; Worker на хосте превью отдаёт `noindex, nofollow`, `private, no-store`,
`Referrer-Policy: no-referrer`, `robots.txt` с `Disallow: /`, без sitemap и canonical. Скриптов WETOP нет вовсе (ключа
нет), значит ни счётчика, ни виджета, ни цены «от», ни брони. Испорченный токен: 404, истёкший: 410, оба нейтрально.
Доводка по ревью владельца (07.10): токен разрешает всю версию, поэтому все внутренние ссылки превью несут его
(`localHref` в `apps/sites/src/render/context.ts`); внешние нет. Worker включает хост превью только при верном
`SITES_BASE_DOMAIN` по `parseSitesBaseDomain`. Сайт счётчика управляемого сайта старым `/analytics` не правится (409
`MANAGED_SITE_READ_ONLY`), его хосты ровно `ACTIVE`-домены.

## 6. Рантайм

`GET /sites-runtime/current`: карта dev и test остаётся вне `production`; иначе хост ищется в `site_domains` со
статусом `ACTIVE`, дальше прежний запрос опубликованной версии. `primaryHost` настоящий; не основной хост Worker
переводит 301 на основной с тем же путём и запросом. Хост архивного сайта, паузы и неизвестный: одинаковый нейтральный
404 (вариант «410 для архива» не берётся: снятый хост не ищется отдельно; так в контракте и документах). Ключ рантайма
открывает ровно два пути: `current` и `preview`.

## 7. ИИ-продавец

`bookingSiteForAgent`: агент → его филиал → `booking_tracked_site_id` → этот сайт, если он того же объекта, `ACTIVE`,
бронь включена и тариф задан; иначе `null`. Сортировки по дате и «первого» больше нет. Тесты, где агент получал сайт по
«самому раннему», явно ставят указатель.

## 8. Стойка

Страница `/marketing/site` (только гостиница, `requireVertical`): состояние, ревизии последняя и опубликованная, адрес
сайта (до публикации «Не опубликован»), «Предпросмотр» (открывает новую вкладку, токен не показывается и не хранится),
«Опубликовать», «Пауза» и «Возобновить», журнал с «Откатить», источник брони для ИИ-продавца (выбор без автоподстановки),
«Архивировать» с вопросом. Редактора нет (MKT9). Подставной API учится тем же маршрутам.

## 9. Проверки (red → green)

База: форма и принадлежность журнала, неизменяемость, домены (принадлежность, основной, уникальность хоста), указатель
брони чужого филиала, перенос (один и неоднозначно), RLS двух организаций, права, откат миграций. Домен: хост, база,
медиа. API и integration: превью (действующий, истёкший, изменённый байт, чужой секрет, чужая версия, ключ без токена,
без брони и счётчика), сценарий §79 ТЗ целиком, Q-275 §80–§83, тарифы §84, гонка двух публикаций, откат (чужая,
неопубликованная, сломанная категория, медиа), состояния сайта в рантайме, 301 на основной. Worker: превью, 301,
регрессия MKT4. UI: страница на 1440 и 390, axe. Полные typecheck, lint, unit, integration, `check-migrations`,
восстановление копии.

## 10. Чего нет

Выкладки, миграций на рабочей базе, DNS, зоны и API Cloudflare, своих доменов, проверки DNS, `SiteAsset`, загрузки
медиа, импорта картинок Channex, редактора, ИИ-правок, сдвига `release`, образа бота. Отмены задач генерации при архиве
нет: воркер MKT6 сам завершает такую задачу `BASE_VERSION_CHANGED`.
