# MKT8: библиотека изображений управляемого сайта (SiteAsset) (07.10.2026)

ТЗ владельца 07.10.2026 «WETOP MKT8 — SITE ASSETS / MEDIA» после слияния MKT7 (PR #283, `89f4e5f7`). Ветка
`claude/sharp-dirac-6s46fw` заново от свежего `main` `89f4e5f726eff42d18e3d1a2f107dbb7b450ce6e` (MKT7 внутри). Последняя
миграция на `main`: `20261007000065_marketing_publication_grants`, значит MKT8 берёт **066** (схема) и **067** (права).

Поток: `загрузка или фото Channex → проверка типа по содержимому → декодирование → снятие EXIF → поворот по ориентации →
уменьшение и перекодирование → SHA-256 → приватный S3 в Казахстане → SiteAsset → проверка ссылок SiteSpec → превью →
публикация → apps/sites выводит картинку`. Снимается общий отказ MKT7 `MEDIA_NOT_READY`. После черновика PR стоп:
MKT9 и MKT10 не начинаются.

## 1. Решение владельца Q-270 (записано в `QUESTIONS.md`)

**Q-270 RESOLVED OWNER 07.10.2026.** Origin медиа сайтов: приватное S3-совместимое хранилище физически в Казахстане.
Первая рабочая конфигурация: PS Cloud Object Storage, но ключи на рабочем сервере не включаются, пока владелец не получит
письменное подтверждение поставщика: проект хранилища, основные данные, реплики и резервные копии поставщика только в
Казахстане. Без подтверждения рабочий поставщик Cloud24 S3 (Алматы). Код и схема от выбора не зависят: только адрес,
бакет, ключи, регион и стиль пути. Cloudflare R2, Supabase Storage, AWS вне Казахстана, иностранный CDN как origin и диск
API как постоянное хранилище не используются (Q-270, ADR-009).

## 2. Что поставщик хранилища НЕ знает и что знает база

`SiteAsset` не знает ни поставщика, ни бакета, ни адреса, ни ключей. В базе только `storage_ref`: непрозрачный ключ
объекта `site-assets/<locationId>/<assetId>/<sha256>.webp` (`.png` у фавиконки). Переезд PS Cloud → Cloud24: переменные
окружения и перенос объектов, схема та же.

## 3. Модель (DATA_MODEL §29.5 «в базе с MKT8»)

Миграция `20261007000066_site_assets` (с `down.sql`):

- enum `SiteAssetKind` (`IMAGE`, `LOGO`, `FAVICON`), `SiteAssetStatus` (`UPLOADING`, `PROCESSING`, `READY`, `REJECTED`,
  `DELETED`), `SiteAssetSource` (`UPLOAD`, `CHANNEX_IMPORT`);
- `site_assets`: `id`, `location_id` → `locations` RESTRICT, `kind`, `status`, `source`, `mime_type` VARCHAR(40),
  `storage_ref` VARCHAR(500) UNIQUE, `byte_size`, `width`, `height`, `sha256` CHAR(64), `default_alt` JSONB NULL,
  `created_by_id` → `users` SET NULL, `created_at`, `updated_at`, `deleted_at`;
- CHECK: хранимый тип только `image/webp` (картинка и логотип) или `image/png` (фавиконка), согласован с видом;
  `storage_ref` строго по шаблону ключа с тем же `location_id`, `id` и `sha256`; размер от 1 байта до 10 МиБ; стороны от 1
  до 2400 (фавиконка ровно 512×512); `sha256` 64 знака hex в нижнем регистре; `default_alt` объект; `DELETED` тогда и
  только тогда, когда `deleted_at` задан;
- частичный UNIQUE `(location_id, kind, sha256) WHERE status <> 'DELETED'`: две одинаковые загрузки дают не больше одного
  живого ассета;
- триггер `site_asset_guard`: вставка без `DELETED`; `id`, `location_id`, `source`, `created_at` не меняются никогда;
  `kind`, `sha256`, `storage_ref`, `mime_type`, `byte_size`, `width`, `height` не меняются после `READY`; переходы
  `UPLOADING → PROCESSING | READY | REJECTED`, `PROCESSING → READY | REJECTED`, `READY → DELETED`, `REJECTED → DELETED`;
  `DELETED` конечный;
- RLS FORCE: политика по цепочке Location → Business → организация (как `marketing_sites`), функция триггера с
  закреплённым `search_path`.

Миграция `20261007000067_site_asset_grants`: только права (их повторяет восстановление копии): `SELECT, INSERT, UPDATE` у
`wetop_app` и `wetop_service`, `DELETE` отозван (удаление это `DELETED`). `site_assets` в `RLS_TENANT_TABLES`.

Состояния `UPLOADING` и `PROCESSING` остаются в модели, но v0 строк в них не заводит: обработка синхронная, строка
появляется сразу `READY` после успешной записи в хранилище; неверный файл строки не создаёт вовсе.

## 4. Домен (`packages/domain/src/marketing/assets.ts`)

- `siteSpecAssetRefs(spec)` → `{ assetId, expectedKind, path }[]` по известным местам документа: `site.brand.logo` →
  `LOGO`, `site.brand.faviconAssetId` → `FAVICON`, `pages[].seo.og.imageAssetId` и картинки секций `hero`, `about`,
  `cta`, `gallery`, `accommodations` → `IMAGE`. Обход по схеме SiteSpec, а не по любым ключам;
- `sniffImageType(bytes)`: JPEG, PNG, WebP по сигнатуре; SVG, GIF, AVIF, HEIC, TIFF, BMP, PDF, HTML, XML дают null;
- `parseAssetKind`, `parseDefaultAlt` (ru, kk, en, до 150 знаков, те же правила обычного текста, что у SiteSpec);
- `siteAssetStorageKey(locationId, assetId, sha256, kind)`; константы пределов (10 МиБ, 40 000 000 точек, сторона
  12 000, 2400, 1600, 512, качество WebP 82).

`siteSpecMediaPaths` (общий отказ MKT7) удаляется вместе с использованием.

## 5. Хранилище (`apps/api/src/marketing-site/asset-storage.ts`)

Интерфейс без поставщика: `put`, `delete`, `signedGet`, `exists`. Реализация `S3SiteAssetStorage` на
`@aws-sdk/client-s3` и `@aws-sdk/s3-request-presigner` (своей подписи нет); контрольные суммы только когда требует
сервер (`WHEN_REQUIRED`): S3-совместимые поставщики не обязаны понимать новые заголовки AWS. Память
(`MemorySiteAssetStorage`) для тестов. Переменные:

```
SITE_ASSET_STORAGE=off|s3            # по умолчанию off
SITE_ASSET_S3_ENDPOINT=              # https://… (http только 127.0.0.1/localhost)
SITE_ASSET_S3_REGION=
SITE_ASSET_S3_BUCKET=
SITE_ASSET_S3_ACCESS_KEY_ID=
SITE_ASSET_S3_SECRET_ACCESS_KEY=
SITE_ASSET_S3_FORCE_PATH_STYLE=0|1
SITE_ASSET_SIGNED_URL_TTL_SECONDS=3600   # от 900 до 86400
```

Закрыто по умолчанию: `off`, неполные или неверные значения дают «хранилища нет». Тогда метаданные библиотеки читаются,
загрузка и импорт отвечают 503 `ASSET_STORAGE_UNAVAILABLE`, публикация, возобновление, откат и превью версии со
ссылками на ассеты 503 тем же кодом; ни диска, ни R2, ни Supabase в запасе нет.

## 6. Обработка картинки (`asset-image.ts`, `sharp`)

Только через API в Казахстане, без presigned PUT: браузер → API → проверка и обработка → S3. Сырой файл в памяти
процесса (multer, `memoryStorage`, один файл, предел 10 МиБ на маршрут, общий JSON-парсер не трогается) и нигде больше:
ни в S3, ни в базе, ни во временном файле.

1. тип по сигнатуре (не по расширению и не по `Content-Type`), должен совпасть с форматом, который увидел декодер;
2. многостраничное и анимированное отклоняется; стороны не больше 12 000, точек не больше 40 000 000
   (`limitInputPixels`);
3. поворот по EXIF в пиксели (`rotate()`), метаданные не переносятся (ни EXIF, ни GPS, ни ICC-профиль с данными камеры);
4. `IMAGE` → WebP, длинная сторона до 2400 без увеличения; `LOGO` → WebP до 1600 с прозрачностью; `FAVICON` → PNG
   512×512: вписать без растяжения и без увеличения, дополнить прозрачными полями;
5. SHA-256 от готовых байтов.

Коды: 415 `UNSUPPORTED_MEDIA_TYPE`, 413 `FILE_TOO_LARGE`, 422 `IMAGE_TOO_LARGE`, 422 `IMAGE_DECODE_FAILED`.

## 7. API управления (`/marketing/site/assets*`, право `settings`, строгий scope MKT3)

| Маршрут | Что делает |
|---|---|
| `GET /marketing/site/assets` | библиотека филиала без `DELETED`; `previewUrl` подписан на TTL, `storage_ref` не отдаётся |
| `POST /marketing/site/assets` | `multipart/form-data`: `file`, `kind`, необязательно `defaultAlt` (JSON). 201 новый, 200 тот же при повторе |
| `PATCH /marketing/site/assets/:id` | только `{ defaultAlt }` (объект или null) |
| `DELETE /marketing/site/assets/:id` | логическое удаление; ответ `retainedForPublishedHistory` |
| `GET /marketing/site/assets/channex` | фото Channex объекта этого филиала: `photoId` = sha256 адреса, описание, для номера ли, порядок; адресов нет |
| `POST /marketing/site/assets/channex/import` | `{ photoIds: [...] }` до 20; сервер заново читает фото и сам сопоставляет; `{ imported, failed }` |

Филиал только из scope; организация, бизнес, филиал и сайт из тела не принимаются. Предел 30 загрузок и импортов на
человека и организацию в час (`RateWindows`, 429). Повтор того же файла того же вида в филиале возвращает тот же ассет и
второй строки не заводит. Гонка: индекс пускает одного, проигравший возвращает победителя и удаляет свой лишний объект
(ключ содержит id, чужой объект не задевается). Запись в S3 не удалась: строки нет. Строка не записалась после S3: свой
объект удаляется, сбой удаления пишется в лог без ключа.

## 8. Удаление и история публикаций

`assetUsedByPublishedHistory(tx, assetId, locationId)`: версии сайтов этого филиала с записью журнала `PUBLISH`,
`ROLLBACK` или `RESUME` разбираются приложением (`siteSpecAssetRefs`), не поиском строки в JSON. Ассет хоть раз
опубликованной версии физически не удаляется: из библиотеки уходит, текущий сайт и откат продолжают видеть картинку.
Ассет только из черновиков: после `DELETED` объект удаляется (сбой не возвращает ассет, пишется предупреждение).

Гонка удаления и публикации: удаление держит строку ассета `FOR UPDATE`, проверка версии берёт ассеты `FOR SHARE` и
читает их состояние под замком. Публикация после удаления видит `DELETED`; удаление после публикации видит её запись в
журнале и объект оставляет.

## 9. Проверка ссылок версии

| Где | Правило |
|---|---|
| сохранение версии | каждая ссылка: ассет этого филиала, `READY`, ожидаемый вид; иначе 409 `ASSET_UNAVAILABLE` с путями, версия не сохраняется |
| публикация новой версии | то же, `READY` |
| публикация ранее опубликованной головы, возобновление, откат | версия «историческая» (есть запись журнала): годится и `DELETED` удержанный ассет, если объект существует (`exists` только для `DELETED`) |
| выдача ссылки превью | обычная версия только `READY`; историческая и удержанные `DELETED` |
| рантайм `current` и `preview` | карта `assets` только по ссылкам этой версии, только ассеты филиала сайта и нужного вида; подписанные GET |

Чужой ассет и несуществующий неотличимы: один код, без владельца. MKT6 не меняется: генерация по-прежнему без ассетов.

## 10. Рантайм и Worker

`GET /sites-runtime/current` и `preview` заполняют `assets: { "<assetId>": "<подписанный GET>" }` только по ссылкам
текущей (или превью) версии. Отдельного `/sites-runtime/assets/:id` нет. Подпись TTL 3600 с, это заметно больше кэша
страницы (60 с) и устаревшей копии контракта (10 мин); в базе подписи нет. Worker принимает адрес ассета только `https:`,
с хостом, без логина, не localhost и не IP; иначе адрес выбрасывается и пишется в лог. В `img-src` добавляются ровно
origin-ы фактических адресов (ни `https:`, ни `*`); в `script-src`, `connect-src`, `frame-src` они не попадают. Без
ассетов политика прежняя. Логотип в шапке, фавиконка `<link rel="icon">` и `og:image` выводятся из той же карты.

## 11. Импорт из Channex и защита от SSRF

Объект только этого филиала (тот же путь, что у брифа MKT5). Браузер присылает только `photoId`; адрес берёт сервер
из свежего ответа Channex. Загрузчик: только `https:`, без логина, порт 443, IP-адрес в адресе не принимается; имя
разрешается до соединения, все адреса должны быть публичными (не loopback, не RFC1918, не link-local, не CGNAT, не ULA и
не прочие служебные), соединение идёт ровно на проверенный адрес; до 3 переадресаций, каждая проверяется заново; 10 с на
весь путь; тело до 10 МиБ (длиннее рвётся); `Content-Type` не учитывается, содержимое проходит ту же обработку, что
загрузка. `img.channex.io` годится как любой публичный адрес. Ошибки по фото: `{ photoId, code }` без тела ответа.

## 12. Журнал и логи

`marketing.site.asset.uploaded`, `.imported`, `.alt_changed`, `.deleted`: id, вид, источник, тип, размер, стороны,
sha256, `retainedForPublishedHistory`. Никогда: байты, подписанный адрес, ключ объекта, секреты, адрес Channex.

## 13. Стойка

`/marketing/site/assets` «Изображения сайта»: сетка карточек (картинка по подписанному адресу, вид, размер, стороны,
источник, ALT), загрузка с выбором вида (и перетаскиванием), подсказка 10 МиБ, ошибки словами, «Импорт из Channex»
(список фото с выбором), удаление с подтверждением и честным текстом про историю публикаций. Редактора страниц нет
(MKT9). Ссылка со страницы «Публикация сайта».

## 14. Проверки (RED → GREEN)

Домен (ссылки, сигнатуры, ALT), обработка (EXIF и GPS из настоящего файла с GPS и ориентацией, поворот, уменьшение,
фавиконка, бомба точек, анимированный WebP, обрезанный JPEG, SVG под видом PNG, HTML под видом JPG, случайные байты,
10 МиБ + 1, нормализованный SHA), хранилище (S3 адаптер против подставного клиента, память), загрузчик (SSRF), API на
настоящей базе (загрузка, повтор, гонка, удаление с историей и без, откат с удержанным `DELETED`, импорт с точным
объектом, сохранение версии, публикация, превью, рантайм только своих ссылок, чужой филиал), миграции (применение,
откат, повтор, восстановление копии), Worker (CSP, адреса, вывод), UI с axe. Затем полные наборы и образ Docker с
пробной обработкой внутри контейнера.

## 15. Не делается

Рабочие бакет, ключи, миграции на рабочей базе, выкладка, перенос настоящих фото, перемотка `release`. Presigned PUT,
несколько размеров и `srcset`, AVIF, кадрирование, выбор картинки в редакторе, автоматическая вставка импортированного
фото в документ (MKT9). Свои домены (MKT10).
