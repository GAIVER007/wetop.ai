# MKT9.2: лицензированный конструктор сайта в духе Lovable

08.10.2026. ТЗ владельца «WETOP MKT9.2: LICENSED LOVABLE SITE BUILDER» (201 пункт). Ветка `claude/sharp-dirac-6s46fw`
заново от `main` `22c6e317` (PR #289 MKT9.1 влит, merge `22c6e317564af56446c46a2cce8eeb123d2a314f`). Последняя
миграция в `main` `20261007000067_site_asset_grants`, значит новые `068` и `069`.

Главное правило владельца: **проект конструктора это текущий лицензированный филиал**. Один филиал, один сайт навсегда;
лицензию выдаёт только главный администратор платформы; без действующей лицензии конструктор только читается, а
опубликованный сайт продолжает работать. Лицензия проверяется в базе, в API и в воркере ИИ, а не в интерфейсе.

## 1. Что меняется для человека

1. Нет сайта: экран «Сайт для Luxx Aparts» (имя филиала), «Опишите, каким должен быть сайт», кнопка «Создать сайт» и
   вторая «Показать варианты оформления». Названия и адреса сайта не спрашиваем, быстрых примеров нет. Ниже тихий
   список «WETOP уже знает» из брифа (номера, адрес, контакты), только то, что найдено.
2. Есть сайт: полоса проекта сверху «Luxx Aparts / Сайт филиала / Лицензия активна / Черновик vN / Опубликована vM» с
   «История», «Изображения», «Публикация». Раскладка MKT9.1 сохраняется: слева ИИ, блоки и сайт, справа живой сайт.
3. Вкладка «ИИ» стала разговором с режимами «Чат», «План», «Сборка» (по умолчанию «Сборка»):
   - «Сборка»: прежние INITIAL, PATCH, SECTION; ход работы человеческими шагами;
   - «План»: ИИ задаёт до четырёх вопросов с вариантами или отдаёт план (что поменяет, на каких страницах, шаги,
     чем придётся пожертвовать); план можно поправить, «Собрать по плану» создаёт ровно одну задачу сборки;
   - «Чат»: ответ словами без новой версии, может предложить «Перейти в сборку»; на «опубликуй» показывает кнопку
     «Перейти к публикации», сам ничего не публикует.
   - «Варианты оформления»: ровно три направления (название, описание, тема, вариант первого экрана, порядок блоков)
     карточками с выбором; у нового сайта выбор уходит в первую сборку, у готового применяется в редакторе без ИИ.
4. Разговор хранится на сервере и виден после обновления страницы и с другого компьютера (сайт филиала, право
   `settings`); в `sessionStorage` остаётся только недописанный текст.
5. «Знания проекта»: постоянные указания для ИИ этого сайта (до 5000 знаков), на вкладке «Сайт».
6. Над живым сайтом «Выбор» (`S`) и «Текст» (`T`). «Текст»: щелчок по разрешённому тексту на сайте даёт правку прямо
   там; Enter применяет, Escape отменяет. Это локальная правка документа, сохранение даёт обычную ручную версию, ИИ не
   зовётся. Цены, даты, бронь, тарифы, коды категорий, картинки, ссылки и контакты так не правятся.
7. «История»: звёздочка у версии делает закладку с подписью, закладки отдельным списком сверху (до 20 на сайт).
8. Лицензии нет или срок вышел: всё видно, кнопки записи выключены, плашка «Конструктор сайта не активен для этого
   филиала.»
9. «Платформа → Организации»: у организации список гостиничных филиалов со статусом конструктора и действиями
   «Пробный», «Активировать», «Продлить», «Выключить».

## 2. Модель данных (DATA_MODEL §29.10–§29.13, утверждено ТЗ владельца)

Миграция `20261008000068_licensed_site_builder` (+ `down.sql`):

- `site_builder_entitlements`: `location_id` PK и FK на `locations`, `status ExtensionStatus` (TRIAL, ACTIVE, OFF),
  `active_until timestamptz NULL` (у TRIAL обязателен), `note varchar(300)`, `updated_by` FK пользователя,
  `created_at`, `updated_at`. Триггер: филиал гостиничного бизнеса. Заполнение: ACTIVE без срока только тем филиалам,
  у которых уже есть сайт (прежняя работа не обрывается). RLS FORCE через Location → Business → организация.
- `marketing_sites`: частичный UNIQUE «один неархивный на филиал» заменён полным `UNIQUE(location_id)`. Перед этим
  проверка: если у какого-то филиала больше одного сайта, миграция падает с понятным текстом и ничего не чинит сама.
  Колонка `builder_instructions varchar(5000) NULL`.
- `site_ai_runs`: разговорные задачи ИИ (CHAT, PLAN, DESIGN) с состояниями QUEUED, RUNNING, SUCCEEDED, FAILED;
  поля из ТЗ п. 63, `payload jsonb` до 32 КиБ (CHECK), `user_text` до 4000, `assistant_text` до 12000,
  `UNIQUE(site_id, request_key)`, триггер переходов и неизменяемости как у `generation_runs`, базовая версия только
  своего сайта. Версии не создаёт никогда.
- `marketing_site_version_bookmarks`: `site_id`, `version_id`, `label varchar(120)`, `created_by_id`, `created_at`,
  `UNIQUE(site_id, version_id)`; триггер: версия этого сайта и не больше 20 закладок на сайт.
- `generation_runs.error_code` и `site_ai_runs.error_code` получают `LICENSE_UNAVAILABLE` (не повторяется).

Миграция `20261008000069_licensed_site_builder_grants`: только права (восстановление копии их повторит).
`wetop_app`: лицензии только `SELECT`; `site_ai_runs` `SELECT, INSERT`; закладки `SELECT, INSERT, UPDATE, DELETE`;
`wetop_service`: лицензии `SELECT, INSERT, UPDATE`, `site_ai_runs` `SELECT, INSERT, UPDATE`, закладки как у
приложения. Удаления лицензий и разговоров нет ни у кого.

Prisma: `Location.marketingSite MarketingSite?` вместо списка, модели трёх таблиц, реестр RLS `RLS_TENANT_TABLES`.

## 3. API

Право `settings`, строгий scope филиала MKT3 (без отката в организацию).

- Центральная проверка `siteBuilderAccess` в `siteTransaction` записи: организация пишет, бизнес ACTIVE и
  HOSPITALITY, филиал ACTIVE, лицензия действует, право `settings`. Иначе 403 `SITE_BUILDER_NOT_ENABLED`
  («Конструктор сайта не подключён для этого филиала») или `SITE_BUILDER_EXPIRED`. Закрыты: создание сайта, сохранение,
  восстановление, все ИИ (сборка, чат, план, оформление), картинки, публикация, возобновление, откат, знания, закладки.
  Пауза, архив и выбор сайта брони не закрыты: они не создают ничего нового и не тратят ИИ.
- `POST /marketing/site/bootstrap` с телом `{}`: имя из филиала, адрес `suggestMarketingSlug` с детерминированным
  суффиксом при занятости; есть сайт 200, новый 201, сайт в архиве 409 `SITE_ARCHIVED`. Прежний `POST /marketing/site`
  с названием и адресом снят.
- `GET /marketing/site` дополнен `builder` (доступ, статус, срок) и знаниями проекта.
- `GET/PATCH /marketing/site/context` `{ instructions }`; в журнале только длина, не текст.
- `POST /marketing/site/assistant` (`requestKey`, `mode` CHAT|PLAN|DESIGN, `text`, необязательные `answers`) ставит
  `site_ai_runs`; `GET /marketing/site/assistant/:id`.
- `POST /marketing/site/assistant/:id/approve` (`instruction` можно поправить): по успешному плану ставит одну задачу
  сборки PATCH (или INITIAL у сайта без версии) с `requestKey` равным id плана, поэтому второй раз задача не создаётся.
- `POST /marketing/site/generations` INITIAL принимает `designId` и `designRunId` выбранного направления.
- `GET /marketing/site/conversation?limit=100`: сборки и разговоры одним списком по времени, с текстом человека
  (решение владельца MKT9.2 отменяет закрытость текста команды MKT9 §110 внутри сайта филиала; в журнал аудита текст
  по-прежнему не идёт).
- `PUT /marketing/site/versions/:id/bookmark` `{ label }` и `DELETE …/bookmark`; список версий несёт закладки.
- Платформа: `GET /platform/organizations/:id/site-builder`, `PUT /platform/organizations/:id/site-builder/:locationId`
  (`status`, `activeUntil`, `note`, разбор `parseExtensionChange`), только главный администратор, служебной ролью базы,
  журнал `site_builder.entitlement_updated` с «было» и «стало».

Общие правила ИИ сайта (Q-274, Q-279): одна активная задача ИИ на сайт по обеим таблицам (проверка под замком сайта);
платные вызовы одной организации по одному (замок организации в захвате воркера, учитывает обе таблицы); один дневной
пул 150 000 токенов на организацию (обе таблицы, кэш не считается дважды); неизвестный расход останавливает ИИ сайта
организации до следующих суток UTC (и при постановке); 10 запросов в час на человека в организации на все режимы.

Воркер: перед платным вызовом заново проверяет лицензию и организацию, иначе FAILED `LICENSE_UNAVAILABLE` без вызова.

## 4. Бот

`POST /internal/site-assistant` (`site-assistant/0`), только служебный ключ, только ключ модели платформы. Разделы
сообщения: правила системы; данные гостиницы; текущий документ; знания проекта; запрос человека (данные, не правила).
Ответ строгим JSON по режиму, разбирает и проверяет платформа (`parseAssistantResult`): CHAT `{answer, suggestBuild,
suggestPublish}`; PLAN `{kind:'QUESTIONS', questions[≤4]}` или `{kind:'PLAN', summary, affectedPages,
affectedSections, steps, tradeoffs, buildInstruction}`; DESIGN `{directions[3]}` только из перечислений SiteSpec.
Ни промпт, ни сырой ответ модели не хранятся и не возвращаются.

## 5. Не делаем (явно)

Новые проекты, ремикс, копии сайта, несколько черновиков, параллельную очередь ИИ, свой код и свою базу у сайта,
автопубликацию, свои домены (MKT10), ИИ-SEO (MKT11), ИИ-картинки, рисование и комментарии на сайте, выделение
нескольких блоков. На рабочей базе ничего не применяем, лицензий не выдаём, `release` не трогаем.
