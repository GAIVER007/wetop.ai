# Mobile access: проверенная карта подключения

24.10.2026. Подготовка этапа 1 утверждённого mobile-product-roadmap-2026-10-24.md.
Источники: локальный commit 4b91e7b18. Это проверка исходников ветки, не текущего production и не полного свежего main. Перед кодовой реализацией повторить сверку после завершения другой сессии.

| Операция | Существующий контракт | Что обязан сделать мобильный клиент |
|---|---|---|
| Вход | POST /auth/login, email/password; ответ token/expiresAt/user | Хранить только токен защищённо, затем запросить me и контекст |
| Проверка | GET /auth/me; user может быть null | Не считать один HTTP 200 успешной авторизацией |
| Идентичность сессии | whoami обновляет expiresAt; sessionIssuedAt стабилен для этой сессии | Не пересоздавать контекст из-за каждого продления expiresAt |
| Организации | GET /auth/organizations: id/name/role/current, активное членство | Показывать только серверный список |
| Смена организации | POST /auth/organization: organizationId; новый token/expiresAt/user, старый токен отозван | Скрыть старые данные, сохранить новый токен, снова получить филиалы и me |
| Филиалы | GET /branches: organization/items/canCreate/personal | Не вычислять personal из профессии или локального переключателя |
| Указатель филиала | business=<uuid>;location=<uuid> в X-Wetop-Scope | Использовать businessId/locationId из разрешённого списка, повторно проверить me |
| Отозванное назначение | me не подтверждает businessId/locationId | Вернуться к разрешению контекста, не показывать прошлый кабинет |
| Выход | POST /auth/logout | Очистить локальную сессию, отдельно подтвердить серверный отзыв |
| Восстановление | POST /auth/password-reset/request | Одинаковое публичное подтверждение, без раскрытия существования аккаунта |

## Источники и важные исключения

- apps/api/src/auth/auth.controller.ts: маршруты и scope ответа me.
- apps/api/src/auth/auth.service.ts: whoami, organizations и switchOrganization. Смена организации выполняет отзыв и создание сессии в транзакции; параллельный переход старым ключом допускает одного победителя.
- apps/api/src/hotel/branches.ts: объединение гостиничных Property и самостоятельных Location салона/ресторана, фильтрация доступных назначений, personal для EMPLOYEE.
- apps/web/src/lib/api.ts: BranchItem содержит currency, timezone, vertical, locationId и location.businessId. Не использовать id Property вместо locationId.
- apps/web/src/app/scope/resolve/route.ts: берёт personal из ответа /branches.
- apps/web/src/lib/scope-resolve.ts: обычный кабинет выбирает один/запомненный филиал либо предлагает выбор. Personal может выбрать первое разрешённое назначение и ведёт в /my-work.
- apps/web/src/lib/scope-pointer.ts: проверка формы указателя с UUID. Валидная форма не является доказательством права, сервер проверяет назначение.

## Обязательные дополнительные случаи при реализации

1. Смена организации успешна, запись нового токена в storage не удалась: старый токен уже отозван. Не возвращать старый кабинет; завершить безопасным закрытым состоянием и объяснением повторного входа.
2. Смена организации завершилась таймаутом: исход операции неизвестен, старую сессию нельзя считать действующей. Повторно проверить серверное состояние, не запускать бесконечный повтор POST.
3. Повторное нажатие переключателя: один запрос и поколение контекста, поздние ответы не восстанавливают старый бизнес.
4. В /branches нет гостиничного Property у салона или ресторана: использовать locationId, не требовать фиктивного объекта гостиницы.
5. Валюта и часовой пояс относятся к текущему филиалу. При смене филиала очистить прежние агрегаты и форматирование контекста.

## Оставшаяся подготовка перед изменением кода

Проверить актуальный доверенный proxy/IP контракт и лимиты шлюза, точные DTO полей me/access/beautyAccess, серверные ограничения статуса организации и доступность выбранной версии SecureStore. Не расширять шлюз произвольными маршрутами рабочих модулей. Отдельные рабочие контракты ресторанов подключаются после mobile-access.
