# Надёжное создание ресторанного заказа

Статус: направление выбрано по поручению владельца; точная поправка DATA_MODEL ожидает утверждения по §2. Схема и код не изменены.

## Сервер

1. После утверждения добавить два nullable-поля и UNIQUE/CHECK из DATA_MODEL. Подготовить forward SQL, backup/validation/rollback инструкцию. Production не изменять. Откат с заполненными ключами запрещён: потеря ключей снимает защиту ранее принятых запросов; для такого состояния только согласованный forward repair.
2. Расширить parser необязательным ключом для совместимости. Мобильный транспорт принимает только валидный ключ и существующий payload заказа, не принимает цену/сумму от клиента.
3. Нормализация v1 фиксирует tableId, waiterId из входа, guestCount, notes, строки в исходном порядке, modifierIds в каноническом порядке после существующей проверки. Хэш содержит версию, пользователя и филиал. Назначение официанта сервером остаётся неизменным. Серверные цены не входят во входной fingerprint.
4. В одной транзакции существующей foodTransaction выполнять проверку повтора и создание. Сериализация повторов должна быть подтверждена проверкой реализации транзакции и конкурентным тестом, UNIQUE обязателен независимо от блокировок. Конфликт уникальности не превращать в слепой повтор INSERT.
5. Replay проходит действующие проверки доступа и принадлежности заказа, затем возвращает orderView существующего заказа. Смена меню не должна блокировать уже принятую попытку. Ключ с иным fingerprint получает 409. Проверять доступ до раскрытия результата.

## Мобильное приложение

Одна попытка содержит неизменяемые key, payload и контекст пользователя/организации/филиала. До сетевой отправки необходимо сохранить восстановимую попытку в защищённом локальном хранилище; не использовать localStorage для реальных данных. Размер заказа может превышать лимит одной записи SecureStore: формат, лимиты и атомарность записи должны быть проверены до реализации, а ошибка сохранения блокирует отправку.

После таймаута показать «Результат пока не подтверждён» и действие проверки/повтора с прежним ключом и payload. Не освобождать ключ по таймеру и не разрешать незаметное редактирование неопределённой попытки. Успешный повтор открывает тот же order ID. Перезапуск приложения восстанавливает попытку только после проверки того же пользователя и филиала. Другой аккаунт не получает старый payload. Выход, смена филиала и неразрешённая попытка требуют отдельного явного безопасного UX без автоматической отправки в новом контексте.

## Проверки до готовности

- Первый запрос: один заказ, строки и одно событие создания.
- Ответ потерян после commit: повтор возвращает тот же ID.
- Два одновременных запроса: один заказ и один номер, без двойного аудита.
- Иной payload/пользователь с тем же ключом: 409, нет раскрытия данных.
- Отозванные права или чужой филиал: отказ; ключ не обходит RLS.
- Изменившееся меню после commit: возврат ранее созданного заказа без пересчёта.
- Rollback транзакции не оставляет принятой попытки.
- Старый веб-клиент без ключа сохраняет текущий контракт.
- Мобильные double tap, timeout, перезапуск, ошибка storage, смена контекста.

RED перед GREEN, синтетические fixtures. Конкуренция и RLS требуют изолированного PostgreSQL либо отдельного CI; unit-тесты сами этого не доказывают. Общая dev-база не используется. Сначала миграция и совместимый сервер, затем включение мобильной отправки; без подтверждённого серверного контракта кнопка не объявляется рабочей.
