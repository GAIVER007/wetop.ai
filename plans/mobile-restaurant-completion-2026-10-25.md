## Следующий порядок реализации

1. Подача отдельной готовой позиции: POST orders/:id/items/:itemId/status, expectedUpdatedAt и status=SERVED. Сотрудник может подать только свою позицию; сервер waiterSelf и scope сохраняются. Готовность кухни/бара нельзя выдавать обычному EMPLOYEE через название роли. При конфликте версии обновить данные, не повторять команду с новой версией автоматически.
2. Прочитать фактически разрешённые способы оплаты филиала через существующий серверный контракт. Не подставлять фиксированные способы, не считать агрегатор способом оплаты. Текущий mobile-food-gateway этого чтения ещё не предоставляет.
3. Платёж только для серверного desk-доступа. Зафиксировать orderId, amount в minor units, method, idempotencyKey и выбранные позиции одной неизменной попыткой до сети. Не использовать слот создания заказа: payload и жизненный цикл отличаются. Разбирать введённую сумму строкой без float; API принимает safe integer, превышение диапазона блокировать явно.
4. POST orders/:id/payments сохраняет существующие правила. Полная оплата автоматически закрывает только SERVED заказ. Полученный orderView не называть фискальным чеком. При потере ответа сохранить попытку, разрешить только явный повтор исходного payload/key. Сервер повтор на том же заказе не сравнивает сумму/метод, поэтому сохранённый запрос нельзя редактировать. Отключённый способ может препятствовать replay; не переключать метод автоматически и не освобождать ключ по ошибке.
5. Закрытие через существующий orderStatus: desk, expectedStatus, expectedUpdatedAt; закрывать только полностью оплаченный заказ и только разрешённым переходом. Не выполнять последовательность команд автоматически после неоднозначного ответа.
6. Гостевой счёт: отдельный просмотр состава и итогов с отметкой состояния данных. Печать и фискализация требуют поддержанного документа/маршрута, их endpoint у ресторана отсутствует. Не использовать отельный folio receipt.

## Доказательства перед следующим переходом

Red-green: чужой филиал/заказ, EMPLOYEE без desk, устаревшая версия, двойное нажатие, таймаут после принятия, восстановление после перезапуска, смена аккаунта, недоступное локальное хранилище. Синтетический PostgreSQL отдельно от общей dev-базы. Для денег проверить частичную и полную оплату, запрет переплаты и расхождения суммы выбранных строк. Проверка реального Keychain/Keystore и устройства остаётся отдельным пунктом даже при зелёном Expo export.

## Фактическое состояние на 25.10.2026, 11:10 America/Los_Angeles

Пункты 1–6 реализованы в мобильной ветке в пределах существующих контрактов: подача, способы оплаты, сохраняемая попытка оплаты, оплата, закрытие и просмотр гостевого счёта. Печать и фискализация не реализованы. Начальные сведения выше о недоступности чтения методов и отправки теперь исторические.

Проверки: 101 мобильный тест (2026-10-25T18-10-10Z-mobile-48f3), mobile-types (2026-10-25T18-10-37Z-mobile-types-713d). Дополнительно проверены точные payload оплаты/закрытия, исходный bearer/scope, запрет cookies/redirect, отсутствие сетевого автоповтора и отклонение позднего ответа после смены филиала. Это регрессия существующего поведения, не новый bugfix. Sandbox-доказательства оплаты и роли wetop_app находятся в docs/decisions/2026-10-25-mobile-order-close.md.

Оставшиеся проверки перед переходом к салону:
1. Цепочка настоящего HTTP: синтетический существующий аккаунт -> bearer -> mobile gateway -> Nest API -> ограниченная роль БД. Текущие unit fetch-заглушки и прямой RestaurantService не заменяют эту цепочку.
2. Установка на iOS/Android, Keychain/Keystore, перезапуск и фон/возврат. Expo export не заменяет устройство.
3. Визуальная проверка маленького экрана и увеличенного текста, включая гостевой счёт.

Работа разрешена владельцем в отдельной ветке параллельно другим сессиям, только с изолированной базой. Прежнее ожидание завершения других сессий отменено. Main, публичные флаги gateway и production-миграции остаются вне этого разрешения.
