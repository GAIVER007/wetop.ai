# Мобильный салон: карта существующих API перед реализацией

Дата: 25.10.2026 UTC. Статус: read-only сверка кода для следующего этапа утверждённого плана. База и production не использовались.

## Администратор и владелец

`GET /beauty/appointments?date=YYYY-MM-DD` даёт журнал дня, мастеров, рабочие интервалы, услуги и записи выбранного филиала. Контроллер требует capability `beauty.appointments`, роль `desk` и право `journal:view`. `GET /beauty/appointments/period?from&to` даёт записи периода с правом `appointments:view`. Это разные разрешения, мобильный gateway не должен считать их взаимозаменяемыми. `GET /beauty/services` также требует `desk` и `services:view`. Финансовые маршруты отдельно требуют `finance:view`. Запись, перенос, статус и оплата имеют отдельные write-права; read-only журнал их не подтверждает.

Сервер использует timezone филиала для даты и UTC для событий. При создании запись проверяется на пересечение до транзакции и внутри неё. Для мобильного POST нужно отдельно проверить повтор после таймаута, текущий контроль конкурентности и состав ответа, прежде чем открывать отправку. Гостевые и финансовые поля необходимо фильтровать в gateway по конкретному экрану.

## Мастер

`GET /employee-portal/me?date&month&range=day|month` является личным маршрутом с `@Access('self')` и проверкой секций назначения. Он уже ограничивает записи `employeeId` и выбранным филиалом, возвращает личный день/месяц, график, профиль, статистику и зарплату только при соответствующих правах. Ответ крупный и содержит телефон, email, профиль, портфолио и другие данные; мобильному приложению нужен узкий DTO, нельзя пересылать ответ целиком. Отсутствие payroll-права показывает статус `NOT_CONFIGURED`, а не придуманную сумму. Веб-аккаунт и привязка сотрудника используются существующие; регистрации в приложении нет.

## Порядок следующего среза

1. Зафиксировать разрешённые DTO владельца, администратора и мастера и проверить серверную фильтрацию филиала.
2. Добавить только чтение личного дня мастера и дня администратора с отдельными тестами прав и отсутствия утечки чужих записей.
3. Затем проверить создание записи, перенос, визит и оплату по существующим write-контрактам, включая неопределённый результат после таймаута.
4. Проверить мобильную ширину, доступность, native устройство и реальный тестовый объект перед заявлением о готовности салона.

Код салона не начат, потому что принятый план ставит полный ресторанный рабочий срез перед ним. Текущий ресторанный POST ждёт решения `MOBILE-FOOD-1` в `QUESTIONS.md`.
