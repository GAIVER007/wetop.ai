## Предлагаемый scope

1. Раздельные read-only отчёты Beauty и Food по выбранному Business/Location и периоду. Hospitality использует существующие отчёты и расчёты.
2. Сначала абсолютные количества по существующим статусам. Подписи статусов соответствуют реальным API, источник каждой цифры фиксируется в отчёте. Не переносить Today формулы текущего момента на произвольный исторический период.
3. Beauty выручка по уже утверждённому §21.5, только после подтверждения фактического источника снимков цены/валюты и доступного безопасного способа суммирования. Цены каталога не заменяют снимок записи; это выручка по утверждённой модели, не полученные оплаты.
4. Food финансовые показатели честно недоступны, без фиктивных нулей. Депозиты и касса B7 отдельными этапами, не добавляются автоматически в MV9.
5. Сводка доступных филиалов группируется по вертикали. Денежные итоги отдельно по валюте; ADR/RevPAR только Hospitality. Даты каждого филиала в его timezone, подпись периода локальных дат обязательна.
6. Период и scope проходят серверную проверку. При переключении сбрасываются старые результаты; устаревший ответ не может заменить новый. Ошибка и частично недоступные данные видны явно.

## Этапы и зависимости

### 1. Контракт и source map

После подтверждения плана проверить схему, действующие API, permissions, pagination и scope boundaries. Зафиксировать в DECISIONS.md выбранную архитектуру read-only адаптеров. Составить таблицу показателей: название, статус/поле, период, timezone, фильтры, валюта, источник и право доступа. Предпочесть существующие endpoints. Если нужен новый API, до его кода представить точный DTO, endpoint и impact report на согласование. Миграций на этом этапе нет.

Критерий: для каждой цифры есть реализованный источник и точная формула; отсутствующие данные обозначены как недоступные. Проверить отсутствие повторного использования гостиничных Property/Folio в Beauty/Food.

### 2. Read-only adapters и проверки

Реализовать периодные адаптеры и scope validation в согласованных boundaries. Все страницы данных дочитываются, дубликаты не увеличивают итоги. Финансовые суммы только decimal-safe/integer minor units, с проверкой диапазона и раздельными валютами. Период локальных дат преобразуется в интервалы существующим timezone механизмом; границы тестируются.

Критерий: RED до исправления/new behavior, затем GREEN для scope isolation, local midnight/DST, пустого периода, пагинации, отказа доступа, недоступного источника и финансовой сверки. Точные пути изменений определяются source map, не создаётся параллельный общий финансовый движок.

### 3. UI аналитики и сводка

Vertical dispatch для аналитики, соответствующее меню, период, абсолютные счётчики и доступные деньги Beauty. В mixed Organization отдельные группы без общего hotel-only KPI. Invalid route redirect выполняется до чужого domain request. Loading/empty/error/read-only states, keyboard, две темы и 1440/390.

Критерий: быстрые Business/Location переключения и reload показывают только актуальный scope, UI = API = независимый SQL reconciliation на синтетических данных; нет запросов к чужой вертикали и горизонтального overflow.

### 4. Evidence и отдельный PR

Собственная localhost PostgreSQL, реальные Nest API и браузер. Shared Supabase и чужие процессы не используются. Полные применимые проверки TESTING.md, unit/integration, typecheck/lint, Hospitality regression и соседние Beauty/Food/branches UI. Итоги фиксируются без сокрытия failures/skips. Финальный report: SHA, команды, источники чисел, reconciliation, screenshots, ограничения. Commit/push, отдельный PR с приложением к чату, затем STOP.

Production/release, merge, MV10/MV11 не входят в разрешение этого этапа.

## Продуктовые развилки, до реализации соответствующей метрики

- No-show rate: требуется согласованный знаменатель и отнесение к периоду. Пока показывать абсолютное число NO_SHOW, без процента.
- Repeat customers: требуется определить окно истории, какие статусы считать состоявшимся посещением, scope Business или Organization. Пока не показывать процент/классификацию повторных клиентов.
- Если фактический Beauty контракт не даёт снимков цены/валюты, финансовую часть остановить с конкретным impact report. Не подменять её актуальным прайсом.

При согласовании плана эти ограничения становятся scope MV9. Новые бизнес-развилки записываются в QUESTIONS.md по AGENTS §4 до их реализации. План не утверждает новые financial rules, schema или API DTO.
