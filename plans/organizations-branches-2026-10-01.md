# Организации, филиалы и общая статистика

Статус: предложение, требуется подтверждение сценария по AGENTS.md §1 и решений ниже по §4.

## Проверено в исходниках

- Organization → Business → Location → Property уже существует (DATA_MODEL.md §18). UUID создаются базой. Новая таблица филиалов не нужна.
- Membership допускает одного пользователя в нескольких организациях. Вход в auth.service.ts выбирает первое членство, полноценное переключение нужно реализовать и проверить.
- Platform показывает организации и управление подпиской, но не создаёт организации.
- createPropertyInChain создаёт объект с филиалом в транзакции. Текущий гостиничный онбординг находит первый объект организации, поэтому его нельзя просто повторно использовать для второго филиала.
- property-ref.ts учитывает LOCATION, но ORGANIZATION выбирает первый объект. Это не общая статистика.
- Финансовая консолидация разных валют не определена; Q-197 остаётся открытым.

## Предлагаемый сценарий

Один вход, список доступных организаций, внутри каждой список филиалов. Создание организации и добавление филиала являются разными действиями. Platform Admin управляет метаданными, но финансовый доступ получает только через членство с подходящей ролью.

1. Создание организации: название, существующий аккаунт владельца, явный статус доступа. Создание организации и членства владельца атомарно, UUID доступен для копирования. Пароли существующих пользователей не меняются. Приглашение внешнего владельца отдельным подтверждённым сценарием.
2. Переключение организации: только доступные членства, повторная серверная проверка, сброс несовместимого выбора филиала и клиентского кэша. Вкладки и перезагрузка не смешивают данные.
3. Добавление филиала: владелец создаёт пустой объект с названием, адресом, валютой и часовым поясом. Далее отдельная настройка категорий, номеров, коек и тарифов для выбранного объекта. Ничего не копируется из Luxx Aparts автоматически.
4. Переключение филиалов: рабочие операции требуют конкретного филиала. «Все филиалы» доступно для отчётов, без случайной записи в первый объект.
5. Статистика: одинаковый период, таблица филиалов и общий итог. Брони, гости, занятые/доступные места и финансовые показатели берутся из существующих источников. Загрузка считается через общий числитель и знаменатель, не среднее процентов. Деньги разных валют показываются раздельно до решения Q-197. Начисления, поступления, возвраты и расходы не подменяют друг друга; отсутствующие источники не выдаются за нули.
6. Проверки и выпуск: red/green на доступ и выбор контекста; два синтетических филиала, посторонняя организация, reload, повтор сохранения, пустой объект, сверка итогов. Затем typecheck, браузер, commit/push/deploy и проверка SHA на домене.

## Порядок задач и критерии

- [ ] Утвердить решения Q-ORG-20261001 и записать принятые контракты в DATA_MODEL.md/DECISIONS.md.
- [ ] Создание организации: запись и владелец сохраняются вместе, повтор не создаёт дубль; запрещённый пользователь получает отказ. Проверка API и транзакций.
- [ ] Выбор организации: смена прав и контекста проверяется на сервере; чужой ID не открывает данные. Проверка auth и браузера.
- [ ] Создание филиала: новый UUID и пустой фонд, старый филиал не меняется. Проверка транзакции и сохранения после reload.
- [ ] Настройка пустого филиала: категории и номера попадают только в выбранный объект. Проверка онбординга с двумя филиалами.
- [ ] Обзор сети: totals сверяются с филиалами, валюты разделены, все показатели имеют определённый источник. Проверка фиксированных синтетических данных.
- [ ] Выпуск: проверенный SHA работает на домене, отчёт содержит ограничения и доказательства.

Работа последовательная. Схему не менять без отдельного утверждения обнаруженной необходимости. Производственную миграцию, если потребуется, выпускать только с backup/validation/rollback и отдельным разрешением.

## Решения, ожидающие владельца

Q-ORG-20261001: предложено создавать собственную организацию с текущим пользователем OWNER; новые организации активировать явно через существующее управление подпиской без автоматического списания и нового бесплатного trial. Филиалы наследуют текущие роли организации (все её участники видят все филиалы в пределах роли), отдельные права на филиал в этот срез не входят. Финансовые итоги по валютам раздельно. Требуется согласование этих условий и плана.

Дополнительные проверенные дефекты: HotelService.property выбирает первый объект по
organizationId; settingsKey не включает locationId. OnboardingService.findProperty также
выбирает первый объект. Обязательные red/green проверки перед созданием второго объекта.

На Главной: выбор «Все филиалы»/конкретный объект, общий обзор и таблица филиалов.
В конкретном объекте сохраняются рабочие действия. В общем обзоре создание брони
сначала требует выбора филиала. В аналитике один выбранный календарный период,
его границы применяются по часовому поясу каждого объекта и поясняются на экране.
Число гостей не называть уникальными гостями сети без дедупликации; использовать точное
название существующего показателя (например, гости в заездах). Загрузку, ADR/RevPAR
пересчитывать из исходных сумм и знаменателей, а не усреднять готовые проценты/цены.

Подписка сейчас: вручную меняется Organization.status, заметка хранится в AuditLog.
Нет Core paidUntil, реестра счетов/оплат или автоматического продления. Цена 49 900 KZT
на филиал до 100 единиц утверждена Q-143, но начислять её автоматически при добавлении
