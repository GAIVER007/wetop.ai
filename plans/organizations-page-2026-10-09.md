# Страница «Организации»: одна страница, управление организациями

**Дата:** 09.10.2026. **Статус:** часть 1 и срез ORG1 (название, архив, возврат) сделаны и проверены, создание организации (ORG2) сделано, раздел 7. Q-283 закрыт. Q-282, Q-284, Q-285 закрыты предложенными умолчаниями (ADR-ORG1).
**Поручение владельца 09.10.2026:** перенести «Платформу» в «Настройки»; на странице «Организации» убрать непонятные
названия и ID, собрать всё на одну страницу: добавить организацию, удалить её, редактировать, видеть статистику по
филиалам.

## 1. Что было

Вкладка «Платформа» с одним пунктом «Организации» (только главный администратор, `/platform`). Внутри склеены два
экрана: филиалы текущей организации (с ID организации и филиала, «Реквизиты организации», «Добавить объект / филиал»,
«Сводка по гостиничным филиалам») и спрятанная раскрывашка «Подписки и администрирование» с таблицей всех организаций.
Статистика жила отдельной таблицей внизу, не рядом с филиалом.

## 2. Часть 1: сделано (только интерфейс, API и модель данных не менялись)

| Одна страница | Сверху своя организация: название, период, итоги (загрузка, гости, начислено, поступило с возвратами), карточки филиалов. Ниже таблица всех организаций платформы (всегда раскрыта) с карточкой выбранной. В самом низу «Состояние системы» |

## 3. Часть 2: чего нет и почему

В API есть только: список организаций, смена статуса подписки, расширение «ИИ-продавец», лицензия конструктора сайта,
создание филиала. Нет создания организации, правки её данных, удаления, правки и удаления филиала. Каждое из этого
меняет данные или деньги и упирается в решение, которое агент не придумывает (AGENTS.md §4, §15):

| Что просят | Где упирается | Вопрос |
|---|---|---|
| Удалить организацию | `plans/slice-13-accounts-2026-09-15.md`: «удаление организации не предусмотрено, статус вместо удаления». Журнал только дописывается (v1.7), у организации брони, гости, счета, платежи | Q-282 |
| Добавить организацию | Сейчас организация появляется только самостоятельной регистрацией на wetop.ai вместе с владельцем | Q-283 |
| Редактировать организацию | Полей «реквизиты», «БИН», «договор» в модели нет (DATA_MODEL §13, §16); переименование филиала открыто как Q-239 | Q-284 |
| Статистика по филиалам других организаций | ADR-083: главному администратору чужие брони, гости и счета не видны по построению | Q-285 |

## 4. Часть 2: предлагаемый срез ORG1 (после ответов)

Предлагаю по умолчанию, владелец может выбрать иначе в Q-282…Q-285:

1. **API (только главный администратор, право `platform`):** `POST /platform/organizations` (название и почта владельца,
   статус `TRIAL`, владельцу уходит приглашение существующим механизмом), `PATCH /platform/organizations/:id`
   (название), архив и возврат из архива через уже существующий статус (`SUSPENDED` и обратно), запись в журнал на
   каждое действие. Новые маршруты попадают в `route-access.test.ts` с правом `platform`, чужих организаций касается
   только главный администратор.
2. **Интерфейс на этой же странице:** кнопка «Добавить организацию» над таблицей (форма раскрывается на месте), в
   строке таблицы «Изменить» и «В архив», подтверждение вводом названия, архивные организации скрыты фильтром
   «Показать архивные».
3. **Тесты:** сначала красные (AGENTS.md §6): API (права, валидация, дубли, журнал), `tests/integration` (изоляция
   организаций, RLS, архив не удаляет данные), UI (форма, подтверждение, возврат из архива).
4. **Модель данных:** если Q-282 решится «удалять насовсем» или Q-284 потребует реквизитов, сначала правка
   `DATA_MODEL.md` и миграция с откатом (AGENTS.md §2, §14). Для варианта «архив» схема не меняется.

## 5. Что не делаем

Окончательное удаление данных организации без выгрузки и срока хранения; показ чужих броней, гостей и счетов; перенос
филиала между организациями; правку и удаление филиала (Q-239).

Я искал по словам `reset-password` и `forgot`, а файл называется `password-reset`. Новый сценарий входа и правка модели не нужны.

## 7. ORG2: создание организации главным администратором (план)

**Поправка к разделу 3 и к Q-283.** Я писал, что создать организацию «за человека» нельзя без нового сценария пароля. Это неверно: ссылку «задайте пароль» уже умеет выдавать и слать существующий механизм (`password_resets`, одноразовый хеш токена, срок 24 часа, письмо `invitationLetter`, страница `/login/set-password`, подтверждение почты ставится тем же шагом). Приглашённые сотрудники заходят именно так. Таблиц и миграций не нужно.

**Как заводим.** `POST /platform/organizations` с `name`, `ownerEmail`, `vertical` (по умолчанию гостиница). Одной транзакцией: организация (`TRIAL`, срок как при регистрации), первый филиал (как при регистрации: гостиница через `createPropertyInChain`, остальные направления бизнес и филиал), человек без пароля (`password_hash = ''`, так заводят приглашённых), членство `OWNER`, ссылка в `password_resets`, строка журнала `organization.created` с автором. После фиксации уходит письмо владельцу. Токен наружу не отдаётся никому, в том числе главному администратору.

**Что проверяем так же строго, как при регистрации.** Название (`isOrganizationNameShaped`), почта (`validEmail`), занятая почта даёт 409 и ничего не создаёт, направление салона и ресторана только для почт из списка пилота (`assertRegistrationVertical`), у гостиницы название не повторяет чужое.

**Письмо не ушло** (нет настроек почты или отказ службы): организация остаётся, ответ говорит `ownerLinkSent: false`, на карточке кнопка «Отправить владельцу ссылку ещё раз». `POST /platform/organizations/:id/owner-link` выдаёт новую ссылку (прежняя гаснет) только владельцу, у которого пароля ещё нет; у уже вошедшего 409: чужой пароль главный администратор менять не может. Не чаще одного письма на почту в пять минут (429).

**Интерфейс на той же странице.** Кнопка «Добавить организацию» раскрывает форму: название, почта владельца, направление (гостиница или салон). В таблице у организации, чей владелец ещё не задал пароль, значок «ждёт пароля». Ссылка на самостоятельную регистрацию остаётся второй строкой в той же панели.

**Тесты (красные до кода).** API с подставной службой; на настоящей PostgreSQL: все строки созданы, токен из письма подходит к хешу в базе, дубль почты откатывает транзакцию, салон без пилота отклонён, повторная ссылка гасит прежнюю, владельцу с паролем 409, а `PasswordResetService.confirm` по ссылке из письма ставит пароль и отметку почты; UI на стенде. Старый ключ `OrganizationSummary` получает `ownerPending`.

**Не делаем.** Передачу владельца другому человеку, массовое создание, оплату и выставление счёта (подписка по-прежнему вручную, «Оплата получена»).

**Сделано (09.10.2026).** `POST /platform/organizations`, `POST /platform/organizations/:id/owner-link`, форма и значок «ждёт пароля» на странице. Решение: ADR-ORG2. Доказательства: API `platform.controller.test.ts` (красный 9 из 33, затем зелёный), настоящая PostgreSQL `tests/integration/platform-organization-create.test.ts` (6), стенд UI `tests/ui/organizations-manage.spec.ts` (3 новых спека красные, затем зелёные). Не проверялось: живая отправка письма с боевой почты.
