# Временно закрыть самостоятельную регистрацию

> План отменён прямым поручением владельца открыть регистрацию 20.09.2026.
> Действующий план: [вернуть регистрацию](reopen-registration-2026-09-20.md).
> Ниже сохранена история прежней реализации.

Подтверждено владельцем: «делай» в ответ на предложение по Q-152 закрыть
самостоятельную регистрацию, сохранив вход и приглашения сотрудников.

1. API отклоняет регистрацию с 403 до обращения к БД. По умолчанию регистрация
   закрыта; явный `REGISTRATION_OPEN=1` нужен только изолированному стенду.
2. Публичный `GET /auth/options` сообщает только доступность регистрации. Стойка
   получает это состояние с API без кэша; при ошибке считает регистрацию закрытой.
   `/register` и `/login?mode=register` показывают вход и объяснение ограничения.
3. Сохранить вход, приглашения, установку/восстановление пароля. Серверный отказ
   действует и для ранее открытой формы, и для прямого запроса.
4. Проверки RED → GREEN, браузерные сценарии, реальный AppModule с отдельной
   PostgreSQL: отказ не создаёт пользователя, организацию, членство или сессию.
5. Проверить изменения, отправить PR, дождаться CI и объединить. Проверить доступ
   к существующему серверу, затем выполнить деплой при наличии рабочего доступа.

Без миграций, изменения действующих учётных записей и обращений к production OTA.
Это временное ограничение входа новых пользователей, а не изоляция организаций.
