## 1. Развилка П-1 — где живёт выбранный контекст (решение владельца)

`DATA_MODEL.md` §18.5: «нужны ли `sessions.business_id` / `sessions.location_id` или контекст ходит
запросом — решается планом фазы 2».

**Предложение — вариант Б, контекст ходит запросом, схема не меняется:**
- стойка держит выбор в куке браузера (`wetop_scope`: businessId/locationId), как тему и плотность;
- каждый серверный вызов API несёт заголовок `X-Wetop-Scope` из этой куки;
- API **не верит заголовку**: middleware проверяет, что businessId принадлежит организации сессии, а
  locationId — этому businessId (один короткий запрос, кэш как у `property-ref`); чужое → scope
  падает до `ORGANIZATION`, без 500;
- плюсы: ни миграции, ни правки `sessions` (§13.5), выбор не «прилипает» к сессии на сервере — две
  вкладки могут смотреть разные филиалы; RLS уже режет по организации, заголовок ничего не расширяет;
- минус: заголовок надо прокинуть в серверные вызовы стойки (одно место — обёртка `apiFetch`).

Вариант А (колонки в `sessions`) — миграция, правка DATA_MODEL §13.5, один выбор на все вкладки;
берём его только если владелец хочет «выбор запомнен на сервере навсегда».

## 2. Срезы фазы (каждый — свой PR, свои тесты red→green)

### К1 — RequestActor со scope (только API)

`Actor` расширяется до §6: `businessId?`, `locationId?`, `vertical?`, `scope`, `role`,
`platformAdmin`. Правило перехода (§6, дословно): **нет businessId/locationId → scope =
`ORGANIZATION`, единственный Property организации разрешается как сегодня** — ни один действующий
сценарий Luxx не меняется; служебные ходоки остаются служебными (ADR-061). Замок `property-ref`
учится второму пути: при `scope = LOCATION` объект разрешается по `properties.location_id` цепочкой
Location → Business → организация сессии; путь по `organization_id` остаётся и первичен, пока
контекст не несёт филиала. Тесты: изоляция (чужой businessId/locationId в заголовке → отказ/падение
scope), переходное правило, служебный путь.

### К2 — переключатель контекста в стойке

Меню выбора Business/Location в шапке (место — по DESIGN.md, компонент сначала ищется на
`/design-system`). **Показывается только когда есть из чего выбирать**: у организации с одним
Business и одним Location (Luxx после backfill) переключателя не видно — §16, маленький клиент
терминов не видит. Выбор — кука; Главная и разделы работают как раньше (scope LOCATION с
единственным филиалом = сегодняшнее поведение). Экраны BUSINESS/ORGANIZATION-уровня этот срез **не
строит** — это этапы ТЗ Главной (A2+ после визуального стопа A1) и §10 аналитики.

### К3 — онбординг цепочки

Регистрация «один объект» создаёт всю цепочку §16: Organization → Business (то же название,
вертикаль HOSPITALITY) → Location (то же название) → Property с `location_id`; существующий
онбординг `/onboarding` встраивается без переделки (§15). «Настроить отель» у организации без
объекта достраивает цепочку так же. `reporting_currency` организации заполняется валютой первого
Location (закрывает NULL-хвост уточнения 4 для новых). Luxx не трогается — цепочка уже создана
backfill. Публичная регистрация остаётся закрытой (ADR-102 п.4) — код работает для ручных
партнёров/пилотов.

### К4 — «Платформа → Партнёры»

Существующий раздел «Организации» показывает цепочку: организация → бизнесы → филиалы → объекты
(§17), только чтение. Главный администратор видит структуру партнёра, не входя в его данные.

## 3. Что фаза 2 НЕ делает

Не строит экраны BUSINESS/ORGANIZATION-уровня Главной (ТЗ A2+, свой стоп-гейт); не трогает Beauty
(§19 — своей фазой); не переносит `properties.organization_id` и не ставит NOT NULL на
`location_id` (gate фазы БЛ); не меняет таблицу прав (линия PR #104); не открывает регистрацию;
не вводит `RoleGuard`-права по scope (Business Manager / Location Manager — Q-140, за владельцем).
