## A. Удаление тестовых данных из рабочей базы

1. **Правило отбора — чистая функция с unit-тестом red → green** (рядом с `e2e-cleanup-rules.ts`). Бронь тестовая, если
   ни одно её проживание не ссылается на Exely и выполнено одно из: метка автотеста; номер PMS; бронь канала не из Exely,
   номер не витринный `-SHOW-`. **Стоп-проверки:** скрипт отказывается работать, если среди кандидатов есть активное
   проживание или назначение ячейки, если у кандидата есть проживание из Exely, или если объект объявлен живым
   (`GUARD_PROPERTY_LIVE=true`) — после переключения каналов номер PMS будет у настоящих броней.
2. **Каскад по каждой брони:** назначения → связи гость↔проживание → начисления, распределения платежей, возвраты →
   платежи (только если все их распределения в удаляемых счетах) → счета → проживания → бронь → гости, у которых
   не осталось ни проживаний, ни броней, с их документами. Отдельно — 64 события уборки.
3. **Журнал действий (экран «Журнал» в WETOP):** удаляются записи, чья сущность после каскада не существует
   (бронь, проживание, счёт, платёж, возврат, гость, блокировка). Записи о тарифах, фонде, импортах Exely и чистке
   гражданства остаются. Число — в пробном прогоне.
4. **Копия до удаления:** все удаляемые строки в JSON — `project-input/exely/backups/2026-09-13-test-data/` (в .gitignore),
   с манифестом счётчиков. **Откат:** скрипт восстановления вставляет строки обратно в порядке зависимостей.
   Удаляются только отменённые брони вымышленных гостей, поэтому A идёт раньше тестовой базы, чтобы сайт стал чистым сразу;
   восстановление из этой копии проверяется на тестовой базе в шаге B, копия хранится до этой проверки.
5. **Channex staging (замечание pms-lux-12):** удалённая бронь не должна вернуться повторной ревизией. Приём ревизий
   отсекает повтор по номеру ревизии (`inbound.service.ts`: событие `PROCESSED` → `skipped_duplicate`, бронь не создаётся,
   ack повторяется), поэтому `external_events` не удаляются. Стоп-проверка: у удаляемых броней Channex нет событий
   `FAILED` или неподтверждённых ревизий (такие Channex присылает снова, и обработка пошла бы заново).
6. **Порядок:** пробный прогон (`--dry`, только счётчики) → владелец видит числа → `--apply` пачками по 50 броней,
   транзакция на пачку, контрольный запрос после записи (как `chunk.ts`).
7. **Доказательство:** опись после — не из Exely только 6 витринных; сверка периода `cli-exely-period.ts` — Exely
   без изменений (790 проживаний, нет в PMS 0); T6 `cli-channex-ari.ts 90` — 0 опасных; двойной ввод на сегодня.

## B. Автотесты в отдельной базе

1. **Проект Supabase** `pms-lux-test`, организация «hotel», регион `ap-southeast-1` (как рабочая; данные вымышленные).
   Цена по Supabase: **0 в месяц** (бесплатный тариф, второй проект). Бесплатный проект засыпает после недели без
   обращений — будится кнопкой в панели. Создаётся через Supabase MCP после подтверждения цены.
2. **Ключи — только владелец:** `TEST_DATABASE_URL` и `TEST_DIRECT_URL` в `.env` (пароль базы задаёт/сбрасывает
   владелец в панели Supabase; агент значений не видит, проверка — `cli-check-env.ts`).
3. **Схема:** все миграции Prisma на тестовую базу (`migrate deploy` с подменой адреса в дочернем процессе, адрес не печатается).
4. **Справочники без ПД:** копия из рабочей базы — объект, корпуса, этажи, категории, комнаты, 88 единиц, тарифы,
   цены, ограничения, услуги (скрипт с теми же id, повтор идемпотентен).
5. **Подключение тестов:**
   - интеграционные (vitest) берут `TEST_DATABASE_URL`; без него — отказ, а не тихий прогон по рабочей базе;
   - e2e (Playwright) поднимают свои API и web на отдельных портах с `DATABASE_URL=TEST_DATABASE_URL` и выключенным
     исходящим ARI (`CHANNEX_ARI=off`, ADR-041); launchd-службы на 3000/3001 остаются на рабочей базе. Предохранителя
     в конфиге мало (замечание pms-lux-12): сейчас `reuseExistingServer` подхватывает уже запущенный рабочий API,
     поэтому тестовые порты другие, и API тестов отдаёт признак базы, который проверяется до первого спека;
   - предохранитель: тестовый прогон падает сразу, если в базе есть брони Exely (значит, подключили рабочую).
   - Риск: спеки, которым нужен живой Channex или туннель, выделяются отдельно и в общий прогон не входят — разобрать при реализации.
6. **Документы:** ADR-042 «Автотесты в схеме pms_test», `TESTING.md`, `tests/README.md` (окна дат остаются —
   спеки всё ещё делят одну тестовую базу), строка в CLAUDE.md о том, что тесты не пишут в рабочую базу.
