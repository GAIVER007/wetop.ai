## 1. Решения владельца 27.09.2026 (Q-214…Q-216 закрыты, ADR-120)

- **Q-214 — контекст запросом, без новых колонок в `Session`.** Выбранные businessId/locationId живут
  на стороне UI как пользовательский выбор; API получает их в request context и **каждый раз**
  валидирует: Business принадлежит Organization пользователя; Location принадлежит Business;
  пользователь имеет доступ к этому scope. **Cookie/header — только указатель выбора, не источник
  доверия.** Схема `Session` не усложняется. (Владельцу этот вариант нравится и тем, что не привязывает
  рабочий контекст к одной сессии и не требует миграции ради UI-переключателя.)
- **Q-215 — переключатель у Luxx скрывать/упрощать.** У организации с ровно 1 Business + 1 Location
  человек видит просто подпись `Luxx Aparts · Алматы`, без dropdown. Переключатель появляется только
  когда реально есть что переключать.
- **Q-216 — вертикаль нового Business всегда явное поле, UX адаптивный.** Доступна только Hospitality —
  система сама ставит `vertical = HOSPITALITY` и шага не показывает; когда доступна Beauty — при
  создании Business спрашивается «Гостиничный бизнес / Салон красоты». Бессмысленный выбор из одного
  варианта человеку не показывается. (Реализация — Platform P3, К3.)

## 3. Финальный контракт RequestActor (утверждён 28.09.2026)

Расширение существующего `RequestActor` (`apps/api/src/auth/request-context.ts`, `AsyncLocalStorage`, ADR-061) —
расширяет, не заменяет:

```
RequestActor {
  userId          string            — как сегодня
  organizationId  string            — как сегодня (сессия)
  businessId?     string            — из указателя выбора, только после валидации
  locationId?     string            — из указателя выбора, только после валидации
  vertical?       BusinessVertical  — выводится из Business, никогда не приходит снаружи
  scope           ORGANIZATION | BUSINESS | LOCATION — вычисляется, никогда не приходит снаружи
  role            MembershipRole    — memberships.role; права определяет линия ролей (PR #104), не P2
  platformAdmin   boolean           — действующая отметка platform_admins
}
```

Служебные ходоки (сторож, импорт, скрипты владельца) — без RequestActor, как в ADR-061: scope к ним
не применяется.

## 4. Правило разрешения scope (точное, по шагам)

Указатель выбора: кука стойки `wetop_scope` → заголовок `X-Wetop-Scope: business=<uuid>;location=<uuid>`
в серверных вызовах API (одна обёртка `apiFetch`). Указатель — намерение пользователя, не право.

1. Сессии нет → служебный путь; scope не вычисляется (как сегодня).
2. Сессия есть, указателя нет или он пуст → `scope = ORGANIZATION`; единственный Property организации
   разрешается как сегодня (`property-ref.ts`) — переходное правило `ARCHITECTURE.md` §6, ни один
   действующий сценарий Luxx не меняется.
3. Указатель несёт `businessId` → проверка: `businesses.organization_id = actor.organizationId`.
   Прошла → `scope = BUSINESS`, `vertical` из строки Business. Не прошла (чужой, несуществующий,
   ARCHIVED) → указатель отбрасывается целиком, `scope = ORGANIZATION` (тихое падение: указатель —
   не право, устаревшая кука не должна давать 500/403 на каждый экран; фактический scope стойка
   видит в ответе).
4. Указатель несёт ещё и `locationId` → дополнительно: `locations.business_id = businessId` (и Location
   не ARCHIVED). Прошла → `scope = LOCATION`; объект — Property этой Location
   (`properties.location_id` UNIQUE в P1, резолвер `location-ref.ts` уже идёт цепочкой
   Location → Business → организация). Фолбэк по `properties.organization_id` — только миграционное окно
   (условие приёмки P1 №2), К1 новых зависимостей от него не заводит. Не прошла → как в п. 3, весь
   указатель отбрасывается.
5. `locationId` без `businessId` — неполный указатель, отбрасывается (п. 3).
6. Доступ к scope: в текущей модели любой член организации видит все её Business/Location (scope-права
   Business/Location Manager — Q-140, за владельцем, вне P2); линия ролей (ADR-107, PR #104) уже в `main`,
   таблица прав применяется к действиям как обычно — scope её не расширяет и не сужает.
7. `platformAdmin` — как сегодня: служебные экраны «Платформы»; указатель организаций не переключает
   (просмотр чужой структуры — Platform P3, «Партнёры», только чтение).
8. База под RLS дублирует всё это своим замком: `wetop_app` с `app.org_id` не видит чужих
   businesses/locations, что бы ни принёс заголовок (доказано тестами P1).

### 4а. Какой объект открывается

- `ORGANIZATION` — самый ранний объект цепочки организации (как сегодня, `property-ref.ts`);
- `BUSINESS` — самый ранний объект, чей филиал принадлежит этому Business;
- `LOCATION` — объект этого филиала (`properties.location_id` UNIQUE).

Кэш объекта в памяти — по организации, scope и id Business/Location (плюс схема базы, ADR-042): переключение не
отдаёт объект прежнего scope.

### 4б. Форматы указателя

- Заголовок API: `X-Wetop-Scope: business=<uuid>;location=<uuid>` (оба id — UUID; иной вид — указатель пуст).
- Кука стойки: `wetop_scope` с тем же текстом (URL-кодирование); серверная обёртка `backendFetch` пересылает её
  заголовком в каждом вызове API. Ставит куку переключатель Platform P3 (К2); до него куки нет, заголовка нет,
  базе нет ни одного лишнего рейса.
- Фактический scope отдаёт `GET /auth/me` полем `context: { scope, businessId, locationId, vertical }`.

### 4в. Где это в коде

- `apps/api/src/auth/scope.ts` — разбор указателя и проверки п. 3–5 (две выборки, только при указателе);
- `apps/api/src/auth/request-context.ts` — поля `scope`, `businessId`, `locationId`, `vertical` и их чтение;
- `apps/api/src/auth/author.interceptor.ts` — вычисляет scope внутри контекста организации (RLS — второй замок) и
  кладёт его в контекст обработчика;
- `apps/api/src/database/property-ref.ts` — выбор объекта по п. 4а;
- `apps/web/src/lib/api.ts` — пересылка куки заголовком.

## 5. Validation matrix

| Указатель | Проверки | Итоговый scope | Примечание |
|---|---|---|---|
| пусто | — | ORGANIZATION | сегодняшнее поведение, Luxx |
| `business=B` | B.organization_id = org сессии; B не ARCHIVED | BUSINESS | vertical из B |
| `business=B; location=L` | то же + L.business_id = B; L не ARCHIVED | LOCATION | объект — по `properties.location_id = L` |
| `location=L` без business | неполный | ORGANIZATION | указатель отброшен |
| чужой/несуществующий B или L | любая проверка не прошла | ORGANIZATION | тихо, без 500/403; право не расширено |
| подделанный заголовок мимо стойки | те же проверки на каждом запросе | не выше своей организации | плюс RLS в базе |
| служебный ходок | scope не применяется | — | ADR-061 |
| platformAdmin | указатель не переключает организацию | — | «Партнёры» — P3, чтение |

Тесты К1 (red→green): по строке на каждую строку матрицы + переходное правило + разрешение объекта
через Location-цепочку (п. 4а) + неизменность служебных путей + пересылка указателя стойкой.
