## 0. Логика в пяти пунктах

1. **Вход один — через платформу** (`app.wetop.ai`, почта и пароль). Своих паролей у ботов нет. Людей в панели
   ботов нет, всем управляют экраны платформы. Платформа ходит к ботам по внутренней сети со служебным ключом.
2. **Бот 1 — техподдержка (ИИ-помощник).** Он один на всю платформу. Пишут в него все пользователи: это их поддержка.
   Управляет им только главный администратор, в разделе «Платформа → Техподдержка».
3. **Бот 2 — ИИ-продавец.** Это платное расширение организации. Раздел «ИИ-продавец» появляется у сотрудников
   организации, когда расширение включено и оплачено. Настраивает продавца владелец организации, диалоги с гостями
   ведут все сотрудники.
4. **Расширение включает главный администратор** в разделе «Платформа → Организации» → «ИИ-продавец: оплачен до …».
   Пока это делается вручную после оплаты по счёту (умолчание Q-141). Когда появится оплата на сайте, она будет
   ставить те же поля.
5. **Права проверяет API, а не меню.** Скрытый пункт меню — удобство, запрет — это отказ сервера. Главный администратор
   видит данные платформы, но не видит брони, гостей и переписку чужих гостиниц.

## 3. Бот 1 — техподдержка (ИИ-помощник)

- **Один на всю платформу:** адрес `assistant.wetop.ai`, `BOT_ROLE=support`, стоит в общей сети с API (ADR-081).
- **Кто пишет.** Вошедший пользователь пишет с любого экрана стойки. Помощник получает подпись: кто пишет, из какой
  организации и, после этапа Э1, с какой ролью (`owner` или `staff`). Посетитель wetop.ai пишет без подписи. Чат стоит в
  общей раскладке стойки (`apps/web/src/app/layout.tsx:82-85`). Если его нужно убрать и у пользователей, это одна
  правка — скажите.
- **Кто управляет — только главный администратор**, раздел «Платформа → Техподдержка»:
  - «Диалоги»: список, карточка, «перехватить», «ответить», «вернуть боту». Видны почта и организация того, кто пишет;
  - «Знания»: загрузка документации и справочника ошибок (md, txt, pdf, docx, xlsx) и список загруженного;
  - «Сводка» за сутки: число диалогов и ответов, диалоги, оставшиеся без ответа дольше срока
    (`src/dashboard/panel_settings.py:206-240`).
- **Как это работает.** API платформы обращается к панели помощника по внутренней сети со своим ключом
  `ASSISTANT_SERVICE_KEY`. В `.env` бота этот ключ записывается в `SELLER_SERVICE_KEY`: у бота одно имя переменной для
  обеих ролей. Ключ и адрес хранятся только в `.env` API и в браузер не попадают. Бот менять не нужно.
- **Людей в панели бота нет.** `DASHBOARD_ADMIN_EMAIL` и `DASHBOARD_ADMIN_PASSWORD_HASH` остаются пустыми, пароля нет.
  `DASHBOARD_PATH_PREFIX` заполняется обязательно: без него бот не подключает маршруты панели, и платформе некуда будет
  обращаться. Наружу через туннель открыты только `/widget/*` и `/health`.
- ~~**Чего в «Техподдержке» нет и не будет.** Правки ядра правил помощника: для служебного ключа `PUT /prompt` закрыт
  намеренно (`auth_router.py:234-235`). Правила помощника меняются коммитом в репозитории.~~ **Изменено 25.09 (ADR-084)**
  по слову владельца «там так же должен настраиватся ии»: в «Техподдержке» есть «Настройки» (правила помощника текстом и
  модель из списка) и «Проверка». Ключ помощника открывает `GET/PUT /prompt` и `/settings` только при явном
  `BOT_ROLE=support`; у продавца они закрыты, как было.

## 4. Бот 2 — ИИ-продавец (платное расширение)

### 4.1. Когда раздел виден

Расширение **действует**, если у него статус «пробный» или «оплачен» и срок не вышел (или срока нет — бессрочно).
Тогда пункт «ИИ-продавец» виден всем сотрудникам организации, а раздел работает как сейчас.

Если расширение не действует:
- пункта в меню нет;
- в «Профиле» стоит карточка «ИИ-продавец не подключён» с контактом для подключения — тем же, что у кнопки
  «Попробовать бесплатно» на главной (Q-129);
- любой вызов `/ai-seller/*` получает отказ 403 «Расширение „ИИ-продавец“ не подключено» — проверка на сервере, а не
  только в меню;
- код для сайта не отдаётся (сейчас его получает кто угодно, §1).

### 4.2. Что можно в разделе

| Экран | Владелец организации | Сотрудник |
|---|---|---|
| Настройки | менять, «Применить» | смотреть |
| Данные объекта | смотреть; менять — в «Настройках гостиницы» и «Тарифах», как сейчас | смотреть |
| Знания | загружать и смотреть | смотреть |
| Диалоги | читать, перехватить, ответить, вернуть боту | то же |
| Код для сайта | смотреть и копировать | смотреть и копировать |
| Проверка | да | да |

Так предлагало ТЗ: «смотреть — все, менять — владелец» (§8 п. 3). Владелец 24.09 отложил это до появления ролей
(ADR-081, Q-175). Каждая правка, как и сейчас, записывается в журнал с автором.

### 4.3. Жизнь расширения

| Состояние | Кто ставит | Что значит |
|---|---|---|
| нет | — | строки нет, раздел не виден |
| пробный до даты | главный администратор | пробный доступ к продавцу. Пробный срок организации (7 суток) расширение само не включает |
| оплачен до даты или бессрочно | главный администратор после оплаты; в заметку — номер счёта | раздел работает. Бессрочно — например, у своей гостиницы |
| выключен | главный администратор, или срок вышел | раздел не работает; что происходит с продавцом на сайте гостиницы — Q-183 |

Переходы делает только главный администратор, каждый пишется в журнал (`extension.updated`: было, стало, автор). Цена
расширения решается вместе с тарифами WETOP (Q-143). Когда появится оплата на сайте (Q-141), платёж будет сам ставить
«оплачен до».

### 4.4. Где живёт продавец каждой организации (Q-181)

Сейчас продавец один и привязан к одной организации (`SELLER_ORGANIZATION_ID`, ADR-081). Чтобы свой продавец был у
каждой оплатившей гостиницы, есть два пути.

| | (а) своя копия бота на каждую гостиницу — как решено 24.09 | (б) один продавец на всех, поле организации в ядре бота |
|---|---|---|
| Изоляция гостиниц | полная: у каждой копии своя база | все в одной базе. Нужна защита на уровне базы (RLS) и тест «вторая гостиница ничего не видит из первой» |
| Правки в боте | не нужны | большие: организация в каждой таблице; профиль из файла в таблицу; поиск по знаниям в пределах организации; адреса сайтов по организации; организация в служебных вызовах. Снимает красное правило кита |
| Новая гостиница | вы запускаете скрипт на сервере: копия, база, ключи, адрес и правило туннеля — не мгновенно | новая строка в базе, мгновенно, без вашего участия |
| Память сервера | растёт с каждой гостиницей. В копии два процесса, каждый держит модель поиска `multilingual-e5-small` с библиотекой torch, плюс свои Postgres и Redis. Оценка — 1–2 ГБ на копию; точно покажет `docker stats` после запуска помощника | не растёт |
| Когда готово | сразу; платформе нужна таблица «организация → адрес копии» | после доработки бота, отдельным планом |

**Рекомендация — (б).** Только так каждая оплатившая гостиница получает своего продавца без вашего участия и без роста
памяти сервера. Пока (б) не готов, продавец остаётся одной копией, привязанной к вашей гостинице. Если партнёр
заплатит раньше, ему заводится временная копия по варианту (а). После перехода на (б) его данные переносятся в общую
базу.

## 5. Главный администратор (Q-184)

- **Как назначается.** Отметкой в базе (таблица `platform_admins`, §6). Ставит и снимает её только команда на
  сервере: `npm run accounts -- platform-admin --email=<почта>` и `npm run accounts -- platform-admin-revoke
  --email=<почта>`. Экрана для выдачи нет намеренно: через взломанную учётную запись нельзя назначить главным
  администратором кого-то ещё.
- **Что видит — раздел «Платформа»** (в меню он есть только у главного администратора):
  - «Организации»: название, статус и пробный срок, дата регистрации, число сотрудников, почта владельца организации
    (для счёта). Расширения — с кнопками «Включить до…», «Продлить», «Выключить»;
  - «Техподдержка» — см. §3.
- **Чего не видит.** Брони, гостей, счета и переписку гостей чужих гостиниц: раздел «Платформа» показывает только
  данные самой платформы. В своей гостинице главный администратор — её владелец, как любой другой.
- **Проверки.** Маршруты `/platform/*` открыты только вошедшему пользователю с действующей отметкой. Служебные ключи
  их не открывают, выключенная проверка входа (`AUTH_REQUIRED=0`) — тоже.
- **Второй фактор.** Это самая сильная учётная запись: она включает платные расширения и читает обращения всех
  пользователей. Сейчас у платформы есть только пароль (ADR-053). Рекомендация — добавить главному администратору
  второй фактор до первого платящего партнёра, отдельным шагом.

## 6. Модель данных — предложение v1.9 (не утверждено)

Полностью — в `DATA_MODEL.md` §16. Коротко:

| Что | Поля | Зачем |
|---|---|---|
| `memberships.role` | enum `MembershipRole`: `OWNER`, `STAFF`; NOT NULL, по умолчанию `STAFF` | роли в организации (Q-182). В существующих организациях `OWNER` получает самый ранний участник: регистрация заводит организацию, объект, человека и членство одной транзакцией (`apps/api/src/auth/auth.service.ts:236-263`) |
| `platform_admins` | `user_id` PK → `users`, `granted_at`, `revoked_at`, `note` | главный администратор (Q-184) |
| `organization_extensions` | PK (`organization_id`, `extension`); `extension` — `AI_SELLER`; `status` — `TRIAL`, `ACTIVE`, `OFF`; `active_until` (NULL — бессрочно, у пробного обязателен); `note` (номер счёта); `updated_at`, `updated_by` → `users`; `created_at` | расширение (Q-183) |

Денег в этих таблицах нет: цена и оплата появятся вместе с Q-141 и Q-143. Персональных данных гостей тоже нет.
Остальные таблицы §1–§15 не меняются. Если владелец утвердит всё вместе, это одна миграция с `down.sql` и порядком
«бэкап → миграция → проверка → откат» (AGENTS.md §15). Применяет её владелец.

## 9. Риски

- **Утечка между гостиницами при (б).** Все в одной базе, поэтому защита должна быть на уровне самой базы (RLS), а не
  только условием в запросах. Тест «вторая гостиница не видит первую» — в каждом прогоне.
- **Своя гостиница остаётся без раздела после Э2.** Защита — шаг выкладки «включить расширение своей гостинице» (Э2).
- **Организация без владельца.** Команда не даёт снять последнего владельца; заблокировать владельца может только
  главный администратор.
- **Главный администратор защищён только паролем.** Нужен второй фактор (§5).
- **Память сервера при (а).** Измерить до решения.

4. `/usr/local/sbin/wetop-auto-deploy --migrations-applied`.
5. Сразу после — отметка главного администратора и расширение своей гостиницы. Без второго пункт «ИИ-продавец» у своей

   cd /root/wetop/deploy
   A="docker compose -f compose.yml -f compose.hostinger.yml exec -w /app api node --import tsx scripts/ops/cli-accounts.ts"

   $A extension --email=ВАША_ПОЧТА --status=active --note="своя гостиница"
