# Модуль «Продвижение» (PROMO): сайт и SEO, ИИ-таргетолог, конкуренты — единый для всех направлений

Дата: 15.10.2026. Решения владельца в чате 15.10.2026 (записаны в ADR-184). Аудит текущего кода:
конструктор сайта (ADR-149, MKT1A…MKT9.2), реклама (только учёт бюджета В1/В2), конкуренты (ADR-142, COMP3).

## 0. Решения владельца 15.10.2026

1. **Единая система.** Продвижение одинаково у гостиницы, салона и ресторана: те же экраны и шаги, меняются
   только данные направления (номера / услуги и мастера / меню и столы) и слова.
2. **Сайты клиентов — на нашем домене, страницами под каждый сайт.** Отдельный домен не покупаем. Нужно решить
   технически, как отдать сайт клиента с домена платформы правильно для SEO и безопасности (см. §2).
3. **Реклама.** Запуск максимально простой для любого клиента. Приложение Meta проходим через проверку
   (App Review) — владелец подтверждает. Подтверждение запуска клиентом обязательно (деньги клиента).
4. **Конкуренты.** Выстроить всю структуру; источники и тестирование доводим дальше вместе.

## 2. Сайт и SEO

### 2.1 Где живёт сайт клиента

Варианты:
- **A. Путь на нашем домене:** `wetop.ai/s/<slug>`. Плюсы: ни DNS, ни Worker, всё уже на сервере. Минусы: все
  клиенты делят репутацию и куки одного домена; поисковик видит один большой сайт, локальное SEO клиента слабее;
  против Q-271 (там отдельный домен ради кук и репутации).
- **B. Поддомен нашего домена:** `<slug>.wetop.site` / `<slug>.sites.wetop.ai`. Поисковик считает поддомен
  отдельным сайтом, у каждого свой sitemap и robots; один wildcard DNS и маршрут на Worker `apps/sites`.
- **C. Свой домен клиента** поверх B (Cloudflare for SaaS, MKT10).

**Решение (предлагается):** B на поддомене домена платформы, который уже есть в Cloudflare, + C позже.
`SITES_BASE_DOMAIN` = зона, где wildcard `*.<зона>` указывает на Worker. Если отдельная зона невозможна,
используем `sites.wetop.ai` (поддомен, куки стойки на `app.wetop.ai` и не делятся). Что меняется в коде:
ничего в рантайме (он уже так работает); нужна выкладка Worker и переменные на сервере — это шаг владельца
или доступ к Cloudflare (`docs/deploy.md`).

### 2.2 Генерация «как Lovable»

Остаётся SiteSpec из проверенных блоков (ADR-149): сайт не ломается от правки ИИ, быстрый, безопасный, это
и даёт SEO-скорость. Lovable-опыт даём интерфейсом: «Создать сайт» → ИИ задаёт 3–4 вопроса → черновик за
минуту → правки чатом и кликом по блоку → публикация одной кнопкой.

Расширение на салон и ресторан (`site-spec/1`):
- общие секции: hero, about, features, gallery, faq, contacts, cta, reviews;
- салон: `services` (услуги и цены из каталога), `masters` (мастера), `appointment` (онлайн-запись);
- ресторан: `menu` (категории и блюда с фото), `hours` (часы работы), `table-booking` (бронь стола);
- schema.org: `BeautySalon`, `Restaurant` + `Menu`, `LocalBusiness` с часами, `AggregateRating`.

Новые публичные контракты (как `/w/*`, с Turnstile и идемпотентностью):
- `POST /w/beauty/appointments` — запись с сайта;
- `POST /w/food/reservations` — бронь стола с сайта.

### 2.3 SEO: за счёт чего сайт растёт

1. Техника (есть частично): meta, canonical, sitemap, robots, JSON-LD, скорость. Добавить hreflang ru/kk/en,
   публикацию языков, Offer/Rating.
2. Локальное SEO — главный рычаг для локального бизнеса: карточки Google Business Profile, 2ГИС, Яндекс
   Карты с теми же названием, адресом и телефоном (NAP), ссылка на сайт, отзывы.
3. Страницы под запросы: услуга × район (`/manikyur-almaly`), тип номера, кухня — генерирует ИИ из каталога,
   без выдуманных фактов.
4. Отзывы: сбор после визита (уже есть оценка заказа у ресторана) → разметка `Review` на сайте.
5. Индексация: Google Search Console и Яндекс Вебмастер (подтверждение через DNS платформы), IndexNow при
   публикации.
6. ИИ-аудит (MKT11): чек-лист по сайту с задачами «что сделать на этой неделе».

## 3. ИИ-таргетолог (реклама Meta без n8n)

Повторяем логику n8n-таргетолога внутри API:

1. **Подключить** — кнопка «Подключить Facebook» (OAuth приложения WETOP, разрешения `ads_management`,
   `ads_read`, `pages_show_list`, `business_management`, `pages_read_engagement`). Выбор рекламного кабинета и
   страницы. Токен шифруется на сервере (ключ из секретов, `SECURITY.md`).
2. **Цель** — одна из трёх: «больше записей/броней» (сообщения в WhatsApp/Instagram), «звонки», «трафик на
   сайт». Бюджет в день, город и радиус.
3. **ИИ готовит кампанию** — аудитория по направлению и городу, 3 текста, креатив из фото бизнеса (без
   сгенерированных картинок, §29.10), предпросмотр.
4. **Клиент нажимает «Запустить»** — кампания создаётся в кабинете клиента (Campaign → AdSet → Ad), сумма и
   лимит видны до нажатия. Без нажатия деньги не тратятся.
5. **Статистика и ИИ-оптимизация** — сбор метрик раз в час, советы «поднять/снизить бюджет, выключить
   объявление»; применение — тоже по нажатию.

Данные (DATA_MODEL, миграция отдельным срезом): `ad_connections` (организация, кабинет, страница, токен
зашифрованный, срок), `ad_campaigns` (локальная запись и id в Meta, статус, бюджет), `ad_operation_approvals`
(кто подтвердил, что, сумма), `ad_metrics_daily`. Адаптер `packages/integrations/meta-ads` по документации
Meta Marketing API в `/docs/integrations/meta-ads.md` (AGENTS.md §5).

## 4. Конкуренты

Структура (есть данные и экраны, ADR-142): `competitors`, `competitor_occupancy`, `competitor_rates`.

Довести:
1. Все направления: у гостиницы загрузка номеров; у салона и ресторана — цены и рейтинг/отзывы конкурентов
   (2ГИС/Google), загрузка для них не меряется.
2. «Добавить конкурента» → поиск по названию → ссылки площадок (Booking/Ostrovok/2ГИС) → число номеров.
3. Сборщик на сервере по расписанию с учётом `refresh_hours` (вместо launchd на Mac).
4. Источники: Ostrovok — работает; Booking — через партнёрский API или поставщика данных (обход защиты
   запрещён ADR-142 п. 10).
