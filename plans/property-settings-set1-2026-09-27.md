# «Настройки объекта» v2 — срез SET1: оболочка раздела и «Основное» (27.09.2026)

**Основание:** ТЗ владельца «WETOP Hospitality — „Настройки объекта“ v2» от 27.09.2026 (передано облачной
сессии задачей, 36 разделов). ТЗ само задаёт порядок: **SET1 — оболочка и «Основное», после SET1 — стоп и
снимки** (§35–36); SET2 (проживание), SET3 (услуги), SET4 (правила отмены в тарифах), SET5 (Location-скоуп)
— отдельно и только после подтверждения. Главный принцип ТЗ: сегодня экран смешивает Property,
Organization и RatePlan; в SET1 меняется подача, **не схема и не домен**.

Решение записано как **ADR-115** (DECISIONS.md).

---

## 1. Аудит перед правкой (§34 ТЗ)

| Вопрос ТЗ | Что в коде на 27.09 |
|---|---|
| Какие поля живут в `Property` | `name`, `legalName`, `bin`, `address`, `phone`, `email`, `timezone`, `currency`, `checkInTime`, `checkOutTime` (`schema.prisma`, `model Property`) |
| Что живёт в `Organization` | `name`, `status`, `trialEndsAt` — реквизитов нет. Название организации синхронизируется с названием объекта при правке (`hotel.module.ts`, `updateSettings`) |
| Откуда `legalName` / `bin` | Из `Property`. Правит владелец организации тем же `PATCH /hotel/settings`; в журнал ИИН/БИН пишется маской `••••1234` |
| Где `currency` / `timezone` | `Property`. Разбор `parseHotelSettingsPatch` их не пропускает: «меняет поддержка WETOP» |
| Где услуги | `Service` (`code`, `nameRu`, `nameKz`, `price` в тиынах, `tax`, `group`, **`active`**). Чтение — `GET /finance/services`. Записи из стойки нет: каталог только для просмотра. Удаление физически невозможно без потери связи с `Charge` — поле `active` уже есть для SET3 |
| Где правило отмены | `RatePlan.cancellationPenalty` (`NONE` / `FIRST_NIGHT` / `FULL_STAY`, умолчание — первые сутки, Q-103). Да, это свойство тарифа |
| Откуда `retired-source-*` | `RatePlan.code` импортированных тарифов (и `RatePlan.retired-sourceId` — ADR-003). В UI попадало подписью строки таблицы правил отмены |
| Что читают печатные формы | Договор и счёт: `name`, `legalName`, `bin`, `address`, `phone`, `email`, часы заезда/выезда (`print/forms.ts`, `propertyParty`) |
| Что читают сайт и бот | Модуль бронирования на сайте — часы заезда/выезда (`web-booking.service.ts`); ИИ-продавец — название, адрес, телефон, часы (`ai-seller/facts.ts`); аналитика — пояс и часы |
| Кто меняет | `updateSettings`: только вошедший владелец (`actorIsOwner`), иначе 403 «Сведения гостиницы меняет владелец организации». «Только чтение» пробного периода — `SessionGuard` отклоняет любую запись (ADR-102) |
| Журнал | Есть: `AuditLog` `hotel.settings.updated`, «было/стало» только по изменённым полям |
| Что будет при смене часов заезда/выезда | Меняется подпись в договоре и счёте, текст модуля бронирования и ответы ИИ-продавца. **Ночи и границы суток от часов не зависят** — проживание хранится датами (`DATE`, AGENTS.md §13). Поэтому фраза ТЗ §25 «используются при расчёте суток» на экран не идёт: она была бы неправдой |
| Частичная правка | `parseHotelSettingsPatch` принимает любое подмножество полей — две формы на двух вкладках не затирают друг друга, если каждая шлёт только свои поля |

**Реквизиты организации отдельной страницы не имеют**, а онбординг прямо обещает: «Название и реквизиты можно
изменить в настройках объекта» (`onboarding-form.tsx`). Поэтому в SET1 юридическое лицо — отдельный блок,
но **правка у владельца остаётся** (это и есть «compat» из ТЗ): иначе новый партнёр не сможет поправить
реквизиты, которые печатаются в договоре. Ссылки «Реквизиты организации» нет — вести ей некуда. Перенос в
Organization — после Platform P1/P2, своим решением по модели данных.

## 2. Что входит в SET1

1. **Название и меню.** «Настройки гостиницы» → «Настройки объекта» (заголовок, меню, поиск по разделам,
   подпись ссылки объекта в боковой панели). В меню пункт «Гостиница» → «Объект». Адреса не меняются:
   `/hotel-settings` остаётся (закладки, ссылки из других экранов, тесты).
2. **Один H1 на все вкладки** — «Настройки объекта», подзаголовок — название объекта (без « · », DESIGN §14).
   Вкладки `Основное | Проживание | Услуги` (`nav.settings-tabs`, как сейчас). Хлебная крошка на вкладках снята:
   раздел один.
3. **«Обновить» снята** со всех трёх вкладок.
4. **«Основное»** — одна форма из трёх блоков:
   - «Основная информация»: название объекта; телефон и почта в две колонки; адрес;
   - «Региональные настройки»: часовой пояс и валюта — только чтение, одна строка пояснения
     «Меняет поддержка WETOP: от них зависят цены, счета и границы ночей»;
   - «Юридическое лицо»: юридическое название и ИИН/БИН, одна строка «Печатаются в договоре и счёте гостя».
5. **Правая карточка «Заезд и выезд» снята.** Часы переехали на вкладку «Проживание» (два поля и одна строка о
   том, где они видны). Это перенос существующих полей, а не SET2: новых правил проверки и новых
   полей нет.
6. **Сохранение (§10 ТЗ).** Кнопка «Сохранить изменения» — в шапке экрана, выключена, пока ничего не
   изменено. После правки поля рядом с кнопкой: «• Есть несохранённые изменения». После сохранения:
   «✓ Изменения сохранены» — строкой, без постоянной зелёной карточки. Отказ API — `Alert` над формой, ввод
   не стирается (как сейчас). Уход с вкладки не блокируется (без `beforeunload`).
7. **«Правила отмены» уходят из настроек** (вкладка и пункт меню). Старый адрес `/hotel-settings/penalties`
   ведёт на «Цены и ограничения». Чтобы правило не пропало с экранов до SET4, на «Ценах» под фильтром — одна
   строка «При отмене по тарифу «Базовый тариф»: без штрафа» для выбранного тарифа. Код тарифа (`retired-source-…`) не
   показывается нигде. Полный перенос в «Тарифные планы» — SET4 после аудита тарифов.
8. **Права и «только чтение».** Форма — только владельцу и только пока организация не в «только чтении»
   (`deskShell().readOnly`, ADR-102). Иначе те же блоки фактами (`dl`), кнопки «Сохранить изменения» нет вовсе
   (DESIGN §8: действия, которого нельзя, не рисуем). Сотруднику — строка «Сведения меняет владелец
   организации». Новой логики пробного периода нет.
9. **Старые адреса:** `/hotel-settings/check-in` → `/hotel-settings/stay`; `description` → `/hotel-settings`;
   `photos`, `amenities` → `/connections#channex-connection` (как было).

## 3. Что не входит

Схема, миграции, API и домен не меняются: в `apps/api` ни одного файла, в `packages/` — только подпись раздела
в журнале ошибок человека (`assistant/user-errors.ts`: имена там «как в меню стойки»). «Услуги» — как есть,
кроме общей оболочки (жирные названия, коды, статус, drawer, «Добавить услугу» — SET3). Проверка «выезд
раньше заезда» и прочие правила проживания — SET2. «Тарифные планы» — SET4. Location/Property-скоуп,
переключатель объектов, права `property.manage` — SET5 после Platform P2. «Команда и доступы» в меню — не
этот раздел ТЗ; меню «Настройки» меняется только подписью «Объект».

## 4. Проверка

- **Красный до правки:** новый `tests/ui/property-settings.spec.ts` — H1 один на всех вкладках, вкладок три,
  «Обновить» нет, дубля «Заезд и выезд» на «Основном» нет, кнопка выключена до правки, состояния
  «есть изменения» / «сохранено» / ошибка, «только чтение», `/penalties` → «Цены» со строкой правила.
- **Зелёный после:** тот же спек + правка затронутых спеков (`settings-simplification`, `workspace`,
  `navigation`, `system-screens`, `ux-retention`, `requests`, `accessibility`), затем полный UI-набор в один
  поток (`--workers=1`), `typecheck`, `lint`, `unit`.
- **Снимки для стопа (§36):** тёмная и светлая темы на 1440, телефон 390; обычное состояние, изменённое поле,
  ошибка проверки, «сохранено», «только чтение»; «Проживание» и «Услуги» — в обеих темах.
  Папка — `reports/property-settings-set1-2026-09-27/`.

**После SET1 — стоп. SET2 и SET3 не начинаются без «да» владельца по снимкам.**
