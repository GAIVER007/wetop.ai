# «Настройки объекта» v2 — срез SET4: правила отмены в «Тарифных планах» (29.09.2026)

**Основание:** ТЗ владельца «Настройки объекта» v2 (SET4 — «правила отмены в „Тарифных планах“ после аудита»),
«давай» владельца 29.09 после SET2/SET3 и два его ответа на вопросы аудита (ниже, §2). Решение — дополнение 29.09 к
ADR-115. Вкладка «Тарифные планы» в плане «Тарифы и цены» v2 числится срезом RT4
(`plans/tz-rates-v2-2026-09-27.md` §3): владелец велел сделать её сейчас в рамках SET4. RT3 и остальное из RT4 (быстрый
просмотр, связь с категориями правкой) — отдельно.

---

## 1. Аудит

| Вопрос | Что в коде на 29.09 |
|---|---|
| Где хранится правило | `RatePlan.cancellationPenalty` (`NONE` / `FIRST_NIGHT` / `FULL_STAY`), умолчание схемы — `FIRST_NIGHT` |
| Где его видно | После SET1 — одна строка под фильтром «Цен» («При отмене по тарифу «…»: …», `rates/page.tsx`); читается из `GET /hotel/settings` |
| Где его меняют | **Нигде.** API тариф не правит; новый тариф (онбординг, «Настроить тариф» категории, ADR-119) всегда получает «первые сутки» |
| Когда правило работает | Только при отмене в день заезда и позже и при незаезде (`penaltyDue`, Q-103); сумма — `penaltyAmount` |
| Откуда правило берёт бронь | **В момент отмены из тарифа** (`reservations.repository.ts`, `it.ratePlan?.cancellationPenalty`); без тарифа — `NONE`. В брони правило не сохраняется. Так же — брони каналов (`inbound.service.ts`) |
| Уходит ли правило в Channex | Нет: в `packages/integrations` правила отмены нет |
| Кто меняет цены и тариф брони | Право `rates` — владелец и управляющий (ADR-107, Q-200) |
| Экран тарифов | «Тарифы и цены» (`/rates`, ADR-111) — одна страница-календарь; вкладок нет |

## 2. Решения владельца (29.09, ответы на вопросы аудита)

1. **Вкладка «Тарифные планы» — сейчас**, в рамках SET4: таблица тарифов с правилом отмены словами; строка правила под
   фильтром «Цен» уходит.
2. **Правило меняют владелец и управляющий, и оно действует для всех броней тарифа** — как система считает сейчас (из
   тарифа в момент отмены). Перед сохранением — сколько будущих броней это заденет; запись в журнал. Модель данных не
   меняется. Отвергнуто: «только показывать» и «старые брони — по-старому» (второе требует хранить правило в брони —
   правка модели и миграция).

## 3. Что делается

**Домен.** `parseCancellationPenalty` рядом с типом (`finance/finance.ts`): строка → политика или `null`.

**API** (модуль тарифов, право `rates`; «только чтение» закрывает запись общим механизмом, ADR-102):
- `GET /rates/plans` — тарифы объекта: код, название, валюта, действует ли, правило, названия категорий, число
  **затронутых броней** — разные брони с проживанием по этому тарифу, ещё не заехавшие и не отменённые
  (`TENTATIVE`, `CONFIRMED`), с выездом сегодня или позже по часам объекта: по ним ещё возможны отмена или незаезд.
- `PATCH /rates/plans/:code` `{ cancellationPenalty }` — неизвестное значение или поле — 400, чужой или неизвестный
  тариф — 404, то же значение — без записи; иначе одна транзакция: тариф и журнал `rate_plan.cancellation_penalty.updated`
  (было / стало и число затронутых броней).

**Стойка.** «Тарифы и цены» получает вкладки `Цены | Тарифные планы` (`.settings-tabs`, как «Аналитика» и «Настройки»):
- `/rates/plans` — таблица «Тариф | Категории | Правило отмены | Брони впереди | Статус», коды не видны; одна строка
  о том, когда правило работает; название — кнопка панели правки у того, кто может;
- панель «Правило отмены»: три варианта словами с пояснением, предупреждение «Правило действует и для уже принятых
  броней: по тарифу N будущих броней», «Отмена» / «Сохранить»; после сохранения — строка «✓ …» у таблицы;
- без права или в «только чтении» — таблица без кнопок;
- `/hotel-settings/penalties` → `/rates/plans`; строка правила на «Ценах» снята.

## 4. Что не входит

Правило в брони (снимок) и любые изменения модели; штраф по каналам и сумма штрафа (`penaltyDue`, `penaltyAmount` не
трогаются); выбор правила при создании тарифа (новый тариф — «первые сутки», правится на вкладке); переименование,
архив, связь тарифа с категориями, быстрый просмотр (RT4 целиком); RT3; Location-скоуп (SET5).

## 5. Проверка

- Red до правки: домен (`parseCancellationPenalty`), API (`/rates/plans` 404 → список, правка, журнал, отказы, права),
  таблица прав маршрутов, integration (число затронутых броней на `pms_test`), UI-спек (вкладки, таблица без кодов,
  панель, предупреждение, «только чтение», переадресация, «Цены» без строки).
- Green, затем typecheck, lint, unit, integration, живые e2e, затронутые UI-спеки в один поток (тарифы, настройки,
  отмена брони, `workspace`, навигация).
- Снимки для стопа: вкладка и панель в светлой и тёмной теме на 1440, телефон 390, «только чтение» —
  `reports/property-settings-set4-2026-09-29/`.
