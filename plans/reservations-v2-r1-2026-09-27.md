# Брони v2 — срез R1: раскладка и иерархия таблицы (27.09.2026)

**Основание:** ТЗ владельца «WETOP Hospitality · „Брони v2“» от 27.09.2026 (передано облачной сессии
задачей). ТЗ само задаёт порядок: **R1 — только раскладка и таблица, после R1 — стоп и показ
владельцу** (§64); дальше R2–R8 отдельными PR (§65). Этот план фиксирует, что именно входит в R1,
что данные уже позволяют, а что честно откладывается.

Решение записано как **ADR-104** (DECISIONS.md).

---

## 1. Аудит перед правкой (§57 ТЗ)

**Экран:** `apps/web/src/app/reservations/page.tsx` — серверная страница; GET-форма
(поиск, «С», «По», «Показать», статус-select для телефона), под ней два ряда чипов
(«Период …», «Статус …» с числами), таблица семи колонок
(Гость / Источник / Место / Проживание / Статус / Стоимость / К оплате), карточки на ≤1200 px,
пагинация «Назад/Далее». Стили — `reservations.css` + общий `directory.css` (в обоих лежит
раскладка карточек `dir-table--reservations` — два конкурирующих экземпляра).

**API:** `GET /hotel/reservations` (`apps/api/src/hotel/reservation-directory.ts`):
- серверная пагинация уже есть (page/pageSize, по умолчанию 25, потолок 200) — §33, §55 ТЗ закрыты;
- N+1 нет: один `findMany` с select по гостю, размещениям и счетам — §56 закрыт;
- фильтры: период (пересечение проживания), статус, поиск (гость/телефон/номер/номер в канале ADR-071);
- счётчики статусов по отбору без статуса (`counts`);
- строка: `confirmationNumber, status, source, channel, arrivalDate, departureDate, currency,
  totalAmountMinor, paidMinor, balanceMinor, hasFolios, unitCodes[], primaryGuest{label, phone, email}`.

**Чего в ответе нет** (нужно для v2, но не всё — для R1): `chargedMinor`/`refundedMinor`
(состояние возврата, §15–16), числа проживаний в брони (группа, §23), категории ячейки,
числа гостей, attention-признаков, сортировок, фильтров оплаты/размещения/семантики дат.

## 2. Что входит в R1 (по §64)

1. **Компактная панель управления** вместо большой карточки фильтров:
   - ряд 1: поиск + готовые отрезки «Сегодня / Завтра / 7 дней / 30 дней» компактными чипами +
     кнопка «Даты», раскрывающая «С / По» (тот же приём, что на шахматке, ADR-058); при выбранном
     пресете полей дат не видно (§62), при ручном периоде блок раскрыт сразу; «Показать» остаётся
     компактной кнопкой в конце строки — GET-форма работает без JavaScript, автоприменение
     фильтров из §6 ТЗ — вместе с новыми фильтрами в R2;
   - ряд 2: компактные чипы статусов с числами (высота `--control-h-sm`), слова «Период»/«Статус»
     сняты (§62) — ряды теперь различимы по содержимому;
   - на телефоне как раньше: чипы скрыты, статус — select в форме, «Показать» видна.
2. **Новая структура колонок** (§10): Бронь / гость → Проживание → Размещение → Источник →
   Финансы → Статус.
   - «Бронь / гость»: имя главным текстом, номер моноширинным под ним; ссылка «Открыть бронь N»
     на всю ячейку; кнопка WhatsApp из строки снята (§11 — меньше шума и ПД; телефон остаётся в
     карточке брони и гостя);
   - «Проживание»: `24 сент. → 27 сент.` + «3 ночи»; вычисляемые пометки «заезд сегодня»
     (TENTATIVE/CONFIRMED, заезд = сегодня) и «выезд сегодня» (CHECKED_IN, выезд = сегодня) — §12,
     без новых статусов в модели (§54);
   - «Размещение»: код ячейки со значком; несколько проживаний — «N размещений» (§13, §23);
     не назначено — «⚠ без ячейки» (слово DESIGN.md §9, вместо прежнего «не назначено»);
   - «Источник»: как было, компактный бейдж (канал словом);
   - «Статус»: слово о **брони** в единственном числе — «не подтверждена» (Q-135), «подтверждена»,
     «проживает», «завершена», «отменена», «незаезд» (§17 ТЗ, DESIGN.md §9; тот же приём, что
     у списка гостей 21.09). Чипы фильтра остаются во множественном («Проживают 74»).
3. **Одна колонка «Финансы»** вместо «Стоимость» + «К оплате» (§15–16): стоимость первой строкой,
   состояние — второй, по данным счётов:
   - счётов нет / счёт пуст → «—»;
   - начислено, не оплачено ни тиына → «не оплачено» (жёлтым словом);
   - оплачено частично → плашка «к оплате N ₸» (слово по DESIGN.md §14 — не «долг»);
   - баланс нулевой, оплата была → «оплачено»;
   - переплата (в т.ч. отменённая бронь с оставшимся платежом) → плашка «к возврату N ₸»;
   - всё возвращено (начислений нет, возврат покрыл оплату) → «возвращено».
   «Удержан штраф» из §16 требует видов начислений в ответе — это R6.
4. **Плотность строк** (§35): переключатель «Обычно / Компактно» справа от строки выборки,
   значение в localStorage браузера; на карточках (≤1200) не показывается.
5. **Липкая шапка таблицы** (§34) на широких экранах.
6. **Карточки на планшете и телефоне** пересобраны под шесть колонок; раскладка карточек живёт
   только в `reservations.css` (дубль из `directory.css` снят).

## 3. Правка API — только поля проекции

В строку ответа `GET /hotel/reservations` добавляются **читающие** поля, которые контроллер уже
считает, но не отдаёт: `chargedMinor`, `refundedMinor` (из того же `folioBalance`) и `itemsCount`
(длина уже выбранного `items`). Новых запросов, команд и полей схемы нет; веб читает их как
необязательные (старый ответ — прежнее поведение). Это не «изменение API» в смысле §57 —
разработчик проверил текущий ответ, недостающее названо выше и уходит в R2+.

## 4. Что честно откладывается (и почему)

| Из ТЗ | Куда | Почему не в R1 |
|---|---|---|
| Быстрые виды «Все / Будущие / Требуют внимания», «Заезды/Выезды» (§4–5) | R2 | нужна семантика даты (заезд/выезд/создана) и attention-признаки в API; R1 не меняет фильтры API |
| Фильтры «Источник / Оплата / Размещение / Категория / Дата относится к» (§29) | R2 | те же новые параметры API |
| `?view=…` и полные URL-состояния (§30), сортировки (§32) | R2 | по плану ТЗ |
| Quick preview drawer (§18–20) | R3 | по плану ТЗ |
| Кнопка «Назначить» в строке, contextual actions, «⋯», «Показать на шахматке» (§13, §36–38) | R4/R7 | действия — status-aware команды |
| «2 гостя» в первой колонке (§11), категория в «Размещении» (§13) | R2/R5 | полей нет в проекции; добавятся вместе с остальными полями списка |
| «Удержан штраф» (§16) | R6 | нужны виды начислений |
| Trial READ_ONLY (§51) | закрыт `main` (ADR-102, 27.09) | Q-144 решён: 14 дней, потом только чтение; механизм общий — полоса оболочки + отказ API на запись. «Брони» его не реализуют повторно: страница лишь прячет «Новую бронь» по флагу `readOnly` оболочки; проверка — тест «только чтение» в `reservations-v2.spec.ts` |

## 5. Правила проекта, которые ТЗ не отменяет

- DESIGN.md главнее сторонних пожеланий (CLAUDE.md §5): слово плашки долга — «к оплате» (§14),
  пустое значение «—», без капса; «без ячейки» — слово из §9.
- Плотность: «обычная» строка выходит ~52–56 px (две строки в ячейке), «компактная» ~44–48 px;
  это фиксируется в DESIGN.md §8 (строка «Отбор и таблица на „Бронях“», ADR-104) — правка правила
  раньше кода, §18.
- `data-testid` списка (`reservations-table`, `directory-meta`, `reservations-empty`,
  `reservations-error`, `reservations-loading`), имена полей `from/to/status/q/page`, aria-подписи
  «Поиск броней», «Статус брони», «Период: с/по», названия навигаций — не меняются.
- Мобильные цели ≥44 px, обе темы, axe — держит обновлённый UI-набор.
