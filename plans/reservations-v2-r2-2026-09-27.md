# Брони v2 — срез R2: server-side фильтры и URL-state (27.09.2026)

**Основание:** визуальное «да» владельца по R1 (PR #105 слит) и его же поручение на R2 от 27.09.2026.
Решение — продолжение **ADR-106** (поэтапный план ТЗ «Брони v2» §65); нового ADR нет: архитектурных
развилок срез не открывает. После R2 — **визуальный стоп**; R3 (quick preview) без отдельного «да»
не начинается.

**Не трогаем** (поручение владельца, совпадает с §66.29 ТЗ): схему Reservation/ReservationItem,
семантику Allocation, расчёт Folio/Payment, Channex, существующие mutation-эндпоинты. Новых
domain-статусов нет — «Требуют внимания» собирается только из существующих фактов.

## 1. API — `GET /hotel/reservations`, только чтение

Новые параметры (все проверяются до запроса, как существующие):

| Параметр | Значения | Смысл |
|---|---|---|
| `view` | `all` (по умолчанию) · `today` · `future` · `inhouse` · `attention` | быстрые виды. `today` — проживание пересекает «сегодня» объекта; `future` — `arrival_date > today` и статус ≠ CANCELLED, период игнорируется; `inhouse` — `status = CHECKED_IN`, период игнорируется; `attention` — см. §2, период игнорируется |
| `date` | `stay` (по умолчанию) · `arrival` · `departure` · `created` | к чему относится период `from..to`: пересечение проживания (как сейчас) / день заезда / день выезда / день создания (границы дня — по поясу объекта, `created_at` в UTC) |
| `source` | значение `ReservationSource` (без регистра) либо текст канала (подстрока, `booking` → Booking.com) | фильтр источника; токен, не совпавший с enum, ищется по `channel ILIKE` |
| `payment` | `paid` · `partial` · `unpaid` · `due` · `refund` · `refunded` | состояние счётов — те же формулы, что `finance-state.ts` (см. §3); `due` = баланс > 0 (partial ∪ unpaid) |
| `allocation` | `assigned` · `missing` · `room` · `bed` | размещение: все проживания с ячейкой / есть активное проживание без ячейки (статус TENTATIVE/CONFIRMED/CHECKED_IN) / назначена ячейка вида ROOM / вида BED (`inventory_units.kind`) |
| `category` | код `accommodation_types.code` | категория проживаний брони |
| `sort` | `arrival` · `departure` · `new` · `amount` · `debt` | ближайший заезд (asc) / ближайший выезд (asc) / новые (`created_at` desc) / сумма (`total_amount` desc) / долг (баланс desc). По умолчанию: прежний `arrival_date desc`; у `view=today` — `arrival` |

Существующие `from/to/status/q/page/pageSize` не меняются; `counts` по статусам считаются прежним
принципом — весь отбор без статуса.

**Как считается.** Отбор, сортировка и счётчики уходят в SQL (`$queryRaw` без имени схемы —
`search_path` направит в `pms_test`; через тот же пул, RLS действует): один WHERE собирается из
параметров; страница — `SELECT id … ORDER BY … LIMIT/OFFSET`; итог — `count(*)`; чипы —
`GROUP BY status`. Деньги в WHERE/ORDER — скалярные подзапросы по `reservation_items → folios`:
`charged = Σ charges.amount (voided_at IS NULL)`, `paid = Σ payment_allocations.amount`
(платёж `COMPLETED`), `refunded = Σ refunds.amount`, `balance = charged − paid + refunded` — байт в
байт формула `folioBalance` домена. Строки ответа собираются прежним Prisma-запросом по `id IN (…)`
(поля и сериализация R1 не меняются, порядок — по списку id). Запросов на страницу — 4, N+1 нет.

## 2. «Требуют внимания» — существующие факты

Ровно четыре условия (ИЛИ), все выражаются из текущих данных:

1. **без размещения**: активная бронь (TENTATIVE/CONFIRMED/CHECKED_IN) с проживанием без allocation;
2. **не заехал вовремя**: TENTATIVE/CONFIRMED и `arrival_date < today` — то же правило, что
   `overdueArrivals` Главной (`desk.service.ts`);
3. **долг гостя в доме или после выезда**: баланс > 0 при CHECKED_IN/CHECKED_OUT (будущая
   неоплаченная бронь — норма объекта, 96,5 %, вниманием не считается);
4. **деньги ждут возврата**: баланс < 0, любой статус.

«Номер не готов» (уборка) в проекции списка данных не имеет — кандидат в R6+, в срез не входит.

## 3. Веб `/reservations`

- **Ряд быстрых видов** над панелью: «Все · Сегодня · Будущие · Проживают · Требуют внимания» —
  чипы-ссылки `?view=…` (сохраняют остальной отбор, сбрасывают страницу); активный — как у чипов R1.
- **Панель**: к поиску и отрезкам добавляются компактные `Select` «Источник», «Оплата»,
  «Размещение», «Категория» (категории — из `GET /inventory/summary`), «Сортировка»; внутри
  раскрытого блока «Даты» — «Дата относится к» (проживание/заезд/выезд/создана). Всё — та же
  GET-форма с «Показать», без JavaScript-магии.
- **URL-state полный**: `/reservations?view=today&payment=due&source=booking&sort=arrival` работает
  и восстанавливает форму; сахар для Главной: `arrival=today|YYYY-MM-DD`, `departure=…` →
  `date=arrival&from&to` (страница нормализует, «today» — день объекта). Deep-links:
  «Заезды» `?arrival=today`, «Выезды» `?departure=today`, «К оплате» `?payment=due`,
  «Без размещения» `?allocation=missing`. Саму Главную не трогаем — это R7.
- Строка выборки называет действующий отбор словами (как в R1), «Сбросить фильтры» сбрасывает всё.

## 4. Фикстура и тесты

- `scripts/preview/fixture-api.ts`: подставной `/hotel/reservations` понимает те же параметры
  (view/date/source/payment/allocation/category/sort) над карточками в памяти — иначе UI-спекам и
  снимкам нечего показывать.
- Интеграционные (red → green, локальный PostgreSQL): каждый параметр против сеяных данных; паритет
  SQL-состояний оплаты с `financeState` (одни и те же брони — одинаковые состояния); сортировка по
  долгу; `counts` без статуса.
- Юнит: валидация новых параметров до запроса (мимо enum — 400).
- UI (`reservations-v2.spec.ts` + новый разд.): виды, комбинация фильтров, сахар `arrival=today`,
  URL после «Показать», пустое состояние; снимки стоп-гейта dark/light: «Сегодня», «Будущие»,
  «Требуют внимания», «Есть долг», «Без размещения», комбинация, empty state (+ строки URL — текстом
  в отчёте).
- DESIGN.md §8 — строка «Брони» дополняется рядом видов и селектами (правило раньше кода, §18).
