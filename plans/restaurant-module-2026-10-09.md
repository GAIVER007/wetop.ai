# Ресторанный модуль по ТЗ владельца (09.10.2026)

Поручение: два файла от владельца — макет «WETOP для ресторанов» (дашборд, зал, заказы, меню,
KDS, калькуляция, зарплата, клиенты) и «ТЗ — Модуль для ресторанов» v1.0 с этапами
RESTAURANT-1…6. Задача: «дизайн точь-в-точь, применить всё».

## Что уже есть (аудит)

- Модель §28: `DiningArea`, `DiningTable`, `ServicePeriod`, `RestaurantReservation`,
  `TableAssignment` (миграции 51, 58, 59). API `apps/api/src/food-service/*`, экраны
  `/floor-plan`, `/table-reservations`, `/dining-areas`, `/customers` (food), `/today` (food).
- Заказов, меню, техкарт, KDS и зарплаты нет ни в схеме, ни в API, ни в UI.
- `Employee`, `EmployeeLocation`, `WorkingHours` — бизнес-уровня, пригодны для официантов.
- `Customer` общий на организацию, брони столов уже на нём.

## Решения модели (DATA_MODEL §33, ADR-159)

1. Меню: `menu_categories`, `menu_items` (вес, цена minor units, валюта филиала, переключатель
   «в меню», текст «Технология»), `menu_item_ingredients` (норма Decimal, единица, цена за
   базовую единицу minor units). Себестоимость, food cost, наценка, прибыль — вычисляются.
2. Заказы: `restaurant_orders` (номер по филиалу, стол, официант-Employee, число гостей,
   статусы NEW → COOKING → READY → SERVED → CLOSED, отмена из NEW/COOKING/READY, снимок
   суммы), `restaurant_order_items` (снимок имени и цены, количество, комментарий).
   KDS — те же заказы по статусам, «задерживается» — производное от времени.
3. Столы: колонка `needs_cleaning` у `dining_tables` (статус «Уборка» на плане зала).
4. Зарплата: `employee_pay_settings` + `employee_pay_adjustments` по форме §19.2
   (для FOOD_SERVICE утверждено ТЗ владельца; у салона §19.2 остаётся предложением).
   Расчёт месяца не хранится: оклад + процент от заказов CLOSED официанта + корректировки.
5. Возможности вертикали: `food.menu`, `food.orders`, `food.staff`.

## Срезы

- R1 — документы: этот план, DATA_MODEL §33, ADR-159, Q-REST-1…6.
- R2 — схема и миграции №78 (домен) и №79 (права), реестр RLS, prisma generate.
- R3 — домен: статусная машина заказа, деньги техкарты, расчёт зарплаты (red → green unit).
- R4 — API: меню CRUD, заказы (создание со строками, статусы, номер), отчёт дня (плитки,
  почасовая выручка, последние заказы), сотрудники и смены, зарплата, уборка стола.
- R5 — веб: `/today` (food) по макету; `/orders`; `/kitchen`; `/menu` с техкартой;
  `/floor-plan` по макету (вкладки залов, легенда, сетка столов); `/employees` для
  FOOD_SERVICE; `/payroll`; `/customers` (food) по макету. Навигация, права, routeVertical.
- R6 — тесты: unit домена, UI-спек `tests/food-ui/restaurant.spec.ts`, прогоны по журналу.

## Что по макету сознательно не делается (и почему)

- Боковое меню оболочки: меню у стойки верхнее (DS2 ещё не начат), пункты добавляются туда.
- Фото блюд: нужна модель медиа (Q-REST-3), пока значок-заглушка.
- Рейтинг сотрудника: источника данных нет (Q-REST-2), прочерк.
- VIP и день рождения клиента: полей нет (Q-REST-4).
- Склад ресторана: бар привязан к отелю (Q-REST-5), отдельный срез.
- Выплаты и касса, фискализация: деньги за пределами статуса заказа не двигаем (Q-REST-1,
  Q-REST-6), это решение владельца по AGENTS.md §15.
- Drag-and-drop плана зала: координат у столов нет, план — сетка по залам; перенос гостей
  между столами — действием «Перенести» (без перетаскивания).

Миграции на рабочей базе применяет владелец (№78, №79) до выкладки кода.
