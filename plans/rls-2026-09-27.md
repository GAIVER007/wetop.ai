Поручение владельца 27.09.2026 (Q-152, ADR-102): «да, готовь план RLS. Код пока не писать до утверждения плана».
Публичная регистрация внешних партнёров закрыта до готового RLS; ручное подключение пилотных партнёров допустимо.

**Утверждено владельцем 27.09.2026 (ADR-103). Сделано 27.09.2026: шаги 1–4 (ниже — «Статус»); включение на сервере — `docs/ops/rls.md`.**

**До утверждения ничего из этого не делается.** Часть шагов меняет модель данных — сначала `DATA_MODEL.md` (AGENTS §2),
боевые миграции применяет владелец (AGENTS §9, §14).

## 1. Что есть сейчас (сверка кода 27.09.2026)

- В миграциях нет ни одного `ENABLE ROW LEVEL SECURITY`, `CREATE POLICY`, `CREATE ROLE`, `GRANT`. Разделение — только в
  приложении: `apps/api/src/database/property-ref.ts` выбирает объект по организации вошедшего, `withOrganizationScope`
  (`auth/request-context.ts`) — у публичного виджета и котировки продавца. Свой запрос мимо этого резолвера замок обходит
  (ADR-061).
- API ходит в базу **одной ролью** (владелец схемы, Supabase, пулер в режиме сессий, 5432, до 15 клиентов),
  `DATABASE_POOL_MAX=5` (`packages/database/src/index.ts`). Переменных сессии для арендатора нет.
- 46 таблиц по отношению к арендатору:

| Путь к организации | Таблицы |
|---|---|
| `organization_id` прямо (9) | `memberships`, `sessions`, `invites`, `user_errors`, `seller_profiles`, `organization_extensions`, `seller_agents`, `wizard_drafts` (NULL допустим), `properties` (**NULL допустим**) |
| `property_id` (9) | `buildings`, `accommodation_types`, `inventory_units`, `reservations`, `rate_plans`, `channel_mappings`, `services`, `payments`, `tracked_sites` |
| через родителя (≈21) | `floors`, `physical_rooms`, `reservation_items`, `stay_guests`, `allocations`, `guest_documents`, `housekeeping_events`, `inventory_blocks`, `rate_plan_accommodation_types`, `daily_rates`, `restrictions`, `folios`, `charges`, `payment_allocations`, `refunds`, `web_sessions`, `web_pageviews`, `web_events`, `wizard_jobs`, `wizard_messages`, `wizard_surveys`/`wizard_events` |
| **без арендатора** | `guests` (!), `audit_logs`, `external_events`, `channel_outbox`, `system_incidents` |
| глобальные по смыслу | `users`, `password_resets`, `email_verifications`, `platform_admins`, `wizard_sessions`, `organizations` |

- Работа без сессии человека: 9 фоновых циклов (`outbox.worker`, `inbound.service`, `sync.service`, `webhook-health`,
  `guard.service`, три чистки хранения, `seller-sync`), публичные пути (вебхук Channex, аналитика сайта, бронирование с
  сайта, котировка бота, мастер, вход), служебные ключи, ~33 скрипта сверки и импорта, копия базы.

## 2. Решение, которое предлагаю

**Две роли базы и переменная арендатора в каждой транзакции.**

1. Роль `wetop_app` — без `BYPASSRLS`, не владелец таблиц: ею ходит API **на запросы вошедшего человека**.
2. Роль `wetop_service` — с `BYPASSRLS`: фоновые циклы, вебхуки, служебные ключи, скрипты, миграции, копия базы. Её
   доступ — только из кода, который сам выбирает объект (как сейчас).
3. На каждый запрос человека API открывает транзакцию и первым делом `select set_config('app.org_id', '<uuid>', true)`
   (локально для транзакции — в пулере сессий переменная не протекает к следующему клиенту). В Prisma — расширение
   клиента, которое оборачивает запросы запроса в транзакцию с этой строкой; организация берётся из `request-context`.
4. Политики `USING`/`WITH CHECK` по одному правилу `app.current_org()`:
   - прямые: `organization_id = app.current_org()`;
   - по объекту: `app.property_visible(property_id)` — функция `STABLE SECURITY DEFINER` над `properties`;
   - через родителя: `EXISTS` к родителю (без копирования колонок — пока хватает скорости; замер на шаге 5).
5. `FORCE ROW LEVEL SECURITY` на все таблицы арендатора: даже владелец таблицы без `BYPASSRLS` не видит чужое.
6. Нет переменной — нет строк (`current_setting('app.org_id', true)` пуст → `NULL` → ни одна строка не проходит):
   забытая обёртка даёт пустой экран, а не чужие данные.

Почему не одна роль с `BYPASSRLS` для всего: тогда RLS работает только там, где не забыли включить, — ровно та же
слабость, что у замка в приложении.

## 3. Что меняет модель данных (DATA_MODEL v1.13 — на утверждение)

| Правка | Зачем |
|---|---|
| `properties.organization_id` — `NOT NULL` | объект без организации сейчас виден всем; перед правкой — проверка, что таких строк 0 |
| **`guests` — чьи гости** | сейчас гость общий для всех организаций и виден через брони (ADR-074). Для RLS нужен владелец строки. Варианты: (а) `organization_id` в `guests`, гость — свой у каждой организации (дубли почты между гостиницами допустимы); (б) видимость через брони (`EXISTS` по `stay_guests → reservation_items → reservations`) без новой колонки — медленнее и гость без брони не виден никому. **Рекомендую (а)** |
| `audit_logs` — `organization_id` | журнал сейчас фильтруется подзапросом по объекту (`audit/audit.module.ts:109`); колонка — одно правило вместо разбора `entity_type` |
| `external_events`, `channel_outbox`, `system_incidents` — остаются глобальными | их читает только служебная роль; стойке — через API, как сейчас. Channex — только у Luxx (ADR-099) |

## 4. Шаги (каждый — отдельный PR с тестами; боевая миграция — владелец)

0. **Утверждение**: этот план, DATA_MODEL v1.13 (п. 3), вопросы п. 6.
1. **Изоляционный набор тестов на локальной PostgreSQL** (`tests/integration/`, `scripts/ops/local-db.sh`): две
   организации, по одной строке каждой таблицы; тест ходит ролью `wetop_app` с переменной первой организации и
   проверяет, что по каждой таблице видно 0 чужих строк и чужое не вставляется. Сначала красный — политик нет.
2. **Роли и обвязка без политик**: миграция `CREATE ROLE`/`GRANT` (пароли — владелец, в `.env`), два клиента Prisma
   (`app` и `service`), расширение с `set_config`; все пути API разнесены по ролям. Поведение не меняется — проверяют
   существующие наборы (unit, integration 101, e2e 25, UI 399).
3. **Политики на прямые и объектные таблицы** (18) + `FORCE`. Изоляционный тест зеленеет по ним.
4. **Политики через родителя** (≈21) и `guests`/`audit_logs` по п. 3. Тест — зелёный целиком.
5. **Замер**: план запросов шахматки, списка броней и финансов на копии боевой базы (88 единиц, ~1000 броней в месяц);
   цель — не медленнее +20 %. Иначе — копия `property_id` в горячие таблицы отдельной правкой модели.
6. **Выкладка**: копия базы → миграции → API переключается на `wetop_app` → проверка по `docs/deploy.md` → сутки
   наблюдения. Откат: API обратно на прежнюю роль (переменная окружения), политики остаются, но их обходит владелец.
7. **Открытие регистрации** — отдельным решением владельца после шага 6 (ADR-102).

Оценка: шаги 1–4 — 4–6 рабочих дней агента с прогонами; 5–6 — день владельца на сервере.

## 5. Риски

- **Пулер Supabase**: роль `wetop_app` должна быть разрешена в пулере; `set_config(..., true)` работает в режиме сессий
  и транзакций, но **только внутри транзакции** — поэтому обёртка обязательна на каждый запрос.
- **Сырой SQL** (`$queryRaw` в `analytics`, `audit`, `finance`, `reservations`, `units`, `wizard`, `guard`, `channels`)
  идёт через ту же транзакцию — проверить каждый вызов; блокировки `FOR UPDATE` и `pg_advisory_xact_lock` не меняются.
- **Фоновые циклы** на `wetop_service` видят всё — как сейчас; их изоляция остаётся в коде (ADR-099).
- **Соединения**: второй клиент Prisma — ещё до 5 соединений при потолке 15; делить пул (3 + 2) или поднять тариф пулера.
