# Роли «управляющий» и «администратор» с разными доступами (27.09.2026)

**Поручение владельца 27.09.2026:** «главный админ сейчас тот пользователь который есть вячеслав ставь его главным
админом так же прокинуть логику добавлять сотрудников к примеру добавим сотрудника с ролью управляющего и с ролью
администратора и у каждого будут свои доступы».

**Решение:** ADR-098. **Модель:** `DATA_MODEL.md` v1.12 — §13.6 `invites.role`, §16.1 роль `MANAGER` и отключение
сотрудника, §16.5 права ролей. Облачная сессия, ветка `claude/cool-hawking-c030jv`.

## 1. Главный администратор

По ADR-083 и §16.2 отметку главного администратора ставит **только команда на сервере**: маршрута API, который пишет
в `platform_admins`, нет намеренно, а из облачной сессии нет ни сервера, ни рабочей базы. Команда для веб-терминала
сервера — в §7. Почту входа в стойку знает владелец; агент её не угадывает.

## 2. Что решил владелец

Четыре ответа (ADR-098): роль — готовый набор прав; управляющий — «всё, кроме владельческого»; администратор — работа с
гостями плюс статистика и «Оплаты» на просмотр; возврат, сторно и снятие штрафа — владелец и управляющий. Таблица прав —
`DATA_MODEL.md` §16.5, в коде — `packages/domain/src/accounts/permissions.ts`.

| Роль | Права |
|---|---|
| Владелец (`OWNER`) | все |
| Управляющий (`MANAGER`) | все, кроме `owner` |
| Администратор (`STAFF`) | `desk`, `dialogs`, `reports` |

## 3. Права маршрутов API

Проверяет глобальный замок ролей `RoleGuard` (после `SessionGuard`) по метке `@Access(…)` у метода или класса. Тест
`apps/api/src/auth/route-access.test.ts` обходит все контроллеры приложения: маршрут без `@Public()` и без `@Access()` —
красный. Без человека за запросом (служебный ключ, замок выключен в разработке) роль не проверяется.

| Маршруты | Право |
|---|---|
| `/auth/me`, `/auth/password`, `/auth/sessions`, `/auth/logout-all`, `/assistant/identity` | `self` — всем ролям |
| `/auth/invites` (создать, список, отозвать), `/auth/members` (список, отключить) | `staff` |
| `PATCH /auth/members/:userId` — смена роли | `owner` |
| `/chessboard`, `/availability`, `/reservations/*`, `/rate-plans`, `/hotel/reservations`, `/desk/*`, `/guests/*`, `/units/*`, `/finance/reservations/:n`, `/finance/services`, начисления, оплаты, закрытие счёта, `/guard/*` (кроме пробной тревоги), `/hotel/settings`, `GET /hotel/onboarding`, `/inventory/summary`, `/inventory/units`, `/system/freshness`, `/system/pii-storage` | `desk` |
| `/ai-seller/status`, `/ai-seller/summary`, `/ai-seller/conversations/*` | `dialogs` |
| `GET /finance/report` | `reports` |
| `POST /finance/charges/:id/void`, `POST /finance/payments/:id/refunds`, корректировка на уменьшение (в `addCharge`) | `refunds` |
| `/inventory/categories`, `/inventory/rooms` | `property` |
| `/rates/*` | `rates` |
| `/channels/channex/*` (кроме webhook — публичный), `/hotel/channel-report` | `channels` |
| `/analytics/sites/*`, `POST /hotel/onboarding`, `/system/connection`, `POST /guard/alert/test` | `settings` |
| `GET /audit` | `journal` |
| остальное `/ai-seller/*`, `/seller-agents/*` | `seller` |
| `/platform/*` | `platform` — только главный администратор |
| `/assistant/errors`, `/assistant/organization` | `service` — только служебный ключ |

Внутри сервисов прежние проверки «только владелец» (`actorIsOwner`) заменены правом (`actorMay`): настройки продавца —
`seller`, агенты — `seller`, приглашения — по ролям (§4). Напоминание о продлении расширения — только владельцу.

## 4. Сотрудники и приглашения

- `POST /auth/invites` принимает `role`: `manager` или `staff` (по умолчанию `staff`). Владелец зовёт обоих,
  управляющий — только администратора, иначе 403. Письмо и журнал (`user.invited`) называют роль.
- `GET /auth/invites` — ожидающие приглашения с ролью и признаком «можно отозвать». Отзывает тот, кто вправе позвать с
  этой ролью.
- Принятие заводит членство с ролью из приглашения; уже состоящему роль не меняет.
- `GET /auth/members` — люди организации: имя, почта, роль, дата, «это вы», можно ли отключить и менять роль.
- `DELETE /auth/members/:userId` — отключить: владелец — управляющих и администраторов, управляющий — администраторов;
  себя и владельца — нет. Удаляет членство, пишет `membership.removed`; сессии гаснут на следующем запросе.
- `PATCH /auth/members/:userId` — владелец меняет роль между «управляющий» и «администратор»
  (`membership.role.updated`). Владельца назначает только команда на сервере.
- Команда сервера `accounts -- role` понимает `--role=manager`.

## 5. Стойка

- Подписи ролей: «Владелец», «Управляющий», «Администратор» (было «сотрудник»).
- Меню по правам: у пунктов `requires` — право из домена; администратор видит «Работа с гостями», «Оплаты»,
  «Статистика», «ИИ-продавец» (диалоги), «Неисправности». Пока `/auth/me` не ответил, меню — как у администратора.
  Никто не вошёл (замок выключен в разработке) — меню целиком, как раньше.
- Закрытая страница, открытая по адресу, вместо содержимого говорит, кому раздел открыт (`AccessGate` в макете,
  путь — из заголовка `x-wetop-path`).
- Карточка брони: у администратора нет кнопок «Вернуть» и «Сторно»; корректировку на уменьшение отклоняет сервер.
- «ИИ-продавец»: администратору — только «Диалоги» (адрес раздела ведёт туда), кнопки «Все агенты» нет.
- Учётная запись (`/login`): блок «Сотрудники» — пригласить с выбором роли, список людей с ролями, «Отключить»,
  смена роли (владелец), ожидающие приглашения с ролью и «Отозвать». Администратору — строка, кто приглашает.
- Фикстура UI (`scripts/preview/fixture-api.ts`) понимает роль `MANAGER`, сотрудников и приглашения с ролью.

## 6. Миграция и выкладка

`20260927000025_manager_role`: `ALTER TYPE "MembershipRole" ADD VALUE 'MANAGER'`; `invites.role` NOT NULL DEFAULT
`STAFF` с CHECK `role <> 'OWNER'` (новое значение в той же миграции не используется — PostgreSQL этого не разрешает).
`down.sql`: колонку убрать, управляющих перевести в администраторов, тип пересоздать без `MANAGER`. Проверка —
`scripts/ops/check-migrations.sh`.

**Порядок — сначала миграция, потом код**: новый код пишет `invites.role`, без колонки приглашения не создаются.

## 7. За владельцем

1. Бэкап, миграция `20260927000025_manager_role` на рабочей базе, проверка
   `select enum_range(null::"MembershipRole"); select role, count(*) from invites group by role;`.
2. Главный администратор — в веб-терминале сервера:
   ```bash
   cd /root/wetop/deploy
   A="docker compose -f compose.yml -f compose.hostinger.yml exec -w /app api node --import tsx scripts/ops/cli-accounts.ts"
   $A platform-admin --email=ПОЧТА_ВХОДА_В_СТОЙКУ --note="владелец WETOP"
   $A list
   ```
3. Слияние PR и перенос `release`.

## 8. Проверка

- Домен: таблица прав, кто кого приглашает и отключает, подписи ролей — `packages/domain/src/accounts/*.test.ts`.
- API: у каждого маршрута есть право (обход контроллеров); замок ролей на живых контроллерах — администратору 403 на
  возврат, тарифы, каналы, журнал, настройки продавца; управляющему — 403 на приглашение управляющего и смену роли;
  приглашения и сотрудники по ролям; корректировка на уменьшение.
- Интеграция (PostgreSQL): миграция — `MANAGER` в типе, `invites.role` с CHECK; принятие приглашения даёт роль;
  отключение удаляет членство и гасит сессию.
- UI: меню и закрытые страницы у администратора и управляющего, форма приглашения с ролью, кнопки возврата.
