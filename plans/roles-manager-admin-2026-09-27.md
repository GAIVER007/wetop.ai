# Роли «управляющий» и «администратор» с разными доступами (27.09.2026)

**Поручение владельца 27.09.2026:** «главный админ сейчас тот пользователь который есть вячеслав ставь его главным
админом так же прокинуть логику добавлять сотрудников к примеру добавим сотрудника с ролью управляющего и с ролью
администратора и у каждого будут свои доступы».

**Решение:** ADR-106. **Модель:** `DATA_MODEL.md` v1.14 — §13.6 `invites.role`, §16.1 роль `MANAGER` и отключение
сотрудника, §16.5 права ролей. Облачная сессия, ветка `claude/cool-hawking-c030jv`.

## 1. Главный администратор

По ADR-083 и §16.2 отметку главного администратора ставит **только команда на сервере**: маршрута API, который пишет
в `platform_admins`, нет намеренно, а из облачной сессии нет ни сервера, ни рабочей базы. Команда для веб-терминала
сервера — в §7. Почту входа в стойку знает владелец; агент её не угадывает.

## 2. Что решил владелец

Четыре ответа (ADR-106): роль — готовый набор прав; управляющий — «всё, кроме владельческого»; администратор — работа с
гостями плюс статистика и «Оплаты» на просмотр; возврат, сторно и снятие штрафа — владелец и управляющий. Таблица прав —
`DATA_MODEL.md` §16.5, в коде — `packages/domain/src/accounts/permissions.ts`.

| Роль | Права |
|---|---|
| Владелец (`OWNER`) | все |
| Управляющий (`MANAGER`) | все, кроме `owner` |
| Администратор (`STAFF`) | `desk`, `dialogs`, `reports` |

## 3. Права маршрутов API

Проверяет глобальный замок ролей `RoleGuard` (после `SessionGuard`) по метке `@Access(…)` у метода или класса. Тест
`apps/api/src/auth/route-access.test.ts` обходит все контроллеры приложения: маршрут без `@Public()` и без `@Access()` —
красный. Без человека за запросом (служебный ключ, замок выключен в разработке) роль не проверяется.

## 4. Сотрудники и приглашения

- `POST /auth/invites` принимает `role`: `manager` или `staff` (по умолчанию `staff`). Владелец зовёт обоих,
  управляющий — только администратора, иначе 403. Письмо и журнал (`user.invited`) называют роль.
- `GET /auth/invites` — ожидающие приглашения с ролью и признаком «можно отозвать». Отзывает тот, кто вправе позвать с
  этой ролью.
- Принятие заводит членство с ролью из приглашения; уже состоящему роль не меняет.
- `GET /auth/members` — люди организации: имя, почта, роль, дата, «это вы», можно ли отключить и менять роль.
- `DELETE /auth/members/:userId` — отключить: владелец — управляющих и администраторов, управляющий — администраторов;
  себя и владельца — нет. Удаляет членство, пишет `membership.removed`; сессии гаснут на следующем запросе.
- `PATCH /auth/members/:userId` — владелец меняет роль между «управляющий» и «администратор»
  (`membership.role.updated`). Владельца назначает только команда на сервере.
- Команда сервера `accounts -- role` понимает `--role=manager`.

## 5. Стойка

- Подписи ролей: «Владелец», «Управляющий», «Администратор» (было «сотрудник»).
- Меню по правам: у пунктов `requires` — право из домена; администратор видит «Работа с гостями», «Оплаты»,
  «Статистика», «ИИ-продавец» (диалоги), «Неисправности». Пока `/auth/me` не ответил или ответил сбоем, меню и кнопки —
  как у администратора; страница по адресу при сбое открывается как есть (`pageOpen`): решает API, а «нет доступа»
  было бы неправдой. Никто не вошёл (замок выключен в разработке) — меню целиком, как раньше.
- Закрытая страница, открытая по адресу, вместо содержимого говорит, кому раздел открыт (`AccessGate` в макете —
  клиентский: путь из `usePathname()` меняется на каждом переходе, а корневой макет Next при переходах по ссылкам не
  перерисовывается).
- Первичная настройка (`/onboarding`) по адресу не закрыта: гейт ведёт туда всех, пока в отеле нет номеров, и
  администратору страница говорит, что настройку делают владелец и управляющий.
- Карточка брони: у администратора нет кнопок «Вернуть» и «Сторно» и подсказки «можно −» у корректировки;
  корректировку на уменьшение отклоняет сервер.
- «ИИ-продавец»: администратору — только «Диалоги» (адрес раздела ведёт туда), кнопки «Все агенты» нет.
- Учётная запись (`/login`): блок «Сотрудники» — пригласить с выбором роли, список людей с ролями, «Отключить»,
  смена роли (владелец), ожидающие приглашения с ролью и «Отозвать». Администратору — строка, кто приглашает.
- Фикстура UI (`scripts/preview/fixture-api.ts`) понимает роль `MANAGER`, сотрудников и приглашения с ролью.

## 6. Миграция и выкладка

`20260927000029_manager_role`: `ALTER TYPE "MembershipRole" ADD VALUE 'MANAGER'`; `invites.role` NOT NULL DEFAULT
`STAFF` с CHECK `role <> 'OWNER'` (новое значение в той же миграции не используется — PostgreSQL этого не разрешает).
`down.sql`: колонку убрать, управляющих перевести в администраторов, тип пересоздать без `MANAGER`. Проверка —
`scripts/ops/check-migrations.sh`.

**Порядок — сначала миграция, потом код**: новый код пишет `invites.role`, без колонки приглашения не создаются.

## 8. Проверка

- Домен: таблица прав, кто кого приглашает и отключает, подписи ролей — `packages/domain/src/accounts/*.test.ts`.
- API: у каждого маршрута есть право (обход контроллеров); замок ролей на живых контроллерах — администратору 403 на
  возврат, тарифы, каналы, журнал, настройки продавца; управляющему — 403 на приглашение управляющего и смену роли;
  приглашения и сотрудники по ролям; корректировка на уменьшение.
- Интеграция (PostgreSQL): миграция — `MANAGER` в типе, `invites.role` с CHECK; принятие приглашения даёт роль;
  отключение удаляет членство и гасит сессию.
- UI: меню и закрытые страницы у администратора и управляющего, форма приглашения с ролью, кнопки возврата.

## 9. Ревью 27.09 (агент-проверяющий, только чтение) и что сделано

Серьёзных обходов нет: каждый маршрут сверен с таблицей, изоляция организаций в сотрудниках и приглашениях держится,
миграция корректна. Подтверждённое исправлено, каждое — красным тестом первым:

- **Сессия действия проверяется полностью.** Замок входа читает заголовки, а контроллер приглашений и сотрудников —
  сначала куку; служба проверяла у такой сессии только срок и отзыв. Теперь — как при входе: приостановленная
  организация (С-4), заблокированный человек, снятое членство (С-10) — отказ 401.
- **Запись по роли в момент записи.** Отключение и смена роли сверяют роль под блокировкой строки (`FOR UPDATE`):
  управляющий не удалит человека, которого владелец только что повысил; повторное «Отключить» — 404, а не 500.
- **Полная сверка с Channex (`POST /guard/tick?all=1`)** — только с правом `channels`; обычная «Проверить сейчас» — всем.
- **Стойка** (после полного UI-прогона): при сбое `/auth/me` меню и кнопки — как у администратора, а не «всё»; страница
  по адресу при этом открывается — следующий полный UI-прогон показал, что иначе при недоступном API владелец видел
  «Нет доступа… ваша роль — администратор» вместо «Нет связи с рабочим API» (`real-data`, `workspace`);
  первичная настройка для администратора — «ждём владельца или управляющего» вместо тупика; подсказка «можно −» у
  корректировки — только тем, кому можно уменьшать счёт; непонятная роль в форме приглашения — отказ, а не
  «администратор».

Вопросы, а не дефекты: смена тарифа брони администратором — Q-199 (закрыт 27.09, §11); плашка «входящая бронь требует разбора» на шахматке у
администратора не видна (о сбое ему говорит неисправность на экране «Неисправности»); журнал организации показывает
изменения расширения с именем главного администратора; отключение человека не гасит выписанные им приглашения — они
принадлежат организации, отзывает их владелец или управляющий.

## 11. Тариф брони (Q-199, ответ владельца 27.09 — «нет не могут»)

Тариф — цена и правило штрафа брони, поэтому у существующей брони его меняют владелец и управляющий: право `rates`
(`DATA_MODEL.md` §16.5, ADR-106). Администратор меняет даты, продлевает и переселяет в том же тарифе; новую бронь с
выбором тарифа создаёт, как раньше.

- **API** (`reservations.service.ts`): смена дат, продление, переселение в другую категорию и их предпросмотры берут
  тариф через одну проверку — другой тариф или тариф брони без него (из Exely) у администратора — отказ 403 словами
  (`RATE_PLAN_CHANGE_MESSAGE`, `RATE_PLAN_UNKNOWN_MESSAGE` в домене). Проверка — до первой записи; без человека за
  запросом (служебный ключ) — как раньше.
- **Стойка** (карточка брони → «Действия»): у администратора нет выбора тарифа при смене дат, продлении и переселении;
  у брони без тарифа — слова «даты пересчитывают владелец или управляющий» вместо кнопки, а «Продлить на ночь»
  неактивна с причиной из предпросмотра. Стенд UI отвечает, как API.
- **Q-200** (открыт на момент §11, закрыт — §12): брони из Exely тариф на проживании не приносят; до ответа их пересчёт
  делали владелец и управляющий. Рекомендация — разрешить администратору назначить тариф один раз и только со штрафом
  не мягче «первых суток».

## 12. Бронь без тарифа (Q-200, ответ владельца 27.09 — «Да, разрешить»)

Брони из Exely без тарифа администратор назначает тариф один раз и только со штрафом не мягче «первых суток»
(`FIRST_NIGHT` или `FULL_STAY`); тариф записывается в бронь, дальше его меняют владелец и управляющий (§11). Без тарифа
штрафа нет (`NONE`, Q-103, `DEFAULT_CANCELLATION_PENALTY`), так что назначенный тариф штраф добавляет, а не снимает.

- **Домен** (`packages/domain/src/accounts/permissions.ts`): `mayAssignPlanWithoutRates` — можно ли администратору такой
  тариф; `plansToChoose` — какие тарифы стойка предлагает: с правом `rates` — любой, у брони с тарифом — никакого, у
  брони без тарифа — только со штрафом. Одно правило на отказ API и списки стойки. Отказ `RATE_PLAN_UNKNOWN_MESSAGE`
  §11 заменён `RATE_PLAN_SOFT_MESSAGE`.
- **API**: без выбора тарифа у брони без тарифа — 400 «ratePlanCode обязателен» для всех ролей (стойка просит выбрать);
  тариф без штрафа от администратора — 403 словами; продление брони без тарифа теперь записывает выбранный тариф (смена
  дат и переселение в другую категорию записывали и раньше); `GET /rate-plans` отдаёт правило штрафа тарифа.
- **Стойка**: у брони без тарифа администратор видит выбор тарифа при смене дат, продлении и переселении — только тарифы
  со штрафом; после записи выбор пропадает. Если тарифов со штрафом нет — слова «пересчитывают владелец или
  управляющий». Стенд UI: у тарифа правило штрафа, `softPlan` добавляет тариф без штрафа, отказ и запись тарифа — как в
  API.
- **Проверки** (журнал `tests/runs/`): домен и API red → green (`…14-44-54Z` → `…14-45-39Z`, `…14-46-02Z` →
  `…14-49-19Z`, `…14-51-02Z` → `…14-51-11Z`); UI red на старой панели стойки (`…14-58-04Z-e2e-7588.log`) → 34/34
  (`…14-59-52Z-e2e-fae7.log`); unit 2162/2165, integration 107/107, живые e2e 25/25 и со входом 26/26, typecheck и
  lint чисто.
- Попутно: сводка `QUESTIONS.md` — строку Roles при записи ответа на Q-199 затёрла строка Q-200, а в разделе Roles
  Q-200 остался открытым; исправлено.
