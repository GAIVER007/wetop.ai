# M4-A: клиент без записи

Статус: план по ТЗ 4 подтверждён; модель phoneNormalized и уникальности утверждена владельцем 18.10.2026. Ветка codex/salons-tz4-m4a от main, отдельно от draft PR #660.

## Цель и диагноз

Сейчас BeautyCatalogController имеет GET клиентов и PATCH меток, но POST отсутствует. Создание записи находит клиента по сырому телефону; уникальность БД также по сырому телефону. Новый клиент поэтому требует записи, а разные формы одного номера могут стать дублями.

## Изменение и границы

Добавить канонический nullable ключ телефона с DB trigger/UNIQUE организации, самостоятельный POST и форму через существующие Overlay/Field/Input/Button. Сохранить исходный номер. Переиспользовать канонический поиск для существующих путей Beauty и публичных форм, обновить изолированную UI-фикстуру. Карточка, импорт/merge, новые поля профиля, маркетинг, оплата и согласия в срез не входят.

## Проверка

Сначала красный HTTP-тест POST и тест отсутствующего ограничения базы. Затем parser, API/права/scope/повторы/архив, разные формы телефона, конкурентный UNIQUE, неизменность исходного ввода и rollback. PostgreSQL только в принадлежащем срезу локальном кластере; общая dev-БД не используется. Браузерный путь на подставном API с отдельными портами, 375 px и axe, затем typecheck/lint. Все прогоны через test:record.

## Выпуск миграции владельцем

1. Сделать backup и подтвердить восстановление на отдельном стенде по docs/ops/backups.md, если этот runbook применим к рабочему окружению; точный действующий runbook сверить перед production.
2. Выполнить preflight на копии: нормализация и число групп коллизий/неподдерживаемых строк. В stdout только агрегаты, без телефонов и имён. При коллизиях STOP, отдельное решение о карточках. Автоматического merge нет.
3. В окно применения выполнить миграцию одной транзакцией с ON_ERROR_STOP. Она блокирует concurrent writes customers на время backfill/index и сама повторяет проверку коллизий под замком.
4. Validation: число клиентов и исходные phone не изменились; ожидаемые нормализованные значения совпадают; дубль в Organization отклоняется; разные организации разрешены; RLS и CustomerBusiness остаются прежними.
5. После owner-applied migration действует штатный release gate. Агент production-команды не выполняет.

## Откат

Сначала отключить новый путь и вернуть совместимый код, затем down.sql одной транзакцией. Удаляется только производный ключ, trigger, функция и его индекс; исходные phone, клиенты, связи и audit сохраняются. Исходный UNIQUE сырого телефона остаётся. Если срез уже создавал клиентов, их не удалять. Production rollback выполняет владелец.
