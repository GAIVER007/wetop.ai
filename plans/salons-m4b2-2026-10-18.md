# M4-B2: сохранение клиентов и безопасная отмена импорта

Дата: 18.10.2026. Ветка codex/salons-tz4-m4b2 от main 89900c55d, где PR #663 уже слит. Статус: модель и все условия явно утверждены владельцем 18.10.2026. Реализация и проверки выполняются в отдельной ветке. Production-миграцию применяет владелец.

## 1. Цель и диагноз

M4-A даёт самостоятельное создание клиента и канонический телефон. M4-B1 проверяет CSV локально. Следующий результат: после подтверждения проверки владелец загружает строки, получает устойчивую к перезапуску задачу с прогрессом и итогом, может отменить её в пределах утверждённого срока без потери записей и ручных изменений.

Повторное использование одиночного POST в цикле недопустимо: нет журнала импорта и атомарного undo. Один JSON на 50 000 строк также не годится: API по умолчанию принимает 100 КБ. Beauty-транзакции имеют timeout 10 секунд, поэтому вся обработка не должна держать одну транзакцию.

## 2. Утверждённые условия

Предложение из DATA_MODEL.md, SL4-M4B-PROPOSAL-20261018:

1. Первый пишущий срез не сливает старые карточки и не перезаписывает существующий профиль. Находит по каноническому телефону, использует существующую карточку и при необходимости создаёт CustomerBusiness. Созданные карточки/связи фиксируются в журнале; отмена до 24 часов от завершения, только если безопасна.
2. Строки с одним телефоном: отображаемое имя «Клиент» либо пропуск без создания. Срок хранения содержимого строк предлагается 30 дней, после него остаются только агрегаты и безопасный audit. Владелец утвердил имя «Клиент» для валидного телефона без имени и хранение содержимого 30 дней.

Полный merge из ТЗ (перенос истории, платежей, тегов и откат слияний) отдельным срезом. Маркетинговые согласия не создаются из наличия телефона или факта импорта. Импорт ограничен уже проверяемыми именем, фамилией и телефоном; расширение полей и XLSX отдельными срезами.

## 3. Предложение технической модели

Утверждённая модель (подтверждение SL4-M4B-OWNER-APPROVAL-20261018 в DATA_MODEL.md):

- CustomerImport: tenant/business, actor, clientRequestId, состояние, ожидаемое/загруженное/обработанное число строк, счётчики исходов, upload checkpoint, lease token/expiry, attempts/nextAttemptAt, createdAt/completedAt/undoDeadline/contentsExpireAt, безопасный errorCode. Все времена событий UTC.
- CustomerImportRow: tenant/import, порядковый номер записи и физическая строка CSV, проверенные поля ввода, состояние/причина, customerId, исход CREATED/LINKED/UNCHANGED/SKIPPED, владение созданной связью, baseline состояния клиента/связи для undo. Уникальность (importId, ordinal), индексы очереди и tenant. Существующая модель Customer и других сущностей не расширяется.
- Состояния: UPLOADING -> QUEUED -> PROCESSING -> COMPLETED, отдельный FAILED с сохранённым checkpoint; COMPLETED -> UNDOING -> UNDONE. Срыв lease возвращает обработку к последнему зафиксированному checkpoint, не стирает результаты.
- Содержимое строки и baseline считаются персональными данными даже в виде хеша. Они недоступны публично и не попадают в audit, stdout, traces или тексты ошибок. Source filename и исходный CSV не сохраняются по умолчанию. Retention очищает поля/снимки, а не карточки клиентов.
- Незавершённые загрузки очищаются вместе с содержимым по тому же утверждённому TTL, без запуска задачи. При очистке сначала берётся lock задачи, чтобы не состязаться с worker/undo.

## 4. Контракт API (предложение)

Все маршруты под /beauty/customer-imports. Организация и бизнес определяются серверной авторизацией; scope из тела не принимается. Проверка capability beauty.customers и write-доступа повторяется в транзакции. Для запуска, отмены и отчёта утверждён OWNER-only доступ.

| Метод и путь | Назначение | Повтор/конфликт |
|---|---|---|
| POST / | Создать UPLOADING с clientRequestId и totalRows <= 50 000 | тот же ключ и параметры возвращают ту же задачу; другие параметры 409 |
| PUT /:id/rows | Загрузить следующий ограниченный пакет mapped raw rows с offset | тот же пакет и digest не добавляет строк; тот же offset с другим содержимым 409 |
| POST /:id/submit | Повторно проверить полноту и поставить в QUEUED | повтор возвращает текущее состояние, не создаёт вторую задачу |
| GET /:id | Состояние, прогресс и безопасные счётчики | чужая задача 404, без выдачи её существования |
| GET /:id/rows | Постраничный отчёт строк своего импорта | защищённый доступ, ограниченная страница; содержимое после TTL недоступно |
| POST /:id/undo | Запросить атомарную отмену завершённого импорта | истёк срок/появилась активность/менялись данные 409; повтор UNDONE без повторного удаления |

Старт/submit/undo не передают персональные данные в URL. Ошибки следуют текущему API: 400 формат, 403 права/read-only, 404 недоступная задача, 409 конфликт состояния/повтора/undo, 413 слишком большой запрос. Причины не содержат имени или телефона.

Передача пакетами с UTF-8 размером сериализованного тела до 64 КБ и ограничением числа строк; общий лимит API 100 КБ не повышается. UI формирует пакет по реальному размеру JSON, а не только количеству строк. Server action также ограничивает пакет; сервер заново проверяет raw rows и нормализует телефоны. Флаги ready/duplicate, canonical key, customerId, audit actor и scope из браузера игнорируются.

## 5. Пакеты, транзакции и восстановление

Загрузка ещё не создаёт клиентов. Только после submit обработка берёт строки из durable PostgreSQL queue. Образец: marketing-site/generation.worker.ts, но без внешнего ИИ, тарифов и usage-контуров.

Claim короткой транзакцией с FOR UPDATE SKIP LOCKED, lease token, сроком и ограничением параллельности. Claim не держит блокировку задачи во время ожидания родительских beauty-locks. Пишущая транзакция придерживается порядка: организация -> бизнес/филиал -> задача -> клиенты в стабильном порядке. Lease проверяется перед записью, старый worker не может дописать результат после повторного claim.

Каждая ограниченная пачка атомарно фиксирует клиентов/связи, исходы строк и checkpoint. Если процесс упал после commit, следующая попытка читает checkpoint и не повторяет создание. Если до commit, вся пачка откатывается. UNIQUE канонического телефона защищает гонки с ручным созданием в другом бизнесе; P2002 требует rollback и повторной сверки всей пачки в новой транзакции, а не продолжения внутри aborted transaction.

Права и write-состояние организации проверяются на каждом пакете. Worker не подставляет роль OWNER из сохранённой строки: служебный путь проверяет актуальное разрешение actor и tenant либо завершает задачу безопасным кодом. Ошибка БД не сохраняется как необработанный message. Прогресс показывает загружено/обработано/создано/использовано/пропущено; частичный результат не выдаётся за завершённый импорт.

В первой версии не запускать несколько пишущих пачек одной организации одновременно. Никаких внешних сервисов или новых queue-зависимостей.

## 6. Безопасное undo

Undo не является удалением всех клиентов по номеру телефона или диапазону createdAt. Используется только журнал операций данной задачи. UNCHANGED не удаляется; существующий профиль не откатывается, поскольку его не меняли.

Перед удалением в одной транзакции блокируются задача и затронутые карточки. Проверяются baseline состояния/связи, дополнительные привязки, Appointment и RestaurantReservation, в том числе отменённые и чужого бизнеса, если удаляется целая созданная карточка. Для удаления только новой привязки проверяются обращения именно в этом бизнесе. Проверка и удаление не разделяются сетевым ожиданием. Любой конфликт откатывает весь undo; результат включает безопасные причины/число конфликтов, без частично удалённых клиентов.

Не использовать cascade для удаления визитов, денег или audit. Блокировки карточки должны сериализовать конкурентный INSERT обращения через FK; это необходимо доказать реальной двухсоединительной проверкой, а не моками. Список всех FK на customers инвентаризуется до реализации undo; неучтённые связи блокируют удаление.

Важная проверка до обещания 50 000 строк: атомарный undo в собственном PostgreSQL должен укладываться в измеренный бюджет транзакции. Текущий beautyTransaction timeout 10 секунд не увеличивается вслепую. Если bulk undo не укладывается, сначала пересмотреть технический план; не заменять атомарность поэтапным удалением без решения владельца.

## 7. Проверка и критерий готовности

Red-before-green, только test:record, собственный синтетический PostgreSQL и отдельные UI-порты. Сначала отсутствующий контракт/идемпотентность/отмена дают RED. Затем:

- Scope/RLS: чужая организация, другой бизнес, поддельный actor/scope/статус/ключ, потеря write-права между пакетами.
- Загрузка: 50 000 строк; лимит 64 КБ по UTF-8; повтор пакета после network timeout; другой payload под тем же offset; upload не создаёт клиентов; неполная загрузка не запускается.
- Обработка: канонические повторы в одном/разных пакетах, конкурирующее ручное создание, архивный клиент, номер без имени по выбранному правилу, имя без номера, неверные строки, crash до/после commit, устаревший lease, повтор submit.
- Undo: 24 часа минус/ровно/плюс граница после утверждения точного сравнения; изменение карточки/связи; обращение в Beauty и Food; гонка обращения с undo; повтор undo; отсутствие потери прежних клиентов/истории/денег; rollback при конфликте последней строки.
- Retention: очистка только истёкшего содержимого, сохранение агрегатов, отсутствие гонки с active worker/undo, отсутствие PII в audit/logs.
- Performance: реальная задача на 50 000 синтетических строк, прогресс, восстановление процесса и bulk undo с замером времени/ресурсов.
- Браузер: исходный файл/сопоставление не теряются при ошибке; прогресс не обещает готовность до COMPLETED; reload открывает ту же задачу; повторы не создают вторую; кнопка undo показывает доступность и причину 409; desktop/mobile, axe, typecheck/lint.

Готовность среза: новый клиент появляется без визита, повтор телефона не меняет существующую карточку, повтор запроса не дублирует данные, после restart обработка продолжается, безопасный undo возвращает прежний набор, а конфликтное undo ничего не удаляет. Полный merge старых дублей и XLSX не считаются выполненными.

## 10. Уточнения после read-only review

Этот раздел конкретизирует требования выше; он также остаётся предложением до утверждения модели.

**Авторизация worker.** Прямой вызов mayBeautyWrite вне HTTP-контекста не подходит. Отдельный серверный путь на каждом пакете читает User.status=ACTIVE, Membership по (createdBy, organizationId), status=ACTIVE и фактическую разрешённую роль. В предложенном owner-only варианте это OWNER. Затем проверяет актуальные Organization/canWrite и Business.status/vertical/organizationId. Actor и tenant берутся из защищённой задачи. Сохранённая роль, тело запроса и cookie worker не авторизуют. Если позже допускаются другие роли, путь должен учитывать полноценный Access и MembershipScope, а не только роль.

**Блокировки и fencing.** Claim блокирует только строку задачи и завершает commit до parent locks; код generation.worker.ts не копируется целиком. Каждая пишущая batch-транзакция сначала берёт PostgreSQL transaction advisory try-lock по организации, без ожидания; это межпроцессная гарантия для нескольких API экземпляров. Затем порядок: организация -> бизнес/филиал -> задача -> клиенты в стабильном порядке. Undo использует тот же порядок. Если try-lock занят, задача переочередится условно по текущему lease token. Retention блокирует только терминальную задачу с SKIP LOCKED и не берёт parent locks.

Token и PROCESSING проверяются под FOR UPDATE задачи, удерживаемым до commit клиентов/связей/исходов строк/checkpoint. Новый claim пропускает этот lock. Checkpoint обновляется условным UPDATE по id/token/state, проверяется ровно одна изменённая строка; ноль вызывает rollback всей пачки. Проверка токена вне пишущей транзакции fencing не считается. beautyTransaction применяется только к ограниченным пачкам, никогда ко всему импорту.

**Дайджесты и размер.** CustomerImport хранит canonical request digest (параметры и scope) и digest принятых пакетов. Измеряются байты полного отправляемого JSON-конверта с offset, ключами и escaped-последовательностями: server action формирует строку, измеряет TextEncoder.encode(body).byteLength и отправляет именно её. Предел 64 КБ относится к этой строке, а не decoded CSV или сумме полей. API сохраняет общий транспортный предел 100 КБ и дополнительно ограничивает число/длины полей.

**Хранение.** Не сохраняются имя исходного файла и полный необработанный CSV. Сохраняются минимальные mapped-поля (имя, фамилия, исходный телефон, номер исходной строки) и baseline, необходимые для обработки, отчёта и undo, до выбранного TTL. Они всё равно персональные данные. contentsExpireAt не раньше undoDeadline. Активные worker/undo исключаются из очистки до терминального состояния. После TTL содержимое отчёта недоступно, агрегаты и безопасный audit остаются.

**Восстановление UNDOING.** У undo отдельный lease/recovery. Удаление и UNDONE фиксируются одним commit. Падение до commit откатывает все удаления; recovery возвращает COMPLETED с безопасной причиной, следующая попытка заново проверяет срок и конфликты. После успешного commit повторный запрос видит UNDONE. Recovery не продолжает удаление за пределами окна автоматически.

**FK и размер undo.** По текущим миграциям найдены три FK на customers: customer_businesses_customer_id_fkey и appointments_customer_id_fkey в 20261003000044_beauty_domain, restaurant_reservations_customer_id_fkey в 20261005000058_food_service_domain. Все ON DELETE RESTRICT. Новый журнал не должен своей FK сделать undo невозможным; способ хранения результата и поведение FK утверждаются в точной модели до schema. На собственном кластере pg_constraint сверяется с ожидаемым списком. Гонки проверяются для всех трёх ссылок в обоих порядках победы транзакций. Это пока требование к проверке, а не утверждение о доказанной сериализации.

Performance gate на максимальных 50 000 строк: точный count durable rows до/после повторной загрузки, размер payload/таблиц/индексов, время загрузки, максимальная длительность batch-транзакции и полного атомарного undo. Успех маленькой пачки не доказывает отмену всего импорта. Если максимальный undo не укладывается в безопасный transaction budget, план пересматривается до выпуска; атомарность не подменяется постепенным удалением.
