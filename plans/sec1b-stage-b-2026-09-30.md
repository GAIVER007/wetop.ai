# SEC-1b, стадия B: права `wetop_app` на данные интеграции (решение владельца 30.09.2026, Q-222 → (б\*))

ADR-124 (дополнение 30.09.2026). Это план: код и миграция не начаты, до подтверждения плана ничего в схеме не меняется.

## Решение

Запрос организации остаётся на `wetop_app` + RLS. Целиком на служебное соединение его не переводим: `reservations`,
`channel_mappings` и прочие таблицы арендатора потеряли бы страховку RLS.

```
HTTP-запрос → wetop_app + RLS → обычные таблицы арендатора

только узкий IntegrationRepository → wetop_service → external_events, system_incidents,
                                     прочие данные «только интеграции»
```

`channel_outbox`: у `wetop_app` — только `INSERT`. `ratesChanged(…, tx)` остаётся в транзакции команды, вариант (в) не применяется.

## Что нужно сделать

1. **Инвентаризация записей `channel_outbox`.** Найти все места, где `wetop_app` пишет в очередь внутри транзакции команды
   (`rates/rates.service.ts` → `publisher.ratesChanged`, `channels/ari-publisher.ts`, дельты остатков при создании, смене дат,
   отмене и т. д.) и все места, где очередь читают или обновляют. Чтение, разбор и смена статуса — только служебный путь
   (фоновые циклы уже ходят служебной ролью).
2. **Проверить на живом Postgres 16 ДО миграции.** У Prisma `create` возвращает строку (`INSERT … RETURNING`), а для `RETURNING`
   нужен `SELECT` на возвращаемые колонки; `ON CONFLICT` и повторный разбор тоже читают. Варианты, если это упирается в права:
   `createMany` без возврата, «сырой» `INSERT` без `RETURNING`, либо `SELECT` только на колонку `id`. Выбор — по результату
   проверки, а не по догадке.
3. **`IntegrationRepository`** (служебная роль, `withServiceDatabase`): единственный вход к `external_events`, `system_incidents`
   и другим таблицам «только интеграции». Метод принимает `integrationPropertyId`, выведенный сервером (`resolveIntegrationProperty`,
   ADR-125); никаких идентификаторов из пути, запроса или тела. Маршруты оператора (`ChannelOperatorInterceptor` в
   `channels/content.ts`, `channels/connection.ts`, `channels/channels.controller.ts`, `guard/guard.controller.ts`,
   `/system/freshness`) читают эти таблицы только через него; обычные таблицы арендатора — как раньше, под `wetop_app`.
4. **Миграция и `down.sql`** (номер — следующий за `…033`): отозвать у `wetop_app` всё на `external_events`, `system_incidents`;
   на `channel_outbox` оставить `INSERT` (и, если п. 2 покажет необходимость, `SELECT (id)`). Права по `current_schema()`, как в `…026`
   и `…033`. `scripts/ops/check-migrations.sh` — зелёный. Применение на рабочей базе — за владельцем (`docs/ops/rls.md`).
5. **Тесты (обязательны):**
   - integration: организация A не читает данные интеграции организации B, и наоборот; чужая организация по интеграционным
     маршрутам получает отказ, а не пустой ответ, который можно принять за «нет данных»;
   - integration: `IntegrationRepository` отвергает идентификатор, не выведенный сервером (нет публичного метода, принимающего
     произвольный идентификатор из запроса); соседний объект не читается;
   - integration под `wetop_app`: `SELECT`/`UPDATE`/`DELETE` по `channel_outbox` и любой доступ к `external_events`,
     `system_incidents` — отказ; `INSERT` в `channel_outbox` в транзакции команды работает; отказ команды откатывает и запись очереди;
   - регресс: вход оператора, «Каналы продаж», `/connections/channex`, `/guard/*`, `/system/freshness` под `wetop_app` в режиме production.
6. **Документы:** `DATA_MODEL.md` §17.2–17.3 (какие таблицы под какой ролью), `docs/ops/rls.md` (раздел про стадию B и откат), ADR-124.

## Порядок выкладки (как у стадии A)

Сначала код, потом миграция: код должен работать и с прежними правами. Откат — `down.sql`, код продолжает работать.

## Риски

- Под служебной ролью у маршрутов оператора пропадает RLS на таблицах, которые они трогают через репозиторий; поэтому репозиторий
  узкий, а фильтр по объекту — в самом запросе и покрыт тестом.
- Молча остановившаяся очередь цен в Channex — самый дорогой сбой стадии; отсюда п. 2 и тест отката транзакции.

## Не входит

Закрытие автогранта на будущие таблицы (`ALTER DEFAULT PRIVILEGES` из `…026`) — отдельное решение; вариант (в) и любое изменение
порядка записи очереди.
