# SEC-2: объект интеграции — по идентификатору, а не по названию (аудит 29.09.2026)

Решение — ADR-125. Открытый вопрос — Q-223. Модель данных не меняется.

## Проблема

Три места определяли «чей объект подключён к Channex» по-разному, два из них — по названию «Luxx Aparts»:

| Где | Как определяло |
|---|---|
| `channels/integration-owner.ts` (гард разделов каналов и сторожа, `/system/freshness`) | самый ранний объект с названием |
| `channels/operator-access.ts` (перехватчик оператора) | сопоставления Channex, потом название |
| `database/property-ref.ts` (служебные пути: сторож, циклы, скрипты) | самый ранний объект с названием |

Проверка владельца на рабочей базе 29.09: объект Luxx один, самый ранний, регистрация не пускает второй объект с тем же
названием. Угроза — если запись пропадёт или её переименуют: первый зарегистрировавшийся с этим названием становится
оператором (общий ключ Channex, экран неисправностей всех арендаторов).

## Что сделано

`resolveIntegrationProperty` — единый выбор: `INTEGRATION_PROPERTY_ID` (решает один; нет такого объекта или не UUID — ничей) →
сопоставления Channex → прежнее название (запасной путь). Все три места идут через него; `property-ref` при заданном
идентификаторе берёт объект по нему. При старте production: не задан — предупреждение, не UUID — отказ запуска.

## Проверки

Красные → зелёные: `integration-property.test.ts` (11), `integration-owner.test.ts` (+2), `property-ref.test.ts` (+4).
Одноимённый объект чужой организации оператором не становится, если идентификатор задан; без идентификатора и без
сопоставлений поведение прежнее.

## Выкладка (владелец)

Вписать `INTEGRATION_PROPERTY_ID` в серверный `.env` (значение — `id` объекта Luxx, запрос в `docs/deploy.md`), пересоздать
API, проверить вход в «Каналы продаж». Без переменной всё работает как раньше. Откат — убрать строку.

## Q-223 закрыт: обязательный идентификатор (решение владельца 30.09.2026, вариант (б))

Цель: production → `INTEGRATION_PROPERTY_ID` → конкретный `Property`. Без переменной production не стартует; ни владение, ни права не
решаются по названию объекта. Порядок, обязательный до включения:

1. записать верный идентификатор в `.env` production;
2. перезапустить API;
3. проверить «Каналы продаж»;
4. проверить `/connections/channex`;
5. проверить отказ чужой организации;
6. только после этого — отдельный PR: удалить путь по названию, а `main.ts` перевести с предупреждения на отказ старта.

До шагов 1–5 код не меняется.

**Решение владельца 30.09.2026.** В production — только `INTEGRATION_PROPERTY_ID`, без пути по названию и без пути по сопоставлениям Channex
для определения владельца интеграции. Вне production оба пути временно остаются для локальных стендов и фикстур, **помечены DEPRECATED**
(комментарий в коде, строка в `docs/deploy.md`) и удаляются целиком, когда dev/test всегда задают идентификатор. Инвариант:
**сопоставления Channex ≠ источник авторизации или владения в production.**

**Что показывает код (разбор 30.09.2026), чтобы шаг 6 не разошёлся с оценкой:**
- Путь по названию живёт в **двух** местах, оба уходят из production: (1) `apps/api/src/database/property-ref.ts`, `propertyRef()` (ветка
  `findFirst({ where: { name } })`, строки 88–103) — она срабатывает **только для служебного ходока без человека** (сторож, скрипты, импорт,
  публичный виджет), а вошедшему объект выбирается по цепочке организации и имя игнорируется (`organizationPropertyRef`); (2)
  `channels/integration-property.ts`, `resolveIntegrationProperty()`, шаг 3 «самый ранний объект с названием установки» — определение
  владельца интеграции для разделов каналов, сторожа и `/system/freshness`.
- `LUXX_APARTS_PROPERTY.name` передаётся в `propertyRef`/`propertyIdRef`/`propertyToday` в 57 местах 19 файлов `apps/api/src`
  (репозитории броней, фонда, финансов, каналов и др.) и в `scripts/reconciliation/src/cli-channex-rates.ts`. Для вошедшего это
  неиспользуемый аргумент; удалять нужно ветку по названию в `propertyRef`, а не 57 вызовов. Сами вызовы можно упростить отдельным
  механическим PR (убрать аргумент), это не блокирует шаг 6.
- Риск шага 6: служебные ходоки без `INTEGRATION_PROPERTY_ID` в своём окружении перестанут находить объект. Проверить до включения обязательности:
  скрипты владельца (`scripts/ops/*`, `scripts/reconciliation/*`) и сторож берут `.env` сервера; тесты (`pms_test`) идут вне production и
  сохраняют путь по названию как DEPRECATED.
- Ещё одно место, зависящее от названия: `apps/api/src/guard/guard.adapters.ts` (`stays()`, фильтр `reservation: { property: { name: LUXX_APARTS_PROPERTY.name } }`) —
  выборка броней сторожем по названию объекта. Это не выбор владельца, но при шаге 6 его тоже нужно перевести на идентификатор.
- Сопоставления Channex как второй шаг цепочки — в `channels/integration-property.ts` (`resolveIntegrationProperty`) и
  `channels/operator-access.ts`; в production они перестают быть источником владельца.

## Не входит

Обязательность переменной и удаление поиска по названию (Q-223, решён 30.09.2026 — код после шагов 1–5 выше); сиды и скрипты владельца, которые ищут объект по названию.
