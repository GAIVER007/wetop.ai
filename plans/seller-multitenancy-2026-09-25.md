# План Э4: один продавец на все гостиницы (25.09.2026)

**Статус: сделано 25.09.2026** (этой же облачной сессией; поручение «давай сам делай»). Доказательства: бот —
`reports/seller-multitenancy-2026-09-25/bot-tests.md` (изоляция 19/19 красный → зелёный, весь набор 1347); платформа —
журнал `tests/runs` (unit, integration с `tests/integration/seller-orgs.test.ts`, полный UI, типы, линтер). За
владельцем — §3 ниже.

**Решение:** Q-181 вариант **(б)** — ADR-083 («давай подвеждаю и продолжай дальше»), раздел Э4 плана
`plans/platform-roles-extensions-2026-09-25.md`: «организация во всех таблицах и миграция alembic; профиль из файла в
таблицу; поиск по знаниям в пределах организации и RLS; публичный ключ гостиницы в теге чата и список её доменов;
организация в служебных вызовах…; тест изоляции: красный → зелёный. В платформе: заголовок организации в клиенте
панели, снятие `SELLER_ORGANIZATION_ID`, заведение и выключение гостиницы у продавца при смене расширения». Сюда же —
хвост Э2 (Q-183): после конца срока расширения продавец на сайте гостиницы **молчит**. Ход работы — по поручению
владельца «давай сам делай» (25.09).

**Что снимается.** Правило кита в `apps/ai-seller/AGENTS.md` «мультиарендности нет и не должно появиться» — снято
решением владельца (ADR-083 называет это прямо: «снимает красное правило кита»). Правило переписывается: один
экземпляр-продавец обслуживает много организаций, изоляция — обязанность каждой двери и доказана тестом.
Экземпляр-помощник (`BOT_ROLE=support`) остаётся без организаций — у него своя база и один хозяин, платформа.

**Ядро бота.** Порядок шагов `process_message` не меняется. Организация входит в ядро одним полем
`IncomingMessage.organization_id`: его ставит дверь канала (виджет — из ключа гостиницы, песочница — из тела), шаг
`accept` ищет и заводит клиента в пределах организации, шаг `context` берёт промпт организации и ищет знания в её
пределах. Больше ядро о платформе не знает.

## 1. Как это работает

| Вопрос | Ответ |
|---|---|
| Кто заводит гостиницу у продавца | платформа, служебным ключом: `PUT /seller/organizations/{id}` — название, действует ли (`active`), домены сайта, публичный ключ виджета. Шлётся при смене расширения и каждой сверкой (раз в минуту) — упавший бот догонит |
| Откуда домены | `TrackedSite.hosts` всех сайтов организации («Настройки сайта», срез 8). Сайта нет — доменов нет, виджет не подключить; экран «Код для сайта» говорит завести сайт |
| Публичный ключ гостиницы | считает платформа: `sk_` + HMAC-SHA256(`SELLER_SERVICE_KEY`, `seller-widget\|<org id>`) первые 24 hex. Ключ публичный (стоит в теге на странице), из него служебный ключ не восстанавливается; в базах платформы ничего нового не хранится |
| Тег чата на сайте гостиницы | `<script async src="…/widget/widget.js" data-key="sk_…"></script>`; скрипт шлёт ключ каждым запросом |
| Как продавец узнаёт гостиницу | по `data-key` → строка `organizations`; Origin страницы обязан совпадать с её доменами. Неизвестный ключ, чужой домен, `active=false` — 403, виджет молча не рисуется. Так после конца срока расширения чат гостиницы гаснет сам (Q-183) |
| Промпт продавца | из файла — в колонку `organizations.system_prompt`: у каждой гостиницы свой. `PUT /seller/profile` с заголовком `X-Organization` пишет туда. Файл `PROMPT_PATH` остаётся помощнику |
| Знания и факты | `documents.organization_id`; поиск по знаниям — только в документах своей организации; `platform:facts.md` — свой на организацию |
| Панель («Диалоги», «Знания», сводка) | платформа шлёт `X-Organization`; продавец отдаёт только её строки. У продавца вызов без организации — 400 |
| Помощник (`BOT_ROLE=support`) | как был: без организаций (все его строки с `organization_id IS NULL`), домены — из `WIDGET_SITE_HOSTS`, ключ в теге не нужен |
| Изоляция | каждая дверь фильтрует по организации (тест изоляции: гостиница Б не видит ничего из А — диалоги, знания, промпт, виджет); плюс политики RLS в Postgres |
| RLS честно | политики создаются и включаются миграцией (ключ — `current_setting('app.org_id')`), но бот сегодня ходит в свою базу владельцем таблиц, а владелец политики обходит. Включаются они, когда пользователь базы станет непривилегированным — отдельный шаг владельца (`vykatka.md`). Сегодняшняя гарантия изоляции — фильтры приложения, доказанные тестом |
| Старые строки без организации | у выложенного продавца диалоги до Э4 остаются с `organization_id IS NULL` и в панели не видны; команда переноса — в порядке выкладки |

## 3. Порядок выкладки (владелец; после слияния)

1. Платформа — `release` на свежий `main` (автовыкладка; миграций платформы нет).
2. Продавец: обновить код копии (`docs/assistant/README.md` §6 «Обновить код…» для папки `seller`) — его alembic
   применит `0002` сам при старте.
3. Ничего не вписывать: `SELLER_ORGANIZATION_ID` из `.env` платформы можно удалить (игнорируется), сверка сама заведёт
   гостиницу продавцу в течение минуты.
4. Тег чата на сайте гостиницы заменить на новый из «Код для сайта» (теперь в нём `data-key`).
5. Старые диалоги в базе продавца (если жалко терять): `UPDATE clients SET organization_id='<uuid организации>' WHERE
   channel='widget' AND organization_id IS NULL;` — uuid показывает «Платформа → Организации».
