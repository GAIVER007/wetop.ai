# План: продавец партнёра под ключ и техподдержка по ID (25.09.2026)

**Основание.** Поручение владельца 25.09 (голосом, в этой сессии), цельная картина двух агентов:

1. **Продавец** — в разделе продаж. Партнёр оплатил подписку → создаёт своего продавца. Одно окно ввода —
   рассказ **голосом или текстом** в свободной форме: сеть хостелов, город, адрес, телефон, сколько номеров и
   прайс по типам (с окном/без окна), время заезда и выезда, дополнительные услуги, как добраться, бар, столовая,
   бесплатный Wi-Fi. «Создать» → собирается **полноценный промпт**; тут же, в чате, продавца можно проверить.
   Отдельное окно — подключение **API-ключа модели самого партнёра** с проверкой действительности. Подключение
   мессенджера **WhatsApp**: бот подхватывает всех, кто пишет на номер. Гость: «хочу забронировать с такого-то по
   такое-то» → бот проверяет свободные и занятые окна и цены **именно своего** объекта, отвечает; дальше спрашивает
   имя и **бронирует** — заводит карточку брони.
2. **Техподдержка** — единый бот внутри системы, видит его **только главный администратор**; «прокачан» на всю
   систему; отвечает клиентам-партнёрам: ошибка, возврат оплаты, продление подписки. Клиент называет своё ID →
   бот видит клиента и его подписку и говорит с этим контекстом.

Решения по границе — ADR-085 (котировка сделана) и ADR-086 (бронь — здесь, этап С4). Вопросы владельцу —
Q-185…Q-188 в `QUESTIONS.md`.

## С1. Рассказ голосом или текстом → поля → промпт

**Что видит партнёр.** Над мастером — одно большое окно: «Расскажите о вашем объекте своими словами» с кнопкой
микрофона. Голос превращается в текст прямо в поле (распознавание браузера — Web Speech API, на устройстве
партнёра; аудио на сервер не уходит и не хранится). «Создать» → извлечённые поля раскладываются по шагам мастера,
партнёр видит их и правит; дальше — как сегодня: «Применить» собирает промпт у бота.

**Как устроено.** Свободный текст **не** становится промптом напрямую — ядро правил бота не переписывается
(ТЗ §2 п. 2, ADR-084 «у продавца всё как было»). Новый маршрут панели бота `POST /extract-profile` (ключ панели,
`X-Organization`): вход — рассказ до 4000 знаков, выход — поля схем Б6/Б7 (имя, манера, цены текстом по типам,
заезд/выезд, услуги, как добраться, частые вопросы) + список «не разобрал». Извлекает модель бота с жёсткой
схемой ответа; защита входа — та же, что у диалогов (инъекция в рассказе не попадает в промпт: поля проходят
проверку слоя 9, как сегодня при правке руками). Платформа показывает поля в мастере — человек остаётся
последней проверкой.

**Файлы.** Бот: `src/dashboard/extract_router.py` (новый), схема ответа рядом со схемами Б6; тесты — извлечение
на образцах рассказа (владельцев пример из поручения — сеть хостелов в Алматы), отказ на пустом и на инъекции.
Платформа: окно рассказа в мастере (`apps/web` раздел «ИИ-продавец → Настройки»), кнопка микрофона
(`webkitSpeechRecognition`, `ru-RU`, без сети — честное «браузер не умеет»); `bot-panel-client.ts` +1 вызов.
Тесты красные первыми; UI-прогон раздела.

**Зависимости.** Ничьих решений не ждёт. Идёт первым.

## С2. Ключ модели партнёра

**Что видит партнёр.** Отдельное окно «Модель»: поле ключа, выбор поставщика из разрешённых, кнопка «Проверить» —
пробный вызов, ответ «действителен / нет». Сохранённый ключ обратно не показывается (только «ключ установлен,
…последние 4 знака»).

**Как устроено.** Ключ хранит **только бот**, шифрованным на своей стороне, в таблице по организации
(alembic `0003_org_llm_keys`); платформа его не хранит и не читает — маршруты панели `PUT /seller/organizations/{id}/llm-key`
(поставить/снять) и `POST …/llm-key/check` (проверка пробным вызовом, наружу — только вердикт). Каскад моделей
продавца на ходе организации берёт её ключ; ключа нет или он мёртв — продавец этой гостиницы молчит, в разделе
продаж предупреждение (как у истёкшего расширения, Q-183), **общий ключ платформы не подставляется** — иначе
деньги WETOP уходят на чужих гостей (рекомендация Q-186).

**Файлы.** Бот: модель+миграция, `src/ai/cascade` — ключ по организации, маршруты панели, тесты (ключ Б не виден А;
мёртвый ключ → молчание и алерт владельцу гостиницы, не гостю). Платформа: окно в разделе продаж, клиент панели.

**Зависимости.** Q-186 — рекомендация записана, делать можно по ней; смена решения владельца меняет только правило
молчания.

## С3. WhatsApp

**Что видит партнёр.** Окно «WhatsApp»: инструкция (номер, Meta Business, постоянный токен — заводит партнёр,
рекомендация Q-185), поля `phone_number_id`, токен, проверочное слово вебхука; «Проверить» — пробное чтение номера.

**Как устроено.** Официальный WhatsApp Cloud API, вебхуком: у продавца одна дверь `GET/POST /channels/whatsapp/webhook`
(GET — подтверждение подписки Meta, POST — сообщения). Дверь канала сама ставит организацию (правило Э4):
`phone_number_id` из тела → таблица подключений → `organization_id`; неизвестный номер — 200 и мимо (Meta повторяет
доставку — идемпотентность по `message id`, как у внешних записей). Исходящие — Graph API с токеном гостиницы;
свободный ответ — только в окно 24 часов после сообщения гостя, первым бот не пишет (шаблоны — не в этом этапе).
Телефон гостя приходит каналом — контакт есть с первого сообщения, «извлечь контакт» его просто подтверждает.
Переписка — персональные данные: как и виджет, канал включается на сайте гостиницы только при базе бота в РК
(ADR-009, ADR-081) — до того work только на своём объекте владельца.

**Файлы.** Бот: `src/channels/whatsapp.py` (дверь+отправка), модель подключений (в миграции С2), тесты — подпись
вебхука (`X-Hub-Signature-256`), маршрутизация по номеру, изоляция организаций, окно 24 часов. Платформа: окно
подключения, клиент панели.

**Зависимости.** Q-185 (чей номер и проверка Meta) — код можно писать по рекомендации (а), включение всё равно
ждёт номера и токена от партнёра.

## С4. Бронь из чата

**Что видит гость.** «Хочу забронировать 13–15 на двоих» → бот (котировкой ADR-085) называет «есть, итого …» →
«Бронирую?» → спрашивает имя (телефон уже есть из WhatsApp; в виджете просит и его) → «Записал, ждём вас» —
и на стойке появляется карточка брони с источником канала.

**Как устроено.** Отдельная узкая дверь записи `POST /bot/book` со **своим** ключом (`SELLER_BOOK_KEY`, не ключ
котировки — ADR-086: чтение и запись не смешиваются), тело как у `POST /w/book`, но `source` канала и без
Origin; лимиты по организации; гость — через `guestForStorage` (до базы в РК — псевдоним, как у сайта, ADR-018);
идемпотентность у бота уже есть (`create_lead`, натуральный ключ). Статус новой брони и удержание места без
предоплаты — ровно Q-114, уведомление гостю — Q-115: **одно решение для сайта и бота**. Источник `WHATSAPP` —
правка `DATA_MODEL.md` §2 и миграция (Q-188).

**Зависимости.** Ждёт решений владельца: Q-188 + Q-114 + Q-115. До них бронь остаётся заявкой администратору —
бот собирает даты и имя и зовёт человека (как сегодня).

## С5. Техподдержка: клиент по ID

**Как устроено.** Для вошедших в стойку ничего называть не нужно — подпись уже говорит боту, кто пишет и из какой
организации: инструмент помощника `get_subscription()` берёт организацию из подписи хода. «Назвать ID» — для
обращений вне стойки; ID = UUID организации (показывается партнёру в разделе подписки; рекомендация Q-187), поиск
только точным совпадением. Платформа: `GET /assistant/organization?id=<uuid>` — второй адрес узкого ключа помощника
(`ASSISTANT_READ_KEY`, список путей +1): название, статус и срок расширений, дата регистрации — **без денег и без
гостей**. Возврат оплаты и продление бот не делает и не обещает — собирает заявку владельцу (правило «не считать
деньги»); знания о системе — как сегодня, файлами в «Знаниях» техподдержки.

**Файлы.** Платформа: маршрут в `assistant.controller.ts`, список путей ключа; бот: инструмент в `hotel_tools`
помощника, тесты — чужой UUID не открывает больше, чем название и статус; вне подписи без ID — «назовите ID».

**Зависимости.** Q-187 — код по рекомендации, спор только о формате ID.
