# План: наличие и цена из чата продавца — котировка WETOP (25.09.2026)

**Основание.** Поручение владельца «давай делай все по очереди» по списку, где первым стоит «наличие, цена и бронь из
чата» (Q-166). Q-166 заведён 22.09 на ветке `claude/laughing-maxwell-z7yke5`, когда бот был чужим проектом; с тех пор
обстоятельства изменились: ИИ-продавец — продукт WETOP (ADR-079…083, Э1–Э4), объект с 19.09 ведётся в WETOP
(ADR-052 — условие 2 варианта (б) выполнено), у бота есть организации (Э4). Не изменилось одно: база не в РК
(`PII_STORAGE` пуст) — гость брони писался бы псевдонимом.

**Решение (ADR-085).** Вариант (б) Q-166 принимается **в объёме котировки** — чтения наличия и цены: в ней нет ПД,
и оба инструмента бота (`check_availability`, `get_price`) начинают отвечать правдой вместо «не знаю». **Бронь из
чата не включается**: она остаётся заявкой администратору (умолчание (а)) до базы в РК и решений Q-114 (статус и
удержание) и Q-115 (уведомление гостю). Q-166 переносится в `QUESTIONS.md` `main` как ЧАСТИЧНО отвеченный.

## 1. Как это работает

| Вопрос | Ответ |
|---|---|
| Дверь | `GET /bot/availability?organization=<uuid>&arrival&departure&guests` — узкий ключ по образцу `GUARD_READ_KEY`/`ASSISTANT_READ_KEY` (ADR-067, ADR-079): `SELLER_QUOTE_KEY` в `x-wetop-service-key`, ровно один адрес, только GET; контроллер сверяет ключ сам (замок молчит без `AUTH_REQUIRED=1`) |
| Чей объект | сайт организации: первый ACTIVE с включённым бронированием и тарифом сайта — тот же выбор, что у фактов продавца. Нет такого сайта — 404, бот говорит «уточнит администратор» |
| Расчёт | ровно тот же, что у публичного виджета (`/w/availability`): из `WebBookingService.quote` выделяется `quoteForSite(site, …)`, обе двери зовут его. Ответ — тот же JSON `Quote` (categories: available, closed, fits, totalMinor строкой минорных, currency) |
| Домены | не проверяются: запрос серверный, не из браузера; вместо домена — ключ. Публичный `/w/availability` не ослабляется ни на волос (вариант (в) отвергнут как и был) |
| Предел частоты | тот же час-окно `allow()`, ключ `bot:<организация>` |
| Бот: организация | движок ставит `dependencies.current_organization_id` на ходе (рядом с `conversation_id_var` — именованная точка, расширена в Э4 по ADR-083); `WetopProviders` читает её и шлёт `organization=` в запросе. Нет организации — параметра нет, платформа ответит 400 → «не знаю» |
| Бот: разбор | `wetop_parse` принимает форму `Quote` платформы: `totalMinor` строкой минорных (единственный источник суммы наравне с `total_minor`), свободные места считаются только по категориям `fits && !closed` |
| Бот: режимы | `INTEGRATION_MODE=wetop` собирается по роли: у продавца — только `availability` (leads остаются как были — заявка, брони из чата нет), у помощника — только `incidents`/`health` (его сегодняшний смысл, ключ `ASSISTANT_READ_KEY`) |
| Числа наружу | как были: точное число мест не называется никогда (признак «есть/мало/нет»), сумму бот только берёт из ответа, не считает |
| Переменные | платформа: `SELLER_QUOTE_KEY`; продавец: `INTEGRATION_MODE=wetop`, `INTEGRATION_BASE_URL=http://api:3001` (сеть `wetop-internal`), `INTEGRATION_API_KEY=<SELLER_QUOTE_KEY>` |

## 3. Порядок выкладки (владелец; после слияния)

1. `openssl rand -hex 32` → `SELLER_QUOTE_KEY` в `.env` платформы; тот же ключ — `INTEGRATION_API_KEY` в `.env`
   продавца, там же `INTEGRATION_MODE=wetop`, `INTEGRATION_BASE_URL=http://api:3001`.
2. Перезапуск `api` и продавца. Проверка: в чате продавца «есть места на завтра на двоих?» — бот отвечает признаком
   и ценой тарифа сайта, а не «уточнит администратор».
3. Брони из чата по-прежнему нет — бот собирает контакт и зовёт человека; включение — после базы в РК (Q-166б).
