# Срез 15. Сервер в Казахстане: подготовка кода и лист команд

Дата: 18.09.2026. Основание — `docs/ops/server-kz-2026-09-16.md` (разбор площадок, Q-070а),
условие допуска №1 в `CUTOVER.md`, ADR-009 и ADR-018 (база с ПД — в РК).
Диагноз, из которого вырос план: `reports/server-kz-readiness-2026-09-18.md`.

## 0. Что уже выяснено и чего делать не надо

Проверено 18.09: агент до ps.kz не достаёт **ни с одной стороны** — в оболочке на машине владельца
сети нет (`ps.kz` не резолвится), из облачной среды наружу только HTTPS через прокси организации,
и он отклоняет `ps.kz:443`; SSH закрыт по построению. Значит любые действия на сервере делает
владелец по командам, а агент проверяет вывод. Это не ограничение этого среза, а постоянное правило:
в лист команд нельзя класть шаг, вывод которого некому прочитать.

Второе: команды прежнего черновика («шаги 1–3, по командам») опираются на `deploy/`,
`tests/unit/deploy-server.test.ts` и план `server-kz-2026-09-17.md`, которых в репозитории нет.
Этот срез их и делает. До него лист команд владельцу не даётся.

## 2. Шаги

### Шаг 1. `GET /health` — настоящая проверка живости

Сейчас такого адреса нет, живость проверяют по `/inventory/summary` (тяжёлый запрос с
джойнами). Под сервером нужен дешёвый: процесс отвечает + база достаётся.

- `GET /health` → 200 `{ status: 'ok', database: 'up', uptimeSeconds }`, база проверяется
  `SELECT 1`; при отказе базы — 503 `{ status: 'degraded', database: 'down' }`.
- `@Public()`: проверку живости делает Docker и туннель, входа у них нет.
- `Cache-Control: no-store`, никаких подробностей драйвера и строки подключения наружу.
- **Готово, когда:** тест через настоящее приложение (как `connection.test.ts`) даёт 200 на живой
  базе и 503 на упавшей, и на старом коде красный (404).

### Шаг 2. Адрес прослушивания API

`main.ts` жёстко слушает `127.0.0.1` — в контейнере это значит «никто не достучится», причём
проверка изнутри того же контейнера пройдёт и соврёт успехом.

- `API_HOST`, по умолчанию `127.0.0.1` — на Mac ничего не меняется.
- В compose — `0.0.0.0` при сети, закрытой наружу (порты не публикуются, наружу только туннель).
- **Готово, когда:** тест на выбор адреса из окружения, red → green; на Mac API по-прежнему
  недоступен снаружи.

### Шаг 3. Один `.env`

Код читает `.env` из корня репозитория в семи местах (`main.ts`, `prisma.config.ts`, скрипты
импорта). Если файл на сервере лежит в `deploy/`, `cli-check-env.ts` напечатает «НЕ ЗАДАН» по всем
ключам, а `prisma migrate deploy` не увидит `DATABASE_URL`.

- Общий разрешатель пути: `ENV_FILE`, если задан, иначе корневой `.env`.
- В compose `env_file` смотрит на тот же файл — одно место, два читателя.
- **Готово, когда:** тест на разрешение пути, red → green; на Mac поведение прежнее.

### Шаг 4. `deploy/`

- `deploy/Dockerfile` — один образ монорепозитория (node:22-slim, `npm ci`, `USER node`),
  из него живут все три службы: разные команды запуска.
- `deploy/compose.yml` — `api`, `web`, `exely-sync`; порты наружу **не публикуются**, наружу
  только туннель (шаг 4 плана домена, отдельно). `env_file` — один файл, `required: false` для
  выключателя ARI.
- `exely-sync` — расписание раз в 15 минут внутри контейнера, `DATABASE_POOL_MAX=1`
  (случай 15.09: сумма пулов больше предела пулера → 500 на стойке).
- `deploy/cloudflared/` — пустая папка под ключ и конфиг туннеля, в git не едет.
- **Готово, когда:** `tests/unit/deploy-server.test.ts` сверяет, что в образ скопированы манифесты
  всех рабочих пакетов (иначе `npm ci` в образе падает), что порты не публикуются, что у
  `exely-sync` задан пул, и что команды служб совпадают со скриптами в `package.json`.
  Сборка самого образа доказывается только на сервере — это записано как недоказанное.

### Шаг 5. Выключатель ARI без launchd

`scripts/ops/ari.sh` целиком на macOS (`launchctl`, `lsof`, `ps eww`). На сервере — свой:
переменная в `deploy/ari.env` + `docker compose up -d api`, проверка через API.

- **Готово, когда:** тест на разбор состояния (задано/не задано, что видит API), red → green;
  живая проверка — на сервере, записывается как недоказанная до неё.

### Шаг 6. Лист команд

`docs/ops/server-kz-setup-2026-09-18.md`: §1 панель, §2 сервер, §3 схема, §4 пул, §5 данные,
§6 первый запуск — переписанные под то, что получилось, с `postgresql-client-16`, одним `.env`
и настоящими адресами проверок. Каждая команда сверена по коду.

### Шаг 7. Прогоны

`npm run test:record -- unit`, `typecheck`, `lint`. Строка журнала коммитится с правкой.

## 3. Чего этот срез не делает

- Не поднимает туннель на сервере — это шаг 4 плана домена, после сверки двух баз.
- Не переносит данные и не трогает Supabase, Exely, Channex на запись.
- Не решает, копировать dev-базу или наполнять импортом: dev анонимизирована (ADR-018), копия даст
  псевдонимы, и полный импорт с `PII_STORAGE=real` всё равно понадобится. Развилка — владельцу,
  записана в `QUESTIONS.md`.
- Не переносит сторожа (срез 11): его пути починки класса А завязаны на launchd. Отдельная задача.
