# ТЗ: перенос WETOP/PMS с ноутбука на сервер ps.kz — что сделать и как

Дата: 18.09.2026. Поручение владельца: «на ноутбуке ничего не надо, всё на сервере; напиши полноценное ТЗ,
что надо сделать и как». Сводит воедино план `plans/server-kz-2026-09-17.md`, инструкцию
`docs/ops/server-setup-2026-09-18.md`, разбор площадок `docs/ops/server-kz-2026-09-16.md` и отчёт параллельной
сессии от 18.09 (неотправленный коммит `08d7fb5`). Где команды уже расписаны, здесь только ссылка.

---

## 1. Цель и конечное состояние

Боевой контур PMS — API, стойка, туннель Cloudflare, синхронизация с архивный источник — работает **на сервере ps.kz** в
Казахстане, база данных — **управляемый PostgreSQL 16** там же. На MacBook владельца не остаётся ни одной
службы: это рабочее место разработчика, не сервер.

Что это закрывает: условие допуска №1 `CUTOVER.md` (сервер в РК, webhook на него), правило «ПД гостей в РК»
(ADR-009, ADR-018), Q-070а, Q-073 (бэкапы — на провайдере). Ручная работа владельца на Mac заканчивается
вместе с последним шагом.

Что это **не** закрывает и что здесь не делается: переключение каналов (условия допуска 2–5), сертификация
Channex, модель данных, финансовая логика, архивный источник и OTA production.

## 3. Правила, которые действуют на всём протяжении

1. **Одна вершина ветки.** Никаких `push --force`. Коммит `08d7fb5` параллельной сессии отправляется в
   **отдельную ветку** и открывается PR; сводит дубли агент (п. 5, Э0). Работа не выбрасывается.
2. Коммит — только своих файлов явным списком, сверка `git diff --cached --name-only` перед каждым.
3. Секреты (`.env`, ключ туннеля, пароль базы) вписывает и копирует только владелец. В чат — без паролей.
4. Миграции боевой базы применяет владелец. Данные с ПД переносит владелец.
5. Каждая правка кода — red → green, прогоны через `npm run test:record`, лог в журнал.
6. Сверка PMS с архивный источник — в ноль. Не 99,5 %, ноль.
7. Ни одного действия в архивный источник production, OTA production, Channex production.

## 5. Работы по порядку

Обозначения: **В** — владелец, **А** — агент. Каждый этап заканчивается критерием приёмки; следующий не
начинается, пока критерий не выполнен и не вставлен в чат.

### Э0. Одна ветка, содержащая `main` (А; В — только push своей сессии)

1. Параллельная сессия: `git push` коммита `08d7fb5` в **новую** ветку (например `claude/server-kz-parallel`),
   PR в `claude/trusting-ramanujan-gi6uzl`. Ничего не переписывать.
2. Агент сводит дубли: один `/health`, один выключатель ARI (`scripts/ops/ari.sh` с режимами против
   `ari-server.sh` — остаётся тот, у которого проверка по запущенному процессу, тесты обоих сохраняются),
   один `compose.yml`, один план и одна инструкция (материал второго вливается в первый), `API_HOST` — один
   помощник. Q-151 записывается в `QUESTIONS.md`.
3. Слить `origin/main` в ветку. Проба 18.09 после слияния параллельной ветки: **54 конфликтных файла,
   ~110 блоков** (`origin/main` = `6293ad4`, 63 коммита `main` нет в ветке, 83 коммита ветки нет в `main`).
   Где сосредоточено: экран входа (`login-form.tsx` 7 блоков, `login/page.tsx`, `login/actions.ts`,
   `lib/session.ts`), сервис стойки (`desk.service.ts` 5, `desk.controller.test.ts` 4), синтетический API
   (`scripts/preview/fixture-api.ts` 7), карточка и форма брони (`actions-panel.tsx` 4, `[number]/page.tsx` 3,
   `new/form.tsx` 3), справочник броней (`reservation-directory.ts` и тест), тарифы, финансы, аудит,
   аналитика, 15 сквозных спеков и 3 UI-спека, `playwright.config.ts`, `.github/workflows/checks.yml`.
   Разбор по файлу, ничего не выбрасывать; сторона `main` в спеках — «категорию выбирает администратор, а не
   код объекта» и окна подтверждения, сторона ветки — предпросмотры сумм 7.3 и экраны Channex 7.2. Дефекты
   слияния, которых не было ни в одной ветке, — ловить прогонами, как 16.09: unit, e2e и integration на
   локальном PostgreSQL, UI-набор, сборка стойки. Отчёт — `reports/merge-main-<дата>.md`.
4. Прогоны на слитом коде: `typecheck`, `lint`, `unit`, `e2e` и `integration` на локальном PostgreSQL 16 с
   сидом, UI-набор на синтетическом API, сборка стойки. CI на GitHub зелёный.
5. PR в `main`. Сервер едет на коде, содержащем `main`.

**Критерий:** ветка содержит `origin/main` без конфликтов; все наборы зелёные по журналу; CI зелёный;
на Mac владельца `git pull` без ошибок. Попутно на Mac: удалить `WETOP/.agent-tmp` (мусор той сессии).

### Э1. Панель ps.kz (В)

По `docs/ops/server-setup-2026-09-18.md` §1: управляемый PostgreSQL 16 (расширение `btree_gist`,
ежедневные бэкапы, записать предел подключений) и сервер Ubuntu 24.04 LTS 2 vCPU / 4 ГБ / от 40 ГБ, **один
регион** для обоих. Заказ и оплату жмёт владелец: это платная услуга.

**Критерий:** в чате хост и порт базы, имя базы, пользователь, предел подключений, IP сервера — **без пароля**.

### Э2. Подготовка сервера одной командой (В запускает, А читает)

По §2 инструкции: скачать `deploy/server-bootstrap.sh`, запустить от root с `--branch <ветка из Э0>`;
первый запуск печатает публичный ключ → добавить как Deploy key только на чтение → запустить ещё раз.
Затем `scp ~/.env` в **корень** клона (`~/wetop/.env`), заменить `DATABASE_URL`, `DATABASE_SCHEMA` не
задавать, `PII_STORAGE` не трогать; `cli-check-env`.

**Критерий:** второй запуск скрипта дошёл до «готово»; `docker compose version` не ниже 2.24;
`cli-check-env` без ошибок. Это же — первое доказательство установки Docker скриптом.

### Э3. Схема на пустой базе (В; А читает)

По §3: `psql` — PostgreSQL 16, таблиц 0; `prisma migrate deploy`; `prisma migrate status`;
`btree_gist` в `pg_extension`. Если падает на `CREATE EXTENSION` — права на расширения в панели.

**Критерий:** все миграции применены, `btree_gist` есть. `check-migrations.sh` сюда не идёт по построению.

### Э4. Пул соединений (А)

По §4: сумма пулов служб (API 5, `retired-source-sync` 1) плюс запас на `psql` и скрипты меньше предела базы из Э1;
иначе `DATABASE_POOL_MAX` в `.env`.

**Критерий:** число названо и записано в `.env` владельцем.

### Э5. Данные (В, по решению Q-151)

Вариант А по §5: `pg_dump --data-only` со старой базы → `pg_restore --disable-triggers` в новую, проверка
`convalidated`. Старая база не выключается и не меняется.

**Критерий:** восстановление без ошибок, невалидированных ограничений нет.

### Э6. Первый запуск без туннеля (В запускает, А читает)

По §6: `docker compose -f deploy/compose.yml up -d --build api web retired-source-sync`; `ps`; `/health` изнутри
контейнера; начало `/inventory/summary`; `bash scripts/ops/ari.sh status`.

**Критерий:** все три контейнера `healthy`; `/health` → 200; `ari.sh status` печатает «машина: docker»
и значение выключателя из процесса. Это же — доказательство сборки образа и `ari.sh` под Docker.

### Э7. Сверка двух баз в ноль (А)

Против нового API (по ssh-туннелю к серверу или изнутри compose): `cli-system-trace.ts`,
`cli-double-entry.ts`, контрольные числа объекта (88 единиц, 5 категорий, 6 тарифов), балансы счетов;
`npm run ui:walkthrough` против сервера — столько же проверок, сколько на Mac 17.09 (322), ноль провалов.

**Критерий:** ноль расхождений между старой и новой базой; обход без FAIL.

### Э8. Туннель — ровно одна копия (А по командам, В вводит `cloudflared tunnel login`)

По плану §4 шаг 4 и шапке `deploy/cloudflared.example.yml`: `tunnel delete --force wetop` (старая копия,
где бы она ни была, подключиться больше не сможет) → `tunnel create wetop` → `route dns --overwrite-dns`
для `app` и `api` → конфиг с именами служб, командой Zero Trust и AUD-тегом → `up -d cloudflared`.
Плановый простой на минуты.

**Критерий:** `cloudflared tunnel info wetop` — один коннектор, `linux_amd64`, IP сервера;
`https://api.wetop.ai/a/pms.js` → 200, `/reservations` → 404; на стойке `/channels` → «Проверить webhook»
→ 200; вход в `app.wetop.ai` через Access работает.

### Э9. Синхронизация с архивный источник — одна копия (В на Mac, А проверяет)

На Mac: `scripts/ops/launchd/uninstall.sh retired-source-sync`. На сервере она уже идёт из Э6.

**Критерий:** строка свежести на стойке обновляется; в журнале `retired-source.sync` одна запись на прогон, не две.

### Э10. Настоящие ПД (В, только после Э7 и решения Q-151)

Если выбран вариант Б: пустая схема (повтор Э3 на чистой базе или очистка данных) и полный импорт из архивный источник
с `PII_STORAGE=real` при снятой синхронизации; затем сверка Э7 заново. Если остаётся вариант А: включить
`PII_STORAGE` для новых записей — старые гости останутся псевдонимами, и это надо записать в `QUESTIONS.md`.

**Критерий:** сверка в ноль после включения; гости каналов пишутся не псевдонимами.

### Э11. Mac — рабочее место (В)

`scripts/ops/launchd/uninstall.sh api web domain awake retired-source-sync`; `status.sh` показывает «не загружен» по
всем, а строка «туннель … → 200» — от сервера.

**Критерий:** на Mac ни одной задачи launchd проекта; адреса снаружи отвечают.

### Э12. Сутки на сервере без вмешательства (А наблюдает, В не трогает)

Сторож молчит, `/incidents` пуст или только информационные, синхронизация идёт, Telegram не будил.
Сквозной набор и UI-набор на сервере зелёные.

**Критерий:** 24 часа без ручных действий; отчёт `reports/server-kz-day-<дата>.md`.

### Э13. Документы (А)

`CUTOVER.md` условие 1 — закрыто с датой; `docs/deploy.md` — раздел про Mac в историю, сервер — основной;
`QUESTIONS.md` Q-070а, Q-151 закрыты; `CLAUDE.md` §2; `HANDOFF.md` граница «с любой машины / только с сервера».

## 7. Границы: чего не делаем

- Не монтируем сокет Docker в контейнеры ради автоперезапуска: красный healthcheck — это видимость в
  `docker compose ps`, а не перезапуск; зависшую стойку на сервере перезапускает человек
  (`docker compose restart web`), автоматика — отдельное решение после Э12.
- Не открываем порты наружу: `expose`, не `ports`; наружу ходит только туннель с шестью публичными путями.
- Не переключаем каналы и не трогаем архивный источник/OTA/Channex production.
- Не меняем модель данных и финансовую логику.
