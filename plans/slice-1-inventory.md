# Slice 1 — Inventory: план

**Статус: подтверждён владельцем 07.09.2026** («давай начинай первый шаг»). Шаг 1 выполнен.
Шаг 2 ждёт выбора БД (§6).

## 1. Цель

Импортировать реальный номерной фонд объекта в новую PMS и показать его в интерфейсе.
Доказательство готовности — отчёт сверки, в котором каждая строка ниже совпадает
с контрольной выгрузкой. Допустимое расхождение — **0**.

```
Единиц продажи                88   = 16 ROOM + 72 BED
Максимум гостей               92
Физических комнат             88   (1:1 до списка Q-095; см. §5)

Одноместная с окном            4   Exely 5074312   вместимость 1
Одноместная без окон           8   Exely 5074686   вместимость 1
Двухместная                    4   Exely 5074687   вместимость 2
Общая мужская (койка)         36   Exely 5074688   вместимость 1
Общая женская (койка)         36   Exely 5074689   вместимость 1
Здание 1 («Основной»), этаж 1 («2»)
Блокировок 0
```

## 2. Источник данных

`project-input/exely/audit-2026-09-07/inventory.md` — таблица «Единицы продажи», 88 строк:
`№ комнаты в Exely | Категория | Тип | Вместимость`. Персональных данных нет, файл в git.
ID категорий — `spravochniki.md` и `OBJECT.md` §2. Кодов замков, комментариев, статусов
уборки в выгрузке нет (в Exely статусы есть, но снимаются отдельно; в Slice 1 все единицы
импортируются со статусом `DIRTY`, как факт на 07.09.2026 для 85 из 88 — уточнение
по трём «Проверено» отложено, в отчёт сверки уборка не входит).

## 3. Что входит и что нет

**Входит:** каркас монорепо; схема БД по утверждённым разделам 1 и 4 модели + `AuditLog`;
парсер выгрузки; идемпотентный импорт; отчёт сверки; API чтения; страница «Номерной фонд».

**Не входит:** брони и шахматка (Slice 2), тарифы (Slice 3), статусы уборки в UI,
блокировки в UI, авторизация и роли (Q-061…064 открыты — UI работает на localhost
без входа, это временное допущение и оно записано), всё из раздела 6 модели.

## 4. Архитектура среза (по ADR-002, ADR-011)

```
apps/web            Next.js 15 + TypeScript — страница /inventory
apps/api            NestJS + TypeScript   — GET /inventory/units, GET /inventory/summary
packages/database   Prisma schema + миграции + PrismaClient
packages/domain     типы и правила инвентаря (без Prisma, без Nest)
packages/shared     общие утилиты (Result, id, даты)
scripts/imports     exely-inventory: parse → validate → upsert
scripts/reconciliation  inventory: БД vs контрольные числа → отчёт .md
tests/unit, tests/integration, tests/e2e
```

Менеджер пакетов — npm workspaces (на машине есть Node 24 и npm 11; pnpm нет, ставить
не обязательно). Тесты — Vitest (unit, integration), Playwright (e2e, в этом срезе один
сценарий «страница показывает 88 строк»). ADR-011 инструмент unit-тестов не фиксирует —
Vitest выбран как стандарт для TS-монорепо; если владелец против, замена бесплатна.

Сущности Prisma в Slice 1: `Property`, `Building`, `Floor`, `AccommodationType`,
`PhysicalRoom`, `InventoryUnit`, `InventoryBlock`, `HousekeepingEvent`, `AuditLog`.
Внешние ID Exely хранятся как поля `exely_id` / `exely_room_number` (ADR-003: ссылка,
не замена ключа). Ничего не выводится из номера единицы (принцип 7).

| # | Шаг | Доказательство |

| 2 | Prisma schema по §1, §4, §10 + первая миграция; `.env` только имена (уже есть) | миграция применяется к пустой БД и откатывается |
| 3 | Парсер `inventory.md` → нормализованные записи. **Red:** тест на синтетической выгрузке (3 вымышленные категории, 7 единиц) падает → **green** | тест unit, фикстура без реальных данных |
| 4 | Импорт: одна транзакция, upsert по `(property, exely_room_number)`; `PhysicalRoom` 1:1; повторный запуск не создаёт дублей. **Red → green** | integration-тест: 2 запуска → 88 единиц, 0 дублей |
| 5 | Отчёт сверки: `scripts/reconciliation/inventory` пишет `reports/inventory-YYYY-MM-DD.md` с diff по каждой строке §1 | отчёт с diff = 0 по всем строкам |
| 6 | API: `GET /inventory/summary`, `GET /inventory/units?category=` | контрактный тест + пример ответа |

Порядок именно такой: сначала данные и сверка, интерфейс последним. Красный тест
показывается до зелёного (AGENTS.md §6). Реальные данные в тесты не попадают:
фикстуры — вымышленные категории; реальная выгрузка используется только в шаге 5.

## 6. Вопрос, без которого шаг 2 не начнётся: база данных

На машине нет ни Docker, ни PostgreSQL, ни Homebrew (проверено 07.09.2026).
Варианты для **разработки** (production-БД — отдельно, Q-070, регион Казахстан):

| | Вариант | Кто делает | Плюсы | Минусы |
|---|---|---|---|---|
| A | **Supabase, отдельный dev-проект** (рекомендую) | владелец создаёт проект, вписывает `DATABASE_URL` в `.env` сам | ничего не ставить; Postgres как в ADR-003/011; MCP уже подключён | облако вне РК — допустимо только потому, что в dev нет ПД (ADR-010); для production не годится |
| B | Postgres.app (локальный PostgreSQL с установщиком) | владелец скачивает и запускает | всё локально, бесплатно | установка руками; агент системный софт не ставит |
| C | Docker Desktop + контейнер postgres | владелец ставит Docker | стандартно для команды | тяжелее всего для машины без Docker |

Ключ подключения в любом варианте вписывает владелец в `.env`, агенту не диктуется.
