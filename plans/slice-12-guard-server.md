## 1. Зачем сервер

Сторож среза 11 живёт внутри API на Mac. Он чинит упавший API, туннель, очередь в Channex, но **не может сообщить
о собственной смерти**: Mac выключился, сел аккумулятор, пропал интернет, закрыли крышку — и тишина выглядит так же,
как «всё хорошо». 13.09 это случилось на глазах: после перезапуска API три минуты падал по кругу, и сторож, живущий
внутри API, об этом никого не известил. Нужен второй сторож в другом месте, который ждёт от первого сигнала и
поднимает тревогу, когда сигнал пропал.

   Сама PMS с базой гостей — отдельный вопрос сервера в РК (Q-112), этот план его не решает.

## 3. Что ставим — по шагам

### Шаг 12.1 — «Сторож сторожа» (без персональных данных)

- Контейнер `pms-lux-watch` на сервере: адрес `POST /heartbeat` за Traefik по https, общий секрет в заголовке.
- Сторож в API раз в минуту шлёт сигнал: время прохода, сколько неисправностей открыто / срочных / ждут человека,
  отработали ли проверки. Заголовки неисправностей — без ФИО по построению (DATA_MODEL §12), но в сигнал идут
  только числа.
- Сигнала нет 5 минут → Telegram в группу дежурных: «PMS на Mac молчит N минут: выключен, нет сети или упал
  API». Повтор раз в 30 минут; сигнал вернулся → «снова на связи, молчала с … до …».
- Сигнал пришёл, но в нём срочные неисправности, а сообщения с Mac не уходят (нет интернета у Telegram на Mac) —
  сервер дублирует тревогу.
- Доказательство: учения — остановить API на Mac → сообщение с сервера через ≤ 6 минут; поднять → «на связи».

### Шаг 12.2 — Сигнал из API (Mac)

- `GUARD_HEARTBEAT_URL` и `GUARD_HEARTBEAT_SECRET` в `.env` Mac (вписывает владелец); без них сигнал не шлётся.
- Тест: подделка сервера получает сигнал раз в проход, без персональных данных, секрет в заголовке, не в адресе.

### Шаг 12.3 — Дежурный агент на сервере (после 12.1)

- Claude Code на сервере в отдельном контейнере, раз в час по той же инструкции `scripts/ops/guard-agent.md`.
- Код берёт из GitHub по ключу развёртывания с правом писать только ветки `guard/*`; исправление — ветка и запрос
  на слияние, мёржит владелец. На сервере нет базы гостей и нет доступа к API на Mac: неисправности агент читает
  из последнего сигнала (12.1).
- Плюс относительно Mac: не зависит от того, открыт ли Claude на ноутбуке и не спит ли он.

## 3в. Работает и прошло учения (13.09.2026, вечер)

Секреты вписал владелец: на Mac — в `.env`, на сервер перенёс сам одной командой из своего терминала (значения
идут по ssh через stdin, агент их не видел). Проверка по поведению: сервер принимает сигнал (HTTP 204), на Mac ошибок
сигнала нет, пробное сообщение будильника с Mac дошло до группы.

| Учения | Время (UTC) | Итог |
|---|---|---|
| Последний сигнал Mac | 16:30:54 | — |
| API остановлен (`launchctl bootout`) | 16:31:31 | Mac замолчал |
| Сервер: «🔴 PMS Luxx Aparts молчит 5 мин» | 16:36:22 | ровно через 5 минут после последнего сигнала; ошибок отправки в Telegram в журнале нет |
| API возвращён (`launchctl bootstrap`) | 16:37:00 | отвечает через 15 с |
| Сервер: «🟢 снова на связи: сторож молчал 7 мин» | 16:37:50 | через 52 с после возврата |

**Настоящий случай до учений.** В 16:27 сервер сам поднял «молчит 5 мин»: сигнала не было с 16:22. В это время
Mac был в тяжёлом свопе (своп 13,4 из 14,3 ГБ, нагрузка 8–9: восемь сессий Claude и серверы разработки на 8 ГБ памяти),
API и стойка отвечали по 60–90 секунд, пулер базы давал таймаут входа. Сторож в API сам об этом сказать не мог —
ровно тот случай, ради которого ставился сервер.

**Первые ложные тревоги того же вечера исправлены (3e09266):** 500 на странице статуса webhook считался «приёмом
брони» и был срочным; обрыв связи с базой считался ошибкой кода; сервер получал все срочные неисправности, включая те,
что сторож ещё чинит сам; стойку перезапускали через 2 минуты, а сборка после слияния шла 5,5.

**Побочный эффект учений — дыра в скрипте туннеля.** Пока API стоял, быстрый туннель умер. Скрипт поднял новый, но
записать адрес в Channex не смог (регистрация идёт через API), сдался и больше не повторял, пока туннель жив: webhook
~10 минут указывал на мёртвый адрес (530), из них ~4 после возврата API. Восстановилось в 16:41:22 только потому, что туннель
умер ещё раз. Брони не потерялись: событий в окне ноль, их страховал опрос ленты раз в минуту. Исправление
`scripts/ops/channex-tunnel.sh` (на каждом цикле сверять адрес в Channex с текущим туннелем) взяла сессия pms-lux-b4.

**Замечено, не исправлено:** если проход сторожа в API завис (своп, зависший запрос), следующие проходы ждут его, и
сигнал на сервер не уходит — сервер скажет «PMS молчит», хотя API формально жив. Для дежурного это верный вывод
(система не работает), но текст сообщения говорит про выключенный Mac.

## 5. Чего сервер не делает

- не хранит гостей, брони, деньги; не принимает webhook Channex (в нём ФИО гостей) — это сервер в РК;
- не трогает контейнеры `vilkabot2`, `hermes-workspace`, `traefik` и их конфигурацию, кроме добавления нашего
  маршрута в Traefik по его же правилам (метки контейнера);
- не мёржит код и не выкатывает его на Mac.
