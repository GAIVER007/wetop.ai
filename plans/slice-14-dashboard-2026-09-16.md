# Срез 14 — «Главная»: дашборд собственника и управляющего

**Дата:** 16.09.2026. **Поручение владельца:** «выведи на главную дашборд главные виджеты … период сегодня /
вчера / этот месяц / прошлый месяц / выбрать … главная — это экран собственника и управляющего»; блок
«Работа с гостями» внизу — «вообще выглядит не удобно, зачем он там». Правки экранов по замечаниям — ADR-027.

## 1. Что меняется

| Было | Стало |
|---|---|
| «Обзор дня»: пять карточек на одну дату, три списка «Заезды / Выезды / Живут» на 500 px | «Главная»: период (сегодня, вчера, 7 дней, этот месяц, прошлый месяц, свой отрезок), показатели за период с сравнением с предыдущим таким же отрезком, график по дням, источники броней, категории; ниже — компактная полоса «Сегодня на стойке» и «Требуют внимания» |
| Списки дня на главной | Убраны. Те же списки живут в «Брони» (`/reservations?date=`), ссылка «Все брони дня» остаётся |

Маршрут `/today` и пункт меню «Главная» не меняются.

## 2. Откуда числа — ничего не придумывается

| Показатель | Источник | Правило |
|---|---|---|
| Загрузка, % | шахматка (`buildChessboard`) по каждой дате периода | занятые клетко-ночи / (единиц × ночей), как «Статистика» и кольцо на «Обзоре дня»; проживания без ячейки — отдельной строкой, в загрузку не входят (Q-107) |
| Выручка (начислено) | начисления счетов по `service_date` в периоде, без сторно | как «Деньги за период»; начисление за проживание датировано заездом |
| Получено оплат | платежи `COMPLETED` по `paid_at` в сутках Алматы | как «Деньги за период» |
| Средняя цена ночи (ADR) | начислено за проживание / занятые клетко-ночи | целочисленно, в тиынах |
| Доход на место (RevPAR) | начислено за проживание / (единиц × ночей) | целочисленно |
| Заезды, выезды, гости | проживания по дате заезда / выезда в периоде, без отменённых и незаездов; отмены и незаезды — отдельно | как «Обзор дня» |
| Источники | брони по дате заезда в периоде, по `source`/`channel` | как отчёт по каналам (`/hotel/channel-report`, база ARRIVAL) |
| Сравнение | тот же расчёт за предыдущий отрезок той же длины | реальные числа, не оценка |

Период до 366 дней (как отчёт по каналам). Если период заходит в будущее, на экране написано «включая
будущие брони».

## 3. Работы

1. `packages/domain/src/dashboard` — чистый расчёт `buildDashboard(input)`; тесты.
2. `apps/api/src/dashboard` — `GET /desk/dashboard?from&to` → `{ current, previous }`; репозиторий читает
   шахматку через `ChessboardService` кусками по 62 дня, начисления/платежи/возвраты — как финансовый отчёт;
   тест контроллера на подставном репозитории.
3. `apps/web/src/app/today` — период (`lib/period.ts`, тесты), новый экран, `dashboard.css`; `day-workspace.tsx`
   удаляется. `data-testid` полосы стойки (`c-inhouse`, `c-arrivals`, `c-departures`, `c-tocheckin`,
   `c-tocheckout`, `c-free`, `c-debt`) сохраняются — их читает сквозная сверка `cli-system-trace.ts`.
4. Фикстура UI (`scripts/preview/fixture-api.ts`) отвечает на `/desk/dashboard` тем же расчётом на своих данных.
5. Тесты: `tests/ui/workspace.spec.ts` (период, задачи), `tests/e2e/desk-day.spec.ts` (заезд виден на главной
   в «Требуют внимания» и в счётчике), `premium.spec.ts` (кольцо загрузки остаётся).
6. Доказательства: unit, typecheck, lint, UI-набор, `desk-day` живьём, скриншоты, отчёт `reports/dashboard-2026-09-16.md`.

## 4. Чего не делаем

Новых таблиц и полей нет (DATA_MODEL не меняется). Прогнозов, «целей», планов продаж и придуманных
сравнений нет. Бизнес-правил бронирования и финансов не трогаем.
