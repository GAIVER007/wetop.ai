## 2. API — только чтение, теми же функциями (Д5)

| Эндпоинт | Ответ | Чем считается |
|---|---|---|
| `GET /reservations/:number/items/:itemId/move-preview?unitCode=&ratePlanCode=` | `{ unitCode, changesCategory, fromCategory, toCategory, nights, currentMinor, newMinor, ratePlanRequired, problem }` | тот же `priceStay` по `repo.nightRates` целевой категории, те же проверки вместимости, тарифа и блокировок, что в `assign` — вынесены в `previewMove` и вызываются из `assign` |
| `GET /reservations/:number/items/:itemId/extend-preview?nights=1&ratePlanCode=` | `{ departureDate, addedMinor, newMinor, ratePlanRequired, unitCode, nextNightsFree, problem }` | `priceStay` на добавленные ночи как в `extend`; занятость — `hasAllocationOverlap` / `hasBlockOverlap` |
| `GET /reservations/:number/cancel-preview?reason=cancel|no_show[&itemId=]` | `{ items: [{ itemId, policy, dueNow, penaltyMinor }], totalPenaltyMinor }` | `penaltyDue` + `penaltyAmount` через общий `penaltyFor(repo, item, reason)`, который использует и `chargePenalty` |

Ничего не пишется, журнал не трогается, каналы не уведомляются. Тест «сумма в окне = начисление»: предпросмотр
отмены → отмена → на счёте штраф той же суммы; предпросмотр переселения → переселение → `priceMinor` равен
`newMinor`; предпросмотр продления → продление → `priceMinor` равен `newMinor`.

`DATA_MODEL.md` §6 — абзац «Пересчёт при действиях стойки» (документация действующих правил: категория —
на весь срок по календарю новой категории; продление — прежняя цена плюс новые ночи по календарю; штраф —
политика тарифа, только с дня заезда, Q-103). Логика не меняется.
