# Обновление базы сервиса продавца 0004 → 0009

01.10.2026. Подготовлено, **рабочая база не изменена**. Не относится к Supabase/PMS.

## Состав

0005: nullable-поля расхода модели в messages. 0006–0007: новые таблицы знаний/действий поддержки.
0008: agents, nullable agent_id у клиентов, диалогов, документов и WhatsApp; прежний агент переносится с id организации.
0009: заполнение пропусков и дополнительные индексы. Старые ключи остаются.
**0010 исключена:** сужение ключей требует отдельного релиза после smoke.

## Проверки

- PostgreSQL 18 + pgvector, отдельный контейнер с tmpfs и внутренней сетью, без портов наружу,
  без секретов и без данных гостей: 0004 → 0009 → 0004 → 0009 успешно.
- Это проверка DDL на пустой базе, не копия production и не доказательство сохранности её содержимого.
- Синтетические перенос/изоляция/откат проверяются pytest test_agent_scope_migration.py,
  test_agent_scope_contract.py, test_agent_scope.py.
- Новый entrypoint ограничивает автоматическую миграцию 0009, принимает уже установленную 0010,
  отказывает на неизвестной ревизии. Red: 3 failed на прежнем upgrade head.

## Перед применением (после отдельного разрешения)

1. Проверить ревизию seller-app-1: должна быть 0004; неизвестная — остановка.
2. Зафиксировать image ID приложения и monitor, пути compose и томов; проверить свободное место.
   На 01.10.2026 свободно 3.6 GB: перед сборкой образа места недостаточно для уверенной выкладки.
3. Остановить приём/обработку seller app и monitor на время снимка и миграции.
4. Сделать pg_dump -Fc базы seller-postgres-1 в закрытый каталог сервера (umask 077).
   Имя базы/пользователя брать из environment контейнера, значения не выводить.
5. Проверить архив через pg_restore --list; посчитать контрольную сумму. Сохранить только на сервере.
6. До запуска нового кода снять агрегаты количества строк и orphan-счётчики (без контактов/сообщений).
7. Применить новым образом с переопределённым entrypoint только `alembic upgrade 0009`.
8. Проверить revision=0009; число организаций равно числу перенесённых агентов;
   agent_id всех строк с организацией совпадает с её прежним ID, orphan=0;
   исходные количества клиентов, диалогов, документов, сообщений не изменились.
9. Запустить новый seller app/monitor. Проверить публичный health (только status), внутренний health,
   чтение инструкции по агенту, отказ чужому агенту, тестовый чат без отправки реальному гостю.

## Откат

До запуска нового кода допустим проверенный downgrade 0004, пока новые таблицы/поля ещё не используются.
После запуска сначала остановить app/monitor и сохранить второй dump: downgrade может удалить новые данные.
Предпочтительный аварийный возврат — прежний образ на расширенной совместимой схеме 0009.
Восстановление исходного dump выполняется только после оценки появившихся после снимка данных и отдельного
решения: автоматическое восстановление потеряло бы новые сообщения. Не менять базу поддержки assistant.

## Граница разрешения

Запрашивается только расширение seller 0004 → 0009 и выкладка совместимого runtime.
Не включает 0010, SellerBookingIntent в PMS, подключение WhatsApp или отправку гостевых сообщений.
