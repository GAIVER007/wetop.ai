# STAFF2.1: аудит «Сотрудники и доступ» (09.10.2026)

Поручение владельца: макет «Сотрудники и доступ 2.0» и ТЗ из шести стадий. Первое задание ТЗ: аудит действующей
реализации, карта маршрутов, ролей, прав и назначений по ORGANIZATION / BUSINESS / LOCATION, **без изменения схемы
доступа до согласования**. Стадия STAFF2.2 (внешний вид, должность выбором) уже влита в `main` (PR 336).

## 1. Что есть сегодня

**Модель.** Доступ одноуровневый: `Membership(userId, organizationId, role, phone, position)`. Роль одна на человека в
организации: `OWNER`, `MANAGER`, `STAFF` (на экране «владелец», «управляющий», «администратор»). Ни `businessId`, ни
`locationId` в членстве нет: каждый человек видит все бизнесы и филиалы своей организации. `EmployeeLocation` связывает
**мастера салона** (`Employee`) с филиалом для расписания, это не доступ учётной записи.

**Права.** Роль это готовый набор (`packages/domain/src/accounts/permissions.ts`, 13 прав, ADR-107, §16.5):

| Право | Владелец | Управляющий | Администратор |
|---|---|---|---|
| self, desk, dialogs, reports | да | да | да |
| refunds, property, rates, channels, settings, seller, staff | да | да | нет |
| journal | да | нет | нет |
| owner (управляющие, роли, платные расширения) | да | нет | нет |

Права отдельному человеку не выдаются (ответ владельца 27.09, «роль = готовый набор»). Проверка в API (`@Access`),
стойка только прячет пункты.

**API (`apps/api/src/accounts/accounts.controller.ts`, префикс `/auth`).**

| Маршрут | Что делает | Кто |
|---|---|---|
| `GET /members` | список людей, `lastLoginAt`, признаки `roleEditable`, `removable`, `detailsEditable` | staff |
| `PATCH /members/:id` | сменить роль, только MANAGER/STAFF | owner |
| `PATCH /members/:id/details` | телефон и должность-подпись | staff |
| `DELETE /members/:id` | отключить: не себя, не владельца, не выше своей роли | staff |
| `POST /invites`, `GET /invites`, `DELETE /invites/:id` | пригласить (почта + роль), список, отозвать | staff, роль по `invitableRoles` |
| `GET /invites/:token`, `POST /invites/:token/accept` | принять по ссылке | публично |
| `GET /sessions`, `POST /logout-all` | свои сеансы | self |

Платформа (`/platform/*`): организации, архив, расширения, техподдержка. Только главный администратор.

**Журнал.** `AuditLog` с `organizationId`, фильтры по сотруднику, датам, группе `staff` (`membership.*`, `invite.*`,
`user.*`). Действия доступа: `invite.created/revoked/accepted`, `membership.role.updated`, `membership.removed`,
`membership.details.updated`. Страница `/journal` только владельцу (право `journal`).

**Стойка.** `/team` (таблица, сводка, панель приглашения, ожидающие приглашения), `/journal`, `/profile/access`
(личные сеансы), `/staff` перенаправляет на `/team`.

## 2. Соответствие ТЗ

| Требование ТЗ | Состояние |
|---|---|
| Приглашение по email, срок, отзыв, повтор не создаёт вторую учётку | есть (срок 7 суток, отзыв есть; «отправить повторно» нет: приглашение отзывают и создают заново) |
| Нельзя назначить роль выше своей | есть (`invitableRoles`, `canSetRoleAtDesk`) |
| Последний владелец защищён | есть: владельца нельзя отключить или понизить с экрана; роль владельца назначает команда сервера |
| Изоляция организаций | есть (RLS, ADR-103) |
| Отключённый человек теряет доступ сразу | есть: сеансы гаснут на следующем действии |
| Журнал изменений ролей и приглашений | есть; значения до/после пишутся |
| Имя и фамилия при приглашении | **нет**: имя берётся из `User` при регистрации |
| Телефон, должность при приглашении | **нет**: задаются потом через «Изменить» |
| Назначения по бизнесам и филиалам, несколько ролей у одного человека | **нет в модели** |
| Дерево «организация → бизнес → филиал → люди» | **нет**: считать не из чего |
| Карточка сотрудника справа, вкладки «Профиль / Доступы / Активность / Безопасность» | нет (есть панель «Изменить» с телефоном и подписью) |
| Приостановить доступ без удаления | **нет**: есть только «отключить» (удаление членства) |
| Отозвать сеансы конкретного человека | нет в API (есть только «выйти везде» для себя) |
| Вкладка «Роли и права» | нет; таблица прав уже в коде, её можно показать только на чтение |
| Журнал по филиалу, фильтры по сотруднику | по сотруднику есть; по филиалу нет, записи не несут филиал |
| «Приглашение просрочено», «ошибка отправки» в списке | частично |

## 3. Что можно сделать без изменения модели (STAFF2.3a)

1. Вкладка «Роли и права» только на чтение: таблица 13 прав на три роли из `PERMISSIONS`/`ROLE_PERMISSIONS`.
2. Статус приглашения: «ждёт ответа» и «просрочено» (по `expiresAt`), кнопка «Отправить заново» (отозвать и создать).
3. Имя в приглашении как необязательное поле только для письма и предзаполнения регистрации: нужна проверка, как
   регистрация по ссылке берёт имя; схему менять не надо, если имя едет в тексте письма, а не в базе.
4. Раздел журнала «Доступ» с готовым фильтром `group=staff` прямо во вкладке «Сотрудники и доступ» (право `journal`
   у владельца, управляющему сейчас закрыто, это решение ADR-107).

## 4. Что требует решения владельца и правки `DATA_MODEL.md`

Это развилка по данным и доступу, поэтому вопросы записаны в `QUESTIONS.md` (Q-286…Q-290), код не начат.

- **Область доступа (Q-286).** Нужна ли привязка человека к филиалам: администратор стойки только в «своём» филиале,
  бухгалтер только в финансах выбранных бизнесов. Сегодня все видят всё. Предложение: таблица назначений
  `membership_scopes(user, organization, business?, location?, role)`, ограничение читается в `scope-resolve` и в
  фильтрах API, RLS остаётся по организации.
- **Несколько ролей у одного человека (Q-287).** Следует из Q-286: роль на назначение, а не на организацию.
- **Новые роли «бухгалтер», «маркетолог» (Q-288).** В ТЗ они «предполагаемые». Решение ADR-107: три роли, без
  пользовательских. Нужен ответ, добавлять ли их как готовые наборы.
- **Приостановка доступа (Q-289).** Статус членства `SUSPENDED` вместо удаления; влияет на тариф (место занято?).
- **Имя и телефон в приглашении (Q-290).** Хранить в `invites` (миграция) или только в письме.

## 5. Предлагаемый порядок

STAFF2.3a (§3, без модели) → ответы владельца по Q-286…Q-290 → STAFF2.3b: миграция и права по назначениям
(ADR, `DATA_MODEL.md`, план миграции, красные тесты на изоляцию) → STAFF2.4 карточка и дерево доступа → STAFF2.5
журнал по филиалам → STAFF2.6 безопасность и регрессия. Миграцию на рабочей базе применяет владелец.
