# Изоляция организаций перед открытием регистрации (26.09.2026)

**Основание.** Владелец 26.09 открыл самостоятельную регистрацию с главной (ADR-095). Проверка кода перед этим
(разведка по запросу сессии «UX улучшение», выводы перепроверены руками) нашла пути, по которым вошедший из
**другой** организации читает и меняет данные Luxx. На рабочем сервере регистрация сейчас закрыта
(`/register` — «Самостоятельная регистрация временно закрыта»), поэтому это не действующая утечка, а условие
открытия. Решения владельца 26.09: (1) код места уникален внутри гостиницы — правка модели разрешена;
(2) интеграция Channex, «Неисправности» и свежесть каналов — только организации Luxx и главному администратору.

## Что закрываем

| № | Путь | Что можно было | Как закрываем |
|---|---|---|---|
| 1 | Название объекта при регистрации | Зарегистрироваться как «Luxx Aparts» — служебные пути и ~20 скриптов владельца ищут объект по имени, `findFirst` без порядка | Регистрация отказывает, если объект с таким названием уже есть (без учёта регистра и пробелов); `propertyRef` берёт самый старый объект (`orderBy createdAt`) |
| 2 | `/units/:code` (карточка, блокировки, уборка) и `unitByCode` в бронях | Код места глобально уникален и ищется без объекта: чтение броней и имён гостей Luxx, блокировка её ячеек | **Модель:** `inventory_units.property_id` + `UNIQUE(property_id, code)` вместо глобального `UNIQUE(code)`; все поиски по коду — в паре с объектом |
| 3 | `/analytics/sites*` | Список всех сайтов всех организаций с ключами, отчёт, пауза, удаление, смена доменов | Все запросы репозитория — по объекту вошедшего; тариф по умолчанию — из своего объекта |
| 4 | Виджет `/w` на сайте | Служебный путь всегда брал объект Luxx: сайт чужой организации продавал бы Luxx | Объект — из самого сайта (`tracked_sites.property_id` по публичному ключу) |
| 5 | `/channels/channex/*`, `/guard/*`, `/system/freshness` | Общие на всю платформу: маппинг, журнал событий и очередь Luxx, `setup`/`sync` пишут в Channex-объект Luxx, неисправности Luxx можно принять и закрыть | Гейт `IntegrationOwnerGuard`: служебный ходок, главный администратор или организация объекта Luxx; остальным 403 словами |
| 6 | `categoryById`/`ratePlanById` в бронях, `stayExtraBlocks` в счетах | Поиск по id без объекта | Фильтр по объекту |

## Модель (DATA_MODEL.md v1.11, до кода)

`inventory_units.property_id uuid NOT NULL → properties.id` (денормализация: объект единицы и так выводится через
категорию; хранится, чтобы уникальность кода держала сама база). Миграция `20260926000025_unit_code_per_property`
(перенумерована при объединении веток 27.09.2026 — номер `20260926000024` заняла миграция `seller_prompt_text` с той же соседней ветки):
добавить колонку, заполнить из `accommodation_types.property_id`, `NOT NULL`, снять `inventory_units_code_key`,
поставить `UNIQUE (property_id, code)`; `down.sql` — обратно (при дублях кодов между объектами откат отказывает
словами). `retired-source_room_number` остаётся глобально уникальным: он есть только у Luxx, у новых объектов NULL.
Проверка на рабочей базе перед применением: `SELECT count(*) FROM inventory_units u JOIN accommodation_types t ON
t.id = u.accommodation_type_id WHERE t.property_id IS NULL` → 0.

## Проверки

Красный до зелёного на каждый пункт: модульные (API, домен регистрации), интеграционные на локальной
PostgreSQL (`tests/integration/organization-isolation.test.ts` расширяется: вторая организация не видит и не
меняет ячейку, сайт, сопоставления Luxx; два объекта с кодом «101»), ворота миграций `check-migrations.sh`,
typecheck, lint, UI без базы.

## Чего не делаем

Row Level Security (ADR-056 называет её путём для разделения) — отдельный срез. Интеграцию Channex для других
организаций не проектируем (CLAUDE.md §3): им раздел закрыт. Миграцию на рабочей базе применяет владелец.

## За владельцем

Копия базы → `migrate deploy` с №24 → `--migrations-applied <sha>`; затем `REGISTRATION_OPEN=1` в `.env` API и
`npm run site:deploy` — только после этого кнопка «Регистрация» на главной ведёт на открытую форму.
