> Основание: ТЗ `plans/tz-today-2026-09-27.md` §4 (правила по блокам) и §12.1 (строка A2), ADR-105.
> A1 принят владельцем 28.09.2026 фактом влития PR #103 («Можно начинать A2, но только в рамках уже
> утверждённого плана A2 — без расширения scope и без новых архитектурных решений»).
> Правило A2 из §12.1: **только существующие данные; нет показателя — сначала показать gap, не
> придумывать новый API молча.** API, домен и модель данных не меняются ни строкой. Дизайн-система по
> стилю не меняется. После A2 — **визуальный STOP**: снимки light/dark, A3 только после «да» владельца.

## 1. Состав A2 — ровно строка §12.1


блока не ломает Главную.

## 3. Блоки: источник, что показываем, пробелы

### 3.1. Заезды | Выезды — `GET /desk/today?date=` (уже загружен на Главной, новых вызовов нет)

- Заголовок колонки со временем объекта из `/hotel/settings` (уже загружен): «Заезды · с 14:00»,
  «Выезды · до 12:00».
- Строка: имя гостя 14/600 и номер брони моноширинным; ниже 13 px — категория и ячейка (нет ячейки —
  «⚠ без ячейки», слово DESIGN.md §9); проблема словами из `blockedReason` («нет гражданства»,
  «карточек 1 из 2»); долг `balanceMinor > 0` — «к оплате N ₸» тоном внимания.
- Действие в строке — ссылкой в существующий поток, без новых команд: заезд без ячейки — «Назначить»
  → `/chessboard?from=D&to=D#unassigned-stays`; остальные заезды — «Заселить», выезды — «Выселить» →
  карточка брони `/reservations/{номер}`. Уже заселённые / выехавшие — не строками, а подписью
  «уже заселены: N».
- До 6 строк в колонке; дальше — «Все заезды дня (N)» → `/reservations?arrival=D` (и
  `?departure=D`) — ссылки уже существуют.
- **Пробелы (показаны, не закрываются):**
  - ожидаемого **времени** заезда/выезда у брони нет — только часы объекта; порядок строк — как отдаёт
    API (сначала требующие действия);
  - **источника/канала** в строке дня нет (`DeskRow` его не несёт; склейка с шахматкой покрыла бы не
    все строки) — не показываем;
  - «оплачено» от «ещё не начислено» по проживанию не отличить (`balanceMinor` = 0 в обоих случаях) —
    показываем только долг;
  - заселение **без открытия карточки** (ТЗ §4) — это новая поверхность команды, не данные: в A2 строка
    ведёт в карточку; вынесено отдельным вопросом владельцу, в A2 не делается.

### 3.2. Номерной фонд — `GET /chessboard?from=D&to=D` (уже загружен, новых вызовов нет)

- Строка чисел: занято / свободно / заблокировано (`summary[D]`) и «не готово» (ячейки с
  `housekeepingStatus` ≠ проверено).
- «N ячеек нужно подготовить до заезда»: заезды дня с ячейкой, чья уборка не «проверено».
- Компактная занятость по категориям одной строкой: «Одноместные 8/12 · Мужские койки 31/36 …»
  (`byCategory[D]`, имена — из строк шахматки).
- Ссылка «Шахматка» → `/chessboard?from=D&to=D` (адрес полосы «На стойке»).
- **Пробелы:** состояния «на уборке» (идёт уборка) в модели нет; уборка — текущее состояние, не по
  датам: на завтра и другую дату строка «не готово» и «подготовить» не показываются, вместо них —
  подпись «уборка — только на сегодня».

### 3.3. Уборка и ремонт — та же шахматка (новых вызовов нет)

- Уборка тремя числами слов домена (`packages/domain/src/housekeeping/flow.ts`): «требует уборки»,
  «убрано, ждёт проверки», «проверено» — по активным ячейкам; только на сегодня (см. 3.2).
- Ремонт: ячейки дня с блокировкой типа «ремонт» / «не в продаже» (`cells[].blockType`), до трёх строк
  «код · причина», дальше «ещё N».
- Ссылка «Шахматка» (там фильтр «Уборка»).
- **Пробелы:** отдельной сущности «неисправность номера» нет — ближе всего блокировки ремонта, так и
  подписано («Ремонт и снятые с продажи»); «неисправности» DATA_MODEL §12 — это системные инциденты,
  они в блоке «Системы»; «убираются сейчас» и назначение горничной — нет; ссылки прямо на фильтр
  уборки шахматки нет (фильтр не в адресе).

### 3.4. Деньги сегодня — `GET /finance/report?from=D&to=D` (+1 вызов; права `reports` есть у всех ролей)

- Четыре `Fact`: Начислено (`chargedMinor`), Оплачено (`paidMinor`), Возвраты (`refundedMinor`),
  К оплате — тот же `debtMinor` дня, что плитка strip (одно определение на экране).
- Подпись мелким под «Начислено»: «проживание начисляется в день заезда целиком» — так считает API
  (DATA_MODEL §6, `metrics.ts`), не наше новое правило.
- ~~Владельцу — строка сравнения «Оплачено: вчера X ₸ · в тот же день прошлой недели Y ₸» тем же
  `GET /finance/report` на D−1 и D−7 (+2 вызова только у владельца).~~ **Снято при реализации 28.09
  (пробел):** два отчёта не помещаются в бюджет экрана — см. §4. Без нового API (один отчёт по дням) или
  решения владельца поднять бюджет `/today` сравнения на Главной нет; сравнение периодов — на
  «Показателях за период». Вопрос владельцу — §8.
- Ссылка «Финансы» → `/finance?from=D&to=D`.

### 3.5. Системы — компактные строки

| Строка | Источник (существующий) | Что показываем |
|---|---|---|
| Channex | опрос свежести оболочки (`useFreshness`, тот же, что значок в шапке; **своего вызова нет** — уточнено при реализации, §4; `channex = null` — строки нет) | «обмен N мин назад», «очередь K», «ошибок M» |
| ИИ-продавец (WhatsApp) | `GET /ai-seller/status` (+1; право `dialogs`) | словом: «работает» / «не подключён» / «срок вышел» / «ошибка», по `state` и `lastError` |
| Копии базы и сторож | `GET /guard/status` (+1; 403 у чужой установки — строки нет) | «копии под наблюдением сторожа» / «проверка копий не настроена» (по `lastTick.checked`); «открытых инцидентов: N» → `/incidents` |

- Всё в порядке — блок одной-двумя строками; проблема словом и тоном, подробности — в
  «Требуют внимания» (A3) и в разделах по ссылкам.
- **Пробелы:** здоровья **сайта** как данных нет (есть только события счётчика у владельца) — строки
  «Сайт» нет; отдельного здоровья **WhatsApp** нет — строка говорит о продавце целиком; времени
  последней **копии** как поля нет — только «под наблюдением / не настроено».

## 4. Бюджет запросов

`tests/ui/requests.spec.ts`: не больше 10 вызовов на экран. **Исправлено при реализации 28.09:**
`/system/freshness` и `/auth/me` спек исключает только из проверки повторов, а в общий счёт они входят (в dev
оболочка опрашивает свежесть дважды). До A2 на `/today` было 7: settings, auth/me, first-steps, desk,
chessboard, freshness ×2. Прежний подсчёт «9 у владельца» был ошибкой: с D−1/D−7 и серверной свежестью
выходило 13 (красный `requests.spec`, лог `…09-19-26Z-e2e-97ba.log`). После A2 — ровно **10**: +finance
(день), +seller, +guard; Channex берётся из опроса оболочки, сравнение D−1/D−7 снято (§3.4). Повторов одного
GET нет.
