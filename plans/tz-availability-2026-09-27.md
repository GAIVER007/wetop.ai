# ТЗ — «Свободные места» (Availability v2): инструмент продажи, а не третья вкладка фонда (27.09.2026)

> **Статус: УТВЕРЖДЕНО владельцем 27.09.2026** («ТЗ Availability v2 утверждаю. AV1 запускать после
> первого визуального шага Inventory, как записано в плане») — ADR-107. Утверждено с одной
> корректировкой до старта: **итог за проживание у койко-категорий считается на всё количество гостей
> запроса, а не на одну койку** (§3–§4); у номеров итог — по выбранной occupancy на весь запрос.
> Тем же решением **закрыт Q-199** — правило состава цены «от» в §4. Источник — разбор владельцем
> экрана «Доступность» (`/rooms/availability`): раздел не удаляется, а перепозиционируется. Реализация —
> по разбивке §10 (AV1–AV5), **после первого визуального шага Inventory**; AV1 цен не касается; после
> AV1 — **STOP** и dark/light скриншоты, AV2 — только после визуального подтверждения владельца (тот же
> порядок, что PR A1 Главной — ADR-105). Дизайн-система не меняется (DESIGN.md, ADR-048): это уплотнение
> и перестановка, не редизайн. Модель данных не меняется.

## 1. Роль экрана

Сейчас название «Доступность» читается как ещё одна настройка номерного фонда. По факту это
**быстрый поиск свободного размещения на конкретные даты** — экран, который администратор открывает
на звонке:

> «Здравствуйте, есть что-нибудь с 27 по 30 сентября на двоих?»

Администратор не листает шахматку: ставит даты — и сразу видит, какие категории свободны → сколько
мест → какие конкретно номера/койки → цена → создать бронь.

Роли экранов разведены жёстко:

| Раздел | На какой вопрос отвечает |
|---|---|
| Номерной фонд | Что физически есть в объекте? |
| Категории | Какие типы размещения мы продаём? |
| Шахматка | Кто где размещён по дням? |
| **Свободные места** | Что я могу продать клиенту на выбранные даты? |
| Тарифы | По какой цене это продаётся? |

**Переименование.** В интерфейсе раздел называется **«Свободные места»** (выбор владельца из
вариантов «Свободные места» / «Поиск размещения»). Технически внутри остаётся Availability:
маршрут `/rooms/availability`, имена API и типов не трогаются.

**Что сохраняется обязательно** (принцип уже верен): показываем место, свободное **на весь выбранный
период**, а не просто свободное сегодня.

## 2. Форма поиска

```
Свободные места

Найдите размещение на весь период проживания.

Заезд          Выезд          Гостей
27.09.2026     30.09.2026     2

[ Найти ]

Сегодня · Завтра · Выходные · 7 дней
```

Новое против текущего экрана — **количество гостей**. Сейчас экран не отвечает на запрос «нас трое».
Правила фильтра по гостям (следуют из примеров владельца):

- категория-номер подходит, если её вместимость ≥ числа гостей;
- категория коек подходит, если свободных коек ≥ числа гостей (1 гость / койка);
- комбинации категорий (двухместный + койка на троих) **не предлагаем** — это отдельная логика
  продажи, в этом ТЗ её нет.

После поиска — резюме результата запроса:

```
27–30 сентября · 3 ночи · 2 гостя

Найдено:
12 номеров · 48 койко-мест
```

Резюме показывает **результат конкретного запроса**, а не весь фонд: единицы, не подходящие по
вместимости или условиям, в счётчики не входят. (Сейчас `16 номеров / 72 койко-мест` выглядит как
найденная доступность — убрать.)

## 3. Основной результат — категории, не 88 отдельных мест

Строка категории (компактная, не карточка на пол-экрана):

```
Одноместная с окном

Свободно: 3 из 4
Вместимость: 1 гость
от 25 000 ₸ / ночь

3 ночи · от 75 000 ₸

[ Выбрать ]        [ Показать 3 номера ]
```

Для хостела (пример владельца в утверждающем решении 27.09):

```
Общая мужская
18 свободных коек

8 000 ₸ / койка / ночь
2 гостя · 3 ночи

Итого от 48 000 ₸

[ Выбрать койку ]   [ Показать 18 мест ]
```

**Корректировка владельца 27.09 (до старта):** итог за проживание у койко-категорий считается
**на всё количество гостей запроса**, а не на одну койку — экран отвечает клиенту «сколько будет нам
двоим»: 8 000 ₸ × 2 гостя × 3 ночи = 48 000 ₸. Unit price «8 000 ₸ / койка / ночь» при этом
показывается отдельно. У номеров аналогично: итог — по выбранной occupancy на весь запрос.

## 4. Цена — обязательна (AV2)

Экран соединяет: **свободное место + подходящий тариф + итог за выбранный период.**
Тариф здесь не редактируется — только показывается. Первично — итог за проживание, вторично — за ночь:

```
от 75 000 ₸ за проживание
от 25 000 ₸ / ночь
```

Если допустимых тарифов несколько:

```
3 тарифа
```

Конкретный rate plan выбирается после «Выбрать» (в форме брони, как сейчас).

**Правило состава «от» — решение владельца 27.09.2026, закрывшее Q-199.** В цену «от» участвуют
только тарифные планы, которые:

- относятся к выбранной категории;
- активны / доступны для продажи в текущем контексте стойки;
- имеют цену для требуемой occupancy;
- имеют валидную цену на **каждую** ночь выбранного периода;
- не запрещают продажу этого проживания существующими restrictions (CTA/CTD, min/max stay, stop sell).

Тариф с дырой хотя бы на одной ночи в «от» не участвует. Для каждого допустимого тарифа считается
полная стоимость всего проживания, показывается минимальная. Для койко-категорий полная стоимость —
на всё число гостей запроса (§3). Ни один тариф не прошёл фильтр — категория показывается без цены.

**Никакой новой pricing-логики не пишется**: расчёт — существующий `priceStay` (`packages/domain`,
им живут виджет сайта `/w/availability` и котировка продавца `GET /bot/availability`, ADR-085),
ограничения — существующие restrictions. Деньги — integer minor units (ADR-008). AV1 цен не касается.

**Реализация AV2 (28.09.2026), уточнения исполнителя — не новые правила, а как показано правило владельца:**
«от N ₸ / ночь» — самая низкая цена одной ночи за единицу продажи (номер целиком или койка) среди
допустимых тарифов, без деления итога на ночи (деньги не дробятся на тиыны); в «от» сравниваются только
тарифы в валюте объекта — сравнивать тенге с долларами нельзя, у Luxx все тарифы в KZT. Номер, который
не вмещает всех гостей, цены не получает. Расчёт — `stayOffer` (`packages/domain/src/availability`) поверх
`priceStay` и `assertRestrictionsAllow`; API — `GET /availability/offers?arrival&departure&guests`.

## 5. Конкретные места — свёрнуты по умолчанию (AV3)

Сейчас раскрытие категории вываливает 36 почти одинаковых плиток «Койка 5 → Создать бронь». Вместо
этого:

```
Свободно 18 койко-мест

[Показать места]
```

После раскрытия — компактный список строк, не плитки:

```
301-01     свободно     [Выбрать]
301-02     свободно     [Выбрать]
301-03     свободно     [Выбрать]
301-04     уборка       недоступно
```

Если конкретная койка безразлична — **«Выбрать автоматически»**: система назначает допустимое
свободное место по уже принятому правилу Q-094 (первая свободная активная ячейка категории на весь
период, по номеру ячейки как числу — `ReservationsRepository.firstFreeUnit`). Новое правило посадки
не выдумывается (AGENTS.md §4).

## 6. «Создать бронь» с заполненными полями (AV3)

После выбора категории:

```
Двухместная
27–30 сентября
2 гостя
96 000 ₸

[Создать бронь]
```

Форма брони открывается с заполненными: arrival, departure, guests, category, unit (если выбрали
конкретный), rate. Повторно ничего не вводится. (Сейчас `/reservations/new` получает только
arrival/departure/unit — передачу category/guests/rate дописать.)

## 7. Если мест нет (AV4)

Категорию без мест не всегда прятать. Вместо исчезновения:

```
Двухместная
Нет мест на весь период

Ближайшая доступность:
с 29 сентября

[Посмотреть варианты]
```

Администратор отвечает клиенту: «С 27-го нет, но есть с 29-го». Позже — варианты ±1 день / ±3 дня.
Глубина поиска «ближайшей доступности» вперёд — параметр интерфейса (по умолчанию до 14 дней), не
бизнес-правило.

## 8. Фильтры, переключатель, связи

**Фильтры** — простые: Категория (все) · Тип (номера / койки) · Гостей. Опционально позже: цена,
корпус, этаж. Страницу в Booking.com не превращать.

**Checkbox «Только свободные» убрать.** Раздел называется «Свободные места» — доступные варианты и
есть умолчание. Вместо него переключатель, если нужно видеть sold-out категории:

```
[ Только доступные ]  [ Все категории ]
```

**Связь с шахматкой** — в обе стороны: у категории «Посмотреть на шахматке» (открывает выбранные
даты + category-фильтр — ссылка уже есть, оставить на уровне категории), а из шахматки — «Найти
свободное размещение» сюда.

**Где живёт раздел.** Вкладка внутри Номерного фонда:

```
Номера и койки | Категории | Свободные места
```

И дополнительно вход из: «+ Новая бронь», Главной, Шахматки, Reservations (AV5) — общий инструмент
поиска availability, а не третья настройка Inventory.

## 10. Разбивка (владелец, 27.09.2026)

Availability v2 — после первого визуального шага Inventory:

| Шаг | Содержимое | Зависимости |
|---|---|---|
| **AV1** | Компактный layout: dates + guests, категории списком вместо огромных карточек, summary результатов запроса, переименование в «Свободные места», переключатель вместо checkbox. Цен не касается. **Потом STOP** — dark/light скриншоты, AV2 только после визуального подтверждения владельца | первый визуальный шаг Inventory |
| **AV2** | Price/rate projection по правилу §4: «от N ₸ за проживание» (первично), «от N ₸ / ночь» (вторично), «K тарифов»; итог койко-категорий — на всех гостей запроса | визуальное подтверждение AV1 (Q-199 закрыт 27.09 — §4) |
| **AV3** | Конкретные units компактным списком + «Выбрать автоматически» (правило Q-094) + создание брони с заполненными параметрами | — |

## 11. Технические заметки (для исполнителя)

- Экран: `apps/web/src/app/rooms/[[...section]]/page.tsx` + `apps/web/src/app/rooms/availability-finder.tsx`;
  вкладки — `apps/web/src/app/inventory/fund-tabs.tsx`; стили — `apps/web/src/app/inventory/fund.css`.
- API стойки: `GET /availability` (`apps/api/src/chessboard/chessboard.controller.ts`) — отдаёт
  `nights` и `byCategory{available, units, availableUnitCodes}`; гостей и цен там нет. Фильтр по
  гостям AV1 делается на клиенте по `capacityAdults` из `inventorySummary` — API не трогается.
  Цены AV2 — по правилу §4: существующий `priceStay` и существующие restrictions, новой
  pricing-логики нет.
- Ограничение периода `MAX_CHESSBOARD_DAYS` и пресеты (Сегодня/Завтра/Выходные/Неделя) сохраняются.
- Статус «уборка / недоступно» в списке мест (§5) показывается из тех данных, что уже есть у стойки;
  новые статусы не вводятся.
- UI-набор стойки гонять в один поток (`--workers=1`) через `npm run test:record` — TESTING.md.
