# ТЗ «Категории v2» — сводка, аудит и этапы (27.09.2026)

Источник: ТЗ владельца от 27.09.2026 (чат, «WETOP Hospitality · Категории v2», 49 критериев приёмки).
Решение — ADR-109. Этот файл сводит ТЗ с фактическим кодом и разбивает работу на этапы C1–C6
с обязательной остановкой на скриншоты после C1 (ТЗ §47–48).

---

## 1. Суть ТЗ одним абзацем

Экран «Категории» сегодня — пять больших карточек, каждая почти на полэкрана, с повторяющимися
кнопками («Редактировать», «Показать состав», «+ Номер / койки», «Настроить тарифы», «Открыть в
шахматке»). ТЗ меняет его на компактную таблицу-список: одна строка на категорию, сравнимость между
категориями, действия в контекстном меню «⋯», состав открывается в «Номерах и койках»
(`/inventory?category=…`), а не раскрывашкой на 36 строк. Категория — тип продаваемого размещения,
а не рабочий объект; экран отвечает на четыре вопроса: какие категории есть, что продаётся,
сколько единиц в составе, всё ли настроено для продаж.

## 2. Аудит §45 — что показал код (27.09.2026)

1. **Что такое `AccommodationType`.** Продаваемая категория объекта (DATA_MODEL §1,
   `schema.prisma:100`): принадлежит `Property`, гостиничная сущность, связана с фондом, бронями,
   тарифами и каналами. Гендерное деление dorm — отдельные категории, не атрибут.
2. **Поля.** `code` (у импортированных `retired-source-<id>`, у созданных в UI `category-<uuid>`; смене
   не выставляется), `name`, `kind` (`PRIVATE_ROOM | DORM_BED | APARTMENT`), `capacityAdults`,
   `capacityChildren` (везде 0, детское размещение выключено), `active` (Boolean, default true —
   **в API и UI сегодня нигде не читается и не пишется**, кроме фильтра `active: true` при создании
   комнаты), `retired-sourceId` (внешняя ссылка, ADR-003). Отдельных полей adults/children сверх этого нет —
   форму под них не расширяем (ТЗ §13).
3. **Категория без тарифа.** Модель допускает (связь — join `RatePlanAccommodationType`), но
   `POST /inventory/categories` требует тариф: существующий `ratePlanCode` или имя нового
   (ADR-077: тариф выбирает человек явно). Онбординг (`POST /hotel/onboarding`) тоже создаёт связь.
   «Настроить позже» из ТЗ §14 — изменение поведения бэкенда, этап C3.
4. **RatePlan ↔ категория.** Многие-ко-многим через `RatePlanAccommodationType`; цены — в
   `DailyRate` (категория + тариф + дата + occupancy). «Одной цены категории» в модели нет —
   в списке показываем число тарифов, не цену (ТЗ §28).
5. **Channex ↔ категория.** `ChannelMapping.localAccommodationTypeId` → категория. Сопоставление
   живёт в модуле каналов; в «Категориях» — только сигнал и переход (ТЗ §21).
6. **Переименование** — безопасно, реализовано (`PATCH /inventory/categories/:code`), пишется в журнал.
7. **Смена `kind` после создания** — в API невозможна и не появляется: Q-173 открыт, ТЗ §17–18 это
   подтверждает (ROOM ↔ BED не редактируется как обычное поле).
8. **Удаление/архив** — ни API, ни UI. Поле `active` в схеме есть, но семантика архива
   (что с бронями, доступностью, каналами) — открытый вопрос Q-173. До решения владельца архив
   не строим (ТЗ §19 «Если схемы нет — отдельно согласовать»).
9. **Исторические брони** ссылаются на категорию напрямую: `ReservationItem.accommodationTypeId`
   (плюс `DailyRate`, `Restriction`, `ChannelMapping`). Категорию с историей терять нельзя.
10. **Кто использует категории.** Онбординг (`/hotel/onboarding`), стойка: `/rooms/categories`
    (CategoryCatalog), `/inventory` (InventoryCatalog: боковой список + фильтр `?category=`),
    `FundEditor` (создание/переименование), `/rates?category=…`, `/chessboard?category=…`,
    доступность, ИИ-продавец (факты Б7). Составные экраны от смены вида «Категорий» не зависят.

## 3. Решения ТЗ, зафиксированные в ADR-109

- Основной вид — компактная таблица: Категория · Тип продажи · Фонд · Вместимость · Тарифы ·
  Статус · меню «⋯». Карточки — второй режим, компактные (этап C2, вместе с preview).
- Постоянные кнопки на каждой карточке убираются; действия — в меню «⋯» строки
  (ActionMenu, DESIGN.md §8) и контекстны типу: ROOM → «Добавить номер»,
  BED → «Добавить комнату с койками».
- «Показать состав» из карточки убирается: число единиц — ссылка в `/inventory?category=…`.
  Inventory внутри Categories не дублируется (ТЗ §10–11, §41).
- Смена ROOM ↔ BED недоступна из UI (Q-173); архив вместо удаления — только после решения
  владельца по Q-173 (семантика, влияние на брони и каналы).
- Технические ID (retired-sourceId, channex room type id, UUID) в обычном UI не показываются (ТЗ §29).
- Category Code, порядок категорий (sortOrder), bulk actions — не делаем (ТЗ §27, §30–31:
  поле не придумываем, drag-to-sort не добавляем).
- Доступность в основном списке v1 не показывается — она живёт во вкладке «Доступность» (ТЗ §23).
- READ_ONLY: список и preview открываются, создание/правка/добавление закрыты — общий механизм
  `writeBlocked` (ADR-102), отдельного кода не требует, проверяется в C6.

## 4. Этапы (ТЗ §47) и что в них входит

### C1 — Layout (этот PR) → **STOP, скриншоты §48**

- Таблица вместо больших карточек (`Table` из ui.tsx; на телефоне строки складываются в карточки —
  приём `.dir-table`).
- Компактный верх: заголовок страницы прежний («Категории номеров» — имя пункта меню, на нём стоят
  e2e), «+ Категория» — в действия заголовка, сводка «5 категорий · 16 номеров · 72 койко-места»
  подзаголовком (ТЗ §26).
- Поиск по названию + фильтр типа чипами: Все / Номера / Койко-места / Апартаменты (`.chips`,
  четвёртой копии стилей не заводим). Чип «Апартаменты» показывается только когда такие категории
  есть (на объекте их нет — пустой фильтр не рисуем).
- Меню «⋯» строки: Открыть состав (→ `/inventory?category=`), Редактировать (существующий drawer),
  Добавить номер / Добавить комнату с койками (существующий drawer с преднабранной категорией),
  Настроить тарифы (→ `/rates?category=`), Показать на шахматке (→ `/chessboard?category=`),
  Доступность (→ `/rooms/availability`).
- Колонка «Тарифы»: число активных тарифов категории; 0 — «нет тарифа» словом с тоном внимания
  (ТЗ §20, §28). Для этого `GET /inventory/categories` дополняется полями **только для чтения**:
  `active` и `ratePlans` (число активных связей) — модель данных не меняется, счёт по существующей
  `RatePlanAccommodationType`.
- Колонка «Статус»: слово из поля `active` («Активна»; архива нет — Q-173).
- Категория с 0 единиц: в колонке фонда — «мест нет» тоном внимания, действие — в меню (ТЗ §35).
- Пустое состояние, загрузка, ошибка — существующие `fund-empty` / skeleton / error.tsx (ТЗ §34–37).

Скриншоты C1 (§48): dark и light desktop 1440, 5 категорий формы Luxx, категория с 0 единиц,
длинное имя, ROOM и BED, телефон 390. Папка — `reports/categories-v2-c1-2026-09-27/`.
Следующий этап — только после визуального подтверждения владельца.

### C2 — Quick Preview — **сделано 28.09.2026** (после визуального «да» владельца по C1)
Drawer категории по клику на строку (ТЗ §9, §40); режим «Карточки» компактными карточками
(клик → тот же drawer, ТЗ §7). Как сделано: название строки — кнопка панели, щелчок по строке мимо
ссылок и кнопок тоже открывает её; первый пункт меню — «Открыть» (ТЗ §8). В панели: «Что продаём»
(тип, вместимость словами), «Номерной фонд» (коды мест, если их не больше 12; иначе число и «Открыть
весь состав»; без фонда — что сделать), «Тарифы» по именам без «одной цены» (ТЗ §28; поле
`ratePlanNames` в `GET /inventory/categories`, только чтение), внизу шахматка, доступность,
«Редактировать». «Добавить…» и «Редактировать» открывают прежние формы. Вид «Список / Карточки» —
`?view=cards`, по умолчанию список. Каналы в панели не показываются — это C5 (ТЗ §21).
Снимки — `reports/categories-v2-c2-2026-09-28/`. Дальше — стоп до «да» владельца по C2.

### C3 — форма создания v2 и «Настроить тариф» (28.09.2026, ADR-119)

Решение владельца 28.09: категория создаётся **без тарифа**; тариф — коммерческая настройка, её делают потом.
Цепочка: создать категорию → добавить фонд → настроить тариф → подключить каналы.

**Аудит перед правкой (28.09):**
- обязательность тарифа — только проверка сервиса `createCategory` (`inventory-editor.ts`); в схеме и DATA_MODEL.md
  связь `RatePlanAccommodationType` необязательна, CHECK и триггеров нет — **миграция не нужна**;
- **привязать тариф к существующей категории было нечем** (пишут только создание категории, онбординг, импорт) —
  поэтому в C3 входит команда «Настроить тариф», иначе «позже» значило бы «никогда»;
- без тарифа категорию не продать и сейчас: виджет и котировка ИИ-продавца её скрывают, бронь стойки — 422,
  цена 0 из пустого календаря не получается;
- вне C3 (решение владельца «не трогать Channex и правила цен»): Q-211 (настройка Channex берёт все активные
  категории, категория без мест роняет её) и Q-212 (онбординг пропускает цену 0 ₸); форма новой брони предлагает
  тариф, не привязанный к категории, и отказывает 422 на отправке — экран «Броней».

**Что делаем:**
1. API: `POST /inventory/categories` — явный выбор: `ratePlanCode` / `newRatePlanName` / `ratePlanLater: true`;
   ничего из трёх — 400. `POST /inventory/categories/:code/rate-plan` — привязать существующий или новый (с
   названием) тариф; повтор пары без дубля; журнал `inventory.category.rate_plan_linked`.
2. Форма «Создать категорию»: название; тип продажи — «Номер целиком» или «Койко-место» (апартаменты в первой
   версии формы не предлагаются, модель их хранит); вместимость — у номера поле, у койки «1 гость на койко-место»
   без поля; тариф — «Настроить позже» (по умолчанию) или «Настроить сейчас» → выбрать существующий или назвать
   новый (прежняя ветка ADR-077). Код категории генерируется, человеку не показывается.
3. После создания — шаг «Категория создана»: «Добавить номер» / «Добавить комнату с койками», «Настроить тариф»
   (если тарифа нет) или «Цены в календаре», «Закрыть».
4. «Настроить тариф» — в панели категории и в меню строки у категории без тарифа; открывает выбор тарифа.
5. Статус строки: нет мест или нет тарифа — «Не готова к продаже» (тон внимания) вместо «Активна».

**Не трогаем:** архив, смену «номер ↔ койка», Channex и сопоставление, массовое создание фонда, цены.

**Стоп после C3:** снимки — категория-номер, категория-койка, «Настроить позже», «Настроить сейчас», ошибки формы,
телефон, обе темы, результат создания без тарифа.

## 5. Что этот план не трогает

Модель данных (миграций нет), бизнес-правила бронирования, тарифы и цены, Channex, финансовую
логику. `AccommodationType` не обобщается в ServiceType, с Beauty не объединяется, значения
ROOM/BED не расширяются (ТЗ §46, ARCHITECTURE.md: Hospitality — свой bounded context).
