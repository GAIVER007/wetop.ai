# ТЗ — Каналы продаж v2: менеджер каналов — состояние интеграций (27.09.2026)

> **Статус: сведено по ТЗ владельца 27.09.2026, на подтверждение.** Решение — ADR-106.
> Источник — текст владельца от 27.09 по реальному экрану «Менеджера каналов». Код в рамках
> этой задачи не писался (AGENTS.md §1: до подтверждения плана код не меняется); выполнен
> бэкенд-аудит, который владелец потребовал перед кодом, — §14, по коду, ничего не менялось.
> Этапность CH1–CH6 — §15; после
> CH1 — **стоп** и dark/light скриншоты, следующий этап только после визуального подтверждения
> владельца (тот же порядок, что у этапа А Главной — ADR-105).

---

## 1. Вывод владельца: назначение модуля меняется

Текущий «Менеджер каналов» (`/channel-manager`) на 70–80% — **аналитика источников
бронирования**: период, счётчики броней/отмен/незаездов, стоимость, таблица источников.
Настоящий channel manager отвечает на другой вопрос:

> Подключены ли мои каналы, правильно ли сопоставлены номера и тарифы, синхронизируются ли
> цены/остатки/ограничения и где сейчас есть ошибка?

Решение: не улучшать дизайн текущего экрана, а переразложить назначение:

- **Менеджер каналов** = состояние интеграций и управление ими (connect, map, sync, monitor,
  resolve);
- **брони / выручка / доли по источникам** = аналитика продаж.

WETOP не заменяет Channex: мы строим понятный слой управления и наблюдения поверх существующей
интеграции, не новый OTA-движок.

## 2. Меню: один пункт «Каналы продаж»

Сейчас в секции «Продажи» два пункта: «Менеджер каналов» (`/channel-manager`) и «Синхронизация
каналов» (`/channels`) — `apps/web/src/lib/navigation.ts:231-243`. Остаётся **один пункт
«Каналы продаж»**, внутри вкладки:

```
Обзор | Подключения | Сопоставление | Синхронизация | События
```

Секция «Продажи» после слияния: Тарифы · Каналы продаж · ИИ-продавец · Сайт и
онлайн-бронирование (аналитика — своим разделом).

Это развитие плана `plans/channel-manager-unification-2026-09-20.md` (там предлагались две
вкладки «Статистика | Синхронизация»): пункт меню по-прежнему один, но статистика теперь не
вкладка менеджера каналов, а раздел аналитики (§11). Расчётные правила того плана (оплаты через
PaymentAllocation, валюты не складывать, алиасы по ADR-024, Q-154 про «отказы») остаются в силе
для аналитического экрана.

## 3. Вкладка «Обзор» (этап CH1)

Открывается **в текущем состоянии системы**, без аналитического фильтра периода — фильтр
«Заезд с / Заезд по / Статус / Показать» с этого экрана уходит вместе со статистикой.

```
Каналы продаж

Все каналы работают                       [ + Подключить канал ]

Активных каналов   N
Последняя синхр.   2 мин назад
В очереди          0
Ошибок             0
Без сопоставления  0
```

- **Строка здоровья**: «Все каналы работают» / «⚠ Требует внимания» со списком проблем и кнопкой
  [Исправить] — незавершённые сопоставления, застой синхронизации, ошибки очереди и событий.
  Сигналы и пороги — существующие (§14.5): сторож, `GET /system/freshness`, `QUEUE_STALE_MIN`.
  Новых порогов не выдумывать (AGENTS.md §4). Те же проблемы попадают на Главную в Attention
  (ТЗ Главной, ADR-105 — блок «Системы»).
- **Карточки подключений**: статус (● Работает / ⚠ Требует настройки / недоступен), «через
  Channex», сопоставлено категорий M/N и тарифов M/N, галочки цены/остатки/ограничения, время
  последней синхронизации, [Открыть]. Пока подключение одно (Channex, объект Luxx) — карточка
  одна; вид списка каналов внутри карточки — §5.
- **Компактный sales-summary** вместо полной статистики: доли за 30 дней **по числу броней**
  (деньги в двух валютах в одну долю не сложить — правило плана 20.09) и ссылка
  «Подробнее в аналитике →».

## 4. Источник брони ≠ канал дистрибуции

Модель уже различает: `Reservation.source` (DESK, PHONE, WHATSAPP, WALK_IN, INSTAGRAM, OTA,
WEBSITE — `schema.prisma:193-201`) и `Reservation.channel` (текст «Booking.com» и т. п. у OTA).
В менеджере каналов «Стойка», «Сайт», «WhatsApp» **не показываются как подключённые каналы** —
это источники броней, их место в аналитике источников. Карточки подключений — только
дистрибуция (Channex и каналы через него).

## 5. Вкладка «Подключения»

Channex — агрегатор, поэтому карточка одна:

```
Channex                               ● Подключён

Property ID
••••••••

Каналы через Channex:
Booking.com · Agoda · …

Последняя связь: сегодня 19:46

[Настройки]
```

- Ключи и секреты не показываются ни в каком виде (маска, «Обновлено <дата>»); сейчас они и не
  доступны экрану — только env (§14.7).
- Состояние подключения — существующий `GET /channels/channex/connection` (READY / NO_KEY /
  NO_MAPPING / MAPPING_MISMATCH / DENIED / NOT_FOUND / RATE_LIMITED / UNREACHABLE).
- Список каналов через Channex: из документации проекта известен `GET /channels/list`
  (`docs/channex/site/`, использован 08.09 — Q-032, Q-096). Если чтения списка на этапе нет —
  показывать каналы, встречавшиеся во входящих бронях, и явно писать «по полученным броням».
  Новых вызовов Channex вне `/docs` не писать (AGENTS.md §5).
- «Переподключить» / «Отключить» — с подтверждением; фактическое отключение затрагивает приём
  броней, поэтому кнопка на MVP может вести к инструкции/поддержке, а не дергать API — решается
  на этапе CH6 по факту доступных безопасных операций.

## 6. Мастер «Подключить канал»

Шаги: провайдер (Channex) → аккаунт/Property → сопоставление категорий → сопоставление
тарифов → проверка → включить. Перед включением — проверочный экран (категории сопоставлены,
тарифы сопоставлены, валюта, остатки и цены получены). Основа — существующий
`POST /channels/channex/setup` (повтор не дублирует сопоставленное) и `GET connection`;
новых протоколов не строить. Пока подключение жёстко привязано к объекту Luxx
(`integration-owner.ts`), мастер для второго объекта не обещать — экран честно говорит
«Подключаем партнёров вручную» (в духе ADR-102), см. §13.

## 7. Вкладка «Сопоставление» (этап CH2)

Два раздельных блока, не одна большая форма:

- **Категории**: WETOP-категория ↔ Channex room type, статус ✓/⚠, действие «Сопоставить»;
- **Тарифы**: WETOP rate plan ↔ Channex rate plan, статус.

Незавершённое сопоставление — actionable-предупреждение с последствием: «До исправления продажи
этой категории не синхронизируются» — это правда по коду: ревизия по несопоставленной комнате
падает `UnmappedRoomError` → событие FAILED (§14.4). Данные — существующий `GET mapping`
(строки `channel_mappings`, §14.1–2). Сейчас счётчик «Без сопоставления» — это категории/тарифы
объекта без строки сопоставления; редактирование пар в UI — только поверх существующего
`setup`, произвольного редактора Channex-идентификаторов не строить.

## 8. Вкладка «Синхронизация» (этап CH3)

Сюда переезжает содержимое текущего экрана `/channels`. Показывается состояние, а не
технический дамп:

```
Остатки          ✓ 19:46
Цены и ограничения ✓ 19:46      ← в очереди это один вид: RESTRICTIONS несёт и цену (§14.3)
Брони            ✓ 19:45

Очередь          0
Ошибки           0
```

- **Свежесть**: «● Актуально / ⚠ Данные устарели N минут [Проверить]» — по `GET
  /system/freshness` и порогам сторожа (§14.5). Раскрытие по сущности (последняя отправка, что
  изменено, результат) — вторичная деталь.
- **Очередь**: человеческие строки («Цена · Deluxe · 30 сентября — ожидает отправки»);
  пустая очередь — строка «Очередь пуста», не пустая таблица. Данные — `GET outbox/rows`,
  `GET outbox`.
- **Ошибки**: actionable-список («Rate plan not mapped → [Исправить сопоставление]»), а не stack
  trace; технический payload — в раскрываемых деталях для поддержки.
- **Ручная синхронизация**: аудит подтвердил, что безопасные ручные операции уже существуют и
  висят на кнопках `/channels` — `POST sync` (полная выгрузка, мимо очереди), `POST
  outbox/flush`, `POST pull`, `POST events/:id/retry` (§14.6). Кнопка «Синхронизировать сейчас»
  с выбором (остатки/цены-ограничения) — обёртка над ними, **новых механизмов не добавлять**.
  `data-testid` и порядок существующих команд не менять: на них записан показ для сертификации
  Channex (DESIGN.md §8, строка «Ручные действия по каналам»).

## 9. Вкладка «События» и inbox (этап CH4)

- **Лента** — человеческим языком: «19:46 · Цены отправлены · 5 категорий · успешно»,
  «19:43 · Получена новая бронь · Booking.com · #…». Технические поля (revision id, payload,
  queue id) — в drawer «Детали». Данные — существующие `GET events`, `GET events/:revisionId`,
  `GET outbox/messages`.
- **Входящие брони**: последние брони из каналов (время, канал, гость, даты, категория, сумма);
  клик ведёт в бронь. Управление бронью — в «Бронированиях», не здесь.
- **Требуют разбора** — полноценный inbox вместо поиска плашки в шахматке: события FAILED с
  причиной («категория не сопоставлена», исчерпаны попытки) и действием [Разобрать] →
  существующая страница ревизии и «Обработать заново». По коду «неразобранная ревизия» — это
  `ExternalEvent.status=FAILED` (отдельной таблицы нет, §14.4). **Правила применения ревизий не
  трогать**: развилки по заселённым/выехавшим/незаездам — открытые Q-158, Q-161, Q-195; inbox их
  показывает и даёт существующие действия, новых правил не вводит.

## 10. Deep links

- Главная, Attention «Channel sync stale» → Каналы продаж, вкладка «Синхронизация»;
- шахматка, «входящая бронь требует разбора» (Q-135) → вкладка «События», конкретная ревизия;
- тарифы, ошибка синхронизации → карточка подключения.

Форма адресов (`?tab=…&id=…`) — деталь реализации этапов; ссылки с Главной — по ТЗ Главной
(ADR-105, блок «Системы»).

## 11. Куда уходит текущая аналитика

Данные не удаляются. Экран «брони/отмены/незаезды/стоимость + таблица источников» с фильтром
периода переезжает целиком в **Аналитика → Источники продаж** (существующий `GET
/hotel/channel-report` — там же). Правила расчёта — по плану 20.09 (оплаты через
PaymentAllocation, только COMPLETED; возвраты отдельным подзапросом; валюты раздельно; алиасы
ADR-024; колонка «Отказы» — только после ответа Q-154). В обзоре каналов остаётся компактный
summary (§3) со ссылкой в аналитику. Правило то же, что в ADR-105: при переносе функциональность
не удаляется — либо она уже доступна в аналитике, либо PR явно показывает, куда перенесена.

## 12. READ_ONLY и права

- В READ_ONLY (пробный период истёк — ADR-102) смотреть можно всё: каналы, сопоставления,
  синхронизацию, события. Изменения (подключить, сопоставить, ручной sync, отключить) — нельзя.
  По коду это уже так: `SessionGuard`/`writeBlocked` пропускает GET и режет POST (§14.12);
  на этапе CH6 кнопки в READ_ONLY выключаются заранее с объяснением, а не падают 403.
- **Серверная синхронизация и webhook при READ_ONLY продолжают работать** — иначе гостиница
  перестанет получать брони. Аудит подтвердил: фоновые воркеры и `@Public`-webhook под
  `writeBlocked` не попадают. Это уже принято в логике trial (ADR-102), здесь не меняется.
- Права `channels.read / channels.manage / channels.sync` — позже, вместе с ролями §16
  DATA_MODEL (ADR-083); сейчас доступ решает организация объекта интеграции и главный
  администратор (`IntegrationOwnerGuard`, `ChannelOperatorInterceptor` — ADR-095, Q-193),
  hardcode на роль OWNER не вводить.

## 13. Пустые состояния и ошибки

- Нет каналов: «Каналы ещё не подключены. Подключите Booking.com, Agoda и другие OTA. —
  [Подключить]». Для организации не-Luxx до платформенной фазы интеграций честнее:
  «Подключаем партнёров вручную» + контакт (в духе ADR-102), а не мастер, который упрётся в 403.
- Ошибка загрузки: «Не удалось загрузить состояние каналов. [Повторить]» — не
  «Failed to fetch external_events». Ошибка загрузки ≠ достоверный ноль (правило плана 20.09).
- Канал недоступен: «Booking.com недоступен. Последняя успешная связь: … Проверьте подключение
  Channex. [Проверить]».

## 14. Бэкенд-аудит (по §33 ТЗ; выполнен 27.09.2026 по коду, ничего не менялось)

1. **Модели** (`packages/database/prisma/schema.prisma`): `ChannelMapping` (`channel_mappings`,
   :539) — property/provider, `localAccommodationTypeId`/`localRatePlanId`,
   `providerPropertyId`/`providerRoomTypeId`/`providerRatePlanId`; поля `channel*` в коде не
   используются (всегда null). `ExternalEvent` (`external_events`, :579) — журнал входящих:
   `provider`+`externalEventId` UNIQUE (идемпотентность, ADR-007), status
   RECEIVED/PROCESSING/PROCESSED/FAILED, attemptCount, lastError, receivedVia
   WEBHOOK/PULL/MANUAL. `ChannelOutbox` (`channel_outbox`, :611) — очередь ARI: kind
   AVAILABILITY/RESTRICTIONS, status PENDING/SENT/FAILED, attempts, nextAttemptAt. Таблицы
   подключения/ключей нет.
2. **Виды сопоставления**: строки `ChannelMapping` двух видов — строка объекта (только
   `providerPropertyId`) и строка «категория+тариф» (одна на пару). Пишет только
   `ChannexSyncService.setup()` (`apps/api/src/channels/sync.service.ts:184-260`).
   Сопоставления уровня OTA-канала в PMS нет — его ведёт Channex.
3. **ARI наружу**: `OutboxAriPublisher` (`apps/api/src/channels/ari-publisher.ts`) ставит в
   очередь AVAILABILITY (пересчёт свободных мест) и RESTRICTIONS (**цена едет внутри
   RESTRICTIONS** вместе с min/max stay, stop sell, CTA/CTD — отдельного вида «цены» нет).
   `OutboxWorker` (`outbox.worker.ts`): такт 5 с, минимум 6 с между отправками вида (лимит
   Channex 10 req/min), до 200 строк за проход, MAX_ATTEMPTS=6, backoff `min(60с·2^n, 6ч)`,
   после 6 попыток FAILED. Аварийный `CHANNEX_ARI=off` копит очередь, приём броней не трогает.
   Полная выгрузка `fullSync` (500 дней, до 730) — мимо очереди, по расписанию раз в сутки
   (`CHANNEX_FULL_SYNC_HOUR`, 03:00 Алматы) и вручную.
4. **Входящие**: webhook `POST /channels/channex/webhook` (`@Public`, секрет в заголовке,
   `timingSafeEqual`) + опрос ленты раз в 5 мин (`inbound.service.ts`); разбор ревизии — журнал
   → транзакция → PROCESSED → ack. **Отдельной таблицы «неразобранных» нет**: это
   `ExternalEvent.status=FAILED` (в т. ч. `UnmappedRoomError` «booking_unmapped_room»,
   неоднозначная связка ADR-024) + потолок 6 попыток, дальше кнопка «Обработать заново»
   (`POST events/:revisionId/retry`). Предупреждения успешного разбора — в `lastError`
   PROCESSED-события с префиксом «Предупреждение:».
5. **Свежесть/сторож**: `WebhookHealthService` — проба адреса раз в 5 мин, окно пропуска 30 мин;
   сторож (`guard.service.ts`) — `feed.stale` 15 мин, `outbox.stuck` 15 мин, `sync.missing`
   26 ч, сверка `ari.oversell` раз в 60 мин, автопочинки (retry, flush, fullSync,
   registerWebhook). `GET /system/freshness` отдаёт `lastEventAt`, `outboxPending`,
   `outboxFailed`, `oldestPendingAt`; UI-порог застоя очереди `QUEUE_STALE_MIN = 10`
   (`apps/web/src/components/data-freshness.tsx`). Эти пороги и есть основа строки здоровья §3.
6. **Ручной sync есть и безопасен** (повтор не дублирует: UNIQUE-ключи, ack, идемпотентный
   setup): `POST sync` (fullSync), `POST sync/scheduled?force=1`, `POST outbox/flush`,
   `POST pull`, `POST events/:id/retry`, `POST setup`. 503 при выключенном ARI, 422 без
   сопоставлений. Кнопки уже стоят на `/channels` (`channels/buttons.tsx`), их `data-testid`
   заморожены сертификацией Channex.
7. **Ключи**: только env всей установки (`CHANNEX_API_KEY`, `CHANNEX_WEBHOOK_SECRET`,
   `CHANNEX_API_BASE_URL` — по умолчанию staging, `CHANNEX_PRODUCTION=1` — допуск к production),
   не per-organization. Id объекта Channex — в `channel_mappings.provider_property_id`.
   Интеграция жёстко привязана к объекту Luxx (`integration-owner.ts`, `operator-access.ts`).
8. **API для UI уже есть**: `GET mapping`, `GET connection` (8 состояний), `GET webhook/status`,
   `GET events`/`events/:id`, `GET outbox`/`outbox/rows`/`outbox/messages`,
   `GET /system/freshness`, `GET /hotel/channel-report` (аналитика источников) + POST-действия
   §14.6. Экраны: `/channel-manager` (статистика с фильтром периода, счётчики, таблица
   источников), `/channels` (полоса состояния, кнопки двух групп, очередь, входящие события,
   таблица сопоставлений, страница ревизии), `/connections` (панель Channex).
9. **Источник ≠ канал в данных**: `Reservation.source` (enum) + `Reservation.channel` (текст) +
   `externalId` (номер у канала, UNIQUE с propertyId). Поля «провайдер получения» на брони нет.
   Нормализация имён — `packages/integrations/src/channex/channel-names.ts` (ADR-024).
10. **Привязка к Location в будущем**: по `ARCHITECTURE.md` конфигурация интеграции планируется
    на Location; сейчас — installation-level env (п. 7). **Перенос ключей в новую модель — не
    задача этого ТЗ** (§16 «чего не делаем»); UI v2 работает поверх существующей интеграции Luxx.
11. **План 20.09** (`plans/channel-manager-unification-2026-09-20.md`): выполнен только аудит и
    нормализация имён каналов в отчёте; вкладки, колонки оплат/возвратов и слияние меню не
    делались — их поглощает это ТЗ (статистика уходит в аналитику, меню сливается этапом CH5).
12. **Права/READ_ONLY**: прав `channels.*` нет; роли OWNER/STAFF на каналы не влияют; доступ
    решают `IntegrationOwnerGuard` + `ChannelOperatorInterceptor` (организация объекта
    интеграции или главный администратор — ADR-095). `SessionGuard`/`writeBlocked` (ADR-102) в
    READ_ONLY пропускает GET и режет POST; webhook (`@Public`) и фоновые воркеры под запрет не
    попадают. Кнопки на `/channels` по READ_ONLY заранее не выключаются — доделка этапа CH6.

## 15. Этапность

| Этап | Состав | Правила |
|---|---|---|
| **CH1 — Обзор** | убрать аналитический фильтр периода; строка здоровья; счётчики; «Требует внимания»; карточка подключения; компактный sales-summary со ссылкой в аналитику | только существующие API (§14.8); после CH1 — **стоп, dark/light скриншоты** (§15.1) |
| **CH2 — Сопоставление** | категории и тарифы раздельно; статусы; actionable-предупреждение | поверх `GET mapping` и `setup` |
| **CH3 — Синхронизация** | свежесть по сущностям; очередь; ошибки; «Синхронизировать сейчас» | обёртки над §14.6; `data-testid` сертификации не трогать |
| **CH4 — События / Inbox** | человеческая лента; входящие брони; «Требуют разбора» | правила ревизий не менять (Q-158, Q-161, Q-195) |
| **CH5 — слияние меню** | один пункт «Каналы продаж»; статистика — в аналитику; убрать «Синхронизацию каналов» | функциональность не удалять — показывать, куда переехала |
| **CH6 — polish** | READ_ONLY-состояния кнопок; mobile; empty/error; подготовка к правам `channels.*` | DESIGN.md; обе темы; доступность |

Каждый этап — свой PR со своим планом среза и red-before-green по затрагиваемым тестам
(AGENTS.md §1, §6); UI-набор — в один поток (`--workers=1`).

### 15.1. Визуальный стоп после CH1

Dark/light скриншоты состояний: всё в порядке · застой синхронизации · незавершённое
сопоставление · очередь > 0 · ошибка · нет каналов · один канал · несколько каналов.
До CH2 — стоп, ждём подтверждения владельца.

## 16. Чего не делаем (зафиксировано владельцем)

Multi-provider abstraction «на будущее»; прямые API Booking.com; собственный OTA-движок;
изменение домена Channex и нового ARI-протокола; перенос credentials в per-Location модель
(отдельная платформенная фаза); ИИ-исправление сопоставлений; автоматический revenue
management. Плюс постоянные ограничения проекта: production ARI/Channex production — только по
AGENTS.md §9; интеграционный код — только по `/docs` (§5); модель данных не меняется (ТЗ
выполняется на существующей схеме — §14.1).

## 17. Приёмка

Управляющий за 10 секунд отвечает: какие каналы подключены · работают ли · когда последний
sync · есть ли очередь · есть ли ошибка · все ли категории сопоставлены · все ли тарифы ·
требуется ли действие · где исправить · пришла ли последняя OTA-бронь.
