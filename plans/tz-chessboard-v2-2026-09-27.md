# ТЗ — WETOP Hospitality · Шахматка v2

Передано владельцем 27.09.2026 как готовое ТЗ для разработчика. Текст сохранён дословно
(убраны только артефакты копирования). Шахматка остаётся Hospitality-модулем: Beauty потом
получает отдельное расписание; `Chessboard`, `Reservation`, `InventoryUnit` и hotel-specific

Сопоставление с кодом и разбивка на PR — `plans/chessboard-v2-2026-09-27.md` (AGENTS.md §1:

## 1. Цель

Шахматка — главный рабочий экран администратора гостиницы/хостела.
Пользователь должен с одного экрана:

* видеть загрузку по датам;
* видеть размещение гостей;
* понимать свободные/занятые места;
* создавать бронь;
* назначать номер/койку;
* переселять;
* продлевать;
* менять даты;
* заселять/выселять;
* быстро видеть долги и проблемы;
* блокировать места;
* работать с уборкой/недоступностью;
* находить гостя, бронь, номер или койку.

Главный принцип:
Шахматка должна позволять провести большую часть смены, почти не открывая другие разделы.

## 2. Что сейчас НЕ надо менять архитектурно

Не переделывать:

```

Allocation
InventoryUnit
AccommodationType
Property

```

Не делать из шахматки универсальный календарь.

```

Текущий аудит уже показал, что backend/grid-алгоритм частично переиспользуемый, но сам `board-grid.tsx` и API шахматки hotel-specific.

* месяц;
* переход по датам;
* поиск;
* фильтр категории;
* комнаты / койки;
* категории;
* drag&drop;
* resize/продление;
* брони без назначенной ячейки;
* отображение свободных мест категории;
* статусы уборки;
* создание новой брони;
* существующие API и domain-правила, если они достаточны.

Не переписывать рабочую логику ради визуального рефакторинга.

## 6. Управление датами

Сделать одну компактную строку.

```
‹     21–27 сентября 2026     ›

Сегодня

[ 7 дней ] [ 14 дней ] [ 30 дней ]

[ Даты ]
```

Поведение
Стрелка влево:

* при 7 днях → предыдущие 7;
* 14 дней → предыдущие 14;
* 30 дней → предыдущие 30.

Стрелка вправо аналогично.
`Сегодня` возвращает диапазон, содержащий текущую дату.
`Даты` открывает calendar range picker.

## 7. Не использовать «Месяц» как основной режим

Лучше:

```
7 дней
14 дней
30 дней
```

Потому что шахматке нужен rolling period.
Если нужен полноценный календарный месяц — можно оставить внутри `Даты`.

## 15. Категории

Категория — отдельная sticky/group row.
Пример:

```
⌄ Одноместная комната с окном                         4 номера

     21       22       23       24       25
     3 св.     3 св.    4 св.    4 св.    1 св.
```

Если:

```
0 св.
```

показывать warning-state.
Категория может:

```
сворачиваться
разворачиваться
```

По умолчанию состояние сохранять пользователю.

Для хостела нужна правильная иерархия.

```

    ├── Койка 02
    ├── Койка 03
    └── ...
```

Не превращать все 72 койки в плоский список без контекста.
Можно сворачивать комнату.

## 18. Карточка брони — базовый вид

Карточка должна быть главным визуальным объектом.

```

## 47. Работа с правами

UI не должен показывать действие, которое пользователь не имеет права выполнять.
Например если пользователь read-only:

```
drag disabled
resize disabled
new booking disabled
```

Но просматривать шахматку может.
Архитектура ролей далее расширится, поэтому permission checks не хардкодить вокруг одного имени роли.

## 48. Audit

Все важные действия из шахматки:

```
move
extend
shorten
assign
unassign
block
unblock
check-in
check-out
```

должны продолжать попадать в AuditLog согласно существующим правилам.
Нельзя ради удобного frontend выполнять изменения вне нормальных backend-команд.

## 49. Optimistic UI

Можно применять для безопасных операций.
Например:

```
move reservation
```

UI сразу показывает новое положение.
Если backend отклоняет:

```
Не удалось переселить:
место уже занято

[Вернуть]
```

UI обязан откатиться.
Backend остаётся source of truth.

## 50. Collision / race conditions

Даже если frontend показывает место свободным, сервер обязан повторно проверить availability.
Сценарий:
два администратора одновременно перемещают две брони в один номер.
Допустимый результат:

* одна операция успешна;
* вторая получает понятный conflict;
* никаких двойных allocations.

Существующий DB-level no-overlap guard сохраняется.

## 51. Auto-refresh

Шахматка должна получать актуальные изменения.
Для MVP можно:

```
poll каждые N секунд
```

или текущий механизм, если уже существует.
Позже WebSocket/SSE.
Но никогда:

```
пользователь работает 30 минут со старой шахматкой
```

и не знает о бронях из OTA.

## 52. Обновление без разрушения контекста

При refresh:
не сбрасывать:

```
scroll position
selected date range
filters
collapsed categories
open preview
```

Если бронь изменилась извне — аккуратно обновить.

## 53. Channex/OTA update

Если пришла внешняя бронь:
она появляется в grid.
Можно кратко подсветить:

```
Новая бронь · Booking.com
```

без popup, мешающего работе.
Если требует размещения:
автоматически попадает в:

```
Брони без размещения
```

## 54. UX ошибки изменения

Не показывать:

```
Error 409
```

Показывать:

```
Не удалось продлить проживание

Номер 203 уже занят с 29 сентября.

[Выбрать другой номер]
```

Domain errors должны переводиться в человеческие сообщения.

## 55. Visual design

Сохранить текущий WETOP стиль:

* dark/light theme;
* существующие tokens;
* radius;
* typography;
* blue accent;
* restrained UI.

Не делать:

* gradients;
* neon;
* glassmorphism;
* случайные новые цвета;
* слишком большие shadows.

Основное изменение:
контраст и информационная иерархия.

## 56. Поверхности

Должны визуально различаться:

```
Page background

Toolbar

Grid header

Category row

Unit row

Today column

Booking

Block

Hovered cell

Selected range
```

Сейчас многие уровни слишком близки по тону.

## 57. Высота строк

Не делать огромными.
Обычный desktop mode ориентировочно:

```
Category row: 40–44px
Unit row: 52–60px
```

Compact:

```
36–44px
```

Не воспринимать числа как жёсткий pixel-perfect контракт — соблюдать текущую дизайн-систему.

## 58. Бронь должна иметь минимальную ширину

Если бронь занимает одну ночь и места мало:
не пытаться вывести 4 строки текста.
Использовать adaptive content:
широкая:

```
Иван Петров
Booking · 3 ночи
```

узкая:

```
Иван П.
```

очень узкая:

```
ИП
```

Tooltip всегда содержит полную информацию.

## 59. Today column

Переделать текущую синюю колонку.
Нужно:

* выделенный header;
* очень лёгкий background;
* возможно border-left/right.

Не насыщенная заливка всей высоты.

## 60. Ключевая UX-метрика

Проверить вручную сценарий:
Новая бронь по телефону.
Администратор:

1. открывает шахматку;
2. видит свободный номер;
3. выделяет 27–30;
4. нажимает «Новая бронь»;
5. вводит гостя;
6. сохраняет.

Цель:
не больше одного перехода/модального flow.

## 61. Второй сценарий

Гость хочет продлить проживание.
Администратор:

1. находит гостя;
2. тянет край брони;
3. видит новую стоимость;
4. подтверждает.

Без ручного поиска Reservation в другом разделе.

## 62. Третий сценарий

Переселение.
Администратор:

1. drag карточки;
2. видит допустимые места;
3. переносит;
4. подтверждает изменение стоимости, если есть.

## 63. Четвёртый сценарий

Заезд.
Администратор:

1. нажимает бронь;
2. quick preview;
3. `Заселить`.

Если есть блокер:

```
Не оплачено
Документы не заполнены
Номер не готов
```

показать до заселения.

## 64. Пятый сценарий

Две брони без места.
Администратор:

1. видит warning сверху;
2. открывает drawer;
3. система показывает допустимые свободные места;
4. назначает.

## 65. Что убрать из текущего UI

Убрать/сократить:

* огромный блок «Без ячейки»;
* крупное синее выделение всей сегодняшней колонки;
* отдельные постоянно видимые группы из множества фильтров;
* лишнее пустое пространство;
* постоянную инструкцию «как работать»;
* дублирование информации между category row и header;
* длинные confirmation IDs внутри самих booking cards.

## 66. Что добавить

Добавить:

* quick preview;
* contextual actions;
* interactive empty cell;
* drag preview;
* price delta;
* warning indicators;
* status semantics;
* sticky headers;
* density switch;
* smarter unassigned drawer;
* improved filters;
* better search;
* meaningful empty/loading/error states.

## 67. Backend/API — сначала аудит текущего

Перед изменением API разработчик должен перечислить:

```
какие endpoints шахматки уже существуют;
каких данных не хватает UI v2;
какие данные можно получить из существующих responses;
какие требуют новых lightweight endpoints.
```

Не тащить в chessboard payload гигантские полные сущности Reservation/Guest/Folio, если для grid нужно 8 полей.

## 68. Suggested lightweight booking projection

Для rendering потенциально достаточно концептуально:

```
reservationItemId
reservationNumber

guestDisplayName

unitId
unitCode

arrival
departure

status
source

paymentState
balanceMinor

hasAttention

canMove
canResize
```

Это не команда немедленно создавать новый контракт.
Сначала сравнить с текущим API.

## 69. Никакого N+1

Шахматка не должна отдельно запрашивать:

```
guest
finance
source
status
```

для каждой карточки.
Grid API должен отдавать достаточную projection батчем.

## 70. Mutation endpoints

Операции:

```
move
extend
shorten
assign
block
unblock
```

должны быть command-oriented, если существующие endpoints уже так работают.
Не делать frontend:

```
PATCH 7 разных таблиц
```

Backend выполняет бизнес-операцию транзакционно.

## 71. Acceptance criteria

Новая шахматка считается готовой, когда:

1. В первом viewport видны toolbar и сама grid.
2. Левая колонка и даты sticky.
3. 88 мест Luxx работают без визуального торможения.
4. 7/14/30 дней работают.
5. Поиск работает по гостю/брони/номеру.
6. Фильтры можно сбросить.
7. Category collapse работает.
8. Booking quick preview работает.
9. Drag&drop сохраняет текущие business rules.
10. Resize сохраняет business rules.
11. Нельзя создать overlap.
12. Создание брони из пустого диапазона работает.
13. Брони без размещения можно назначить из drawer.
14. Финансовая проблема видна на карточке без перегрузки.
15. Статус уборки виден у unit.
16. Today визуально выделен, но не доминирует.
17. Ошибки backend показываются человеческим текстом.
18. Все изменения продолжают аудитироваться.
19. Existing Hospitality tests остаются зелёными.
20. Channex/архивный источник reconciliation не меняется.
21. Существующие Reservation/Allocation ID не меняются.
22. Light/dark theme не ломаются.
23. При refresh не сбрасывается рабочий контекст пользователя.

## 72. Порядок реализации

Не делать всю шахматку одним гигантским PR.
Разбить:

```
PR 1
Layout + toolbar + visual hierarchy

PR 2
Grid visual refactor + sticky + categories

PR 3
Booking card + quick preview

PR 4
DnD / resize UX

PR 5
Create from empty range

PR 6
Unassigned drawer

PR 7
Filters/search/density

PR 8
Loading/error/performance polish
```

Если существующие тесты заставляют безопаснее разбить иначе — разработчик должен предложить.

## 73. Главное ограничение

Не переписывать рабочую Hospitality domain logic ради нового интерфейса.
Новый интерфейс обязан адаптироваться к доказанному backend/domain там, где текущая модель корректна.
Изменение domain допускается только если конкретный UX-сценарий невозможно реализовать существующим контрактом и это отдельно доказано.

## Итоговый продуктовый принцип

Шахматка WETOP должна ощущаться не как:
таблица, где видно брони.
А как:
единое рабочее пространство администратора для управления размещением.
Пользователь должен видеть ситуацию, принимать решения и выполнять основные действия прямо на сетке.
