# ТЗ: посадить WETOP на домен wetop.ai

**Дата:** 15.09.2026. **Основание:** ADR-045 (принят 14.09), `plans/wetop-domain-2026-09-14.md` §6 и §8,
`docs/site/domain-wetop-2026-09-15.md`. **Исполнитель:** агент в Cowork на Mac владельца — там `.env`,
службы launchd, `cloudflared`, доступ к Supabase, Exely и Channex. С другой машины задача не делается:
половина шагов — это службы и ключи на этом Mac.

**Результат, за который отвечает исполнитель:** три адреса работают так, как описано в §6 «Приёмка», и это
доказано не словами, а ответами команд и отчётом в `reports/`.

---

## 1. Задача одним абзацем

Домен `wetop.ai` куплен на Spaceship, его DNS пуст, серверы имён — регистраторские. Нужно перевести домен в
Cloudflare, выложить главную платформы на Cloudflare Pages, поднять постоянный именованный туннель с Mac на
`app.wetop.ai` (стойка за входом) и `api.wetop.ai` (только публичные пути API), закрыть стойку входом
Cloudflare Access, перевести webhook Channex и код счётчика на постоянный адрес и убрать быстрый туннель.
Код для этого уже написан — задача сводится к настройке, проверке и разбору того, что не сойдётся.

## 3. Что уже готово в коде — не переделывать

Проверено 14–15.09.2026:

- `apps/site` — главная и блог, статическая сборка: `npm run site:build` → `apps/site/out` (7 страниц, 1,4 МБ);
- `apps/site/src/site.config.ts` — единственное место для данных владельца; пустое поле скрывает блок, «TODO» на
  сайт не попадают, битая ссылка роняет сборку с понятной ошибкой;
- `scripts/ops/cloudflared-wetop.example.yml` — конфиг туннеля с белым списком путей и проверкой токена Access
  на стороне `cloudflared`;
- `scripts/ops/launchd/install.sh domain` — служба постоянного туннеля; быстрый туннель (`tunnel`) вместе с ней
  не ставится;
- API: наружу только шесть путей, IP посетителя из `CF-Connecting-IP` (только от loopback), регистрация webhook
  на адрес, отличный от `PUBLIC_API_URL`, отбивается 409;
- стойка: `/login` показывает почту из `cf-access-authenticated-user-email` и кнопку «Выйти».

Если на месте что-то из этого окажется не так — это дефект, а не повод переписывать схему: чинить точечно,
тестом красный → зелёный, и записать в отчёт.

## 4. Кто что делает

Агент не имеет доступа к браузеру владельца, к аккаунтам Cloudflare и Spaceship и к `.env`. Всё, что ниже
помечено «владелец», агент готовит текстом и просит нажать, а потом проверяет результат командой.

| Шаг | Кто | Что вернуть агенту |
|---|---|---|
| Аккаунт Cloudflare, Add a domain → `wetop.ai`, план Free | владелец | два адреса NS |
| Spaceship → Domains → `wetop.ai` → Nameservers → Custom | владелец | «сохранено» |
| Zero Trust: имя команды, план Free | владелец | имя команды |
| Access → Applications → Self-hosted `app.wetop.ai`, политика Allow по почтам | владелец (или агент, если у него есть доступ к Zero Trust) | AUD-тег приложения, список почт |
| `cloudflared tunnel login` и `wrangler login` — подтверждение в браузере | владелец | «вошёл» |
| `.env`: `PUBLIC_API_URL=https://api.wetop.ai` | владелец | «вписал» (значение не печатать) |
| Данные для главной: название, город, контакты, канал заявок (Q-129) | владелец | текст или «пока без этого» |
| Mac: питание от сети, запрет сна при закрытой крышке | владелец | «сделано» |
| Всё остальное — команды, конфиги, проверки, отчёт | агент | — |

**Важно про Spaceship:** от него нужны только серверы имён. DNS-хостинг, почту, «веб-хостинг», переадресацию
и privacy-надстройки там покупать не нужно — это делает Cloudflare бесплатно. Если владелец показывает корзину
с чем-то, кроме продления домена, сказать, что для задачи это не требуется.

## 5. Работы по этапам

У каждого этапа: что сделать, чем доказать, когда остановиться и спросить.

### Э0. Снимок «как было» (15 минут)

1. Ветка от свежего `main`: `git fetch origin main && git checkout -B domain/wetop origin/main`.
2. `scripts/ops/launchd/status.sh` — какие службы живы; `npm run test:status` — что доказано на текущем коде.
3. Записать текущий адрес webhook в Channex (`GET /channels/channex/webhook/status` через стойку или API) и
   текущий адрес быстрого туннеля — понадобится для отката.
4. Сверка до работ: `npm run reconcile:day` за сегодня и T6 по остаткам. Если уже есть расхождения — сначала
   разобрать их, потом трогать домен: иначе после переключения непонятно, чьё это.

**Доказательство:** вывод `status.sh`, `test:status` и сверки в черновике отчёта.

### Э1. Домен в Cloudflare (владелец нажимает, агент ждёт)

1. Владелец: Cloudflare → Add a domain → `wetop.ai` → Free → получить два NS.
2. Владелец: Spaceship → Nameservers → Custom → вставить оба → сохранить.
3. Агент проверяет, пока не сойдётся: `dig NS wetop.ai +short` должен вернуть адреса Cloudflare.
   Обычно минуты, по правилам реестра — до суток. Ждать проверками раз в несколько минут, не долбить.

**Стоп:** пока NS не сменились, шаги Э2–Э5 не делать — Cloudflare не выдаст сертификаты, и результат
проверок будет ложным.

### Э2. Главная на Cloudflare Pages

1. Заполнить `apps/site/src/site.config.ts` тем, что дал владелец (Q-129). Чего не дал — оставить пустым.
   **Ничего не придумывать:** ни названия компании, ни контактов, ни отзывов, ни цен.
2. Показать владельцу локально: `npm run dev -w apps/site` → 127.0.0.1:3002. Дождаться «выкладывай».
3. `npm run site:build` — сборка должна пройти без ошибок и предупреждений.
4. Владелец: `npx wrangler@latest login` (браузер).
5. `npx wrangler@latest pages project create wetop-site --production-branch main`, затем `npm run site:deploy`.
6. Cloudflare → Workers & Pages → `wetop-site` → Custom domains → добавить `wetop.ai` и `www.wetop.ai`.
   DNS-записи Cloudflare поставит сам.

**Репозиторий к Pages не подключать.** Он приватный, в истории финансы объекта и рабочие контакты
(`SECURITY.md` §4); наружу отдаётся только собранная папка `apps/site/out`. Это решение, а не предпочтение:
менять его — через владельца и ADR.

**Доказательство:** `curl -sI https://wetop.ai` → 200; открываются `/blog/`, `/sitemap.xml`, `/robots.txt`;
`https://www.wetop.ai` ведёт туда же; главная жива при выключенной стойке.

### Э3. Именованный туннель

По шапке `scripts/ops/cloudflared-wetop.example.yml`:

1. Владелец: `cloudflared tunnel login` → выбрать `wetop.ai`.
2. `cloudflared tunnel create wetop` → запомнить TUNNEL-ID и путь к файлу ключа.
3. `cloudflared tunnel route dns wetop app.wetop.ai` и то же для `api.wetop.ai`.
4. Скопировать образец в `~/.cloudflared/wetop.yml`, подставить TUNNEL-ID, путь к ключу, имя команды Zero Trust
   и AUD-тег приложения Access (из Э4 — этапы можно делать в порядке Э4 → Э3, если удобнее).
5. `scripts/ops/launchd/uninstall.sh tunnel && scripts/ops/launchd/install.sh domain`.
6. Проверить, что быстрый туннель больше не поднимается: `scripts/ops/launchd/status.sh` показывает `domain`;
   попытка `install.sh tunnel` при живом `domain` должна отказать.

**Доказательство:** `status.sh`, ответы `curl` из §6, отсутствие в журналах перерегистрации webhook каждые две
минуты (этим занимался скрипт быстрого туннеля).

### Э4. Вход в стойку (Cloudflare Access)

1. Zero Trust → имя команды (например, `wetop`), план Free. Cloudflare может попросить карту — план $0.
2. Access → Applications → Self-hosted → домен `app.wetop.ai` → политика **Allow** по списку почт владельца.
3. Взять AUD-тег и имя команды, вписать в `~/.cloudflared/wetop.yml`, перезапустить службу `domain`.
4. Проверить втроём: без входа — страница Access; почта из списка — стойка и на `/login` видно «Вы вошли
   как …»; посторонняя почта — отказ.

**Доказательство:** три скриншота или три ответа `curl` (без токена — 302 на Access), запись в отчёте.

### Э5. Постоянный адрес API

1. Владелец вписывает в `.env`: `PUBLIC_API_URL=https://api.wetop.ai`. Значение агент не печатает и не читает
   из `.env` (`SECURITY.md` §3).
2. `launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.api`.
3. Стойка → `/channels` → «Зарегистрировать webhook». Проверить, что в Channex стоит
   `https://api.wetop.ai/channels/channex/webhook`.
4. Убедиться, что попытка зарегистрировать webhook на любой другой адрес отвечает 409.
5. Сторож: `GET /channels/channex/webhook/status` — адрес совпадает с ожидаемым, «под подозрением» не стоит.

**Доказательство:** живая бронь на staging Channex доходит в PMS webhook'ом за секунды (записать время),
`received_via = webhook`, а не `pull`.

### Э6. Код счётчика и виджета для сайта отеля

1. `/analytics/setup` → взять новый код с адресом `https://api.wetop.ai`.
2. Заменить мёртвый адрес быстрого туннеля в `docs/site/snippet-luxx-aparts.html`
   (`profit-offered-rotary-titanium.trycloudflare.com` → `https://api.wetop.ai`) и в
   `docs/site/install-2026-09-12.md`, если он там есть.
3. Проверить снаружи: `https://api.wetop.ai/a/pms.js` и `/w/widget.js` отдают 200 и правильный адрес внутри.

**На настоящий сайт отеля код не ставить** — адрес сайта и форма поиска дат ещё не подтверждены (Q-111).
Постоянный адрес снимает только своё препятствие (Q-112).

### Э7. Проверка живьём

1. Полный проход §6 «Приёмка» — все строки.
2. Channex: цикл брони на staging (создать → перенести → отменить) через экраны стойки на `app.wetop.ai`;
   сверка T6 остатков — 0 расхождений.
3. Прогоны через журнал тестов: `npm run test:record -- e2e` (в один воркер) и UI-обход экранов. Лог и строку
   журнала коммитить вместе с правками.
4. Сквозная сверка `cli-system-trace.ts` за сегодня — слои сходятся.

### Э8. Записать

1. Отчёт `reports/wetop-domain-2026-09-15.md`: что сделано, чем доказано, сколько заняло, что не сошлось.
2. `CLAUDE.md` §2 — короткий абзац о состоянии (адреса живы, webhook на постоянном адресе, что осталось).
3. `QUESTIONS.md`: **Q-112 закрывается** доказательством из Э5 (постоянный адрес API есть). Q-111, Q-129,
   Q-070 и Q-123 остаются открытыми — их этот ТЗ не решает.
4. `CUTOVER.md` условие 1: отметить, что половина закрыта (webhook на постоянном адресе), **сервер в РК —
   нет**; условие целиком остаётся невыполненным.

## 6. Приёмка

Задача принята, когда каждая строка даёт ожидаемый ответ, и ответы приложены к отчёту.

| # | Проверка | Ожидаемо |
|---|---|---|
| 1 | `dig NS wetop.ai +short` | серверы имён Cloudflare |
| 2 | `curl -sI https://wetop.ai` и `https://www.wetop.ai` | 200, HTTPS без предупреждений |
| 3 | `https://wetop.ai/blog/`, `/sitemap.xml`, `/robots.txt` | открываются, ссылки живые |
| 4 | главная при остановленных службах API и стойки | по-прежнему открывается |
| 5 | `https://app.wetop.ai` без входа | страница входа Cloudflare Access, не стойка |
| 6 | вход почтой из списка | стойка открывается, `/login` показывает эту почту и «Выйти» |
| 7 | вход посторонней почтой | отказ |
| 8 | `curl -s -o /dev/null -w '%{http_code}' https://api.wetop.ai/a/pms.js` и `/w/widget.js` | 200 |
| 9 | `https://api.wetop.ai/w/demo`, `/a/demo`, `/reservations`, `/guard` | 404 |
| 10 | webhook без секрета | 401 |
| 11 | webhook в Channex | `https://api.wetop.ai/channels/channex/webhook`, попытка сменить адрес → 409 |
| 12 | живая бронь на staging | приходит в PMS webhook'ом, `received_via = webhook`, время записано |
| 13 | T6, остатки по клеткам | 0 расхождений |
| 14 | `scripts/ops/launchd/status.sh` | служба `domain` жива, `tunnel` снят |
| 15 | сверка суток и `cli-system-trace.ts` | сходятся так же, как до работ |
| 16 | `npm run test:record -- e2e` | зелёный, лог в журнале тестов |

## 7. Запреты

- не менять модель данных и бизнес-правила брони, цен, денег (`CLAUDE.md` §3, `AGENTS.md` §15);
- не придумывать тексты о компании, контакты, цены, отзывы и клиентов — только то, что дал владелец;
- не читать и не печатать значения из `.env`, не коммитить `.claude/settings.local.json`;
- не подключать приватный репозиторий к Cloudflare Pages, GitHub Actions или другому внешнему сборщику;
- не выставлять наружу ничего сверх шести путей из `SECURITY.md` §11, демо-страницы — тем более: бронь с них
  настоящая;
- не включать `PII_STORAGE=real` и не трогать переключение каналов: домен этого не разрешает, нужен сервер в РК
  (`CUTOVER.md` условие 1);
- не трогать Exely production и OTA production;
- `git add -A` и `git commit -a` запрещены — коммит своих файлов явным списком: в дереве работают другие сессии;
- любая правка кода — тест красный до неё и зелёный после; прогоны только через `npm run test:record`.

## 8. Откат

Если после переключения что-то важное встало (стойка недоступна смене, брони не приходят):

1. `scripts/ops/launchd/uninstall.sh domain && scripts/ops/launchd/install.sh tunnel` — вернуть быстрый туннель;
2. перерегистрировать webhook на его адрес (`/channels`); при `PUBLIC_API_URL=https://api.wetop.ai` API ответит
   409 — временно убрать переменную из `.env` (это делает владелец) и перезапустить API;
3. проверить, что брони каналов идут (webhook или опрос ленты), и записать в отчёт, что именно не сработало.

Откат домена в Spaceship (возврат NS регистратора) не нужен: главная на Pages и туннель — независимые слои,
DNS при откате остаётся в Cloudflare.

## 9. Заминки, которых стоит ждать

| Что | Что делать |
|---|---|
| Домен долго не «активен» в Cloudflare | ждать и проверять `dig`; ускорить нельзя, это реестр |
| Zero Trust просит карту при бесплатном плане | это известное поведение Cloudflare, план $0; решает владелец |
| `cloudflared` пускает на стойку без Access | не заданы `teamName`/`audTag` в `~/.cloudflared/wetop.yml` — проверить оба |
| Стойка за прокси ругается на источник запроса | `allowedOrigins` в `apps/web/next.config.ts` уже настроен на `app.wetop.ai`; если нет — дефект, чинить точечно |
| После перезапуска Mac туннель не поднялся | служба launchd `domain`; `launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.domain` |
| Mac уснул и утянул API с туннелем | питание от сети и запрет сна (шаг владельца); в отчёт — если повторилось |
| Pages отдаёт старую версию | это прямая загрузка, не Git: нужен повторный `npm run site:deploy` |

## 10. Что не входит

- сервер в Казахстане и перенос туда PMS (Q-070, условие 1 `CUTOVER.md`): адреса `app` и `api` при переезде
  не меняются, меняется машина под туннелем;
- собственные учётные записи, роли и регистрация с пробным периодом (ADR-023, Q-129);
- установка счётчика и виджета на настоящий сайт отеля (Q-111);
- переключение каналов и двойной ввод — отдельные условия допуска;
- внешний вид стойки (решение ментора 13.09, ADR-027).

## 11. Что спросить у владельца до начала

1. Почты, кого пускать в стойку (`app.wetop.ai`).
2. Данные для главной: название компании, город, контакты, куда ведёт «Попробовать бесплатно» (Q-129) —
   или «пока без этого».
3. Подтверждение, что главную можно выкладывать (первая публикация во внешний сервис).

Пока нет ответа на 1 — Access настраивать не на что; пока нет ответа на 2 — главная выкладывается с пустыми
блоками, это допустимо.
