# ТЗ — «Номерной фонд v2» (27.09.2026, вечер)

Источник — ТЗ владельца от 27.09.2026: «Номерной фонд функционально есть, но сейчас он больше
похож на админку справочника, чем на сильный рабочий модуль PMS». Решение — ADR-107.
Здесь ТЗ сведено к плану работ: аудит §48 по реальному коду, разбивка I1–I8, стоп-гейт после I1.

Главная продуктовая мысль ТЗ: экран должен отвечать не «какие записи есть в таблице
InventoryUnit», а «как устроен мой объект: комнаты, номера, койки, их состояние и что с ними
можно сделать». Самое важное для Luxx с 72 койками — создание хостельной комнаты с несколькими
койками за один flow (он уже есть в API, см. аудит п. 6 — не хватает формы, которую понимает
администратор).

---

## 1. Аудит §48 — как фонд устроен в коде на 27.09.2026

Вопросы ТЗ §48, ответы — по schema.prisma, `apps/api/src/inventory`, `apps/api/src/units`,
`scripts/imports/src/read-inventory-from-db.ts`, `packages/domain/src/inventory`.

| # | Вопрос §48 | Ответ по коду |
|---|---|---|
| 1 | Связи Building / Floor / PhysicalRoom / AccommodationType / InventoryUnit | `Property → Building → Floor → PhysicalRoom → InventoryUnit`; `InventoryUnit → AccommodationType` строго 1:1 (DATA_MODEL §1). Код места уникален внутри объекта: `UNIQUE(property_id, code)` (v1.12, ADR-099); комната уникальна на этаже: `UNIQUE(floor_id, room_number)` |
| 2 | Заполнен ли PhysicalRoom у всех 88 | Да, у каждой единицы `physical_room_id NOT NULL`. Импорт Luxx заполняет 1:1 (ADR-013, Q-095 отложен): 88 единиц = 88 записей PhysicalRoom |
| 3 | Есть ли реальные hostel rooms или всё 1:1 | У Luxx — всё 1:1 до списка Q-095 (какие койки в какой из 4 dorm-комнат — знает только владелец). Но редактор фонда УЖЕ создаёт настоящие иерархии: `POST /inventory/rooms` для категории DORM_BED создаёт одну PhysicalRoom (`is_dorm`, `capacity = N`) и N коек в ней |
| 4 | Как InventoryUnit различает ROOM/BED | Enum `kind` (`ROOM \| BED`) на единице; при создании выводится из `kind` категории (`DORM_BED → BED`, иначе `ROOM`) |
| 5 | Где хранится capacity | Продаваемая вместимость — `AccommodationType.capacity_adults` (койка всегда 1). Физическая — `PhysicalRoom.capacity` (у dorm = числу коек). Сводка 92 гостя считается `summarizeInventoryPlan`: BED → 1, ROOM → вместимость комнаты |
| 6 | Как создаётся unit; можно ли N beds одной транзакцией | `POST /inventory/rooms` (`inventory-editor.ts`): в ОДНОЙ транзакции upsert Building → upsert Floor → create PhysicalRoom → `createMany` InventoryUnits + запись в журнал. N коек за раз уже работает (textarea «по одному на строку»); не хватает удобной формы «количество коек → 301-01…301-12» и bulk-номеров |
| 7 | Есть ли archive/active | В модели есть: `InventoryUnit.active`, `AccommodationType.active` (умолчание true). API выключения НЕТ (редактор умеет только create/rename), UI нет. Физического удаления нет нигде — правильно. Правила архивирования (что с будущими бронями, ARI) — вопрос владельцу, Q-199 |
| 8 | Как blocks / housekeeping / incidents связаны с InventoryUnit | Блокировки: `InventoryBlock` (unit + даты + `type MAINTENANCE\|MANAGEMENT\|OUT_OF_ORDER\|OTHER` + reason), API `/units/:code/blocks`. Уборка: `housekeeping_status` на единице + журнал `HousekeepingEvent`, цикл в `@pms/domain` `housekeeping/flow.ts`, API `/units/:code/housekeeping`. «Неисправность номера» как сущности НЕТ: `SystemIncident` (§12 модели) — поломки ПРОГРАММЫ, к номерам отношения не имеет. Ремонт/поломка номера в модели — блокировка с типом и причиной («ремонт: кондиционер», DESIGN §9). Вторую incident-систему не создаём — ТЗ §34 закрывается показом блокировок |
| 9 | Как category связана с rate plans / Channex | `RatePlanAccommodationType` (M:N; создание категории привязывает или создаёт тариф). Channex: `ChannelMapping.local_accommodation_type_id / local_rate_plan_id` → provider room type/rate plan. Семантику не трогаем (ADR-004, ТЗ §49) |

Дополнительно найдено при аудите:

- `GET /inventory/units` не отдаёт ни корпус/этаж, ни уборку, ни блокировки, ни `active` —
  для колонок «Расположение / Состояние / Уборка» (ТЗ §9) читающий API надо дополнить
  (схема не меняется, только выборка).
- Дерево фонда кэшируется на 60 с по объекту (`PrismaInventoryRepository`); уборка и блокировки —
  живые, их в кэш класть нельзя — читать отдельным свежим запросом (как `countActiveBlocks`).
- `apps/web/src/app/rooms/room-grid.tsx` не импортируется никем — мёртвый код, снять при I1.
- `summarizeInventoryPlan` считает `physicalRooms` по множеству `roomNumber` без этажа: две
  комнаты «201» на разных этажах посчитаются одной. На Luxx не проявляется; поправить по пути.

## 2. Соответствие ТЗ ↔ модель (что уже решено, менять нельзя)

- **Модель данных не меняется ни в одном срезе I1–I8.** Всё ТЗ ложится на утверждённую модель
  v1.12: иерархия, N коек транзакцией, active, блокировки, уборка уже есть.
- **«Неисправность» (ТЗ §34)** = `InventoryBlock` с типом `MAINTENANCE`/`OUT_OF_ORDER` и причиной
  словом. Отдельного вида «неисправность места» не заводим (ответ на «источник данных сначала
  проверить»).
- **«По комнатам» (ТЗ §8, I5)**: до списка Q-095 у Luxx покажет 88 комнат по одной единице —
  честно, но бесполезно. Вид строится в I5 и полезен для новых объектов, заведённых редактором
  (там dorm-комнаты настоящие); Luxx группируется после ответа на Q-095 данными, без схемы.
- **Channex semantics (ТЗ §49)**: `AccommodationType / InventoryUnit / RatePlan / ChannelMapping`
  не переименовываются и не обобщаются (ARCHITECTURE.md §8: Hospitality-контур не переписывается,
  «Room → generic Resource» запрещён).
- **Hospitality-only**: модуль виден только Hospitality; для Beauty его нет (ARCHITECTURE.md §9).
  Сейчас вертикалей в меню нет — учитывается в PR-ах архитектуры v3, не здесь.
- **READ_ONLY (ТЗ §38)**: общий механизм уже есть (`readOnlyOf` в `lib/desk-person.ts`,
  `SessionGuard` 403 на запись, ADR-102) — экран его наследует, письмо-запреты в UI — I8.
- **Права (ТЗ §39)**: как в остальной стойке — по `NavigationAccess`/способностям, не по роли;
  расширение под Location Manager — вместе с ADR-104 фазами, не здесь.

## 3. Разбивка реализации (ТЗ §50)

### I1 — Layout + information hierarchy ← ЭТОТ PR, после него визуальный STOP
- Sidebar: раздел «Номерной фонд» — один пункт `/inventory` (вместо трёх); deep links
  `/rooms/categories`, `/rooms/availability` живут, вкладки внутри страницы остаются.
- Header: подзаголовок «Luxx Aparts · 88 мест»; справа `[+ Добавить ▼] [Шахматка]`;
  отдельная кнопка «Доступность» из шапки снята (она — вкладка).
- «+ Добавить» — выпадающее меню: «Номер», «Комнату с койками», «Категорию» (открывают
  существующие drawer-формы; сами формы переделывает I3).
- Сводка: «Единиц продажи 88 · Номеров 16 · Койко-мест 72 · Вместимость 92 · Недоступно N»
  (N — действующие блокировки на сегодня, как считает API; testid сохраняются).
- Левая панель категорий снята; категория — фильтром в toolbar (select), тип — чипами
  «Все 88 | Номера 16 | Койки 72».
- Таблица: Место · Категория · Расположение (корпус, этаж · комната) · Вместимость ·
  Состояние (доступен / заблокирован до … причиной) · Уборка (значками §7/§9) · «⋯».
- 88 кнопок «Редактировать» сняты: строка кликабельна (карточка места), справа меню «⋯»
  (Открыть, Показать на шахматке, Переименовать комнату).
- Виды: «Список» по умолчанию на desktop; «Карточки» остаются для телефона (вид «По комнатам» — I5).
- API (только чтение, схема не меняется): `GET /inventory/units` дополняется
  `buildingName`, `floorName`, `housekeepingStatus`, `active`, `block { dateTo, type, reason }`
  (действующая на сегодня); уборка и блокировки — свежим запросом мимо кэша дерева.
- Снять мёртвый `rooms/room-grid.tsx`.
- Тесты: обновить `tests/ui/inventory-catalog.spec.ts`, `navigation.spec.ts`,
  `tests/e2e/inventory.spec.ts` под новую разметку; testid `inventory-summary`, `unit-row`,
  `category-row`, `total-units/rooms/beds/max-guests` сохранить.

**Стоп-гейт (ТЗ §51):** dark и light, desktop 1440 (шапка + таблица), кейсы — номер, койка,
разные категории, уборка, заблокировано, неисправность (блокировка MAINTENANCE с причиной),
88 units, длинное название категории; минимум один mobile. До «да» владельца I2 не начинать.

### I2 — Quick Preview
Drawer места по одному клику: категория, расположение, вместимость, состояние, уборка,
блокировки, «сейчас» (свободен/занят, следующая бронь), действия. Данные — `GET /units/:code`
(уже отдаёт всё, кроме следующей брони — дополнить чтение).

### I3 — Creation flows
Три отдельных формы: «Добавить номер» (категория, номер; корпус/этаж — автоматически, если
корпус один; display label — под «Дополнительными настройками»), «Добавить комнату с койками»
(количество коек → предпросмотр «301-01…301-12 · будет создано: 1 комната, 12 коек»),
«Добавить категорию» (тариф необязателен — «Настроить позже»; после создания — «Добавить
номера»). Проверка дубля кода — до submit (`GET /inventory/units` уже на клиенте).
Тариф-«настроить позже» трогает `createCategory` — сейчас тариф обязателен: ослабить можно
без модели (связь M:N остаётся пустой), поведение записать в план I3 отдельно.

### I4 — Bulk creation
«Несколько номеров 101–120» с предпросмотром и валидацией; сервер — тот же `POST /inventory/rooms`
раз на номер в одной транзакции или новый пакетный вход (без изменения модели).

### I5 — «По комнатам»
Иерархический вид Корпус → Этаж → Комната → места. Для Luxx осмыслен после списка Q-095.

### I6 — Categories v2
Таблица категорий (Категория · Что продаём · Единиц · Вместимость · Базовый тариф · Статус),
drawer, безопасное редактирование (предупреждения при бронях/тарифах/Channex-сопоставлениях),
архив вместо удаления — только после ответа на Q-199.

### I7 — Availability v2
Категории × даты: всего / продано / заблокировано / доступно, предупреждение при нуле,
ссылки на шахматку/тарифы/каналы. Данные считаются как `GET /availability` (те же правила).

### I8 — Polish
URL-state всех фильтров, responsive, пусто/загрузка/сбой по DESIGN §8, READ_ONLY-запреты в UI,
права, производительность на 300+ units, доступность.

## 4. Что убираем / сохраняем / не трогаем (ТЗ §45–47, §49)

Убираем: submenu из трёх пунктов, дубли навигации, кнопку «Доступность» в шапке, четыре
равнозначные CTA, левый список категорий, «Карточки» как основной desktop-вид, 88 «Редактировать»,
поле «Обозначение номера в шахматке» из основного flow (I3), ручное создание каждой койки (I3–I4).

Сохраняем: название «Номерной фонд», сводку 88/16/72/92, вкладки, поиск, категории, list view,
building/floor, доменные модели, ссылки на шахматку, токены/тему DESIGN.md.

Не трогаем: семантику Channex-сущностей, финансовую логику, бизнес-правила бронирования,
модель данных, `data-testid` записи сертификации Channex.

## 5. Открытые вопросы

  историей, Channex ARI; кто вправе). До ответа архив в UI не строится (I6 предупреждает).
- **Q-095 (старый, отложен):** список «какие койки в какой dorm-комнате» — нужен, чтобы вид
  «По комнатам» (I5) был полезен на Luxx.
