## ПРИОРИТЕТ B — дефекты приёма ревизий каналов (до боевых каналов)

Перенесены из PR #9 (`reports/inbound-review-2026-09-15.md`). На боевой это правила приёма входящих броней — их надо закрыть до подключения каналов с потоком.

- **Q-158** — ревизия по заселённому/выехавшему проживанию: приём не проверяет статус, отмена снимает койку под живущим гостем, модификация возвращает заселённого в «ждём». Предложение: не применять, ставить `FAILED` и будить дежурного. *(Смягчено для первого канала: Hostelworld заселённых в момент переключения не имеет.)*
- **Q-159** — порядок ревизий: нет сравнения версий, «Обработать заново» на старой ревизии откатывает бронь. Нужно поле «время последней применённой ревизии» — **правка `DATA_MODEL.md` до кода**.
- **Q-160** — отмена брони, которой нет в PMS: подтверждается каналу и исчезает, сторож видит только `FAILED`. Предложение: инцидент класса Б, не подтверждать до разбора.
- **Q-161** — дефекты модификации из канала: (а) смена типа комнаты не переносит гостя; (б) комнаты сопоставляются по порядку, а не по составу; (в) суммы без сверки валюты; (г) уменьшение состава оставляет предоплату минусом. Что правило, что дефект — вопрос владельцу; (б)(в)(г) чинятся одним срезом.

**Критерий готовности блока:** по каждому вопросу — решение владельца в `QUESTIONS.md`, затем срез с red→green тестом; приём входящих не ломает заселённые брони и не подтверждает вслепую.

- **Q-162…Q-165** — дефекты повторного импорта Exely. **Актуальны только при реимпорте дампа**, а Exely больше не источник (ADR-052). Рекомендация: пометить «неактуально до реимпорта» и не тратить срез сейчас; решение — владельца. *Сверка 22.09:* если по Q-167 выбран импорт из Exely, эти четыре становятся блокерами до первого канала — не закрывать до ответа на Q-167.

## ПРИОРИТЕТ C — SaaS-трек (после первой живой смены, порядок ADR-046/Q-139)

Владелец: «SaaS-сервис, партнёры/компании, у каждого свои этапы регистрации, логин/пароль, вход, мы видим статус оплат». Шаг 1 (вход, роли, автор в журнале) — сделан. Шаги 2–4 — после первой смены.

- **C1. Мультитенантность до конца (Q-152).** *Сверка 22.09:* в `main` с 21.09 регистрация заводит свой объект, вошедший видит только объект своей организации (замок в приложении, ADR-061; модульные тесты `apps/api/src/database/property-ref.test.ts`). Осталось: Row Level Security; тест разделения на настоящем PostgreSQL; ключи Channex и почты сейчас на установку, а не на организацию; служебные пути (webhook, виджет, сторож) берут объект по имени Luxx. Спор ADR-055/061 ↔ ADR-056 — Q-157. **Критерий:** данные одной организации не видны другой; тест изоляции.
- **C2. Онбординг доделать.** Отель → номера → цены одной транзакцией. *Сверка 22.09:* сервис, экран и тесты есть (`apps/api/src/hotel/onboarding.ts`, `packages/domain/src/onboarding`, `tests/ui/onboarding.spec.ts`); нет сквозного «регистрация → подтверждение почты → онбординг → бронь → заселение» на настоящей базе. **Критерий:** новичок из пустого кабинета за один экран доходит до «можно поселить гостя» (категория+места+тариф+цены на горизонт); e2e.
- **C3. Подписки, пробный период, биллинг, статус оплат — НЕ построено.** В коде модулей подписок/биллинга нет. Нужны: организации-арендаторы, пробный период (после 7 дней — только чтение, ADR-046), тарифные планы подписки, приём оплаты, экран «статус оплат» для владельца платформы. **Требует модели платформы v2 в `DATA_MODEL.md` (ADR-019 отложен) — сначала модель, потом код.** *Сверка 22.09:* до модели нужны ответы владельца Q-141 (чем платят партнёры), Q-143 (тарифы WETOP), Q-144 (пробный период), Q-145 (где ПД сотрудников). Окончание пробного периода в коде не исполняется: статус TRIAL и срок ставятся, перехода в «только чтение» нет. **Критерий:** организация регистрируется сама, живёт в пробном периоде, платит, статус оплаты виден владельцу; тесты.
- **C4. Q-153** — продлевается ли смена по паролю (сессии). Решение владельца → срез.
- **C5. Q-157 / Q-129** — сайт обещает «Заявку», продукт строит регистрацию. Свести: куда ведёт «Попробовать бесплатно», нужен ли раздел «О компании» (название/город/контакты). Решение владельца.
