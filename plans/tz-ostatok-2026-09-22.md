# ТЗ — остаток работ по WETOP (на 22.09.2026)

Собственная PMS для хостела **Luxx Aparts** (Алматы, 88 единиц) взамен Exely, дальше — SaaS-продукт.
Документ описывает **что осталось**, в порядке приоритета, с критерием готовности в каждой задаче.
Пишется для переезда в новый чат: открыть сессию в папке проекта, прочитать `HANDOFF.md` §3, затем этот файл.

**Правило проекта:** задача не закрывается словом «done» — нужен тест, скриншот или отчёт сверки
(AGENTS.md §10). Диагноз до правки. Модель данных меняется через `DATA_MODEL.md`, потом код. Развилка
по данным/деньгам/availability/тарифам/каналам — вопрос в `QUESTIONS.md`, гадать запрещено.

## ПРИОРИТЕТ A — довести переезд Luxx Aparts на боевую

Пять условий допуска до переключения каналов (ответ ментора 13.09, пересмотр 20.09, `CUTOVER.md`). Пока не закрыты все пять — **ни один настоящий канал не подключается**.

### A1. Сервер и база в Казахстане + webhook на него  — **главный блокер**
**Что:** перенести PMS и базу с боевыми ПД на площадку в РК. Провайдер выбран владельцем — **ps.kz** (Алматы/Астана, управляемый PostgreSQL, PCI DSS), аккаунт заведён 18.09. Образ и compose к площадке не привязаны (переезжают как есть, шаг 0 сделан 17.09).
**Шаги:** развернуть сервер и управляемую базу на ps.kz → перенести данные → `PII_STORAGE=real` только на этой базе → перевести `app.`/`api.` и webhook Channex на неё → проверить сторож и откат уже на этой машине.
**Критерий готовности:** `cli-check-env` печатает предупреждение «боевые ПД» только на базе в РК; на остальных `PII_STORAGE` пуст; webhook Channex отвечает 200 с нового адреса; сторож поднимает API/туннель после сбоя на новой машине; отчёт о переезде в `reports/`.
**Файлы:** `docs/ops/server-kz-setup-2026-09-18.md`, `docs/ops/server-setup-2026-09-18.md`, `plans/server-kz-2026-09-17.md`, Q-070а, Q-073, Q-112.
**Кто:** агент готовит команды и compose; развёртывание, оплату ps.kz и ключи — владелец (SSH из облака нет). Открытый под-пункт — **кто платит** (Q-070а).

### A2. Один живой день объекта в новой системе (Gate 8)
**Что:** смена ведёт **полный рабочий день целиком в PMS** — заезды, выезды, оплаты, переселения заводятся руками, параллельно хостел работает в Exely как обычно (Exely больше не источник, ADR-052, поэтому это не «двойной ввод», а живая смена).
**Критерий готовности:** к вечеру в PMS есть все события дня; ни одна бронь не потеряна; расхождения с кабинетами каналов разобраны поимённо; лист смены заполнен.
**Файлы:** `plans/live-day-2026-09-20.md`. Дата не назначена.
**Кто:** владелец + администраторы; агент готовит лист смены и сверочный отчёт.

### A3. Проверенный откат на реальном канале + ночной дежурный (Q-123)
**Что:** откат записан (`CUTOVER.md` → ROLLBACK), шаги 1 и 6 проверены на staging, но **ни по одному каналу не проверены живьём**. Сторож ночью есть (двойной: Mac + сервер, будильник Telegram).
**Критерий готовности:** откат одного канала (Hostelworld) проверен по шагам живьём и записан в таблицу ROLLBACK (кем, дата); назван **человек, который читает группу дежурных ночью**.
**Файлы:** `CUTOVER.md` (ROLLBACK, таблица по каналам), `plans/plan-2026-09-13-rollback-drill.md`, Q-123.
**Кто:** владелец (экстранет OTA и Exely — только он) + агент по сверке.

### A4. Channex — живая проверка сертификации
**Что:** анкета отправлена; осталась живая проверка — созвон с показом экрана **или присланная запись видео** (Channex принимает оба, срока нет). Показывать надо действия именно через PMS: изменение цены/остатков/ограничений и приём брони.
**Критерий готовности:** Channex подтвердил прохождение и открыл боевой (production) доступ.
**Файлы:** `reports/channex-certification-form-*.md`, страница-результатов с task_id (этот чат).
**Кто:** владелец (запись/созвон); агент помогает прогнать сценарии на видео.

### A5. Переключение каналов по одному (Gate 9–10)
**Что:** каналы переключаются строго по одному, следующий — только после reconciliation прежнего в ноль. Порядок: **Hostelworld → Ostrovok → Expedia → Agoda → Trip.com → Booking.com (последним)**; OneTwoTrip и Bronevik — адаптеров в Channex нет (решение владельца, Q-096).
**Важно:** 157 будущих броней (Booking/Trip/Expedia) Channex подтянет сам; **25 броней (Agoda 19, Hostelworld 2, Ostrovok 4) переносятся из нашей БД вручную** и сверяются с кабинетом канала. У перенесённых броней не просить оплату повторно (96,5% «не оплачено», но площадка уже взяла — Q-086).
**Критерий готовности на канал:** чеклист канала из `CUTOVER.md` закрыт целиком, `npm run cutover:channel -- <канал>` даёт расхождение 0, тестовое событие получено, мониторинг включён.
**Файлы:** `CUTOVER.md` (migration matrix, порядок, чеклист, маппинг 5 категорий/тарифов).
**Кто:** владелец (экстранеты) + агент (отчёты, маппинг, сверка).

> **Проверка маппинга перед первым каналом:** в `GET /channels/channex/mapping` на каждую категорию ровно одна пара, тариф `exely-10158310` («для ОТА +35%»). Ошибка тарифа = цены в OTA уедут на 35%. На боевой базе объект настраивается `POST /channels/channex/setup` **без параметра**.

## ПРИОРИТЕТ B — дефекты приёма ревизий каналов (до боевых каналов)

Перенесены из PR #9 (`reports/inbound-review-2026-09-15.md`). На боевой это правила приёма входящих броней — их надо закрыть до подключения каналов с потоком.

- **Q-158** — ревизия по заселённому/выехавшему проживанию: приём не проверяет статус, отмена снимает койку под живущим гостем, модификация возвращает заселённого в «ждём». Предложение: не применять, ставить `FAILED` и будить дежурного. *(Смягчено для первого канала: Hostelworld заселённых в момент переключения не имеет.)*
- **Q-159** — порядок ревизий: нет сравнения версий, «Обработать заново» на старой ревизии откатывает бронь. Нужно поле «время последней применённой ревизии» — **правка `DATA_MODEL.md` до кода**.
- **Q-160** — отмена брони, которой нет в PMS: подтверждается каналу и исчезает, сторож видит только `FAILED`. Предложение: инцидент класса Б, не подтверждать до разбора.
- **Q-161** — дефекты модификации из канала: (а) смена типа комнаты не переносит гостя; (б) комнаты сопоставляются по порядку, а не по составу; (в) суммы без сверки валюты; (г) уменьшение состава оставляет предоплату минусом. Что правило, что дефект — вопрос владельцу; (б)(в)(г) чинятся одним срезом.

**Критерий готовности блока:** по каждому вопросу — решение владельца в `QUESTIONS.md`, затем срез с red→green тестом; приём входящих не ломает заселённые брони и не подтверждает вслепую.

- **Q-162…Q-165** — дефекты повторного импорта Exely. **Актуальны только при реимпорте дампа**, а Exely больше не источник (ADR-052). Рекомендация: пометить «неактуально до реимпорта» и не тратить срез сейчас; решение — владельца.

## ПРИОРИТЕТ C — SaaS-трек (после первой живой смены, порядок ADR-046/Q-139)

Владелец: «SaaS-сервис, партнёры/компании, у каждого свои этапы регистрации, логин/пароль, вход, мы видим статус оплат». Шаг 1 (вход, роли, автор в журнале) — сделан. Шаги 2–4 — после первой смены.

- **C1. Мультитенантность до конца (Q-152).** Сейчас регистрация пускает в общий/демо-объект; изоляция организаций не завершена (ADR-061 «объект принадлежит организации» принят, но ADR-056 «одна установка — одна гостиница»). **Критерий:** данные одной организации не видны другой; тест изоляции.
- **C2. Онбординг доделать.** Есть план и частичный код (`/onboarding`, `packages/domain/src/onboarding`, `apps/api/src/hotel/onboarding.ts`): отель → номера → цены одной транзакцией. **Критерий:** новичок из пустого кабинета за один экран доходит до «можно поселить гостя» (категория+места+тариф+цены на горизонт); e2e.
- **C3. Подписки, пробный период, биллинг, статус оплат — НЕ построено.** В коде модулей подписок/биллинга нет. Нужны: организации-арендаторы, пробный период (после 7 дней — только чтение, ADR-046), тарифные планы подписки, приём оплаты, экран «статус оплат» для владельца платформы. **Требует модели платформы v2 в `DATA_MODEL.md` (ADR-019 отложен) — сначала модель, потом код.** **Критерий:** организация регистрируется сама, живёт в пробном периоде, платит, статус оплаты виден владельцу; тесты.
- **C4. Q-153** — продлевается ли смена по паролю (сессии). Решение владельца → срез.
- **C5. Q-157 / Q-129** — сайт обещает «Заявку», продукт строит регистрацию. Свести: куда ведёт «Попробовать бесплатно», нужен ли раздел «О компании» (название/город/контакты). Решение владельца.

## Границы (что агент НЕ решает и НЕ трогает)

- Exely production, OTA production, Channex production — не менять.
- Ключи только в `.env` руками; агенту закрыто чтение `.env` и реальных выгрузок; ключ не диктуется в чат.
