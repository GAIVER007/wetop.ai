# ТЗ — Главная WETOP: рабочий экран, а не отчёт (27.09.2026)

> **Статус: УТВЕРЖДЕНО владельцем 27.09.2026** («ТЗ на Главную утверждаю»), ADR-101; архитектура v3
> утверждена и заморожена тем же днём (ADR-100). Источник — два текста владельца от 27.09: целевая
> модель Главной (три уровня контекста) и разбор реальных экранов текущей Главной. Здесь они сведены
> в одно ТЗ. Этап А идёт первым и разбит владельцем на четыре PR — §12.1; после PR A1 — стоп и
> dark/light скриншоты на реальных данных Luxx, следующий PR только после визуального подтверждения
> владельца. Дизайн-система не меняется: это перестановка иерархии, не редизайн (§11).

## 1. Роль экрана

Главная отвечает на три вопроса:

1. **Что происходит прямо сейчас?**
2. **Что требует моего внимания?**
3. **Что я могу сделать отсюда одним действием?**

Главная НЕ заменяет аналитику, финансы, шахматку, брони и каналы — она показывает их главные сигналы
и даёт быстрый переход к действию.

Принцип UX: `увидел → понял → сделал`, а не
`увидел цифру → пошёл искать раздел → открыл таблицу → нашёл бронь → сделал действие`.

## 2. Один маршрут — три уровня

Маршрут один: `/today`. Содержимое зависит от выбранного рабочего контекста
(`ARCHITECTURE.md` §6: scope `ORGANIZATION | BUSINESS | LOCATION`):

| Scope | Что это | Пример заголовка |
|---|---|---|
| ORGANIZATION | главная всей компании; только показатели, которые корректно сравнивать между вертикалями | «Yuri Group · Все бизнесы» |
| BUSINESS | показатели сети одного бизнеса и его вертикали | «Luxx Hotels · Все филиалы» |
| LOCATION | операционный рабочий экран филиала — настоящее «Сегодня» администратора | «Luxx Aparts · Алматы» |

Shell один, бизнес-наполнение своё у каждой вертикали (§9 — Hospitality, §10 — Beauty).

## 3. Постоянная верхняя панель

```
WETOP
Yuri Group → Luxx Hotels → Luxx Aparts Almaty ▼
Сегодня · 27 сентября                      [ + Создать ]
```

Переключатель контекста: «Вся компания» → бизнесы → «Все филиалы» / конкретный филиал. Для
организации с одним бизнесом и одним филиалом переключатель визуально упрощается (сегодняшний
случай Luxx: заголовок без дерева). Кнопка `+ Создать` может открывать command menu: новая бронь,
новый гость, оплата, блокировка, неисправность.

Верхнюю часть уплотнить (сейчас: заголовок, attention-карточка, две кнопки, время, линия, фильтр):

```
Luxx Aparts / Алматы
Главная                                   16:48
Сегодня, 27 сентября       [Шахматка] [+ Новая бронь]
[Проживают] [Заезды] [Выезды] [Свободно] [Загрузка] [Долг]
```

## 4. Location · Hospitality — порядок блоков

Итоговая структура (закреплена владельцем по разбору скринов):

```
1. Header: объект / филиал · Сегодня · [Шахматка] [+ Новая бронь]
2. Операционный KPI strip: Проживают · Заезды · Выезды · Свободно · Загрузка · К оплате
3. Требует внимания  +  Быстрые действия (рядом, двумя колонками)
4. Ближайшие события: Заезды / Выезды (лента по времени)
5. Состояние объекта  +  Уборка / Неисправности
6. Деньги сегодня
7. Короткие показатели: ADR · RevPAR · Источники
8. Ссылки: → Аналитика · → Финансы · → Шахматка
```

Desktop-сетка:

```
┌─────────────────────────────────────────────────────┐
│ Luxx Hotels / Almaty             Сегодня   + Создать│
├─────────────────────────────────────────────────────┤
│ KPI │ KPI │ KPI │ KPI │ KPI │ KPI                   │
├───────────────────────────────┬─────────────────────┤
│ Требует внимания              │ Быстрые действия    │
├───────────────────────────────┴─────────────────────┤
│ Заезды │ Выезды │ Проживают                         │
├───────────────────────────────┬─────────────────────┤
│ Номерной фонд                 │ Уборка              │
├───────────────────────────────┼─────────────────────┤
│ Деньги сегодня                │ Каналы / системы    │
└───────────────────────────────┴─────────────────────┘
```

Правила по блокам:

- **KPI strip** — максимум 5–6 карточек, не 15. Нажатие открывает фильтр: «Заезды 31» →
  `/reservations` с фильтром «заезд сегодня»; «К оплате» → финансы / неоплаченные.
- **Ближайшие события** — лента по времени с действием в строке: `14:00 · Иван Петров · Booking.com ·
  Deluxe 203 · Оплачено · [Заселить]`; проблемная строка называет проблему: «Номер не назначен»,
  «Долг 80 000 ₸ · [Назначить номер]». Стандартный check-in — без открытия карточки брони.
  (Гости в примерах вымышленные — ADR-010.)
- **Быстрые действия** — существующий блок (`today/dashboard-widgets.tsx`: Заселить гостя, Выселить
  гостя, Продлить проживание, Переселить, Создать счёт) сохранить почти как есть, поднять к attention;
  дополнить со временем: новая бронь, принять оплату, заблокировать номер, добавить неисправность.
- **Номерной фонд** — не шахматка, компактное состояние: занято / свободно / на уборке / не готово /
  заблокировано + «2 номера нужно подготовить до ближайшего заезда» + [Открыть шахматку].
- **Уборка** — компактно: готово / нужно убрать / убираются / нужна проверка + [Открыть уборку].
  Позже — отдельный полноценный Hospitality-модуль.
- **Деньги сегодня** — только оперативные: начислено / оплачено / к оплате / возвраты + [Финансы].
  Владельцу дополнительно «vs вчера» и «vs тот же день прошлой недели», но без BI-дашборда.
- **Источники** — компактный сигнал долей броней сегодня (Прямые 38% / Booking 31% / …), без большого
  графика; полная карточка — в аналитике.
- **Системы** — маленький блок статусов (Channex · Сайт · WhatsApp AI · Backup); всё нормально —
  блок максимально компактный; проблема — она и так в «Требует внимания».
- **Короткие показатели** — Загрузка / ADR / RevPAR одной компактной карточкой с
  [Подробнее в аналитике], ниже операционки: администратору стойки они прямо сейчас не нужны.

## 5. «Требует внимания» — главный блок

Не статистика, а **очередь реальных проблем и действий**, отсортированная по важности
(Critical → Warning → Info), у каждой строки — кнопка действия:

```
ТРЕБУЕТ ВНИМАНИЯ                         8
🔴 2 гостя приезжают в течение часа, но номер ещё не готов   [Открыть]
🔴 1 бронь без назначенного номера                            [Назначить]
🟠 4 проживания имеют задолженность 380 000 ₸                 [Посмотреть]
🟠 2 номера требуют уборки                                    [Открыть уборку]
🟡 Channex не синхронизировался 12 минут                      [Проверить]
🟡 1 новая неисправность                                      [Посмотреть]
```

Блок ровно один: сейчас он дублируется (малая сводка сверху `AttentionSummary` + полный
`DayAttention` внизу) — оставить один главный, сразу после KPI strip. Когда проблем нет:
«✓ Всё в порядке. Нет просроченных заездов, долгов и незавершённых операций.»

События Hospitality и приоритеты:

| Событие | Приоритет |
|---|---|
| Риск овербукинга | Critical |
| Заезд скоро, номер не готов | Critical |
| Бронь без назначенного номера/койки | Critical |
| Ошибка каналов | Critical/Warning |
| Просроченная оплата | Warning |
| Заезд сегодня без оплаты | Warning |
| Номер требует уборки | Warning |
| Неисправность (§12 DATA_MODEL) | Warning |
| Check-out просрочен | Warning |
| OTA/webhook stale | Warning |
| Новый no-show | Info/Warning |

**Главное правило: если пользователь не может ничего сделать с уведомлением — ему не место в
Attention.** Источники сигналов существующие: день стойки, свежесть каналов (`/system/freshness`),
`system_incidents`; конкретные пороги («в течение часа», «12 минут») — в плане этапа, по уже
принятым порогам сторожа, новых бизнес-правил не выдумывать (AGENTS.md §4).

## 6. Периоды уходят с Главной

Сейчас `/today` предлагает вчера / 7 дней / месяц / прошлый месяц / произвольный диапазон
(`period-bar.tsx`) — это аналитический дашборд, а не «Сегодня». Решение владельца:

- на Главной остаётся максимум **один день**: сегодня / завтра / другая дата (`?date=` уже есть) —
  не диапазон;
- периоды и сравнение отрезков переезжают в раздел аналитики целиком.

Это частично пересматривает ADR-047 (ADR-101): маршрут, определения показателей и данные ADR-047
остаются в силе — меняется место, где они показываются.

## 7. Что уносим с Location-Главной (в какой модуль)

| Блок сейчас (`apps/web/src/app/today/`) | Куда |
|---|---|
| Выбор периода `period-bar.tsx` | аналитика (весь диапазонный режим) |

| Загрузка по категориям / по дням `daily-bars.tsx`, `OccupancyChart` | аналитика; на Главной — компактная «Занятость»: `Одноместные 8/12 · Мужские койки 31/36 … [Шахматка]` |
| Таблица «По категориям» `CategoriesPanel` (ночей продано, выручка, средняя ночь) | аналитика целиком |
| «Источники броней» `SourcesPanel` (полная карточка) | продажи / аналитика; на Главной — компактный сигнал §4 |
| «Оплаты по способам» `PaymentsPanel` | финансы → платежи → по способам; на Главной — общая строка «Получено сегодня 980 000 ₸» |

Точное место в разделах аналитики и финансов — планом этапа А (существующие экраны «Статистика» и

Не показывать на Location-Главной: большие BI-графики, аналитику сайта, полный журнал действий,
webhook/outbox-логи, длинные OTA-отчёты, полный P&L, десятки KPI — для этого есть модули.

## 8. Что оставить из текущей Главной

Хорошая база, полной замены не требует: маршрут `/today`, карточки KPI, паттерн attention,
заезды/выезды, долги, состояние номеров, «Первые шаги» (ADR-098), быстрые действия. Сохраняются
`data-testid` полосы стойки (`c-inhouse`, `c-arrivals`, `c-departures`, `c-tocheckin`, `c-tocheckout`,
`c-free`, `c-debt`) — их читает `cli-system-trace.ts` (ADR-047, последствия).

## 9. Business scope

Пример: «Luxx Hotels · Все филиалы» — дашборд управляющего сетью, не стойка.

```
ВЫРУЧКА 18.4 млн ₸ · РАСХОДЫ 11.2 млн ₸ · ПРИБЫЛЬ 7.2 млн ₸ · ЗАГРУЗКА 81% · ADR 24 500 ₸ · REVPAR 19 845 ₸

ФИЛИАЛЫ            Загрузка   Выручка   Долг    Статус
Алматы               88%       8.2m     180k      ●
Астана               79%       6.1m     240k      ●
Дубай                72%       4.1m      90k      ⚠
```

Клик по филиалу переключает scope на эту Location. Attention агрегированный — владелец сети не видит
каждую неубранную комнату: «Dubai · Channel sync stale», «Astana · долг вырос на 28%», «Almaty ·
3 критические неисправности».

**Зависимость:** «Расходы» и «Прибыль» появятся только с управленческими финансами
(`ARCHITECTURE.md` §11, после Q-197); до них Business-дашборд показывает выручку, загрузку, ADR,
RevPAR и долги — числа, которые уже считаются. Ничего не выдумывать.

## 10. Organization scope и Beauty

**Organization** («Yuri Group · Все бизнесы») — только универсальные показатели: выручка, расходы,
прибыль, cash flow, клиенты, сотрудники; ниже — карточки бизнесов (Revenue / Expenses / Profit).
Occupancy, ADR, RevPAR, master utilization, no-show rate здесь НЕ показываются: KPI вертикалей не
смешиваются (`ARCHITECTURE.md` §10).

**Beauty Location** (фаза 3, `ARCHITECTURE.md` §9): тот же shell `/today`, наполнение своё — записи
сегодня, свободные окна, работает мастеров, no-show, выручка, к оплате; attention: клиенты
опаздывают, свободные окна, мастер отменил смену, неоплаченные записи; лента «Ближайшие записи»
с [Начать / Открыть].

## 11. Что сохраняем визуально

Редизайна с нуля нет. Сохраняются: тёмная тема, тонкие borders, синий акцент, спокойные карточки,
крупные цифры, типографика, скругления, отсутствие шума. Меняются **иерархия информации и
плотность, а не стиль**. Все блоки — из готовых компонентов `/design-system`; новый компонент —
только после строки в DESIGN.md §8 (ADR-048); правила блоков Главной в реестре DESIGN.md §8
(строки «Блок задач смены», «Полоса „На стойке“», «Первые шаги») обновляются вместе с перестановкой.

### 12.1. Разбивка этапа А на PR (решение владельца 27.09.2026, ADR-101)

| PR | Состав | Правила |
|---|---|---|
| **A1 — иерархия экрана без новой бизнес-логики** | убрать диапазонный period bar с Главной; поднять «На стойке» наверх; новый KPI strip; один Attention; поднять быстрые действия; уплотнить header; убрать/переставить существующие аналитические панели | API и расчёты не менять. | **A3 — Attention v2** | единая очередь; Critical / Warning / Info; каждое событие с действием | существующие пороги сторожа и `system_incidents`; новых бизнес-правил не создавать |

Сквозные правила всех PR: при переносе существующих аналитических блоков функциональность не удалять —
либо она уже доступна в аналитике/финансах, либо PR явно показывает, куда перенесена; дизайн-систему по
стилю не менять — только иерархия, плотность и композиция.

## 13. Критерий качества

Администратор открывает WETOP утром и без перехода по пяти разделам понимает: кто приезжает, кто
уезжает, какие номера готовы, где проблемы, кто должен денег, что сделать прямо сейчас. Управляющий
видит, как работает объект и где финансовая или операционная проблема. Владелец сети выбирает
Business и видит, какой филиал работает хорошо, а какой требует внимания. Владелец группы выбирает
Organization и видит, сколько компания зарабатывает, тратит и где прибыль.
