## 1. Что есть сейчас (проверено по `main`)

| | «Специалисты» `/employees` | «Сотрудники» `/team` |
|---|---|---|
| Данные | `employees` (бизнес): имя, телефон, назначение `personnel_kind`, филиалы, услуги, график, зарплата | `users` + `memberships` + `membership_scopes` + `invites` (организация): почта, роль, область, приостановка |
| Ответ API | `BeautyEmployeeRow`, у ресторана свой, **признака входа нет** | `AuthMember`, **ссылки на карточку нет** |
| Право | `desk` (администратор видит) | `staff` (только владелец и управляющий) |
| Меню салона | Персонал → Специалисты | Персонал → Сотрудники |
| Меню ресторана | Персонал → Сотрудники | Персонал → Доступ и роли |
| Гостиница | пункта нет | Персонал → Сотрудники; карточки сотрудников гостиницы заводятся отсюда же |

Что уже сделано для связи двух половин:

- общий компонент `StaffBoard` (решение 20.10, вариант A): обе страницы уже выглядят одинаково;
- «Доступ в WETOP» в форме нового сотрудника (решение 20.10, четыре уровня): приглашение уходит с `invites.employee_id`,
  при принятии `employees.user_id` заполняется сам (`accounts.prisma-repository.ts`, журнал `employee.account_linked`);
- в карточке сотрудника есть ручная привязка и отвязка входа (`PUT`/`DELETE /employees/:id/account`, `account-options`);
- у гостиницы список уже отдаёт `hasLogin` (`hotel-staff.service.ts`).

**Чего не хватает:** ни один список не показывает пару «карточка ↔ вход», поэтому человек виден дважды на двух
экранах, а мастер без входа и бухгалтер без карточки неотличимы от «забыли настроить».

## 2. Цель

Один пункт меню «Персонал → Сотрудники» во всех трёх направлениях. Одна строка на человека. Строка собирается из двух
необязательных частей, сведённых по `employees.user_id = memberships.user_id`:

- **карточка** (работает: услуги, смены, записи или заказы, зарплата);
- **вход** (роль, филиалы, приглашение, приостановка).

Виды строк: «карточка и вход», «только карточка» (без входа), «только вход» (например, бухгалтер), «приглашён, ждёт»
(приглашение с `employee_id` или без).

Колонки (StaffBoard, без плиток сводки, решение 20.10): имя и должность, назначение, **доступ в WETOP** (без входа,
личный кабинет, администратор, управляющий, ждёт приглашения, приостановлен), филиалы, смена или нагрузка сегодня,
«Принёс», действия. Вкладки: все, специалисты, другие сотрудники, с доступом, ждут приглашения, не назначено.
Число людей на вкладках, как сейчас.

Действия в строке (только у того, кто может выдавать доступ):

- нет входа → «Дать доступ» (существующее приглашение с `employee_id`);
- нет карточки → «Завести карточку» (В3);
- есть вход → роль, филиалы, приостановить (существующие действия `/team`);
- «Открыть» → `/employees/<id>/profile` (решение 20.10, страница, не диалог).

`/team/roles` («Должности») остаётся вкладкой этого экрана.

## 3. Чего не трогаем

Модель данных, миграции, права ролей, денежные расчёты, правила приглашения и привязки. Таблицы не сливаются. Новые
поля только в ответах API и только дописываются (additive), прежние клиенты их не замечают.

## 4. Срезы

**U1. Пары в API (без экрана).** В ответы списков сотрудников салона и ресторана добавить `userId` (или `hasLogin`
по образцу гостиницы); в `AuthMember` добавить `employeeId` карточки в текущем бизнесе (или `null`). Чистая функция
домена `pairPeople(employees, members, invites)` собирает строки и решает вид строки. Red → green: unit на функцию
(четыре вида строк, приглашение с карточкой и без, приостановленный, сотрудник в архиве), API-тесты на новые поля,
проверка, что `staff`-поля не утекают администратору (В2).

**U2. Экран.** `/team` рисует собранный список через `StaffBoard`; `/employees` переадресует на `/team` с вкладкой
«Специалисты» (старые ссылки и закладки живы). Карточка, график и зарплата не меняются. Red → green: UI-спек на три
направления, axe в двух темах, 1440 и 390 px.

**U3. Меню и хвосты.** Один пункт в «Персонале» (`navigation.ts`, `vertical-copy.ts`), тесты меню всех направлений,
тур, подсказки чек-листа салона (`word: 'specialists'`), хлебные крошки, `/beauty/masters`. Набор `route-access`.

**U4 (по ответу на В5). «Связать»** для пар, которые сейчас не связаны, хотя это один человек: подсказка по совпадению
почты, связывает только руководитель кнопкой через существующий `PUT /employees/:id/account`. Автоматически не связываем.

Порядок: U1 → U2 → U3 одним PR или тремя, U4 отдельно. Выкладка обычная (ADR-152), миграций нет.
