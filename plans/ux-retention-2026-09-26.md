## 0. Что важно знать до чтения

1. **Цифры из статьи (−23 % на экране настройки, +31 % после упрощения) в ТЗ не переносятся.** Это чужая маркетинговая
   статья без методики. У нас один живой объект и единицы пробных организаций — статистически значимого A/B не получить.
   Берём механизмы (лишние параметры, нет умолчаний, нет «что важно», нет ответа системы), а успех мерим своими
   воронками и разбором на 5 реальных администраторах (§8).
2. **Многое из документа у нас уже есть** — не переделывать заново (§2, столбец «Есть»). Мобильная версия проверяется
   в ~30 UI-наборах, есть `EmptyState`/`ErrorState`/`Skeleton`, окно подтверждения, уведомления, ⌘K, шестишаговый
   мастер ИИ-продавца с умолчаниями и словом состояния у каждого шага.
3. **Главная дыра не в отдельном экране, а в трёх сквозных вещах:** (а) интерфейс обещает то, чего нет («всё меняется
   в настройках» — а настройки только для чтения); (б) после «Запустить отель» человек оставлен без ведущей нити;
   (в) **продукт ничего не знает о том, как им пользуются** — ни воронки, ни времени до первой брони, ни кнопки
   «сообщить о проблеме».
4. **Границы проекта не двигаем** (CLAUDE.md §3): не придумываем бизнес-правила брони/денег, не трогаем финансовую логику,
   миграции на рабочую базу — только владелец. Всё, что упирается в решение владельца, вынесено в §9 как «вопрос»,
   а не сделано молча.

## 1. Что из документа реально влияет на WETOP

| Тезис документа | Берём? | Почему |
|---|---|---|
| Время до первой пользы: кто выполнил первую задачу за ≤5 мин, удерживается вдвое чаще | **Да, главное** | Наш путь: регистрация → письмо → онбординг → 4 экрана до первой брони, минимум 8 вводов с клавиатуры (§3.1) |
| Экран настройки с лишними параметрами без умолчаний и без «что важно» | **Да** | `/rates` — 18 полей разом; форма брони — 17 элементов; «рекомендуется» в интерфейсе нет ни разу |
| Ошибки при регистрации → уход ×3 | **Да** | Тупик «письмо не ушло — обратитесь к владельцу» для самостоятельно зарегистрированного |
| Неясная информационная архитектура: подписи не по ментальной модели | **Да** | Один экран — три названия; ⌘K не находит «койки»; в интерфейсе Channex, webhook, архивный источник, CTA/CTD |
| Сломанные петли обратной связи: молчаливые действия, ошибки без объяснения | **Да** | Тосты вызываются в 3 файлах (9 мест); успех у ~20 действий карточки брони, счёта, ячейки, гостя не подтверждается; ошибки API показывают имена полей и форматы (`birthDate — YYYY-MM-DD`) — этап 5 |
| Постепенное раскрытие: сложное — за «Дополнительно» | **Да** | Спрятаны только справки и установочные коды; настройки — целиком |
| Мобильность | **Частично** | Уже проверяется; не хватает манифеста PWA и единого списка нижней навигации |
| Скорость: +1 с загрузки = +32 % отказов | **Да, но уже в работе** | `plans/section-loading-performance-2026-09-20.md`; не дублируем |
| Метрики UX: успех задач, время, частота ошибок, SUS, когорты | **Да, основа** | Сейчас нет ничего кроме `audit_logs` и `user_errors` |
| Обратная связь внутри приложения, опрос при оттоке | **Да** | Нет ни кнопки, ни опроса; есть чат ИИ-помощника, который можно использовать |
| Обнаружение функций, «что нового», пометки new | **Низкий приоритет** | Малая команда, функции появляются редко; после §3–§8 |
| Пути обновления, лимиты, апгрейд | **Заблокировано** | Тарифов и оплаты в продукте нет по решению владельца (Q-141, Q-143, Q-144) |
| Тепловые карты, запись сессий | **Нет** | Персональные данные гостей на экране; ADR-009/ADR-018, база в РК |
| A/B-тесты | **Нет (пока)** | Мало трафика; вместо них — воронка «до/после» и разбор на людях |
| «Не переделывать всё сразу; не отнимать у опытных нужные возможности» | **Да, как правило исполнения** | Срезы малые; расширенные поля прячем, не удаляем (для Luxx их администраторы используют ежедневно) |

## 6. Правила исполнения (из CLAUDE.md и AGENTS.md)

1. Перед любой задачей по интерфейсу — `DESIGN.md`; готовый компонент искать на `/design-system`; новый — только после
   строки в DESIGN.md §8 (ADR-048). Затрагивает 2.1 и 3.4.
2. **Красный до зелёного:** каждый срез начинается с теста, который падает на текущем коде. Прогоны — только через
   `npm run test:record -- <набор>`; до прогона — `npm run test:status`. Журнал и лог коммитятся вместе с правкой.
3. **Коммит только своих файлов явным списком;** перед коммитом сверка `git diff --cached --name-only`. В дереве
   параллельно работают другие сессии (в списке сессий сейчас есть занятая «WETOP обновление и развёртывание»).
4. Модель данных — сначала `DATA_MODEL.md`, потом код (3.1 при недостающих колонках, 7.3, 7.4). Миграции на рабочую базу
   применяет владелец. Выкладка на сервер агенту не разрешена.
5. Деньги и бронь: ничего из этого ТЗ не меняет финансовую логику или правила бронирования; пункты 3.1 (валюта/пояс
   только чтение) и 2.7 (без обещаний READ_ONLY) стоят на этой границе намеренно.
6. Сохранять `data-testid`, `role="alert"`, «закрыто» на экранах Channex-сертификации (`rates`, `channels`).
7. Каждый экранный срез: снимки 390/1440, светлая/тёмная тема, axe, клавиатура — как в `tests/ui/accessibility.spec.ts`.
8. Каждое решение владельца — ADR в `DECISIONS.md`; вопросы — в `QUESTIONS.md` под следующими свободными номерами
   после подтверждения (в этом файле — рабочие метки UQ-N, чтобы не занять номер, который параллельная сессия
   возьмёт раньше).

## 8. Чего НЕ делаем

- Не копируем цифры и «проверенные» приёмы статьи без своих данных.
- Не убираем ни одного поля, которым администраторы Luxx пользуются ежедневно — прячем за «Дополнительно».

- Не ставим сторонних трекеров, тепловых карт и записи сессий (ПД, РК).
- Не вводим подписку, оплату, автоблокировку по сроку и лимиты — решения владельца Q-141/Q-143/Q-144.
- Не переделываем весь интерфейс сразу: срезы малые, каждый со своим снимком «до/после».
- Не трогаем публичную главную (`apps/site`, ADR-070) — кроме UQ-9.
