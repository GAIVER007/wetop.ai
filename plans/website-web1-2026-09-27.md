# «Сайт и онлайн-бронирование»: аудит и срез WEB1

Дата: 27.09.2026. Поручение владельца от 27.09: сайт разложен по трём местам стойки — «Продажи → Аналитика сайта»,
«Настройки → Сайт» (`/analytics/setup`) и панель «Сайт и бронирования» в «Интеграциях». Собрать в один модуль
«Продажи → Сайт и онлайн-бронирование» с вкладками «Обзор | Бронирование | Аналитика | Настройки». Сначала аудит,
потом WEB1 (только раскладка и переадресация поверх существующей модели), после WEB1 — стоп и снимки.
WEB2 без отдельного «да» не начинается. Решение — ADR-117.

---

## 1. Аудит: ответы на вопросы владельца

| Вопрос | Ответ по коду и истории |
|---|---|
| Что такое `Site` в модели | Таблица `tracked_sites`, модель `TrackedSite` (DATA_MODEL §11, срез 8 от 12.09, ADR-025; поля бронирования — срез 9, ADR-026). Поля: `name`, `hosts[]`, `publicKey` (`pms_` + 12 hex, стоит в HTML сайта, не секрет), `status` ACTIVE/PAUSED, `bookingEnabled`, `bookingRatePlanId`. Одна запись — это одновременно счётчик, виджет бронирования и список разрешённых доменов |
| Кто создаёт «Сайт Luxx Aparts» | Не seed, не фикстура, не онбординг и не регистрация: ни одна миграция, сид или шаг онбординга `tracked_sites` не заполняет (проверено поиском по репозиторию — `trackedSite.create` есть только в `PrismaAnalyticsRepository.createSite` и в интеграционных тестах). Запись заведена руками 12.09.2026 вечером через форму `/analytics/setup` → `POST /analytics/sites` на рабочей базе (`docs/history.md`, срез 9; `docs/site/install-2026-09-12.md`). Ключ `pms_5724b8e298e4` уже вписан в готовый код для сайта (`docs/site/snippet-luxx-aparts.html`) |
| Откуда `luxx-aparts.example` | Форма требует хотя бы один домен (`parseHosts`: «нужен хотя бы один домен сайта»), а адреса настоящего сайта не было — Q-111 открыт до сих пор. Сессия 12.09 вписала заглушку `.example` (зарезервированный домен RFC 2606) и оставила владельцу шаг «замените заглушку на настоящий адрес» |
| Seed/demo или рабочая запись | Рабочая запись в боевой базе, с заглушкой вместо домена. Пока стоит заглушка, приёмник (`/a/hit`) и виджет (`/w/*`) отбрасывают всё, что приходит не с этого домена, — то есть не принимают ничего. Зелёный «Счётчик включён» на ней — неправда о состоянии, а не данные |
| Кому принадлежит Site | `tracked_sites.property_id` → `properties` → `organizations` (с 27.09 — RLS по организации, `tracked_sites` в списке таблиц с прямой колонкой, `web_sessions` / `web_pageviews` / `web_events` — через родителя). То есть сайт — объекта (Property), не организации целиком. После ARCHITECTURE v3 он окажется под Location через Property; модель менять не нужно |
| Допускается ли больше одного сайта | Модель — да (уникального ключа на `property_id` нет), API — да, прежний экран — да («Ещё один сайт», выбор сайта в отчёте). На боевой базе сайт один. Полноценный UX нескольких сайтов — WEB5 и только если он действительно нужен |
| Какие события собирает счётчик | Просмотр страницы (адрес, заголовок, реферер, ширина экрана, язык, пояс, случайные ID посетителя и сессии) и события `search` (даты заезда → календарь спроса), `booking_step`, `phone_click`, `whatsapp_click`, `custom`; `props` — только ключи из allow-list. IP и полный User-Agent не хранятся |
| Что значит `enabled` | `bookingEnabled` — виджет бронирования включён. Без тарифа не включается: API подставляет тариф сайта по умолчанию или отказывает |
| Что значит `paused` | `status = PAUSED` останавливает **и счётчик, и виджет**: `collect.service` отвечает `rejected:site paused`, `web-booking.service` — «бронирование с сайта выключено». Прежняя кнопка называлась «Поставить на паузу», а сообщение — «Счётчик на паузе: события не сохраняются»: про то, что перестают приниматься брони, не говорилось |
| Связь Site → Reservation | Виджет создаёт бронь через `ReservationsService.create` с источником `WEBSITE` (ADR-026, `CONFIRMED` без предоплаты). Сессия счётчика, в которой сделана бронь, получает `web_sessions.reservation_id` — отсюда «Брони с сайта» в отчёте и по источникам. Второй модели брони для сайта нет и не нужно |
| Как определяется source website | Только путём создания: бронь из `POST /w/book` → `source = WEBSITE`. Фильтра «источник = сайт» в списке броней пока нет (WEB4) |
| Где настройки виджета | В той же `tracked_sites`: `booking_enabled`, `booking_rate_plan_id`. Цвета, подписи, языки, промокоды в модели не хранятся: цвета сайт переопределяет своим CSS (`docs/site/install-2026-09-12.md`), языки — Q-116 |
| Где allowlist доменов | `tracked_sites.hosts`; сравнение — `hostMatches` (сам домен и поддомены, `www` снимается при записи). Им пользуются и приёмник счётчика, и виджет, и CORS виджета |
| Зачем отдельные `/analytics` и `/analytics/setup` | История срезов: срез 8 дал отчёт и страницу подключения счётчика, срез 9 дописал бронирование на страницу подключения; 21–22.09 страницу подключения переименовали в «Настройки сайта» и унесли в «Настройки», а отчёт остался в «Продажах». Панель в «Интеграциях» появилась при упрощении настроек и вела на ту же страницу |
| Что native WETOP, а что интеграция | Счётчик (`/a/pms.js`, `/a/hit`), виджет (`/w/widget.js`, `/w/availability`, `/w/book`) и отчёт — свои, WETOP. Внешний сервис здесь только Channex, и он к сайту отношения не имеет. Значит, в «Интеграциях» сайту не место |

Что ещё нашлось по дороге:

- Учебный сайт подставного API (`scripts/preview/fixture-api.ts`) тоже на заглушке — `example.invalid`.
- `ai-seller` берёт у страницы подключения кнопку «Скопировать код» и ссылается на `/analytics/setup`.
- ADR-105 переносит аналитику за период с Главной «в аналитику»: адрес `/analytics` может понадобиться общей
  аналитике. Поэтому переадресация со старых адресов — временная (307), а не постоянная (308): браузеры запоминают
  308 навсегда.

## 2. WEB1: что делаем

Только раскладка экранов и переадресация. Схема, миграции, API и логика домена — без изменений.

1. **Один пункт меню.** «Продажи»: Тарифы → Менеджер каналов → Синхронизация каналов → **Сайт и онлайн-бронирование**
   → ИИ-продавец. «Аналитика сайта» из «Продаж» и «Сайт» из «Настроек» убраны. Переименование каналов из списка
   владельца («Каналы продаж») в WEB1 не входит.
2. **Маршруты.** `/website` (Обзор), `/website/booking`, `/website/analytics`, `/website/settings`; вкладки —
   `nav.settings-tabs`, как у «ИИ-продавца» и «Настроек гостиницы». Новых компонентов нет.
3. **Переадресация** в `next.config.ts`, 307, адрес с параметрами сохраняется:
   `/analytics` → `/website/analytics`, `/analytics/setup` → `/website/settings`.
4. **«Интеграции»** — без панели «Сайт и бронирования»; подпись пункта меню без «счётчика и модуля бронирования».
5. **Заглушка домена не выглядит подключённым сайтом.** Домен из зарезервированных для примеров (`.example`, `.invalid`,
   `example.com/net/org`) — это «адрес не указан». `.test` и `.localhost` — адреса локального стенда: с них запросы
   доходят, сквозные тесты заводят сайт на `test-site.localhost`. Обзор без настоящего домена — пустое состояние
   «Сайт ещё не подключён» с кнопкой «Подключить сайт»; на Luxx-заготовку — одна строка, что ключ сохранится.
   Запись в базе не трогаем: её ключ уже в готовом коде для сайта, а удаление — действие владельца.
6. **Обзор** (сайт с настоящим доменом): `StateBar` — состояние, домен, «Открыть сайт ↗»; четыре факта: Домен,
   Счётчик, Онлайн-бронирование, Брони с сайта за этот месяц (то же число, что плитка «Брони с сайта» в отчёте).
   Состояние счётчика — из того, что API уже отдаёт: приостановлен / ждём первое посещение (событий не было) /
   работает (события сегодня) / сегодня событий нет (с датой последнего). Полная машина состояний — WEB2.
7. **Бронирование** — прежний блок «Бронирование с сайта»: состояние словами, что делает виджет, домен, объект,
   валюта, тариф; включение и тариф — прежняя форма; код виджета и демо — под раскрывашкой.
8. **Аналитика** — прежний отчёт без кнопки «Подключение счётчика» (её заменили вкладки); ссылки из пустых таблиц
   ведут в «Настройки».
9. **Настройки** — прежняя карточка сайта без блока бронирования: домены (textarea остаётся до WEB2) с понятной
   строкой вместо «приёмник не примет запрос», счётчик и «Проверить счётчик», код под раскрывашкой, демо-страница
   внутри неё. «Поставить на паузу» и «Удалить» — в «Опасную зону» внизу, оба с подтверждением; пауза называется
   «Приостановить сайт» и прямо говорит, что перестанут приниматься и посещения, и брони (так работает API).
10. **Тексты**: тур по стойке, описание раздела «Продажи», ссылки из «ИИ-продавца».

## 3. Чего WEB1 не делает (следующие срезы, каждый — после «да» владельца)

| Срез | Содержание |
|---|---|
| WEB2 | Домены списком вместо textarea, машина состояний счётчика, окно установки (script / GTM / вручную), проверка установки |
| WEB3 | Виджет: предпросмотр, настройки только тех возможностей, что есть в модели |
| WEB4 | Воронка (посещение → поиск → начало брони → бронь), выручка с сайта, переход в «Брони» с отбором «сайт» |
| WEB5 | «Только чтение», телефон, несколько сайтов — если они действительно нужны |

Открытые вопросы, от которых WEB1 не зависит: Q-111 (адрес сайта Luxx), Q-114/Q-115/Q-116 (предоплата,
уведомление гостю, языки виджета). Раздельная пауза «только счётчик» / «только брони» потребует правки API —
решать в WEB2.

## 4. Проверки

- unit: `lib/website.ts` (заглушка домена, состояние сайта) — red → green; `actions.test.ts` — обновляет новые адреса;
  `navigation` — один пункт, старых нет.
- UI-набор стойки на подставном API: переадресация со старых адресов с параметрами, вкладки, пустое состояние на
  заглушке, «Интеграции» без сайта, доступность (axe) новых экранов в двух темах и двух ширинах.
- typecheck, lint.
- Снимки: `reports/website-web1-2026-09-27/` — обзор (заглушка и настоящий домен), бронирование, аналитика,
  настройки, меню; светлая и тёмная темы.
