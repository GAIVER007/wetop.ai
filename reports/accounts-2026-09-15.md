# Вход по логину и паролю — срез 13, шаг 1 (15.09.2026)

Основание: поручение владельца 15.09.2026 («мы же этот делаем под сас сервис… у каждого будет свои этапы
регистраций логин пароль вход в систему»), ответ на развилку — «шаг 1 сейчас». План
`plans/slice-13-accounts-saas.md`, модель `DATA_MODEL.md` §13, решение ADR-047 (принято в части шага 1),
Q-134 закрыт.

## 1. С чего начался разговор

Владелец нажал «Войти» на `wetop.ai` и не нашёл формы логина. Нашлось две причины, обе настоящие:

1. Кнопка вела на корень `app.wetop.ai`, а корень стойки редиректом уходит на `/today`. После того как
   Cloudflare Access пропускал человека, он проваливался сразу в рабочий день смены: экрана входа не видел,
   под какой почтой его пустили и как выйти — посмотреть было негде. Починено отдельным коммитом (PR #11).
2. **Формы «логин и пароль» в системе не было вообще.** Access своих паролей не хранит — он пускает по
   одноразовому коду на почту; форма на `/login` была заглушкой от фронтенда и честно говорила, что вход не
   подключён. Ни `User`, ни `Session` в модели не существовало, `audit_logs.user_id` всегда был `NULL`.

## 2. Что сделано

| Слой | Что появилось |
|---|---|
| Модель | `DATA_MODEL.md` §13: `User`, `Session`, `PasswordReset` утверждены; организации, планы и подписки остались предложением шагов 2–4 |
| База | миграция `20260915000013_accounts` + `down.sql`: три таблицы, два CHECK (почта в нижнем регистре и в виде почты; действующий сотрудник без пароля невозможен), внешний ключ `audit_logs.user_id → users` с `ON DELETE SET NULL` |
| Домен | `packages/domain/src/accounts`: хеш пароля (`scrypt`), проверка политики, решение о входе с запретом после промахов, срок сессии, токен и его хеш |
| API | модуль `auth`: `POST /auth/login`, `GET /auth/me`, `POST /auth/logout`, `POST /auth/password`; замок `SessionGuard` на непубличных маршрутах; `@Public()` на `/a/*`, `/w/*` и webhook Channex |
| Журнал | автор действия подставляется сам: контекст запроса (`AsyncLocalStorage`) + расширение клиента Prisma на `auditLog.create`. Ни один репозиторий не переписан |
| Стойка | рабочая форма входа, «Выйти» (отзывает сессию в базе, а не только чистит cookie), имя и роль вошедшего в меню профиля, токен в cookie `httpOnly`/`SameSite=Lax` |
| Владельцу | `npm run accounts -- list \| create \| password \| block \| unblock`; пароль только через `PMS_NEW_PASSWORD`, в аргументах не принимается |

Решения, которые стоит знать:

- **Cloudflare Access не снят.** Замка теперь два: Access снаружи (ADR-045) и свой вход внутри. Пока PMS
  живёт на Mac владельца, снимать периметр нельзя. Почта из заголовка Access подставляется в поле, но сама
  никуда не пускает.
- **Замок в API по умолчанию молчит** (`AUTH_REQUIRED` не задан). Иначе первый же выкат положил бы сторожа,
  импорт из Exely, скрипты сверки и сквозные тесты — они ходят в API без токена (ADR-023). Токен, если он
  пришёл, опознаётся и при выключенном замке: журналу нужен автор. Включение — отдельный шаг, см. §5.
- **Роль хранится, но ничего не запрещает:** ADR-023 в силе, администраторы равноправны. Права по ролям —
  Q-135, выдумывать их запрещено (AGENTS.md §4).
- Пароль не попадает ни в журнал, ни в ответы, ни в текст ошибок. Неверная почта и неверный пароль отвечают
  одинаково, и одинаково долго: для неизвестной почты проверка всё равно считается.

## 3а. Письма: приглашение и сброс пароля (вечер 15.09, решение владельца по Q-137)

Владелец выбрал сервис писем (Resend), и в тот же вечер сделано так, как он просил: сотрудник получает
письмо и **задаёт пароль себе сам** — владелец его не знает.

| Что | Как устроено |
|---|---|
| Приглашение | `npm run accounts -- invite --email=… --name='…' [--role=]` → учётная запись `INVITED` без пароля, письмо со одноразовой ссылкой |
| Сброс пароля | экран `/login/reset` («Забыли пароль?» на входе) → письмо с той же ссылкой |
| Ссылка | `/login/set-password?token=…`: пароль дважды, не короче 10 символов; ссылка живёт 24 часа, работает один раз, новая гасит прежние |
| После установки | учётная запись становится `ACTIVE`, все открытые сессии этого сотрудника гаснут, вход возвращает на `/login` с «Пароль сохранён» |
| Отправитель | `packages/integrations/src/mail` (ADR-004), внешнее API описано в `docs/mail/README.md` |
| Без ключа | система работает: приглашение печатает ссылку в консоль, `/login/reset` отвечает «отправка писем не настроена» |

Чего в письмах нет: пароля (только ссылка), данных гостей, сумм и номеров броней. Запрос сброса отвечает
одинаково для любой почты — по ответу нельзя узнать, кто есть в системе; на одну почту письмо уходит не
чаще раза в пять минут.

Доказано: unit по клиенту писем 7/7 (подставной `fetch`: адрес, заголовок, тело, ошибки без ключа и без
адреса получателя), домен ссылок и текстов 8/8, сервис приглашения и сброса 16/16, UI в браузере 7/7
(`tests/ui/password-reset.spec.ts`: ссылка → пароль → вход им; повторная ссылка, просроченная, разные пароли,
короткий пароль, ссылка без ключа). Весь UI-набор на этом коде — **88 из 92**, те же четыре падения на
доступности экранов настроек объекта, что и до правок. **Живой отправки письма не было ни одной** — нет ключа, и из среды
агента внешние сервисы закрыты. Перед первой отправкой сверьте поля запроса с resend.com/docs.

**Что нужно от владельца для писем:** аккаунт Resend, подтверждение домена `wetop.ai` записями SPF и DKIM
(DNS уже в Cloudflare), затем `RESEND_API_KEY` в `.env`; при желании `MAIL_FROM` и `PUBLIC_APP_URL`.

## 3б. Автор действия виден, служебные ходоки готовы к замку (ночь на 16.09)

**Кто сделал.** Автор писался с утра, но нигде не показывался: на экране журнала не было такого столбца.
Теперь `/audit` отдаёт имя вошедшего (только имя — почта сотрудника это ПД, экрану она не нужна), в таблице
появился столбец «Кто» со значением «система» для импорта, сторожа и скриптов, действия с учётными записями
переведены на русский и отбираются фильтром «сотрудники». Доказано: сервис 6/6 (красные до правки), UI в
браузере — столбец, «система» и отбор.

**Готовность к включению замка.** Включить `AUTH_REQUIRED=1` сходу нельзя: в API ходят не только люди.
Сделано `scripts/lib/service-api.ts` — служебный ключ и понятный разбор 401 вместо «HTTP 401»; через него
пошли 11 скриптов, включая задачу синхронизации с Exely и уборку после тестов. Стойка при
`APP_AUTH_REQUIRED=1` уводит человека на `/login`, получив 401, но никогда для `/auth/*` — иначе неверный
пароль молча возвращал бы на тот же экран. Unit: служебный клиент 8/8, клиент API стойки 14/14.

**Чего не хватает для включения:** 23 сквозных спека ходят по стойке вообще без входа — нужен вход в
фикстуре `tests/e2e`. Пока его нет, замок остаётся выключенным; порядок включения расписан в
`plans/slice-13-accounts-saas.md` §7а.

## 3в. Слияние с `main`: две модели одного среза (16.09, ночь)

Выбор я не делал — он за владельцем (**Q-141**). Обе работы сохранены:

## 4. Что владельцу сделать по шагам

```bash
# 1. миграции на dev-БД: 20260915000013_accounts (модель) и 20260915000014_password_login (пароль).
#    Откат у каждой свой down.sql в её папке
npx prisma migrate deploy --schema packages/database/prisma/schema.prisma

# 2. доказать, что база держит правила (красные до миграций, зелёные после)
npm run test:record -- integration tests/integration/accounts-schema.test.ts
npm run test:record -- integration tests/integration/password-login-columns.test.ts

# 3. завести себя. Пароль только так: в аргументах он остался бы в истории оболочки
PMS_NEW_PASSWORD='придумайте-длинный-пароль' npm run accounts -- \
  create --email=ваша@почта --name='Имя Фамилия'

# 3б. администраторов лучше приглашать: пароль они задают себе сами по ссылке из письма
npm run accounts -- invite --email=aigul@luxx.kz --name='Айгуль Сеитова'

# 4. перезапустить API и стойку, чтобы код входа поднялся
launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.api
npm run build -w apps/web && launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.web

# 5. открыть https://app.wetop.ai/login и войти
```

Остальным администраторам учётки заводятся той же командой с `--role=desk`. Пароль выдаётся лично: рассылок
в системе нет, это Q-137.
