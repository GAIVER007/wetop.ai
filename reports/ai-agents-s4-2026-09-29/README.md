# S4 — контекст обратившегося для WETOP Support (29.09.2026)

Решения владельца: Q-A2, Q-A6, план `plans/ai-agents-wetop-support-2026-09-29.md` §9. Новой модели `RequestActor`
нет: платформа читает то, что уже есть (членство, организация, Business, Location, таблица прав ролей, статус
организации по ADR-102). Модель данных и миграции не менялись.

## Как идёт запрос

```
человек пишет в чат → канал проверяет подпись → (userId, organizationId) в контексте посетителя
→ инструмент бота (аргументов «кто» нет) → GET /assistant/requester узким ключом помощника
→ API сверяет пару с членством, читает от имени этой организации
→ buildRequesterContext (домен) собирает ответ по белому списку → бот делает из него текст для модели
```

Модель не называет ни человека, ни организацию: лишний аргумент отвергает реестр инструментов (`неверные
аргументы`), платформа до вызова не доходит.

## Какие поля получает модель

| Инструмент | Что в тексте |
|---|---|
| `get_requester_context` | роль (владелец / управляющий / администратор), отметка «главный администратор платформы», название организации, бизнесы (название, вид, филиалы — до 5 и до 10, названия сплющены в строку и урезаны до 80 знаков), область «вся организация» |
| `get_account_status` | ACTIVE / TRIAL / READ_ONLY / SUSPENDED, можно ли менять данные, безопасная причина словами (`TRIAL_ENDED`, `READ_ONLY_BY_PLATFORM`, `SUSPENDED`), срок пробного периода |
| `get_permissions` | одно право «есть / нет» или короткая сводка «Есть … Нет …» по названиям прав; права не меняются и не выдаются |

## Что остаётся только у сервера

Почта, телефон, имя человека, пароль и хеш, сессия, куки, токены, документы и данные гостей, ключи и секреты,
внутренние id (человека, организации, бизнеса, филиала), псевдоним `requester.ref` (в ответе API он есть для
различения ходов, в текст модели не попадает), всё, что API добавит в ответ сверх контракта: текст собирается по
белому списку полей, лишнее ему взять неоткуда (тест `test_extra_server_fields_never_reach_the_model`).

Не вошло, потому что нечем подтвердить: `currentRoute` и `locale` — в подписи посетителя их нет, а незаверенное
значение от клиента контекстом не считаем; `displayName` человека — по Q-A6 «только если нужен», сейчас не нужен.

Дополнительно: заблокированный человек — «нет такого»; чтение идёт в контексте организации запроса
(`databaseTenant()` в тесте API), поэтому при включённой RLS база тоже не отдаст чужого; ключ обязателен
(401/403), кривые id — 400 без обращения к базе.

## Три сценария (настоящий вывод инструментов)

### 1. ACTIVE, владелец
- `get_requester_context` → Обратился: владелец. Организация: Гостиница А. Бизнесы: Luxx Hotels (гостиничный бизнес; филиалы: Алматы). Область: вся организация.
- `get_account_status` → Аккаунт организации: ACTIVE — активен: данные можно менять.
- `get_permissions{"permission": "settings"}` → Право «настройки гостиницы» (settings) у роли «владелец»: есть.

### 2. READ_ONLY, администратор
- `get_account_status` → Аккаунт организации: READ_ONLY — режим «только чтение»: данные видны, менять их нельзя. Причина: пробный период закончился. Срок пробного периода — до 20.09.2026.
- `get_permissions{"permission": "desk"}` → Право «работа с гостями» (desk) у роли «администратор»: есть.

Ответ модели по этому выводу: «Я проверил ваш аккаунт: организация в режиме „Только чтение“ — пробный период закончился, поэтому новую бронь создать нельзя. Смотреть данные можно. Могу передать вопрос по оплате команде WETOP».

### 3. Нет нужного права, администратор
- `get_account_status` → Аккаунт организации: ACTIVE — активен: данные можно менять.
- `get_permissions{"permission": "settings"}` → Право «настройки гостиницы» (settings) у роли «администратор»: нет. Права я не меняю: роли и права меняет владелец организации.

Ответ модели: «С системой всё в порядке. У вашей роли нет права на настройки гостиницы; это может сделать владелец организации».
