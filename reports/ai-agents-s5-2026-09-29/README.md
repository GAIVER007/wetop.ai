## Как идёт запрос

```
человек пишет в чат → канал проверяет подпись → (userId, organizationId) в контексте посетителя
→ инструмент бота (аргументов «кто/где» нет; у брони — только номер, который назвал человек)
→ GET /assistant/integrations | GET /assistant/reservation узким ключом помощника
→ API сверяет пару с членством (как S4), читает от имени организации (withSignedInUser → RLS)
→ buildIntegrationHealth / buildReservationDiagnostics (домен) собирают ответ по белому списку
→ бот делает из него текст словами (support_diagnostics_text.py) — тоже по белому списку
```

`CANCELLED`, `NO_SHOW`, `UNASSIGNED_ITEMS`, `ARRIVAL_PASSED_NOT_CHECKED_IN`, `DEPARTURE_PASSED_NOT_CHECKED_OUT`,
`UNIT_NOT_INSPECTED_BEFORE_ARRIVAL`. Пороги не новые: 30 мин — та же мера, что у «Свежести» (T6), сутки — окно ошибок.

## Что остаётся только у сервера

Имя, телефон, гражданство и документы гостя, заметки брони, суммы и оплаты (Q-S5-4), ключ и адреса Channex, адреса
получателей оповещений, внутренние id (брони, объекта, ячейки, категорий — в ответе только коды ячеек и названия
категорий), неисправности сторожа (Q-S5-3), чужие организации. Ответ API типизирован белым списком
(`ReservationCardLike` читает из карточки только перечисленные поля); текст бота — тоже по белому списку, лишние поля
сервера до модели не доходят (тесты `test_integration_extra_server_fields_never_reach_the_model`,
`test_reservation_status_text_has_facts_and_nothing_personal`).
