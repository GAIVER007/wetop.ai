## Как этим пользоваться

```bash
# публичный адрес на время разработки (в отдельном окне, рядом с API)
scripts/ops/channex-tunnel.sh
# состояние webhook: зарегистрирован ли, когда доставлял последний раз, не под подозрением ли
```

## Дефект сторожа туннеля, найденный ночью (19:14–19:23 UTC)

Первый же перезапуск после смерти быстрого туннеля не перерегистрировал webhook. Журнал сторожа:

```
19:14:44Z туннель умер — поднимаю новый
19:14:50Z туннель: Binary file …/pms-channex-tunnel/cloudflared.log matches
19:16:51Z регистрация не прошла: {"message":"callback_url должен начинаться с https:// …"}   (×6)
19:17:51Z не удалось поднять туннель, попробую через 30 с
19:18:51Z туннель умер — поднимаю новый                                                   (и так каждые ~4,5 мин)
```

Причина: общий журнал усекался, а убитый `cloudflared` дописывал свои последние строки по прежнему смещению,
файл получал дыру из NUL, `grep` без `-a` считал его бинарным и вместо адреса печатал «Binary file … matches».
Эта строка попадала в файл адреса и в запрос регистрации. Четыре часа webhook в Channex указывал на
несуществующий хост; брони страховал только опрос ленты раз в 5 минут. Сторож в API подозрения не поставил:
оно возникает лишь при брони, пришедшей опросом, а броней в это время не было.

Исправлено в `scripts/ops/channex-tunnel.sh`: журнал на каждый туннель (хранятся пять последних), `wait` после
`kill`, чтение журнала с `grep -a`, проверка формы адреса до записи и регистрации. Прогон исправленного сторожа:

```
19:21:24Z туннель: https://decide-kate-connected-became.trycloudflare.com
19:23:27Z webhook зарегистрирован: {"id":"4f759bc6-…","callbackUrl":"https://decide-kate-connected-became.trycloudflare.com/channels/channex/webhook","created":false,"eventMask":"booking","active":true}
19:23:28Z пробный вызов Channex → PMS 200
```

## Дыра закрыта 13.09.2026: сторож сам проверяет адрес

Сторож ставил подозрение только по косвенному признаку — бронь пришла опросом ленты, а webhook её не
доставил. Пока броней нет, мёртвый адрес не замечался вовсе: ровно так webhook четыре часа указывал на
несуществующий хост.

Теперь у подозрения два независимых признака. Второй: раз в пять минут сторож спрашивает у Channex
зарегистрированный адрес и стучится в него. Живым считается любой ответ сервера, даже 404 — webhook
принимает только POST, и 404 на GET означает, что запрос дошёл. Провал — это отказ сети: хост не
резолвится, соединение не встаёт, ответа нет за пять секунд. Если Channex сам недоступен, результат —
«не проверяли»: подозрение из чужого сбоя не выдумывается.

Снятие несимметрично, и это главное в правиле. Событие, дошедшее webhook'ом, снимает любое подозрение:
это прямое доказательство, что цепочка Channex → PMS работает. Ожившый адрес снимает только подозрение по
адресу — то, что хост отвечает, ещё не значит, что пропущенная бронь дошла.

Где: `apps/api/src/channels/schedule.ts` (чистое правило `assessWebhook`, признак `callbackReachable`,
вид подозрения `kind`), `webhook-health.service.ts` (проба, прореживание, поля в статусе
`callbackProbedUrl`, `callbackReachable`, `callbackCheckedAt`).

Доказательство: тесты red → green — шесть на правило в `schedule.test.ts`, пять на сторожа в
`webhook-health.test.ts`; до правки первые три и все пять падали. Полный модульный прогон 428 из 428.
Попутно тест контроллера поймал регрессию: поле снимка перекрывало настоящий адрес из Channex в ответе
`/channels/channex/webhook/status` — поле переименовано.

Проверка того же руками в ночь на 13.09: адрес `rugs-climbing-consulting-fruits.trycloudflare.com`
резолвится, GET на путь webhook отдаёт 404 за 0,5 с, процесс `cloudflared` жив, очередь исходящих пуста
(0 в ожидании, 0 ошибок, 858 отправлено), последнее событие webhook — 07:18 UTC.
