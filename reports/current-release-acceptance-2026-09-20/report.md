План: `plans/current-release-acceptance-2026-09-20.md`. Исходная актуальная версия:
`06729e90f7f430a08a8e6078894f7ce234d9a71a`. Это проверка кода и доступных
подключений, а не разрешение на production-cutover.

Во время приёмки в main появился `4363d96` с исправлением раскладки зависимостей
NestJS и собственной починкой Bash-сообщения ARI. Он включён в итоговую ветку;
дублирующая локальная правка ARI снята в пользу версии main.
Следом включён `da6f79f`: эквивалентная поправка Nest probe из main сохранена
целиком при разрешении конфликта. Собственные исправления стенда не потеряны.

- Локальная папка отставала от GitHub на 175 коммитов. Обновлена fast-forward.
- До обновления 94 изменённых/неотслеживаемых файла сохранены вне Git:

- Один Cloudflare Tunnel одновременно обслуживали старый Mac и Linux-сервер.
  Это позволяло одному домену попадать на разные версии приложения.
- После копирования plist отключены автозапуск и процессы четырёх старых служб
  Mac: `kz.luxx.pms.domain`, `kz.luxx.pms.exely-sync`, `kz.luxx.pms.web`,
  `kz.luxx.pms.api`. Серверные процессы не изменялись.
- Повторный `cloudflared tunnel info wetop`: один коннектор, `linux_amd64`,
  сервер `187.77.145.152`. Mac больше не обслуживает публичные домены.
  Возвращать старый Mac-туннель при работающем сервере нельзя.
- Публичная `/login` возвращает 302 в Cloudflare Access. Это проверяет периметр,
  но не вход за ним. Скрипт `/a/pms.js` отвечает 200; непубличный `/reservations`
  через API-домен — 404. Сводка без cookies/токенов: `public-routes.json`.

## Supabase: только чтение

Одна PostgreSQL-сессия, read-only transaction, затем rollback. По адресу из
локальной `.env`: 15 миграций применены, checksums совпадают, пропущенных нет.
Объект один, единиц размещения 88, бронь одна, гость один, импортированных
проживаний из Exely нет. Числа и время проверки: `database.json`.

В прежнем отчёте другой сессии были тысячи записей. Причина расхождения пока
не установлена: сначала надо сравнить конфигурацию серверного API и этой
папки. По этому наблюдению ничего не импортировалось и не удалялось.

## Channex: подключение staging

Существующим клиентом выполнены только GET properties и GET webhooks. Ключ
работает, доступен один объект; активен booking-webhook на
`https://api.wetop.ai/channels/channex/webhook` с секретным заголовком.
CHANNEX_PROPERTY_ID в локальном окружении не задан; сопоставления есть в БД.
Сводка без ключей, ID объектов и значений заголовков: `channex.json`.
Это подтверждает настройки staging, но не доставку и обработку нового события
сервером. Тестовый webhook, ARI и изменения каналов не отправлялись.

## Исправленные причины сбоев проверок

1. `local-db.sh` заполнял `pms_test` дважды: `test:schema`, затем второй
   `seed-local`. PostgreSQL отклонял пересекающиеся размещения (`23P01`).
   Второй засев удалён; PostgreSQL из явно выбранного PATH имеет приоритет.
   Новый регрессионный тест подставляет все внешние команды и не касается БД.
   RED: `11-49-34Z-unit-4a9c`; GREEN: `11-50-01Z-unit-fcff`.
   Затем новая локальная PostgreSQL успешно создана и засеяна всеми миграциями.
2. Изолированному e2e API не хватало SESSION_SECRET для accounts middleware.
   Задан отдельный тестовый секрет только для изолированного стенда, с возможностью
   переопределения E2E_SESSION_SECRET. Production-конфигурация не меняется.
   RED: `11-54-04Z-unit-f9d4`; GREEN: `11-54-27Z-unit-2ae8`.
3. В тесте аналитики pageview и search могли попадать в разные пакеты коллектора.
   До открытия серверного отчёта проверяется сохранение обоих событий в БД.
   Исходный сбой: `11-54-32Z-e2e-71c2`. Проверки интерфейса сохранены полностью.
4. Bash на macOS воспринимал символ рядом с `$v` как часть имени переменной
   в сообщении отказа остановки ARI. `${v}` устраняет аварийный выход.
   Два существующих отрицательных теста были красными в
   `11-59-15Z-unit-caa4`; проверяется отказ с понятным сообщением, а не
   ложный успех. Настоящие ARI start/stop и отправка в Channex не вызывались.

Все ID выше имеют префикс `2026-09-20T`; полные логи — `tests/runs/logs/`.
Первый общий unit-прогон при одновременной нагрузке браузера имел также таймауты.
При ограничении двумя workers остались только два воспроизводимых Bash-сбоя.

## Локальная конфигурация

Для локальных сессий заполнен отсутствовавший SESSION_SECRET случайным значением
в игнорируемой `.env`. Исходная `.env` сохранена в приватном backup с правами 0600;
секрет в Git не попадает. Серверные секреты и настройки авторизации не менялись.
Локальный APP_API_URL очищен от ссылки на прежний localhost API: обычный
`npm run dev` после остановки preview снова поднимет оба процесса сам.
Локальный preview запускается вручную на loopback, с выключенными фоновыми
синхронизациями, ARI и уведомлениями. Старые launchd-службы и публичный Mac-туннель
остаются выключенными.
Чтением через настоящий браузер проверены 9 разделов localhost: главная,
шахматка, номерной фонд, бронирования, гости, финансы, подключения, менеджер
каналов и аналитика. Все вернули 200, видимый main и отсутствие экрана
«Не удалось загрузить данные»; API `/health` — 200. Персональные данные и
скриншоты рабочих гостей не сохранялись. Доказательство: `local-routes.json`.

## Учётные записи и границы SaaS

Отдельная проверка настоящего AppModule и локальной PostgreSQL подтвердила:
регистрацию, запись membership, вход по коду, запрет повторного кода,
приглашение второго пользователя в ту же организацию, запрет повторного
приглашения, отзыв сессии после выхода. Письма перехвачены в памяти; внешняя
почта не отправлялась. Все вымышленные пользователи удалены. Агрегаты:
`account-journey.json`. Это дополнительная разовая проверка, отдельно от
журналируемых наборов тестов ниже.

**Блокер публичной регистрации:** TRIAL-пользователь получил 200 на
`/inventory/summary` общего объекта. Замок проверяет сессию, но отдельный
демо-объект для trial ещё не реализован. ADR-046/Q-130 требуют демо вместо
доступа к Luxx. Это не разрешение открыть регистрацию внешним клиентам.
Мультиарендность и модель данных этой проверкой не изменялись.

## Непроверенное на сервере

Документированный SSH-ключ отсутствует на Mac; существующий профиль hostinger
ведёт на другой адрес. Для `187.77.145.152:5555` нет подтверждённого host key.
Проверка подлинности SSH не обходилась; запрошен рабочий профиль доступа.

До получения доступа остаются открытыми: deployed SHA, серверные env и адрес БД,
реальная доставка писем, состояние webhook/очередей Channex на сервере,
автоматические backup и восстановление копии в отдельную базу. HTTP 200 от
скрипта аналитики не доказывает эти пункты. Cloudflare Access остаётся включён.

## Реальная смена после серверной проверки

1. Зафиксировать SHA, единственный источник рабочей БД, свежую резервную копию
   и успешное восстановление в отдельную базу; не накатывать миграции вслепую.
2. Проверить вход действующего сотрудника, автора в журнале, выход и запрет
   доступа после отзыва сессии. Пароли/коды не включать в отчёты.
3. Зафиксировать начальные агрегаты Exely/PMS: заезды, выезды, проживающие,
   занятость, платежи и задолженность. Разницу объяснить до начала смены.
4. По согласованному порядку параллельного учёта пройти настоящую смену:
   новая бронь, изменение, заселение, оплата, переселение, выезд и отмена.
   После каждого действия сверить связанные экраны и запись в БД.
5. Закончить сверкой суток и внешних событий: дубли, пропуски, retries,
   неразобранная очередь. Расхождения оформить с ID без персональных данных.
6. Только после отдельного решения владельца выполнять cutover по CUTOVER.md.
   Автотест «полный день» не заменяет день работы персонала.
