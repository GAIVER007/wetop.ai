# Учения «мёртвое соединение с базой» — 14.09.2026

**Зачем.** Проверить ADR-043 (сроки пула соединений) в условиях 14.09: Mac уснул, соединения пула умерли молча,
новые соединения работают, а API стоял до перезапуска. Настоящий сон Mac не применялся: он остановил бы API,
синхронизацию архивный источник, туннель Channex и соседние сессии, а разбудить машину может только владелец.

**Как.** `scripts/ops/db-dead-connection-drill.ts` (коммиты 95d9300, deee9ac, 2e852cd):

- между процессом и **настоящим пулером Supabase** стоит прокси;
- прогрев: два соединения пула, одно держит открытую транзакцию;
- «сон»: все уже открытые соединения перестают доставлять байты в обе стороны, сокеты при этом открыты;
  новые соединения через прокси работают;
- сразу 4 запроса, затем проба каждые 3 с до первого ответа;
- в базу идёт только `SELECT 1`, мест в пуле 2 (у API 5), строка подключения не печатается.

Запуск: `npx tsx scripts/ops/db-dead-connection-drill.ts` — сроки из окружения; `--control` — сроки выключены,
как было до ADR-043.

## Со сроками ADR-043 (прогон 4), пробы свёрнуты

```
Режим: сроки пула ADR-043; подключение и место в пуле: 30,0 с, ответ базы: 30,0 с, keepalive: 10,0 с; мест в пуле 2
   Шифрование до пулера (первые байты соединения): клиент: БЕЗ TLS (StartupMessage открытым текстом); пулер: без TLS, вход: SCRAM (SASL)
3. Итог запросов после «сна» (время от «сна»):
   транзакция, открытая до «сна»  до «сна»       ошибка: Database did not answer for 30000 ms; connection closed на +30,0 с
   запрос 1                       старт +0,0 с   ошибка: Database did not answer for 30000 ms; connection closed на +30,0 с
   запрос 2…4                     старт +0,0 с   ошибка: timeout exceeded when trying to connect на +30,0 с
   проба 1…10                     старт +3…+30 с ответ на +30,9…+31,6 с
   проба 11                       старт +33,1 с  ответ на +33,2 с
4. После восстановления 5 запросов подряд: 189 мс, 170 мс, 170 мс, 172 мс, 168 мс; соединений через прокси всего 4
ИТОГ: ПУЛ ВОССТАНОВИЛСЯ САМ: первый ответ через 30,9 с после «сна», висящих запросов 0
```

Запросы, пришедшие в первые 30 с, получают ошибку: два — на мёртвых соединениях, три — в очереди за местом.
Сроки ожидания места и ответа равны, поэтому очередь истекает на те же +30,0 с, когда освобождаются места.
Проба, пришедшая позже, дожидается места и получает ответ по новому соединению.

## Что доказано и что нет

- **Доказано** на настоящем пулере: пул без сроков висит бесконечно; со сроками ADR-043 каждый запрос завершается не
  позже ~30 с, транзакция, открытая до «сна», место не держит, пул восстанавливается без перезапуска.
- **Не проверено:** TCP keepalive — на его пробы отвечает локальный прокси, а не пулер; сон самой ОС. Это проверит
  следующее пробуждение Mac: в `~/Library/Logs/pms-lux/api.log` ожидаются `Database did not answer` или
  `Connection terminated`, но не тишина, и API должен отвечать без `kickstart`.

## Попутно: соединение с пулером без шифрования

По первым байтам соединения: клиент сразу шлёт StartupMessage без запроса TLS, пулер отвечает запросом входа SCRAM.
Пароль по сети не передаётся (SCRAM), но запросы и ответы базы идут открытым текстом. В ADR-043 это прежде было
записано как «TLS-соединение» — ошибка, исправлено. Строку подключения меняет только владелец (`SECURITY.md`).
