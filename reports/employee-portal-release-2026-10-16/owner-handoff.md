- Полная активная цепочка содержит **133 миграции**, не136 из прежнего checkpoint. Все применились на пустую отдельную базу, Prisma drift отсутствует, каждый down вернул исходную схему. Боевая база не использовалась.
- Первичные логи: `final-restore.log`, `final-migrations.log` в `/srv/hermes/workspace/wetop-portal-release-evidence-61af/`. Итоговый отчёт кандидата содержит остальные проверки и точный SHA.

Это локальная репетиция, не подтверждение актуального production backup, применения SQL или рабочего S3.

## Что остаётся исключительно владельцу/администратору

1. После полного зелёного `release-checks` проверить точный SHA кандидата и слить PR штатным способом. Агент не перематывает `release` и не подменяет гейт.
2. Сверить реальный production migration ledger со всеми активными SQL кандидата. Проверить126/127 marketing и128/129 portal, но не считать, что это гарантированно весь pending-набор. Проверить отсутствие дублирующих активных связок business/user, существование роли приложения и схему установки. Не исправлять дубли автоматически.
3. Сделать свежий backup именно целевой базы и закрытых объектов. Проверить восстановление именно этой копии в изоляции с совместимым набором миграций. Сохранить предыдущие образы и конфигурацию, определить допустимость отката старых writers. SQL down разрушителен, не запускать автоматически.
4. Применить SQL только через существующий разрешённый администратору порядок из `docs/ops/backups.md` и `docs/deploy.md`. Прежнее разрешение root migration helper относится к другому финансовому пакету, не к кабинету. Не вызывать helper вслепую, не переделывать его, не сбрасывать attempted fence и не расширять права hermes.
5. После SQL проверить таблицы, ограничения, RLS, ACL и resolver128/129. Для восстановления ACL штатный restore переигрывает чистую129, не повторяет CREATE TABLE128. Не выдавать один migrate status за полную проверку схемы.
6. После подтверждения всех pending SQL того же полного `origin/release` SHA администратор использует существующий `wetop-auto-deploy --migrations-applied` с этим SHA. Этот флаг не применяет SQL. Если release изменился, снова сверить pending-набор. Сохранить health/rollback-гейты.
7. Для фотографий подтвердить размещение API и private S3 в Казахстане, включая реплики/backup, отсутствие anonymous read/list, ограниченные права на `employee-portal/*`, подписи GET60с и отказ неподписанных/подменённых/истёкших запросов. Не выводить значения конфигурации и подписанные URL. Без этих условий storage остаётся выключенным. Загрузка тестовых данных в production не разрешена.
8. Отдельно развернуть `apps/sites` через уже выбранный Cloudflare Worker `wetop-sites-production` по существующей документации. В среде агента нет разрешённой Cloudflare авторизации. Не создавать новый маршрут/механизм и не брать доступы соседнего проекта. Авторизацию администратор предоставляет только штатным закрытым способом, не в чате.
9. После выкладки сверить реальные image/build SHA API/web и Worker, health и поведение на `app.wetop.ai`/реальном домене сайта. Клон, push, HTTP200 и зелёный CI сами по себе публикацию не доказывают. Открытие приватного кабинета впервые может создать default profile; только разрешённое нормальное использование после SQL, без production fixtures.

## Откат и честный статус

Предыдущие неизменяемые календарные артефакты и исходные доказательства сохранены. Автоматический откат приложения не восстанавливает БД или объекты. Новый кабинет нельзя назвать опубликованным до выполнения администраторских пунктов и проверки реальной версии. Неизвестное состояние production, S3 и Cloudflare остаётся неизвестным, не зелёным.
