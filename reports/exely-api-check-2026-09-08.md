## Единице-сутки августа: начисления API против отчёта Exely (контроль Gate 2)

| Категория | API (строки «проживание» по дням) | Контроль (аудит) | diff |

| Двухместная | 114 | 121 | −7 |

| Общая женская | 662 | 690 | −28 |
| **Итого** | **2172** | **2174** | **−2** |

Начисления за проживание в августе (kind=1): 15 430 564,86 ₸. Это другая база, чем 15 688 018 ₸
оборота «по заездам» из аудита (там — целые проживания заездов августа, включая ночи сентября).

**Вывод.** Итог сходится с точностью до 2 единице-суток, а по категориям расходится в обе стороны
(+38 мужской dorm, −28 женский, −7 двухместная). Категория в начислении — это категория
**брони** (`roomTypeId` проживания), а отчёт загрузки Exely, по всей видимости, считает по
**фактической единице**. Разница = гости, размещённые не в той категории, которую бронировали
(например, бронь женского dorm, койка в мужском). Это гипотеза — **Q-099**. Для нашей шахматки
это прямо важно: клетка принадлежит единице, а не категории брони; сверять Gate 2 надо
по единице (наш `Allocation`), а не по `roomTypeId` брони.

## Что это значит для шахматки

Одна строка начисления `kind=0` = одна клетка: `date` × `reservationId` (проживание), у проживания
есть `roomNumber` (единица) и `roomTypeId`. То есть API уже отдаёт шахматку в «разобранном» виде.
