# Разбор кода, которым доказывается гейт «сутки сошлись с Exely»

15.09.2026, удалённая сессия. Читался код, который каждые пять минут переносит брони из Exely, сажает
их по койкам и потом сам же говорит «сутки сошлись»: `scripts/imports/src/exely/**`, `cli-sync-day.ts`,
`scripts/reconciliation/src/cli-double-entry.ts`, `cli-balances.ts`, `cli-system-trace.ts`.

Повод простой: эти скрипты — единственное доказательство, что новая система не теряет броней. Если
инструмент измерения зелёный сам по себе, зелёными будут и гейты.

Каждая находка перепроверена по коду руками. Правки внесены только в измерительную часть; всё, что
меняет правила брони, места или деньги, ушло вопросами владельцу (AGENTS.md §15).

> **Состояние на 21.09.2026.** Exely больше не источник (ADR-052): автосинхронизация и `cli-sync-day.ts` сняты.
> Разбор от этого не устарел — импортёром `cli-import-reservations.ts` по-прежнему возвращают брони, а сверки
> (`cli-double-entry.ts`, `cli-system-trace.ts`, `cli-balances.ts`) остаются тем, чем доказывают гейт. Вопросы
> перезаведены под номерами Q-156…Q-163: прежние Q-136…Q-143 в `main` заняты другим.

## Починено: инструмент перестал быть зелёным сам по себе

### 1. Двойной ввод: вердикт складывался из четырёх чисел

Было: `RESULT: OK` выставлялся по равенству заездов, выездов, занятых и категорий. Поимённые списки
(«только в PMS», «только в Exely») считались **после** того, как числа уже разошлись, и в вердикт не входили.
Две встречные ошибки давали ноль:

- бронь, заведённая в PMS (сайт, канал, стойка), +1 к занятости — и рядом бронь из Exely, которая не доехала, −1;
- незаезд: стойка ставит `NO_SHOW`, PMS такое проживание не считает, а в Универсальном API Exely незаезда нет
  вовсе — бронь там продолжает занимать ночь. Систематический −1 на каждый незаезд;
- ранний выезд: импорт заканчивает проживание фактической датой (правило стойки), а сверка брала у Exely
  плановую. Ровно ±1 в занятых и выездах в противоположные стороны — идеальный гаситель чужой ошибки.

Стало: логика вынесена в `scripts/reconciliation/src/double-entry.ts` (7 тестов), CLI только читает данные.
Вердикт требует и равенства чисел, **и** пустых поимённых списков. Выезд считается по фактической дате
с обеих сторон — тем же правилом, что в импорте. Незаезды названы отдельным разделом отчёта: их снимает
в Exely человек.

Доказательство red → green: те же семь тестов против прежнего правила — три красных
(встречные ошибки, ранний выезд, незаезд), четыре зелёных.

### 2. Сквозная сверка: одна бронь «в пути» объясняла любое расхождение суток

Было: `if (exelyDayBad.length && pending.length === 0) fail(...) else warning(...)`. Проверки, что
расхождение объясняется **именно этими** бронями, не было — хватало непустого списка. На живом объекте
кто-то изменён в Exely после последней синхронизации почти всегда, значит расхождение суток штатно
не поднимало FAIL.

Стало: `explainedByPending(rows, pending)` — разница по каждому показателю должна укладываться в число
броней «в пути», нечисловое расхождение не объясняется вовсе; сами номера печатаются в предупреждении.
Тесты red → green в `system-trace.test.ts`.

Там же: проживание **без ячейки** было предупреждением, хотя двойной ввод за то же самое даёт FAIL.
Две сверки одного факта расходились в вердикте — теперь обе называют это расхождением: гостя нет на шахматке.

### 3. Сверка балансов доказывает меньше, чем написано в отчёте

Импорт пишет платёж как `amount − toPayAmount`, начисление — как `amount`. Сверка считает
`баланс = начислено − оплачено` и сравнивает с `toPayAmount` из того же снимка. Подставим:
`amount − (amount − toPayAmount) = toPayAmount`. Равенство выполняется алгебраически для любого
проживания, которого не касалась стойка, при любых суммах — даже если Exely отдал чушь.

Код не менялся: другого источника «сколько гость заплатил» Универсальный API не даёт. В отчёт добавлена
строка о том, что сверка доказывает (импорт положил ровно то, что отдал Exely, и после переноса баланс
никто не сломал) и чего не доказывает (что сама сумма верна). «1449 из 1449 до тиына» из отчёта
`reports/balances-2026-09-08.md` надо читать именно так.

### 4. Переключатель ПД не был подключён к импорту

`PII_STORAGE` (ADR-018, `CUTOVER.md` «Условия допуска») читал приём броней из каналов и проверка
окружения, а оба импорта из Exely передавали соль анонимизации всегда. На боевой базе в РК у всех
перенесённых гостей вышло бы «Гость Тест-…» с выдуманным телефоном, а заметки брони — пустые; для
158 будущих броней каналов опознать гостя на заезде было бы нечем.

Стало: `importPiiSalt()` — один переключатель на систему, тесты на оба режима. По умолчанию ничего
не меняется: без `PII_STORAGE=real` перенос по-прежнему анонимный.

## Вопросы владельцу: правила брони, места и деньги

Эти четыре трогают то, что агенту решать нельзя. Код не менялся.

| | Что нашли | Вопрос |
|---|---|---|
| Статус | Импорт пишет `status` из Exely безусловно, мимо правил домена. Стойка ставит незаезд → через ≤5 минут синхронизация видит в Exely «New» (незаезда в API нет), возвращает `CONFIRMED`, снова занимает койку и заводит **второе** начисление поверх штрафа. То же с отменой и с заселением, сделанным в PMS раньше, чем в Exely | **Q-140** |
| Возврат | Возврат денег в Exely в PMS не приходит никогда: `paidMinor = amount − toPay` при возврате даёт 0, а нулевой платёж пропускается — на счёте остаётся вечный минус. `toRefundAmount` читается адаптером и не используется никем | **Q-141** |
| Место | У проживания, которому Exely не назначил комнату, администратор сажает гостя руками. Дальше в Exely двигают даты: импорт переписывает даты проживания, а назначение остаётся на старых ночах — на шахматке гость стоит не те ночи, и койка продаётся ещё раз | **Q-142** |
| Устойчивость | Одна бронь, которую нормализатор не разобрал (незнакомый источник, неизвестный тип комнаты, бронь без проживаний), роняет прогон целиком: в базу не попадает ничего, и так каждые пять минут. Для ленты Channex эту дыру закрыли 10.09, для пути из Exely — нет | **Q-143** |

Записаны в `QUESTIONS.md` с предложением по каждому.

## Проверено, не подтвердилось

- Две брони на одной койке: невозможно, `EXCLUDE USING gist` по `(inventory_unit_id, daterange)` плюс
  проверка пересечения до вставки; импорт сажает через `planSeats`.
- Рассадка пачкой (`seat-plan.ts`, ADR-044): обмены, циклы, переезд — конфликтов внутри пачки нет, 20 тестов.
- Повторный запуск: ключи `confirmationNumber`, `exelyRoomStayId`, `exelyPersonId`, `exely:<roomStayId>`;
  весь импорт в одной транзакции, обрыв не оставляет половины.
- Гражданство (Q-118): пустое значение из Exely колонку не трогает.
- Деньги в тиынах: `toMinorUnits` через `toFixed(2)` и `BigInt`, ошибки float не протекают.
- Дельта остатков в Channex: отмена, перенос дат, смена категории, горизонт 500 суток — пропущенной дельты нет.

## Замечено попутно

- Окно догона ограничено семью сутками, а полный проход идёт только по броням текущих суток: изменение
  будущей брони, пропущенное при простое дольше недели, не подхватится уже никогда. Часть Q-143.
- `currency` пишется в `CHAR(3)` без `trim` — та же ловушка, что дала 401 гостя с гражданством из пробелов.
  Сейчас Exely отдаёт `KZT`, но защиты в коде нет.
