## B. Тесты в схеме pms_test (14.09.2026, ADR-042)

**Как устроено.** `DATABASE_SCHEMA=pms_test` → Prisma строит запросы в `pms_test`, а `search_path` соединения направляет
туда же прямой SQL. `npm run test:schema` создаёт схему, накатывает 12 миграций и копирует все таблицы рабочей базы одной
транзакцией (первая копия: 33 таблицы, 27 744 строки, 07:50 UTC). integration получает схему из `vitest.config.ts`;
e2e поднимает свой API :3101 (фоновые задачи, ARI, Telegram выключены) и стойку :3100, первым идёт `schema-guard`.

**Найдено по дороге.** Первый прогон integration (07:54 UTC) — 5 из 17 упали: запись неисправности и длительность сессии
сайта сделаны прямым SQL, а опция схемы Prisma его не меняет. Запись неисправности ушла в рабочую `system_incidents`,
живой сторож поднял её до ESCALATED и отметил будильник (строка `e77b8212…` удалена в 08:00 UTC; если в Telegram пришло
предупреждение про `INTEGRATION-TEST` — оно ложное, от этого прогона). Исправлено `search_path` при подключении (Session
pooler Supabase его пропускает — проверено), тест `tests/integration/test-schema.test.ts` red → green.

Гость, появившийся в рабочей схеме за это время (08:11), — бронь `BDC-WETOP-MU0YRKY4` из Channex staging, пришла в рабочий
API из цикла канала другого чата; тестовый API опрос и приём Channex не выполняет.

**Осталось.** `web-booking.spec.ts` держит жёсткий адрес рабочего API и в изолированный прогон не входит, пока адрес не
переведён на `APP_API_URL` (файл сейчас правит другой чат). Брони автотестов из прогонов на старых настройках, созданные
до 08:08 UTC 14.09, лежат в рабочей схеме отменёнными — их уберёт повторный `cli-purge-test-data.ts --apply`, когда станут
старше часа. Рабочий API на launchd получит поле `schema` в `/system/connection` при следующем перезапуске; на изоляцию
это не влияет — тесты поднимают свой API.
