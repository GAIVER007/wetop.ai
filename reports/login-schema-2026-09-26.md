# Локальный вход 500: схема базы отстаёт от API

26.09.2026: API на 3001 подключён к DATABASE_URL из корневого .env, схема public.
Read-only проверка: health=200/database up; неизвестная синтетическая почта получает 401.
В рабочей базе последняя завершённая миграция 20260924000019_seller_profiles.
В public.memberships отсутствует role, таблица public.platform_admins отсутствует.
AuthService.login загружает memberships и после успешной проверки пароля читает права
через access(). Текущая схема не соответствует этим запросам; SELECT 1 в health этого не обнаруживает.

## Необходимое исправление

Применить только существующую 20260925000020_access_extensions после отдельного разрешения
на рабочую базу и проверенной резервной копии. Миграция добавляет memberships.role,
platform_admins, organization_extensions и enum-типы. Самый ранний участник каждой организации
получает OWNER, остальные STAFF, по ранее принятой модели; главные администраторы не назначаются.
Миграции 21–23 не входят в этот шаг. Нельзя запускать общий migrate deploy, применяющий все ожидающие.

Проверка: транзакционное применение точного SQL, регистрация checksum в журнале Prisma,
сверка новых объектов и ролей без вывода пользовательских данных; затем реальный вход владельцем.
Откат: down.sql миграции 20 и согласованная предыдущая версия API; сначала сохранить выданные
после миграции роли/расширения. После появления новых данных слепой down недопустим.

Рабочая схема в ходе диагностики не изменялась. Обход проверки прав не добавлялся.

Резервная копия создана перед запросом разрешения: wetop-20260926T114209Z.dump,
256K, 43 таблицы с данными; pg_restore --list проверен скриптом. Копия хранится
в закрытом каталоге вне репозитория. Пробное восстановление этой копии ещё не выполнено.

## Исправление после отдельного разрешения владельца

Владелец разрешил применить именно миграцию 20 в рабочую Supabase.
Резервная копия восстановлена в отдельную временную локальную базу: 43 таблицы.
На восстановленной копии проверены точный migration.sql и down.sql; временная база удалена.
Примечание совместимости: дамп PostgreSQL 17 содержит SET transaction_timeout, которого нет
в локальном PostgreSQL 16. Для проверки исключена только эта команда настройки таймаута.

В рабочей public применён только 20260925000020_access_extensions в одной транзакции,
с advisory lock, lock_timeout=5s, statement_timeout=30s и проверкой исходной миграции 19.
Проверено ровно одно членство OWNER на каждую существующую организацию.
В той же транзакции записаны SHA-256 точного SQL и завершение в _prisma_migrations.
Независимые SELECT memberships.role, platform_admins.revoked_at и organization_extensions.status
после commit прошли. API /health вернул status=ok/database=up.
Миграции 21–23 не применялись. Успешный реальный вход ожидает проверки владельцем;
его пароль не запрашивался и не использовался в тестах.
