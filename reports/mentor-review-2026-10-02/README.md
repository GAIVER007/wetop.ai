## Что нашлось по дороге

**Наивное восстановление копии снимало SEC-1b.** Копия `db-backup.sh` снимается без прав, а таблицы при
восстановлении создаются заново и получают права по умолчанию из миграции 026. Проба на всей цепочке миграций:
роль стойки `wetop_app` получала 286 лишних прав, в том числе чтение `users.password_hash` и полный доступ к десяти
закрытым таблицам. Поэтому `db-restore-prod.sh` повторяет миграции прав той же транзакцией; после этого отличий 0 из
10 104 проверок (`restore-privileges-simulation.txt`).

**Почему не условие `if:` в `checks.yml` против форков.** Для `pull_request` GitHub берёт файл проверок из самого
запроса, автор форка условие просто уберёт; а пропущенная задача для обязательной проверки считается успешной. Хук
лежит в образе раннера, запрос его не меняет, задача краснеет (документация GitHub: ненулевой код хука, и задача
не запускается и помечается проваленной).

**Почему uv, а не actions/setup-python.** Python из setup-python ссылается на системные `libsqlite3.so.0` и `libssl.so.3`
(проверено `readelf`), а в образе раннера их может не быть, sudo же под `no-new-privileges` не работает. Python от uv
собран статически и требует только glibc.

**Миграция 042 в рабочей базе не применена.** Запрос 02.10 около 21:00 UTC: у `wetop_app` нет права на
`users.last_login_at`, в `_prisma_migrations` нет `20261002000042`. Автовыкладка вершину с новой миграцией не выкладывает,
пока владелец её не применит и не запустит `--migrations-applied` (`docs/deploy.md` §1д). Если пришло сообщение об отказе
про 042, порядок: копия, `mig deploy`, `--migrations-applied <вершина>`.

**`cli-rollback-window.ts` удалён 28.09** (f760c301) вместе с инструментами архивного источника; старый раздел отката
на него ссылался. В новом плане брони каналов между копией и откатом ищутся в кабинете Channex.
