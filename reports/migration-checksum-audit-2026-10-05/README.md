Это историческая предпроверка однозначности выбора филиала при переносе legacy-агента, не инвариант запрета нескольких филиалов после переноса. Агент уже имеет корректный филиал, нарушения связей отсутствуют. Повтор `seller_scope_assert()` сейчас закономерно отказал бы в старом переносе. На production assert/backfill/ensure/bind не вызывались.

В apps/, packages/domain/ и scripts/ кандидата нет вызовов seller_scope_assert/precheck. 052 также их не вызывает. Повторное применение 035/036/039 не является способом устранить checksum и запрещено. Новая исправляющая миграция только из-за этой исторической проверки не нужна.

## Изолированные проверки совместимости

Две новые пустые БД на localhost:55742, PostgreSQL 16.15; production PostgreSQL 17.6. Реальные данные не копировались. Первая собрана из всех 56 миграций релиза с тремя историческими SQL, вторая из всех 56 текущих SQL. Обе цепочки PASS, [список применённых миграций](rehearsal.json).

На обеих изолированных схемах применена 052: PASS. Создан только синтетический объект и черновик. Новое подключение прочитало черновик, down.sql отказался удалять непустую таблицу, последующая проверка подтвердила сохранение строки. [Результаты](052-rehearsal.json).

На исторической схеме после 052 `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code --script` кандидата завершился кодом 0, [diff пуст](prisma-diff.sql). Prisma не сравнивает всю семантику функций/триггеров/RLS, поэтому каталог выше проверен отдельно. Код продавца читает профиль через agentId; мастер использует onboardingProgress по locationId.

Это доказательство совместимости схемы в проверенном объёме, не замена полной приёмки на домене. Full CI кандидата ранее успешен: https://github.com/GAIVER007/wetop.ai/actions/runs/37267233807. В этом аудите полный CI и браузерная приёмка повторно не запускались. Восстановление свежего production backup и полный прогон на PostgreSQL 17 ещё не выполнялись.

## Решение для следующего этапа

Технических оснований ремонтировать эти три миграции не найдено. Можно согласовать продолжение исходного этапа резервного копирования и проверки восстановления. Сам checksum drift остаётся документированным: записи истории и применённые файлы не исправлялись. Не следует обходить проверку release, скрывать расхождение или выдавать этот отчёт за разрешение на выпуск. Любая необходимость адаптировать штатную процедуру к документированному drift должна быть согласована до выкладки. На SHA, 052 и deploy разрешение всё ещё требуется отдельно.
