## 2. Что в коде работает иначе, чем вчера

- `release` двигает только `scripts/ops/promote-release.sh` (нужен вошедший `gh` или `GITHUB_TOKEN`); прямой
  `git push origin <sha>:release` больше не штатный путь. **Найдено по пути:** на момент разбора `release` стояла на
  `8a65868`, на один коммит впереди `main` («fix: release same-day checkouts…»): пуш мимо `main`, а не перемотка на
  проверенный коммит `main`. К вечеру 01.10 этот коммит уже в `main` (`9f2ee55`); скрипт такого больше не допустит.
- Выкладка стойки по правилу 18 ждёт «да» владельца, скрипт его спрашивает.
- Схема автотестов и ворота миграций строятся вместе с `migrations-held`; `prisma migrate dev` с отложенной
  миграцией не запускать (`docs/ops/migrations-held.md`).
- Дежурный агент без отдельного ключа не стартует.
- Очередь CI теперь у каждой задачи своя: пока свой раннер `wetop` не берёт задачи, задача `db` на раннере GitHub всё
  равно стартует (01.10 прогон 836 висел «pending» за прогоном 834 с очередью на свой раннер; red → green
  `ci-runner.test.ts`, `…15-39-37Z-unit-a541.log`).
- Рулсеты для `main` и `release` лежат файлами `docs/ops/github-rulesets/*.json`: Settings → Rules → Rulesets →
  New ruleset → Import a ruleset, без ручного набора полей.
- Объект в Channex создаётся с автообновлением остатка только по подтверждению брони.

## 4. Три вопроса аудита

**На чём работает дежурный агент на сервере.** В репозитории это не записано: `scripts/ops/guard/run.sh` до
01.10 принимал и токен подписки, и ключ API, а README советовал токен подписки как «не требующий отдельных денег».
Значит, скорее всего, агент работает на токене подписки владельца и делит с ним лимит. Проверка на сервере без
показа значений: `grep -c '^CLAUDE_CODE_OAUTH_TOKEN=' /root/wetop/scripts/ops/guard/.env` (1 означает токен
подписки). После пункта 6 ответ будет однозначным: с токеном скрипт не стартует.

**Применены ли 038 и 039 на рабочей базе.** Из облачной сессии рабочая база недоступна (подключённый Supabase
содержит другие проекты, к базе WETOP он не ведёт; проверка `list_projects`, только чтение). По репозиторию: 038,
039 и 040 лежат в `release` с 30.09 (`af10b817` уже содержал 039), автовыкладка на такую вершину отказывает до
`--migrations-applied`, то есть либо сервер стоит на вершине до 038 и ждёт, либо владелец применил 038–040 и
выложил. Ответ даёт запрос только на чтение:

```sql
SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY migration_name DESC LIMIT 5;
```

Если 039 там есть, папку `migrations-held` вернуть в цепочку (пункт 4). Если нет, порядок 038 (код первым, уже в
`release`) и 039 (после смоуков SA2.5) описан в `docs/ops/rls.md` и `docs/ops/sa25-agent-scope.md`.

**Дата живой смены и переезда на ps.kz.** Не назначены: `CUTOVER.md` условие 2 («дата не назначена»),
`plans/kz-move-2026-09-26.md` (A1 не начат, аккаунт ps.kz заведён 18.09, платит владелец). Порядок по ответу
ментора: сначала сервер в Казахстане (A1), затем живой день (A2). Условие 3 допуска (откат) после этого разбора
ждёт Q-237.
