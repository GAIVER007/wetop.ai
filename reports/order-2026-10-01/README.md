## 2. Что в коде работает иначе после слияния

- `release` перематывается только на коммит `main` с зелёной `release-checks` и по «да» владельца (AGENTS.md §18):
  `scripts/ops/promote-release.sh <коммит>` проверяет оба условия, перемотку только вперёд и пушит; прямой
  `git push origin <коммит>:release` остаётся запасным путём. **Найдено по пути 01.10:** `release` стояла на `8a65868`,
  на один коммит впереди `main`, то есть пуш мимо `main`; скрипт такого не допустит.
- `auto-deploy.sh` отличает миграцию, снятую из цепочки, от новой и говорит об этом словами
  (`tests/unit/auto-deploy.test.ts`).
- Объект в Channex создаётся с автообновлением остатка только по подтверждению брони (редакция `main`);
  существующему объекту то же ставит `cli-channex-property-settings.ts --apply`.
- `CLAUDE.md` больше не хроника: записи дня идут в `docs/history/` файлом задачи (письмо ментора 03.10), старые в
  `docs/history.md`; закрытые вопросы в `docs/questions-closed.md`.

## 4. Три вопроса аудита

**На чём работает дежурный агент на сервере.** Ответ к 06.10: `run.sh` на `main` (ADR-137 п. 7) с токеном подписки
без `GUARD_ALLOW_SUBSCRIPTION=1` не стартует, так что после пересборки образа ответ даёт сам журнал агента («платит
ключ API»). Разбор 01.10: в репозитории это не было записано: `scripts/ops/guard/run.sh` до
01.10 принимал и токен подписки, и ключ API, а README советовал токен подписки как «не требующий отдельных денег».
Значит, скорее всего, агент работает на токене подписки владельца и делит с ним лимит. Проверка на сервере без
показа значений: `grep -c '^CLAUDE_CODE_OAUTH_TOKEN=' /root/wetop/scripts/ops/guard/.env` (1 означает токен
подписки). После пункта 6 ответ будет однозначным: с токеном скрипт не стартует.

**Применены ли 038 и 039 на рабочей базе.** Ответ к 06.10 с `main`: 039 применена 30.09.2026 отдельным шагом (список
миграций Supabase, `tests/unit/migrations-hold.test.ts`, ADR-137 п. 4); цепочка на `main` дошла до 059, записи выкладок
02–05.10 в `docs/history.md`. Разбор 01.10: из облачной сессии рабочая база недоступна (подключённый Supabase
содержит другие проекты, к базе WETOP он не ведёт; проверка `list_projects`, только чтение). По репозиторию: 038,
039 и 040 лежат в `release` с 30.09 (`af10b817` уже содержал 039), автовыкладка на такую вершину отказывает до
`--migrations-applied`, то есть либо сервер стоит на вершине до 038 и ждёт, либо владелец применил 038–040 и
выложил. Ответ даёт запрос только на чтение:

```sql
SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY migration_name DESC LIMIT 5;
```

Если 039 там есть, папку `migrations-held` вернуть в цепочку (пункт 4). Если нет, порядок 038 (код первым, уже в
`release`) и 039 (после смоуков SA2.5) описан в `docs/ops/rls.md` и `docs/ops/sa25-agent-scope.md`.

**Дата живой смены и переезда на ps.kz.** Ответ к 06.10: двойная смена назначена на вторник 06.10.2026
(`plans/double-shift-2026-10-06.md`, черновик 03.10, утверждает владелец); переезд на ps.kz не начат. Разбор 01.10: не
были назначены: `CUTOVER.md` условие 2 («дата не назначена»),
`plans/kz-move-2026-09-26.md` (A1 не начат, аккаунт ps.kz заведён 18.09, платит владелец). Порядок по ответу
ментора: сначала сервер в Казахстане (A1), затем живой день (A2). Условие 3 допуска (откат) после этого разбора
ждёт Q-237.
