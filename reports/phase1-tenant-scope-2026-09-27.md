## 2. Backfill (внутри той же миграции, детерминированный, без угадывания)

| Таблица | Правило | Неоднозначно → |
|---|---|---|
| `guests` | Все брони гостя (как основного и через `stay_guests`) → объекты → организации; заполняется, только если организаций РОВНО ОДНА | NULL + отчёт |
| `audit_logs` | (а) по сущности: `entity_type`/`entity_id` → таблица сущности → объект → организация (Property, Reservation, ReservationItem, Folio, Payment, InventoryUnit, InventoryBlock, AccommodationType, RatePlan, ChannelMapping, Service, TrackedSite, Guest, SellerProfile); (б) остатки — по автору с РОВНО ОДНИМ членством | NULL + отчёт |
| `external_events` | Единственный объект с `channel_mappings` данного провайдера | NULL + отчёт |
| `channel_outbox` | То же | NULL + отчёт |

Особенность `audit_logs`: журнал append-only (триггер `audit_logs_immutable`, миграция 20260925000022) — триггер **выключается только внутри транзакции миграции** и включается там же; содержимое строк (кто/что/before/after) не меняется, заполняется только новая пустая колонка. Это разовое обогащение, санкционированное ADR-100.

**Отчёт:** `scripts/ops/phase1-scope-report.sql` (только чтение) — по каждой таблице: total / linked / remaining NULL, и раскладка остатка («кандидатов больше одного» vs «связи нет»; для журнала — по `entity_type` и наличию автора). Репетиция на локальной тестовой схеме прошла (см. §4); **прод-цифры снимает владелец этим же скриптом на шаге проверки** (§6, шаг 4) — в этой сессии доступа к рабочей базе нет и не должно быть.

Ожидание для прода (обоснование): у Luxx `properties.organization_id` заполнен миграцией 20260920000016, «channex» сопоставления — у одного объекта ⇒ гости с бронями, события и очередь привяжутся полностью; NULL-остаток журнала — только строки, чью сущность не вывести (неизвестные `entity_type` без автора). NOT NULL сознательно не вводится — поле остаётся nullable до полного разбора остатка (поручение: «остановить перевод в NOT NULL, если это создаёт риск»).

Новые проверки (вторая синтетическая организация против первой):
- не меняет гостя по прямому id (`update`) — «не найден», данные не тронуты;
- не добавляет и не удаляет документ гостя по прямому id;
- не читает журнал первой организации (было закрыто цепочками — осталось, плюс колонка);
- не видит `external_events` первой (список и **ревизия по прямому id**);
- не видит и не считает `channel_outbox` первой (строки и сводка);
- прямые ID гостя/счёта/начисления/платежа/ячейки/сайта — прежние тесты, зелёные;
- новые записи всех четырёх таблиц рождаются со scope (проверено raw SQL): гость — организация объекта; журнал — организация (и на служебном пути синка); событие и очередь — объект.

Существующее поведение Luxx: первая организация во всех тестах видит и меняет своё, как раньше; NULL-строки (не разобранные backfill-ом) остаются видимыми ей через прежние цепочки — стойка не теряет ни гостей, ни журнал.

## 5. Риски

| Риск | Оценка / смягчение |
|---|---|
| Backfill журнала при выключенном триггере | Только внутри транзакции миграции; ALTER TABLE и так держит ACCESS EXCLUSIVE — конкурентных записей в окне нет. Содержимое строк не меняется |
| NULL-остаток после backfill на проде | Ожидается малым (см. §2); остаток виден владельцу отчётом; такие строки видны только своей организации через прежние цепочки, чужой — никогда |
| Порядок деплоя | Код Phase 1 читает новые колонки ⇒ **сначала миграция, потом код** (§6). Старый код с новой схемой совместим (колонки nullable) — откат кода без отката миграции безопасен |
| Производительность | 4 новых btree-индекса; фильтры точечные; на Luxx-объёмах незаметно |
| Channex/OTA | ARI-worker (`pendingOutbox`) не фильтровался и не фильтруется — отправка остатков не меняется; вебхук пишет события как раньше (плюс штамп объекта) |

3) Деплой кода Phase 1 (только ПОСЛЕ шага 2) — обычным порядком.

5) ROLLBACK (если что-то не так):
   a. Откатить код на пред-Phase 1 (новые колонки старому коду не мешают — можно оставить схему);

## 7. Подтверждение неизменности Hospitality-поведения

- Ни одна `Reservation`/`Payment`/`InventoryUnit`/`RatePlan`/`ChannelMapping` не меняет ID и содержимое (миграция их только читает).
- Стойка Luxx: гости/журнал/каналы видны как раньше (колонка+fallback-цепочки; полные наборы тестов зелёные — строки журнала в этом же коммите).
- UI/UX/маршруты/навигация не менялись; полный локальный `e2e` прогнан на коде Phase 1 (см. §4 — свежая строка журнала, не ссылка на прежний прогон).
- Сверки Luxx: то, что backfill не пишет в таблицы сверяемых сущностей, — обоснование низкого риска, **но не замена сверки** (приёмка владельца 27.09.2026): фактические контрольные показатели снимаются владельцем ПОСЛЕ применения миграции на рабочей базе (§6, шаг 4c) и являются условием закрытия Phase 1 вместе с отчётом backfill без неожиданных неоднозначных строк.
