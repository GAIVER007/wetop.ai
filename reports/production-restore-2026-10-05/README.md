## Разрешённый контур

Владелец разрешил свежую production-копию и восстановление в защищённой изолированной PostgreSQL 17. Использована процедура `docs/ops/backups.md`: каталог `/root/backups` на существующем сервере WETOP, права 700, dump 600. Персональные данные не копировались на Mac, в Git или на новый сервер. Восстановленный кластер находился только в tmpfs временного Docker-контейнера на том же сервере.

Контейнер PostgreSQL: версия 17.11; production: 17.6. Проверка выполнена на той же основной версии 17, но не на идентичной patch-версии. Для CLI Prisma использовалось то же изолированное сетевое пространство с loopback 127.0.0.1. Приложения, боты, cron и обработчики внешних событий не запускались, production-секреты в тестовый контур не передавались. wetop_app специально создана NOLOGIN; пароль production не копировался.

### Объяснение сырых отличий каталога

В comparison.json исходные сравнения columns/constraints/enums/roles отмечены equal=false. Они не скрыты:

1. PostgreSQL при восстановлении убирает дырки физических ordinal_position от прежних DROP COLUMN. Относительный порядок, определения и содержимое колонок сохранились.
2. MembershipRole имеет тот же порядок OWNER, MANAGER, STAFF. Внутренние enumsortorder 1, 1.5, 2 стали 1, 2, 3.
3. Четыре CHECK на seller_agents и seller_booking_intents после разбора PostgreSQL 17.11 показывают преобразование varchar-массива в text через каждый элемент вместо приведения целого массива. Оба выражения сравнены на комбинациях разрешённых значений, посторонних значений, пустой строки, NULL и пустого/заданного location_id. Для каждого ограничения 0 различий, constraint-equivalence.tsv. Условия и статус validated сохранены.
4. wetop_app в тестовом кластере NOLOGIN вместо production LOGIN. Это сознательная изоляция, эффективные права и NOBYPASSRLS совпадают. Production-пароль не переносился.

## 052 и документированное расхождение checksum

Использованы точные schema.prisma и каталог миграций из Git archive `a5c5050c`. Перед deploy Prisma корректно сообщила одну ожидающую 052, код status 1. Затем штатный migrate deploy применил только `20261004000052_onboarding_progress`, checksum `b8566ad5c85ce6b8ad22a7cf3b6eaf1c06a6053af0cb643cfb0c8aee1a8b4e9a`, и завершился кодом 0. После status код 0.

Штатная процедура на восстановленной копии не блокируется расхождением 035/036/039. Исключение, изменение файлов, checksum/history, reset или resolve не потребовались. Успешный Prisma status сам по себе не доказывает идентичность старых файлов: исторический checksum drift остаётся явно зафиксированным в отдельном аудите.

У 052 проверены RLS и tenant-политика; wetop_app имеет SELECT/INSERT/UPDATE. Тестовый черновик создан только у синтетического объекта в восстановленной копии. down.sql начал транзакцию, увидел непустую таблицу и отказался удалять её. Новое подключение подтвердило сохранение таблицы и JSON.
