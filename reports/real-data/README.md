# Frontend → backend → Supabase

14 сентября 2026, рабочая копия WETOP. **Подключение к живой Supabase в этом запуске ещё не подтверждено:** в начале работы отсутствовали `.env` и `DATABASE_URL`, API на 3001 не был запущен. В браузере работал отдельный `dev:demo`. Создан приватный локальный шаблон `.env` без значений; данные подключения должен добавить владелец.

## Что изменено

- Новый `GET /system/connection` читает объект гостиницы и агрегаты существующих таблиц. Проверка отделяет доступную БД с данными, отсутствие объекта и отказ базы. Ошибка не подменяется нулями. Запросы не возвращают гостевые данные, идентификаторы, строку подключения или текст ошибки драйвера, не выполняют запись и не вызывают провайдеров.
- На `/connections` добавлена панель «Данные проекта»: источник, состояние базы, гостиница, часовой пояс, валюта, количество единиц/категорий/броней/тарифов/услуг/сайтов. Channex проверяется отдельно. Fixture всегда отображается как тестовый или демонстрационный источник, не как подключённый Supabase.
- Каркас, мобильная навигация, меню рабочего места и обзор дня берут название гостиницы из backend. При ошибке показано «Объект не загружен». Suspense ограничен текстовыми слотами: поздний ответ не заменяет каркас, не стирает заполненную форму и не закрывает меню. Это доказано сценарием с удержанным ответом API (сначала тест воспроизвёл потерю ввода). Чтение сведений объединяется React.cache в пределах одного серверного запроса; между запросами кеша нет. Часы обзора используют часовой пояс объекта из API.
- `npm run dev` запускает обычный frontend вместе с backend, проверяя базу перед запуском frontend. Если указан `APP_API_URL`, используется уже работающий backend. Неподтверждённый/demo/test источник отклоняется. Ключи корневой `.env` не передаются в окружение Next.js новым launcher, кроме явно выбранного адреса API; унаследованные серверные переменные процесса остаются серверными. В browser bundle DB/Channex credentials не добавлялись.
- `npm run check:connection` выполняет только GET-проверку существующего backend и заканчивается с кодом 1 при отказе. HTTP 200 диагностического endpoint сам по себе не означает готовность: нужны `source=database`, `state=READY`, `database.connected=true`.

Существующая цепочка данных сохранена: **Next.js/server actions → NestJS → Prisma → PostgreSQL/Supabase**. Схема БД, бизнес-правила, деньги и API-команды не изменялись. Прямые запросы из браузера к Supabase не добавлялись.

## Чего одно подключение базы не включает

В существующем backend не реализованы авторизация/сотрудники/роли, доставка и постоянное хранение переписок, акции/промокоды, загрузка фото и редактирование удобств, редактор каталога услуг, рекламные рассылки/лояльность. Для них нет готовых API и утверждённой реализации моделей. Они не объявляются подключёнными и не заполняются фиктивной статистикой. eQonaq и фискальные провайдеры также остаются вне текущего подключения.

Dev-база проекта по документации содержит псевдонимы гостей (ADR-018). Подключение к ней не преобразует псевдонимы в настоящие ФИО. Достоверность и свежесть бронирований зависят от имеющегося импорта/Channex и требуют отдельной живой сверки после получения доступа.

## Запуск на этой или другой машине

1. Получить актуальный репозиторий, установить зависимости, сгенерировать клиент: `npm ci`, `npm run generate -w packages/database`. Генерация клиента не применяет миграции.
2. Владелец добавляет строку существующей базы в корневой `.env`: `DATABASE_URL`. В Supabase строка находится в **Connect → Session pooler**, порт 5432 для такого серверного приложения; используйте существующие учётные данные проекта. [Официальная инструкция Supabase](https://supabase.com/docs/guides/database/prisma). Не создавать новые роли/таблицы по примерам инструкции, не сбрасывать пароль и не запускать migrate/seed для подключения UI.
3. Выполнить `npm run dev`. Новый launcher выключает фоновые `CHANNEX_PULL`, `CHANNEX_OUTBOX_WORKER`, `CHANNEX_FULL_SYNC`, `CHANNEX_WEBHOOK_HEALTH`, `GUARD` и `GUARD_AUTOFIX`. Он не включает туннель и не меняет существующую операционную настройку launchd/API. Существующие ручные команды UI остаются доступны: это не принудительный read-only режим всего приложения и не OTA cutover.
4. Если backend уже работает, указать `APP_API_URL` в корневой `.env` (HTTPS для удалённого API, HTTP допускается для loopback), затем `npm run dev`. Локальный API тогда не создаётся; настройки фоновых задач удалённого процесса не меняются.
5. Открыть `/connections`: должны отображаться **«База проекта»**, **«Supabase подключён»** и данные своего объекта. `npm run check:connection` должен завершиться кодом 0. Проверка выполняется только по текущему состоянию базы, не по наличию ключа.

При отдельном запуске `npm run dev -w apps/web` Next читает `apps/web/.env.local` либо окружение процесса. Корневую `.env` в этом случае загружает только новый общий launcher. Секреты не передаются через Git: получение обновлённого дизайна с другой машины не переносит доступ к БД автоматически.

До решения авторизации приложение по-прежнему слушает loopback. Эта работа не публикует локальные административные API в интернет.

### Review

Проверены корректность, читаемость, границы модулей, безопасность и влияние на загрузку. Новый контракт ограничен диагностикой; БД-фильтр объекта совпадает с существующими repository. Новые запросы не загружают гостевые строки и не выполняют мутаций. Ожидание метаданных изолировано от интерактивного дерева, чтение сведений объединено в рамках серверного запроса. Публикация API, роли, миграции, OTA cutover и финансовые изменения не добавлялись. Нагрузочный тест Supabase и многопользовательские операции в этом прогоне не подтверждены.

### Зависимости

`npm audit` сохранён в [dependency-audit.json](dependency-audit.json): 9 high, 2 moderate, 0 critical с учётом транзитивных цепочек. Зависимости и lockfile этим изменением не обновлялись. Автоматический `audit fix --force` предлагает несовместимый откат Nest/Prisma, поэтому не выполнялся.

Проверка достижимости по установленному дереву (`npm ls`) и коду:

- `multer` находится в Nest platform-express; в API нет upload interceptors/MulterModule или multipart upload handlers. Уязвимые сценарии обработки загрузок не вызываются новыми endpoint/запуском.
- `deepmerge-ts` — конфигурация Prisma CLI с доверенным локальным объектом; рекурсивные графы пользовательских запросов туда не передаются.
- `mysql2` и `lodash` входят в Prisma CLI/Studio; текущий runtime использует PostgreSQL adapter, Studio в этом запуске не поднимается. Новый UI не вызывает MySQL protocol, `_.template`, `_.unset` или `_.omit`.
- `uuid` используется ExcelJS через `v4`; advisory касается v3/v5/v6 с переданным буфером. Таких вызовов в пути текущего приложения не найдено.

Достижимого в добавленном потоке high-вектора не найдено. Это не утверждение, что весь набор зависимостей безопасен: обновление дерева и оценка дополнительных CLI/Studio/upload-сценариев остаются отдельной работой. Нельзя сообщать, что `npm audit` зелёный.

## Что требуется для живой приёмки

Настроенный `DATABASE_URL` или адрес существующего backend этого проекта. После этого: подтвердить `READY`, сверить агрегаты БД с UI на одной дате, открыть существующие карточки без вывода ПД в отчёт, проверить отсутствие ошибок API. Запись, оплата, импорт и OTA cutover не являются частью безопасной проверки подключения. До выполнения этой приёмки считать работу с живыми данными подтверждённой нельзя.
