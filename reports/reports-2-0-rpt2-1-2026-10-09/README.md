## 1. Что есть сейчас

Единого движка отчётов нет. `/reports` это хаб из карточек: каждая берёт живое число из того же API, что и целевой
экран, и ведёт туда со своим периодом. Настоящая аналитика лежит в `/management/analytics`, деньги в `/finance`.

| Экран | Что делает | Период и фильтры | Предел |
|---|---|---|---|
| `/reports` | хаб карточек | `from`, `to`; 4 пресета; без филиала, источника, категории, сравнения | 366 дней |
| `/management/analytics` | Обзор, Загрузка, По номерам, Каналы | пресеты, `fund=all/rooms/beds`, `compare` (по умолчанию вкл.), у каналов `channel`, `sort`, `cfrom/cto` | 366 дней |

| `/reports/form-910`, `/reports/print` | форма 910 по полугодиям, печать дня | `year`+`half`; `form`, `date`, `lang` | |

Права: одно право `reports` (OWNER, MANAGER, STAFF). Отдельного «финансового» права нет, деньги, долги и форма 910 идут
под тем же `reports`. `GET /desk/dashboard` держится на `desk`, то есть Обзор и Загрузка отдаются и без `reports`, но вкладки
в меню под `reports`. `GET /finance/cash` и `GET /bar/report` тоже `desk`.

Выбор филиала: куки `wetop_scope`, внутри отчёта фильтра «филиал» нет. `GET /branches/overview` собирает только
гостиничные филиалы, без итога по организации, салон и ресторан сознательно не входят (решение владельца от 06.10).

ИИ-аналитики для владельца в коде нет. `apps/api/src/assistant` это поддержка, финансов и дашборда он не читает.

## 3. Расхождения и дефекты (по тяжести)

### 3.1 Формульная инъекция в CSV, защиты нет (безопасность)
`apps/web/src/app/finance/csv.ts` `csvField` берёт в кавычки только поля с `;`, `"`, CR, LF. Значение, начинающееся с
`=`, `+`, `-`, `@`, не нейтрализуется. Уязвимые поля: `note` и `category` в выгрузке операций. Тестов нет. Требование ТЗ п. 9.
Отрицательные суммы начинаются с `-` намеренно, поэтому защита должна применяться к текстовым колонкам, не к суммам.

### 3.2 Выручка бара на счёт выпадает из отчётов
`bar.repository.ts` при продаже на счёт создаёт `Charge` kind SERVICE без `serviceDate` (в `create` поля нет). Все периодные
отчёты фильтруют начисления по `serviceDate`, поэтому такая выручка не попадает ни в `/finance/report`, ни в
`/finance/services-report`, ни в дашборд, ни в выбор броней для долгов, но входит в остаток счёта. Долг считается с ней, выручка нет.
Это финансовая логика: исправление только через решение владельца (AGENTS §15), вопрос в п. 6.

### 3.4 Формулы по требованиям ТЗ

| Требование ТЗ | Как сейчас | Статус |
|---|---|---|
| Occupancy = занятые / доступные единицы-ночи | занято: размещения не CANCELLED/NO_SHOW; знаменатель: активные единицы × дни, **блокировки не вычитаются** | расходится: ТЗ просит «доступные к продаже», нужно решение по блокировкам и out-of-order |
| Не смешивать room-nights и bed-nights | при `fund=all` номер и койка по 1 единице в одном знаменателе | **нарушает требование ТЗ**, нужно решение |
| ADR | есть, только в дашборде | частично |
| RevPAR | есть, только в дашборде | частично |
| Начисленная выручка по дате услуги | финансы да; Обзор и Каналы по заезду | расходится (п. 3.3.1) |
| Поступления по дате платежа | `paidAt` в сутках объекта, COMPLETED | есть |
| Возвраты отдельным показателем | одна сумма, без способа и причины | частично |
| Долги на дату | только остаток «сейчас», aging нет | нет |
| Расходы по категориям | только сумма за период | нет |
| Денежный поток по дням | нет, остатки только «сейчас» | нет |
| Остатки по способам на дату | только текущие | нет |
| Прибыль | только валовая у бара | не показывать (как требует ТЗ) |
| Отмены | счётчик по броням с заездом в периоде, даты отмены нет | частично |
| Гости | сумма взрослых и детей, уникальных и повторных нет | частично |

Деньги везде integer minor units (`bigint`, наружу строкой), float в денежных расчётах не найден. Часовой пояс берётся из
`Property.timezone`, жёсткого +5 в запросах нет. Это соответствует AGENTS §12 и §13.

## 5. Производительность

- Индексов по `charges.service_date` и `refunds.created_at` нет (`charges` и `refunds` индексированы только по `folio_id`).
- Отчёты выручки читают все начисления периода в память и суммируют в JS; дашборд делает это дважды (период и предыдущий).
- `/finance/cash` каждый раз агрегирует платежи и возвраты за всё время.
- `/branches/overview` последовательно вызывает полный дашборд на каждый филиал; экран салона и ресторана делает запрос на каждый день.
- RLS по организации, по филиалу RLS нет: филиал отсекается только прикладным кодом (риск для «Location Manager»).
- Кеширования отчётов нет.
- Любая новая индексная миграция требует решения и применяется владельцем.
