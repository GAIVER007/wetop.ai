Помимо времени, детерминированные проверки удерживают ответ настроек до явного
освобождения: заголовок/KPI/стойка уже видны. Запрос шахматки начинается до ответа
дня. Отказ дня показывается, даже если шахматка всё ещё ждёт. Опрос свежести не
перекрывает сам себя; после 503 восстанавливается. При размонтировании fetch отменяется.

## Рабочий API и ограничения

До правки: `DATABASE_POOL_MAX=1 npx tsx scripts/ops/cli-slow.ts --passes=3 --no-db --no-desk`.
Только чтения из рабочей dev-базы, никаких созданий гостей/броней/платежей, никаких
внешних команд Channex/Exely. Медианы: шахматка 14 дней 2,5 с, месяц 2,4 с,
стойка 2,0 с, месячный dashboard 8,3 с, брони 7,2 с (1,8–9,1 с), фонд 334 мс,
тарифы 341 мс, настройки 4 мс после холодного обращения 3,2 с.

На машине 8 ГБ RAM, 8,7 ГБ swap, load 12,1 при 8 ядрах. Скорость SQL и расчёта
месячного отчёта этой правкой не менялась: ускорена выдача независимых блоков и
устранена дублирующая нагрузка. Пул соединений не увеличивался. Быстрое открытие
каркаса не означает мгновенное завершение тяжёлого отчёта. Нагрузочный тест
production и полевые Core Web Vitals не выполнялись.
