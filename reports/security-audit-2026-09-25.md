# Аудит безопасности и проблемных мест — 25.09.2026

Полный «шпионский» разбор репозитория по поручению владельца: уязвимости, ошибки, проблемные места,
вес каждой находки и как исправить. Ветка `claude/youthful-hypatia-i0v104`, дерево на `main` (`1cbd2e9`).

**Как проверялось.** Шесть параллельных проходов только на чтение: API платформы (`apps/api`,
`packages/*`), боты (`apps/ai-seller`), деплой и эксплуатация (`deploy/`, `scripts/ops/`, CI),
фронтенд (`apps/web`, `apps/site`, виджеты), слой данных (`schema.prisma`, 22 миграции,
`packages/integrations`), гигиена репозитория (история git, `.gitignore`, ПД в файлах).
`.env`, `secrets/` и выгрузки `project-input/retired-source/` не открывались (SECURITY.md §3).
Самые серьёзные находки перепроверены по коду вручную (цитаты сверены с файлами).

**Главный вывод.** Критических дыр (готовый удалённый взлом без предусловий) нет. Код written
дисциплинированно: деньги — BIGINT-тиыны без float, овербукинг запрещён exclusion-constraint'ом в базе,
секреты сравниваются за постоянное время, XSS-гигиена на фронте и в виджетах образцовая, SQL-инъекций
не найдено, секретов в git-истории нет. Но есть **6 находок высокого веса** — одна даёт прямой обход
пароля, остальные пять означают, что компрометация одного звена (почтового ящика, права push,
переменной окружения) обходит всю остальную защиту.

## Высокий вес — разбор и исправления

### В-1. Ссылка подтверждения почты — вечный вход без пароля ⚠️ чинить первой

`email-verification.service.ts:101-105`: повторный переход по **уже использованной** ссылке
принимается, если почта подтверждена, — и контроллер (`auth.controller.ts:76`) на этот результат
**открывает новую сессию**. `verifyState` (`packages/domain/src/accounts/email-verification.ts:23`)
проверяет `usedAt` раньше срока, поэтому для использованной ссылки 72-часовой срок не проверяется
вообще. В этой ветке нет и проверки `status === 'BLOCKED'`.

**Сценарий.** Письмо о регистрации лежит в ящике годами. Любой, кто получит доступ к ящику
(компрометация почты позже, пересланное письмо, прокси, журналы ссылок), входит в стойку без пароля,
бессрочно. Смена пароля и «выйти везде» отзывают сессии, но ссылку не гасят — постоянный обход
пароля и локаута.

**Исправление.** Ветку «used + verified» превратить в ответ «почта уже подтверждена, войдите
паролем» без `startSession`. Сессию открывать только при `state === 'active'`. Если нужна
дружелюбность к почтовикам, которые сами ходят по ссылкам, — разрешить повтор в коротком окне
(10 минут после `usedAt`) и всё равно проверять `expiresAt` и `status`.

### В-2. Замок API fail-open

`auth.guard.ts:97`: `const required = process.env.AUTH_REQUIRED === '1'` — любое иное значение
(опечатка `true`, пустая переменная, новый стенд без строки в compose) молча открывает весь
непубличный API: гостей, финансы, брони. То же у стойки: `apps/web/src/lib/session.ts:19`.
Смягчение уже есть: `deploy/compose.yml:72` ставит `${AUTH_REQUIRED:-1}`, «Платформа» и
`/assistant/errors` сверяют доступ сами. Но вся защита held одной строкой compose.

**Исправление.** Fail-closed: `required = env !== '0'` — замок включён всегда, выключается только
явным нулём. Либо при `NODE_ENV=production` и невключённом замке — отказ старта или неисправность
сторожа + баннер в стойке.

### В-3. Автовыкладка: ветка `release` = root-исполнение без проверки источника

`auto-deploy.sh:87-137`: cron root каждые 2 минуты собирает и запускает **любой** коммит, оказавшийся
вершиной `origin/release`: ни подписи, ни проверки автора, ни сверки с зелёным CI на стороне сервера.
`docker compose up --build` исполняет `compose.yml` и `Dockerfile` из этого же коммита — произвольные
тома и команды с root. `merge-base --is-ancestor` защищает только от перемотки назад.

**Сценарий.** Компрометация любого credential с правом push (токен агентской сессии, ключ владельца,
самозахват через CI-раннер — В-4) → push в `release` → через ≤2 минуты произвольный код с root на
сервере с боевой базой и ключами Channex/Telegram.

**Исправление.** GitHub branch protection на `release` (push — только владельцу); лучше — проверка
подписи (`git verify-commit`) или сверка SHA с зелёным check-run через API перед `checkout`.

### В-4. Self-hosted CI-раннер исполняет код любого PR на боевом сервере

`checks.yml:7-10,22,110`: триггер `pull_request` без фильтра + `runs-on: [self-hosted, …]` — любой PR
(коллабораторы и агентские сессии) исполняет произвольный код (`npm ci` → postinstall, тесты) на
сервере рядом с боевой стойкой. Смягчения хорошие: docker-сокета нет, лимиты памяти/CPU,
`no-new-privileges`, `pull_request_target` не используется, `${{ }}`-инъекций нет. Но раннер имеет
исходящий интернет (эксфильтрация, майнинг) и видит хостовую сеть.

**Исправление.** Settings → Actions: требовать approve для запусков workflow; label-gate на
self-hosted джобы; в связке с В-3 — это и есть путь самозахвата `release`.

### В-5. ПД гостя в журнале аудита — против собственного правила «Без PII в логах»

`reservation-card.ts:38-45` — карточка содержит `label` («Имя Фамилия») и `phone`; комментарий на
строке 53 прямо говорит «Карточка брони для стойки **и для AuditLog**»; `audit()` кладёт
`before`/`after` как есть (`reservations.repository.ts:1292-1303`). Сейчас гости псевдонимизированы
(`PII_STORAGE ≠ real`) — в журнале «Гость Канал-a1b2c3». Но после переезда в РК настоящие ФИО и
телефоны потекут в `audit_logs`, и **тем же шагом переезда** вводится
`deploy/sql/audit-append-only.sql` — ПД в журнале станут неудаляемыми. Конфликт с правом на удаление
ПД и с собственной моделью (номер и даты документа шифруются, журнал — нет).

**Исправление — обязательно ДО `PII_STORAGE=real`.** Редактирующая проекция карточки для журнала:
`guestId` вместо `label`, маска телефона (`maskNumber` уже есть в `pii-crypto.ts:44`); либо шифровать
`before`/`after` тем же `PII_ENCRYPTION_KEY`.

### В-6. Единственная незашифрованная копия базы на том же сервере — известный Q-073

Подтверждаю как главный эксплуатационный риск: в дампах хеши паролей и почты сотрудников, копия одна,
на той же машине, без шифрования. Потеря/компрометация сервера или аккаунта Hostinger = потеря базы
и утечка разом. **Исправление** уже описано в `docs/ops/backups.md` (вариант Б: R2/диск владельца) —
одна строка в cron после `db-backup.sh` + шифрование `age`/`gpg -c` перед отправкой; ключ — не на
этом сервере. Решение за владельцем.

## Средний вес — разбор по областям

### Деньги и брони (данные + API)

- **С-2. Гонка возвратов** (`finance.service.ts:584-605`): проверка предела — чтением, вставка —
  отдельной транзакцией. Два одновременных `POST /finance/payments/:id/refunds` оба проходят
  проверку → суммарный возврат больше платежа. *Исправление:* `pg_advisory_xact_lock` по `paymentId`
  (образец уже есть в `reservations.repository.ts:567`) + повтор проверки в транзакции.
- **С-3. Блокировка × бронь** (`units.service.ts:72-86`): exclusion-constraint запрещает только
  allocation×allocation; пересечение с `inventory_block` не запрещает ничто — гость назначается
  в ячейку, закрытую на ремонт. *Исправление:* тот же advisory-lock категории в `block()` +
  проверка и вставка одной транзакцией.
- **С-4. Нет `UNIQUE(property_id, external_id)`** (`schema.prisma:217`): защита от дубля ручной
  OTA-брони — только check-then-act в коде; тот же столбец без индекса сканируется на каждой ревизии
  Channex. *Исправление:* одна миграция — частичный уникальный индекс
  `WHERE external_id IS NOT NULL`; закрывает обе беды.
- **С-14. Ни одного CHECK на деньги** (миграция `20260909000006`): отрицательный `payments.amount`
  или `Σ allocations > payment` база примет; журнал аудита сегодня можно `UPDATE/DELETE` любым кодом
  с DATABASE_URL (append-only отложен до РК — ADR-082, но окно можно сузить дёшево). *Исправление:*
  CHECK'и `amount > 0` на payments/allocations/refunds + триггер
  `BEFORE UPDATE OR DELETE ON audit_logs … RAISE EXCEPTION` (работает и с одной ролью).
- **С-13. UTC+5 захардкожен в 11 местах** (`almatyToday` и копии): от «сегодня» зависят штрафы
  (`penaltyDue`), досрочный выезд, отмены каналов. Для Luxx верно; платформа уже мультитенантна
  (§16) — первый объект не в UTC+5 получит штрафы в чужой час. *Исправление:* одна функция
  `todayAt(property.timezone)` через `Intl.DateTimeFormat`, 11 копий заменить.
- **С-7. Спам публичной брони** (`web-booking.service.ts:289`): Origin вне браузера ставится
  свободно, лимиты — в памяти процесса. Скрипт с ротацией IP создаёт до 30 настоящих броней в час,
  дельты уезжают в Channex → фальшивые брони закрывают продажи в OTA (denial of inventory).
  *Исправление:* лимиты в базе + дедуп по телефону/почте + алерт сторожа на всплеск + автоснятие
  неподтверждённых.
- **С-5/С-6. Локаут и лимиты в памяти**: `failedAttempts` пишется вычисленным значением — параллельные
  попытки размывают порог 5/15 мин; `windows.clear()` при 20 000 ключей сбрасывает все счётчики
  разом; `lastSent` растёт вечно. На login/register/reset/resend нет IP-лимитов вовсе (открытая
  регистрация создаёт организации без ограничений). *Исправление:* атомарный
  `UPDATE … SET failed_attempts = failed_attempts + 1 RETURNING`; вытеснять только протухшие окна;
  окно по IP на четыре маршрута.

### Боты (ИИ-продавец / ИИ-помощник)

- **С-8. `X-Organization` выбирает вызывающий** (`auth_router.py:328-347`): у панельной учётки бота
  нет `organization_id`, у служебного актёра тем более — держатель одного `SELLER_SERVICE_KEY` или
  одна учётка панели читает телефоны и переписку клиентов **всех** гостиниц, меняя заголовок. Через
  платформу изоляция держится (org из сессии), но один утёкший ключ раскрывает всех арендаторов.
  *Исправление:* per-org ключи или HMAC-подписанный платформой org-контекст; панельные учётки
  привязать к организации.
- **С-9. RLS мёртв и неполон** (`0002_organizations.py:195-208`): бот подключается владельцем таблиц
  (обходит политики), `app.org_id` кодом нигде не ставится (включение RLS молча *сломает* продавца,
  а не защитит), `messages`/`chunks`/`owner_actions` — без политик вовсе. *Исправление:* при переходе
  на непривилегированную роль — `SET LOCAL app.org_id` в каждой транзакции,
  `FORCE ROW LEVEL SECURITY`, политики на messages через EXISTS.
- **С-10. Нет бюджета токенов LLM** (`config.py:155`): лимиты только 60/час на ключ и IP; токены
  считаются в `messages.tokens_used`, но предела «в сутки на организацию» нет — распределённая атака
  по публичному `sk_` конвертируется в счёт за LLM. *Исправление:* суточный счётчик на организацию
  и экземпляр, алерт, вежливая деградация.
- **С-11. Реальный IP не гарантирован** (`ip_block.py:62-67`, `Dockerfile:57` без
  `--forwarded-allow-ips`): в зависимости от конфигурации nginx клиентский X-Forwarded-For либо
  подделывается (обход per-IP лимитов; через страйки инъекций — блокировка ЧУЖИХ IP), либо не
  пробрасывается вовсе (все посетители делят IP nginx — три страйка одного хулигана блокируют виджет
  всем на час). *Исправление:* зафиксировать в выкладке и проверить тестом: nginx ставит
  `X-Forwarded-For $remote_addr` перезаписью, gunicorn — явный `--forwarded-allow-ips`.

## Низкий вес (кратко)

**API:** ключ ПД принимает слабую фразу молча и без AAD — шифртексты переставимы между строками
(`pii-crypto.ts:15-28`; AAD = id документа); CORS `/w/*` объединяет домены всех сайтов
(`web-booking.module.ts:60-69`); кука на `.wetop.ai` доступна любому поддомену (`cookie.ts:44-55`);
парольная политика минимальна — `aaaaaaaaaa` проходит (`password.ts:28-34`, Q-140 открыт); ответ о
локауте называет точное время разблокировки; нет CSP/helmet на HTML от API; общая песочница
`…-service` для анонимных проверок.

**Боты:** сравнение `sk_` не в постоянном времени (SQL-lookup — практически неэксплуатируемо);
`Host`-заголовок как «свой адрес» (сверять с `PUBLIC_BASE_URL`); утечка системного промпта LLM
выходным фильтром не ловится (ущерб мал — свободного текста в промпте нет намеренно); `lead_data`
из модели может донести HTML до панели платформы (React экранирует — проверено, чисто);
fail-open лимитов при падении Redis (осознанно); long-poll и вложения без квот диска; переписка
и ПД клиентов бота — открытым текстом в его базе и в бэкапах (зафиксировать политику хранения).

**Фронтенд:** блог — `marked` без санитизации + `dangerouslySetInnerHTML` (контент из репозитория,
но любой `<script>` в принятом PR = stored XSS на wetop.ai); `org=${…}` в ссылке техподдержки без
`encodeURIComponent`; счётчик аналитики шлёт полный `location.href` — ПД из query сайта осядут в
аналитической БД (слать `origin + pathname`); `visitor_key` чата в query string (перенести в
заголовок, как уже сделано для identity); identity-подпись в DOM-атрибуте (принято осознанно).

**Данные:** down.sql миграции `20260925000021` при откате теряет даты документов (документировано,
документов 0; добавить защёлку `RAISE EXCEPTION` при непустых датах); спаривание комнат ревизии по
индексу массива (`inbound.service.ts:906-935`) — при другом порядке от канала истории folio
спутаются; дедуп не-booking событий нестоек к повтору с другим timestamp; индексы шахматки не
покрывают диапазоны дат (пока незаметно); `Math.round(Number(price)*100)` в онбординге — единственный
float на пути денег (заменить на `decimalToMinor`); `payment_allocations` удаляются физически без
сторно; каскад удаления организации уносит `user_errors`, сайта — всю веб-аналитику (осознать в UI).

**Деплой:** regex-ингресс помощника пропускает `/widget/../…` до бота (сузить до
`^/widget/[A-Za-z0-9._-]+$`); наивный разбор `.env` в shell-скриптах (хвостовой комментарий ломает
значение молча); нет замка между автовыкладкой и ручной сборкой; `set -a; . ./.env` исполняет `.env`
как shell; тарбол CI-раннера без sha256; cloudflared без healthcheck; `audit-append-only.sql` — только
GRANT без триггера (признано в файле).

## Что сделано хорошо (не чинить)

Деньги — всюду BIGINT-тиыны, float на серверных путях денег нет; овербукинг запрещён физически
(EXCLUDE USING gist); внешние события идемпотентны (`UNIQUE(provider, external_event_id)`, retry с
потолком, backoff исходящей очереди); секреты сравниваются `timingSafeEqual`/`compare_digest` везде;
сессии — случайные 32 байта, в базе только SHA-256, scrypt с decoy-хешем; IDOR закрыт «по построению»
(`propertyRef`, фильтр организации во всех выборках, подтверждено тестом изоляции бота); SQL-инъекций
нет (все raw — тегированные шаблоны); XSS-гигиена образцовая (виджеты только `createElement`/
`textContent`, закреплено тестом); маскировка ПД до LLM и в журналах; порты наружу не публикуются,
`wetop-internal` действительно internal, `no-new-privileges` + `USER node`; `.env` вне образа; дампы
600 с проверкой восстановления; Channex production закрыт флагом; секретов в git-истории нет.
