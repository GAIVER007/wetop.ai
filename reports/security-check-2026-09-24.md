## 2. Исправлено сразу

Каждое исправление — одна функция или строка, каждое сначала красное.

**И1. Лимит броней с сайта считал всех посетителей одним адресом (§11).**
- `clientIp` (`apps/api/src/web-booking/client-ip.ts`) брал `CF-Connecting-IP` только от loopback. Это правило писалось
  для Mac, где туннель и API на одной машине.
- На сервере туннель — соседний контейнер сети compose (`deploy/compose.yml`), его адрес 172.x. Заголовок
  отбрасывался, и все посетители сайта шли одним адресом cloudflared.
- Итог: «5 броней в час с одного адреса» стало «5 броней в час на весь интернет», шестая настоящая бронь за час
  получала 429. Для проекта, где «ни одна бронь не потеряна», это дефект, а не мелочь.
- Теперь заголовок принимается от loopback и частных сетей (10/8, 172.16/12, 192.168/16, fc00::/7). Порты API наружу
  не публикуются, так что с частного адреса до API достают только свои службы. С публичного адреса заголовок
  по-прежнему не принимается.
- Red `…09-11-40Z-unit-b942.log` (получено `172.18.0.4` вместо адреса посетителя) → green `…09-11-54Z-unit-1be7.log`,
  вместе с прежними тестами виджета — 16/16.

**И2. `npm run db:local` мог молча накатить миграции на рабочую базу (§8, AGENTS §14).**
- `packages/database/prisma.config.ts` берёт `DIRECT_URL || DATABASE_URL` и дочитывает `.env` корня, не перетирая
  уже заданное.
- `local-db.sh` задавал только `DATABASE_URL`, поэтому `DIRECT_URL` из `.env` перебивал локальную базу.
- Вывод `migrate deploy` уходит в `/dev/null`: новая миграция из ветки встала бы на рабочую базу без бэкапа, и никто бы
  этого не увидел.
- Есть ли `DIRECT_URL` в `.env` на Mac, агенту не видно. План 13.09 предлагал `TEST_DIRECT_URL` рядом.
- Теперь скрипт задаёт `DIRECT_URL` той же локальной базой. Red `…09-11-16Z-unit-4a7d.log` (миграции ушли на адрес
  из «.env») → green `…09-11-25Z-unit-fe8b.log`.
- Живьём: база для integration и e2e ниже поднята исправленным скриптом.

**И3. Адрес почты в тексте ошибки отправки (§11: «адрес получателя не попадает в тексты ошибок»).**
- `resend.ts` прятал только ключ, а сообщение Resend переносил дословно. Сам Resend называет в нём адреса — например,
  адрес владельца аккаунта в тестовом режиме.
- Текст ошибки пишется в журнал API (`accounts.service.ts`).
- Теперь любой адрес заменяется на `<почта>`. Red `…09-12-20Z-unit-172c.log` → green `…09-12-33Z-unit-caec.log`.

**И4. Маскировщик логов тестов не знал соль обезличивания и куку сессии (§3).**

## 3. Находки, которые без решения не чинятся

### Н1. Ревизия Channex хранится целиком — с данными заказчика (высокая, §2, ADR-018)

- `sanitizeRevision` (`apps/api/src/channels/inbound.service.ts:62`) удаляет только `guarantee`.
- `payload: sanitized` (`:515`) кладёт в `external_events.payload` всё остальное:
  - `customer` — имя, фамилию, телефон, почту, адрес, город, индекс, страну;
  - `rooms[].guests[]` — имена;
  - `notes`.
- Это не зависит от `PII_STORAGE` и ничем потом не удаляется. Код знает об этом сам (`revision-facts.ts:3`).
- Тест ADR-018 проверяет только строку в `guests`.
- Утверждённый DATA_MODEL §8 колонки `payload` не содержит — она добавлена при реализации (`DATA_MODEL.md:705`).
- События, кроме броней, пишут тело webhook без разбора (`inbound.service.ts:201`). Сейчас подписка — только `booking`,
  в её теле одни номера.

**Сейчас.** Через Channex идут только тестовые брони staging. Первый канал, подключённый через Channex production,
начнёт писать настоящие имена и телефоны в базу в Сингапуре.

**Что можно сделать.** Хранимую ревизию читают только факты для экрана и поиск по `unique_id` и `ota_name`. Повтор
забирает ревизию из Channex заново (`inbound.service.ts:473-476`). Значит, ПД можно вырезать, ничего не сломав.

**Блокер подключения первого канала** — план П1.

### Н2. Свободный текст пишется как есть (средняя, §2) — Q-169

- **Заметка канала:** `notes: a.notes ?? null` (`inbound.service.ts:742, 818`; связывание — `:338`). У Channex это
  «Customer notes for booking». Импорт Exely такие заметки стирает именно из-за ПД (`anonymize.ts:58`), приём Channex —
  нет.
- **Комментарий гостя с сайта:** `web-booking.service.ts:210`, до 500 знаков.
- **Заметка стойки:** `reservations.service.ts:476, 987` — без проверки. Есть только подсказка в форме новой брони
  «без имён и телефонов гостя», в правке карточки нет и её.
- **Копии в журнале:** карточка брони с `notes` и телефоном гостя целиком уходит в `audit_logs.before/after` при каждом
  действии (`reservation-card.ts:91, 97`). Стёртая заметка в журнале остаётся.
- ADR-072 заметки брони не упоминает. По FINDINGS §2 это главный канал передачи смены, так что имена и телефоны там
  вероятны.
- Туда же — `charges.description`, `refunds.reason` и `inventory_blocks.reason`, которые набирает стойка.

### Н3. `last_error` не очищается от ПД (средняя, §7)

- `inbound.service.ts:562` пишет `e.message` любого исключения как есть. Так же пишут очередь исходящих
  (`channels.repository.ts:418, 436`) и `api.error` сторожа (`guard.service.ts:290`: имя, сообщение, три кадра стека).
- `redactText` сторожа прячет секреты, но не почту и телефоны в тексте.
- Сообщения, которые сегодня собирает код, ПД не содержат. Настоящий путь утечки — текст ошибки Prisma. Формат
  `pretty` (он в проекте по умолчанию) печатает аргументы вызова, например заметку брони.
- Дальше `last_error` попадает в неисправности, в Telegram, в отчёты `reports/*.md` (`cli-webhook-check.ts:87`) и в
  подсказку дежурного агента `claude -p` (`scripts/ops/guard/run.sh`) — внешнему ИИ, чего §4 не допускает для ПД.
- План П2.

### Н4. Пробелы журнала действий (§6)

**Пишется в той же транзакции, с автором, before и after:** смена дат (стойка, продление, ранний выезд, канал),
переселение (включая перетаскивание на шахматке), отмена и незаезд со стойки, платёж, возврат, ручные начисления.

**Пробелы:**

| Операция | Что не так | Где |
|---|---|---|
| Цены и ограничения (`/rates/bulk`: ячейка, массовая правка, стоп-продажа, CTA/CTD, min/max) | Старые строки удаляются, в журнал пишется только запрос как `after`; `before` нет | `rates.repository.ts:152, 176, 198-208` |
| Отмена брони каналом | `after: { uniqueId }`, `before` нет | `inbound.service.ts:673-678` |
| Предоплата канала (создание, сумма, снятие), штраф при отмене или незаезде | Своей строки нет; карточка брони счёта не содержит | `reservations.repository.ts:957-1144` |
| Цены и фонд при онбординге | Строк нет | `hotel/onboarding.ts` |
| Документ гостя | `{fields:['type','number']}` и `{fields:['id']}` — какой документ удалён, не узнать | `guests.service.ts:184, 191` |
| Блокировка ячейки | Журнал пишется отдельным запросом, не в транзакции с блокировкой | `units.repository.ts:159-197` |

Изменить или удалить запись журнала через API нельзя. В базе можно: триггеров, `REVOKE` и хэш-цепочки нет.

План П3.

### Н12. Мелочи (низкая)

- **Счётчик сайта хранит сессии 13 месяцев** через `npm run analytics:retention`. Запуск ручной, расписания нет.
