## 1. Ключи во фронтенде — нет проблемы

- `NEXT_PUBLIC_*` не используется нигде; `apps/web/next.config.ts` не отдаёт `env`/`publicRuntimeConfig`.
- Все `process.env` в `apps/web/src` — серверные и не секреты: `APP_API_URL`, `APP_AUTH_REQUIRED`, `APP_URL`,
  `ASSISTANT_URL`, `SITE_ORIGINS`, `NODE_ENV`, `APP_DEMO_MODE`, `APP_ALLOW_TEST_DATA` (`lib/api.ts:64-71`,
  `lib/session.ts:22`, `lib/session-cookie.ts:14`, `lib/site-auth.ts:28`, `middleware.ts:24`).
- Клиентские компоненты импортируют из `lib/api` только типы; в браузер уходят вызовы лишь своих `/api/*`
  (`components/data-freshness.tsx:37`, `app/create/use-guest-draft.ts:16`). Стойка ходит в API одной точкой —
  `backendFetch` (`lib/api.ts:63-121`) — с сессией человека, служебных ключей у стойки нет.
- Ключи моделей читает только бот (`apps/ai-seller/src/config.py:56,60,73`; `src/ai/llm.py:228-235`), ключи партнёров
  лежат в его базе шифрованными (`src/security/llm_keys.py:52`). В браузер виджета уходит только публичный `data-key`.
- `apps/site` — статика без токенов и скриптов аналитики.
- Замечание (не утечка): `deploy/compose.yml` через якорь `x-app` отдаёт весь `.env` и контейнеру `web`. В сборку он
  не попадает (`.dockerignore`), но по принципу наименьших прав стойке хватит пяти переменных выше.
- В `docs/channex/site/api-v.1-documentation/api-reference.md:61` лежит ключ-пример из публичной документации
  Channex (`uU08XiMgk8a7…`) — убедиться, что это не собственный ключ объекта.

## 2. Supabase: RLS и service role — частично

Что есть: RLS включён политикой `rls_tenant` на 43 таблицах из 53 (`…028_rls_policies`, `…030`), запросы организации
идут ролью `wetop_app` без `BYPASSRLS`, production без `DATABASE_APP_URL` не стартует (`packages/database/src/rls-startup.ts`,
`apps/api/src/main.ts:24-29`). Клиента `@supabase/*` в коде нет, service role key нигде не используется — база только
через Prisma. Изоляция под `wetop_app` на рабочей базе проверялась 29.09 (SECURITY.md §14).

Что найдено:

1. **Права `anon`/`authenticated` на схему `public` так и не отозваны** (SECURITY.md §12: Data API выключен 22.09, а
   вариант Б «отобрать права» не выполнен). Десять таблиц без RLS (`users`, `password_resets`, `external_events`, …)
   держатся только на выключателе Data API. **Исправлено:** миграция
   `packages/database/prisma/migrations/20260930000034_revoke_supabase_api_roles/` (с `down.sql`) — снимает права на
   таблицы, последовательности, функции и умолчания для будущих объектов; на базе без этих ролей — ничего не делает.
   Применяет владелец (`docs/ops/rls.md`), затем — советник безопасности Supabase.
2. **Стадия B SEC-1b не закончена:** `wetop_app` держит полный CRUD на `external_events`, `channel_outbox`,
   `system_incidents` (грант из `…026_rls_roles:30-32`), RLS на них нет. Код уже переведён на ворота
   `apps/api/src/database/integration-tables.ts`, миграция B2 по плану `plans/sec1b-stage-b-2026-09-30.md` ждёт отчёта
   владельца по рабочей базе — в этой ветке не трогалась (у плана свои ворота).
3. `FORCE ROW LEVEL SECURITY` не ставится: владелец таблиц и служебные пути (платформа, вебхук, фоновые циклы,
   скрипты) идут мимо RLS — так задумано (§17.3), но это значит, что изоляция там держится только на коде.
4. `…026:32` даёт `wetop_app` полный DML на любую **будущую** таблицу по умолчанию; новая таблица без своей политики
   RLS открыта всем организациям. Отдельное решение (план стадии B, «не входит»).
5. База бота (`apps/ai-seller`) — свой Postgres, бот ходит владельцем таблиц, RLS там не действует по признанию
   самой миграции `0002_organizations.py:17-22`; изоляция — фильтры приложения (`_foreign()` в панели).

## 4. Админка и служебные маршруты — нет проблемы

- API закрыт по умолчанию: `SessionGuard` + `RoleGuard` глобально (`apps/api/src/app.module.ts`); маршрут без
  `@Access` — 403, `@Public()` — явный список (`auth/*`, `/health`, вебхук Channex, публичная бронь `/w/*`,
  счётчик `/a/*`, мастер). Тест `auth/route-access.test.ts` ломается, если у маршрута нет ни того, ни другого.
- Платформа: `@Access('platform')` (`platform/platform.controller.ts:35`, `support.controller.ts:28`) плюс
  `requirePlatformAdmin()` в каждом методе сервисов; `platformAdmin` берётся из `platform_admins` на каждом `whoami`,
  служебные ключи платформу не открывают (`platform/admin.ts:11-13`).
- IDOR по выборке (финансы, гости, брони, места, тарифы, `assistant/reservation`): объект и организация — из сессии,
  не из запроса (`database/property-ref.ts:63-69`); плюс RLS.
- Стойка: `middleware.ts` сессию не проверяет, `AccessGate` — только UX, но все данные и мутации идут через API с
  сессией (`backendFetch`), служебных ключей в `apps/web` нет; четыре `route.ts` и 18 server actions проверены.
- Тестовые двери (`x-wetop-test-client`, подставной API) закрыты в production (`apps/web/src/lib/api.ts:65-74,111-115`).
- Бот: панель под `Depends(current_user)` (JWT + 2FA или служебный ключ по списку маршрутов), сравнение ключей —
  `compare_digest` по байтам.

Найдено и исправлено: ключ идемпотентности действий помощника хранился без организации
(`assistant/actions.service.ts:106,116`) — вторая организация с тем же ключом получала ответ первой из памяти.
Остаётся за владельцем: `/internal/sandbox` бота открывает и ключ `/internal/health` (`dashboard_router.py:82-96`),
а `organization_id` берёт из тела — ключ живости может гонять модель от имени любой организации (сеть внутренняя);
`SERVICE_API_KEY` — сквозной ключ на всё, его утечка = вся база (по замыслу, но хранить как самый важный секрет).

## 5. Лимиты на ИИ-маршруты — были дыры, исправлено

Что есть: `/auth/*` — 10–30 в час на IP плюс локаут; `/w/book` 5 в час на IP и 30 на сайт с проверкой по журналу;
`/assistant/actions/*` — раз в 10 минут на организацию; виджет поддержки — 60 в час на посетителя и на IP; тело
виджета 64 КБ, WhatsApp 256 КБ; суточный бюджет токенов в Redis.

Найдено и исправлено в ветке:

| Где | Было | Стало |
|---|---|---|
| `apps/ai-seller/src/channels/widget.py` `post_message` | реплика до 64 КБ принималась целиком, ложилась в историю и уходила в модель 20 ходов подряд (до 12 платных вызовов за ход) | реплика длиннее `widget_max_message_chars` (4 000, `config.py`) — 413 до хода |
| `apps/ai-seller/src/ai/context.py` `build_messages`, `engine.py` | история в модель — как есть | каждая реплика истории режется до `guard_max_input_chars` (`max_turn_chars`) |
| `apps/ai-seller/src/dashboard/panel_extract.py` | разбор рассказа звал модель мимо суточных бюджетов и без предела | часовой предел на организацию (тот же счётчик, что у виджета), 429 |
| `apps/ai-seller/src/db/ip_block.py` | блок за инъекции ставился по `CF-Connecting-IP`, а middleware сравнивала сокет — за cloudflared сокет один у всех, блок не срабатывал никогда | middleware берёт адрес той же `client_ip` |
| `apps/api/src/ai-seller/seller.service.ts` | `/ai-seller/sandbox`, `/extract`, `/llm-key/check` без предела (последний — оракул годности чужих ключей) | 60 / 10 / 10 в час на человека (`SELLER_LLM_LIMITS`), 429 до вызова продавца |
| `apps/api/src/platform/support.service.ts` | `/platform/support/sandbox` без предела | 60 в час на администратора |

Остаётся (решения владельца): лимиты виджета и бюджет — fail-open при сбое Redis (осознанно, `widget_guards.py:272`);
WhatsApp без предела на отправителя (у Meta свой лимит 4 096 знаков на сообщение, суточный бюджет организации
действует); все лимиты API живут в памяти процесса и сбрасываются перезапуском; в конфигурации края (`deploy/`)
лимитов нет — для `assistant.wetop.ai/widget/*` стоит поставить rate limit на Cloudflare.

## 6. Оплата — не применимо, мелочь исправлена

- Онлайн-провайдера нет (QUESTIONS.md Q-141, DECISIONS.md: «счёт и реквизиты, главный администратор подтверждает
  вручную»). `kaspi`/`halyk` — только значения `PaymentMethod` для ручной записи.
- `POST /finance/payments` (`finance/finance.controller.ts:91`, право `desk`): статус не принимается (всегда
  `COMPLETED`), валюта — из счёта, сумма — целые тиыны > 0 (`packages/domain/src/finance/finance.ts:40-56` и CHECK в
  базе `…022_integrity_guards`), возвраты — под замком и в пределах оплаченного.
- Публичная бронь `/w/book` не принимает ни цены, ни предоплаты, ни статуса (`packages/domain/src/web-booking/request.ts:94-128`);
  статус, тариф и цена — сервер. Предоплаты из Channex создаются из ленты, которую сервер тянет сам, вебхук — только сигнал.
- Подписка платформы: статус меняет только главный администратор, регистрация жёстко `TRIAL`.
- Вебхуки: Channex — общий секрет в заголовке, `timingSafeEqual`, без секрета 503; WhatsApp — HMAC-SHA256 тела.
  **Исправлено:** `apps/ai-seller/src/channels/whatsapp.py:125,162` сравнивали `str` — не-ASCII в запросе давал 500
  вместо 403; теперь байты.
- За владельцем: у ручной оплаты нет ключа идемпотентности (двойная отправка формы — двойной платёж) — это финансовая
  логика, менять только по решению; когда появится эквайринг — сначала подписанный вебхук.
