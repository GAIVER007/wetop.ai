## 3. Команды, которые не выполнятся как написано

### 3.1 `/health` такого адреса нет

§6 предлагает `curl http://127.0.0.1:3001/health`, а §7 разбирает «`/health` 503 при живой базе».
В API нет ни одного контроллера с маршрутом `health`: контроллеры — `auth`, `analytics`, `a`, `audit`,
`channels/channex`, `desk`, `system`, `finance`, `guard`, `guests`, `hotel`, `inventory`, `rates`,
`reservations`, `rate-plans`, `units`, `w` и корневой (шахматка). `WebhookHealthService` — это состояние
webhook внутри `/channels/channex`, а не проверка живости процесса.

Сейчас роль «жив ли API» играет `GET /inventory/summary` — именно его опрашивают `ari.sh`
(`wait_api`) и сторож. Либо документ правится на этот адрес, либо в API заводится настоящий `/health`
(отдельная задача: маршрут, проверка соединения с базой, тест red → green).

### 3.2 API слушает только `127.0.0.1` — из контейнера он никому не виден

`apps/api/src/main.ts:18`: `await app.listen(port, '127.0.0.1')`, и это осознанно
(комментарий там же: авторизации нет до Q-061…064). В Docker это значит, что ни `web`, ни
`cloudflared`, ни хост к API не достучатся — `127.0.0.1` внутри контейнера это сам контейнер.
Проверка `docker compose exec api wget -qO- http://127.0.0.1:3001/health` из §6 пройдёт (она внутри
того же контейнера) и **создаст ложное впечатление, что всё работает**, а стойка получит отказ.

Адрес прослушивания должен стать настраиваемым (например `API_HOST`, по умолчанию `127.0.0.1`,
в compose — `0.0.0.0` при закрытой наружу сети), с тестом. Это правка кода, не документа.

### 3.3 `ari.sh` под Docker не работает в принципе

`scripts/ops/ari.sh` целиком построен на macOS и launchd: `launchctl setenv`, `launchctl kickstart -k
gui/$(id -u)/kz.luxx.pms.api`, `lsof -nP -tiTCP`, `ps eww`. На Ubuntu в контейнере нет ни launchctl,
ни такого `ps eww`. §6 велит вставить в чат вывод `bash scripts/ops/ari.sh status` — вывода не будет.
Выключатель ARI на сервере — это отдельный вариант скрипта (переменная в `deploy/.env` +
`docker compose up -d --force-recreate api` + проверка через API), и он тоже не написан.

### 3.4 `.env` кладётся не туда, откуда его читает программа

§2.4: `scp ~/.env pms@<IP>:~/wetop/deploy/.env`, «compose читает `.env` рядом с собой». Для compose —
да. Но **весь код читает `.env` из корня репозитория**: `apps/api/src/main.ts:14`
(`../../../.env`), `packages/database/prisma.config.ts:10` (`../../.env`), все скрипты
`scripts/imports/src/*` (`resolve(ROOT, '.env')`), включая тот самый `cli-check-env.ts`.
Поэтому команда в конце §2.4 — `cd ~/wetop && npx tsx scripts/imports/src/cli-check-env.ts` —
напечатает «НЕ ЗАДАН» по всем пяти ключам: она ищет `~/wetop/.env`, а файл лежит в `~/wetop/deploy/.env`.
То же касается §3: `npx prisma migrate deploy` возьмёт `DATABASE_URL` из корневого `.env`.

### 3.5 `psql "$DATABASE_URL"` — переменной в оболочке нет

§3 и §5 вызывают `psql "$DATABASE_URL"`, `pg_dump "$SRC"`, `pg_restore --dbname="$DST"`. `DATABASE_URL`
живёт в `.env` и в окружение оболочки сам не попадает. Нужен явный шаг (`set -a; . ~/wetop/.env; set +a`)
либо ввод строки руками. Плюс `psql`, `pg_dump` и `pg_restore` в §2.1 не ставятся —
`postgresql-client-16` в списке `apt-get install` отсутствует. Версия клиента должна быть не ниже
версии сервера, иначе `pg_dump` откажется.

## 4. Перенос данных (§5): переносить нечего в смысле ПД

§5 предупреждает «в выгрузке настоящие ПД гостей». На деле dev-БД в Supabase анонимизирована
(ADR-018, `CLAUDE.md`: «только анонимизированные ПД»), `PII_STORAGE` там пуст, гости каналов записаны
псевдонимами. Значит копия даст новой базе те же псевдонимы, и после §6 всё равно понадобится
полный импорт из Exely с `PII_STORAGE=real` на базе в РК — иначе условие допуска №3 `CUTOVER.md`
формально выполнено, а настоящих имён в базе нет.

Это меняет порядок шагов: либо (а) копируем dev как есть, ставим `PII_STORAGE=real` и переливаем
данные импортом из Exely заново, либо (б) не копируем вовсе, а разворачиваем базу миграциями и
наполняем импортом. Развилка для владельца — в коде она ничего не требует.

Что в §5 верно и проверено: схему действительно нужно ставить миграциями, а не дампом. Сериалов и
представлений в схеме нет (`autoincrement()` не встречается, `CREATE VIEW` в миграциях нет), поэтому
после `--data-only --disable-triggers` последовательности чинить не придётся, а проверка
`pg_constraint where convalidated = false` уместна.

- Нумерация единиц не выводится из номера — к переезду отношения не имеет, но импорт после переезда
