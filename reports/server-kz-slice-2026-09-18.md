План — `plans/server-kz-2026-09-18.md`. Диагноз, из которого он вырос — `reports/server-kz-readiness-2026-09-18.md`.
Лист команд владельцу — `docs/ops/server-kz-setup-2026-09-18.md`.

## 1. Главное, что выяснилось про способ работы

Агент до ps.kz не достаёт **ни с одной стороны**, и это проверено, а не предположено:

- оболочка агента на машине владельца сети не имеет вовсе — `ps.kz` не резолвится;
- из облачной среды наружу ходит только HTTPS через прокси организации, и он отклонил `ps.kz:443`
  (`connect_rejected`); SSH закрыт по построению;
- расширение Claude в Chrome владельца на вызовы не отвечает;
- встроенный браузер работает, но у него свой профиль: `console.ps.kz` перебросил на форму входа.

Значит все действия на сервере делает владелец по командам, а агент разбирает вывод. Это записано в
плане как постоянное правило: в лист команд нельзя класть шаг, вывод которого некому прочитать.

## 3. Что решено не делать кодом

Переменная `ENV_FILE` была написана и **убрана**. `.env` читается в 64 местах, все — от корня
репозитория; проще держать файл там, где его уже ищут, чем править 64 файла. На сервере `.env` лежит в
`~/wetop/.env`, compose читает его оттуда (`env_file: ../.env`), внутрь контейнеров переменные приходят
окружением — dotenv там не нужен вовсе. Записано в `deploy/README.md` первой строкой правил.

## 4. Прогоны на этом коде (облачная среда, Linux)

- unit: **1162 прошли, 3 пропущено, 1 красный** — `design/tokens.test.ts`, который зовёт `git ls-files`;
  в облачной копии нет `.git`. Это среда, не код: **перепроверить на машине стойки**.
- `typecheck`, `typecheck:api`, `lint` — без ошибок.
- Прогоны шли не через `npm run test:record`: журнал `tests/runs` ведётся на машине стойки, а копия
  исходников в облаке — временная. На машине владельца набор надо прогнать своим порядком:
  `npm run test:status`, затем `npm run test:record -- unit`.
