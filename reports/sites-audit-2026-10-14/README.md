## 3. Архитектура лендингов (система A)

```
apps/site/src/lib/landings.ts        реестр: DIRECTIONS (3) + SUBTYPES (9) + фото
apps/site/src/app/for/hotels/page.tsx        свой каркас направления (герой + факты +
   salons/page.tsx, restaurants/page.tsx      возможности + скрин продукта + рост + подтипы + FAQ + финал)
apps/site/src/app/for/[segment]/page.tsx     один каркас всех 9 подтипов, параметры из реестра
apps/site/src/i18n/ru.ts                     словарь: segments.items[slug] (title, lead, cards,
                                             about, faq, seo), segments.day[direction]
apps/site/public/photos/*.jpg                фото KIE (10-11.10), public/og/*.jpg 1200x630
apps/site/src/app/sitemap.ts, компонент подвала   обе читают реестр
tests/site/segments.spec.ts                  контракт всех 9 страниц (заголовок, герой, карточки,
                                             FAQ 4, CTA, запреты текста)
```

Каркас страницы подтипа: крошки, герой `hotel-hero` (текст + мокап интерфейса своей вертикали `/design-only/<vertical>.svg`), полоса фактов направления, карточки возможностей, «Как проходит день» (3 шага), у гостиниц скрин календаря `hotel-shot`, текст «о формате» (`prose--center`), блок маркетинга, FAQ + финальный CTA (фото направления `ctaPhoto`, общее для всех подтипов направления). Уникальны на подтип только тексты словаря и OG-картинка; **собственное фото подтипа на самой странице не показывается нигде** (используется только для соцсетей), это главный визуальный резерв.

Выкладка: вручную `site:deploy` (Cloudflare Pages), в гейт `release-checks` входит задача «главная» (`site:check`). Тесты: 15 спеков `tests/site/*`, с axe, 390 и 1440 px.

## 4. Конструктор клиентских сайтов (системы B и C): кратко

Полные отчёты четырёх исследований лежали в сессии; здесь выжимка для второго ТЗ.

- **Документ сайта**: SiteSpec v0 (`packages/domain/src/marketing/site-spec.ts`), строгая схема до 256 КБ: site (бренд, контакты, SEO, юрлицо), theme (4 пресета x 6 акцентов x 3 шрифта x 3 радиуса x 2 плотности, только светлая), navigation, 1-20 страниц по 1-30 секций, integrations (бронь, счётчик).
- **Секции**: 11 типов, 21 вариант (hero, about, features, accommodations, amenities, pricing, gallery, booking, contacts, faq, cta). Реально различаются вариантами только features, accommodations, faq, contacts; у hero IMAGE_FULL и IMAGE_SIDE, amenities LIST и ICONS, gallery GRID и CAROUSEL, cta BANNER и SPLIT рендер одинаковый (разница максимум в наличии картинки). Подписи вариантов в редакторе обещают то, чего рендер не делает.
- **Вертикаль одна**: `vertical: oneOf(['HOSPITALITY'])`; салонам и ресторанам конструктор закрыт на всех слоях (схема, scope API, SQL рантайма, воркер ИИ, меню). Это решение ADR-149 п.1.
- **Шаблонов нет**: ни пресетов, ни стартовых SiteSpec по категориям. Первую версию собирает только ИИ по брифу филиала (бот `apps/ai-seller`, каскад моделей, бюджет 150k токенов/сутки на организацию, 10 запросов/час на человека). Выбор «3 варианта оформления» генерируется ИИ каждый раз заново (тема + вариант hero + порядок блоков), это не каталог.
- **Редактор** `/marketing/site/editor`: гибрид (формы блоков + ИИ-чат Чат/План/Сборка + живой превью с правкой текста по месту). Перетаскивания нет (кнопки вверх/вниз). Картинки только из библиотеки `site_assets` (S3 Казахстан, EXIF срезается, WebP). Лицензия `site_builder_entitlements` на филиал, выдаёт платформа.
- **Публикация**: неизменяемые версии (`marketing_site_versions`, дерево ревизий), журнал публикаций, поддомен `<slug>.<SITES_BASE_DOMAIN>` (не wetop.ai), пауза/возврат/архив. Свои домены (CUSTOM): только схема в БД, API и интерфейса нет (этап MKT10).
- **Рантайм** `apps/sites`: Worker по хосту спрашивает `GET /sites-runtime/current`, кэш 60 с, рисует HTML без своего JS; SEO полный (meta, OG, JSON-LD, sitemap, robots); CSP `default-src 'none'`; доступность хорошая (встроенные тесты 390/1440 + axe). Живые данные на странице: активность категорий, вместимость, заезд/выезд, цена «от» скриптом, бронь настоящая через `/w/book` (Turnstile, лимиты, EXCLUDE-защита от двойной продажи).
- **БД** (все таблицы в Prisma, RLS `rls_tenant` FORCE): `marketing_sites` (1:1 с филиалом, один сайт навсегда, UNIQUE location_id), `marketing_site_versions`, `generation_runs`, `site_ai_runs`, `marketing_site_publications`, `site_domains`, `site_assets`, `site_builder_entitlements`, `marketing_site_version_bookmarks`, плюс аналитика `tracked_sites`, `web_sessions/pageviews/events` (хранение 13 месяцев, без ПД и cookies). Таблиц лидов и форм нет (намеренно, §29.10).
- **Салон и ресторан**: живых данных на сайтах нет и быть не может сейчас: нет секций услуг/мастеров/меню, нет публичной записи (ни одного @Public в beauty), у ресторана нет даже модели меню. Это работа уровня модели данных и API (решение 7 в `plans/mkt10-marketing-2-audit-2026-10-09.md`).

## 5. UI/UX и мобильная версия

Лендинги (жил. скрины в этой папке и в scratchpad сессии):
- 🟢 Страницы подтипов собраны ровно: крошки, герой с мокапом продукта, карточки, шаги дня, FAQ, финал; подвал ведёт на все 12 страниц тремя группами.
- 🟡 Визуально страницы бедны фотографиями: на странице подтипа ни одного фото (только мокап интерфейса), фото финала общее на направление. Фото подтипов уже есть в репозитории, но показываются только в соцсетях (OG).
- 🟡 Стилистика направлений разошлась: `/for/hotels/` в голубой гамме со скринами, барбершоп белый карточный. Не дефект, но целевая линия нужна.
- 🟢 Мобильная 390 px: одна колонка, без горизонтальной прокрутки (есть сторожа в tests/site с axe).

Клиентские сайты (локальный рендер fixture, 1440/768/375):
- 🟢 Резиновая вёрстка, axe-набор в tests/sites, цели от 44 px, FAQ на details.
- 🔴 На телефоне шапка sticky высотой 184 px (~23% экрана 812 px): название + меню в перенос + большая кнопка, гамбургера нет. При 7 пунктах меню станет хуже.
- 🟡 Вероятный дефект ROWS у accommodations: один дочерний блок в сетке `1fr 2fr` с 800 px (карточка в левой трети). Пример спеки и e2e этот вариант не покрывают.
- 🟡 e2e рантайма идут с пустыми assets: раскладки с картинками не проверяются вовсе.
- 🟡 Аналитика в режиме «ждать согласия» не запустится никогда: баннера согласия нет, CSP запрещает инлайн-скрипты.
- 🟡 Виджет брони не получает язык сайта (откроется по-русски на kk/en сайте); подвал не выводит контакты вопреки документации; подпись цены «/ ночь» зашита.

## 6. Проблемы и риски (для второго ТЗ)

1. **Ветка `recovery/owner-design-v2-20261010` в основном дереве отстаёт от main по `apps/site`**: в ней [segment] на 6 страниц без реестра `landings.ts` и некоммиченные правки тех же файлов. Слияние как есть даст конфликт или откат раздела. Перед любой работой по сайту стартовать от свежего `main`.
2. Один сайт на филиал навсегда (UNIQUE `location_id`, миграция 068): подкатегории и шаблоны обязаны жить внутри одного сайта, а не плодить сайты.
3. Варианты-клоны секций (5 типов) и два несверяемых списка значков (site-spec и render/icons): сначала навести порядок, потом множить шаблоны.
4. Блокеры публичного запуска клиентских сайтов: Worker не выложен (нет домена `SITES_BASE_DOMAIN`, Q-271 закрыт только способом), `SITE_ASSET_STORAGE=off` (без него публикация версий с картинками невозможна), свои домены MKT10 не сделаны, подтверждение перед публикацией отсутствует, казахские тексты не проверены носителем (MKT12), режим `BOT_ROLE` на проде надо проверить.
5. Гостиничная специфика размазана (подписи цены, значки, JSON-LD, publicFacts, промпты ИИ): для новых вертикалей собрать «профиль вертикали» одним реестром.
6. Контент двоится: удобства/описание/правила из «Настроек объекта» (ADR-158) и фото `property_media` на сайт не попадают, их вводят заново в SiteSpec.
