## 2. API — только чтение существующих данных (план §2)

| Эндпоинт | Что | Тест |
|---|---|---|
| `GET /channels/channex/outbox/rows?status=&limit=` | строки очереди с `dateFrom`/`dateTo` (края всех сообщений), `roomTypes` (коды категорий по маппингу `channel_mappings`; имена подставляет экран), `messages`, статус, попытки, task id, ошибка, время | `outbox-rows.test.ts` 3/3, `channels.controller.test.ts` «строки очереди…» |
| `GET /channels/channex/events?limit&offset&status&type&q` → `{ rows, total }` | к строке события — `uniqueId`, `otaName` из payload и `confirmationNumber` брони по `Reservation.externalId = unique_id`; поиск по id ревизии, `unique_id` и номеру брони | `channels.controller.test.ts` «события: фильтр, поиск, постраничность, без ПД» |
| `GET /channels/channex/events/:revisionId` | `{ event, facts, categoryByRoomType, reservation, balances }`; 404 на неизвестную | `revision-facts.test.ts` 3/3, контроллер «страница ревизии…» |

`revisionFacts(payload)` отдаёт наружу только канал, даты, гостей, сумму и комнаты: `customer`, `guarantee`,
`notes`, `guests` отрезаются — тест «персональные данные гостя наружу не уходят» был красным на версии,
пропускавшей `guests`. Модель данных не менялась; деньги — тиыны строкой, остаток счёта — тот же `folioBalance`,
что в карточке (`stayFacts`).

Попутно (не чинил, к сведению): `external_events.payload` хранит ревизию целиком, включая `customer` с
именем, телефоном и почтой гостя, — в сингапурской dev-БД при `PII_STORAGE` ≠ `real` это настоящие ПД броней
каналов (`SECURITY.md`, ADR-018). Записать вопрос владельцу отдельно (усечение payload при приёме).
