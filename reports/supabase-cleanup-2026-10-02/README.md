### Результат: скрипт запущен владельцем 02.10.2026, всё сошлось

Владелец выполнил `cleanup.sql` в SQL Editor. Проверка со стороны сессии независимым
запросом, шире, чем показал редактор:

| Проверка | Ожидали | Получили |
|---|---|---|
| `system_incidents` всего / со статусом RESOLVED | 1 / 0 | **1 / 0** |
| `sessions` всего / из них мёртвых | 2 / 0 | **2 / 0** |
| `password_resets`, `invites` | 0 | **0, 0** |
| `reservations`, `reservation_items`, `stay_guests`, `allocations` | 0 | **0, 0, 0, 0** |
| `guests`, `guest_documents` | 0 | **0, 0** |
| `folios`, `charges` | 0 | **0, 0** |
| `payments`, `payment_allocations`, `refunds` | 0 | **0, 0, 0** |
| `inventory_units` | 88 | **88** |
| `physical_rooms` | 88 | **88** |
| `accommodation_types` | 5 | **5** |
| категория с «TEST» в имени | 0 | **0** |
| `audit_logs` (не трогали) | 98 | **98** |
| `user_errors` (не трогали) | 71 | **71** |
| `daily_rates` (не трогали) | 8 640 | **8 640** |

Фонд сошёлся и по составу: **88 = 16 отдельных номеров (`PRIVATE_ROOM`) + 72 койко-места
(`DORM_BED`)**, то есть ровно контрольное число CLAUDE.md §6, расхождение ноль.

Живая сессия владельца не пострадала: удалялись только просроченные и отозванные, мёртвых
теперь ноль. `inventory_blocks` стало 0 (единственная блокировка стояла на тестовом месте),
`housekeeping_events` 6 → 3 (три события принадлежали тестовому месту).

Размер базы остался 24 МБ: место возвращается после `VACUUM`, который отработает сам
(autovacuum). Можно не ждать и выполнить вручную, строки в конце скрипта.

**Почему пришлось запускать вручную.** MCP-инструмент Supabase выполняет чтение, но любой `DELETE`
возвращает таймаут 60 с и откатывается, даже на двух строках: деструктивные операции
требуют подтверждения, которое до облачной сессии не доходит. Проверено трижды, в том
числе на одной мелкой операции; зависших транзакций и блокировок в `pg_stat_activity` нет,
`transaction_read_only` выключен, прав роли достаточно. То есть препятствие в инструменте,
а не в базе.

Готовый скрипт: **`cleanup.sql`** рядом с этим файлом. Запускать в Supabase Dashboard →
SQL Editor, одной транзакцией, с контрольными числами до и после. В скрипте стоит
страховка: если найдётся гость вне стендового шаблона имени, он прерывается и не применяет
ничего. Копию базы перед запуском делает владелец (`pg_dump` в `/root/backups`).

## 4. Расхождение фонда 89 против 88: причина найдена

`inventory_units` и `physical_rooms` содержали по **89** строк при контрольных **88**
(CLAUDE.md §6), а `accommodation_types` 6 при пяти. Причина конкретная: категория
**«TEST ЮНГА INVENTORY20261001 EDIT»** (код `category-74665316-234f-4968-aeec-685bcefa71d4`)
с единственным местом **`YUNGA-TEST-20261001`** и одной физической комнатой, заведённые
01.10.2026 при проверках стойки.

Настоящие 88 сходятся ровно: 36 + 36 коек в двух общих комнатах, 8 + 4 одноместных,
4 двухместных.

Проверено по зависимостям: у тестовой категории **0** проживаний, **0** цен, **0**
ограничений, **0** связей с тарифами и **0** сопоставлений Channex; на её месте только
3 события уборки и 1 блокировка. Поэтому удаление ничего не задевает, и оно добавлено
шагом 4 в `cleanup.sql` со страховкой: если имя категории не содержит «TEST», шаг
прерывается. После него контрольные числа сойдутся: 88, 88 и 5.

## 5. Советники Supabase

Проверены оба советника проекта (это тот пункт, что стоял за владельцем с 30.09).

**Безопасность, два предупреждения, оба требуют DDL на рабочей базе и поэтому самостоятельно
не исправлялись** (CLAUDE.md §3: production migration только владелец):

1. **13 функций с изменяемым `search_path`**: `audit_logs_immutable`,
   `audit_logs_organization`, `app_current_org`, `app_audit_organization`,
   `app_property_visible`, `rate_plans_parent_guard`, `seller_agents_check_chain`,
   `seller_profiles_link_agent`, `seller_scope_precheck`, `seller_scope_assert`,
   `seller_agent_ensure`, `seller_agents_backfill`, `seller_agent_bind_location`.
   Среди них функции RLS и защита журнала, то есть как раз те, где подмена `search_path`
   опаснее всего. Лечится `ALTER FUNCTION … SET search_path = ''` отдельной миграцией.
   Описание: https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable
2. **Расширение `btree_gist` установлено в схему `public`**, его рекомендуют перенести.
   Описание: https://supabase.com/docs/guides/database/database-linter?lint=0014_extension_in_public

**Производительность, только уровень INFO, срочного нет:** 28 внешних ключей без
покрывающего индекса и 26 ни разу не использованных индексов. Больше половины приходится
на схему `pms_test`, то есть на тесты. В `public` значимые из них: `audit_logs.user_id`,
`charges.service_id`, `daily_rates.rate_plan_id`, `reservations.primary_guest_id`,
`user_errors.organization_id`. При базе 24 МБ это ни на что не влияет; смысл появится
с ростом данных.

## 6. Ещё одна находка, не исправлялась

каналами, и переименование ушло бы в Channex. Решение за владельцем.
