## 2. Что оказалось проще, чем в плане

Интеграционные тесты **уже** не зависели от живых данных: каждый импортирует вымышленный объект из фикстур
внутри откатываемой транзакции. На пустой базе без единой правки прошли 17 из 21; красными были только два
файла, которые ищут настоящий объект «Luxx Aparts» или единицу «1» (`overbooking-guard`, `web-analytics`). Их
вылечил сид — тесты не трогались.

## 3. Сид (`tests/tools/test-seed.ts`)

- **Фонд настоящий:** 88 единиц, 5 категорий, 6 тарифов, услуги — из аудита архивный источник 07.09.2026
  (`project-input/retired-source/audit-2026-09-07/inventory.md`, `spravochniki.md`; они в репозитории, гостей там нет).
  Нумерация единиц — из файла, из номера ничего не выводится.
- **Остальное вымышленное:** календарь цен на 480 суток (базовый, ОТА +35 %, Островок −10 %, суммы круглые),
  ~330 броней с придуманными гостями на −10…+2 суток от «сегодня» в Алматы, загрузка ~65 %, три брони без ячейки,
  отмены, незаезды, частичные оплаты. Дальше +2 ячейки свободны: с +3 начинаются окна спеков (`tests/README.md`).
- **Тем же кодом, что бой:** брони идут `adaptUniBooking → normalizeархивный источникReservation → importReservations` —
  номера в формате архивный источник, гости через анонимизацию с солью, счета и платежи создаёт импортёр; уборка автотестов
  такие брони не трогает (номер не в формате PMS).
- **Детерминирован:** одно зерно — те же брони, суммы и номера на любой машине; прогон воспроизводим.
- **Выбор источника** — `TEST_DATA=copy|seed`, без переменной: копия `public`, если там есть объект, иначе сид
  (`chooseTestDataSource`, `tests/unit/test-data-source.test.ts`). На Mac владельца ничего не меняется.

## 4. Что нашлось по дороге

### 4.1. Стойка ~300 мс держит две копии страницы (Next 16, потоковая отрисовка)

После `page.goto` содержимое страницы приходит в скрытом сегменте `<div hidden id="S:0">`, а клиент тем временем
отрисовывает её сам; обе копии живут в DOM 35…330 мс после `load` (замер на `/today`, `/inventory`,
`/reservations/new`, печатной форме; на `/chessboard` дублей нет). Человек скрытую копию не видит; Playwright в
строгом режиме находит каждый элемент дважды и падает сразу — **10 из 23 спеков** в первом прогоне
(«resolved to 2 elements»). На Mac окно уже, и те же дубли всплывали плавающими падениями (журнал 14.09,
«hidden streaming copy» в `tests/ui/premium.spec.ts`).

Сделано: `tests/e2e/fixtures.ts` — `page.goto` дожидается ухода скрытого сегмента; все спеки переведены на него
(одна строка импорта). Причина в стойке не тронута — это поведение потока Next/React, а не ошибка кода; но двойная
отрисовка на каждый переход — повод посмотреть на `app/loading.tsx` при полировке после первой смены (ADR-027).

### 4.2. Спеки с датой «08.09.2026»

`chessboard.spec.ts` и `print-and-journal.spec.ts` ждали занятость на 08.09.2026 — на рабочей копии это работало,
потому что август и сентябрь перенесены из архивный источник. Теперь оба берут «сегодня» в Алматы (`tests/e2e/dates.ts`):
и копия, и сид держат занятость вокруг сегодняшней ночи.

### 4.3. Календарь и фиксированные даты

`manual-reservation.spec.ts` бронирует на 10–12.05.2027; календарь сида был на 150 суток, и стойка честно
отвечала «нет цены». Календарь продлён до 480 суток — как у объекта, где цены загружены до конца следующего года.

### 4.4. Бронь с сайта теряла источник на быстрой сети — гонка приёмника счётчика (исправлено)

`web-booking.spec.ts` не попадал в изолированный прогон из-за жёсткого адреса рабочего стенда `:3001`; переведён на
`APP_API_URL` и сразу дал красный: «брони с сайта» в отчёте 0 при созданной брони. Причина — в API, не в тесте:
приёмник `/a/hit` пишет события пачкой раз в секунду, а `/w/book` привязывает бронь к сессии через `updateMany` по
ключу сессии. Посетитель, который бронирует быстрее секунды после открытия страницы (быстрая сеть, или тест),
приходит раньше, чем его первый просмотр доехал до базы: сессии ещё нет, привязка никого не находит, в журнале при
этом стояло `linkedSession: true` (ключ прислан — «привязано»). Воспроизведено на стенде командами: хит → сразу
`/w/book` → `reservation_id` пуст; хит → 2 с → `/w/book` → привязан. На Mac владельца API отвечает за ~2 с, поэтому
там гонка не проявлялась.

Исправлено в `WebBookingService.book`: перед привязкой очередь приёмника записывается (`CollectService.flush()`), в
журнал идёт настоящий итог привязки. Тест `web-booking.controller.test.ts` «бронь сразу после первого просмотра»
красный без `flush` и зелёный с ним (журнал прогонов 15.09); подделка репозитория теперь привязывает только
записанную сессию, как база. Сквозной `web-booking.spec.ts` — 3 из 3 в изолированном стенде.

## 5. Как повторить

```bash
# PostgreSQL 16 с btree_gist, пустая база pms_dev; .env не нужен
npm ci && npm run generate -w @pms/database && npm run build -w apps/web
DATABASE_URL=postgresql://pms@127.0.0.1:5432/pms_dev npm run test:record -- integration
DATABASE_URL=postgresql://pms@127.0.0.1:5432/pms_dev npm run test:record -- e2e
# без браузеров Playwright, но со своим Chromium: CHROMIUM_PATH=/путь/к/chrome
```

## 6. Чего это не доказывает

Сид — не объект. Сверки с архивный источник (фонд, сутки, цены, балансы) остаются единственным доказательством, что PMS
совпадает с реальностью; сид доказывает, что код делает то, что задумано, на любой машине. Гейты PLAN.md
закрываются сверками, не этим отчётом.
