## 1. Метод и ограничения

Аудит выполнен только статическим чтением файлов в рабочем дереве `.claude/worktrees/sidebar-nav`. Git-команды, тесты, серверы, базы данных, браузер, внешние API и production не запускались. `.env`, credentials и секреты не читались. Поэтому:

- `confirmed` ниже означает подтверждённое расхождение между кодом и принятым контрактом либо доказуемый из кода дефект управления состоянием;
- `hypothesis` означает риск, для которого статического чтения недостаточно для окончательного вывода;
- отчёт не является runtime, deployment или production proof;
- существующие тесты оценены по исходному коду, но в этом аудите не выполнялись;
- отсутствие бизнес-данных само по себе не считается ошибкой.

Порядок проверки: сначала сверка с принятыми решениями и моделью, затем качество реализации, права, безопасность границ, деньги, даты, ошибки и покрытие.

## 6. Подтверждённые проблемы

### B-01 [P1] Принятый контур S1 для `/today` не завершён

Статус: **confirmed, implementation completeness gap**.

Классификация: это незавершённый принятый контур. Статическое чтение не доказывает поломку существующих действий «Открыть календарь», ссылок внимания или старой краткой сводки.

Доказательство:

- ADR-160 требует выручку, клиентов, «Мастера на смене X из Y», отдельную панель мастеров и быстрые действия: `DECISIONS.md:6567-6571`.
- Экран выводит только «Запланировано», «Подтверждено», «Завершено», «Мастеров» и ближайшие записи: `apps/web/src/app/today/beauty-today.tsx:42-63`.
- Загрузчик делает только один запрос дня журнала и не получает данные клиентов или отдельную информацию смены: `apps/web/src/app/today/vertical-load.ts:15-21`.

Условие воспроизведения: открыть `/today` в Beauty-контексте с завершёнными записями, клиентами и мастерами с разным состоянием смены.

Наблюдаемое по коду: существующая краткая сводка продолжает показывать свои четыре показателя и ближайшие записи, но в ней нет новых принятых блоков: плитки выручки, количества клиентов, отношения X/Y, панели мастеров и быстрых действий.

Влияние: основной экран салона не показывает утверждённые владельцем операционные показатели. Пользователь вынужден переходить в календарь и другие разделы, а выручка по принятому правилу вообще не видна.

Исправление: реализовать S1 ровно по ADR-160. Выручку считать в integer minor units как сумму snapshot-цен `DONE`, не добавлять неутверждённые сравнения или финансовые сущности. Добавить статические и UI-проверки каждого блока.

### B-02 [P1] Принятый расширенный контур S3 для `/customers` не завершён

Статус: **confirmed, implementation completeness gap**.

Классификация: это незавершённый принятый контур. Существующий простой список клиентов и его пустое состояние не доказаны сломанными.

Доказательство:

- ADR-160 требует визиты, последний визит, средний чек по `DONE`, производный сегмент, поиск и фильтр: `DECISIONS.md:6574-6576`.
- API выбирает только `id`, имя, телефон и статус: `apps/api/src/beauty/beauty.module.ts:54-64`.
- UI выводит только «Клиент», «Телефон», «Статус» и не содержит поиска или фильтра: `apps/web/src/app/customers/page.tsx:21-45`.

Условие воспроизведения: открыть `/customers` в бизнесе, где есть клиенты с одной и двумя завершёнными записями.

Наблюдаемое по коду: существующий список продолжает показывать имя, телефон и статус. Новые принятые данные и действия отсутствуют: невозможно увидеть число визитов, последний визит, средний чек и сегмент, нет управления поиском и отбором.

Влияние: утверждённый клиентский сценарий не реализован. Администратор не может отличить нового клиента от постоянного или быстро найти клиента по принятому интерфейсу.

Исправление: расширить агрегат `GET /beauty/customers` на существующих таблицах, использовать только `DONE` для визитов и среднего чека, вернуть значения в minor units, вычислить сегмент по порогу из Q-BS-3. Добавить поиск и фильтр без VIP.

### B-03 [P2] `/employees` остаётся таблицей и не показывает принятые данные S2

Статус: **confirmed, spec compliance**.

Доказательство:

- ADR-160 требует сетку карточек, инициалы, специализацию, состояние смены, число записей сегодня и часы смены: `DECISIONS.md:6572-6573`.
- Реализация выводит HTML-таблицу: `apps/web/src/app/beauty/masters/board.tsx:80-128`.
- В колонке «Сегодня» вычисляется только «Работает» или «Не работает»: `apps/web/src/app/beauty/masters/board.tsx:107-110`.

Условие воспроизведения: открыть `/employees` при наличии мастеров с графиком и записями на текущий день.

Влияние: отсутствует утверждённый визуальный и операционный срез. Число записей и часы смены не видны без дополнительных действий.

Исправление: заменить представление на карточки по S2, переиспользуя уже загруженные `services`, `today` и `schedule`. Не добавлять фото, использовать инициалы по Q-BS-4.

### B-04 [P1] Профиль мастера и список услуг сохраняются неатомарно

Статус: **confirmed, data integrity**.

Доказательство:

- Server action сначала создаёт или обновляет мастера, затем отдельным запросом сохраняет `serviceIds`: `apps/web/src/app/beauty/actions.ts:76-103`.
- Создание/изменение мастера выполняется в своей транзакции: `apps/api/src/beauty/beauty.module.ts:247-327`.
- Замена списка услуг выполняется в другой транзакции: `apps/api/src/beauty/beauty.module.ts:331-368`.
- Общий `catch` возвращает «Не удалось сохранить мастера», даже если первая операция уже зафиксирована: `apps/web/src/app/beauty/actions.ts:101-103`.

Условие воспроизведения: создать или изменить мастера, затем получить отказ или сетевую ошибку на `PUT /beauty/employees/:id/services` после успешного первого запроса.

Влияние:

- при создании мастер останется в базе без выбранных услуг, а повтор может создать дубликат;
- при изменении профиль уже поменяется, но форма сообщит общий отказ и оставит старые услуги;
- audit trail содержит две независимые операции и не отражает единый результат формы.

Исправление: добавить один API-контракт, который сохраняет профиль и `serviceIds` в одной транзакции, либо ввести явный идемпотентный составной workflow с видимым частичным состоянием. Нужен тест с принудительным отказом после записи профиля, который доказывает отсутствие частичного коммита.

### B-05 [P1] Гонка между снятием мастера с филиала и созданием записи

Статус: **confirmed, concurrency and data integrity, повторно проверено по Prisma schema и миграциям**.

Доказательство:

- Проверка будущих записей перед снятием филиала выполняется до транзакции: `apps/api/src/beauty/schedule.ts:257-275`.
- Удаление `workingHours` и `employeeLocation` происходит позже в отдельной транзакции: `apps/api/src/beauty/schedule.ts:277-299`.
- Создание записи проверяет назначение мастера и план до своей транзакции: `apps/api/src/beauty/appointments.ts:175-189`, затем вставляет запись в `apps/api/src/beauty/appointments.ts:227-260`.
- Prisma-модель не связывает Appointment с EmployeeLocation. У Appointment отдельные отношения с Employee и Location: `packages/database/prisma/schema.prisma:2857-2884`. EmployeeLocation является отдельной моделью с составным первичным ключом: `packages/database/prisma/schema.prisma:2752-2763`.
- Миграция подтверждает отсутствие составного FK `(employee_id, location_id)` из `appointments` в `employee_locations`. У `appointments` есть отдельные FK на `locations` и `employees`: `packages/database/prisma/migrations/20261003000044_beauty_domain/migration.sql:156-180`. FK самой `employee_locations` направлены только к `employees` и `locations`: `packages/database/prisma/migrations/20261003000044_beauty_domain/migration.sql:60-69`.
- `beauty_appointment_guard` проверяет EmployeeLocation обычным `SELECT EXISTS`, без `FOR KEY SHARE`, `FOR SHARE` или `FOR UPDATE`: `packages/database/prisma/migrations/20261003000044_beauty_domain/migration.sql:265-290`.
- На `employee_locations` установлен только guard для INSERT/UPDATE самой связи. DELETE-trigger, который проверял бы будущие записи, отсутствует: `packages/database/prisma/migrations/20261003000044_beauty_domain/migration.sql:209-221`.
- Статический просмотр всех миграций не нашёл более позднего изменения этих Beauty FK или guard-trigger.
- Общая транзакционная обвязка блокирует только Organization, Business и Location в режиме `FOR SHARE`, но не пару Employee-Location: `apps/api/src/beauty/scope.ts:93-108`.
- PrismaClient создаётся без `transactionOptions` или `isolationLevel`: `packages/database/src/index.ts:58-70`; Nest provider дополнительных транзакционных настроек не добавляет: `apps/api/src/database/prisma.provider.ts:33-50`. Вывод о гонке при этом не зависит от конкретного isolation level, потому что проверка количества записей и удаление выполняются в разных транзакциях.

Достаточное последовательное чередование между двумя запросами:

1. Запрос A, `setLocations`, считает будущие записи вне своей транзакции и получает 0.
2. До входа A в `beautyTransaction` запрос B создаёт и фиксирует новую будущую запись. Guard B видит ещё существующую EmployeeLocation.
3. Запрос A входит в транзакцию и удаляет EmployeeLocation без повторной проверки записей.
4. Отдельные FK записи на Employee и Location остаются валидными, поэтому удаление EmployeeLocation не блокируется.

Это TOCTOU-гонка, для доказательства которой не требуется одновременный commit двух транзакций. Достаточно паузы между проверкой A и его транзакцией. Статический статус остаётся confirmed. Runtime-воспроизведение в рамках этого аудита не выполнялось.

Влияние: возникает запись, назначенная мастеру, который уже не работает в филиале. Экран управления филиалами и журнал начинают противоречить друг другу.

Исправление: перенести проверку будущих записей внутрь той же транзакции, заблокировать конкретную EmployeeLocation через `FOR UPDATE`, а создание записи должно брать на ту же строку совместимую защитную блокировку до проверки и вставки. Если создание первым зафиксирует запись, удаление после ожидания должно повторно увидеть её и отказать. Если удаление первым удалит связь, создание после ожидания должно получить отказ. Дополнительно нужен DB-level guard удаления либо иной общий механизм сериализации этой пары. Составной FK без отдельного бизнес-решения может быть слишком строгим, так как запретит снять филиал при любых исторических записях. Добавить конкурентный integration-тест `setLocations` против `appointments.create`.

### B-06 [P2] Форма новой записи предлагает заведомо недопустимые значения

Доказательство:

- Недоступные в филиале услуги остаются выбираемыми и лишь получают подпись: `apps/web/src/app/beauty/appointment-form.tsx:73-88`.

- API запрещает мастера без выбранной услуги и недоступную услугу: `apps/api/src/beauty/appointments.ts:385-438`.

Условия воспроизведения:

2. Выбрать услугу с подписью «недоступна в филиале» и отправить форму.
3. Выбрать мастера, у которого нет выбранной услуги, и отправить форму.

Влияние: форма разрешает сценарии, которые сервер предсказуемо отклонит. Пользователь тратит время на заполнение и получает конфликт только после отправки.

Исправление: архивных клиентов и неселлабельные услуги исключить или сделать `disabled`; мастеров динамически фильтровать по `serviceId`, рабочему дню и отсутствию. Исторические архивные значения сохранять только при просмотре существующей записи.

### B-07 [P2] Кнопка «Новая запись» может быть активной без единой допустимой записи

### B-09 [P2] Числовые поля услуг не имеют верхних доменных границ

Статус: **confirmed, validation gap**.

Доказательство:

- `parseMinutes` принимает любое положительное целое Number, `parseMinor` любую неотрицательную строку цифр: `packages/domain/src/beauty/catalog.ts:164-176`.
- Модель хранит длительность в PostgreSQL `integer`, цену в `bigint`: `DATA_MODEL.md:1968-1973`.
- Формы не задают `max`, `maxLength` или доменную верхнюю границу для длительности и цены: `apps/web/src/app/beauty/services/board.tsx:164-185`, `apps/web/src/app/beauty/services/board.tsx:235-260`.

Условие воспроизведения: отправить длительность больше диапазона `integer` или цену больше диапазона `bigint`; меньшие, но практически невозможные длительности также проходят доменную проверку.

Влияние: вместо понятной ошибки формы запрос доходит до слоя БД или создаёт практически непригодную услугу. Конкретный runtime-текст ошибки этим аудитом не проверялся.

Исправление: определить принятые максимумы длительности и minor units на уровне домена, валидировать одинаково в API и UI, добавить граничные unit-тесты. Если бизнес-максимум не утверждён, сначала записать вопрос, но технический максимум типа всё равно должен проверяться до Prisma.

### B-10 [P3] Некорректная дата запроса молча заменяется сегодняшней

Статус: **confirmed, input handling**.

Доказательство:

- День вычисляется как `parseDate(rawDate) ?? todayIn(timezone)`: `apps/api/src/beauty/appointments.ts:57-65`.
- `parseDate` возвращает `null` и для отсутствующей даты, и для синтаксически или календарно неверной даты: `apps/api/src/beauty/appointments.ts:476-480`.

Условие воспроизведения: запросить `/calendar?date=2026-99-99` или API `GET /beauty/appointments?date=bad`.

Влияние: повреждённая ссылка или клиентская ошибка не видны, пользователь получает сегодняшний день и может принять его за запрошенный.

Исправление: использовать today только когда параметр отсутствует. Переданный, но неверный параметр должен давать контролируемую ошибку 400 и понятное состояние страницы.

## 7. Hypotheses, требующие отдельной проверки или решения

Эти пункты не входят в количество confirmed-проблем.

### H-01 [P2 hypothesis] Отсутствие мастера имеет неясную семантику для сети с разными часовыми поясами

`time_offs` относится к Employee без Location, но окно для подсчёта и показа строится в часовом поясе текущего выбранного филиала: `apps/api/src/beauty/schedule.ts:158-173`, `apps/api/src/beauty/schedule.ts:330-371`. При мастере в двух филиалах с разными IANA-поясами одна и та же календарная дата может охватывать разные UTC-моменты.

Почему не confirmed: модель не определяет, является отсутствие сетевым календарным днём в одном основном поясе либо должно интерпретироваться отдельно для каждого филиала.

Что нужно: зафиксировать правило в `QUESTIONS.md` и `DATA_MODEL.md`, затем проверить пограничные записи двух филиалов.

### H-02 [P2 hypothesis] Неоднозначные и несуществующие локальные времена DST не обрабатываются явно

`instantOf` дважды корректирует смещение и возвращает один ISO-момент без проверки round-trip локального времени: `apps/web/src/app/beauty/time.ts:1-7`. В день перехода DST локальное время может не существовать или встречаться дважды.

Почему не confirmed: текущие рабочие филиалы и их зоны в этом аудите не проверялись, браузер и runtime не запускались.

Что нужно: unit-тесты для IANA-зон с весенним пропуском и осенним повтором часа, затем явная ошибка или выбор смещения.

### H-03 [P3 hypothesis] Перенос записи на другую дату не переводит пользователя на новый день

Форма разрешает менять дату через `datetime-local`: `apps/web/src/app/beauty/appointment-card.tsx:112-140`. Action только ревалидирует страницы и возвращает сообщение: `apps/web/src/app/beauty/journal-actions.ts:50-68`. Если drawer закрывается и текущий маршрут обновляется на старую дату, запись исчезает из текущего дня без перехода на новую дату.

Почему не confirmed: фактическое поведение закрытия drawer и router refresh не проверялось в браузере.

Что нужно: браузерный сценарий переноса на другой день. Если гипотеза подтвердится, переходить на целевую дату либо оставлять явную ссылку «Открыть 12 октября».
