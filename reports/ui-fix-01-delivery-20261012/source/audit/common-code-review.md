## Подтверждённые дефекты P0-P3

### P0

Подтверждённых P0 нет.

### P1

#### P1-1. Сбой загрузки структуры доступа превращает приглашение в доступ ко всей организации

- Файлы: `apps/web/src/app/team/page.tsx:25-32`, `apps/web/src/app/team/team-board.tsx:104-118`, `apps/web/src/app/team/team-board.tsx:198-208`.
- Условие воспроизведения: `authApi.invites()` и `authApi.members()` отвечают успешно, а `authApi.accessStructure()` отвечает 500, timeout или несовместимым ответом. Страница заменяет ошибку на `null`, скрывает `ScopeEditor`, затем отправляет `scopes: []`. По доменному контракту пустой список означает всю организацию.
- Последствие: transient failure расширяет область нового сотрудника вместо блокировки опасного действия. Это маскирующий fallback, а не совместимость с доказанной внешней границей.
- Исправление: при ошибке структуры показать отдельный `LoadError` и запретить приглашение и изменение scopes. Если нужен version fallback, он должен быть ограничен конкретной версией API, сохранять видимой причину и не разрешать пустую область автоматически.

#### P1-2. Кнопка публикации знания публикует сохранённую версию, а не текущий текст редактора

- Файлы: `apps/web/src/app/platform/support/kb-forms.tsx:31-50`, `apps/web/src/app/platform/support/kb-forms.tsx:52-62`, API публикации `apps/api/src/platform/support-kb.service.ts:213-220`.
- Условие воспроизведения: открыть DRAFT, изменить название или текст, не нажимать `Сохранить`, нажать `Опубликовать` и подтвердить. `publish()` вызывает только `kbPublishAction(id)`, текущий `values` не передаётся. API публикует сохранённую запись по id.
- Последствие: оператор видит новый текст в форме, но помощник начинает отвечать по старому. Это особенно опасно для runbook, security и известных ошибок.
- Исправление: либо блокировать Publish при dirty state с явным требованием сохранить, либо сделать атомарное `save-and-publish`, которое публикует именно подтверждённый текст. В confirm показывать версию или выдержку публикуемого содержимого.

#### P1-3. Публичный status сообщает `ok`, если журнал incidents не читается, но `SELECT 1` успешен

- Файл: `apps/api/src/health/health.module.ts:97-107`.
- Условие воспроизведения: `HealthService.check()` получает успешный `SELECT 1`, а `incidents.open()` падает, например из-за отсутствующей таблицы, прав или ошибки запроса. Catch заменяет ошибку на `[]`, затем `publicStatus` считает все компоненты исправными.
- Последствие: источник деградаций потерян, а публичный экран показывает `Все части WETOP работают`. Это маскирующий fallback и ложный operational status.
- Исправление: сохранить состояние `incidentsUnknown`. При невозможности прочитать журнал возвращать как минимум `degraded` для overall и явное безопасное общее состояние без внутренних деталей. Ошибку логировать и покрыть regression.

### P2

#### P2-1. Повторная отправка приглашения сначала безвозвратно отзывает рабочую ссылку

- Файлы: `apps/web/src/app/login/actions.ts:237-254`, лимит нового приглашения `apps/api/src/accounts/accounts.service.ts:223-226`.
- Условие воспроизведения: у организации уже исчерпан дневной лимит или почта недоступна, затем на `/team` нажать `Отправить заново`. Старое приглашение отзывается на строке 249, новое создание или отправка падает.
- Последствие: до действия была действующая ссылка, после действия нет ни старой, ни новой. UI сообщает потерю только постфактум.
- Исправление: серверный атомарный resend. Сначала подготовить и доставить новый invite, затем в одной контролируемой операции заменить старый, либо сохранить старый действующим при отказе до подтверждённой доставки.

#### P2-2. Повторная owner link гасит старую ссылку до результата отправки письма

- Файл: `apps/api/src/platform/organization-creation.ts:124-142`, обработка отказа mailer `apps/api/src/platform/organization-creation.ts:145-155`.
- Условие воспроизведения: у pending owner есть живая ссылка, пяти минутный лимит уже прошёл, mailer падает. Транзакция отмечает старые tokens использованными и создаёт новый, затем `send()` возвращает false.
- Последствие: старая доставленная ссылка перестаёт работать, новая остаётся в БД, но пользователь её не получил.
- Исправление: не отзывать старую ссылку до подтверждённой доставки новой, либо отправлять ссылку на заранее подготовленный token и атомарно активировать замену после успешной отправки.

#### P2-3. Подтверждение email запускается автоматически при mount вопреки контракту явной кнопки

- Файлы: контракт страницы `apps/web/src/app/login/verify/page.tsx:3-6`, реализация `apps/web/src/app/login/verify/verify-panel.tsx:22-34`.
- Условие воспроизведения: открыть `/login/verify?token=<живой token>` в любом JS-клиенте. `useEffect` сразу вызывает state-changing server action и расходует одноразовый token без отдельного нажатия.
- Последствие: поведение страницы прямо расходится с защитным комментарием про почтовые проверки. Риск срабатывания конкретного mail scanner остаётся гипотезой, но автоматический side effect подтверждён кодом.
- Исправление: убрать вызов из `useEffect`, оставить явную POST-кнопку. Если нужен быстрый UX, показывать кнопку с autofocus, но не менять состояние от простого открытия URL.

#### P2-4. Несуществующий номер брони бесшумно превращает связанную задачу в обычную

- Файл: `apps/api/src/tasks/tasks.repository.ts:130-135`, поиск брони `apps/api/src/tasks/tasks.repository.ts:109-114`.
- Условие воспроизведения: открыть `/tasks?reservation=UNKNOWN`, заполнить форму и создать задачу. `reservationId()` возвращает `null`, запись создаётся без связи и без отказа.
- Последствие: пользователь пришёл из контекста брони и ожидает связь, но она теряется без предупреждения. После создания номер брони в строке задачи отсутствует.
- Исправление: если `reservationNumber` передан и не найден в текущем объекте, вернуть 400 с понятным текстом. Покрыть stale и foreign reservation cases.

#### P2-5. Список задач молча обрезается до 500 записей

- Файл: `apps/api/src/tasks/tasks.repository.ts:87-95`.
- Условие воспроизведения: в объекте больше 500 задач, особенно накопленные done-задачи. API возвращает первые 500 по сроку и не возвращает `total`, cursor или признак truncation.
- Последствие: часть задач полностью исчезает из UI, empty/count секции выглядят окончательными.
- Исправление: пагинация или отдельные лимиты для открытых и завершённых задач, плюс `total` и явный UI-признак неполной выборки.

#### P2-6. Platform admin не может создать организацию Food Service из UI

- Файлы: варианты формы `apps/web/src/app/platform/forms.tsx:282-286`, coercion action `apps/web/src/app/platform/actions.ts:210-220`, сервер поддерживает любую разрешённую `BusinessVertical` в `apps/api/src/platform/organization-creation.ts:56-90`.
- Условие воспроизведения: открыть `Добавить организацию` на `/platform`. В select есть только Hospitality и Beauty. Даже подмена формы значением `FOOD_SERVICE` action преобразует его в `HOSPITALITY`.
- Последствие: ресторанный контур нельзя завести через заявленный административный экран, хотя branches и backend умеют Food Service.
- Исправление: добавить Food Service option и передавать результат через `parseBusinessVertical`, не через двоичный ternary. Пилотный allowlist должен оставаться серверным.

#### P2-7. Цена онбординга вычисляется через JavaScript float вопреки денежной политике проекта

- Файлы: конверсия `apps/web/src/app/onboarding/onboarding-form.tsx:75-82`, поле `apps/web/src/app/onboarding/onboarding-form.tsx:167-174`, кнопка вне формы `apps/web/src/app/onboarding/onboarding-form.tsx:196-210`, серверные пределы `packages/domain/src/onboarding/plan.ts:48-49`, `packages/domain/src/onboarding/plan.ts:96-99`.
- Подтверждено кодом: строка цены преобразуется выражением `Math.round(Number(r.price) * 100)`. Это финансовое вычисление через JavaScript `number`, что нарушает обязательную политику `Money is never float`. Сервер принимает только целый `priceMinor` от 0 до 100 000 000 включительно.
- Не доказано как пользовательская финансовая ошибка: у `input type="number"` без `step` неявный шаг равен 1, поэтому `1.005` имеет `stepMismatch` и не является доказательством нормального успешного ввода. Кнопка запуска вызывает обработчик `onClick` вне формы и код не вызывает `checkValidity`, но без browser run не подтверждено, что конкретный клиент сохранит такое значение и доведёт его до успешного API-ответа. Для допустимых целых значений от 0 до 1 000 000 единиц валюты умножение на 100 остаётся в точном целочисленном диапазоне JavaScript, поэтому воспроизведённой потери допустимой суммы по прочитанному коду нет.
- Последствие: подтверждено нарушение проектного инварианта и хрупкая граница UI/API. Фактическое искажение сохранённой цены остаётся условным риском до определения допустимой дробности и воспроизведения входа, который проходит UI и сервер.
- Исправление: зафиксировать контракт ввода цены. Если разрешены только целые единицы валюты, явно задать `step=1`, клиентский максимум 1 000 000 и безопасный целочисленный разбор строки. Если разрешены дробные единицы, задать точный `step` и преобразовывать строку в minor units decimal-safe способом без `Number` и float. Контракт клиента и API должен совпадать с серверным диапазоном.

#### P2-8. Профиль сообщает устаревшую и неверную модель прав

- Файл: `apps/web/src/app/profile/profile-view.tsx:68-74`.
- Условие воспроизведения: войти как MANAGER или STAFF и открыть вкладку `Доступ` на `/profile`.
- Последствие: текст утверждает, что все вошедшие видят и делают одно и то же, а приглашает только владелец. Текущая доменная модель различает OWNER, MANAGER, STAFF, и manager может управлять частью команды.
- Исправление: строить объяснение из текущих ролей и permissions либо дать нейтральный текст со ссылкой на `/team/roles`.

#### P2-9. Ошибки `currentMe` маскируются как выход или отсутствие прав

- Файлы: `apps/web/src/app/team/page.tsx:19-23`, `apps/web/src/app/team/roles/page.tsx:24-28`, `apps/web/src/app/profile/page.tsx:6-10`.
- Условие воспроизведения: `/auth/me` отвечает 500, 502 или timeout. Team показывает сообщение, что управляют owner/manager, roles показывает отсутствие доступа, profile показывает пользователя как невошедшего и скрывает состояние extension.
- Последствие: service failure диагностируется как permission state, пользователь получает неверную инструкцию, а ошибка теряется.
- Исправление: fallback допустим только для точного 401, ожидаемый 403 обрабатывать отдельно, остальные ошибки показывать через `LoadError`.

#### P2-10. Onboarding gate пропускает пользователя при любом API error, кроме специально распознанного 404

- Файл: `apps/web/src/app/onboarding-gate.tsx:21-32`.
- Условие воспроизведения: `hotelApi.settings()` отвечает 500, 502, 503 или 403 на пути, который должен проверять onboarding. Ошибка превращается в объект `ApiError`, `propertyMissing=false`, `needsOnboarding=false`, redirect не выполняется и ошибки на гейте нет.
- Последствие: broken primary contract маскируется как `онбординг не нужен`. Следующая страница получает непредсказуемое частичное состояние.
- Исправление: обрабатывать только 404 как `propertyMissing`; 401/403 передавать штатному auth/access контуру, остальные ошибки показывать или пробрасывать в error boundary.

### P3

#### P3-1. Форма нового пароля не отражает минимальную длину в HTML-валидации

- Файл: `apps/web/src/app/login/set-password/set-password-form.tsx:38-60`.

- Исправление: добавить `minLength={10}` обоим полям, сохранив обязательную серверную проверку.

#### P3-2. Wizard предполагает JSON для любого ответа proxy

- Последствие: пользователь получает технический текст JSON parser вместо предусмотренного `Не удалось сохранить`.
- Исправление: проверять content-type или безопасно разбирать body, при не-JSON использовать общий текст и HTTP status.

#### P3-3. Ошибка загрузки summary на Support полностью скрыта

#### P3-4. Редактор KB не использует native required для обязательных полей

- Исправление: добавить `required` для title и content, сохранив серверную проверку и сохранение введённых данных после отказа.

## Неработающие или работающие не по заявленному контракту функции

1. Scoped invite при недоступной структуре прав: вместо безопасного отказа создаёт invitation без scopes, то есть на всю организацию.

## Гипотезы и непроверенные runtime-условия

- Не подтверждено, выполняет ли конкретный почтовый scanner проекта JavaScript. Поэтому автоматическое подтверждение email является подтверждённым поведением кода, а досрочное расходование token сканером является гипотезой риска.
- Не подтверждено, достигает ли какой-либо production-объект лимита 500 задач. Бесшумное усечение при таком объёме подтверждено кодом.

Поэтому выбор первого филиала указан как факт реализации, но не засчитан как дефект. Также не подтверждено наличие такого production-набора филиалов.
- Не подтверждено, возвращает ли production proxy wizard не-JSON ответы. Небезопасное предположение `response.json()` для любого ответа подтверждено кодом.
- Не проверялось фактическое наличие или отсутствие runtime ошибок, browser behavior, CI status, deployed SHA и production behavior.
