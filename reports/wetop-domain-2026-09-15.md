## 3. Что нашлось попутно и было починено

Ничего из этого в ТЗ не значилось, но без этого домен не сел бы.

1. **Рабочая копия репозитория отставала от `main` на 62 коммита.** API работал на коде до доменных
   правок, `scripts/ops/launchd/install.sh` не знал имени службы `domain`, `apps/site` в копии не было.
   Перемотано `git pull --ff-only` до `002173a`, дерево было чистым.
2. **Служб launchd не было ни одной.** `launchctl list | grep luxx` пустой, при этом API и стойка
   висели вручную запущенными процессами и умирали: за время работы PID менялся трижды, один раз
   порт 3001 не слушал никто. Установлены `api`, `web`, `domain`, `awake` через `install.sh --takeover`.
3. **`cloudflared` не был установлен.** Значит быстрый туннель не работал, и webhook Channex всё это
   время указывал на мёртвый адрес. Поставлен через Homebrew.
4. **Скрипт служб искал node в `~/.local/bin/node`, а node лежит в `/usr/local/bin/node`.** Сделаны
   симлинки, без них `install.sh` не отработал бы.
5. **Сборка главной не идёт в среде агента:** `next/font/google` тянет Manrope и IBM Plex с
   `fonts.googleapis.com`, а этот адрес закрыт политикой исходящего трафика. Сборка сделана на Mac
   владельца. Если это будет мешать дальше, лечится переводом шрифтов на `next/font/local`, но это
   правка кода и решение владельца.
6. **AUD-тег приложения Access добыть не удалось.** Новый дашборд Cloudflare его на странице приложения
   не показывает, а `cloudflared access login` упал на `no route to host`: у Mac нет маршрута IPv6.
   Поэтому в `~/.cloudflared/wetop.yml` блок `originRequest.access` не заполнен. Замок на `app.wetop.ai`
   при этом стоит: Access проверяет вход на краю Cloudflare, до Mac запрос без входа не доходит.
   Проверка в самом `cloudflared` была вторым замком из образца конфига, её надо вернуть.

## 6. Добавлено вечером 15.09: что нашлось при попытке закрыть приёмку

### 6.1. Пустой `APP_API_URL` ломал все скрипты сверки

`cli-channex-ari.ts`, `cli-system-trace.ts` и `cli-channex-wetop-cycle.ts` падали одинаково:

```
[TypeError: Failed to parse URL from /channels/channex/mapping]
```

Причина: адрес API берётся как `process.env.APP_API_URL ?? 'http://127.0.0.1:3001'`. Оператор `??`
подставляет запасное значение только для `undefined` и `null`. В `.env` переменная была объявлена,
но пустой строкой, поэтому адрес становился пустым и `fetch` получал путь без хоста. Владелец вписал
`APP_API_URL=http://127.0.0.1:3001` и `WEB_URL=http://127.0.0.1:3000`.

Дефект не в домене, он был и раньше; домен только вывел его наружу, потому что сверки понадобились.
Стоит поправить сами скрипты: пустая строка должна падать с понятным сообщением или уходить в запасной
адрес, а не давать `Invalid URL` на середине работы.

### 6.2. Стойка тормозит из-за Mac, а не из-за туннеля

Замеры сделаны на самом Mac, без сети и без домена:

```
своп:   used = 16 095 МБ из 17 408        (при 8 ГБ памяти)
диск:   свободно 6,4 ГБ из 228

API    /desk/today          2,91 с
API    /chessboard          1,08 с
API    /system/freshness    0,37 с
API    /rate-plans          0,43 с
стойка /today               5,93 с
стойка /chessboard          1,18 с
стойка /reservations        1,19 с
```

Шесть секунд на `127.0.0.1` означает, что дорога через Cloudflare ни при чём: её вклад это десятки
миллисекунд. Машина свопится на почти забитый диск. Кэши занимают около 23 ГБ (`~/.npm` 7 ГБ,
`~/.cache` 5,2 ГБ, `~/Library/Caches` 11 ГБ). Это же объясняет и 6.3.

Отдельно: все экраны стойки серверные (`ƒ Dynamic`), при каждом переходе страница рисуется заново на
Mac, а данные идут в Supabase в Сингапуре. Пока PMS живёт на этом Mac, это потолок скорости.
Настоящее лечение это сервер в РК (Q-070, условие 1 `CUTOVER.md`).

### 6.3. e2e: 21 из 23, оба падения не по продукту

`npm run test:record -- e2e`, лог `tests/runs/logs/2026-09-15T11-46-56Z-e2e-7e89.log`.
Упали `chessboard-drag.spec.ts` и `chessboard-unassigned.spec.ts`, обе на записи артефактов Playwright:

```
ENOENT: no such file or directory, open '.../traces/…-recording2.network'
```

Это файлы трассировки, которые Playwright пишет себе сам. Бизнес-логика тут не проверялась вовсе.
Причина та же, что в 6.2: на диске не осталось места. Строка 16 приёмки закрывается повторным
прогоном после чистки диска.

### 6.4. Своей авторизации у стойки нет, хотя экран нарисован

`apps/web/src/app/login/login-form.tsx` содержит готовый экран входа: рассказ о продукте, поля Email и
Пароль, кнопка «Войти». Обработчик формы не проверяет ничего:

```js
setError('Вход в рабочий аккаунт ещё не подключён. Используйте доступное рабочее пространство.')
```

Кнопки регистрации нет. При входе через Cloudflare Access форма прячется и показывается «Вы вошли как …».
То есть поделиться стойкой как сайтом сейчас нельзя: единственный способ дать доступ это добавить почту
человека в политику Access. Своя регистрация с пробным периодом это ADR-023 и Q-129, они не сделаны.

### 6.5. Webhook на постоянном адресе доказан живыми событиями

Сторож записал `reports/webhook-check-2026-09-15.md` в 12:15 UTC:

```
событий в выборке 8, из них по webhook 8
11:28, 11:35, 11:37, 11:44, 11:58 UTC — PROCESSED, задержка до секунды
RESULT: OK — бронь приходит без опроса ленты
```

Webhook был перерегистрирован на `https://api.wetop.ai/channels/channex/webhook` около 11:25 UTC, значит
все пять поздних событий прошли уже по новому пути: Channex → Cloudflare → именованный туннель → API на
Mac. Опрос ленты их не подбирал, поле «как дошло» у всех `сама (webhook)`.

### 6.6. Сторож зря поднимал тревогу: он стучался в старый адрес быстрого туннеля

`GET /channels/channex/webhook/status` в 15:19 UTC:

```
callbackProbedUrl:  https://lows-plain-invite-opinion.trycloudflare.com/channels/channex/webhook
callbackReachable:  null
webhookSuspect:     true
```

В 15:35 UTC, после следующего цикла проверки:

```
callbackProbedUrl:  https://api.wetop.ai/channels/channex/webhook
callbackReachable:  true
webhookSuspect:     false
```

«Адрес не отвечает» в сверке 12:04 означало не поломку туннеля, а то, что сторож держал в памяти адрес мёртвого
быстрого туннеля и стучался туда. Проверки с Mac подтверждают, что постоянный адрес отвечает всеми способами:
`curl`, `curl -4` и `node fetch` дают 404 на GET, а 404 это и есть признак живого адреса, webhook принимает
только POST. Стоит отдельно посмотреть, почему сторож подхватил новый адрес не сразу после перерегистрации,
а только следующим циклом: на живом объекте это лишняя тревога ночью.

### 6.7. Служба `retired-source-sync` не была установлена

Сверка 12:04 жаловалась: «синхронизация архивный источник последняя 43 минуты назад, норма ≤ 15». Причина не в домене:
задача launchd `retired-source-sync` (ADR-032, раз в 15 минут) на машине отсутствовала, как и остальные службы.
Поставлена через `scripts/ops/launchd/install.sh retired-source-sync`; в сверке 15:20 свежесть к концу проверки была
4 минуты. Напоминание из `CUTOVER.md`: в день двойного ввода эту задачу снимают.
