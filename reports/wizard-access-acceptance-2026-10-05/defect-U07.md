# U07: временная недоступность API разлогинивает мастер

Статус FAIL. SHA a5c5050c8c835ae4e2d43e73092355176f5a53f2. Воспроизведено дважды, приложение не исправлялось.

## Повторение

1. Войти синтетическим OWNER, открыть /register/setup на незавершённом Beauty-филиале A2, сохранить draft.
2. Ввести новое businessName без сохранения. Остановить только localhost QA API, оставить web и PostgreSQL работающими.
3. Нажать «Сохранить». Наблюдать переход /?next=%2Ftoday#login вместо ошибки внутри мастера. При локальной public-root конфигурации следующий адрес /today.
4. Восстановить API, вручную открыть /register/setup. Сохранённый прежний draft восстановлен, новое несохранённое имя потеряно.
5. Повторить с другим значением. Получен тот же результат. Ручной ввод после восстановления + Save/reload работает, дублей нет.

Доказательства: U07-reproduction-before.png/txt, U07-reproduction-redirect.png/txt, U07-real-network-failure.png/txt, U07-route-log.txt, U07-network-before-db.json и U07-network-after-db.json. Снимки БД подтверждают сохранность записанных данных, но не исправляют потерю несохранённого ввода.

## Причина

apps/web/src/lib/api.ts представляет ошибку транспорта как ApiError 503. apps/web/src/app/login/signed-in.ts ловит любую ApiError и возвращает user:null. apps/web/src/app/register/setup/page.tsx при user:null вызывает redirect(publicAuthUrl()). После ошибочного server action происходит повторный render страницы; временная ошибка auth/me трактуется как отсутствие сессии. apps/web/src/app/register/setup/actions.ts возвращает ошибку Save, но перенаправление страницы не позволяет остаться в форме. Это не доказанный отказ сессии: после запуска API сохранённый контекст доступен.

## Минимальный предложенный план (не реализован)

1. Добавить регрессионный браузерный тест: заполненный draft, реальная остановка API, Save, сохранение URL/значения, восстановление API и retry. Зафиксировать RED на текущем SHA.
2. Разделить подтверждённое отсутствие/отзыв сессии (401) и временный transport/5xx в signed-in.ts и пути мастера. На временном отказе оставить форму с понятной ошибкой связи и повтором, сохранить несохранённый client draft. Не превращать недоступный auth/me в разрешение записи или обход проверки входа. При необходимости ограниченно изменить shell/actions/error boundary, без схемы БД и бизнес-правил.
3. GREEN на регрессии, затем U02/U03/U04/U06/U07/U08/U10/U11/U12; настоящий 401 по-прежнему ведёт на вход, STAFF/read-only по-прежнему 403, данные чужих филиалов недоступны.
4. Полный CI на новом итоговом SHA. Отдельное решение о выпуске, без изменения production или release в этой задаче.

Риски: ошибочное сохранение authenticated UI при настоящем отзыве сессии; потеря клиентского draft при server rerender; повтор Save после потерянного ответа. Приёмка требует проверки этих трёх случаев, а не подавления исключений ради зелёного теста.
