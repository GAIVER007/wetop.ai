# Дежурный агент PMS Luxx Aparts — инструкция на каждый запуск

Второй слой сторожа (срез 11, `plans/slice-11-guardian.md` §4, ADR-028). Первый слой — сторож в API: раз в минуту
проверяет систему, пишет неисправности в таблицу `system_incidents`, сам чинит технику и будит человека.
Дежурный агент приходит **раз в час** и делает то, что сторож не умеет: разбирается в неисправностях,
которые ему отдали, пишет понятный разбор владельцу и исправляет ошибки кода — в отдельной ветке, без выката.

Перед работой прочитать `CLAUDE.md` (особенно §3 и §5), затем этот файл. Правила проекта важнее этой инструкции.

---

## 1. Что запрещено всегда

- менять брони, гостей, счета, платежи, ячейки, цены, ограничения — ни через API, ни в базе, ни скриптом;
- отправлять что-либо в Channex, OTA, Exely, кроме того, что уже делают кнопки `/channels` на **staging**;
- применять миграции, мёржить в `main`, пушить, менять `.claude/`, `CLAUDE.md`, `AGENTS.md`, настройки доступа;
- читать `.env` любым способом, печатать секреты; класть ФИО, телефоны и документы гостей в отчёт или коммит;
- закрывать неисправность класса Б (данные) — это делает человек или сторож после разбора;
- запускать полный `e2e` (13 минут, живая база, мешает другим сессиям); `unit`, `typecheck`, `lint` — можно;
- больше одного исправления кода за запуск.

Сомнение → не делать, записать в отчёт как вопрос владельцу.

## 2. Порядок запуска

1. Состояние:
   ```bash
   curl -s http://127.0.0.1:3001/guard/status
   ```
   API не отвечает → `scripts/ops/launchd/status.sh` и последние 40 строк `~/Library/Logs/pms-lux/api.log`
   (журнал без секретов; `.env` не открывать). Задача `api` загружена, но падает → записать причину из журнала
   в отчёт, `launchctl kickstart -k gui/$(id -u)/kz.luxx.pms.api` один раз. Дальше не чинить — отчёт.
2. Свежий проход и список:
   ```bash
   curl -s -X POST "http://127.0.0.1:3001/guard/tick?all=1"
   curl -s "http://127.0.0.1:3001/guard/incidents?status=open"
   ```
3. По каждой открытой неисправности со статусом `ESCALATED` — по классу (§3). `OPEN`/`FIXING` — сторож ещё
   работает, не вмешиваться. `ACKNOWLEDGED` — человек в курсе; только проверить, не изменилось ли что-то.
4. Отчёт (§4). Коммит только файла отчёта и своей ветки (§3 В).

## 3. Что делать по классам

**А — техника, сторож не справился за свои попытки.** Разобраться, почему: журнал API, `GET /channels/channex/webhook/status`,
`GET /channels/channex/outbox`, `scripts/ops/launchd/status.sh`, журнал туннеля `~/Library/Logs/pms-lux/tunnel.log`.
Разрешено один раз: `POST /channels/channex/pull`, `POST /channels/channex/outbox/flush`,
`POST /channels/channex/sync/scheduled?force=1` (только если `GET /channels/channex/mapping` показывает staging-объект),
перезапуск задачи launchd. Не помогло — в отчёт: что видно, что пробовал, что нужно от человека.

**Б — данные (овербукинг, без ячейки, отклонённая бронь, упавшая сверка).** Ничего не менять. Разбор только
чтением: номер брони, категория, даты, что говорит отчёт сверки в `reports/`, какие вопросы в `QUESTIONS.md`
уже про это (Q-109, Q-119, Q-120…). В отчёт — текст для владельца: что случилось, что предлагается по правилам
проекта, какое решение нужно. Сами варианты решения не выбирать.

**В — код (ошибка программы 500, падающий набор тестов).**
1. Разобрать: `details` неисправности (маршрут, текст ошибки, первые строки стека).
2. Если исправление касается запретного из `CLAUDE.md` §3 (модель данных, правила брони, финансы, интеграция
   Channex) — не исправлять, записать вопрос в отчёт.
3. Иначе — в отдельной рабочей копии, чтобы не мешать другим сессиям в основном дереве:
   ```bash
   git worktree add .claude/worktrees/guard-<ГГГГММДД>-<кратко> -b guard/<ГГГГММДД>-<кратко>
   ```
   В ней `npm ci` не нужен: `node_modules` находятся в корне основного дерева. Но `@pms/*` оттуда указывают на
   пакеты **основного** дерева — если исправление в `packages/*`, тест должен импортировать исправленный файл
   относительным путём, иначе проверит старый код. Дальше: красный тест, воспроизводящий ошибку → исправление → зелёный; `npm run test:record -- unit <файл>`, затем
   `typecheck` и `lint`. Коммит только своих файлов явным списком (`git commit -- <файлы>`).
4. Не мёржить, не перезапускать API на этой ветке. В отчёт — ветка, коммит, что исправлено, как проверено.
   Неисправность не закрывать: закроется сама после суток тишины, когда владелец примет ветку и API
   перезапустится.

## 4. Отчёт

Файл `reports/guard/<ГГГГ-ММ-ДД>.md` по дате Алматы; дописывать раздел на каждый запуск:

```markdown
## HH:MM Алматы — дежурный агент

Сторож: работает / не отвечает; проход HH:MM, проверок N, не отработали: …; будильник: настроен / нет
Открыто: N (срочных N, ждут человека N)

| Неисправность | Класс | Что сделал | Что нужно от владельца |
|---|---|---|---|

Ветки с исправлениями: guard/… (коммит …, тесты: …)
```

Если за запуск нечего разбирать — одна строка «HH:MM — открытых неисправностей, ждущих разбора, нет».
Отчёт коммитить отдельным коммитом, только этот файл: `git commit -m "docs(guard): on-call report HH:MM" -- reports/guard/<дата>.md`.

## 5. Итог запуска

Последним сообщением — три строки: что открыто, что сделано, что нужно от владельца. Без ФИО гостей.
