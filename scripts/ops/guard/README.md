# Дежурный агент на сервере — шаг 12.3

Второй слой сторожа круглые сутки, независимо от того, открыт ли Claude на маке владельца
(`plans/slice-12-guard-server.md` §12.3, `plans/slice-11-guardian.md` §4). Отдельный проект Docker
`pms-lux-guard` на том же сервере: падение или перерасход агента не задевают боевую PMS.

## Что он делает и чего не делает

Раз в час `run.sh` снимает у сторожа список открытых неисправностей и смотрит, есть ли класс Б или В.
Нет — спит дальше, модель не зовётся: рассуждение стоит денег, а класс А сторож чинит сам. Есть — зовёт
Claude Code по инструкции `scripts/ops/guard-agent.md`, с потолком по времени.

Три замка стоят не на совести агента, а снаружи:

1. **Ключ.** В контейнере нет `SERVICE_API_KEY` и нет доступа к базе. Есть `GUARD_READ_KEY` — он пускает
   только `GET /guard/status` и `GET /guard/incidents` (`apps/api/src/auth/auth.guard.ts`, тесты рядом).
   Ни броней, ни денег, ни учёток этим ключом не видно, и закрыть неисправность им тоже нельзя.
   Сам ключ агенту не достаётся: список снимает `run.sh` и кладёт файлом `incidents.json`.
2. **Push.** У агента команда `git push` отобрана (`--disallowedTools`). Пушит скрипт и только ветки
   `guard/*`.
3. **Время и деньги.** `GUARD_RUN_LIMIT_SECONDS` (по умолчанию 900) обрывает затянувшийся запуск,
   `mem_limit` и `cpus` — потолки контейнера.

## Права ключа развёртывания — что GitHub не умеет

В плане среза 12 записано «ключ развёртывания с правом писать только ветки `guard/*`». **GitHub так не умеет:**
ключ развёртывания даёт запись на весь репозиторий, ограничений по веткам у него нет — ни у ключа, ни у
мелкозернистого токена. Разница между планом и правдой закрывается на стороне GitHub:

- в настройках репозитория включить защиту ветки `main`: слияние только через запрос, запрет прямого пуша
  и force-push — тогда ключ физически не сможет изменить `main`;
- ключ развёртывания завести **с правом записи** и только для этого репозитория.

Без защиты ветки третий замок отсутствует, и это надо знать до запуска, а не после.

## Ключ: чем платим за рассуждение

Только **отдельный ключ Anthropic** (`ANTHROPIC_API_KEY`), заведённый для этого агента и ни для чего больше.
До 01.10.2026 скрипт принимал и токен подписки владельца (`CLAUDE_CODE_OAUTH_TOKEN`): ночной разбор шёл на той же
подписке, под которой владелец работает днём, и делил с ней лимит. Разбор 01.10.2026
(`reports/order-2026-10-01`, пункт 6) это снял: с токеном подписки в `.env` агента `run.sh` не стартует и говорит,
почему.

Что у ключа должно быть:

- **свой предел расхода.** В консоли Anthropic у ключа (или у отдельного workspace под него) ставится предел трат
  в долларах; агент, который ушёл в цикл, упирается в него, а не в счёт владельца;
- **свой отзыв.** Ключ утёк или агент не нужен: отзывается один ключ, подписка владельца не задета;
- **ничего общего с ключами PMS и бота.** `SERVICE_API_KEY`, ключи продавца и помощника в контейнер агента не попадают.

Второй предохранитель стоит в самом скрипте: `GUARD_RUNS_PER_DAY` (по умолчанию 6) ограничивает число вызовов модели
за сутки UTC. Сторож, который каждый час «находит» ту же неисправность, иначе дал бы 24 разбора за ночь. Предел
исчерпан: агент не зовётся до полуночи UTC, в группу дежурных уходит одно сообщение, неисправности остаются открытыми
и ждут человека. Счётчик лежит в `/home/node/work/state` внутри контейнера и сбрасывается с пересозданием контейнера.

## Что вписывает владелец (агент значений не видит, SECURITY.md §3)

Рядом с `compose.yml` файл `.env`:

```
ANTHROPIC_API_KEY=…      отдельный ключ только для этого агента, с пределом расхода в консоли Anthropic
GUARD_RUNS_PER_DAY=6     необязательно: вызовов модели в сутки, по умолчанию 6
GUARD_READ_KEY=…         тот же, что в .env боевой PMS
GUARD_REPO=git@github.com:GAIVER007/wetop.ai.git
TELEGRAM_BOT_TOKEN=…     тот же бот, что у сторожа
TELEGRAM_CHAT_ID=…       группа дежурных
```

И ключ развёртывания файлом `./ssh/id_ed25519` (права 600), рядом `./ssh/known_hosts` с отпечатком
github.com — проверка отпечатка включена намеренно, `StrictHostKeyChecking=yes`.

В боевой `.env` PMS добавляется строка `GUARD_READ_KEY=…` с тем же значением. Оба ключа придумывает
владелец, в чат они не диктуются.

## Запуск

```
cd /root/wetop/deploy/..                        # корень клона на сервере
docker compose -f scripts/ops/guard/compose.yml up -d --build
docker compose -f scripts/ops/guard/compose.yml logs -f guard-agent
```

Сеть `pms-lux_default` должна существовать — то есть боевой проект уже поднят.

## Критерий готовности

- `docker compose … logs` показывает «тихий час», когда открытых неисправностей класса Б и В нет;
- в `.env` агента нет `CLAUDE_CODE_OAUTH_TOKEN`, а `ANTHROPIC_API_KEY` в консоли Anthropic отмечен пределом расхода;
  проверка на сервере, значений не показывает: `grep -c '^CLAUDE_CODE_OAUTH_TOKEN=' scripts/ops/guard/.env` даёт 0;
- при поднятой неисправности класса В в GitHub появляется ветка `guard/…`, а в группе дежурных — сообщение;
- `GUARD_READ_KEY` в запросе к `/reservations` или `/finance/payments` получает отказ (проверяется руками
  один раз после выката);
- мак владельца выключен, а всё вышеперечисленное продолжает работать — ради этого шаг и делается.
