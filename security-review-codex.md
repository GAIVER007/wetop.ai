## 1. Встроенная проверка — навык `code-review`

У Codex это отдельный навык, он так и называется — **`code-review`**.
Набирайте прямо в поле ввода:

```
/review
```

Дальше он сам спросит, что смотреть, и предложит четыре варианта:

| Вариант | Что возьмёт |
|---|---|
| против базовой ветки | разницу вашей ветки с той, от которой отделились |
| незакоммиченные изменения | всё несохранённое, включая новые файлы |
| конкретный коммит | ровно то, что вошло в выбранное сохранение |
| свои критерии | то, что вы опишете словами |

Правки он не вносит — только показывает найденное по убыванию важности.

⚠️ **Это разбор изменений, а не всего проекта.** Для полного аудита
берите промпты из раздела 3 и давайте их агенту в обычном разговоре —
там он видит проект целиком.

Хороший порядок: `/review` перед каждым сохранением состояния,
полный аудит — раз в неделю и обязательно перед выкладкой.

**Аналог GitHub Action из версии для Claude Code у Codex тоже есть** —
автоматическая проверка каждого PR, запроса на слияние правок, прямо на GitHub.
Включается разделом `## Code Review Rules` в том `AGENTS.md`, который лежит
ближе всего к проверяемому коду.

## 2. Своя безопасность: настройки Codex — это тоже поверхность атаки

**Раздел, которого нет в версии под Claude Code, потому что там иначе
устроено.** У Codex безопасность начинается не с кода проекта,
а с того, что вы разрешили самому агенту.

🔴 **Сначала проверьте, какая система настроек у вас включена.** У Codex их
две, и работает всегда только одна. Новая — профиль разрешений
(`default_permissions` и блок `[permissions]` в `~/.codex/config.toml`),
он же закрывает файлы с ключами по имени; разбор в уроке 1.4. Старая —
песочница, про неё этот раздел. Если `sandbox_mode` стоит хоть в одном
файле настроек или вы запускаете Codex с ключом `--sandbox`, Codex берёт
старую песочницу, а профиль разрешений не читает вовсе. Держать обе сразу
нельзя.

📎 «Permission profiles do not compose with the older sandbox settings»:
https://learn.chatgpt.com/docs/permissions — проверено 03.09.2026.

### Два независимых рычага

**`--sandbox`** — что агенту физически разрешено:

| Значение | Что можно | Когда брать |
|---|---|---|
| `read-only` | только читать | разбор чужого кода, аудит |
| `workspace-write` | писать в папке проекта | **рабочий режим по умолчанию** |
| `danger-full-access` | всё | практически никогда |

**`--ask-for-approval`** — когда спрашивать разрешения:

| Значение | Поведение |
|---|---|
| `untrusted` | спрашивает почти на всё |
| `on-request` | решает сам, когда спросить |
| `never` | не спрашивает |

### 🔴 Три сочетания, которых не должно быть

**`danger-full-access` где угодно, кроме одноразовой задачи под присмотром.**
Агент получает доступ ко всей машине. Одна неудачная формулировка задачи —
и он наводит порядок не в той папке.

**`--dangerously-bypass-approvals-and-sandbox`.** Название говорит само
за себя. В справке прямо написано: только для окружений, изолированных
снаружи.

**`never` вместе с `danger-full-access`.** Полный доступ и никаких вопросов.
Это уже не помощник, а незапертая дверь.

### Что ставить

**На рабочем проекте:** `--sandbox workspace-write`,
`--ask-for-approval on-request`.

**Боту на сервере:** `--sandbox workspace-write`,
`--ask-for-approval never` — спросить в Telegram не у кого,
но песочница держит агента в папке проекта.

**При разборе чужого кода:** `--sandbox read-only`.

## 3. Семь целевых промптов

⚠️ **Эти промпты — НЕ для `/review`.** Он смотрит только изменения,
и полный аудит через него даст разбор диффа, который вы примете за разбор
проекта. Ошибка опасная: отчёт будет выглядеть полным.

**Вставляйте их в обычный разговор с агентом** — там он видит проект
целиком. Промпты про код, от инструмента не зависят.

### Промпт 1 — Вход в систему
```
Выступи в роли старшего инженера по безопасности. Проверь аутентификацию:
1. Пароли хешируются надёжно (bcrypt/argon2, не md5/sha1)
2. Сессии имеют срок жизни и гасятся при выходе
3. Подтверждение почты включено для новых аккаунтов
4. Токены сброса пароля одноразовые, живут около часа
5. На входе есть ограничение попыток (не больше 5 в минуту)
6. Секреты входа не попадают в код, который видит браузер
7. Перенаправления после входа проверяются
8. Защищённые маршруты действительно проверяют сессию
По каждой проблеме: в чём уязвимость, где в коде, как чинить.
```

### Промпт 2 — Кто чьи данные видит
```
Проверь все точки доступа к данным. Убедись, что каждый запрос проверяет,
принадлежат ли данные текущему пользователю. Найди:
1. Места, где идентификатор берётся из адреса без проверки владельца
2. Выборки без условия на пользователя
3. Изменение и удаление без проверки принадлежности
4. Открытые точки доступа, которые должны быть закрыты
5. Правила доступа на уровне базы: покрыты ли все таблицы и все операции
По каждой: как получить чужие данные, конкретный фикс.
```

### Промпт 3 — Проверка входящих данных
```
Найди каждое место, где данные пользователя попадают в систему: формы,
точки доступа, загрузка файлов, параметры адреса. Для каждой проверь:
1. Есть ли серверная проверка по схеме
2. Запросы к базе параметризованы, а не склеены строкой
3. Вывод экранируется, нет вставки сырого html
4. Загрузка файлов: проверяются тип, размер, расширение
5. Числовые параметры имеют верхнюю границу
Невалидное — отклонять с понятной ошибкой.
```

### Промпт 4 — Секреты и ключи
```
Просканируй проект на секреты. Проверь:
1. Ключи и адреса баз не вписаны в код
2. Файл с ключами в списке исключений; в файле-образце только заглушки
3. Серверные ключи используются только на сервере
4. Публичные переменные не содержат секретов
5. Платёжные секреты не уезжают в браузер
6. В истории изменений нет ранее сохранённых секретов
7. Токены хранятся в защищённых cookie, не в хранилище браузера
Всё найденное — перенести в переменные окружения.
```

### Промпт 5 — Защита от перебора и ботов
```
Проверь защиту от злоупотреблений:
1. Ограничение частоты на входе, регистрации, сбросе пароля
2. Ограничение на дорогих операциях (отправка почты, обращения к моделям)
3. Защита форм от автоматических отправок
4. Ограничение размера загружаемых файлов и тела запроса
5. Что происходит при превышении: понятный отказ, а не падение
```

### Промпт 6 — Выкладка и наблюдение
```
Проверь готовность к работе под нагрузкой:
1. Отладочные режимы выключены, подробные ошибки не показываются людям
2. Логи не содержат ключей, паролей и персональных данных
3. Есть журнал ошибок и способ узнать о падении
4. Резервные копии базы делаются и восстанавливаются
5. Обновление зависимостей: нет известных уязвимостей
6. 🔴 Открытые наружу адреса не рассказывают об устройстве системы.
   Проверь адрес проверки живости и все служебные страницы: наружу
   не должны уходить имена сервисов (postgres, redis), имя окружения
   (production, staging), версии библиотек и языка, внутренние пути
   и адреса, тексты ошибок от базы. Публичная проверка живости отдаёт
   только статус. Подробную вынеси отдельным адресом, закрытым по сети
   или ключом.
```

⚠️ **Шестой пункт добавлен из живого случая:** открытая наружу проверка
живости отдавала имя окружения `production` вместе с именами сервисов.
Именно это первым собирает автоматический сканер, чтобы подобрать
уязвимости под конкретные версии.

### Промпт 7 — Полный аудит
```
Проведи полный аудит безопасности проекта: вход, доступ к данным,
проверка ввода, секреты, защита от перебора, выкладка.
По каждой находке: уровень опасности, где в коде, как чинить.
Начни с самого опасного. Не чини сам — сначала покажи список.
```

⚠️ Последняя строка важна. **Сначала список, потом решаете, что чинить.**
Иначе агент начнёт править всё подряд, включая то, что вам не нужно.

## 4. Своё задание под разбор изменений

Среди четырёх вариантов, которые предлагает `/review`, последний — **свои
критерии**. Туда и уходит то, что важно именно вам: свои правила
именования, свои запреты, свои болевые точки из прошлых разборов.

Чтобы не набирать их каждый раз, держите файл с постоянным заданием
и просите агента:

> **«Возьми мои критерии разбора из `review-instructions.md` и прогони
> по ним проверку изменений»**

⚠️ Это по-прежнему разбор **изменений**. Полный аудит проекта — промптами
из раздела 3 в обычном разговоре, не через эту команду.

## 5. Чек-лист перед выкладкой

- [ ] Секретов в коде нет, файл с ключами в исключениях
- [ ] В истории изменений секретов нет
- [ ] Вход: ограничение попыток, срок жизни сессий
- [ ] Данные: каждый запрос проверяет владельца
- [ ] Ввод: серверная проверка на каждой точке входа
- [ ] Ошибки людям — без подробностей, подробности в журнал
- [ ] Логи без ключей и персональных данных
- [ ] Резервная копия делается **и восстанавливается** — проверено
- [ ] Есть способ узнать, что упало
- [ ] Режимы Codex: `workspace-write`, не `danger-full-access`
- [ ] Полный аудит пройден, критичное закрыто

## 6. Про 152-ФЗ, коротко

Работаете с персональными данными россиян — они должны храниться
в России. Это про **базу данных**, а не про то, где работает агент.

Отсюда развилка, которую надо решать архитектурно: рабочий контур
моделей из России недоступен, а данные должны лежать в России.
Разделяется контурами — база отдельно, логика отдельно.

⚠️ Это не юридическая консультация. Работаете с чужими персональными
данными — берите юриста, а не гайд из комплекта.

---

## Главное

**Проверяйте результат, а не отчёт.** Агент сказал «уязвимостей нет» —
это не значит, что их нет. Это значит, что он их не нашёл в том,
куда посмотрел.
