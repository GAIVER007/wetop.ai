# tests

| Папка          | Что покрывает                                    |
| -------------- | ------------------------------------------------ |
| `unit/`        | Функции, доменные правила, расчёты денег и дат   |
| `integration/` | API endpoints, БД, адаптеры интеграций (sandbox) |
| `e2e/`         | Playwright, критичные сценарии стойки            |

Инструменты: Vitest (unit, integration), Playwright (e2e). Запуск: `npm test`, полная проверка: `npm run check`.
Прогоны с записью в журнал, что уже доказано на текущем коде и известные грабли — [`TESTING.md`](../TESTING.md):
`npm run test:status`, `npm run test:record -- <unit|integration|e2e|typecheck|lint>`.
Первый тест — `unit/scaffold.test.ts`: пакеты `@pms/*` резолвятся по имени.

## Правила

1. **Red before green** (AGENTS.md §6): новый bugfix или business rule начинается
   с падающего теста. Тест, который никогда не был красным, не считается доказательством.
2. **No real guest data** (AGENTS.md §8, ADR-010): все тестовые гости вымышленные.
   Запрещено копировать реальные ФИО, телефоны, паспорта, email, документы в fixtures.
3. Минимальное покрытие — 80%, включая unit, integration и E2E.

## Один прогон на дерево

`e2e` и `integration` берут **один общий замок на дерево** (`tests/runs/.locks/dev-database.lock`,
`tests/tools/run-lock.ts`): второй прогон любого из них отказывается запускаться и называет набор, pid и
время первого. Замок общий, а не на имя набора, потому что база у них одна и Session pooler Supabase —
один на проект (15 клиентов). Замок от убитого прогона перехватывается, поэтому упавший прогон не
блокирует набор навсегда. Чистых наборов (`unit`, `typecheck`, `lint`) это не касается.

16.09.2026, зачем общий: замок брался на имя набора, `e2e` и `integration` пошли одновременно, ночной
прогон e2e растянулся на 6 часов и упал десятью таймаутами базы («Database did not answer for 30000 ms»,
«Connection terminated unexpectedly», браузер не стартовал за 180 с).

Зачем: 15.09.2026 в одном дереве шли сразу два прогона `e2e` — свой в один воркер и чужой в два. Playwright
чистит `test-results/` в начале прогона, поэтому второй снёс трассы живого первого, и три спека упали с
`browserContext.close: ENOENT … .playwright-artifacts-N/traces/…`; заодно его воркеры заняли койку в чужом
окне дат, и `chessboard-drag` получил «Ячейка 6 уже занята». Поодиночке все три зелёные. Окна дат от этого
не спасают: сторож `tests/unit/e2e-windows.test.ts` сверяет спеки между собой, а не два прогона друг с другом.

## Окна дат: у каждого спека свои сутки

Сквозные тесты создают **настоящие брони на настоящих койках** общей dev-базы. Пока окна дат
пересекались, прогон в два воркера падал то на `unit-blocks`, то на `cancellation-penalty`, а
поодиночке каждый был зелёным: два спека занимали одну койку на одну ночь. Теперь у каждого спека
свой отрезок будущих суток — константа `BASE` рядом с его `plus()`:

| Спек                    | BASE | Сутки от сегодня |
| ----------------------- | ---: | ---------------- |
| `check-in-out`          |    0 | +3 … +6          |
| `desk-day`              |    0 | сегодня … +1 (операции за сегодня; выезд +1) |
| `desk-tasks`            |    6 | +13 … +16        |
| `finance`               |    9 | +18 … +19        |
| `stay-extras`           |   10 | +21 … +24        |
| `chessboard-drag`       |   14 | +26 … +28        |
| `desk-edit`             |   18 | +30 … +31        |
| `print-forms`           |   18 | +33 … +35        |
| `chessboard-unassigned` |   28 | +38 … +46        |
| `cancellation-penalty`  |   28 | +48 … +52        |
| `full-day`              |   28 | +54 … +55        |
| `unit-blocks`           |   18 | +58 … +60        |

Вне таблицы: `web-booking` бронирует на завтра (+1 … +2) — виджет показывает настоящую доступность,
далёкие даты тут не годятся; `manual-reservation` работает на фиксированных 2027-05-10 … 12.

**Добавляете спек, который создаёт брони** — задайте ему `BASE` за последним занятым днём и допишите
строку сюда. Пересечение поймает `tests/unit/e2e-windows.test.ts`: он читает сами файлы спеков и падает,
если отрезки наложились или у спека с `plus()` нет `BASE`.

## Интеграционные тесты и живая БД

**С 14.09.2026 тесты не пишут в рабочие данные (ADR-042).** Integration и e2e работают в схеме `pms_test` проекта
Supabase «hotel» — копии рабочих таблиц (`npm run test:schema`, освежить — `-- --refresh`). e2e поднимает свой API :3101
и стойку :3100; рабочие 3000/3001 под launchd тесты не используют. Первым идёт проект `schema-guard`: API тестов обязан
ответить `database.schema = pms_test`, иначе ни один спек не запускается. Спек с жёстким адресом `127.0.0.1:3000/3001`
(без `??`) в прогон не берётся — адрес API берите из `process.env.APP_API_URL` (с 15.09 так делает и `web-booking.spec.ts`). Окна дат ниже остаются: спеки делят
одну тестовую схему. Сертификация Channex — отдельно: `E2E_CHANNEX_LIVE=1 npx playwright test`.

**Прогон с замком API (по умолчанию с 07.10.2026).** Изолированные сквозные идут вошедшим пользователем: после MV8 стойка production-сборкой без входа не угадывает гостиницу, и прогон без входа проверял бы не тот продукт (решение владельца). Стенд поднимается с `AUTH_REQUIRED=1` и `APP_AUTH_REQUIRED=1`, перед спеками идёт шаг `_auth.setup.ts` — он заводит сотрудника автотестов в `pms_test` (человек вымышленный, ADR-010), кладёт его сессию в cookie стойки и **проверяет, что замок и правда включён**: запрос без токена и ключа обязан получить 401, иначе прогон останавливается (стенд от прежнего прогона подбирается `reuseExistingServer`, и зелёное ничего бы не доказало). Прямые запросы спеков к API идут со служебным ключом заголовком `x-wetop-service-key`. Спек «Неисправностей» входит отдельным вымышленным главным администратором: глобальные неисправности видит только он. Старый прогон без входа только явным отказом `E2E_AUTH=0`; `release-checks` ставит `E2E_AUTH=1` явно. Живой режим Channex (`E2E_CHANNEX_LIVE=1`) не меняется.

**Сколько запросов стоит экран.** Фикстура считает обращения по путям: `GET /__test/hits` отдаёт `{ total, byPath }`, обнуляется вместе с `POST /__test/reset`. Сторож `tests/ui/requests.spec.ts` держит правило «путь с данными — один запрос на показ» и потолок в десять запросов на экран; `/system/freshness` и `/auth/me` исключены (первый браузер опрашивает сам, второй рисуется в двух местах оболочки, а стенд UI работает на `next dev`, где React вызывает рендер и эффекты по два раза). Проверка появилась при разборе «всё тормозит» 16.09.2026: она отвечает на вопрос, лишнее в стойке или в API.

**UI-набор со включённым замком.** Стойку такой, какой она станет после включения замка, проверяет отдельный набор: `npm run test:record -- e2e --config tests/ui/playwright.auth.config.ts`. Он поднимает свой стенд на 3102 и 4313 (`APP_AUTH_REQUIRED=1` у стойки, `FIXTURE_AUTH_LOCK=1` у синтетического API — без сессии тот отвечает 401 на всё, кроме входа и публичных `/a/*`, `/w/*`) и проверяет: без входа любой экран уводит на `/login`, после входа рабочее место открывается, «Выйти» закрывает двери снова. В обычный UI-набор этот спек не берётся — ему нужен другой стенд.

**С 15.09.2026 живая база не обязательна (`plans/tests-without-live-db-2026-09-15.md`).** Пустая схема `pms_test`
заполняется одним из двух способов, `tests/tools/test-schema.ts` выбирает сам: `TEST_DATA=copy` — копия рабочей
схемы `public` (Mac владельца, как раньше); `TEST_DATA=seed` — сид из кода, `tests/tools/test-seed.ts`. Без переменной:
копия, если в `public` есть объект, иначе сид. Сид кладёт настоящий фонд из аудита (88 единиц, 5 категорий, 6 тарифов,
услуги — `project-input/retired-source/audit-2026-09-07/*.md`, гостей там нет) и вымышленное остальное: календарь цен на 150
суток, ~300 броней с придуманными гостями вокруг «сегодня» в Алматы, три брони без ячейки, отмены, незаезды.
Брони идут через тот же импорт, что и настоящие из архивный источник, поэтому счета, платежи и номера в формате архивный источник — боевым
кодом; уборка автотестов их не трогает. Сид детерминирован: одно зерно — одни и те же брони на любой машине.
Занятость держится до +2 суток от сегодня; с +3 начинаются окна спеков ниже, там ячейки свободны.

Поднять тесты на своём PostgreSQL 16 без `.env` и ключей (нужно расширение `btree_gist`):

```bash
DATABASE_URL=postgresql://pms@127.0.0.1:5432/pms_dev npm run test:record -- integration
DATABASE_URL=postgresql://pms@127.0.0.1:5432/pms_dev npm run test:record -- e2e     # плюс npm run build -w apps/web
```

Без браузеров Playwright, но со своим Chromium: `CHROMIUM_PATH=/путь/к/chrome` — конфиг e2e и конфиг главной его подхватят.

`tests/integration` ходит в базу через пулер Supabase. В `vitest.config.ts` это отдельный проект с
`fileParallelism: false`: параллельные PrismaClient вычерпывают сессии пулера, и 11.09.2026 три файла
отвалились по обрыву соединения, просидев 2,5 часа на таймаутах; по одному проходят за ~2,5 минуты.
Запуск только их: `npx vitest run --project integration`.

Брони автотестов e2e занимают ячейки тестовой схемы и убираются `tests/e2e-teardown.ts` после прогона;
вручную для тестовой схемы — `DATABASE_SCHEMA=pms_test E2E_API_URL=http://127.0.0.1:3101 npm run e2e:cleanup`
(без переменных скрипт смотрит в рабочую схему; тестовые брони, попавшие туда раньше, удаляет `cli-purge-test-data.ts`).

**Воркеры e2e (12.09.2026).** По умолчанию Playwright берёт половину ядер (здесь 4). API dev-базы в
Сингапуре отвечает ~2 с на простой запрос, и при четырёх параллельных тестах действия форм (server actions)
не укладываются в 30 с ожидания — срывы «Сохраняю…» без ошибки в интерфейсе. Полный прогон гонять так:

```bash
npm run test:record -- e2e
```

Внутри то же `npx playwright test --workers=2`, плюс лог и строка журнала. 31/31 за 13 минут; в четыре воркера
тот же код дал 9 срывов по таймауту.
