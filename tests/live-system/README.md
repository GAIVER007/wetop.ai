# Проверка коммитов в Supabase

Этот набор выполняется только с отдельным разрешением на тестовые записи в общей базе. Он не входит в обычные unit/UI/e2e-прогоны.

```sh
npm run dev
# В другом терминале, из корня того же проекта:
WETOP_LIVE_AUDIT=1 npm run test:record -- e2e --config tests/live-system/playwright.config.ts --workers=1
```

Не запускать параллельно с другим live-аудитом или `tests/ui`: эти два набора используют один `.next-ui`. Не использовать общую e2e-уборку — она может отменить чужие тесты и отправить ARI.

Требуются приватная `.env` с действующим `DATABASE_URL`, ключом шифрования документов, обычный API на 3001, свободные порты 3200/4320 и цены/свободное место на будущие даты. Секреты не передаются браузеру. Существующие номера, цены, гости и платежи не редактируются.

- Browser 3200 → настоящий Next/server actions → Nest 4320 → настоящие Prisma-репозитории → та же Supabase.
- Конфигурация аудита ограничивает каждый свой процесс одним соединением, чтобы не исчерпать лимит
  Session pooler Supabase, пока обычный API на 3001 продолжает работать.
- Только ARI publisher заменяется перехватчиком без записи в outbox. Ключи внешних провайдеров удалены из окружения тестового backend; фоновые задачи отключены. Команды каналов/сторожа запрещены на 4320.
- Второе соединение Prisma проверяет коммиты. Чтение созданной брони через обычный API 3001 подтверждает общую базу.
- Каждому прогону назначается уникальная метка `E2E-АВТОТЕСТ audit-<uuid>`. Создаются только вымышленные записи; никакие банковские или фискальные операции не выполняются. Платёж — проверка внутреннего учёта на собственном синтетическом счёте.
- Уборка удаляет только записи данного прогона; чужой гость/платёж или повторное использование гостя останавливают уборку. API audit trail остаётся. После сбоя уборки сначала разобрать конкретную метку и ID, не ослаблять проверки и не запускать общую очистку.
- Trace, video и screenshots выключены, чтобы отчёт не копировал существующие гостевые данные из соседних строк. В Git отправляется журнал результата, а не содержимое живой базы.

Проверяются: создание брони и размещения; редактирование гостя, шифрование/удаление синтетического документа; изменение источника и дат; поиск и связанные карточки; отказ при превышении вместимости; начисление, платёж, возврат; отмена и освобождение доступности; блокировка/снятие; сайт аналитики — создание, пауза и удаление.

Не доказывает отправку в OTA, фоновые синхронизации, фискализацию, авторизацию, сохранение сообщений и новые редакторы гостиницы. Они проверяются/реализуются отдельными срезами, без подмены отсутствующей функциональности.
