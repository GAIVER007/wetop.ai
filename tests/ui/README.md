# Изолированные проверки интерфейса WETOP

Это браузер → настоящий Next.js → настоящие server actions → синтетический HTTP API.
Нет подключения к БД, Channex, Telegram, eQonaq или фискальному провайдеру. Синтетические ответы
включены только в отдельный тестовый процесс. Отдельная команда `npm run dev:demo` запускает
маркированную демонстрацию на другом порту; рабочий frontend не подменяет данные при сбое API.

## Запуск

Из корня репозитория после `npm ci` и `npm run generate -w packages/database`:

```sh
npm run test:status
npm run test:record -- e2e --config tests/ui/playwright.config.ts --workers=1 --note "Изолированный UI, без БД"
```

Node 24, установленный Google Chrome, свободные loopback-порты 3100 и 4311.
В окружении с установленным Playwright Chromium можно задать `UI_BROWSER_CHANNEL=chromium`.
Готовый бинарник Chromium другой версии (удалённая среда Claude Code: `/opt/pw-browsers/chromium`) —
`UI_BROWSER_EXECUTABLE=/путь/к/chrome`; после прогона вернуть `apps/web/next-env.d.ts` (`git checkout`), его переписывает `next dev`.
Конфигурация запускает оба процесса и завершает их после тестов; существующие серверы не подхватывает.
Основной `playwright.config.ts` и его очистка живой БД не используются.

Журнал помечает запуск с `--config` как **частичный e2e**. Он доказывает UI-сценарии и передачу DTO,
но не доказывает реальные транзакции, доступность мест, тарификацию, работу провайдеров или production-нагрузку.

## Что проверяется

- Все разделы, карточки, печать; 1440 и 390 px без горизонтального переполнения страницы.
- Задачи дня ведут к счетам; поиск не меняет сводку; обзор без переполнения на 320/768/1024 px.
- Поиск, списки дня, мобильное меню, Escape и восстановление фокуса.
- Шахматка 88 × 30, фильтры, продолжение проживания, перенос выбранной койки в форму брони.
- Создание одиночной и групповой брони: DTO, конфликт, сохранение ввода, успешный переход.
- Профиль гостя и заселение через server actions.
- Распределение одного платежа: отказ, сохранение полей, успешный повтор и новые балансы.
- Отсутствующие записи (404), недоступный API и восстановление кнопкой повтора.
- Новые неисправности из main: принятие, закрытие и отдельное состояние сбоя загрузки.

Скриншоты с вымышленными данными: `reports/hostel-frontend/screenshots/` и `reports/premium-ui/`.
Экраны для дизайн-системы (витрина крайних случаев `showcase` в fixture, светлая и тёмная тема):
`tests/ui/design-reference.spec.ts` → `design/reference/current/`.
Новые проверки покрывают light/dark/system, сохранение темы, ⌘K, меню профиля, сводку,
вкладки и drawer, каталог броней, карточки номеров, сообщения и экран входа.
12 основных маршрутов дополнительно проверяются на 320/390/768/1280/1440/1920 px.
Трассы неудачных прогонов остаются в игнорируемом `test-results/`.


Дополнение разделов гостиницы: 33 маршрута в desktop/mobile (плюс печать), вложенная навигация,
перенос периода и доступной единицы в бронирование, фильтры и пустой отчёт каналов, отказ API,
независимый сбой подключения. Акции/фото/удобства явно обозначают отсутствие редактора.

## Защита от демонстрационных цифр в рабочем интерфейсе

Next dev тестов получает `APP_ALLOW_TEST_DATA=1`. Все fixture-ответы помечены
`x-wetop-data-source: synthetic`, а запросы требуют `x-wetop-test-client: 1`.
Production-сборка игнорирует разрешение тестовых данных и отказывается от такого источника.
Сервер тестов нельзя использовать для обычного preview. При недоступном рабочем API интерфейс
показывает ошибку; нулевые показатели проверяются отдельными пустыми ответами.

Дополнительные проверки: копирование при отказе clipboard; неверный период финансов; отказ
справочника тарифов; изменение уборки, создание/снятие блокировки; очередь изменения цен с
сохранением после отказа; домены/пауза/виджет/удаление/создание сайта; команды Channex и GET-проверка
соединения без команд; отсутствие данных отдельно от отказа API. UI-команды Channex здесь
обрабатывает только fixture — внешние сервисы не вызываются.

## Отдельная локальная демонстрация

Общий HTTP fixture находится в `scripts/preview/fixture-api.ts`; тестовый entrypoint импортирует его.
Демо использует порт 4312, заголовок `x-wetop-demo-client` и источник `demo`; тесты — 4311 и `synthetic`.
Демо разрешено только при `NODE_ENV=development`, явном `APP_DEMO_MODE=1` и точном loopback-адресе.
Тестовые reset/failure endpoints в демо недоступны. Состояние временное, часть команд эмулируется
только для UI-проверок; реальные бизнес-правила проверяются отдельными unit/integration наборами.

54 сценария в полном изолированном наборе. Проверка axe: 38 маршрутов × две темы ×
1440/390 px, а также все четыре вкладки открытой карточки в этих же состояниях.
Новые регрессии проверяют повреждённые и повторяющиеся query-параметры, сохранение полей
после отказа, блокировку повторной команды, согласованность идентификаторов и отсутствие
ссылок на несуществующие страницы демонстрации. Ни одно правило axe не отключено.
